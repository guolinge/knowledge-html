有五条规矩返工最多，先看完再动手：

详见「多会话协作」一节。开工前跑 npm run status，收尾跑 npm run done。

🧭

这个 skill 最常犯的错，是回答了一个用户没问的问题。

用户说「画个架构图」，你画了架构图 —— 但他真正想的是「理解这个项目」。 架构图只是他以为的入口。结果他看完发现到处缺前置知识，你一路补窟窿。

所以先读「第 0 步」。它比后面所有步骤加起来都重要。

🩸

第二个最常犯的错：把原文的文字搬进 HTML，然后配几张插图。

用户手上本来就有文字版（飞书文档、博客、代码）。他来找「图解」， 要的就是文字表达不了的那部分。你把段落换个排版搬过来，交付价值是零。

它的来源是这条被误读的规矩：

图是稀缺资源，只有卡点值得画图。

「卡点优先」是排序问题，不是取舍问题。卡点先画、画细； 其余的照样要画，只是可以画轻一点（cards / compare 也是图）。

真正的判据在「原则 ①」。 每次交付前还要过一遍「复盘 ⑦」。

平台优先级 · 宽屏是主场

knowledge-html 主要在电脑宽屏上阅读。移动端能打开就有价值，但不是和宽屏同级的设计目标。 遇到取舍时，按这个顺序决定：

优先级 先保证什么
① 图和交互的完整性 关系、状态、信息量和完整操作链不因屏幕变窄而删减
② PC / 宽屏体验 以 1280px 视口判断图是否清楚、交互是否顺手、画布是否充分利用
③ 移动端安全降级 页面能打开、正文能读、关键内容可到达；不追求一屏看全和触屏精修

一张图是不是太密，只在 1280px 宽屏下判断。 如果它在宽屏下清楚、只在手机上拥挤， 那不是图太复杂，也不是拆图或删内容的理由。窄屏优先用局部横向滚动、最小画布宽度、缩放， 或者提示「复杂图解建议在宽屏查看」。

🖥

400px 不是第二套设计稿。

不要为了手机一屏放下而删节点、隐藏关键标签、把空间关系图改成普通卡片， 也不要把一个丰富的交互缩成几个简单按钮。图义和交互完整性高于移动端排版。

窄屏的合格线是：页面不被遮死、正文可读、关键控件可到达、 宽图能通过滚动或缩放看到完整内容。做到这里就停。

外壳和内容分开处理：目录、遮罩、正文排版继续做基础响应式； 复杂图和交互可以保留桌面画布，不必强行折成竖屏版本。 只有用户明确要求手机使用时，才把移动端提升为完整设计目标。

原则 ① · 图是这个产品的本体，不是配图

判据只有一句话：这一段描述的，有没有「空间 / 顺序 / 状态 / 归属」？

这段文字在说什么 该用什么
谁指向谁、谁包含谁、谁和谁并列 tree / flow / arch
先发生什么、后发生什么、谁在等谁 seq / lane-stack / flow
某个东西从 X 变成了 Y journey / flow（shape: pill）
按时间演进 timeline
几个东西按维度对比 compare / matrix
同一条轴上多种方案的差异 demo 控件
纯因果论证、经验判断、取舍理由 文字。这是图替代不了的

反直觉的那一条

「原文里已经有一段文字在解释它」不是不画图的理由，恰恰是该画图的信号。

理由很直接：那一整段文字用户已经读过了。你再搬一次，他得到的是同一份信息换了个字体。

反过来，一段文字如果只有在这里才说得清（比如「为什么用链表而不是数组」）， 那才是真正该留给文字的东西 —— 因为它是个判断，不是个结构。

什么样的东西不该画

这条是防「机械执行」的。下面三类留在文字里是对的：

情况为什么留文字例子
清单式的操作步骤①②③④ 之间没有空间关系，画成图反而要多绕一层「分配 pid → 分配资源 → 初始化 PCB」
真正的判断和理由它回答的是「为什么」，不是「长什么样」「PCB 是有限的，申请不到就直接失败」
一句话的过渡和结论它本来就是用来断句的「到这里是五个状态」

这条规矩和「图是稀缺资源」怎么共存

说法什么意思
「只有卡点值得画图」❌ 这句话把优先级当成了门槛，结果 60% 的内容退回文字见一次删一次
卡点优先，其余照画✅ 卡点画得深、配交互；其余的用 cards / compare / 一张小图带过

一张 cards 也是图。 判断标准不是「这算不算大图」， 而是「读者扫一眼能不能拿到结构，不用逐字读」。

原则 ② · 整体图

有的问题，把零件一个一个讲是讲不清楚的。

比如「容器到底是什么」。它不是一个对象 —— 内核里没有叫「容器」的东西。 它指的是一个进程，加上挂在这个进程上的几样东西：一组 namespace、一个 cgroup、 一个 rootfs。这几样任何一样单独讲，都得不出「容器」这个词的意思。 得把它们摊在同一张图上，读者才看得出它们怎么凑成那个概念。

这类图叫整体图。它回答的不是「一个东西怎么工作」，是「这一堆东西彼此什么关系、 各属于谁」。

用户的原话：

假如我比较熟悉进程，那么画一个整体图，我很快就能把进程和 socket 的联系和区别 记到脑海里。

什么时候要它

读者要理解的 用什么
一个东西怎么工作（一条链怎么走） flow / journey / seq。拆开讲更清楚，不要画整体图
一堆东西彼此什么关系、各属于谁 整体图
读者已经熟悉其中一个零件，要把它接到别的零件上 整体图，加一个入口（见下面「入口」一节）

具体说，这三种情况一定要画：

  • 一个概念被当成「一个东西」，其实是一组东西。 容器是典型。 只讲 namespace、只讲 cgroup，都推不出「容器」是什么。
  • 一堆名词散在正文各处，读者记不住谁属于谁。 比如 fd 表、监听 socket、 连接 socket、TCP 协议栈、就绪队列、调度器 逐个都讲过， 但读者拼不出它们的关系。
  • 要回答「A 和 B 有什么联系和区别」。 这种问题得让两边同时在场。 讲完一个再讲另一个，读者接不上。

反过来，只想讲清一条链怎么走的时候别画整体图。它零件多、线多， 读起来成本本来就高，用来讲一条链不划算。

四种关系，四种画法

整体图最容易犯的一个错：把四种不同的关系全画成箭头。

关系 它回答什么 怎么画
分类 这东西属于哪一类 带，当背景
包含 这东西在谁里面 框套框
1 : N 一个变出几个 基数标记。一个东西被 N 个共用时，只画一条边
流动 谁把东西给了谁 箭头

分类当背景，不等于它不重要。「用户态 / 内核态」「硬件 / 软件」「控制面 / 数据面」 这些分类本身就是理解的一部分，而且常常就是读者已经认识的那个锚点。 只是当主角它撑不住：分层只说明「它属于哪一类」，说明不了「它和谁有什么关系」。

⚠

踩过的坑。 容器那篇里，「容器 = 进程 + namespace + cgroup + rootfs」 被画成了 进程 → namespace → cgroup → rootfs 一条链， 读起来像「进程导致 namespace，namespace 导致 cgroup」。

这四样是并列挂在同一个进程上的，谁也不导致谁。正确的形状是从进程散开， 不是串成一条。

判断的办法：把每条边读一遍，问「这条边代表什么关系」。说得出来（指向、导致、 然后、属于、包含）就留着；说不出来、只是因为想让它们排成一列， 那就是排版边，删掉换积木。

这和「原则 ⑥ · 表格是排版，图是表达空间关系」是同一件事， 只是整体图零件多，更容易不自觉地拿箭头当排版用。

一张图只装一个主角

整体图的主角是四种关系里的哪一种，一篇图只能选一个，其余的要么不画、 要么退成背景。

主角 该突出的 该退到背景的 例子
包含 框套框 带 宿主机 ⊃ 容器 ⊃ 进程
流动 箭头 框 网卡 → 内核 → 进程 → 代码

C4 模型的第一条原则也是这个意思：一张图只装一个层级，不混抽象 （Context 图里不出现 Python 类）。

可读性有红线

一张图的元素数有个经验上限，大约 12~15 个。超过之后读者的注意力会散， 一眼扫不完就得来回找。整体图容易超，所以要拆：

  • 零件超过 15 个左右，拆成两张，别硬塞
  • 光看零件数不够，还要看线的密度。15 个零件配 12 条线可以，配 40 条线一定糊
  • 拆开之后每张反而更好读，因为它各自变成了一条故事线
  • 拆的判据：如果一张图里有两条边在讲不同的事（一条是「谁创建谁」， 另一条是「谁唤醒谁」），它们本来就该是两张图

最坏的做法是把线藏起来 —— 压到框底下、调低透明度，让它看着不乱。 线还在那里，读者找起来更费劲，而且这么做不会报错。见复盘 ⑧。

入口：从读者已经知道的那个东西出发

整体图零件多，从哪儿开始看是它自己的问题。用户那句话给了答案：

「假如我比较熟悉进程」

给几个「我熟悉 ___」的按钮。点了，就把那个零件和它的直接邻居点亮，其余淡出。 之后点任何被点亮的零件，它就变成新的中心，邻域跟着走。 读者就是这样一步步把不熟的东西接到熟的东西上的。

这和原则 ③ 里「画到读者已经认识的锚点」是同一件事的两种用法。 那一条讲画布上的位置：这条链最后那个东西，读者是不是已经认识。 这一条讲进入图的方式：读者不需要认识全部零件才能开始看。

原则 ③ · 关键图要有信息量，「把名词摆一遍」不算图

反例长这样：一个框，标题「共享资产」，副标题「代码段 · 堆 · 文件描述符表 · 线程共用」。

那不是图，那是带框的目录。它只告诉你有这么几个名词， 没告诉你它们在哪、多大、怎么摆、什么时候变。

一张图的信息量分三层

层次图里有什么同一个概念的三种画法
名词❌ 只是列名字「代码段 · 堆 · 文件描述符表」
结构在哪、多大、谁挨着谁、朝哪长在地址空间里从高到低排开：栈向下长、堆向上长，中间夹着 mmap 区
机制✅ 关键图至少要到这里栈随线程走、堆随进程走；pthread 栈 8MB 定死，goroutine 2KB 起步自己长

判据：把正文全部盖住，只看这张图 ——

  • 它能回答一个「为什么」吗？
  • 它给出了「多大 / 多少 / 在哪」这类具体的量吗？
  • 换一个尺寸或数量级，这张图会变吗？（不会变 = 它只是个名字列表）

三条都答不上来，就是名词层，重画。

从「一段文字」到「一张丰富的图」，中间那截信息从哪来

这是这个 skill 里最容易出问题的一步，也是用户点名说过的一条：

你是从少量文字然后画一个丰富的图嘛，中间你是需要补充信息的。 然后这信息呢，如果你 100% 从你知识库里面肯定是对的，你就使用； 如果你不肯定的话，你就得使用联网搜索。

门槛是「我确不确定」，不是「这张图重不重要」。 不确定就查，跟它是不是关键图无关 —— 因为你在图上写下的每个数字都会被读者当真。

你手上的信息怎么做
100% 确定（教科书级常识）直接用。比如「x86-64 用户空间是 47 位」
想起来是这样，但说不出出处联网查。这就是「不肯定」的判据
数字 / 版本 / 上限 / 默认值一律查。这类最容易被记成错的
机制（「因为…所以…」）查，或者去读代码。推出来的机制最危险，因为它看着最顺
⚖

「不肯定」的自我判据只有一条：能不能说出出处。

「我记得栈是 8MB」—— 说不出出处 → 查。 「Go 的 _StackMin 是 2048」—— 能说出是 runtime/stack.go → 可以用。

这和「复盘 ①b」里那条是同一个东西： 写下「因为…」之前，问自己「我是读到的，还是推出来的？」 推出来的，就得回去查。

这一次的真实对照（画「进程 vs 线程」那张图）：

只照原文画 查完之后
一个框：共享资产 =「代码段 · 堆 · 文件描述符表」 整张虚拟地址空间：内核空间 / 三块线程栈 / mmap 区 / 堆 / BSS / 数据段 / 代码段，带地址和增长方向
「线程共享文件描述符」 查完发现 fd 表根本不在地址空间里 —— 它在内核的 files_struct。原文那句话本身没错，但塞进「内存布局」这张图里就是错的
栈大小没提 Go _StackMin = 2048 字节起步；pthread 默认 8MB 且定死

中间那一列，全部来自联网查，不是从原文推的。

怎么查：用什么语言、信谁、用哪个工具

上面说「不确定就查」。但怎么查是另一回事 —— 这一节补三个具体的决定。

① 默认英文查，而且中英一起搜

原理、标准、数字、报错 —— 一律先英文。

理由是一手的资料基本都在英文那边：内核文档、RFC、POSIX、各家官方 docs、 GitHub issue 和源码。中文内容大多是转述，而转述会丢限定条件。

🩸

一个真实的例子（查 OverlayFS 的合并规则）：

中文的两份材料都说「上层文件盖住下层」。照着画出来的图会说 ls /etc 只能看到上层那几个文件。

换成英文去查内核文档，第一条就是：

If a name refers to a non-directory in either layer, the lower object is hidden.

「非目录才隐藏」—— 这句话把目录排除在外了。 目录是合并的。

那两份中文材料不是写得差，是转述时把限定条件丢了。这就是二手信息的固有损耗。

场景 用哪种 为什么
原理 / 标准 / 规范 英文 一手资料：内核文档、RFC、POSIX、W3C
数字 / 默认值 / 上限 / 版本行为 英文 这些只在一手资料里是准的
报错信息 英文 把报错原样贴进去搜，命中率最高
国内产品的行为（飞书、微信、阿里云） 中文 官方文档只有中文
中文社区特有的约定 中文 比如面试题对概念的划分方式

不知道英文怎么叫的时候，先搜「<中文名> 英文」拿到对应词，再用那个词深挖。 例：快表 英文 → TLB → 再搜 TLB flush context switch。

② 写进笔记时，用原文的术语

查证用英文，行文用原文的术语 —— 读者要能对得上他手上那份原文。

第一次出现时括号附英文，之后就不用了：

快表（TLB）          ← 原文叫「快表」，读者是照这个词对上原文的
阻塞挂起（blocked-suspend）
只读层（read-only layer）

不要因为「英文更准」就把正文里所有术语都换成英文。 那是拿查证语言替换行文语言， 读者会更难对上原文。

③ 认来源：一手 / 二手分两档

档次哪一类怎么用
一手kernel.org · docs.*.com · RFC 编号 · github.com/<org>/<repo> 的 issue 和源码用它定事实
二手个人博客、教程、问答站、另一个 AI 的回答只用来找线索和关键词，不用来定事实

看一条到手的信息属于哪档，有个快办法：它有没有提到限定条件。

「上层盖住下层」是一手的说法吗？不是 —— 一手说的是「非目录才隐藏」。 带限定条件的说法通常来自一手，不带的那种多半是转述时被磨平了。

③b 能跑就别推；方案与代码不一致，按代码算

源码也是二手 —— 哪怕是写得很认真的设计文档。文档描述的是当时打算怎么做， 代码是实际怎么做。两者分叉是常态，不是例外。

手上有什么怎么做
本地有能跑的代码直接跑一次，把真实值打印出来 —— 比读源码还硬一等
本地有源码但跑不动读实现，别推。看它返回什么类型、抛什么
只有一份设计文档按文档写，但标清楚「这是文档说的」

实战代价：一篇拆「SQL Builder 四步」的笔记，输入输出表是照设计文档写的， 其中一格写成「一段 WHERE 片段 + 绑定值列表」。实际跑一遍才发现：

文档说 代码是
某一步「输出还是一份 DSL」 那个函数的返回类型是 void —— 什么都不返回
编译产出「片段 + 绑定值列表」 对外只给字符串；{sql, bindings} 是更内层、且只在需要再包一层时出现的中间物
有个错误码叫 DISABLED_REF 那个码在包里出现 0 次

三处全是“读着很顺、实际不存在”的类型 —— 它们不会报错，只会让听众当场提问。

怎么跑：内部包通常在 node_modules/.bin/ 里有 tsx，可以直接 import 源码里的 .ts：

npx --no-install tsx /tmp/probe.ts    # 里面用绝对路径 import 目标包的 src/*.ts

探针放 /tmp 也行（和前面的探针不同 —— 那些要看相对路径的 CSS）。 区别是：这里只 import 模块、不渲染页面。

④ 三个工具，分工不同

工具 什么时候用
web_search 还不知道该信谁的时候，铺开找。给它 2~4 个不同角度的 query，别只搜一条
source_check 手上有一个具体断言要验。它会返回 passage 级的引文 —— 正好喂给「复盘 ①b」那条「回源码核实」，而且引文是可以贴进笔记 sources 的
fetch_content 已经知道是哪一页，直接读它（比如那一页 overlayfs.html）。也能用 mode: answer 让它只根据这一页回答问题

更狠的一条：关键图要画到「读者已经认识的锚点」为止

上面说信息量分三层（名词 → 结构 → 机制）。但对调度 / 流转 / 加工这一类概念， 还有一层更高的要求，用户的原话：

我需要它一个任务线程，要把 CPU 画出来，然后上面有几个核心也画出来。 然后任务线程是怎么穿过、怎么利用 CPU 核心的这个管道我想画出来。 任务是怎么排队、队列长什么样、用户态调度器在哪、最后的结果是怎么样的，也画出来。

我需要一个丰富的图去理解它，落实到一些具体的结构上， 让我感受到「原来它现实中是这样经过的」，在硬件上它是这样表现的。

翻译成可操作的五条：

① 画到底，不许停在半截

任何一个「东西从 A 流到 B」的概念，链条要一路画到最后那个物理部件：

输入 → 在哪排队 → 谁在挑 → 执行者 → 落在哪块物理资源上 → 结果长什么样

停在中间（比如只画到「少量线程」就收笔）就是半截图。

🔌

判据：这条链的最后那个东西，读者是不是已经认识？

停在一个「读者还不认识的抽象」上，就是半截图。

最常见的锚点是物理的，因为它人人都认识，不会骗人：

物理锚点 · CPU 核 · 内存条 · 磁盘 · 时钟 · 网卡 · 光电信号

但物理不是唯一的一类。 下面这些都算落地：

锚点类型 例子
物理部件 落到「4 个核里有 3 个空着」
生活经验 落到「饭堂三个窗口只开了一个」
读者用过的东西 落到「一个 git 仓库的 .git 目录」
本篇前面已经定义过的概念 第 2 节讲过「页表」，第 5 节就能拿它当锚点

最后一行很关键：锚点是相对的，不是绝对的。 「页表」对刚翻开这篇的人是抽象，对读完第 2 节的人就是锚点。 所以判断的是「读到这里的人认不认识」，不是「外行认不认识」。

② 容器要画出「容量」

队列不能画成一个写着「队列」的框。要画成一排看得见的格子：

  • 有几格
  • 现在装着什么
  • 满了 / 空了往哪去

这三件事画出来，「排队」这件事才成立。 写一个「队列」的框，读者只能记住这个词。

③ 通道要画成「一条通路」

「任务怎么利用核心」要画成从线程穿到核的那条线， 而不是在箭头旁边写一个词（submit、多路复用）。

读者要能顺着线走一遍。 标签是注解，线才是路径。

④ 状态要落在图上，不要落在图下面那句话里

哪个在跑、哪个在等、哪个核空着 —— 这些是结果。

结果要能从图上直接看出来（颜色 / 虚实 / 标注）， 不能靠下面那段文字告诉他「所以有些核会闲着」。

⑤ 有「层」的概念，每层要标出「谁的地盘」

用户态 / 内核态 / 硬件是三个不同的世界。谁在哪一层、 跨层的时候发生了什么（系统调用 / 中断），是这类图最容易丢的信息。

一条终极判据：能不能顺着这张图讲一个 30 秒的故事

「六个任务排在队列里 → 用户态调度器一次挑一个 → 交给三条线程 → 三条线程占住三个核 → 剩下三个核从头到尾闲着。」

能讲出来 = 图到位了；讲不出来 = 还缺东西。 照着这句话回头补图，缺什么补什么。

注意这个故事里的每一个名词 —— 任务、队列、线程、核 —— 读到这里的人都认识。只要有一个不认识，故事就卡住了，那张图就还没落地。

反过来的做法会怎样
画到「少量线程」就收笔读者知道有这回事，但想象不出它长什么样、在哪儿发生补上 CPU 和核
队列写成一个框「排队」变成一句需要相信的话，而不是看见的事实画成一排格子
通道只写一个词读者拿不到「谁穿过什么、往哪去」的路径感画成线
结果写在图注里图只负责输入，结论全靠文字 —— 那要图干什么让结果在图上可见
🏗

积木画不了这种图的时候，要做积木，不要缩减表达。

这就是原则 ⑦ 说的四条路（组合 / 加字段 / 新建积木 / raw）。 实践中真的会出现「现成积木都装不下这个形状」的情况 —— 那个时刻不要去削内容，去加工具。

这次为了画地址空间加了 memmap，为了画 GMP 到核的拓扑， 又发现 flow 的箭头承载不了「排队 → 收敛 → 铺开」这种漏斗形状。

顺带一条：别让画布空着

五个节点铺在 1400px 上，四周全是空白，读者会先看到「空」再看到节点。

症状怎么办
几行节点、大片留白往图里加信息，不是把图放大。缺的通常是「量」和「方向」
节点的 sub 只有 2~4 个字那是标题，不是说明。把机制写进 sub
同类节点长得一模一样差异化 —— 谁共享谁独享、谁大谁小、谁先谁后，都该在图上有痕迹
一句话概括得了整张图那它就不该是图。改成 callout，把版面让给真正需要画的东西

原则 ④ · 讲透卡点，不是搬运内容

你的任务不是「把内容搬进 HTML」，是「把用户卡住的那个环节讲透」。

用户粘过来的原文通常有 60% 是铺垫、重复、客套。原样搬进去只会得到一个更长的、 仍然看不懂的页面。用户要的是图和交互 —— 这是 HTML 相对纯文本唯一不可替代的价值。

所以：先找卡点，再决定画什么图，最后才写文字。

不是搬运式讲透式
结构照着原文分段按「卡点」重新组织
篇幅原文多长就多长砍到骨架，该删的删
图配几张插图把讲不清的地方变成图或交互
判据「内容都在了」「用户看完能说出所以然」

原则 ⑤ · 先对齐理解层次

同一份材料，不同的人卡在不同层次。写之前先判断读者在哪一层。

概念  →  组织 / 层面  →  架构
是什么    怎么组织      代码怎么实现
  • 概念层：这个领域有哪些词？每个词对应现实中的什么？
  • 组织层：这些概念怎么被组织成一个整体？
  • 架构层：代码怎么实现它？

判断方法：读者说「没接触过」「完全不懂」「看不懂」「有点抽象」 → 他卡在概念层，从最具体的场景和真实数据开始，不要从架构开始。

概念层的三条硬规矩

❌ 不要 ✅ 应该
出现类型名 / 类名 / 文件名 用业务词汇 + 真实数据举例
「输入是 X 树，输出是 Y」这种抽象定义 「运营要发券给最近 7 天加购的 VIP」这种场景
直接上表结构 / 字段名 先给一行真实数据长什么样

类型名是架构词汇，不是概念。 概念层出现 XxxTree / XxxStruct / XxxBuilder 这类东西就是劝退。

概念讲清楚了，读者自己会问「那为什么需要写个库」—— 那时才进组织层。

一个自检方法

写完开头，问自己：一个完全不懂这个领域的人，读完前三节能说出「这东西是干嘛的」吗？ 说不出就是概念层没写够。

原则 ⑥ · 表格是排版，图是表达空间关系

最容易犯的错：用表格的思维做图。

表达什么 用什么
表格 / 卡片 并列的、离散的信息 compare cards spec
图 空间关系：东西在哪、怎么流动、状态怎么变 lane-stack flow journey timeline

判断方法：

  • 只能用「第一行是 X，第二行是 Y」描述 → 表格
  • 能用「A 指向 B」「A 变成 B」「A 和 B 汇合到 C」描述 → 图
⚠

spec 是拆解卡，看起来像图，本质还是两栏文字。

它适合速查（10 个文件各是什么、6 个依赖各是什么）， 不适合讲机制（这个东西怎么工作）。讲机制一定要画图。

讲机制的正确顺序

用户的原话：「先介绍概念，让我对概念建立认识；再用图把概念连起来。」

  1. 拆成 3~6 个原子概念，每个概念一两句话
  2. 每个概念配一张图 —— 不要吝惜图，几张十几张都行
  3. 概念讲完再上交互 —— 让用户亲手跑一遍

反例（错误做法）：直接上「输入 / 处理 / 输出」的表格，用户看完还是不知道它怎么工作。

原则 ⑦ · 积木是词汇，不是语法

画图是为了让用户理解内容、思想、设计、意图。怎么好呈现就怎么来，不要拘泥。

lane-stack / journey / compare … 这些积木的作用是 让你不用每次从零写 CSS，不是限制你能表达什么。

⚠

最危险的失败模式：读完积木清单，然后把内容硬塞进最接近的那一个。

结果是「合规但没讲清楚」—— 比不画图更糟，因为看起来做了工作。

表达不顺手时，四条路，按优先级：

优先级 做法 什么时候用
1 组合 现有积木拼一拼就能表达（大多数情况）
2 加字段 方向对但缺一个能力。例：给 demo 加 html 字段支持自定义布局
3 新建积木 同一类表达反复出现（见 references/extend.md）
4 raw 直接写 HTML/CSS 一次性排版。这是合法选择，不是投降

判断标准只有一条：

这样呈现，用户能不能秒懂？ 而不是「这符合积木规范吗」。

theme.css 的变量（--tone / --surface / --border / --blue …）随你用， 深色模式自动跟着走。唯一底线：不写死色值，否则换肤会坏。

交互也一样：demo 积木的 html 字段可以放任意自定义控件， WIDGETS 注册表里加一个函数就行。别因为「没有现成控件」就放弃一个能讲清楚的交互。

工作流

第 0 步 · 判断：用户要的是「一个点」还是「一个面」

不要看到【图解】就开始画图。先判断用户要的是哪一种。

用户的说法 他要的是 你怎么做
「这个函数干什么」「A 和 B 有什么区别」「这段代码为什么这么写」 一个具体问题的答案 直接跳到第 2 步
「理解这个项目」「搞懂这一章」「从零学 X」「理解 X 的架构」 一条理解路径 必须先走第 1 步

判断信号：用户说的是「一个点」还是「一个面」。 说「面」的时候，不要急着产出内容，先产出「脉络」。

⚠

用户说「给我架构图」不等于「我只需要架构图」。

他可能是想「理解这个项目」，而架构图只是他以为的入口。 直接给架构图，他会发现到处都缺前置知识，然后东补一块西补一块。

不确定时，直接问：一句「你是想快速要一张图，还是要从零搞懂它？」 能省掉后面好几轮来回。

第 1 步 · 梳理知识树（只在「一个面」时做）

1.1 画一棵「要理解什么」的树

理解 X
├─ ① 业务背景 —— 为什么需要它、解决什么问题
├─ ② 概念    —— 有哪些词、每个词对应现实中的什么
├─ ③ 组织    —— 它由什么组成、怎么分类
├─ ④ 架构    —— 它怎么工作
├─ ⑤ 设计取舍 —— 为什么这么设计、不这样会怎样
└─ ⑥ 代码细节 —— 具体到文件 / 模块 / 函数

每个节点标三样：

标什么 为什么 例子
依赖 理解它之前必须先理解谁（决定顺序） 依赖: ②概念
深度 概念 / 组织 / 架构 / 代码（决定详略） 深度: 架构
产物 值得单独一篇，还是并入上一篇（决定切分） 产物: 单独一篇

1.2 这棵树是递归的

⚠

六层不是某个项目的专属结构，而是「理解任何东西」的通用结构。

所以每一层里的模块，只要大到需要单独理解，就要自己再走一遍这六层：

理解一个 Web 框架
├─ ① 业务背景
├─ ② 概念
│   └─ 中间件 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它是什么、为什么需要
│       ├─ 组织：有哪几种（普通 / 错误处理 / 路由级）
│       ├─ 架构：next() 怎么把它们串起来
│       └─ 细节：代码在哪
├─ ③ 组织
│   └─ 核心包 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它负责什么
│       ├─ 组织：由哪些文件组成
│       ├─ 架构：怎么工作
│       └─ 细节：路由 ──────→ 再递归一次！
├─ ④ 架构
├─ ⑤ 设计取舍
└─ ⑥ 代码细节
💡

所以产物不是「一篇 HTML」，而是一棵嵌套的、互相链接的产物树。

每篇笔记对应树上的一个节点，节点之间有 needs 关系（前置依赖）。 读者沿着树走，每篇开头都写清楚「读这篇之前需要知道什么」。

1.3 判断一个节点要不要单独成篇

单独成篇 并入父节点
它有自己的概念要解释 它只是父节点的一个属性
它大到需要分几节 一两段能说完
其他节点会引用它（是别人的前置） 只有父节点用到它

用最后一条最准：一个节点被别的节点 needs 引用了，它就必须独立成篇， 否则读者会被迫跳进另一篇的中间去找。

1.4 梳理时不断拷问自己

这一步是 AI 拷问自己，不是拷问用户。 每个节点问四个问题：

  1. 要理解这个节点，读者必须先知道什么？那个前置知识在哪一层？
  2. 有没有循环依赖？（A 需要 B，B 又需要 A → 拆法有问题，要重新切）
  3. 哪些是可以推迟的细节？（不放进第一轮）
  4. 有没有用户已经知道的？（他的背景里已经有了，跳过）

1.5 和用户确认

把树给用户看，问三个问题：

  1. 这个脉络对吗？有没有多余的、有没有漏的？
  2. 顺序对吗？
  3. 先做哪一块？
✅

确认脉络花的 2 分钟，能省掉后面来回补窟窿的 2 小时。

用户看到树之后，往往能立刻指出「这块我已经懂了」「这块才是重点」—— 这些信息你猜不到。

1.6 最后才决定产物切分

一棵树 ≠ 一篇文档，也不等于 N 篇。

按「一块能独立读懂」来切：

  • 前置知识自足的一块 → 一篇
  • 太短的合并
  • 太长的再拆
  • 每篇开头写清楚「读这篇之前需要知道什么」
⚠

跳过这一步会怎样？

读者每看完一篇就发现「这里缺一块」，于是回头补；补的时候又发现另一块缺，再补。 好几轮来回，全在补第一轮就该规划好的窟窿。

根因：把「用户要的产物」当成了「用户的目标」。 信号：如果用户连续三轮都在问「那 X 是什么」，说明第一轮就该梳理脉络。

1.8 树是边写边长的，不是一次画完的

⚠

第一次读代码，你只看得见「结构」，看不见「哪个分支信息量大」。

信息量是在写的时候才暴露的 —— 写到某一节发现「这里塞不下」， 那说明它是一个新节点。

真实例子（写「方言篇」时遇到的）：

写到「17 个方法逐条对照」这一节，遇到 getStringArrayRule：

  · 它不在 SqlDialect 接口里，而在 utils.ts 里按 dbType if/else
  · 它有 ByteHouse / Doris / MySql 三个分支
  · 它还要一个 columnType 参数（array / string）
  · 它只在 relation.ts 一处被调用
  · 它和接口里的 jsonArrayContainsRule 是**两套并存的机制**
  · 它里面有 MySql 分支 —— 说明写于「还支持三个库」的年代

  → 这一节写不下。==它不是「方言层的一个方法」，它是一条独立的架构裂缝。==

1.8.1 什么时候该长出新节点

写作时的信号意味着什么怎么办
「这里得先说清 X 才能讲 Y」X 是 Y 的前置给 X 一个节点，加进 needs
「这一节写了三段还没讲完」它大到需要分几节给它一个节点
「这个分支和主线不是一回事」它是旁路给它一个节点，或并入已有的旁路节点
「这个词在别处也会用到」它会被别的节点 needs必须独立成篇
「这里和前面某一节重复了」两个节点边界划错了合并或重新切

1.8.2 怎么维护

✅

每写完一篇，回头改一次 plans/<topic>.yaml。

  • 发现新节点 → 加进去，填 needs 和 blurb
  • 发现两篇重复 → 合并，把 artifact 指到同一处
  • 发现某篇太大 → 拆成两个节点
  • 写完了 → status: drafted

plan 不是「开工前画的图」，是一直在改的施工图。

⚠

但要克制。 不是每个「写不下」都要开新篇。

先问：它能被别的节点 needs 吗？

  • 能 → 独立成篇（否则读者要跳进另一篇中间找）
  • 不能，而且只有父节点用它 → 就是父节点的一节，写长点没关系

新节点要有「别人也需要它」这个理由，不能只是「它挺大」。

第 2 步 · 找到卡点

用户可能明说（「Flink CDC 和 CDC 有什么区别」），也可能没说（只粘了一篇文档）。

没说的时候，从这些信号里找：

  • 原文里篇幅最长但最抽象的那一段
  • 用户加粗、划线、单独贴出来的部分
  • 出现了三个以上并列概念的地方
  • 流程/链路类描述（「先…然后…再…」）
  • 任何反直觉的结论

一句话：卡点通常是「需要读者在脑子里维护状态或追踪顺序」的地方。

第 3 步 · 拆骨架

把内容切成 3~7 个 h2 章节，每章回答一个具体问题。

写之前先问自己：如果只留 5 段，留哪 5 段？ 其余的删掉。

如果走过了第 1 步，骨架直接来自知识树的节点，不用重新想。

第 4 步 · 逐段过一遍，决定画哪些图

这一步不是「挑几个重点画图」，是「把每一段都过一遍」。

做法：把骨架里的每一段读一遍，对每一段问一句 ——

这一段描述的是「空间 / 顺序 / 状态 / 归属」吗？ 是 → 它为什么还是文字？

命中就画。判据和反例见「原则 ①」。这一步的产出是一张「哪几段要画图」的清单， 而不是「挑三个卡点」。

下面的表是起点，不是清单。找不到合适的就改积木、拼组合、或自己画（原则 ⑦）， 别把内容削足适履地塞进表里 —— 但也别因为「没有现成积木」就退回文字。

原文里出现的是 用什么 为什么
「先 A，再 B，然后 C」的链路/分层 lane-stack 顺序用文字描述，读者要自己排队
有分支或汇合的流程 flow 一条直线讲不了「分两路再合起来」
「某东西从 X 变成了 Y」 journey 状态变化是文字最大的盲区
三个以上方案/概念的横向对比 compare 表格比排比句快十倍
一堆没有先后关系的并列概念 cards 用文字排会很平，卡片能一眼扫完
「2020 年…2022 年…」的演进 timeline 时间顺序需要视觉锚点
调用链、握手过程 seq 参与者 + 消息顺序 + 自动激活条 + 时间段框
决策定位（重要度 × 紧急度） matrix 两维定位用表格看不出来
类层次、目录树、对象嵌套 tree 层级关系需要缩进感
反直觉的点、坑、一句话结论 callout 需要跳出正文节奏
正例/反例清单 checklist 勾叉比「应该/不应该」直观

陷阱：拿箭头当排版用

规则表告诉你「并列的概念该用 cards」，但真正会犯的错不是选错积木， 而是积木挑对了、箭头却多画了。

↗

几个并列的东西（一个结构体的成员、一个容器的几项属性、同一层的几种选择）， 被一条条边串起来 —— 读起来立刻变成「A 导致 B」或者「先 A 后 B」。

我犯过一次，被用户当场指出来。 原因很具体，值得记：

我想让三个并列的成员待在一个 groups 框里、排成一列， 而 flow 只给「同一列且首尾相连」的节点画那个框 —— 于是就顺手补了两条空边，纯为了布局，没有任何语义。

struct sock 下面挂着：接收队列 / 发送队列 / 连接状态
它们完全并列  →  却画成了  接收队列 → 发送队列 → 连接状态

换 tree 就对了：它用缩进和肘形线，天然表达归属而不是先后， 节点还支持 tone（可以把「两条队列」染成同一个色）。

你其实想说 别用 用
这几个东西都属于 X flow + 空边 tree
这几个东西并列对比 flow + 空边 compare
这几个东西是一份清单 flow + 空边 cards

自检：把每条边读一遍，问自己「这条边代表什么关系」。

  • 说得出来（指向 / 导致 / 然后 / 交给）→ 留着，空 label 不是罪 （一条 ①②③④ 的链，边不带标签也成立，因为你仍然说得出那个「然后」）
  • 说不出来 → 它就是排版边。删掉，或者按上表换积木。

顺带一条：别拿节点当旁白。「从这里开始分叉」这种话不是一个东西， 它是一个过渡句。把它做成节点、再用箭头指过去，等于在图里插了一句正文 —— 该写在图外面。

第 5 步 · 决定哪里必须做成交互

判据：用一句话说不清「A 和 B 差在哪」，但让用户亲手跑一遍就秒懂 → 做 demo。

典型：轮询 vs CDC、乐观锁 vs 悲观锁、B+ 树插入 vs 删除、 不同隔离级别的并发异常。

写 demo 需要三步（详见 references/blocks.md）：

  1. assets/app.js 的 WIDGETS 里注册一个控件函数
  2. 在 note.md 里用 demo 积木声明外壳和分栏
  3. 两边靠 log 这个 key 对接

如果只是顺序，别做交互，画 lane-stack 就够。 交互有成本，只在「静态图讲不清」时才用。

第 6 步 · 写 note.md

cd ~/works/codes/knowledge-html
npm run new -- <slug>          # slug 用小写英文连字符，如 mysql-index-internals

然后编辑 notes/<slug>/note.md，填 notes/<slug>/meta.json。

积木的完整语法见 references/blocks.md， 可运行示例见 notes/blocks-cheatsheet/note.md（写之前先读一遍）。

meta.json 填什么

没挂树的笔记，记得填 topic。

「未归类」区默认按主题分组，分组轴就是 meta.json 里的 topic：

{ "topic": "Flink" }
⚠

为什么不用 tags 分组？

因为这个仓库的实测数据（2026-09-30 快照）：
11 篇未归类笔记 51 个标签（去重 37 个）
每篇平均 4.6 个标签
覆盖 ≥2 篇的标签 只有 11 个

而且大标签是横切的 —— 一篇「算子和函数」的标签是 Flink · 算子 · StreamOperator · 状态 · Checkpoint， 按标签分组它要出现在 5 个组里，反而比平铺还乱。

标签适合筛选（首页已经有标签 chip 了），不适合分组。 分组要单一归属。

写 topic 的三条规矩：

规矩 为什么
一篇一个 它是单一归属。多归属会让同一张卡片重复出现
写得像人话 它是给人看的分组标题，不是给机器匹配的 key
≈ 3 篇一组最舒服 一组一篇也能接受，但超过七八组就该合了
做法好处代价
用 topic 显式标注分组干净、名字可控新增笔记时要记得填
用 tags[0] 当主标签不用填首标签是随手写的，会出「架构」这种只有 2 篇的大类
按 eyebrow 分组不用填实测 19 种值 / 28 篇 —— 一篇一个，根本归不了类

不填 topic 的会落在「其他」组里 —— 不会报错，也不会丢， 但别人就看不出它属于哪一块。

⚠

上面那几张表的数字是快照，会漂。

笔记每加一篇，标签数、平均数、未归类篇数都在动。 别把它们当成长期有效的判据 —— 要看的是那个方向： 「标签数远多于笔记数」「多数标签只覆盖一篇」。

真要引用具体数字时，像这里一样标上快照日期。

第 7 步 · 校验、构建、量图

npm run check              # 先校验。会指出第几行哪个积木有问题
npm run view -- <slug>     # 构建 + 在浏览器打开
npm run visual-check       # 无头浏览器真的去量每个积木有没有溢出

但真正的回路是「写完一块就看一块」

npm run block -- <slug> --list    # 这一篇有哪些块（编号 + 行号 + 语言）
npm run block -- <slug> 3         # 只看第 3 个块：截图到 /tmp/kb-<slug>-3.png + 打开
⚠

写完一整篇才第一次看图，是最贵的错。

一篇 22 个积木的笔记，问题会一次性暴露，然后每个都要单独一轮 「改 → 构建 → 截图 → 看」。实测：22 个积木、19 张截图、8 个问题。

所以写图的时候不要往下写 —— 停一下，跑 npm run block 看一眼。

npm run check 必须过。它报的每一类问题都对应一个真实踩过的坑：

  • 积木名拼错 → 会静默退化成普通代码块，页面看着正常但图没了
  • YAML 语法错 → 定位到文件和行号，并回显原始内容
  • 缺 quiz → 违反本仓库约定（见「硬约束」）
  • 源码里写了裸的 <script> / <style> → 积木会把裸 HTML 原样输出，而 script 是 raw-text 元素，没有 </script> 时浏览器会把后面整篇文档当成脚本文本吃掉。 表现是「那之后的图连线全空、demo 控件全不挂载」，而构建和 check 都不报错。 用反引号包起来就对了。
⚠

构建通过 ≠ 画对了。 这条踩过五次，每次 npm run check 都是绿的。

改了样式之后必须跑 visual-check，再截图看一眼。

但它量不了「挤不挤」

⚠

visual-check 判的是有没有重叠（TOL = 2px），不是读起来顺不顺。

真实例子：一张 flow 上有两条边标签，横向间隙 9px —— 检测器判 ✓， 但两条语义不同的标签读起来像一句（「只能进「值」的位置 决定这支行不行」）。

只影响「值」      决定行不行        ← 间隙 9px，检测器过，但读着像一句

所以「检测器过了」不等于「这图好看」。还得自己看一眼。

一个实用的经验判据：把相邻的标签连起来读一遍。 如果读成了一句有语义的话，就该把其中一个改短（或删）。

绿灯是怎么做到「真的对」的

visual-check 不只看溢出。它还会查这些所谓「渲染出来但不是你想的那样」：

查什么 不查会怎样
flow 的边有没有穿过无关节点 看着像流程真的从那个节点走过
边标签有没有压在节点上 字被框挡住
两个边标签有没有叠在一起 叠成乱码（「podmup.pod重建down」）
有没有真的画出来 绘制抛异常 → 空 SVG，而布局检查全绿
控件自己拼的几块之间有没有留白 没套那层带 gap 的 wrapper → 四块紧贴着，而所有检查都是绿的

⚠️ visual-check 曾经会串页 —— 真凶是共用的临时文件

于是：

会话 A 写入 crowd 的页面
会话 B 写入 core-rule 的页面      ← 覆盖掉 A 刚写的
会话 A 的 Chrome 加载 file://…/.vc-tmp.html   ← 读到的是 core-rule 的页面

A 的探针忠实地量了 core-rule 的图，然后把这些结果记在 crowd 头上。 整个过程没有任何报错。

🧱

两条要记住的：

① 任何写临时文件的工具，路径必须带 PID 或随机后缀。 一个「全局唯一」的临时路径，在单会话时代永远是对的， 在多会话时代永远会串 —— 而且不报错。

② 一个省事的约定（软链 node_modules）制造了一份跨会话的共享可变状态。 推荐一个约定的时候，要顺手想一想它把什么东西变成了共享的。

③ 这条规矩修完要全仓库搜一遍：后来又踩了第二次 —— visual-check.mjs 当时修好了，但 block.mjs 的预览页还写着固定路径 node_modules/.block-preview.html，两个会话同时跑 npm run block 时， 我截到的第 N 块是另一个会话的第 1 块（截图上的行号和我这一篇对不上）。 修好一处不等于修好这一类；「临时文件」这个字符串要在 tools/ 下 grep 一遍。

修完之后的判定规则（ATTEMPTS = 3）仍然保留 —— 噪声还在，只是不再是主因：

三次的结果 判定
任一次干净 ✅ 通过。中途挂过就报一条 ⚠ 第 N 次才通过（不阻塞）
三次都挂、诊断一样 ✗ 真的，阻塞
三次都挂、诊断不一样 ⚠ 负载导致，不阻塞
三次都没拿到数据 ✗ 阻塞（探针自己坏了）
⚠

看到 ⚠ … 检查不稳定 或 ⚠ 三次的诊断不一致 时别忽略。

它不阻塞推送，但那篇笔记的检查不可信。等负载降下来重跑 —— 如果同样的位置还在，那才是真问题。

已知问题基线：tools/visual-baseline.json

有些问题不是笔记写错了，是积木画不了（例如 flow 画不了「阶梯 + 公共出口」）。

情况会怎样怎么做
不在基线里的问题✗ 阻塞推送去修笔记
在基线里的问题⚠ 报出来但不阻塞不用管，或者重画图
基线里已不成立的条目✗ 阻塞推送删掉那条 —— 基线只能变小
⚠

加基线之前先问自己：这是「作者写错了」还是「积木画不了」？

写错 → 修笔记，别加基线。基线不是绕过检查的口子。

第 8 步 · 交付前的九次复盘（复盘清单）

改稿多轮之后内容一定会「长歪」。每次都有具体动作，不是「再读一遍」。

复盘 ① · 术语审计

用任何术语前，读者知道这是什么吗？

把正文里的代码标识符列出来，看哪些没在概念章节出现过：

grep -oE '`[A-Za-z_][A-Za-z0-9_.]{2,}`' notes/<slug>/note.md | sort -u

判断标准：术语如果在「定义它」之前就被使用了，就是堵塞点。 处理：在开头加一个「先搞清几个词」的章节。

复盘 ①b · 数字和事实回源码核实

凡是写进文档的数字，都要回源码数一遍。

手边没有源码、只能靠查的时候，怎么查（用什么语言、信哪些来源、哪个工具干哪件事）， 见 principles.md 里「原则 ③」的「怎么查」一节。 那一节还讲了一件事：二手转述会丢掉限定条件 —— 这正是下面这类事故的根因。

真实事故：文档里写「这个接口有 14 个方法」，实际 17 个。 同一个错误在架构图、正文、速查表里各出现一次，三轮都没人发现。

⚠

但光数数字不够 —— 机制也要核。

第二个真实事故：文档里写「countSql 包一层是因为展示列会 LEFT JOIN 出重复行」。 数字都对、术语都对、句子通顺 —— 但机制是编的。

回源码一看，两个错：

我写的 事实
展示列会 LEFT JOIN 出重复行 展示列根本不参与 countSql，它用的是 uidsSql
包一层才数的是人不数行 包一层不会去重；而且这里也没有东西需要去重

怎么发现的？别人看了图觉得不对，去问了一圈才确认。 靠外部反馈才发现，说明自己那一轮核实是缺的。

两类要核的东西，别只核第一类：

写下的东西长什么样怎么核
数字「14 个方法」「1700 行」「5 种类型」grep -c / wc -l —— 命令一跑就知道
机制（因果关系）「包一层因为…」「校验分两段是因为…」把那条代码路径读出来，看它到底会不会那样
💡

机制比数字危险，因为它看着更有道理。

数字错了读者会怀疑（「真的 17 个？」），但机制错了读者会信 —— 因为它语法通、逻辑顺、还带着解释力。

判别方法：写下「因为…」之前，问自己「我是读到的，还是推出来的？」 推出来的，就得回去读。

容易写错的几类数字：接口方法数、文件行数、枚举取值数、调用点数量。

grep -cE '^\s+[a-zA-Z]+\(' <接口文件>     # 数方法
wc -l <文件>                              # 数行数
grep -c '^\s*[A-Z_]* =' <枚举文件>        # 数枚举值

数字错了比文字错了更危险 —— 读者会信数字，而且不会去数。

复盘 ② · 每个概念必须配例子

⚠

只给定义不给例子，等于没定义。

「软删除是一种标记删除的机制」—— 读者完全不知道那是什么。

每个概念至少给三样（以「软删除」为例）：

给什么 例子
一句话定义 「删除时不真删，只打个标记」
长什么样（最重要） { id: 7, deleted_at: '2026-03-01 10:00:00' }
和相邻概念的区别 「普通删除是行没了；软删除是行还在，查询要额外加 where deleted_at is null」

用 cards 的 code 字段放例子最省事。

复盘 ③ · 小白通读

假装你只能看到这份 HTML，看不到任何代码。 从头读，每段问：

  • 这里出现的词，我前面见过定义吗？
  • 「它」「这个」指代清楚吗？
  • 这张图 / 表，不看正文能理解吗？
  • 有没有结论来得太突然的地方？

记下所有卡住的位置，回到原文补。

复盘 ④ · 结构复盘

改过三轮以上，目录一定会乱。

grep -nE '^#{2,4} ' notes/<slug>/note.md

检查四件事：

检查 典型症状
层级 某个 h3 其实是上一个 h3 的下级，却平级了
归属 内容跑到了别的章节（A 的讲解跑进了 B 里）
顺序 先讲「怎么工作」后讲「由什么组成」
编号 改稿后编号重了或跳号
💡

读者的路径应该是：这是什么 → 由什么组成 → 怎么工作。 先看零件清单，再看零件怎么配合。

复盘 ⑤ · 篇幅复盘

改过几轮之后，篇幅一定会往「好写的方向」歪，不是往「读者需要的方向」。

真实数据（写 notes/insight-dsl 那次）：

  94 行   03 · 走一遍完整编译
 136 行   04 · 三段管道        ← 读者来这篇就是找它
 256 行   05 · 三处反直觉的设计  ← 最大的一节
 177 行   07 · 怎么保证它是对的  ← 第二大的

读者最想看的那节只排第五，而「测试」排第二。

根因不是偷懒 —— 是「反直觉」「测试」这类内容每一点都能独立成段，好写；而「怎么工作」要讲清一条链上的每一步，难写。写着写着就歪了。

一条可操作的判据：

假想意味着什么篇幅应该
把这一节整段删掉，读者还能理解主题吗它可删 → 是边角料短
删掉之后主题就讲不明白了它是主线最长

半小时能做完的度量：

grep -nE '^## ' notes/<slug>/note.md

把每节的行数算出来，排一下序。如果最大的一节不是「怎么工作」，就是歪了。

重写之后：

 435 行   04 · 三段管道        ← 是第二大的两倍多
  78 行   06 · 怎么保证它是对的  ← 从 177 压到 78
⚠

「抽出来的内容」看着比主线重要，是因为它独立成节了。

insight-dsl 那篇单列了一节「三处反直觉的设计」，256 行。 但那三处（include/exclude 写法、派生字段、权限下推）本来就在「拼 SQL」里面。

抽出来之后两头都亏：

  • 主线缺了细节，变得单薄 —— 读者看完「三步管道」还是不知道每一步具体干什么
  • 细节离开上下文，读起来像三个孤立的知识点

只有「主线讲完之后的延伸」才该独立成节。从主线里抽出来的，要并回主线。

复盘 ⑥ · 语气审计

写完通读一遍，按这张表查。这些都是真实踩过的：

症状 例子 改法
破折号过多 「第二段不重新检查空列表——那是第一段的职责」 拆成两句，或换逗号
对话腔起手 「结论：用 Knex」「补一句容易搞错的」「用一句话验」 直接说内容
辩护腔 「但要说清楚：这不是「必须要」。」 删掉整句 —— 那是讨论过程
提醒腔 「注意它只改变排版」「其实」「必须」 删掉这两个字
排除式论证 「这不是 X，而是 Y」 读者没听过 X。直接说 Y
编排说明 「三条理由，按重要性排：」 直接列，不用报幕
元叙述 「这一节的每一处，只看代码都看不出为什么」 那是写给你自己的
加粗过密 一段里五个 ** 全篇加粗数应该是个位数
⚠

一条总的规则：文档只陈述「是什么」和「不这么做会怎样」，不写「我为什么没选另一个」。

后半句是讨论过程，不是文档该有的东西。 它是对话里说给对方听的，落到文档里就变成了辩护。

可查的量化（写完对着 grep 一遍）：

grep -c '——'  notes/<slug>/note.md     # 目标 < 5
grep -c '\*\*' notes/<slug>/note.md     # 目标 < 20
grep -c '注意\|其实\|必须\|唯一' notes/<slug>/note.md   # 目标 0

复盘 ⑦ · 图解缺口审计

这是和复盘 ⑤ 并列的最重要一步，因为它直接决定「这份东西为什么存在」。

做法：把正文里所有描述「空间 / 顺序 / 状态」的句子捞出来，逐条问一句「它为什么还是文字」。

# 把这些「叙述性信号词」全 grep 出来 —— 命中的每一行都是缺口候选
grep -nE '先|然后|接着|之后|最后|变成|指向|包含|位于|上一层|下一层|依次|交替' notes/<slug>/note.md \
  | grep -v '^\s*[0-9]*:\s*[|>#]'

命中之后，按三种情况处理：

情况怎么办
确实在讲顺序/位置/状态补图。优先用现成积木；没有合适的就按原则 ⑦ 的四条路走
是个判断或理由（「为什么不用 X」）留着。这是图替代不了的
是操作清单（①②③④）留着。它没有空间关系，画成图更绕

还有一个更快的自检：写完一篇之后，把所有的 ``` 围栏块和正文段落分别数一遍。

grep -c '^```' notes/<slug>/note.md          # 图/积木用了多少个
awk 'BEGIN{n=0} /^```/{f=!f; next} !f && NF && $0 !~ /^[#>|-]/ {n++} END{print n}' notes/<slug>/note.md

正文段落数 ÷ 2 就是「多少段配一张图」。 如果这个比值大于 3，回头看看是不是有几段该画没画。

第二条检查：关键图的信息量（原则 ③）。

逐个打开这一篇的图，问三句：里面有没有「量」？有没有「方向」？盖住正文它还讲得通吗？ 答不上来的那张，回去查原理重画。

🧭

一次真实的返工：有人指出「红框里这几段为什么不用图 —— 我们不就是图解吗」。

那几段讲的是：程序和进程的关系（一个文件 → 若干进程）、 A 等盘时 CPU 去跑 B 再被中断叫回来、轮询到中断驱动的演进。

三样都是标准的「关系 / 顺序 / 时间线」，全都该有图。

根因是被误读成门槛的那句「只有卡点值得画图」。 现在那句话说清楚了：卡点决定先画哪张，不决定画不画。

复盘 ⑧ · 别用画法掩盖密度

整体图读不懂时，第一反应往往是「怎么把线藏起来」，而不是「线是不是太多了」。

真实事故：一张 15 个零件、13 条边的整体图，密密麻麻。我的处理是 把线画在零件框底下（这样擦碰看不到）、调低透明度、聚焦时才显示。 看起来「能跑」，视觉检查也是绿的 ——

但它没有解决任何问题：线还在那里，只是从「看得见的乱」变成了「看不见的乱」。 而用户的反馈恰恰是同一件事的两面：他说「线在乱飞」「又是重叠」， 工具（archify 的校验器）说的是「边穿节点 / 交叉 / 微段」—— 这是同一个抱怨。

🎭

判据：你做的这个改动，是让图更清楚了，还是只是让它更不容易被挑错？

  • 调间距、拆成两张、把并列的东西从箭头串改成扇形 → 更清楚
  • 把线压到框底下、调低透明度、只在聚焦时显示 → 更不容易被挑错

第二种不是优化，是掩盖。而且它不会报错 —— 检查工具和肉眼都会被骗过去。

真正的解法几乎总是「改图的结构」：拆开、少画、把关系画成它本来的形状。

这一条不只适用于图。 凡是「改一改让它看着没问题」的动作，都要先问这一句。

复盘 ⑨ · 照着自己写过的规矩做

这一条比 ⑧ 更难受：规矩早就写在 skill 里了，我没照做。

真实事故：拿挤在一起的网格布局去试 archify，失败了三次。 三次都得出结论「它画不了这个」—— 分别是「画不了分层带」「框不能嵌套」「只能自己写」。

三条全错，而且 两条的正确写法就写在 skill 自己的「结构化图」那节里：

我说「它不行」 skill 里早就写着
画不了分层带 boundaries 包住一行的节点就是带
框不能嵌套 （这条 skill 里没写，是真缺 —— 已补）
— 「写法参考 ~/.agents/skills/archify/examples/*.<type>.json」

而那个 examples/ 目录里，第一个架构图例子就是正确用法：

"layout": null,
"clients": { "pos": [38, 300] },
"edge":    { "pos": [230, 300] },     // 每步 200px，手工写死的像素坐标
"gateway": { "pos": [430, 300] }

我一次都没打开过那个目录。

🔧

顺序应该是：

  1. 先用参考实现自己的例子证明「这工具能做这件事吗」
  2. 再证明「我能让它做这件事吗」—— 照它推荐的用法来
  3. 两条都试过还不行，才轮到「自己写」

跳过第 1、2 步直接自研，代价是把自己重新踩一遍那个领域几十年的坑。

判断「该不该自己写」也要有证据：「我试了它的正确用法，它确实做不到 X」 才算证据；「我试了三次没调通」不算。

这一条的代价：因为跳过它，我手写了约 200 行布局 + 布线代码， 然后在上面连续修了七八个几何层的经典 bug（端口落在错的一侧、跨带通道借到画面外、 坐标基准搞错、量完坐标再改高度）—— 而这些正是布局引擎几十年专门在解的问题。

第 9 步 · 交付后的自我反馈

⚠

每次交付完，回头问一遍：刚才哪一步慢？哪一步反复来回？

这一步不是「再读一遍稿子」—— 那是第 8 步。

这一步看的是过程，不是内容： 我在跟工具较劲的地方，就是下一个会话会再较一次劲的地方。

关键区分：

发现的问题改哪里例子
内容问题（这一篇讲错了 / 漏了）改这一篇「卡点图没画」「概念没配例子」
工具问题（跟内容无关，但耗了时间）改工具，然后把改进写回这份 skill「截图被截断」「要手动关标签页」

工具问题不会自己消失。 你不写回来，下一个会话的 agent 会一模一样地再踩一次 —— 而它甚至不知道自己踩了，只会默默地多花二十分钟。

十个信号：出现就是在提示「工具该改了」

信号说明什么怎么办
同一条命令跑了 >2 次才过工具一次没把话说清，只能试探让它在第一次就把原因和修法打全
一个积木看了 3 次截图还没对这个形状它画不了换积木 / 拆两张图 / 真的画不了就进 visual-baseline.json
手算坐标、猜尺寸、硬填数字积木缺自动测量加测量，别手填 —— 手填的数字换个屏就错
反复「改 → 构建 → 截图 → 看」反馈回路太长缩短它（npm run block 就是为这个加的）
绕过了工具（手写 HTML、手动裁图、自己写脚本）工具的边界差一点把绕过的那个动作变成工具的一个参数
产生了要手动收拾的东西工具默认行为不对改默认值，别靠人记得加参数
同类内容手写了三遍它是个新积木见 references/extend.md
文档说的和工具做的不一致文档在骗人改一边 —— 通常是文档
并行会话改坏了同一个文件共享文件缺约定把约定写进「多会话协作」
同一个坑，同一篇里踩了第二次规则写在了错的地方把它挪到用它的那一节旁边，别让它躺在文档末尾
代码写了吗、页面上也有，但看着就是不对（挤、偏、少一块）静默的渲染问题 —— 没有报错，只有眼睛看得出来给探针加一条检查，别指望下次还记得看

真实案例：这条规矩是怎么来的

🧱

一根一根点掉标签页。

写 notes/insight-dsl 那次，跑了二十几次 npm run block。 它每次都 open 一个浏览器标签 —— 而 agent 看的是截图文件，标签页对它毫无用处， 纯粹留给用户收拾。

挨个点掉之后，用户提出来才改：默认不打开，人要看时加 --open。

按上面的表对，它是信号 ⑥：产生了要手动收拾的东西。

图的视觉规范

图的「丑」通常不是配色问题，是结构太单一。四条规矩：

① 节点用语义类型，不要纯文字盒子

用 kind 标出节点是什么（backend / database / cloud / security …）—— 它会自动带图标和配色。读者看图标就知道这是数据库还是服务，不用读文字。

② 用区域框表达归属

几个节点属于同一个 VPC / 同一个部署单元 / 同一层？用 groups 圈起来。

💡

「结构单一」的最大来源就是没有区域框。 平铺的节点看不出「谁和谁是一伙的」，读者要自己在脑子里分组。

③ 开背景网格

grid: true。给图「工程图纸」的质感，也让大片空白不那么飘。

④ 边要有语义

  • 同步实线、异步虚线 —— 别混用
  • 关键路径用 tone 上色（比如绿色的 HTTPS、红色的鉴权）
  • 每条边都该有标签（协议、动作、方向），除非两端完全自明

⑤ 文字不许互相压

用户点名过的一条，原话：

你在画图的时候要注意文字互相重叠的情况。 线可能你判断线的重叠比较有难度，但判断文字重叠应该比较轻松，对吧？ 尽量不要出现文字被挡到的情况。

为什么单拎出来：字被压住不会报错，字还在，只是读不通。 它比「图没画出来」隐蔽得多 —— 出图看着是成功的，只是有一行字废了。

最常见的成因只有一条：标签比它所在的那条缝还宽。

   ┌──────────┐            ┌──────────┐
   │  节点 A   │   这条缝    │  节点 B   │
   └──────────┘            └──────────┘
        └──── 标签比缝宽就压到框上 ────┘

flow 里还有一种固定搭配会撞：群组框的标签画在框的左上角， 而边标签默认落在那条缝的水平中点 —— 缝一窄，两个标签就叠在一起。

修法按优先级：

修法 说明
调节点位置 让缝变宽（改 row，或把节点拆开）
edges[].labelDx / labelDy 手动把边标签挪开。工具算不出「那里已经有群组标签了」，但作者一眼就知道该往哪挪
把标签改短 最后手段。别为了塞下标签而把话说残
🤖

这条已经进了探针，不用靠眼睛。

npm run visual-check 会报 文字压文字：「…」↔「…」（重叠 Npx）。 它用 Range 取每个文本节点自己的墨迹矩形（不是父元素的盒子）—— 父盒子带 padding、跨行时是一整块，都会把「挨着」误判成「压着」。

改完图一定要跑它。构建通过 ≠ 画对了，这条踩过五次。

⚖

不查什么：文字被线 / 边框穿过。

那要判断「这条线是不是本来就应该在那儿」—— 机器判不了， 人工排查的成本也高于收益（用户原话：「如果是线和文字重叠，排查比较费时间的话，就不用管了」）。

所以探针只查文字 vs 文字：这条能机械判定，而且它才是真的读不通。

结构化图：调用 archify skill

archify 是一套完整的图渲染系统，能力超出我们自己的积木：节点的语义类型 （声明是 database / messagebus / cloud，自动带图标、配色和图例）、精确区域框、 真边路由，以及一个会量文字宽度、检测碰撞的校验器。

我们自己的积木是「半自动」的 —— 你给 row，它排位置，不做标签避让和碰撞检测。 两套工具各管一段，按图的形状选。

它能画 5 种图

由 spec 里的 diagram_type 决定（tools/archify.mjs 会自动读）：

diagram_type 画什么 结构数组
architecture 系统组成、部署拓扑、依赖关系 components · boundaries · connections
workflow 跨角色的流程 lanes · phases · mainPath · nodes · edges
sequence 调用链、握手、时序 participants · messages · activations
dataflow 数据流水线 stages · nodes · flows
lifecycle 状态机、生命周期 lanes · states · transitions

写法参考 ~/.agents/skills/archify/examples/*.<type>.json。

什么时候该调 archify

用 archify 用我们自己的积木
有区域/边界要表达归属（「这几个在同一个 VPC」） 没有归属关系，就是一根轴或一列卡片
节点有语义类型（这是数据库、那是队列） 节点就是纯文字盒子
需要图例 不需要图例
形状是 DAG / 状态机 / 泳道 / 时序 / 阶段流水线 形状是时间轴 / 状态对照 / 两列匹配 / 行列表
要作为独立图交付、反复引用 图文混排成一节，要跟着页面换肤和重排

画整体图（原则 ② 的做法层）

判据在「原则 ② · 整体图」那节，这里只讲做法。

一 · 用手工坐标，间距给足

整体图读不了的头号原因是「挤」。 用 pos 手工摆，相邻零件 横向约 200px、纵向 100~150px 起步。挤在一起的网格布局必然让线绕来绕去。

{ "components": [
    { "id": "clients", "pos": [38, 300],  "size": [150, 56] },
    { "id": "edge",    "pos": [230, 300], "size": [150, 56] },
    { "id": "gateway", "pos": [430, 300], "size": [150, 56] } ] }

参考 examples/production-deployment.architecture.json（12 零件 / 4 框， 就是这个尺寸感）。注意它顶层没有 layout。

二 · 四种关系分别怎么表达
关系 用什么 注意
分类 boundaries 包住一行的节点 当背景，别当主角
包含 boundaries 嵌套 —— 成员集合包含 = 框套框，外层框自动比内层大 不用手工算层级
1 : N 边上写 label: "1 : N" 一个东西被 N 个共用时只画一条边，别画两条
流动 connections 跨行的边显式写 fromSide / toSide
🔢

「一个东西被 N 个共用」只画一条边 —— 这条不只是省地方。

画两条会有什么问题：第二条必然横穿第一个容器，校验器直接报交叉。 而且两条边说的是同一句话。

写 1 : N 那个标记，信息一样，风险归零。

三 · 一张图一个主角 + 元素数红线
  • 主角只能一个（包含 / 流动 / 分类），其余的退成背景 —— 见原则 ②
  • 零件 超过 ~15 个就拆图，别硬塞；线太密同样要拆
  • 拆的判据：如果这张图里有两条边在讲不同的事，它们本来就该是两张图
四 · 拆完之后，先看它自己的校验过不过

tools/archify.mjs 会先跑 archify validate，不过就不出图。它报的 edge-through-node / proper-crossing / micro-segment 是硬门， 不是风格建议 —— 见下一节。

它的硬边界（踩过）

  • 边不能穿过无关节点。 archify 直接报 crosses component "xxx" (unrelated to this relationship)，它不会帮你绕过去。 遇到这种拓扑只能拆图、改布局、或手填 route/via 航点。

  • 竖长的分层图别用 architecture，用 lane-stack。 .archfig svg { width: 100% } 会把 SVG 拉满容器宽度 —— 一张 745×1483 的「五层堆叠」图放进 1280 宽的正文里，会变成 2549px 高， 文字被放大到很夸张。archify 适合宽高比接近 1:1 的拓扑图，不适合一列到底的层叠图。

    这次画「谁能看见谁」（CPU / 内核 / 进程 / runtime / G 五层）就撞上了， 改用 lane-stack 一次过 —— 它本来就是为「一层接一层」设计的，横着排，不拉高。

  • architecture 有两种排法：写 layout（网格），或者给每个组件写 pos。 两条路二选一，都不写才报错：

    Component "x" must include pos [x, y] when layout.mode is omitted

    排法怎么写什么时候用
    网格顶层写 layout，组件只写 row / col零件少、排得规整
    手工坐标顶层不写 layout，每个组件写 pos: [x, y]整体图用这个 —— 官方 examples/production-deployment.architecture.json 就是这么写的

    这条原来写的是「必须写 layout」，是错的 —— 而且正是它把我带到沟里： 我照它用网格模式去排一张密集的整体图，挤成一团、校验不过， 然后得出「archify 画不了整体图」的结论。其实该走的是另一条路。

  • 组件尺寸是每个显式声明的（默认 120×60），不随 layout.cellW 变。 标签长了要么裁文案，要么给它加 size。

  • label / sublabel 里不能写我们的行内标记。 archify 不解析 == ** ++， 它会原样显示成 **它不干活**。它只认自己的 meta.legend。 写进去之前先把标记去掉。

  • 跨行的边要显式写 fromSide: "bottom" / toSide: "top"。 上下相邻两行的节点，自动推断可能给出 fromSide: "left"，然后报 first segment does not honor inferred fromSide "left" —— 错误里说的方向和你看到的走向对不上，直接写上 bottom/top 最省事。

  • boundaries 里的 kind 只有 region 和 security-group 两种， 而 security-group 画出来是红色虚线框。红色在别处一律表示「出事了」， 知识图里没有这个含义，默认用 region。

  • 边有几何下限：微段短于 8px、两条边挤在同一条走廊里，都会判失败。

  • 嵌套的 boundary，两层标签会叠在一起。 外框和内框包的是同一批零件时， 它们的上边界只差 pad 之差。外框的 pad 又被限制在 34px 左右 —— 再大就报 extends outside the viewBox，而且加大 meta.viewBox 不管用 （它按成员的实际footprint 判，不看你写的 viewBox）。

    出路的反直觉之处：把内框的 pad 收紧（pad: 10），而不是把外框撑大。 这样两层标签能差出 24px 左右，够放下两行字。

  • 产出是静态 SVG，不跟着容器宽度重排。

  • lifecycle 的 lane 语义是写死的，别拿它画通用状态机。 render-lifecycle.mjs 里写死了：lane: main → 上排「阶段带」（5 列，y=126）、 lane: terminal → 下排「结局带」（3 列，y=450）、其它所有 lane 全挤在中间那条 「事件带」（只有 3 列，y=278，靠 yOffset 上下分开）。 几何常量也是死的（phaseXs: [94,248,402,556,710]、eventXs: [402,556,710]）。

    拿「进程七态」试过：四个状态要横排、还要跨三行画挂起，label 碰撞报了二十几条。 状态机用 flow + shape: pill，别用 lifecycle。 lifecycle 留给「一条主路径 + 几个中断 + 几个结局」那种形状。

版面原则：文字窄，图宽

屏幕越宽，不要把文字拉长（长行伤可读性），而是把多出来的宽度给图。

theme.css 里三层控制：

  • --prose（880px）管文字元素（p / h2 / h3 / ul / .callout / .quiz）
  • main 的 max-width（1280px）管整列上限，防 4K 屏上积木被拉飞
  • 积木不受 --prose 限制，自动用满整列

判断一个新积木该不该限宽：它主要是文字还是图形？ 文字限，图形不限。

行内强调与颜色：别让一种标记承担所有重点

写法 语义 颜色
==文字== 关键结论 / 最该记住的一句 蓝
!!文字!! 坑 / 反直觉 / 注意 橙
++文字++ 正确做法 / 推荐 绿
**文字** 句子内的重音（降级用） 加粗不变色

一屏之内不要超过 3 个 == —— 到处都是重点等于没有重点。 写完后扫一眼：如果整页加粗密密麻麻，说明该用彩色标记做取舍了。

代码块：先分行，再谈分色

⚠

粘一段单行 SQL 进笔记，等于没写。

子句、权限、条件全挤在一行，读者要在脑子里自己断句。 这跟「把图挤成一团」是同一种偷懒 —— 只是不容易被截图抓出来。

两条规矩，按优先级：

① 分行 —— 一个子句一行，嵌套的缩进

写法读者要做什么什么时候必须分行
一整行塞完在脑子里断句、数括号、找 AND 在哪永远不要。除非真的只有 SELECT 1 这么短
一个子句一行从上往下读，一眼看出结构SELECT / FROM / WHERE / GROUP BY 各占一行
嵌套再缩进子查询、AND 续行看层级子查询整体缩进两格；AND 接在下一行、再缩两格

实测对照（notes/insight-dsl 那个交互）：

❌ 挤成一行（真编译器就是这么输出的）
SELECT COUNT(*) AS `count` FROM (SELECT `u`.`uid` AS `uid` FROM `user_portraits_wide` AS `u` WHERE `u`.`staff_id` = 101 AND (TIMESTAMPDIFF(YEAR, `u`.`birthday`, CURRENT_DATE()) >= 18)) AS `t`

✅ 按子句分行
SELECT COUNT(*) AS `count`
FROM (
  SELECT `u`.`uid` AS `uid`
  FROM `user_portraits_wide` AS `u`
  WHERE `u`.`staff_id` = 101
    AND (TIMESTAMPDIFF(YEAR, `u`.`birthday`, CURRENT_DATE()) >= 18)
) AS `t`
⚠

但如果原文就是这样（比如真编译器的输出），分行之后要说明。

读者会以为「真代码就长这样」。

正确做法是分行展示 + 一句注明：

语句内容跟真输出逐字相同；真输出是一整行（省字节），这里换了行。 换行只是排版，不改变语义 —— SQL 本来就不看换行。

② 分色 —— 分的是来源，不是语法

💡

不要做语法高亮（SELECT 蓝、字符串橙）—— 那是编辑器的事，不是笔记的事。

笔记里分色的价值在另一件事：一段代码里混了多个「来源」时， 用颜色把来源分开。

照 notes/insight-dsl 那个交互的做法：

颜色代表什么为什么值得一色
琥珀权限 —— 演员身份决定的它不是用户圈出来的，读者最容易把它当成条件的一部分
白（默认）用户圈的条件 —— 界面上点出来的主体，不需要额外颜色
紫派生表达式 —— 逻辑字段到物理列的变换age → TIMESTAMPDIFF(YEAR, birthday, ...)，这是最反直觉的一层

判据：一段代码里如果有 2 个以上来源不同的东西混在一起， 分色讲得清；只有一种来源就别上色（纯噪音）。

③ 做成交互时，分色是自动的

那个演示不是手写的 HTML —— 它按语义片段拼出来：

[['SELECT ', 'kw'], ['`u`.`uid`', 'cond'], ['WHERE ', 'kw'], ['`u`.`staff_id` = 101', 'perm']]
//                    ↑ 默认色            ↑ 关键字          ↑ 琥珀（权限）

所以换身份、勾条件、切 include/exclude 时颜色一直是对的， 不需要作者维护两套东西。

写这类 demo 时：先想清楚有几种语义来源，再定颜色。 不要先挑颜色再往里塞内容。

响应式：宽屏完整呈现，窄屏安全降级

  • 宽屏（≥1081px）：目录是一列，点顶栏 ☰ 可收成 0；图和交互按完整形态呈现
  • 窄屏 / 竖屏（≤1080px）：目录变成左侧抽屉，点遮罩或 Esc 关闭
  • 状态记在 <html data-toc> 上，样式全在 theme.css，JS 只切属性
  • 复杂图和交互不要求改成竖排；可以保留桌面画布，在自身容器内滚动

第七次：--virtual-time-budget 下 CSS 过渡不会被推进 —— 截图会骗你

📸

点一下控件再截图，截到的是点击前的样式 —— 而 DOM 里 class 已经是对的。

实测：一个「选中态」按钮。点第二个之后， class 和计算样式完全对调 —— 掉了 .on 的那个显示成选中态，加上 .on 的显示成未选中。

0 [nw-seg-btn]     bg=rgb(234,241,255)   ← 看起来是选中的，其实不是
1 [nw-seg-btn on]  bg=rgb(255,255,255)   ← 明明是选中的

根因：所有无头截图都跑在 --virtual-time-budget 下，而那个模式下 CSS 过渡（transition）不会随虚拟时间推进 —— 元素停在过渡的起点，再也不会动。

怎么确认是它：注入 * { transition: none !important } 之后再读一次计算样式，样式立刻归位。 上面那个例子，关掉过渡后两个按钮的颜色正好对调回来。

已经修在工具里：tools/block.mjs 生成的预览页现在带一条

*, *::before, *::after { transition: none !important; animation: none !important; }

过渡只在值改变时触发，初次渲染不受影响 —— 所以量静态布局的 visual-check 基本不受影响， 只有「点一下再截图」这条路会踩到。

自己写截图脚本时也要记得加这条，否则会像我一样，花时间去找一个根本不存在的 CSS bug。

第五次：archify 的共用 CSS 被削薄

🌗

写过 transition: background 的元素，只要它的背景是 color-mix(...)， 换主题时颜色会卡在旧主题上。

不是过渡一下就到了 —— 是永远不更新，直到这个元素因为别的原因重新布局。

这个 bug 只在切主题时出现，npm run check / visual-check 全是绿的。 （它们不切主题，只量布局。）

真实经过（写「三种 IPC 数据流」那个控件时）：
症状 浅色模式下，未激活的格子渲染成深色；但同一张卡片的外壳是白的
第一反应 以为变量作用域错了 —— 打印 --surface-2，发现是 #f2f4f7（正确的浅色）
打印元素的实际值 oklab(0.283 0.003 -0.029) —— 一个暗色，和变量对不上
排除法 把 transition: background .2s 删掉，立刻正确（rgb(234,231,246)，正是手算出来的淡紫）

根因：元素在 data-theme 还是 dark 时完成首次渲染，主题切成 light 后 背景值要变，但 Chrome 对两个 color-mix() 计算值之间的插值处理不了， 于是停在起点。改成普通 var(--x) 的颜色不会中招（那是两个具体颜色之间的插值）。

规矩：给「背景是 color-mix」的元素写 transition 时，只写具体属性，不写 background、更不要写 all。

/* ❌ 换主题会卡住 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent); transition: .18s; }

/* ✅ 只过渡真正会动的东西 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent);
        transition: color .18s, box-shadow .18s; }

查法（一条命令扫全站）：

python3 - <<'EOF'

css = pathlib.Path('assets/blocks.css').read_text()
for sel, body in re.findall(r'([^{}]+)\{([^}]*)\}', css):

    t = re.search(r'transition:\s*([^;]+)', body).group(1).strip()
    if 'background' in t or re.fullmatch(r'\.?\d+(\.\d+)?(m?s)?', t):

改共享文件的四条硬规矩

  1. 改一条 CSS 规则就替换那一条，别用大区间。 非要大改，改完 grep 一遍原来的选择器。
  2. 绝对定位的装饰元素要考虑「会不会超出容器」。 加了就配 padding。
  3. 坐标计算必须统一参照系。 容器一有 padding，相对不同父元素量的坐标就会错开。
  4. 放进 grid / flex 的元素要设 min-width: 0，否则内容会把容器撑破。
  5. background: color-mix(...) 的元素，别写 transition: background 或 transition: .2s。 换主题时 Chrome 插值不了两个 color-mix 计算值，颜色会卡在旧主题上 —— visual-check 抓不到（它不切主题）。详见上面「第六次」。

怎么写：笔记正文和 skill 文档都适用

这一节是给写文字的，不是给排版的。起因是用户看过一版 skill 之后说：

有些语句充满了 AI 味道，我希望所有的语句都平实、自然、连贯一些。

下面四条是把那句话拆成可执行的样子。改稿时对照着看，比事后凭感觉删有效。

一、别先甩一个判断，再用破折号复述一遍

这是最像 AI 的一种句式：先给一个大的、抽象的判断，然后破折号， 再把同一个意思用具体一点的话说一遍。两句话说的是同一件事。

写法例子
❌ 改前本体里有一类图，它给的理解是别的什么都替代不了的 —— 把一堆东西和它们的关系一次铺开。
✅ 改后有的问题，把零件一个一个讲是讲不清楚的。 比如「容器到底是什么」。它不是一个对象 —— 内核里没有叫「容器」的东西。

改后的版本直接从具体的东西开始（「容器到底是什么」），读者自己就能得出那个大判断。 把结论留给读者，比替他下结论更可信。

二、删掉空转的过渡句

「这一条接着说下一层」「下面我们来看」「值得一提的是」这类话不承载信息， 只是在标记「我要换话题了」。直接换话题就行。

写法例子
❌ 改前原则 ① 立的是「图是这个产品的本体」。这一条接着说下一层：
✅ 改后（整句删掉）

三、去掉没依据的绝对化

「唯一」「全都」「永远」「根本」「只能」—— 这些词让句子更有力，但多半不准， 而且读者一旦发现反例，整篇的可信度都掉。

写法例子
❌ 改前这是它唯一的强项后者只能由整体图给
✅ 改后这是它擅长的这类问题得把东西放在一起看

例外：真能举出反例说「没有」的时候可以用。 「内核里没有叫『容器』的东西」是真话，而且恰恰是那一节的关键。

四、对举句要看后半句是不是读者的真实误解

「不是 A，而是 B」这个句式本身没问题，问题在 A 是不是读者真会以为的东西。
✅ 可以用 「原文里已经有一段文字在解释它」不是不画图的理由，恰恰是该画图的信号 —— 因为「有文字就不用画」是很多人的真实想法
❌ 别用 「它不是简单地把 X 存起来，而是……」—— 读者没以为过 X，这个否定是空的

五、加粗和 == 要省着用

skill 自己有一条规矩：全文都是加粗的时候，等于没有重点。 写 skill 文档时同样适用 —— 一段最多一处 ``，一节最多两三处。==

改稿时可以数一下：一节里 == 超过 5 处、** 超过 10 处，基本就是超了。

依赖策略：默认零依赖

页面要能单文件发人，所以每加一个库都在增加分发成本。

需求 用什么 要不要库
高亮、淡入、位移 CSS transition / animation 不要
元素沿路径移动 CSS offset-path 不要
流程连线 测量 + 内联 SVG（见 flow 积木） 不要
数字滚动、按步播放 Web Animations API / setTimeout 不要
复杂时间轴编排、物理弹簧 —— 到这一步再说

先零依赖做到极限。 真不够时再讨论装什么，并且要把决定写回这一节。

变体：源码通读

用户说「读 xxx 代码，画出架构」时，不要从 README 开始读 —— README 经常过期。

⚠

也不要直接从架构开始写。 源码通读同样要先过原则 ⑤ 的三层： 先讲清楚这个领域的概念（有哪些词、对应什么现实事物）， 再讲怎么组织，最后才是代码怎么实现。

跳过概念层，得到的就是一份只有作者看得懂的架构图。

按这个顺序读：

  1. 摸依赖图 —— 一条命令看出谁依赖谁：
    find . -name '*.ts' -not -path '*/node_modules/*' | while read f; do
  echo "$f → $(grep -oE "from '[^']+'" "$f" | sed "s/from '//;s/'//" \
    | grep -E '^(\.|src|@)' | tr '\n' ' ')"
done
    横切的（被所有层依赖）和纵深的（依赖所有层）一眼可见。
  2. 按行数排序 —— 最大的文件就是复杂度所在，也是卡点所在。
  3. 读入口 —— index.ts / context.ts / 工厂，它们定义了架构骨架。
  4. 找反直觉的实现 —— 这是最值钱的卡点。信号：
    • 注释里出现「为什么不用 X」的解释
    • 有一行代码做了意料之外的事
    • 到处都在 ?? new XxxDefault() 兜底（往往是个真实的坑）
    • 常量里出现取模 / 哈希分片
    • 有一个 switch 的 default 直接 throw
  5. 确认，不要猜 —— 断言「这里会 throw」之前，先把那几行读出来。

结构用现有积木就能画好（lane-stack + 分组正好表达包的边界）。 真正需要新表达的是机制，不是结构 —— 力气花在那里。

把「分派逻辑」图形化

源码通读最值钱的产出，是把代码里的分派点变成一张表或一个交互。

判据很直接：代码里有 switch / if-else 分派的地方，就是该画图的地方。

代码里是什么变成什么例子
一个 switch 分派节点类型一张「输入形态 → 生成什么」的表compileNode 的四种叶子各编译成什么
一个 op 分派一张「操作符 → SQL 片段」的表applyComparison 按 op 分派到 where / whereIn / whereBetween / whereRaw
一个「按输入挑分支」的校验器一个「喂坏输入，看它在哪一步被拦」的交互validateStructure / validateSemantics 各自拦什么
一条「输入 → 几道处理 → 输出」的链一个分步执行的交互「一个条件走完三段管道」
💡

「分派」是代码里信息密度最高的地方。

一个函数如果有 8 个分支，读代码要来回跳 8 次； 画成一张表，一眼扫完。

而且表能顺带回答「漏了哪个分支」—— 代码里看不出来，表里缺一行就很显眼。

反过来也成立：如果一个东西没有分派，别硬画。

情况怎么办
一条直线流程、没有分支用 lane-stack 或直接文字说清，不用做交互
一个纯数据结构用 tree 或一张字段表
一段几十行的顺序逻辑值得做 stepper —— 但先问「读者会想单步走一遍吗」

catalog.ts（474 行，混着夹具和查找函数） 整个文件删掉了，查找函数搬进 metadata.ts
defaultCatalog（硬编码的 46 个字段） 删掉了，字典只剩 MySQL 一个源
「10 个文件、1717 行」 11 个文件、1507 行（重构之后反而变小）
一整节「一个诚实的问题」 那个问题被重构修了

npm run check 全绿 —— 它查的是格式，不查事实。

两个做法：

做法说明
在 meta.json 的 sources 里写清 commit「本仓库 packages/dsl/src/ @ abc1234」—— 至少读者知道以哪一版为准
过一段时间回头对一遍重点是数字和「谁在用什么」 —— 这两类最容易变
⚠

最危险的是「数字 + 判断」的组合。

「catalog.ts 是最大的文件（474 行）」这句话里， 行数会变，但更会变的是「它是不是最大的」和「它还在不在」。

写的时候回源码数一遍（复盘 ①b），过一阵子还要再数一遍。

变体：拆解一个东西

用户说「拆解一下 X」时，用这六个问题逐条回答，写进 spec 积木：

维度 问什么
输入 喂给它什么？什么类型、什么形态？
处理 中间做了什么？有哪几步？
输出 吐出什么？给谁用？
怎么调用 别人实际怎么用它？贴一段真实调用代码
为什么这么设计 作者为什么这样选？注释里常藏着答案
业务价值 它到底解决了什么问题？没有它会怎样？
⚠

但不是所有东西都值得拆。

先判断该不该拆：在代码里搜一下它被调用几处。

  • 调用很多（几十处）或位于主干 → 值得拆，六个维度都写
  • 只有 1~3 处调用 → 用 compare 一行说清就够，硬拆六个维度是凑字数
  • src/ 里根本搜不到 → 它是被动依赖（编译期 / 间接），没有输入输出可言， 归到一张表里说明「为什么在 deps 里」即可

判断依据不是「用户让我拆」，是这个东西本身有没有那么多可讲的。 拆一个只有两处调用的工具库，写出来的六段全是废话。

先搞清楚：这不是分支的问题

⚠

多个会话共用一个工作目录，才是根因。

开分支解决不了 —— git checkout -b 只改 HEAD 指向哪， 工作区里的文件一个都没变。两个 agent 在同一目录里，改的还是同一批文件。

真实发生过（2026-09-29）：

提交 8575596

实际：44 个文件，+39461 行，其中包括
  notes/data-admin-to-ui/note.md        428 行   ← 另一个会话 17:41 建的
  dist/data-admin-to-ui.html           6382 行
  archify/data-admin-flow.json          112 行
  assets/arch/data-admin-flow.svg       138 行

反向也一样：另一个提交用 git add -A 把别人做到一半的 13 个 meta.json 一并带走了。

三个设计放大了它 —— 它们本身都没错，错的是假设只有一个改动人：

设计 本意 共用目录时
git add -A 提交一个自洽快照 仓库级 —— 分不清谁改的
产物是全量的 clone 下来就能开 我 build 会重建所有人的产物
保存即有竞态 —— A 保存、B 正在 build → B 构建出 A 的半成品

先做这件事：每个会话一个 worktree

cd ~/works/codes/knowledge-html
git worktree add ~/works/codes/kh-<会话名> -b <会话名>
cd ~/works/codes/kh-<会话名>
ln -s ~/works/codes/knowledge-html/node_modules node_modules

每个目录是完整独立的工作区：文件互不可见，git add -A 只会扫到自己的改动。 误提交从根上消失。

三个实测出来的坑：

坑 怎么办
node_modules 不跟着 worktree 来 软链过去（上面那条），或各自 npm install
软链显示成 ?? node_modules .gitignore 里写的是 node_modules/（带斜杠 = 目录），匹配不上软链 —— 改成 node_modules
skill 的符号链接固定在主目录 worktree 里改 skill 不生效。skill 只有一份，这是好事
习惯性 cd 回主仓库 开了 worktree 之后，每条命令都要从 worktree 目录起。习惯性的 cd ~/works/codes/knowledge-html 会把改动全写回共享目录，而自己的 worktree 干净得可疑 —— git status 一片空白就是信号
🪢

但「worktree 里改 skill 不生效」这句话会误导人走错一步。

真实布局是这样：

~/.agents/skills/knowledge-html  ──软链──→  <主仓库>/.agents/skills/knowledge-html
                                            <worktree>/.agents/skills/knowledge-html   ← 独立副本

.agents/skills/** 是进仓库的跟踪文件，所以每个 worktree 各有一份。 你按直觉去改 ~/.agents/skills/knowledge-html/SKILL.md，改的其实是主仓库的工作区， 而 npm run check 读的是 worktree 里那份 —— 于是：

你看到的 实际发生的
文件确实改了，内容也对 主仓库工作区脏了（别的会话会看到）
npm run check 还是报「SKILL.md 说 20 个控件」 worktree 那份没动

正确做法：在 worktree 里改 .agents/skills/knowledge-html/SKILL.md。 主仓库那份等分支合并时自然更新。

这次先改错了地方，check 报的却是「代码 22 个 vs 文档 20 个」， 完全看不出是「改的是另一个副本」。

用完的 worktree 也要收（删之前有四道门）

git worktree add 是一条随时能开的命令，但没有任何一条命令会提醒你关掉它。 量过（2026-10-09）：这个仓库留下了 9 个工作区目录、共 345MB，大部分早就并进了 main， 只是没人敢删 —— 因为「还有人在用吗」只能靠猜。

npm run worktree-audit        # 只读：分类 + 给出待执行的命令 + 报数

它只做三件事：分类、把命令写出来、把 df -h 的数字摆出来。 删除不可逆，所以它自己不删 —— 「可删候选」是建议，不是许可。 四道门：

门 为什么
路径只从 git worktree list 读，不手打 手打的路径会漏掉开在别处的工作区
主仓库和当前所在的工作区永远不进候选 删掉当前目录，会话当场死
wip:N（有未提交的改动）停下来问人 删掉干净的工作区可以从分支恢复，未提交的东西不能
板子上最后一次提到它的时间一起打出来 哪个会话你钉着，只有你知道

钉住的会话不进候选。 脚本算不出「你还想留着哪个」—— 它把候选和命令行摆出来，由你点名。删掉一个已并入 main 的工作区， git branch -d 会跟着把分支收掉；报错就说明判断错了，停下来重看一遍。

合并时冲突面比想象的小。量过：全仓库只有 index.html 一个文件是全量的 （dist/<slug>.html 和 notes/<slug>/index.html 都是每篇一个文件，只有作者会动）：

文件 合并时
dist/<slug>.html、notes/<slug>/index.html 各改各的 → 不冲突
index.html（首页树视图） 所有人都动 → 必然冲突

index.html 冲突时别手动 merge —— 它是生成的：

git checkout --theirs index.html   # 随便选一边，反正是生成的
npm run build:standalone           # 用合并后的源重建
git add index.html && git commit

没条件开 worktree 时：点名 add，别用 -A

⚠

把 git add -A 换成 git add <具体路径>。

git add notes/<你的 slug>/ archify/<你的名字>.json assets/arch/<你的名字>.svg
git add assets/blocks.css assets/app.js      # 只在你确实改了它们时
git add index.html dist/                     # 产物是全量的，必须一起带上

为什么这样更安全：-A 是仓库级的，它不问「这是谁改的」。 点名 add 只带走你确认过的东西。

还有第二个矛盾：产物是全量的

即使分了 worktree，合并时还有一道坎。

⚠

构建产物是全量的。

index.html、dist/*.html 里包含所有人的内容。 所以你没法「只提交自己的部分」—— 那样仓库就停在「产物新、源旧」的不一致状态， pre-push 钩子会直接拦下。

推论：提交 = 提交一个自洽快照 = 当前所有源 + 由它们构建出的所有产物。

这意味着你必然会把别人的改动一起提交。这不是错误，是设计。关键是把这件事做安全。

三类文件

类别 例子 谁负责
共享产物 index.html、dist/*.html、notes/<任意 slug>/index.html、skill/*.html 每次提交都要带上全部
共享源 assets/theme.css blocks.css app.js、tools/*.mjs、package.json、.agents/skills/** 谁改谁提交，但要小心
私有源 notes/<你的 slug>/、archify/<你的名字>.json、assets/arch/<你的名字>.svg 只有你改

开工前（30 秒）

它会把你工作区的改动分类列出来（临时文件 / 共享产物 / 共享源 / 笔记源）， 并标出每项的修改时间。

这一步只说明「开工那一刻」。 别的会话可能在你干活期间才开始 —— 开工时干净不等于全程干净。

场景怎么办
短活（一篇笔记，半小时内）直接干。收尾再跑一次 status 就够
长活，或要改共享源（assets/ tools/ plans/ SKILL.md）开 worktree。写共享源之前重跑一次 status —— 这一条是真实事故换来的，见下

真实事故：改 plans/insight.yaml 加完节点几分钟后，同一个文件被另一个会话写回， 我的改动静默消失（git log -S 查不到，像从没写过）。两个会话都「开工时干净」。 共享源的写入冲突是这样的 —— 不报错、不留痕，只是你写的东西没了。

  • 干净 → 直接干活
  • 有别人的改动 → 两种走法：
    • 你在 worktree 里 → 与你无关，但合并时要注意
    • 你在共用目录里 → 记住它们，但不要用 -A，点名 add
  • 有别人的改动且明显是半成品（写了一半、构建不过）→ 先问用户

干活时

  1. 只改自己的文件。 不要顺手改别人的 note.md，哪怕发现它写错了 —— 报告，不擅自改。
  2. 改共享源要小步。 blocks.css / app.js 有别人在用：
    • 改一条 CSS 规则就替换那一条，别用大区间替换
    • 加控件 / 积木用新名字，别改别人的
    • 改完尽快提交，别攒着
  3. 临时文件进 .gitignore。 预览副本、截图、草稿别留在 notes/ 里。 约定：以 _ 开头的文件是临时的（_p.html、_wip.html）。

提交时

npm run status              # ① 分类看清 —— 这一条不能省
npm run check               # ② 校验（含 skill 一致性）
npm run build:standalone    # ③ 重建全部产物
npm run skill               # ③b 重建 skill/（改了 skill 文档才需要）
npm run visual-check        # ④ 量图
git add <点名清单>          # ⑤ 优先点名；确认过才用 `-A`
node tools/status.mjs --cached   # ⑥ 再看一遍 staged 的
⚠

第 ⑤ 步优先点名 add。

共用目录里 git add -A 会把你没看过的东西一起带走 —— 包括别人正在写的半成品。它不问「这是谁改的」。

只有在你确实逐项确认过（第 ① 和 ⑥ 步都看过）时，-A 才可以。

⚠

但有一条例外：如果别人的源是半成品，不要提交。

半成品 = 明显写了一半、或构建不过。

这时停下来问用户，别替别人改，也别把它带上。 替别人提交一个坏文件，比漏提交更糟 —— 它会被当成「已经完成」。

情况 怎么办
别人的源完整、构建能过 一起提交，提交信息里注明来源
别人的源是半成品 停下来问用户

别人改了共享源（blocks.css） 一起提交，在信息里说明你确认过它的改动

提交信息里的注明格式（已有先例）：

- tools/visual-check.mjs（加 .keyby-viz 容器 + JSON 解析错误上下文）

构建和提交之间的竞态（真实踩过）

⚠

npm run build 和 git add 之间，别人的文件可能又变了。

于是你提交的是「源是新的、产物是旧的」—— pre-push 钩子一重建就发现对不上，直接拦下。

时间线（真实发生）：

① 我 npm run build:standalone   → 从 note.md 的版本 A 构建出产物 A
② 我 git add -A && commit       → 期间别人保存了版本 B
                                  结果提交的是：源 B + 产物 A   ← 不一致
③ pre-push 重建                 → 从 B 构建出产物 B ≠ 产物 A → 拦下

修法：源已经提交了，只是产物过期 —— 重建后 amend：

npm run build:standalone
git add -A
git commit --amend --no-edit
git push
⚠

如果这样还反复被拦，说明别人正在持续编辑。

那就别再重试了 —— 停下来问用户，等对方告一段落。 反复 amend 只会把你的提交变成「别人半成品的快照」。

别人的文件坏了，阻塞了共享构建

⚠

npm run check 是全仓库的。别人一篇笔记写坏，你这边也过不了。

先分清是哪一类：

例子 怎么办
机械性问题 YAML 裸标量以反引号开头 · 积木名拼错 · 引号没闭合 ✅ 可以修。工具自己会给出修法，改的是语法不是意思
语义性问题 内容写错了 · 数字不对 · 结构乱 ❌ 不碰。报告用户
✅

判断标准：这个修改会不会改变别人想表达的意思？

加一对引号不会。改一个数字会。

机械性修复要在提交信息里单独列出来并注明，别混在自己的改动里。

真实案例：并行会话的 Flink 笔记里有两行 - q: \xxx` 是什么？—— YAML 里裸标量不能以反引号开头，整个仓库的check` 都挂了。 预检工具直接给出了修法（外面包一层双引号），修它零风险。

冲突处理

冲突的文件 怎么办
index.html、dist/*、notes/*/index.html 重新构建，不要手动 merge。产物是生成的，冲突无意义
package.json 通常两边都加了 script → 两边都保留
blocks.css / app.js 真冲突，逐条看，两边的改动都要留
note.md 不该发生。如果发生，说明两个会话改了同一篇 → 问用户

推送被拦下来怎么办

pre-push 会重建 + 量图。它拦下来通常不是你的问题。

✗ 构建产物有变化（note.md 改了但没提交构建结果）

→ 有人（可能是你）改了源没重建。git add 上产物，--amend 重新提交。

✗ 有图被画坏了

→ 看是哪个积木、哪一篇。如果是别人笔记里的图坏了，报告用户，别去改别人的内容。

git 与多会话：五条硬规矩

  1. 优先开 worktree。 没条件就在共用目录里点名 git add，别用 -A —— 共用目录里 -A 会带走别人正在写的半成品。
  2. 产物和源必须一起提交。 只交产物 → 来源不明；只交源 → 构建过期。
  3. 不替别人改东西。 发现问题 → 报告，不擅自改。
  4. 提交前跑 npm run status —— 而且要看完。 别 | head -45 只扫前面一截就往下走。
  5. 收工把 worktree 收掉。 用完不删的会一直堆着，而且没人敢删 —— 跑 npm run worktree-audit 拿分类，wip 的先问人。

硬约束

这张表随时要用，所以留在这一页。

❌ 不要 ✅ 应该
为了「符合积木规范」而扭曲表达 怎么讲清楚怎么来。积木是省力工具，不是验收标准
为了手机一屏放下而删节点、隐藏关键标签、把图改成简陋卡片或缩减交互 保留图义和完整交互；窄屏用局部滚动、最小画布宽度、缩放或「建议宽屏查看」

硬把内容塞进最接近的积木 组合 / 加字段 / 新建 / raw 直接写 —— 四条路任选
编辑 notes/*/index.html 那是产物，会被覆盖。只改 note.md
在单篇 note.md 里塞 <style> 改 theme.css / blocks.css —— 一次全站生效

meta.json 里自己填 verified: "日期" 它会进页面的溯源条，那是「有人核对过」的声明。agent 生成的一律留空
没挂树的笔记不填 topic 填一个 —— 否则它在首页的「未归类」里落进「其他」组
原样搬用户的原文 先砍到骨架，再决定哪几段变成图

写「这一步我之前没讲」「这张图我第一版画错了」 读者不知道你迭代过几轮，这些话只对你有意义。直接陈述事实

YAML 裸标量以 * & ! % @ 开头 加引号（会被当成别名/锚点/标签）

只给卡点画图，其余照搬原文 用户已经有文字版了。卡点是排序不是取舍：其余那些「空间 / 顺序 / 状态」的段落照样要画，只是可以画轻（cards / compare 也算图）。见原则 ①
因为「没有现成积木」就退回文字 原则 ⑦ 给了四条路：组合 / 加字段 / 新建积木 / raw。退回文字是第五条路，也是最贵的那条

写空转的过渡句（「这一条接着说下一层」） 不承载信息，直接换话题
没依据的绝对化（唯一 / 全都 / 永远 / 根本 / 只能） 多半不准，读者找到反例就整篇不信了。真能举出反例说「没有」时才用
一段里堆 == 和加粗 一段最多一处 ==，一节最多两三处。见 style.md 的「怎么写」

改了「站点外壳」要多做一步

外壳 = tools/lib/home.mjs（首页）、assets/theme.css / blocks.css。 下面两个坑 npm run check 一个都报不出来，而且都是静默的：属性设上了、JS 里读也是对的，只有屏幕上不对。

⚠

一、内联在模板字符串里的浏览器 JS，语法检查查不出 ReferenceError。

首页那段 <script> 是拼在 JS 模板字符串里的，node --check 看不到它。 我重构时把旧函数整个换掉，连同里面声明的 var mode 一起删了 —— 语法完全合法，表现是「排序按钮点下去毫无反应」。

→ 在真实页面里跑一遍，并把 window.onerror 收上来（否则连报错都看不到）。

这条已经收成一条命令了：npm run probe:home。 17 项：抽屉开关 / 排序是否真的重排 / 遮罩有没有色 / 右缘贴不贴边 / 横向溢出 / 焦点进出 / window.onerror。失败退出码 1，并把你没过的项逐个打出来。

它自己也是被验过的 —— 故意注入一个悬空变量，它会报两项失败（历史真发生过这个： 重构时把 var mode 跟着旧函数一起删了，排序按钮哑了而 node --check 是绿的）。

⚠

二、el.hidden = true 会被作者样式里的 display 盖掉。

浏览器自带的 [hidden] { display: none } 在 UA 样式表里， 而 作者样式表里任何一条 display 都会盖掉它 —— 跟优先级无关。

所以 .tnode { display: grid } 一写，n.hidden = true 就完全失效： 属性在、el.hidden 读出来是 true、屏幕上还画着。 首页的搜索和标签筛选因此哑了很久（实测：32 个节点全被标了 hidden，32 个全在显示）。

theme.css 里已经加了兜底，站内新写的组件不用再操心：

[hidden] { display: none !important; }

但要是哪天自己写页面 / 导出 HTML，记得补上这条。

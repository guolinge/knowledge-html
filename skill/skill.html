开工第一件事

npm run status        # 仓库状态、有没有别人在动

这个仓库会被多个会话同时编辑，而且构建产物是全量的 —— 提交时必然带上别人的改动。 不止一个会话在干活时，先读 references/mult-session.md。

两个最常犯的错

一、回答了一个用户没问的问题。 他说「画个架构图」，你画了架构图 —— 但他真正想要的是「理解这个项目」，架构图只是他以为的入口。看完发现到处缺前置知识，你一路补窟窿。 → 先读 references/workflow.md 的第 0 步。它比后面所有步骤加起来都重要。

二、把原文的文字搬进 HTML，再配几张插图。 用户手上本来就有文字版。他来找「图解」，要的就是文字表达不了的那部分。换个排版搬过来，交付价值是零。 → 判据在 references/principles.md 的原则 ①。

硬约束

这张表随时要用，所以留在这一页。

❌ 不要 ✅ 应该
为了「符合积木规范」而扭曲表达 怎么讲清楚怎么来。积木是省力工具，不是验收标准
硬把内容塞进最接近的积木 组合 / 加字段 / 新建 / raw 直接写 —— 四条路任选
编辑 notes/*/index.html 那是产物，会被覆盖。只改 note.md
在单篇 note.md 里塞 <style> 改 theme.css / blocks.css —— 一次全站生效
在正文写 # 一级标题 标题只写在 meta.json 的 title
meta.json 里写 status: "verified" agent 生成的内容一律 draft。verified 是人工核对过的信号
没挂树的笔记不填 topic 填一个 —— 否则它在首页的「未归类」里落进「其他」组
原样搬用户的原文 先砍到骨架，再决定哪几段变成图
写「它不是 X，而是 Y」这类否定句 读者没听过 X。除非 X 是读者真会有的误解，否则直接说 Y 是什么
写「这一步我之前没讲」「这张图我第一版画错了」 读者不知道你迭代过几轮，这些话只对你有意义。直接陈述事实
图上的编号和正文对不上 正文用编号指代时，图上必须真有那个编号（archify 的边标签、积木的 badge 都要对得上）
图上有文字被压住 字还在、只是读不通，所以最容易滑过去。 npm run visual-check 会报「文字压文字」，改完图必须跑
把 SQL / 代码粘成一整行 一个子句一行，嵌套的缩进。原文本来就在一行时（如编译器输出）要注明「换行只是排版」
把语法高亮当成分色 笔记里分的是来源（权限 / 条件 / 派生）—— 不要连 SELECT 都要上色
YAML 裸标量里出现 : （冒号+空格） 加引号，或用 `
YAML 裸标量以反引号 ` 开头 加引号
YAML 裸标量以 * & ! % @ 开头 加引号（会被当成别名/锚点/标签）
值里有 [ 或 { 却没加引号 加引号（Rule[] 里的方括号会被当数组起始）
担心 **「术语」** 这类中文加粗失效 已经修好了，不用管；但 ** 跨行仍然不生效
只给卡点画图，其余照搬原文 用户已经有文字版了。卡点是排序不是取舍：其余那些「空间 / 顺序 / 状态」的段落照样要画，只是可以画轻（cards / compare 也算图）。见原则 ①
因为「没有现成积木」就退回文字 原则 ⑦ 给了四条路：组合 / 加字段 / 新建积木 / raw。退回文字是第五条路，也是最贵的那条
先甩一个抽象判断，再用破折号复述一遍 两句话说的是同一件事。直接从具体的东西说起，把结论留给读者
写空转的过渡句（「这一条接着说下一层」） 不承载信息，直接换话题
没依据的绝对化（唯一 / 全都 / 永远 / 根本 / 只能） 多半不准，读者找到反例就整篇不信了。真能举出反例说「没有」时才用
一段里堆 == 和加粗 一段最多一处 ==，一节最多两三处。见 style.md 的「怎么写」

每篇结尾必须有 quiz。 这不是可选项 —— 知识库头号死因是「收藏代替理解」， 攒到 30 篇时自己都不记得里面有什么。2~3 题，逼自己合上答案复述一遍。

meta.json 的 status / sources 会渲染成页内的溯源头。 漂亮的 HTML 会自带「这应该是对的」的暗示，而它可能只是某次对话的产物。 半年后你必须能一眼看出哪个结论没人核对过。

# 变体：输入不是「一份文档」的时候

> 从 SKILL.md 拆出来的。

## 变体：源码通读

用户说「读 xxx 代码，画出架构」时，**不要从 README 开始读** —— README 经常过期。

```callout
tone: amber
icon: ⚠
text: |
  **也不要直接从架构开始写。** 源码通读同样要先过原则 ⑤ 的三层：
  先讲清楚**这个领域的概念**（有哪些词、对应什么现实事物），
  再讲**怎么组织**，最后才是**代码怎么实现**。

  跳过概念层，得到的就是一份只有作者看得懂的架构图。
```

按这个顺序读：

1. **摸依赖图** —— 一条命令看出谁依赖谁：
   ```bash
   find . -name '*.ts' -not -path '*/node_modules/*' | while read f; do
     echo "$f → $(grep -oE "from '[^']+'" "$f" | sed "s/from '//;s/'//" \
       | grep -E '^(\.|src|@)' | tr '\n' ' ')"
   done
   ```
   横切的（被所有层依赖）和纵深的（依赖所有层）一眼可见。
2. **按行数排序** —— 最大的文件就是复杂度所在，也是卡点所在。
3. **读入口** —— `index.ts` / `context.ts` / 工厂，它们定义了架构骨架。
4. **找反直觉的实现** —— 这是最值钱的卡点。信号：
   - 注释里出现「为什么不用 X」的解释
   - 有一行代码做了意料之外的事
   - 到处都在 `?? new XxxDefault()` 兜底（往往是个真实的坑）
   - 常量里出现取模 / 哈希分片
   - 有一个 `switch` 的 `default` 直接 `throw`
5. **确认，不要猜** —— 断言「这里会 throw」之前，先把那几行读出来。

**结构用现有积木就能画好**（`lane-stack` + 分组正好表达包的边界）。
真正需要新表达的是**机制**，不是结构 —— 力气花在那里。

### 把「分派逻辑」图形化

源码通读最值钱的产出，是**把代码里的分派点变成一张表或一个交互**。

判据很直接：**代码里有 `switch` / `if-else` 分派的地方，就是该画图的地方。**

```compare
first: 代码里是什么
head: [变成什么, 例子]
rows:
  - 一个 switch 分派节点类型:
      - "一张「输入形态 → 生成什么」的表"
      - "`compileNode` 的四种叶子各编译成什么"
  - 一个 op 分派:
      - "一张「操作符 → SQL 片段」的表"
      - "`applyComparison` 按 op 分派到 where / whereIn / whereBetween / whereRaw"
  - 一个「按输入挑分支」的校验器:
      - "一个「喂坏输入，看它在哪一步被拦」的交互"
      - "`validateStructure` / `validateSemantics` 各自拦什么"
  - 一条「输入 → 几道处理 → 输出」的链:
      - "一个分步执行的交互"
      - "「一个条件走完三段管道」"
```

```callout
tone: violet
icon: 💡
text: |
  ==**「分派」是代码里信息密度最高的地方。**==

  一个函数如果有 8 个分支，读代码要来回跳 8 次；
  画成一张表，一眼扫完。

  ++而且表能顺带回答「漏了哪个分支」—— 代码里看不出来，表里缺一行就很显眼。++
```

**反过来也成立**：如果一个东西没有分派，别硬画。

```compare
first: 情况
head: [怎么办]
rows:
  - 一条直线流程、没有分支:
      - "用 `lane-stack` 或直接文字说清，不用做交互"
  - 一个纯数据结构:
      - "用 `tree` 或一张字段表"
  - 一段几十行的顺序逻辑:
      - "值得做 `stepper` —— 但先问「读者会想单步走一遍吗」"
```

### 笔记会静默过期

**源码通读类笔记必然会过期，而且没有工具会发现。**

真实情况（写 `notes/insight-dsl` 那次，中间代码重构了一轮）：

| 笔记里写的 | 实际变成 |
|---|---|
| 「纯字符串拼接」 | 改成用 Knex 构造了 |
| `sql.ts` 是「拼 SQL 的唯一入口」 | 只剩一个函数在用，其余不在生成路径上 |
| `catalog.ts`（474 行，混着夹具和查找函数） | **整个文件删掉了**，查找函数搬进 `metadata.ts` |
| `defaultCatalog`（硬编码的 46 个字段） | **删掉了**，字典只剩 MySQL 一个源 |
| 「10 个文件、1717 行」 | 11 个文件、1507 行（重构之后反而变小） |
| 一整节「一个诚实的问题」 | 那个问题被重构修了 |

`npm run check` 全绿 —— **它查的是格式，不查事实**。

**两个做法：**

```compare
first: 做法
head: [说明]
rows:
  - 在 `meta.json` 的 `sources` 里写清 commit:
      - "「本仓库 packages/dsl/src/ @ abc1234」—— 至少读者知道以哪一版为准"
  - 过一段时间回头对一遍:
      - { text: "==重点是数字和「谁在用什么」== —— 这两类最容易变", tone: amber }
```

```callout
tone: red
icon: ⚠
text: |
  **最危险的是「数字 + 判断」的组合。**

  「`catalog.ts` 是最大的文件（474 行）」这句话里，
  ==行数会变，但更会变的是「它是不是最大的」和「它还在不在」。==

  写的时候回源码数一遍（复盘 ①b），**过一阵子还要再数一遍**。
```

## 变体：拆解一个东西

用户说「拆解一下 X」时，用这六个问题逐条回答，写进 `spec` 积木：

| 维度 | 问什么 |
|---|---|
| **输入** | 喂给它什么？什么类型、什么形态？ |
| **处理** | 中间做了什么？有哪几步？ |
| **输出** | 吐出什么？给谁用？ |
| **怎么调用** | 别人实际怎么用它？贴一段真实调用代码 |
| **为什么这么设计** | 作者为什么这样选？**注释里常藏着答案** |
| **业务价值** | 它到底解决了什么问题？没有它会怎样？ |

```callout
tone: amber
icon: ⚠
text: |
  ==但不是所有东西都值得拆。==
```

**先判断该不该拆**：在代码里搜一下它被调用几处。

- **调用很多（几十处）或位于主干** → 值得拆，六个维度都写
- **只有 1~3 处调用** → 用 `compare` 一行说清就够，硬拆六个维度是凑字数
- **`src/` 里根本搜不到** → 它是被动依赖（编译期 / 间接），没有输入输出可言，
  归到一张表里说明「为什么在 deps 里」即可

> 判断依据不是「用户让我拆」，是**这个东西本身有没有那么多可讲的**。
> 拆一个只有两处调用的工具库，写出来的六段全是废话。

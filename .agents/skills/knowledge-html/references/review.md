# 工作流 · 阶段三：复盘与反馈（第 8~9 步）

### 第 8 步 · 交付前的九次复盘（复盘清单）

改稿多轮之后内容一定会「长歪」。**每次都有具体动作，不是「再读一遍」。**

#### 复盘 ① · 术语审计

**用任何术语前，读者知道这是什么吗？**

把正文里的代码标识符列出来，看哪些没在概念章节出现过：

```bash
grep -oE '`[A-Za-z_][A-Za-z0-9_.]{2,}`' notes/<slug>/note.md | sort -u
```

**判断标准**：术语如果在「定义它」之前就被使用了，就是堵塞点。
处理：在开头加一个「先搞清几个词」的章节。

#### 复盘 ①b · 数字和事实回源码核实

**凡是写进文档的数字，都要回源码数一遍。**

> **手边没有源码、只能靠查的时候**，怎么查（用什么语言、信哪些来源、哪个工具干哪件事），
> 见 `principles.md` 里「原则 ③」的[「怎么查」](principles.md#怎么查用什么语言信谁用哪个工具)一节。
> 那一节还讲了一件事：==二手转述会丢掉限定条件== —— 这正是下面这类事故的根因。

真实事故：文档里写「这个接口有 14 个方法」，实际 **17 个**。
同一个错误在架构图、正文、速查表里各出现一次，**三轮都没人发现**。

```callout
tone: red
icon: ⚠
text: |
  ==**但光数数字不够 —— 机制也要核。**==

  第二个真实事故：文档里写「`countSql` 包一层是因为展示列会 LEFT JOIN 出重复行」。
  数字都对、术语都对、句子通顺 —— **但机制是编的**。

  回源码一看，两个错：

  | 我写的 | 事实 |
  |---|---|
  | 展示列会 LEFT JOIN 出重复行 | 展示列**根本不参与** `countSql`，它用的是 `uidsSql` |
  | 包一层才数的是人不数行 | ==包一层**不会去重**==；而且这里也没有东西需要去重 |

  怎么发现的？别人看了图觉得不对，去问了一圈才确认。
  ==靠外部反馈才发现，说明自己那一轮核实是缺的。==
```

**两类要核的东西，别只核第一类：**

```compare
first: 写下的东西
head: [长什么样, 怎么核]
rows:
  - 数字:
      - "「14 个方法」「1700 行」「5 种类型」"
      - "`grep -c` / `wc -l` —— 命令一跑就知道"
  - "**机制**（因果关系）":
      - "「包一层**因为**…」「校验分两段**是因为**…」"
      - { text: "==把那条代码路径读出来，看它到底会不会那样==", tone: amber }
```

```callout
tone: violet
icon: 💡
text: |
  **机制比数字危险，因为它看着更有道理。**

  数字错了读者会怀疑（「真的 17 个？」），但机制错了读者**会信** ——
  因为它语法通、逻辑顺、还带着解释力。

  ++判别方法：写下「因为…」之前，问自己「我是读到的，还是推出来的？」++
  推出来的，就得回去读。
```

容易写错的几类数字：**接口方法数、文件行数、枚举取值数、调用点数量**。

```bash
grep -cE '^\s+[a-zA-Z]+\(' <接口文件>     # 数方法
wc -l <文件>                              # 数行数
grep -c '^\s*[A-Z_]* =' <枚举文件>        # 数枚举值
```

> 数字错了比文字错了更危险 —— ==读者会信数字，而且不会去数==。

#### 复盘 ② · 每个概念必须配例子

```callout
tone: red
icon: ⚠
text: |
  ==只给定义不给例子，等于没定义。==

  「软删除是一种标记删除的机制」—— 读者完全不知道那是什么。
```

**每个概念至少给三样**（以「软删除」为例）：

| 给什么 | 例子 |
|---|---|
| 一句话定义 | 「删除时不真删，只打个标记」 |
| **长什么样**（最重要） | `{ id: 7, deleted_at: '2026-03-01 10:00:00' }` |
| 和相邻概念的区别 | 「普通删除是行没了；软删除是行还在，查询要额外加 `where deleted_at is null`」 |

用 `cards` 的 `code` 字段放例子最省事。

#### 复盘 ③ · 小白通读

**假装你只能看到这份 HTML，看不到任何代码。** 从头读，每段问：

- 这里出现的词，我前面见过定义吗？
- 「它」「这个」指代清楚吗？
- 这张图 / 表，不看正文能理解吗？
- 有没有结论来得太突然的地方？

**记下所有卡住的位置，回到原文补。**

#### 复盘 ④ · 结构复盘

**改过三轮以上，目录一定会乱。**

```bash
grep -nE '^#{2,4} ' notes/<slug>/note.md
```

检查四件事：

| 检查 | 典型症状 |
|---|---|
| **层级** | 某个 h3 其实是上一个 h3 的下级，却平级了 |
| **归属** | 内容跑到了别的章节（A 的讲解跑进了 B 里） |
| **顺序** | 先讲「怎么工作」后讲「由什么组成」 |
| **编号** | 改稿后编号重了或跳号 |

```callout
tone: violet
icon: 💡
text: |
  读者的路径应该是：==这是什么 → 由什么组成 → 怎么工作==。
  先看零件清单，再看零件怎么配合。
```

#### 复盘 ⑤ · 篇幅复盘

**改过几轮之后，篇幅一定会往「好写的方向」歪，不是往「读者需要的方向」。**

真实数据（写 `notes/insight-dsl` 那次）：

```text
  94 行   03 · 走一遍完整编译
 136 行   04 · 三段管道        ← 读者来这篇就是找它
 256 行   05 · 三处反直觉的设计  ← 最大的一节
 177 行   07 · 怎么保证它是对的  ← 第二大的
```

**读者最想看的那节只排第五，而「测试」排第二。**

根因不是偷懒 —— 是**「反直觉」「测试」这类内容每一点都能独立成段，好写；而「怎么工作」要讲清一条链上的每一步，难写**。写着写着就歪了。

**一条可操作的判据：**

```compare
first: 假想
head: [意味着什么, 篇幅应该]
rows:
  - 把这一节整段删掉，读者还能理解主题吗:
      - "它可删 → 是边角料"
      - "短"
  - 删掉之后主题就讲不明白了:
      - "它是主线"
      - { text: "==最长==", tone: green }
```

**半小时能做完的度量**：

```bash
grep -nE '^## ' notes/<slug>/note.md
```

把每节的行数算出来，排一下序。**如果最大的一节不是「怎么工作」，就是歪了。**

重写之后：

```text
 435 行   04 · 三段管道        ← 是第二大的两倍多
  78 行   06 · 怎么保证它是对的  ← 从 177 压到 78
```

```callout
tone: amber
icon: ⚠
text: |
  ==**「抽出来的内容」看着比主线重要，是因为它独立成节了。**==

  `insight-dsl` 那篇单列了一节「三处反直觉的设计」，256 行。
  但那三处（include/exclude 写法、派生字段、权限下推）**本来就在「拼 SQL」里面**。

  抽出来之后两头都亏：

  - 主线缺了细节，变得单薄 —— 读者看完「三步管道」还是不知道每一步具体干什么
  - 细节离开上下文，读起来像三个孤立的知识点

  ++只有「主线讲完之后的延伸」才该独立成节。从主线里抽出来的，要并回主线。++
```

#### 复盘 ⑥ · 语气审计

写完通读一遍，按这张表查。这些都是真实踩过的：

| 症状 | 例子 | 改法 |
|---|---|---|
| **破折号过多** | 「第二段不重新检查空列表**——**那是第一段的职责」 | 拆成两句，或换逗号 |
| **对话腔起手** | 「**结论：**用 Knex」「**补一句**容易搞错的」「**用一句话验**」 | 直接说内容 |
| **辩护腔** | 「**但要说清楚：这不是「必须要」。**」 | 删掉整句 —— 那是讨论过程 |
| **提醒腔** | 「**注意**它只改变排版」「**其实**」「**必须**」 | 删掉这两个字 |
| **排除式论证** | 「这不是 X，而是 Y」 | 读者没听过 X。直接说 Y |
| **编排说明** | 「三条理由，按重要性排：」 | 直接列，不用报幕 |
| **元叙述** | 「这一节的每一处，只看代码都看不出为什么」 | 那是写给你自己的 |
| **加粗过密** | 一段里五个 `**` | 全篇加粗数应该是个位数 |

```callout
tone: amber
icon: ⚠
quote: true
text: |
  ==**一条总的规则：文档只陈述「是什么」和「不这么做会怎样」，不写「我为什么没选另一个」。**==

  后半句是**讨论过程**，不是文档该有的东西。
  它是对话里说给对方听的，落到文档里就变成了辩护。
```

**可查的量化**（写完对着 grep 一遍）：

```bash
grep -c '——'  notes/<slug>/note.md     # 目标 < 5
grep -c '\*\*' notes/<slug>/note.md     # 目标 < 20
grep -c '注意\|其实\|必须\|唯一' notes/<slug>/note.md   # 目标 0
```

#### 复盘 ⑦ · 图解缺口审计

==这是和复盘 ⑤ 并列的最重要一步，因为它直接决定「这份东西为什么存在」。==

**做法：把正文里所有描述「空间 / 顺序 / 状态」的句子捞出来，逐条问一句「它为什么还是文字」。**

```bash
# 把这些「叙述性信号词」全 grep 出来 —— 命中的每一行都是缺口候选
grep -nE '先|然后|接着|之后|最后|变成|指向|包含|位于|上一层|下一层|依次|交替' notes/<slug>/note.md \
  | grep -v '^\s*[0-9]*:\s*[|>#]'
```

命中之后，按三种情况处理：

```compare
first: 情况
head: [怎么办]
rows:
  - 确实在讲顺序/位置/状态: [{ text: "补图。优先用现成积木；没有合适的就按原则 ⑦ 的四条路走", tone: green }]
  - 是个判断或理由（「为什么不用 X」）: ["留着。这是图替代不了的"]
  - 是操作清单（①②③④）: ["留着。它没有空间关系，画成图更绕"]
```

**还有一个更快的自检**：写完一篇之后，把所有的 `` ``` `` 围栏块和正文段落**分别数一遍**。

```bash
grep -c '^```' notes/<slug>/note.md          # 图/积木用了多少个
awk 'BEGIN{n=0} /^```/{f=!f; next} !f && NF && $0 !~ /^[#>|-]/ {n++} END{print n}' notes/<slug>/note.md
```

> 正文段落数 ÷ 2 就是「多少段配一张图」。
> ==如果这个比值大于 3，回头看看是不是有几段该画没画。==

**第二条检查：关键图的信息量（原则 ③）。**

逐个打开这一篇的图，问三句：里面有没有「量」？有没有「方向」？盖住正文它还讲得通吗？
答不上来的那张，回去查原理重画。

```callout
tone: violet
icon: 🧭
quote: true
text: |
  ==**一次真实的返工**：有人指出「红框里这几段为什么不用图 —— 我们不就是图解吗」。==

  那几段讲的是：程序和进程的关系（一个文件 → 若干进程）、
  A 等盘时 CPU 去跑 B 再被中断叫回来、轮询到中断驱动的演进。

  **三样都是标准的「关系 / 顺序 / 时间线」，全都该有图。**

  根因是被误读成门槛的那句「只有卡点值得画图」。
  现在那句话说清楚了：==卡点决定先画哪张，不决定画不画。==
```

#### 复盘 ⑧ · 别用画法掩盖密度

**整体图读不懂时，第一反应往往是「怎么把线藏起来」，而不是「线是不是太多了」。**

真实事故：一张 15 个零件、13 条边的整体图，密密麻麻。我的处理是
**把线画在零件框底下**（这样擦碰看不到）、**调低透明度**、**聚焦时才显示**。
看起来「能跑」，视觉检查也是绿的 ——

但它**没有解决任何问题**：线还在那里，只是从「看得见的乱」变成了「看不见的乱」。
而用户的反馈恰恰是同一件事的两面：==他说「线在乱飞」「又是重叠」，
工具（archify 的校验器）说的是「边穿节点 / 交叉 / 微段」——
这是同一个抱怨。==

```callout
tone: red
icon: 🎭
text: |
  **判据：你做的这个改动，是让图**更清楚**了，还是只是让它**更不容易被挑错**？**

  - 调间距、拆成两张、把并列的东西从箭头串改成扇形 → ==更清楚==
  - 把线压到框底下、调低透明度、只在聚焦时显示 → ++更不容易被挑错++

  第二种不是优化，是掩盖。而且它**不会报错** —— 检查工具和肉眼都会被骗过去。

  ==真正的解法几乎总是「改图的结构」：拆开、少画、把关系画成它本来的形状。==
```

**这一条不只适用于图。** 凡是「改一改让它看着没问题」的动作，都要先问这一句。

#### 复盘 ⑨ · 照着自己写过的规矩做

**这一条比 ⑧ 更难受：规矩早就写在 skill 里了，我没照做。**

真实事故：拿挤在一起的网格布局去试 archify，失败了三次。
三次都得出结论「它画不了这个」—— 分别是「画不了分层带」「框不能嵌套」「只能自己写」。

**三条全错**，而且 ==两条的正确写法就写在 skill 自己的「结构化图」那节里==：

| 我说「它不行」 | skill 里早就写着 |
|---|---|
| 画不了分层带 | `boundaries` 包住一行的节点就是带 |
| 框不能嵌套 | （这条 skill 里没写，是真缺 —— 已补） |
| — | ==「写法参考 `~/.agents/skills/archify/examples/*.<type>.json`」== |

而那个 `examples/` 目录里，**第一个架构图例子**就是正确用法：

```json
"layout": null,
"clients": { "pos": [38, 300] },
"edge":    { "pos": [230, 300] },     // 每步 200px，手工写死的像素坐标
"gateway": { "pos": [430, 300] }
```

==我一次都没打开过那个目录。==

```callout
tone: amber
icon: 🔧
text: |
  **顺序应该是：**

  1. 先用**参考实现自己的例子**证明「这工具能做这件事吗」
  2. 再证明「我能让它做这件事吗」—— 照它推荐的用法来
  3. **两条都试过还不行**，才轮到「自己写」

  ==跳过第 1、2 步直接自研，代价是把自己重新踩一遍那个领域几十年的坑。==

  ++判断「该不该自己写」也要有证据：「我试了它的**正确用法**，它确实做不到 X」
  才算证据；「我试了三次没调通」不算。++
```

**这一条的代价**：因为跳过它，我手写了约 200 行布局 + 布线代码，
然后在上面连续修了七八个几何层的经典 bug（端口落在错的一侧、跨带通道借到画面外、
坐标基准搞错、量完坐标再改高度）—— 而这些正是布局引擎几十年专门在解的问题。

### 第 9 步 · 交付后的自我反馈

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==**每次交付完，回头问一遍：刚才哪一步慢？哪一步反复来回？**==

  这一步不是「再读一遍稿子」—— 那是第 8 步。

  这一步看的是**过程**，不是**内容**：
  **我在跟工具较劲的地方，就是下一个会话会再较一次劲的地方。**
```

**关键区分**：

```compare
first: 发现的问题
head: [改哪里, 例子]
rows:
  - 内容问题（这一篇讲错了 / 漏了）:
      - "改这一篇"
      - "「卡点图没画」「概念没配例子」"
  - "**工具问题**（跟内容无关，但耗了时间）":
      - { text: "==改工具，然后把改进写回这份 skill==", tone: green }
      - "「截图被截断」「要手动关标签页」"
```

**工具问题不会自己消失。** 你不写回来，下一个会话的 agent 会一模一样地再踩一次 ——
而它甚至不知道自己踩了，只会默默地多花二十分钟。

#### 十个信号：出现就是在提示「工具该改了」

```compare
first: 信号
head: [说明什么, 怎么办]
rows:
  - 同一条命令跑了 >2 次才过:
      - "工具一次没把话说清，只能试探"
      - "让它在第一次就把原因和修法打全"
  - 一个积木看了 3 次截图还没对:
      - "这个形状它画不了"
      - "换积木 / 拆两张图 / 真的画不了就进 `visual-baseline.json`"
  - 手算坐标、猜尺寸、硬填数字:
      - "积木缺自动测量"
      - "==加测量，别手填== —— 手填的数字换个屏就错"
  - 反复「改 → 构建 → 截图 → 看」:
      - "反馈回路太长"
      - "缩短它（`npm run block` 就是为这个加的）"
  - 绕过了工具（手写 HTML、手动裁图、自己写脚本）:
      - "工具的边界差一点"
      - "把绕过的那个动作变成工具的一个参数"
  - 产生了要手动收拾的东西:
      - { text: "工具默认行为不对", tone: amber }
      - "==改默认值，别靠人记得加参数=="
  - 同类内容手写了三遍:
      - "它是个新积木"
      - "见 `references/extend.md`"
  - 文档说的和工具做的不一致:
      - "文档在骗人"
      - "改一边 —— 通常是文档"
  - 并行会话改坏了同一个文件:
      - "共享文件缺约定"
      - "把约定写进「多会话协作」"
  - 同一个坑，同一篇里踩了第二次:
      - { text: "规则写在了错的地方", tone: red }
      - "==把它挪到用它的那一节旁边==，别让它躺在文档末尾"
  - 代码写了吗、页面上也有，但**看着就是不对**（挤、偏、少一块）:
      - "**静默的渲染问题** —— 没有报错，只有眼睛看得出来"
      - "==给探针加一条检查==，别指望下次还记得看"
```

#### 真实案例：这条规矩是怎么来的

```callout
tone: amber
icon: 🧱

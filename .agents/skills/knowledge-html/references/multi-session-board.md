# 会话板：多个 agent 之间怎么通信

> 这份文档定义了一套**跨会话通信协议**。它解决的问题是：
> 用户在同一个仓库上开好几个 AI 会话（各自一个 worktree、各自一个规划），
> 它们平时互相看不见 —— 于是会出现「提交撞车」「两个人改同一个文件」
> 「一个人把另一个人做到一半的东西提交了」。

---

## 为什么是「一个文件」而不是别的

**因为这是 pi 官方推荐的跨进程协调方式。** `pi-subagents` 自己的文档写着：

> `pi.events` is in-process only. It does not reach separate Pi processes or child
> subagents; use **the file lifecycle artifacts** or `pi-intercom` for cross-process
> coordination.

`pi-intercom` 是一个需要额外安装的扩展 —— 没装的时候，**文件就是唯一的通道**。

这条路子还有几个额外好处：

| 好处 | 说明 |
|---|---|
| 零基础设施 | 不需要守护进程、不需要端口、不需要网络 |
| 和 git 无关 | 它在仓库**外面**，所以不会被提交、不会有冲突、不需要 pull |
| 任何会话都能用 | 不依赖某个会话的 commit 状态 —— 纯 shell 一行就够 |
| 人和 AI 都能读 | 就是个 markdown 文件，用户自己也能看 |

## 文件在哪

```
~/works/codes/.kh-board.md
```

推导方式（**在任何 worktree 里结果都一样**）：

```bash
BOARD="$(dirname "$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")")/.kh-board.md"
```

`--git-common-dir` 是所有 worktree **共享的那一个** `.git`，所以从它往上退两级
就落在所有 worktree 的共同父目录。这一步是整个协议能成立的关键：

```
~/works/codes/knowledge-html/     ← 主仓库
~/works/codes/kh-ipc/             ← worktree
~/works/codes/kh-go/              ← worktree
~/works/codes/.kh-board.md        ← 板子在这里，三个都看得见
```

> ⚠️ **方案文件**（`plans/*.yaml`）放在仓库里是对的，但**通信**不能放在仓库里 ——
> 各 worktree 是各自独立的目录，仓库里的文件互相看不见。

## 消息格式

**一条消息 = 一行。** 这是为了能做到「原子追加」。

```
[<会话名> | <月-日 时:分> | <状态>] 在做…; 会动…; 需要…
```

- **会话名**：用 worktree 目录名（`basename "$(git rev-parse --show-toplevel)"`）
- **状态**：`进行中` / `帮助` / `冲突` / `收工`
- **在做 / 会动 / 需要**：三段自由文本，用 `;` 隔开

真实例子：

```
[kh-ipc | 10-02 02:40 | 进行中] 在做 IPC 对比 6 篇; 会动 notes/ipc-compare-*、assets/app.js 的 WIDGETS 段; 需要 无
[kh-os  | 10-02 02:45 | 帮助]   求助：我要把 assets/blocks.css 的 .flowd-row gap 从 30px 调到 44px，会影响所有 flow 图的标签宽度。kh-ipc 你那边有 flow 吗？ 到 03:00
[kh-ipc | 10-02 03:05 | 冲突]   我也有 flow（sched-lab 那张）。建议你改的时候只用 .flowd-row 加个 modifier class，别动全局。我先去写别的，到 03:30 没回复我就按你的方案接受
[kh-os  | 10-02 03:10 | 进行中] 按 kh-ipc 说的办：新增 .flowd.wide-label 而不是改 .flowd-row
```

## 五条规则

### ① 一条消息一次 `printf >>` 追加

```bash
printf '%s\n' "[$NAME | $(date '+%m-%d %H:%M') | 进行中] ..." >> "$BOARD"
```

`>>`（`O_APPEND`）的一次 `write()` 是原子的。只要**一条消息在一次调用里写完**，
就不会和别人的写交错。

### ② 永远不要重写整个文件

**不要**用编辑器打开改，**不要**用 `>`（那是截断）。

```bash
printf '...' >  "$BOARD"     # ❌ 别人刚写的全没了
vim "$BOARD"                 # ❌ 保存时会覆盖掉这期间的写入
printf '...' >> "$BOARD"     # ✅
```

### ③ 不编辑别人的消息

要更正就**再发一条**。板子是**流水账**，不是文档 —— 让读者看到「先说了什么、
后改成了什么」，比一个被改干净的现状更有信息量。

### ④ 不阻塞

声明完就去干，**不要等回复**。

- 真撞上了 → 发一条「我建议怎么办 + 我的截止时间」，然后**去干不冲突的部分**
- 到点没回复 → 按自己写的方案干，**再发一条告诉对方你按什么干了**
- 对方的反对意见可能在你干完之后才到 —— 那时再看要不要改

> 这条很重要。两个只在被调用时才醒着的 AI，如果互相等，就是死锁。

### ⑤ 关键动作前后各读一次

板子**不会通知你** —— 它只在你去读的时候生效。所以：

| 什么时候读 | 看什么 |
|---|---|
| 开工时 | 全局态势：有几个人、各自在动什么 |
| **动共享源之前**（`assets/*`、`tools/*`、`.agents/skills/**`） | 有没有人正在动同一个文件 |
| **推送之前** | 有没有人和你撞在同一批文件上；有没有人给你留了话 |
| 收到别人的求助 / 冲突消息后 | 回一句 |

## 它解决不了什么

诚实说清楚，免得当成万能药：

```compare
first: 问题
head: [板子能帮上什么, 真正的解法]
rows:
  - 两个人改同一个文件: ["只能让他们**知道**对方在改，不能阻止", "worktree 隔离 + 改共享源要小步 + 改完立刻提交"]
  - 提交时带上别人的半成品: ["发一条「我要推了」能减少概率", "==点名 `git add`，不用 `-A`==；推之前 `npm run status` 分类看一遍"]
  - 推送被拒（别人先推了）: ["提前知道能少撞几次", "`git pull --rebase` → `npm run build:standalone` → 再推"]
  - "`index.html` 冲突": ["——", "它是生成的，**别手动 merge**：随便选一边，重建，再提交"]
  - "`visual-check` 报出并不存在的问题": ["——", "==并行会话也在跑无头浏览器时会假阳性==。等负载降下来重跑"]
  - 两个会话都在等对方: ["规则 ④ 就是为了防这个", "声明完就干，不要阻塞"]
```

**一句话**：板子解决的是**信息不对称**，不解决**资源争用**。
资源争用还得靠 worktree + 点名 add + 改完立刻提交。

## 附：为什么不用 git 分支来通信

有人会想：开一个 `board` 分支，大家往上提交不就行了？

不行，有三个硬伤：

1. **每次读都要 `fetch`** —— 板子要的是「随手看一眼」，走 git 就变成了一次网络操作
2. **write-write 冲突要人工解** —— 两个会话同时提交，第二个必然冲突，而「合并两条公告」没有任何自动化价值
3. **读到的可能是旧的** —— 别人 push 了你没 pull，等于没看

文件直读没有这三个问题：读永远是「当前的样子」，写永远不会冲突。

# 把知识变成能看懂的 HTML

## 触发与项目位置

用户以 **【图解】** 开头（后面可接内容、飞书链接、或「看上面」）。

项目固定在：

```
~/works/codes/knowledge-html
```

正文就在这一份里：原则、工作流、硬约束。`references/` 里三份是用到再打开的细节：`blocks.md`（积木字段）、`extend.md`（加积木）、`multi-session-board.md`（会话板协议）。文末「参考」有命令和文档索引。

写之前先按原则 ⑦ 判断读者的起点；选择表达与工具看原则 ⑧⑨；排版前读 [原则 ⑩](#原则-⑩-版面服务阅读图按内容铺开)，写正文、图注和导览前读 [原则 ⑪](#原则-⑪-平实连贯准确地写)。不要等交付复盘才第一次检查这些要求。

## 动手前

==这个仓库会被多个会话同时编辑== —— 用户会同时开好几个窗口，每个窗口一个 agent。

有五条规矩返工最多，先看完再动手：

1. **会话隔离**：优先开 worktree；在共用目录里干活就点名 `git add`，别用 `-A`
2. **产物全量**：构建产物每次全带上；源和产物必须一起提交
3. **不替别人改**：别人的笔记有问题就报告，不擅自改
4. **图必须量**：改完图跑 `npm run visual-check`，构建通过不等于画对了
5. **收尾写回**：交付后回「第 10 步」，把这次跟工具较劲的地方写回 skill

详见「多会话协作」一节。开工前跑 `npm run status`，收尾跑 `npm run done`。

**先分清用户要一张图，还是要借这张图理解整个项目。**

例如，用户说「画个架构图」，可能只想快速看组成，也可能想从零理解项目。后一种情况还需要概念和阅读顺序；直接交图，容易让他不断追问图里的名词。先按第 0 步判断，不确定就问，不替用户扩大任务范围。

==所以先读「第 0 步」。== 先分清他要的是一个具体答案，还是一条理解路径。

**另一个常见的错：把原文搬进 HTML，再配几张插图。**

用户手上**本来就有文字版**（飞书文档、博客、代码）。他来找「图解」，要的是文字表达不了的那部分。段落换个排版搬过来，==交付价值是零==。

有「空间 / 顺序 / 状态 / 归属 / 对比」的地方，用图、控件或表，不要退回段落。

++完整判据在「原则 ①」。++ 交付前再过一遍「复盘 ⑦」。

## 平台 · 只在电脑屏幕上看

常规任务只设计电脑阅读的页面，不另做手机版。图义和完整交互优先，不为窄屏删节点、隐藏关键标签或把空间关系改成普通卡片；已有组件的安全降级保留。

桌面视口也可能很窄，不能把浏览器窗口大小直接当成设备类型。布局按本次目标页面的可用宽度设计，不套统一画幅，也不以工具默认视口代替用户屏幕。

版面设计与验收统一按 [原则 ⑩](#原则-⑩-版面服务阅读图按内容铺开)。共享组件或外壳仍做基础窄屏冒烟；只有用户明确提出手机需求时，才另确认完整移动端目标，不自动扩展每篇笔记的任务范围。

## 谁在读

这些 HTML 只给同一个人看。他用这份 skill 给自己把东西看懂，不打算分享，也不写成给外人的教程。

同一段文字他可以读很多遍，仍不如一张图收得快。有空间、顺序、状态、归属或对比，就做成图、控件或表。文字只留图给不了的判断和理由。

## 原则 ① · 有结构就不要留在段落里

**判据：这段如果留在段落里，他要不要自己在脑子里维护结构？** 要自己排位置、排顺序、认状态、认归属，或比较差异，就做成他扫一眼能收下的形式。空间、顺序、状态、归属、对比是常见的几种，不是全部。

图、控件、表是常用的三类，也不是全部。现有积木里有更合适的，用那个。

| 这段文字在说什么 | 该用什么 |
|---|---|
| 要同时看见几样东西在哪、彼此什么关系、各属于谁 | 一张整体图，不要拆成几张小图。见原则 ② |
| 谁指向谁、谁包含谁 | `tree` / `flow` / `arch` |
| 谁和谁并列，没有指向或包含 | `cards` / `compare` |
| 先发生什么、后发生什么、谁在等谁 | `seq` / `lane-stack` / `flow` |
| 某个东西从 X 变成了 Y | `journey` / `flow`（`shape: pill`） |
| 按时间演进 | `timeline` |
| 几个东西按维度对比 | `compare` / `matrix` |
| 同一条轴上多种方案的差异 | `demo` 控件 |
| 纯因果论证、经验判断、取舍理由 | 文字 |

他已经读过这段文字。再贴一遍，只是换了个字体。里面的结构做成图、控件、表，或更合适的积木。

只有在这里才说得清的判断，留文字。比如「为什么用链表而不是数组」：它回答的是为什么，不是长什么样。

下面三类留文字：

- 清单式的操作步骤。①②③④ 之间没有空间关系，画成图要多绕一层。
- 真正的判断和理由。它回答的是为什么，不是长什么样。
- 一句话的过渡和结论。它是用来断句的。

## 原则 ② · 整体图

整体图把相关对象放在同一张地图上，帮助读者从整体上把握一件事。

整体图按原则 ⑩ 使用目标页面的可用宽度，把真实分区、关系和节点细节铺开，不用固定小画幅限制信息，也不为填满屏幕凑节点。看整张图，能看见这件事的全貌；涉及运行过程时，也能看见它整体往哪运行。层级要分明。局部里要有细节，不是只有名字。整张图要清楚。

有的事，把零件一个一个讲是讲不清楚的。

比如解释 Linux 容器，不能只给出「namespace、cgroup、rootfs」三个名字。需要把进程与它们放在一起：namespace 隔离进程看到的系统视图，cgroup 限制和记账资源使用，rootfs 提供它看到的根目录文件树。这些机制怎样围绕进程组合起来，才是这个例子想说明的整体关系，不是让读者先学完三个术语再读本节。

可运行的参照是 `notes/process-thread-relation/note.md` §01。读这个示例时，重点看画法：几条线程平级排列，共用的文件表和地址空间各画一份，CPU 与物理内存放在进程框外；节点内还有数量、地址和使用者。它示范的是「归属、共享和执行关系同时可见」，具体内核结构和加载步骤由那篇笔记解释。

他熟悉其中一个零件时，从那个零件看起，就能把它接到旁边的零件上。比如他熟悉进程，一张图就能记下进程和 socket 的联系和区别。图里的结构越多，他越容易看进去。

### 什么时候铺开整张图

要把握一件事的全貌、位置和归属，就用整体图；涉及运行过程时，把过程也放在同一张图上。只讲静态组成时，不为满足格式编造运行方向。

| 要理解的 | 用什么 |
|---|---|
| 一件事的全貌，以及它整体往哪运行 | 整体图 |
| 一个概念被当成一个东西，其实是一组东西 | 整体图。容器是典型 |
| 名词散在各处，拼不出谁属于谁 | 整体图 |
| 要同时看见 A 和 B 的联系和区别 | 整体图 |
| 只剩一条没有位置、没有归属的短顺序 | `flow` / `journey` / `seq`，不必铺开整张地图 |

### 一张图是一个整体，不是一份材料

材料的边界不是图的边界。他交来的一篇文档、一章、一次「【图解】」，只说明这些东西一起出现过。一起出现过，不等于它们是一个整体。

先把材料里的东西分开。拿掉 B，A 的全貌还在；拿掉 A，B 的全貌也还在。A 和 B 就是两件事，各有各的整体图。C、D 也一样。不要因为它们写在同一节、用了同一个总标题，就画进同一张图。

一件事自己也可以再拆。它比较大，里面有的点相对独立：拿掉那个点，这件事的全貌还在；那个点自己又有需要整体看清的结构和层级，涉及运行时也有自己的过程。那个点就再做一张整体图，不塞进外面那张。

进程和线程的首图回答「一个进程拥有哪些资源，多条线程怎样共用它们」。所以资源、线程与使用的硬件需要同时在场。地址空间怎样隔离、创建线程有哪些选项、CPU 怎样排队调度，是另外的解释主题；首图保留入口和对外关系，细节在各自的图里展开。

同样，容器组成需要把进程和几种隔离、限制机制放在一起；磁盘调度则回答「读写请求怎样被安排」。即使它们出现在同一份材料里，也不应为了共用标题而塞进同一张图。

判断只有这一句：这些东西必须同时看见，才构成这一个整体吗？

必须，就留在这一张上，按原则 ⑩ 排开分区和关系，局部细节放进格子。不必同时看见，就各自另做一张。这在动笔之前定，不等它们画到一张图上互相挡了再拆。互相挡是一张图排坏了。彼此独立是从一开始就不是一张图。

### 关系不要全画成箭头

不要把不同的关系全画成箭头。下面几种是整体图里常出现的，还会有表上没有的关系。

| 关系 | 它回答什么 | 怎么画 |
|---|---|---|
| 并列 | 挂在同一个东西上，谁也不导致谁 | 从它散开，不串成一条 |
| 分类 | 这东西属于哪一类 | 带，当背景。层级靠带来分 |
| 包含 | 这东西在谁里面 | 框套框。写明是组成，还是只是逻辑上归在一起。再套一层，就要多一条原先看不见的归属；只换标题不算新的一层 |
| 指向 | 谁引用谁，东西还在原处 | 资源只画一份，真实引用默认分别画线。需要代表线时，标清基数和代表范围，并补全关系表，见后文「关系怎么落到字段上」 |
| 流动 | 谁把东西给了谁、然后怎样 | 箭头。整张图的运行方向要能顺着这些箭头看出来 |
| 在外 | 被用到，但不属于这个整体 | 画在框外，但仍留在这张图上 |

容器那篇曾经把「进程 + namespace + cgroup + rootfs」画成 `进程 → namespace → cgroup → rootfs`。读起来像谁导致谁。这四样是并列挂在同一个进程上的，从进程散开，不串成一条。

一条线要说得出是指向、包含还是流动。并列的东西不要用线串起来。说不出关系的线，删掉。

### 这些关系放在同一张图上

上一张表是在说每种关系怎么画，不是每种关系各画一张图。

仍以进程和线程首图为例：用户态、内核态、硬件用背景带分类；进程框内用子框组织共享资源与线程；线程之间是并列，各自的引用线指向共享资源；硬件在进程框外，执行与地址翻译等实际过程用箭头表达。它们共同回答一个问题，不需要按关系类型再拆图。

容器也一样。namespace、cgroup、rootfs 和进程出现在同一张图上，从进程散开。

### 整张图不要拆开

同一件事的各个局部留在这一张图上，能在节点尺度讲清楚的细节也留在格子里。

局部机制在节点尺度讲不清楚时，就另补详图或一节。判断的是解释效果，不只是文字能不能塞下；需要逐步展开、多个反例或独立交互时，也可以补详解。整体图仍留着它的位置和它跟旁边的关系。详解里的名字、标识和归属跟这张图一样，看完能放回原来的位置。进程和线程那篇的首图上有 `execve`，下一节再写它换映像的步骤。

已经判定属于这一个整体的局部，不要因为节点多、线多就拆开。彼此独立的东西，按「一张图是一个整体」已经分成多张图，不要先画在一起再等它们互相挡。

### 全图、点选、导览

| 方式 | 做什么 |
|---|---|
| 全图 | 看全貌、层级；有运行过程时看整体方向。分区、关键对象、主要关系在这张图上就能看见 |
| 点选 | 点一个对象，看它格子里的细节，以及通过图上实际连线相接的邻居，再沿邻居走 |
| 导览 | 围绕一个问题，按运行路径或理解顺序突出这一步需要的对象并解释 |

图本身不动，只改变眼前看哪一块。点选和导览不移动节点。随时回到全图。实际运行方向不靠导览才出现。

每条导览只讲一个问题，每一步只突出这一步需要的对象。运行图可以沿一条路径走，静态图可以逐层讲归属或对照差异，不强造一条因果链。节点上的详细解释放在点开之后的说明里，名字和主要关系在全图上仍然能看见。

较复杂的整体图默认配零件说明和导览。简单图中，不增加解释价值的面板或导览可以省略，关键节点的内容不能因此退回一行名字。区域、格子入口按真实关系配置，不为配齐字段虚构归属或跳转。

从已经认识的那个零件点进去。这是进入这张图的方式，不是要求图上每个东西他都已经认识。图注写成从哪个零件进入。导览按所讲问题的顺序写。

### 节点里要有结构

只有一行名字的矩形拼成的是目录。关键零件的矩形要装下它自己的结构：有几个、多大、朝哪长、属于谁。局部的细节优先放在这些格子里；节点尺度讲不清楚的，按上一节补详解。

想加内容时，先往已有节点里加，再加节点。只有已经属于这一个整体、又在格子里放得下的内容，才往这张图里加。彼此独立的，另做一张整体图。为了看起来清爽，把内容收成一行字，是不该做的。

节点数量不决定拆图。先按原则 ⑩ 在目标视口检查最终显示：内容有没有可用空间，文字能不能读，连线能不能分辨。不能为了多塞节点缩字，也不能为手机拆散整体或藏线。线多，只要每条都说得出关系，不因此判失败；线少，也不因此算清楚。

区域框、导览、节点里装什么，见 `references/blocks.md` 的 `arch`。这里不重抄。

## 原则 ③ · 图要有信息量，名词列表不算图

图要让人看见位置、数量、变化和工作方式，不只是认出几个名字。

下面用一个示意任务队列说明三层信息。先约定本例只有四个等待位置，按进入顺序取任务，队列满时拒绝新任务；这不是任何工具的默认配置。

| 层次 | 图里有什么 | 读者能理解什么 |
|---|---|---|
| 名字 | 一个写着「任务队列」的框 | 知道有队列，不知道里面怎样排 |
| 结构 | 四个格子，三个有任务、一个空着，标出进入与取出的方向 | 看见容量、占用和顺序 |
| 机制 | 取走最前面的任务后腾出一格；四格全满时，新任务走拒绝分支 | 看见什么时候变化、什么条件决定结果 |

关键图要到机制这一层。只在图外写「满了会拒绝」，却没画满队列和拒绝路径，仍把重要信息留给了文字。原则 ① 中的判断和取舍理由继续用文字，不为了「图里有机制」把所有论证都画成箭头。

写完盖住正文，看位置、数量和变化能否从图上读出。再改变本例的容量或任务数量，检查格子、状态或路径是否随之改变；如果图始终只是几个同样的名字，就还没把结构和机制画出来。

图四周空着时，先检查是否漏掉数量、方向或机制；不是为了填空而添信息。需要铺开时按原则 ⑩ 调整画布和布局。字号保持能读，已经排好的小图不要只靠放大来显得丰富。

## 原则 ④ · 画到小白认识的地方

图不能停在一个还需要继续解释的名字上。例如，调度图只画到「少量线程」，读者知道有线程，却还不知道任务怎么排队、由谁挑选、线程占着哪些核、最后发生了什么。

这里的小白指还不了解本篇机制的读者，不是对用户能力的判断。默认从具体结构和本篇已经讲明白的概念出发，不靠模型猜测「你应该懂这个」来决定在哪收笔。原则 ② 里的入口是从熟悉的零件走进图；这一条检查的是，图走到最后有没有落到能理解的东西上。

### 什么可以作落点

- 看得见的物件：例如 CPU 上哪些核被这组线程占用，哪些没有。
- 生活里遇到过的情形：例如三个窗口只开了一个。类比要标明对应关系，不能冒充实现。
- 亲手用过的东西：例如一个 git 仓库的 `.git` 目录。
- 本篇前面已经解释清楚的概念：例如前面讲过页表，后面就可以把页表当作落点，不必每次重新讲一遍。

落点随阅读进度变化。一个词第一次出现时需要解释，讲明白之后就可以继续用。不是所有图都要一路画到 CPU、磁盘或网卡；只有解释依赖这些资源时才画到那里。软件内部的关系已经讲清楚，也可以停在前面定义过的对象上。

### 按内容检查，不按积木名套清单

整体图、`flow`、`seq`、`lane-stack`、`journey` 都可能表达流转；`memmap` 等静态布局图主要表达位置、归属和尺度。用哪种积木，不决定它必须出现哪些环节。

1. **有流转，就画清输入到结果。** 涉及排队或调度时，画出队列、选择者、执行者和资源落点；没有这些环节的过程不补虚构的队列或调度者。
2. **有队列，就画出队列里的东西。** 用格子表现当前有几个、谁在等、从哪里入队、取走后去哪。容量有限时写明上限和满队列的处理；没有固定上限时就说明。画出的几格只是示意窗口时，标明它不是容量，数量和行为按原则 ⑤ 核对。
3. **有通路，就让人能沿线走。** 任务怎样交给线程、线程怎样占用核心，要有可追踪的关系。`submit`、`多路复用` 是路径的注释，不能只写一个词代替通路。连线仍按原则 ② 区分引用、归属和流动。
4. **有状态差异，就把结果画在图上。** 正在运行、正在等待、未被占用，用颜色、虚实或标注区分，并写明是哪一时刻或场景。不能只在图下面补一句「所以有些核会空着」，也不能把一个快照画成始终如此。
5. **有层级，就标清范围和跨层动作。** 操作系统图按真实关系区分用户态、内核态、硬件，并标出系统调用、中断等相关跨层动作。业务图按角色或系统边界分层，不套操作系统的三层。

在进程和线程图里，CPU、物理内存位于进程资源域框外，仍留在硬件区域内。其他图按真实归属摆放，不把「硬件在框外」套成通用规则。磁盘调度若是另一件完整的事，按原则 ② 另画整体图；同一块磁盘可以在本图作落点，在另一张图作主角。

例如一个示意场景：六个任务待执行，三条工作线程各取一个。此刻三个任务在跑、三个仍在等；在六个核的图上，标出这组线程占用的三个核，另外三个未被这组线程占用。这是在解释一个场景，不是在断言整台机器的其余核心始终空闲。

### 盖住正文，沿图讲一遍

用大约 30 秒讲清这张图的主过程；静态图就讲位置、归属和差异。讲到某个词需要停下来补定义时，检查它在图上或前文是否已经解释过。缺概念就补前置解释，缺关系、状态或资源落点就补图。30 秒用来找堵塞点，不是删掉必要内容的篇幅上限。

现有积木表达不了时，按原则 ⑨ 走组合、加字段、新建或 `raw` 四条路。局部在节点尺度讲不清楚时，保留它在整体图上的位置和对外关系，再补详解；不能为了迁就积木，把完整通路收成几个名字。

## 原则 ⑤ · 事实不靠猜

从少量原文画出丰富的图，往往需要补信息。补的是可核对的结构和机制，不是模型顺着句子编出来的细节。图上的数字、默认值、上限、版本、归属和因果都会被读者当真，写入之前先找依据，不因它不是关键图就跳过。

### 把说法和依据对上

核对两件事：能不能指出来源，以及那份来源是否真的支持准备写下的这句话。一个链接、一段搜索摘要或「我记得是这样」都不等于完成核对。读到对应段落、函数或输出，保留版本、平台、配置和输入等必要条件；稳定常识可以引用原始材料，数字、默认值和因果仍要逐项核对。

来源可以是公开文档和源码，也可以是用户提供的材料、本次项目代码或任务相关的本地文件。查证不扩大任务权限，不读取无关文件，也不把内部材料送去公开搜索。

- 内核文档、官方文档、RFC 和目标版本的实现，用来确定相应事实。
- 博客、教程、问答和另一个模型的回答，用来找线索与检索词，再回到原始依据。
- 仓库 issue 中的复现和维护者确认可以作证据，但问题描述或尚未确认的猜测不能直接当结论。
- 用户给的设计文档可以说明设计意图，不自动证明当前代码已经这样实现。

有没有限定条件，是检查信息是否被转述磨平的线索，不是判断一手来源的充分条件。二手文章也会写条件，一手文档也可能不适用于当前版本。

例如，假设某个队列默认有四个等待位置，但配置允许调整容量。核对后应写「默认四个，可配置」，不能写成「最多只能放四个」。要查的不只是数字，还有它究竟是默认值、当前配置还是硬上限。

### 怎么查，怎么写

先读手头与问题直接相关的原文和实现。知道是哪一页，就打开对应段落；不知道可信来源在哪，先搜索；手上已有具体断言，就核对支持它的原句和适用条件。按当前环境选择工具，例如用 `web_search` 找来源、`source_check` 核验断言、`fetch_content` 读指定页面；工具不可用时换等价方法，不把工具返回的摘要当成原文。

查原理、标准、数字和报错时，优先读英文原始材料；报错按原样检索。国内产品的行为和中文社区特有的约定，以相应官方文档或中文原文为准。还不知道英文名称时，先找对应词，再用它深入查。

行文仍用读者手上原材料的术语，第一次出现时括号附英文，例如「请求超时（request timeout）」。查证语言不是行文语言，不把正文的术语全部替换成检索词。

转述容易丢掉范围。例如「队列最多容纳四个等待任务」，不等于「整个系统最多处理四个任务」：执行者还可能持有正在处理的任务。省掉「等待」这个条件，图里的容量就会画错。

图中的归属也不能只靠措辞推断。「用户提交的任务」不意味着队列放在用户的电脑上；它可能存放在后台服务中。先核对实际存放位置和持有者，再把队列放进相应区域。

### 能安全复现的，对照实际实现

解释某个版本的实际行为时，先确认源码或工作区快照，再读对应入口和代码路径。设计文档写的是意图，实现体现该版本怎样做；两者不一致时区分写明，不把设计意图写成已经支持的能力。

能在授权范围内安全复现的，运行对应输入，打印返回值、错误或关键状态。先检查入口是否有外部副作用；会修改业务数据、调用外部系统或触发服务动作的验证，先确认权限，未获授权就只读实现。一次运行只证明这组输入和环境，不能据此推成「所有情况都这样」。

例如一个示意核对：设计文档写「处理函数会返回一份新数据」。如果运行后发现函数没有返回结果，而是修改了传入的数据，图就应表达「原数据被更新」，不能画成「返回一份新数据」。核对时同时看返回值和输入数据的变化，不能只看文档里的输入输出描述。

还要分清正在核对的对外函数与内部辅助函数。内部函数有返回值，不等于对外函数也返回那份结果。直接运行源码的具体办法见后文「变体：源码通读」。

### 查不到时怎么办

- 缺的是解释主线必需的事实：指出缺什么，请用户补材料或确认版本。可以先给骨架和待核问题，不把缺口编成已完成的解释。
- 缺的是非关键数字或细节：不影响解释时省略它；需要举例时明确标成示意或假设，不冒充实测值、默认值或上限，不为填满画布凑细节。
- 只有设计文档，无法核对实现：按文档解释，并注明「这是文档里的说法，未核对实现」；有源码但不能运行时，说明已读哪些实现、哪些运行行为未验证。
- 来源相互矛盾：先对齐版本、平台、配置和输入。仍不能确认时保留分歧和待核项，不挑一句最符合当前图的说法当事实。

第 5 步整理待写说法、依据、条件和核对结论。后续补新节点或新交互时，新出现的事实也走同一轮核对。复盘 ①b 在交付前再核一次，检查正文、图和速查表是否说的是同一件事；来源及版本写入 `meta.json.sources`。Agent 自己查证或运行过，仍不等于人工核对，不自行填写 `verified`。

## 原则 ⑥ · 讲透卡点，不是搬运内容

**你的任务不是「把内容搬进 HTML」，是「把用户卡住的那个环节讲透」。**

原文可能包含重复解释、铺垫和客套。先判断哪些内容有助于回答用户的问题，再删去不必要的部分，不按固定比例压缩。HTML 的价值在于把关系、变化和操作过程直接呈现出来，而不是把原文换个排版再贴一遍。

所以：**先找卡点，再决定画什么图，最后才写文字。**

```compare
first: 不是
head: [搬运式, 讲透式]
rows:
  - 结构: ["照着原文分段", "按「卡点」重新组织"]
  - 篇幅: ["原文多长就多长", "砍到骨架，该删的删"]
  - 图: ["配几张插图", "把讲不清的地方变成图或交互"]
  - 判据: ["「内容都在了」", "「用户看完能说出所以然」"]
```

## 原则 ⑦ · 先对齐理解层次

每次任务中，读者已有的基础可能不同。同一个人也可能认识词而不清楚关系，或知道流程只想定位代码。写之前先找出这次缺少的是词的含义、对象的组织，还是实际运行过程，不一律从零讲起。

| 读者卡在哪里 | 理解层次 | 从哪里开始 |
|---|---|---|
| 不知道这些词指什么、为什么需要它们 | 概念：是什么 | 具体业务场景、对象定义和一份可核对的例子 |
| 认识每个词，但拼不出谁属于谁、谁和谁共用 | 组织：怎样组成整体 | 分类、包含、共享和引用关系 |
| 已知道组成，但不知道输入怎样变成结果 | 架构 / 机制：怎样工作 | 一次真实输入经过的路径、分支、状态变化与代码实现 |

「没接触过这个领域」通常先补概念；「看不懂」本身不是层次诊断。能从用户问题找到明确缺口，就直接补那一块；缺口会影响产物范围而又无法判断时，问清楚，不用大量前置教程代替判断。

### 从零介绍概念时，先给场景和对象

| 不要 | 应该 |
|---|---|
| 在概念介绍中堆类型名、类名和文件名 | 用业务词说明对象与作用；源码标识留到实现层 |
| 只给「输入是某种树、输出是另一种结构」 | 先说用户要做什么、输入长什么样、希望得到什么结果 |
| 没有背景就展示表结构和字段清单 | 先给场景与一份数据或操作例子，再解释相关字段 |

概念层不出现类型名 / 类名 / 文件名的约束仍然保留；这针对从零的概念介绍，不是要求源码定位任务隐去用户已经指定的函数或文件名。源码名字是定位信息，不能代替对概念的解释。

例如介绍上传处理，先解释「上传任务是待处理的文件与请求」「队列保存等待任务」「处理者取走任务并生成结果」，再把三者连起来。实际数据优先；只能构造示意时按原则 ⑤ 标清，不冒充业务事实。

### 检查开头是否接住了读者

从零理解整个项目的笔记，检查开头能否让读者说出它解决什么问题、有哪些基本对象，再进入组织和实现。已有基础的具体问题，检查缺少的前置是否补齐，不强行凑前三节，也不重复定义已经讲明白的词。内容跨度与知识树仍按第 0、1 步确认。

## 原则 ⑧ · 表格对照属性，图连接对象和过程

表格和卡片不是低一级的表达。它们适合把属性、方案和区别摆在一起；图适合让人追踪位置、归属、连接、顺序与状态。按要回答的问题选择，不按「看起来像图」判断。

| 要回答的问题 | 适合的表达 | 不能丢掉什么 |
|---|---|---|
| 几个对象有哪些共同维度、差在哪 | `compare` | 对照维度、具体属性和例子 |
| 并列对象各是什么，或单个对象的职责与输入输出 | `cards` / `spec` | 定义、具体样子和使用场景，不伪造先后关系 |
| 谁包含谁、谁引用谁、东西放在哪 | `tree` / `arch` 等结构图 | 归属、位置和实际关系 |
| 输入经过哪些环节，分支与结果怎样出现 | `flow` / `seq` / `lane-stack` / `journey`，或整体图上的导览 | 路径、条件、状态与结果 |
| 改一个条件才能看清差异 | `demo` 控件 | 操作、变化与可核对的结果 |
| 为什么这样设计，什么条件下不成立 | 文字，必要时配对照 | 依据、理由与例外 |

`spec` 可以快速列输入、输出和职责，却不会自动说明中间怎样工作。若「处理」一栏只写「处理数据」，即使表格完整，机制也没有讲清楚；还要画出相关对象、路径和变化。反过来，只有属性对照的问题，用表就能讲清楚，不为追求大图再造连线。

### 从概念到机制的讲解顺序

用户的原话是：「先介绍概念，让我对概念建立认识；再用图把概念连起来。」这要求先建立认识，不等于每个概念各有一张独立图。

1. 按原则 ⑦ 补本次需要的概念，给定义、场景和例子，不固定成 3~6 个，也不把每个定义截成同样长度。
2. 把必须同时理解的对象与关系连起来。同一整体留在同一张图上，节点内可放局部结构；需要独立展开的细节按原则 ② 补详解。
3. 静态图已能说明的就停在静态表达。需要亲手切状态、改参数或执行分支才能理解时才加交互，不把交互当每个概念的必填项。

例如沿用任务队列示意：先认清任务、队列和处理者，再画任务入队、被取出和产出结果的过程。任务数改变后有新的状态需要比较，再考虑控件；不能用三张互不相连的名词卡代替这个过程。

## 原则 ⑨ · 积木是词汇，不是语法

先决定要表达的位置、关系、变化和理由，再选工具。积木减少重复排版，但不决定文章怎么组织，也不决定哪些信息该删。所谓「词汇，不是语法」，就是可以按内容组合能力，不把一个积木的默认形状当成唯一画法。

表达不顺手时，有四条路：

| 考虑顺序 | 做法 | 适用条件 |
|---|---|---|
| 1 | **组合** | 已有积木或控件拼起来就能表达，优先复用 |
| 2 | **加字段** | 现有方向正确，只缺一个可复用能力；先确认字段是否已存在 |
| 3 | **新建积木 / 控件** | 这类表达会反复使用，已有组合或字段仍不合适；明确能预见复用时，不必等做满三次 |
| 4 | **`raw` 写一次性结构** | 一次性排版或特殊结构，不值得为它造通用工具；可以直接选，不必先把前面三条都试一遍 |

这些是选择条件，不是必须逐级执行的流程。比如 `demo` 的 `html` 字段已能承载自定义结构，就先用现有能力，不再新建同义控件。交互先检查现有控件能否用 `config` 表达，真正缺能力时才进入注册与扩展，完整做法见 `references/blocks.md`、`references/extend.md`。

验收看图能否呈现所需对象、关系、条件和结果，交互是否给出预期反馈，不只看它用了多少字段或是否符合某种模板。不能因为「没有现成积木」退回含糊文字，也不能因为选了合法积木就省掉解释。

一次性结构仍复用主题变量和样式，不写死色值；`raw` 不豁免 HTML、图义、版面和验证要求，不用它给单篇加覆盖全站版心的补丁。具体修改层按原则 ⑩ 选择。

四条路也不是自动修改共享工具的许可。改共享源先按多会话协作检查；改控件行为先给用户可点原型，别人的笔记不擅自改。一次性表达与已有配置能解决时，不顺手扩大成工具重构。

## 原则 ⑩ · 版面服务阅读，图按内容铺开

版面在画图和写正文前就要确定，不等最后发现拥挤才压缩信息。常规任务以电脑阅读为目标，优先保住图义、真实关系和完整操作；已有组件的响应式是安全降级，不是要求再做一份手机版。

### 先确定目标页面的可用空间

记录本次浏览器视口宽度、页面缩放和目录展开状态，再看正文区域的实际可用宽度。显示器分辨率不等于页面宽度，正文宽度也不等于整个视口。已有明确条件就沿用，不为每张图重复询问；无法获知时先问，不把工具默认视口当成用户屏幕。

| 版面对象 | 怎样安排 | 避免什么 |
|---|---|---|
| 正文 | 限制阅读行宽，按段落职责组织 | 为用满宽屏把文字拉成长行 |
| 整体图 | 把真实分区、关系与节点细节铺进可用宽度 | 先套固定小画幅，再删信息或缩字挤进去 |
| 小图、短表、局部控件 | 保持适合自身内容的宽度 | 内容很少却拉成海报，或为填空凑细节 |
| 字号与图的尺度 | 看最终渲染是否可读，保留获批原型的尺度 | 只看源文件字号，或随页面变宽无上限放大 |

「用满」是利用可用空间讲清楚，不是所有对象都必须 `width: 100%`，也不是四周不能有走线和标题的留白。整体图可以丰富，判断清楚与否看分区、局部邻域、文字和关系，不按节点数定上限。已有获批原型优先保留，不仅为「用满宽屏」重新排图；要改变它时依据本次明确的反馈和目标。

需要铺开底图时，调整源 spec 的画布、节点尺寸、位置与路由；只扩大 `meta.viewBox` 会增加空画布，不自动重排。`arch.maxScale` 默认 1，按本图尺度封顶；显式调整倍率会连图和字一起缩放，不能代替布局或补信息。字段细节见 `references/blocks.md` 的 `arch`，实现维护见后文「当前版面实现与维护边界」。

### 设计验收与固定回归分开

| 检查 | 什么时候做 | 检查什么 |
|---|---|---|
| **目标桌面视口** | 本次图或控件的设计与交付 | 最终字号、全貌、层级、关系和完整交互是否讲清楚 |
| **固定 1280×900** | `visual-check` 的布局回归 | 溢出、重叠、穿节点、空图等工具可检出的故障；不是统一设计画幅 |
| **1920px 宽度** | 修改图的缩放策略时 | 图与字号不因容器变宽无上限放大，正文与图宽分工正常 |
| **约 500px 窄屏** | 新增或修改共享积木、共享控件、目录或外壳时 | 做一次安全冒烟：正文不被遮住，关键内容和控件可通过滚动等通道到达 |

固定回归报出的问题仍要处理，不拿「目标屏幕清楚」跳过真实故障；也不为通过另一档视口机械删节点、缩字或拆散同一整体。某个自动探针附带多档视口可以照常运行，不代表需要另做手机设计或反复搭精确设备测试；各工具的实际高度和覆盖范围以实现为准。

宽图只在组件已经支持的范围内滚动或缩放，不凭文案假定每种积木都有这些能力。属性表和纯并列卡片可保留不改变含义的重排，空间关系图不通过普通卡片化改变拓扑。

用户明确提出手机使用时，再确认目标设备与交互，才扩展为完整移动端设计。没有这个要求时，窄屏只修不可恢复的裁切、关键控件不可达或外壳遮挡，不做触屏精修。

## 原则 ⑪ · 平实、连贯、准确地写

写作要求在组织内容和起草时就执行。它适用于笔记正文、图注、节点说明、导览和 Skill 本身，不只是在交付前去几个词。目标是读者能跟着对象、动作和逻辑理解内容，不是把文字压到最短。

用户曾明确要求：「有些语句充满了 AI 味道，我希望所有的语句都平实、自然、连贯一些。」少 AI 味靠具体内容和清楚关系，不靠禁用一份词表或刻意换同义词。

### 先组织要讲的事，再润色句子

- 每节回答一个具体问题。按读者已知基础选择起点，先交代缺少的背景，再讲对象、关系或过程，最后说明结果、条件和取舍；这是组织方向，不是每节都要填满的模板。
- 每段有明确作用，例如定义对象、解释动作、给依据、举例或说明限制。没有作用的段落删掉，缺少承接的地方补背景，不能只有一串各自正确的孤立结论。
- 需要推迟的细节保留入口；主线里决定结果的条件不能抽走。图中的结构按原则 ①②⑧ 处理，文字保留必要定义、判断与理由。

### 句子写清对象、动作与关系

让读者知道谁做了什么、处理什么、产生什么结果。长句中换了主语、叠了多层条件时，拆成有明确承接的句子；「它」「这个」「该机制」指不回具体对象时，重写主语。

句间关系也要准确。因果、先后、归属和对比不能混用；「因为」「所以」「先」「然后」不能拿来串一个没核对过的解释。技术因果按原则 ⑤ 查证，不能因为一句话读着顺就当真。

过渡句不是一律删除。能说明为什么转到下一个问题、补了哪个前置的承接要保留；只有「下面介绍另一个重要部分」这类报幕，没有增加理解就删。先下抽象评价、再用破折号复述同一句话的写法，直接改为具体内容。

### 词语平常，术语与要求精确

- 优先用明确的日常动词：读取、保存、等待、比较、返回、修改。少用「赋能」「打造闭环」「完成跃迁」等没有说明具体动作的评价；确为技术术语时先定义，不靠术语增加气势。
- 沿用材料中的标准术语。不要为求新鲜创造「架构裂缝」等未定义概括，也不要擅自改代码标识符、API 名或真实输出。
- 「可以、建议、默认、必须、禁止」按事实或约定使用。不能为了有力把建议写成必须，也不能为了柔和删掉硬约束。绝对词有依据才用，限定条件不能丢。
- 对举句用于纠正明确误解。读者把默认值当上限时，可以解释两者不同；没有这个上下文就直接陈述事实，不凭空立一个要反驳的观点。
- 正文不写本次创作的自我辩护，例如「我第一版为什么没选这个画法」。所解释系统的设计理由、适用条件和不这样做的后果仍然保留。

### 例子、强调与警示服务理解

例子先给场景和要说明的问题，再给对照或动作，最后让读者知道据此怎样判断。所需前置不能比当前规则更难；「那次事故」「那个接口」没有上下文时换成具体对象。真实案例保留相关的现象、原因、处理和防复发动作；示意例子标明假设，不冒充实测。

说明文字的行内强调选真正的重点，不把每句话都加粗或上色。每段最多一处 `==`，每节通常两三处；这是控制阅读重点，不是凑数量或删内容的办法。图中的类型、状态与代码来源配色属于信息表达，不以文字重点的计数删改。提示颜色表达风险或说明性质，不表示作者觉得这句话重要；具体标记与颜色见后文「行内强调与颜色」。

沿用原则 ③ 的示意队列，对照下面的写法：

| 问题 | 含糊或突兀的写法 | 更清楚的写法 |
|---|---|---|
| 抽象评价代替机制 | 该机制有效优化了任务处理 | 队列有四个等待位置，满了拒绝新任务 |
| 无用报幕 | 接下来介绍另一个非常重要的环节 | 队列已经满了，下面看提交者会收到什么结果 |
| 指代不明 | 它处理后把它返回给它 | 处理者完成任务后，把结果返回给提交者 |
| 无依据扩大范围 | 所有失败都可以重试 | 先检查失败原因及请求能否安全重放，再决定是否重试 |

这些例子示范写法，不新增业务规则。写完沿正文读，检查每段为什么出现在这里、与上一段有什么关系、例子证明什么；交付前按复盘 ⑥ 回查。不要用加粗次数或「禁词为零」代替这个检查。

## 工作流

### 第 0 步 · 判断：用户要的是「一个点」还是「一个面」

**不要看到【图解】就开始画图。先判断用户要的是哪一种。**

| 用户的说法 | 他要的是 | 你怎么做 |
|---|---|---|
| 「这个函数干什么」「A 和 B 有什么区别」「这段代码为什么这么写」 | **一个具体问题的答案** | 直接跳到第 2 步 |
| 「理解这个项目」「搞懂这一章」「从零学 X」「理解 X 的架构」 | **一条理解路径** | **必须先走第 1 步** |

**判断信号**：用户说的是「一个点」还是「一个面」。
说「面」的时候，**不要急着产出内容，先产出「脉络」**。

```callout
tone: red
icon: ⚠
text: |
  ==用户说「给我架构图」不等于「我只需要架构图」。==

  他可能是想「理解这个项目」，而架构图只是**他以为的入口**。
  直接给架构图，他会发现到处都缺前置知识，然后东补一块西补一块。
```

**不确定时，直接问**：一句「你是想快速要一张图，还是要从零搞懂它？」
能省掉后面好几轮来回。

### 第 1 步 · 梳理知识树（只在「一个面」时做）

#### 1.1 画一棵「要理解什么」的树

```
理解 X
├─ ① 业务背景 —— 为什么需要它、解决什么问题
├─ ② 概念    —— 有哪些词、每个词对应现实中的什么
├─ ③ 组织    —— 它由什么组成、怎么分类
├─ ④ 架构    —— 它怎么工作
├─ ⑤ 设计取舍 —— 为什么这么设计、不这样会怎样
└─ ⑥ 代码细节 —— 具体到文件 / 模块 / 函数
```

**每个节点标三样：**

| 标什么 | 为什么 | 例子 |
|---|---|---|
| **依赖** | 理解它之前必须先理解谁（决定顺序） | `依赖: ②概念` |
| **深度** | 概念 / 组织 / 架构 / 代码（决定详略） | `深度: 架构` |
| **产物** | 值得单独一篇，还是并入上一篇（决定切分） | `产物: 单独一篇` |

#### 1.2 这棵树是**递归**的

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==六层不是某个项目的专属结构，而是「理解任何东西」的通用结构。==
```

所以每一层里的**模块**，只要大到需要单独理解，就要**自己再走一遍这六层**：

```
理解一个 Web 框架
├─ ① 业务背景
├─ ② 概念
│   └─ 中间件 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它是什么、为什么需要
│       ├─ 组织：有哪几种（普通 / 错误处理 / 路由级）
│       ├─ 架构：next() 怎么把它们串起来
│       └─ 细节：代码在哪
├─ ③ 组织
│   └─ 核心包 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它负责什么
│       ├─ 组织：由哪些文件组成
│       ├─ 架构：怎么工作
│       └─ 细节：路由 ──────→ 再递归一次！
├─ ④ 架构
├─ ⑤ 设计取舍
└─ ⑥ 代码细节
```

```callout
tone: violet
icon: 💡
text: |
  **所以产物不是「一篇 HTML」，而是一棵嵌套的、互相链接的产物树。**

  每篇笔记对应树上的**一个节点**，节点之间有 `needs` 关系（前置依赖）。
  读者沿着树走，每篇开头都写清楚「读这篇之前需要知道什么」。
```

#### 1.3 判断一个节点要不要单独成篇

| 单独成篇 | 并入父节点 |
|---|---|
| 它有**自己的概念**要解释 | 它只是父节点的一个属性 |
| 它**大到需要分几节** | 一两段能说完 |
| **其他节点会引用它**（是别人的前置） | 只有父节点用到它 |

> 用最后一条最准：==一个节点被别的节点 `needs` 引用了，它就必须独立成篇==，
> 否则读者会被迫跳进另一篇的中间去找。

#### 1.4 梳理时不断拷问自己

**这一步是 AI 拷问自己，不是拷问用户。** 每个节点问四个问题：

1. 要理解这个节点，读者**必须先知道什么**？那个前置知识在哪一层？
2. 有没有**循环依赖**？（A 需要 B，B 又需要 A → 拆法有问题，要重新切）
3. 哪些是**可以推迟的细节**？（不放进第一轮）
4. 有没有**用户已经知道的**？（他的背景里已经有了，跳过）

#### 1.5 和用户确认

**把树给用户看**，问三个问题：

1. 这个脉络对吗？有没有多余的、有没有漏的？
2. 顺序对吗？
3. 先做哪一块？

```callout
tone: green
icon: ✅
text: |
  ==确认脉络花的 2 分钟，能省掉后面来回补窟窿的 2 小时。==

  用户看到树之后，往往能立刻指出「这块我已经懂了」「这块才是重点」——
  这些信息你猜不到。
```

#### 1.6 最后才决定产物切分

**一棵树 ≠ 一篇文档，也不等于 N 篇。**

按「**一块能独立读懂**」来切：

- 前置知识自足的一块 → 一篇
- 太短的合并
- 太长的再拆
- **每篇开头写清楚「读这篇之前需要知道什么」**

```callout
tone: amber
icon: ⚠
text: |
  **跳过这一步会怎样？**

  读者每看完一篇就发现「这里缺一块」，于是回头补；补的时候又发现另一块缺，再补。
  ==好几轮来回，全在补第一轮就该规划好的窟窿。==

  **根因**：把「用户要的产物」当成了「用户的目标」。
  **信号**：如果用户连续三轮都在问「那 X 是什么」，说明第一轮就该梳理脉络。
```

#### 1.7 落地：把树写成 `plans/<topic>.yaml`

```callout
tone: amber
icon: ⚠
text: |
  ==确认的脉络不要只留在对话里。==

  对话会滚走，脉络会丢。写进文件，它才能驱动页面、才能在几周后还看得见。
```

```bash
# 树的唯一真相源
plans/<topic>.yaml
```

```yaml
# 示意：理解一个文件管理项目，名称和 source 换成本次任务的实际值
topic: file-management
title: 理解文件管理项目
summary: 从文件访问权限到上传和下载流程
source: "示意：本次项目路径与代码版本"

nodes:
  - id: access
    title: 谁能访问哪些文件
    layer: 概念
    needs: []
    artifact: file-access
    status: planned                 # planned / drafted / done
    blurb: 文件所有者、访问者与权限规则
    children: []

  - id: upload
    title: 文件上传流程
    layer: 架构
    needs: [access]                 # 学习前置，不是代码调用关系
    artifact: file-upload
    status: planned
    blurb: 文件从选择、检查到保存
    children:
      - id: upload-retry
        title: 上传失败后怎样重试
        layer: 模块
        needs: [upload]
        artifact: file-upload-retry
        status: planned
        blurb: 哪些失败可以重试，怎样避免重复上传
        children: []

  - id: download
    title: 文件下载流程
    layer: 架构
    needs: [access]
    artifact: file-download
    status: planned
    blurb: 检查访问权限后把文件交给用户
    children: []
```

**笔记那边只写两行**（`meta.json`）—— 层级和依赖关系**不在两处维护**：

```json
{ "tree": { "topic": "file-management", "id": "upload-retry" } }
```

**自动得到两样东西**：

| 得到什么 | 从哪来 |
|---|---|
| 首页的**树视图**（我在哪、下一步看什么、哪些还没写） | plan 的整棵树 |
| 每篇顶部的**「前置」区块** | plan 的 `needs` |

```
读「上传失败后怎样重试」之前，你需要先知道
  ← 文件上传流程    文件从选择、检查到保存
```

**两个自动行为**（不用你操心）：

- 前置节点**还没写出来**时，显示成灰色的「待产出」，**不做成 404 死链接**
- `needs` 引用了不存在的 id → **`npm run check` 直接报错**，不会静默少一条

> **没挂树的笔记照常存在**，在首页显示在「未归类」区。
> 一棵树不是必须的 —— 只讲一个点的时候（「这个函数干什么」），不需要建树。

> **没挂树的笔记也要填 `topic`** —— 见「第 7 步 · 写 note.md」那一节。

#### 1.8 树是**边写边长**的，不是一次画完的

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==**第一次读代码，你只看得见「结构」，看不见「哪个分支信息量大」。**==

  信息量是在**写的时候**才暴露的 —— 写到某一节发现「这里塞不下」，
  那说明它是一个**新节点**。
```

例如，梳理一个文件管理项目时，起初只计划写上传、下载、删除三条流程。写上传流程时发现，需要先解释「谁能访问哪些文件」；下载和删除也用到同一套权限概念。

这时给「文件访问权限」一个独立节点，让三条流程都通过 `needs` 引用它。新增节点的理由是其他篇也需要这个前置，不是这一节写长了。只有上传流程用到的局部细节，仍可以留在上传篇里。

#### 1.8.1 什么时候该长出新节点

```compare
first: 写作时的信号
head: [意味着什么, 怎么办]
rows:
  - 「这里得先说清 X 才能讲 Y」: ["X 是 Y 的**前置**", "给 X 一个节点，加进 needs"]
  - 「这一节写了三段还没讲完」: ["它**大到需要分几节**", "给它一个节点"]
  - 「这个分支和主线不是一回事」: ["它是**旁路**", "给它一个节点，或并入已有的旁路节点"]
  - 「这个词在别处也会用到」: ["它会被别的节点 needs", "**必须独立成篇**"]
  - 「这里和前面某一节重复了」: ["两个节点**边界划错了**", "合并或重新切"]
```

#### 1.8.2 怎么维护

```callout
tone: green
icon: ✅
text: |
  **每写完一篇，回头改一次 `plans/<topic>.yaml`。**

  - 发现新节点 → 加进去，填 `needs` 和 `blurb`
  - 发现两篇重复 → 合并，把 `artifact` 指到同一处
  - 发现某篇太大 → 拆成两个节点
  - 写完了 → `status: drafted`

  ==plan 不是「开工前画的图」，是**一直在改的施工图**。==
```

```callout
tone: amber
icon: ⚠
text: |
  **但要克制。** 不是每个「写不下」都要开新篇。

  先问：**它能被别的节点 `needs` 吗？**
  - 能 → 独立成篇（否则读者要跳进另一篇中间找）
  - 不能，而且只有父节点用它 → 就是父节点的一节，写长点没关系

  ==新节点要有「别人也需要它」这个理由，不能只是「它挺大」。==
```

### 第 2 步 · 找到卡点

用户可能明说（「Flink CDC 和 CDC 有什么区别」），也可能没说（只粘了一篇文档）。

没说的时候，从这些信号里找：

- 原文里**篇幅最长但最抽象**的那一段
- 用户**加粗、划线、单独贴出来**的部分
- 出现了**三个以上并列概念**的地方
- **流程/链路**类描述（「先…然后…再…」）
- 任何**反直觉**的结论

一句话：**卡点通常是「需要读者在脑子里维护状态或追踪顺序」的地方。**

### 第 3 步 · 拆骨架

按原则 ⑦ 确定读者起点，再把内容切成回答具体问题的 h2 章节。3~7 节可以作骨架参考，不是需要凑满的配额；一个具体问题不强拆成多章，复杂主题也不为满足节数删掉必要信息。

先列出主问题和必需的前置，区分主线、局部详解与可推迟的延伸。按原则 ⑪ 给每段明确作用，再删重复和无关铺垫，不先按段落数决定取舍。

**如果走过了第 1 步，骨架直接来自知识树的节点**，不用重新想。

### 第 4 步 · 逐段过一遍，决定画哪些图

**这一步不是「挑几个重点画图」，是「把每一段都过一遍」。**

做法：把骨架里的每一段读一遍，对每一段问一句 ——

> **这一段描述的是「空间 / 顺序 / 状态 / 归属 / 对比」吗？**
> 是 → 它为什么还是文字？

命中就画。判据和反例见「原则 ①」。==这一步的产出是一张「哪几段要画图」的清单，
而不是「挑三个卡点」。==

> 下面的表是**起点，不是清单**。找不到合适的就改积木、拼组合、或自己画（原则 ⑨），
> 别把内容削足适履地塞进表里 —— 但也别因为「没有现成积木」就退回文字。

| 原文里出现的是 | 用什么 | 为什么 |
|---|---|---|
| 「先 A，再 B，然后 C」的链路/分层 | `lane-stack` | 顺序用文字描述，读者要自己排队 |
| 有**分支或汇合**的流程 | `flow` | 一条直线讲不了「分两路再合起来」 |
| 「某东西从 X 变成了 Y」 | `journey` | 状态变化是文字最大的盲区 |
| 三个以上方案/概念的横向对比 | `compare` | 表格比排比句快十倍 |
| 一堆**没有先后关系**的并列概念 | `cards` | 用文字排会很平，卡片能一眼扫完 |
| 「2020 年…2022 年…」的演进 | `timeline` | 时间顺序需要视觉锚点 |
| 调用链、握手过程 | `seq` | 参与者 + 消息顺序 + **自动激活条** + 时间段框 |
| 决策定位（重要度 × 紧急度） | `matrix` | 两维定位用表格看不出来 |
| 类层次、目录树、对象嵌套 | `tree` | 层级关系需要缩进感 |
| 反直觉的点、坑、一句话结论 | `callout` | 需要跳出正文节奏 |
| 正例/反例清单 | `checklist` | 勾叉比「应该/不应该」直观 |

#### 陷阱：拿箭头当排版用

==规则表告诉你「并列的概念该用 `cards`」，但真正会犯的错不是选错积木，
而是**积木挑对了、箭头却多画了**。==

````callout
tone: red
icon: ↗
text: |
  几个**并列**的东西（一个结构体的成员、一个容器的几项属性、同一层的几种选择），
  被一条条边串起来 —— 读起来立刻变成「A 导致 B」或者「先 A 后 B」。

  **我犯过一次，被用户当场指出来。** 原因很具体，值得记：

  我想让三个并列的成员待在一个 `groups` 框里、排成一列，
  而 **`flow` 只给「同一列且首尾相连」的节点画那个框** ——
  于是就顺手补了两条**空边**，纯为了布局，没有任何语义。

  ```
  struct sock 下面挂着：接收队列 / 发送队列 / 连接状态
  它们完全并列  →  却画成了  接收队列 → 发送队列 → 连接状态
  ```

  **换 `tree` 就对了**：它用缩进和肘形线，天然表达归属而不是先后，
  节点还支持 `tone`（可以把「两条队列」染成同一个色）。

  | 你其实想说 | 别用 | 用 |
  |---|---|---|
  | 这几个东西**都属于** X | `flow` + 空边 | `tree` |
  | 这几个东西**并列对比** | `flow` + 空边 | `compare` |
  | 这几个东西是**一份清单** | `flow` + 空边 | `cards` |
````

**自检**：把每条边读一遍，问自己「**这条边代表什么关系**」。

- 说得出来（指向 / 导致 / 然后 / 交给）→ 留着，**空 `label` 不是罪**
  （一条 ①②③④ 的链，边不带标签也成立，因为你仍然说得出那个「然后」）
- 说不出来 → 它就是排版边。删掉，或者按上表换积木。

!!顺带一条：**别拿节点当旁白**。!!「从这里开始分叉」这种话不是一个东西，
它是一个**过渡句**。把它做成节点、再用箭头指过去，等于在图里插了一句正文 ——
该写在图外面。

### 第 5 步 · 核对事实

第 4 步确定哪些段落画成图之后，先做这一步，再写 `note.md`。

按原则 ⑤，把准备写上图和写进正文的数字、默认值、上限、版本、归属和因果列成事实表。每行记录待写说法、具体依据（段落 / 函数 / 输出）、适用条件（版本 / 环境 / 输入）和核对结论，不只贴一个链接。

能够在授权范围内安全复现的，运行对应输入；不能运行就读实现并写明验证边界。缺证据时按原则 ⑤ 判断：补材料或暂停主线，省略非关键细节，或标清文档说法、示意及待核项，不编造事实。

主线必需的事实有依据后，再写 `note.md`；关键缺口没有解决时先问用户，不能只标成待核就当作完成。只解释设计文档时可按文档写，说明未核对实现。后续新增节点和交互带来的新事实，也补进这张表再核对。

### 第 6 步 · 决定哪里必须做成交互

#### 多状态控件：交付前把每个状态点一遍

`npm run visual-check` 只量**当前 DOM** 有没有溢出 —— 某个状态被 JS 异常清空时，
它的形状区是空的、什么都不溢出，==检查照样打 ✓==。
例如某个按钮切换到新状态时触发脚本错误，内容区域被清空。空区域不一定溢出，所以初始布局通过不能证明状态切换正确。

有多个状态按钮时，逐个点击，确认每种状态都出现预期内容，并收集脚本错误。需要自动化时，可用下面的页面测试脚本模板：它点击按钮，打印内容子块数和错误列表。先替换控件序号、按钮文案和内容区域选择器；`.rc-shape` 是示例中的区域名称，不是所有控件都有的固定字段。

把测试脚本注入该篇 `dist/<slug>.html` 的临时副本，用无头 Chrome 跑，再从 `<pre id="dbg">` 读结果；不要改正式产物。输出子块数仍要和预期对照，不只看有没有报错：

!!要看的是页面下半部分的积木时，别用 `scrollIntoView` —— 无头截图只认滚动位置 0。!!
把 demo 之前的内容 `display: none` 掉（`display` 让它脱离文档流，demo 自然顶上来），
不要用 `remove()` 删布局容器 —— 删错了会把正文列宽一起删没，截出一张 230px 宽的窄图。

!!`display: none` 藏掉 grid 容器里的兄弟节点（比如目录 `aside.toc`）是同一个坑：==它一消失，`main` 会顶进目录那一列（240px）==，所有积木都被挤成窄版，看着像控件坏了。只从 `<main>` 内部往上藏，或顺手给 `.shell` 写上 `grid-template-columns: minmax(0, 1fr)`。!!


```js
window.__errs = [];
window.addEventListener('error', function (e) { window.__errs.push(String(e.message)); });
setTimeout(function () {
  var box = document.querySelectorAll('.demo')[0];   // 第几个控件
  var btns = [].slice.call(box.querySelectorAll('button'));

  ['状态A', '状态B'].forEach(function (key) {          // 换成本控件的按钮文案
```

#### `meta.json` 填什么

**没挂树的笔记，记得填 `topic`。**

「未归类」区默认**按主题分组**，分组轴就是 `meta.json` 里的 `topic`：

```json
{ "topic": "文件处理" }
```

`topic` 决定这篇放在哪个主题组，`tags` 用来筛选不同侧面。

例如一篇「文件上传」可以有「前端、文件、安全」三个标签。如果按所有标签分组，同一篇会重复出现在三个组里；如果按首个标签分组，换一下标签顺序就会换组。显式填写 `topic: 文件处理`，归属才稳定。

写 `topic` 的三条规矩：

| 规矩 | 为什么 |
|---|---|
| **一篇一个** | 它是单一归属。多归属会让同一张卡片重复出现 |
| **写得像人话** | 它是给人看的分组标题，不是给机器匹配的 key |
| **不要分得过碎** | 相关笔记放在同一主题；分组能帮助查找，而不是每篇各占一组 |

```compare
first: 做法
head: [好处, 代价]
rows:
- 用 `topic` 显式标注: ["分组干净、名字可控", "新增笔记时要记得填"]
- 用 `tags[0]` 当主标签: ["不用另填主题", "归属依赖标签顺序，不能稳定表示主主题"]
- 按 `eyebrow` 分组: ["不用另填主题", "页眉短标签用于提示页面类型或背景，不一定能表达主题归属"]
```

> 不填 `topic` 的会落在「其他」组里 —— **不会报错，也不会丢**，
> 但别人就看不出它属于哪一块。

如果确实要用笔记数、标签数等统计解释分组选择，记录统计范围和日期。它们会随内容增长而改变，不是长期固定的分组标准。

#### 但真正的回路是「写完一块就看一块」


```callout
tone: red
icon: ⚠
quote: true
text: |
  ==写完一块就看一块，不把所有问题攒到最后。==

  例如第一张图的标签已经重叠，继续照着它写后面的图，就会重复同一个布局问题。
  写完当前块，先用 `npm run block` 看截图，确认文字、关系和内容正确，再继续。
```

`npm run check` 必须过，但它通过不等于页面内容正确。以下分别是它能检查的格式问题，以及仍需查看实际页面的盲区：

- **积木名拼错** → 会静默退化成普通代码块，页面看着正常但图没了
- **YAML 语法错** → 定位到文件和行号，并回显原始内容
- **缺 `quiz`** → 违反本仓库约定（见「硬约束」）
- **源码里写了裸的 `<script>` / `<style>`** → 积木会把裸 HTML 原样输出，而
  `script` 是 raw-text 元素，没有 `</script>` 时**浏览器会把后面整篇文档当成脚本文本吃掉**。
  表现是「那之后的图连线全空、`demo` 控件全不挂载」，==而构建和 check 都不报错==。
  用反引号包起来就对了。
- **块名对、字段名错** → `summary` 只认 `title` + `text: |`（`items:` 是 `cards` / `checklist` 的字段）。
  写成 `items:` 时整块渲染成一个**空框**，而 `check` / `build` / `visual-check` 全绿 ——
  2026-10-15 四篇图解同时中招，==是用户先看出来的==。改完顺手在页面上看一眼那块有没有字。
- **`flow` 的 `groups` 按「行」分带** → 组框按**连续行**画。同一个组里的节点被别的组的节点隔开
  （行号 0 / 1 / 0 / 1 交替）时两组框必然相交，`visual-check` 报「区域框相交」；
  组标签也别写长，它会压到相邻的边标签（真报过「文字压文字：重叠 7px」）。**让一组占连续的行。**

```callout
tone: red
icon: ⚠
text: |
  ==构建通过 ≠ 画对了。== 构建验证能否生成页面，不能证明图中的文字、关系和交互正确。

  **改了样式之后必须跑 `visual-check`，再截图看一眼。**
```

#### 但它量不了「挤不挤」

````callout
tone: amber
icon: ⚠
text: |
  ==`visual-check` 判的是**有没有重叠**（TOL = 2px），不是**读起来顺不顺**。==

  例如两条边分别标「检查权限」和「保存文件」，标签虽然没有重叠，却挨得太近。
  读者可能把它们看成同一条边的说明。此时要扩大间距或调整标签位置，而不是拿通过检测作理由。

  ```
  检查权限 保存文件    ← 文字没重叠，但看不出各自属于哪条边
  ```

  ++所以「检测器过了」不等于「这图好看」。还得自己看一眼。++

  一个实用的经验判据：**把相邻的标签连起来读一遍**。
  如果读成了一句有语义的话，就该把其中一个改短（或删）。
````

#### 分清自动检查与人工验收

`visual-check` 会检查布局溢出、部分图的连线与文字碰撞，以及空图、控件未挂载等运行信号。它不能判断每种状态是否符合预期，也不能判断一张图是否讲清楚。

| 检查方式 | 看什么 | 为什么还需要这一步 |
|---|---|---|
| `visual-check` | 溢出、重叠、穿节点、空图或挂载异常 | 拦住能机械判断的渲染故障 |
| 看整页和单块截图 | 标签归属、相邻块的间距、图中是否真有内容 | 几块挤在一起或一块内容缺失，可能仍通过布局检查 |
| 点击每个状态和导览 | 状态内容、切换结果、错误信息 | 初始画面正常，不代表点击后仍正常 |

```
会话 A 把笔记 A 写入 .vc-tmp.html
会话 B 把笔记 B 写入同一个文件    ← 覆盖了 A 的临时页面
会话 A 的 Chrome 加载这个文件    ← 实际读到笔记 B
```

A 的检测脚本量了笔记 B，却把结果记在笔记 A 的报告里。
整个过程没有任何报错。

```callout
tone: amber
icon: 🧱
text: |
  **避免这类串页的三个动作：**

  ① ==**任何写临时文件的工具，路径必须带 PID 或随机后缀。**==
  固定临时路径在单会话时可能不暴露问题，多会话同时写入时却会互相覆盖，而且未必报错。

  ② **一个省事的约定（软链 `node_modules`）制造了一份跨会话的共享可变状态。**
  ==推荐一个约定的时候，要顺手想一想它把什么东西变成了共享的。==

  ③ 这条规矩**修完要全仓库搜一遍**：后来又踩了第二次 ——
  `visual-check.mjs` 当时修好了，但 `block.mjs` 的预览页还写着固定路径
  `node_modules/.block-preview.html`，两个会话同时跑 `npm run block` 时，
  我截到的第 N 块**是另一个会话的第 1 块**（截图上的行号和我这一篇对不上）。
  ==修好一处不等于修好这一类；「临时文件」这个字符串要在 `tools/` 下 grep 一遍。==
```

修完之后的判定规则（`ATTEMPTS = 3`）仍然保留 —— 噪声还在，只是不再是主因：

| 三次的结果 | 判定 |
|---|---|
| 任一次干净 | ✅ 通过。中途挂过就报一条 `⚠ 第 N 次才通过`（不阻塞） |
| 三次都挂、诊断**一样** | ✗ 真的，阻塞 |
| 三次都挂、诊断**不一样** | ⚠ 负载导致，**不阻塞** |
| 三次都没拿到数据 | ✗ 阻塞（探针自己坏了） |

```callout
tone: amber
icon: ⚠
text: |
  ==**看到 `⚠ … 检查不稳定` 或 `⚠ 三次的诊断不一致` 时别忽略。**==

  它不阻塞推送，但那篇笔记的检查**不可信**。等负载降下来重跑 ——
  如果同样的位置还在，那才是真问题。
```

#### 量图工具报 ENOBUFS 时先检查输出大小

`visual-check` 通过 Chrome 的 `--dump-dom` 读取整页内容。页面内联很多截图时，输出可能超过子进程的缓冲区，表现为 `ENOBUFS`，容易被误认为浏览器没有启动。

维护这个工具时，先检查 `execFileSync` 的输出限制，不要反复重画笔记来处理工具故障。当前实现设置 `maxBuffer: 64MB` 并单独报告 `ENOBUFS`；若仍超限，要依据实际输出调整或改变采集方式。

#### 已知问题基线：`tools/visual-baseline.json`

有些问题**不是笔记写错了，是积木画不了**（例如 `flow` 画不了「阶梯 + 公共出口」）。

```compare
first: 情况
head: [会怎样, 怎么做]
rows:
  - 不在基线里的问题: [{ text: ✗ 阻塞推送, tone: red }, 去修笔记]
  - 在基线里的问题: [{ text: "⚠ 报出来但不阻塞", tone: amber }, 不用管，或者重画图]
  - 基线里已不成立的条目: [{ text: ✗ 阻塞推送, tone: red }, 删掉那条 —— 基线只能变小]
```

```callout
tone: amber
icon: ⚠
text: |
  **加基线之前先问自己**：这是「作者写错了」还是「积木画不了」？

  写错 → ==修笔记，别加基线==。基线不是绕过检查的口子。
```

### 第 9 步 · 交付前的九次复盘（复盘清单）

改稿多轮之后内容一定会「长歪」。**每次都有具体动作，不是「再读一遍」。**

#### 复盘 ① · 术语审计

**用任何术语前，读者知道这是什么吗？**

把正文里的代码标识符列出来，检查哪些理解必需的词还没有说明作用；源码定位名不自动等于需要新开概念章节：

```bash
grep -oE '`[A-Za-z_][A-Za-z0-9_.]{2,}`' notes/<slug>/note.md | sort -u
```

**判断标准**：读者理解当前段落必需的术语，在首次使用前没有解释或明确前置，就是堵塞点。先在使用处补说明，或指向已经解释过的概念；确有一组共同前置时再放进开头的概念节。按原则 ⑦ 判断，不为每个源码名字重新写入门。

#### 复盘 ①b · 数字和事实复核

**把正文、图和速查表里的数字与因果，逐项和依据再对一遍。** 有源码的回源码数、读对应路径；标准、文档或实验中的事实，回到对应原文或输出，不要求每种事实都来自源码。

> 第一次核对在第 5 步，按原则 ⑤ 做。这里检查改稿后是否丢了条件、变了说法，或同一事实在几处写得不一致。
> 源码版本或环境变了就重新核对。未核项仍按原则 ⑤ 处理，不因格式检查通过就当作事实。

真实事故：文档里写「这个接口有 14 个方法」，实际 **17 个**。
同一个错误在架构图、正文、速查表里各出现一次，**三轮都没人发现**。

```callout
tone: red
icon: ⚠
text: |
  ==**但光数数字不够 —— 机制也要核。**==

  例如一个示意队列：容量确实是四个，图和正文却都写「满了就丢弃新任务」。
  如果实现实际是让提交者等待，数字虽然正确，机制仍然错了。

  核对时要找到满队列的处理分支，确认它是拒绝、等待还是其他行为，再一起修改图和正文。
  不能因为数字对、句子通顺，就把推测出来的因果当作已验证。
```

**两类要核的东西，别只核第一类：**

```compare
first: 写下的东西
head: [长什么样, 怎么核]
rows:
  - 数字:
      - "「14 个方法」「1700 行」「5 种类型」"
      - "`grep -c` / `wc -l` —— 命令一跑就知道"
  - "**机制**（因果关系）":
      - "「包一层**因为**…」「校验分两段**是因为**…」"
      - { text: "==把那条代码路径读出来，看它到底会不会那样==", tone: amber }
```

```callout
tone: violet
icon: 💡
text: |
  **机制比数字危险，因为它看着更有道理。**

  数字错了读者会怀疑（「真的 17 个？」），但机制错了读者**会信** ——
  因为它语法通、逻辑顺、还带着解释力。

  ++判别方法：写下「因为…」之前，问自己「我是读到的，还是推出来的？」++
  推出来的，就得回去读。
```

容易写错的几类数字：**接口方法数、文件行数、枚举取值数、调用点数量**。

```bash
grep -cE '^\s+[a-zA-Z]+\(' <接口文件>     # 数方法
wc -l <文件>                              # 数行数
grep -c '^\s*[A-Z_]* =' <枚举文件>        # 数枚举值
```

> 数字错了比文字错了更危险 —— ==读者会信数字，而且不会去数==。

#### 复盘 ② · 新概念配例子

```callout
tone: red
icon: ⚠
text: |
  ==只给定义不给例子，等于没定义。==

  「软删除是一种标记删除的机制」—— 读者完全不知道那是什么。
```

**本篇需要新建立认识的概念至少给三样**；已解释过的概念可引用，不重复堆例子。下面以一张用 `deleted_at` 标记删除状态的记录表示意「软删除」，不是所有系统都使用这个字段：

| 给什么 | 例子 |
|---|---|
| 一句话定义 | 「删除时不真删，只打个标记」 |
| **长什么样**（最重要） | `{ id: 7, deleted_at: '2026-03-01 10:00:00' }` |
| 和相邻概念的区别 | 「普通删除是行没了；软删除是行还在，查询要额外加 `where deleted_at is null`」 |

用 `cards` 的 `code` 字段放例子最省事。

#### 复盘 ③ · 小白通读

**假装你只能看到这份 HTML，看不到任何代码。** 从头读，每段问：

- 这里出现的词，我前面见过定义吗？
- 「它」「这个」指代清楚吗？
- 例子先交代了场景和问题吗？不认识旧项目的读者，能看出它在说明哪条规则、据此要做什么吗？
- 这张图 / 表，不看正文能理解吗？
- 按原则 ④，图的落点是否是可辨认的具体对象，或前文已经解释过的概念？缺定义、关系或状态时有没有补齐？
- 有没有结论来得太突然的地方？

**记下所有卡住的位置，回到原文补。**

#### 复盘 ④ · 结构复盘

**改过三轮以上，目录一定会乱。**

```bash
grep -nE '^#{2,4} ' notes/<slug>/note.md
```

检查四件事：

| 检查 | 典型症状 |
|---|---|
| **层级** | 某个 h3 其实是上一个 h3 的下级，却平级了 |
| **归属** | 内容跑到了别的章节（A 的讲解跑进了 B 里） |
| **顺序** | 先讲「怎么工作」后讲「由什么组成」 |
| **编号** | 改稿后编号重了或跳号 |

```callout
tone: violet
icon: 💡
text: |
  读者的路径应该是：==这是什么 → 由什么组成 → 怎么工作==。
  先看零件清单，再看零件怎么配合。
```

#### 复盘 ⑤ · 篇幅复盘

**改过几轮之后，篇幅一定会往「好写的方向」歪，不是往「读者需要的方向」。**

例如用户想弄懂「文件怎样从浏览器上传并保存」。页面却只用几句话带过主流程，把大量篇幅放在测试工具和性能优化上。即使每一节单独都正确，用户最想知道的过程仍没讲清楚。

根因不是偷懒 —— 是**「反直觉」「测试」这类内容每一点都能独立成段，好写；而「怎么工作」要讲清一条链上的每一步，难写**。写着写着就歪了。

**一条可操作的判据：**

```compare
first: 假想
head: [意味着什么, 篇幅应该]
rows:
  - 把这一节整段删掉，读者还能理解主题吗:
      - "它可删 → 是边角料"
      - "短"
  - 删掉之后主题就讲不明白了:
      - "它是主线"
      - { text: "==充分展开==，不能被辅助内容挤成几句概括", tone: green }
```

**用章节长度检查篇幅是否偏离主问题**：

```bash
grep -nE '^## ' notes/<slug>/note.md
```

把每节的行数算出来，排一下序，再与用户的核心问题对照。用户来理解工作机制，主流程只有短短几段、辅助内容却占大半篇时，优先补主流程。长度只是检查线索，不为凑最长章节加内容，也不因一节较短就认定它没价值。

```callout
tone: amber
icon: ⚠
text: |
  ==**「抽出来的内容」看着比主线重要，是因为它独立成节了。**==

  例如把上传流程中的权限检查、失败重试和保存确认全抽到末尾的「补充说明」，
  主流程就只剩「选择 → 上传 → 保存」。读者不知道这些处理在哪发生，补充说明也失去了上下文。

  抽出来之后两头都亏：

  - 主线缺了细节，变得单薄 —— 读者看完「三步管道」还是不知道每一步具体干什么
  - 细节离开上下文，读起来像三个孤立的知识点

  ++只有「主线讲完之后的延伸」才该独立成节。从主线里抽出来的，要并回主线。++
```

#### 复盘 ⑥ · 写作质量回查

写作规则已在原则 ⑪，起草时就应执行。这里检查多轮改稿后有没有偏离，不重新设另一套语气或禁词标准。

1. 看每个标题和段落能否对应一个问题，缺背景或承接的补齐，无作用的重复删掉。
2. 沿正文读一遍，检查主语、指代、因果、先后、归属和对比；逻辑缺口不能靠过渡词掩盖，事实因果回到原则 ⑤ 核对。
3. 找抽象评价、自造词、报幕和改稿辩护，改为对象与动作；标准术语、设计理由、硬约束和例外不因文风被删或变弱。
4. 检查例子的场景、对照和用途，不认识旧项目的读者也应知道它在说明什么；示意与真实材料分开。
5. 扫一眼强调和警示，保留真正的重点与风险，不为数量目标删信息。

可以用下面的搜索定位候选句，再按原则 ⑪ 判断是否需要修改：

```bash
grep -nE '——|注意|其实|必须|唯一|本质上|赋能|闭环' notes/<slug>/note.md
```

命中不等于错误，没命中也不等于写得清楚。最后仍要检查读者能否跟着段落说出对象、过程、结果与边界。

#### 复盘 ⑦ · 图解缺口审计

==这是和复盘 ⑤ 并列的最重要一步，因为它直接决定「这份东西为什么存在」。==

**做法：把正文里所有描述「空间 / 顺序 / 状态 / 归属 / 对比」的句子捞出来，逐条问一句「它为什么还是文字」。**

```bash
# 把这些「叙述性信号词」全 grep 出来 —— 命中的每一行都是缺口候选
grep -nE '先|然后|接着|之后|最后|变成|指向|包含|位于|上一层|下一层|依次|交替' notes/<slug>/note.md \
  | grep -v '^\s*[0-9]*:\s*[|>#]'
```

命中之后，按三种情况处理：

```compare
first: 情况
head: [怎么办]
rows:
  - 确实在讲顺序/位置/状态: [{ text: "补图。优先用现成积木；没有合适的就按原则 ⑨ 的四条路走", tone: green }]
  - 是个判断或理由（「为什么不用 X」）: ["留着。这是图替代不了的"]
  - 是操作清单（①②③④）: ["留着。它没有空间关系，画成图更绕"]
```

**再检查没有命中关键词的段落**：

```bash
npm run gaps -- <slug>    # 列出正文段落、行号和段落/围栏块比值
```

它帮助定位候选段落，不判断这些段落是否该画图；围栏块也包含代码示例，不全是图。逐段按原则 ① 判断，不能为了降低比值删掉必要的判断、理由或操作说明。

**第二条检查：关键图的信息量（原则 ③）。**

逐个打开这一篇的图，问三句：里面有没有「量」？有没有「方向」？盖住正文它还讲得通吗？
答不上来的那张，回去查原理重画。

```callout
tone: violet
icon: 🧭
quote: true
text: |
  例如正文写「文件先检查权限，再上传；上传失败后重试，成功后保存结果」。
  这段有顺序和分支，应在流程图中看见。它已经写成文字，不是省掉图的理由。

  卡点决定哪里优先做、哪里讲得更细，不决定其他结构是否需要表达。
```

#### 复盘 ⑧ · 别用画法掩盖坏布局

**整体图读不懂时，先看布局是不是坏了：线穿过节点、互相叠、或者关系画错。** 不要先把线藏起来。信息多、线多，本身不是故障。

曾有一张整体图的线穿过节点、互相重叠，处理时却把线压到节点下面、调低透明度，只在聚焦时显示。画面看起来干净了，原来的错误路径并没有改变。这个例子提醒的是：先修位置和路由，再用聚焦帮助阅读，不能靠隐藏故障取得视觉上的通过。

聚焦可以淡化旁边的对象，用来沿着一条路径看。全图里的分区、对象和主要关系要本来就能辨认；涉及运行过程时，方向也要清楚。恢复全图之后，穿节点和重叠还在，就是没有修好。调间距、改布线、把并列画成散开，才是在修布局。

**这一条不只适用于图。** 凡是「改一改让它看着没问题」的动作，都要先问这一句。

---

#### 复盘 ⑨ · 照着自己写过的规矩做

**使用不熟悉的工具前，先核对它的示例和正确用法。**

例如 archify 同时支持网格与手工坐标。把密集整体图硬塞进网格，几次布局失败只能说明这次用法不合适，不能证明工具不支持整体图。先看它的 `examples/`，再按本 Skill「结构化图」一节检查 `pos`、区域框和路由的写法。

```callout
tone: amber
icon: 🔧
text: |
  **顺序应该是：**

  1. 先用**参考实现自己的例子**证明「这工具能做这件事吗」
  2. 再证明「我能让它做这件事吗」—— 照它推荐的用法来
  3. **两条都试过还不行**，才轮到「自己写」

  ==跳过第 1、2 步直接自研，代价是把自己重新踩一遍那个领域几十年的坑。==

  ++判断「该不该自己写」也要有证据：「我试了它的**正确用法**，它确实做不到 X」
  才算证据；「我试了三次没调通」不算。++
```

直接自研布局，会把端口方向、坐标系、避让和尺寸测量等问题一并接过来。只有确认已有工具的正确用法仍无法表达所需关系，才承担这部分成本；具体缺什么能力要写清楚。

### 第 10 步 · 交付后的自我反馈

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==**每次交付完，回头问一遍：刚才哪一步慢？哪一步反复来回？**==

  这一步不是「再读一遍稿子」—— 那是第 9 步。

  这一步看的是**过程**，不是**内容**：
  **我在跟工具较劲的地方，就是下一个会话会再较一次劲的地方。**
```

**关键区分**：

```compare
first: 发现的问题
head: [改哪里, 例子]
rows:
  - 内容问题（这一篇讲错了 / 漏了）:
      - "改这一篇"
      - "「卡点图没画」「概念没配例子」"
  - "**工具问题**（跟内容无关，但耗了时间）":
      - { text: "==改工具，然后把改进写回这份 skill==", tone: green }
      - "「截图被截断」「要手动关标签页」"
```

**工具问题不会自己消失。** 你不写回来，下一个会话的 agent 会一模一样地再踩一次 ——
而它甚至不知道自己踩了，只会默默地多花二十分钟。

### 控件里要写强调文字时，用 `richText`

积木那边的 `==强调==` / `**重音**` / `` `代码` `` 是**构建期**由 `tools/lib/blocks.mjs`
处理的，控件跑在浏览器里拿不到它 —— 所以 `app.js` 里有一份最小的 `richText(host, text)`。

```js
richText(el('p', 'my-note'), '这一步 ==很关键==，注意 `read()` 的返回值');
```

==不写它就直接 `textContent` 的话，页面上会字面显示 `==很关键==`。==
它只认那三种标记，别往里加东西 —— 两边逻辑越像，越容易漂移。

### 图的视觉规范

先让对象类型、归属和连线含义可辨，再检查视觉样式。下面五项用于制作和验收图：

#### ① 节点用语义类型，不要纯文字盒子

用所选工具的语义类型区分服务、数据库、队列等对象。`flow` 的节点用 `kind`，archify 的组件用 `type`；不要把两个字段混用。图标和配色帮助识别对象，名称与说明仍要清楚。

#### ② 用区域框表达归属

例如几个服务部署在同一区域，或几个对象属于同一资源域，用区域框标出归属。`flow` 用 `groups`，archify 用 `boundaries`，内联整体图需要区域解释和父子语义时再配 `frames`。

```callout
tone: violet
icon: 💡
text: |
  ==「结构单一」的最大来源就是没有区域框。==
  平铺的节点看不出「谁和谁是一伙的」，读者要自己在脑子里分组。
```

#### ③ 开背景网格

`grid: true`。给图「工程图纸」的质感，也让大片空白不那么飘。

#### ④ 边要有语义

- 同步实线、异步虚线 —— 别混用
- 关键路径用 `tone` 上色（比如绿色的 HTTPS、红色的鉴权）
- **每条边都该有标签**（协议、动作、方向），除非两端完全自明

#### ⑤ 文字不许互相压

用户点名过的一条，原话：

> 你在画图的时候要注意文字互相重叠的情况。
> 线可能你判断线的重叠比较有难度，==但判断文字重叠应该比较轻松，对吧？==
> 尽量不要出现文字被挡到的情况。

**为什么单拎出来**：字被压住不会报错，**字还在，只是读不通**。
它比「图没画出来」隐蔽得多 —— 出图看着是成功的，只是有一行字废了。

**最常见的成因只有一条：标签比它所在的那条缝还宽。**

```
   ┌──────────┐            ┌──────────┐
   │  节点 A   │   这条缝    │  节点 B   │
   └──────────┘            └──────────┘
        └──── 标签比缝宽就压到框上 ────┘
```

`flow` 里还有一种固定搭配会撞：**群组框的标签画在框的左上角，
而边标签默认落在那条缝的水平中点** —— 缝一窄，两个标签就叠在一起。

修法按优先级：

| 修法 | 说明 |
|---|---|
| 调节点位置 | 让缝变宽（改 `row`，或把节点拆开） |
| **`edges[].labelDx` / `labelDy`** | ==手动把边标签挪开。工具算不出「那里已经有群组标签了」，但作者一眼就知道该往哪挪== |
| 把标签改短 | 最后手段。**别为了塞下标签而把话说残** |

```callout

icon: 🤖
text: |

  `npm run visual-check` 会报 `文字压文字：「…」↔「…」（重叠 Npx）`。
  它用 `Range` 取每个**文本节点自己的墨迹矩形**（不是父元素的盒子）——
  父盒子带 padding、跨行时是一整块，都会把「挨着」误判成「压着」。

```

```callout

  **不查什么：文字被线 / 边框穿过。**

  那要判断「这条线是不是本来就应该在那儿」—— 机器判不了，
  人工排查的成本也高于收益（用户原话：==「如果是线和文字重叠，排查比较费时间的话，就不用管了」==）。
```


### 结构化图：调用 archify skill

archify 是一套完整的图渲染系统，能力**超出**我们自己的积木：节点的**语义类型**
（声明是 database / messagebus / cloud，自动带图标、配色和图例）、**精确区域框**、
**真边路由**，以及一个会量文字宽度、检测碰撞的校验器。

我们自己的积木是「半自动」的 —— 你给 `row`，它排位置，不做标签避让和碰撞检测。
两套工具各管一段，**按图的形状选**。

#### 它能画 5 种图

由 spec 里的 `diagram_type` 决定（`tools/archify.mjs` 会自动读）：

| diagram_type | 画什么 | 结构数组 |
|---|---|---|
| `architecture` | 系统组成、部署拓扑、依赖关系 | components · boundaries · connections |
| `workflow` | 跨角色的流程 | lanes · phases · mainPath · nodes · edges |
| `sequence` | 调用链、握手、时序 | participants · messages · activations |
| `dataflow` | 数据流水线 | stages · nodes · flows |
| `lifecycle` | 状态机、生命周期 | lanes · states · transitions |

写法参考 `~/.agents/skills/archify/examples/*.<type>.json`。

#### 什么时候该调 archify

| 用 archify | 用我们自己的积木 |
|---|---|
| 有**区域/边界**要表达归属（「这几个在同一个 VPC」） | 没有归属关系，就是一根轴或一列卡片 |
| 节点有**语义类型**（这是数据库、那是队列） | 节点就是纯文字盒子 |
| 需要**图例** | 不需要图例 |
| 形状是 DAG / 状态机 / 泳道 / 时序 / 阶段流水线 | 形状是时间轴 / 状态对照 / 两列匹配 / 行列表 |
| 要作为**独立图**交付、反复引用 | 图文混排成一节，要跟着页面换肤和重排 |

#### 画整体图（原则 ② 的做法层）

**效果在「原则 ② · 整体图」。** 这里只写 archify 怎么摆。

##### 一 · 用手工坐标，把内容铺进屏幕

整体图顶层不写 `layout`，每个零件写 `pos`。把分区、关系和节点里的细节排进已确定的目标桌面页面的可用宽度。零件之间留出走线的缝。不要排成挤在一起的网格，也不要为了留缝把节点收成一行字。

要扩展画布，改 `archify/<图>.json` 的 `meta.viewBox: [宽, 高]`，同时调整节点的 `pos`、`size` 和连线路由，再生成 SVG。只增大 viewBox 不会自动重排节点，只会增加空画布。最终 SVG 的 `viewBox` 是四项属性，属于产物，不手改。

零件少的图可以紧一些。`examples/production-deployment.architecture.json` 是 12 个零件、横向大约每步 200px，那是小图的尺寸，不是整体图的标准。

下面只展示 `pos` 和 `size` 的字段片段，不是可直接生成图的完整 spec；完整的标题、类型等必填结构参考示例目录。

```json
{ "components": [
    { "id": "clients", "pos": [38, 300],  "size": [150, 56] },
    { "id": "edge",    "pos": [230, 300], "size": [150, 56] },
    { "id": "gateway", "pos": [430, 300], "size": [150, 56] } ] }
```

##### 二 · 关系怎么落到字段上

| 关系 | 用什么 | 注意 |
|---|---|---|
| 并列 | 不画边，从同一个东西散开 | 不要为了排成一列补空边 |
| 分类 | `boundaries` 包住一行，当背景 | 层级靠带分，带不是主角 |
| 包含 | `boundaries.wraps` 包成员；`frames.parent` 写区域的父子 | 写明是组成，还是只是逻辑上归在一起。再套一层，就要多一条原先看不见的归属 |
| 指向 | `connections` | 共享资源只画一份，各个真实引用默认保留。多条线是否交叉取决于布局和路由 |
| 流动 | `connections` | 跨行的边写 `fromSide` / `toSide`。整张图的运行方向要能顺着这些箭头看出来 |
| 在外 | 画在那个框的外面 | 仍留在这张图上 |

多条引用拥挤时，先改节点位置和路由。确实需要代表线时，在边标签或节点说明中标清基数和代表范围，例如「三条线程共用一份文件表」，并用 `compare` 补全每个对象的引用关系。不要把布局困难改写成对象没有关系。

点选邻域和 `parts` 的关系列表都来自 SVG 中实际画出的边。`parts.detail` 能补文字，但不会恢复省略边的可追踪邻居。用了代表线，就在图注说明这个限制；任务要求逐对象追踪完整关系时，不用代表线代替真实边。

##### 三 · 按原则 ② 看全图

不在这里另写一套判据。在目标视口上看：全貌、层级和主要关系在不在，涉及运行时方向是否清楚，关键格子里有没有细节。配了点选说明，就检查能否沿实际连线走；配了导览，就检查每条是否围绕一个问题推进。局部在节点尺度讲不清楚，就保留其位置和对外关系，另补详解。彼此独立的东西按原则 ② 分开，不要先画在一起再等它们互相挡。

##### 四 · 布局完成后，先看校验

`tools/archify.mjs` 会先跑 `archify validate`，不过就不出图。`edge-through-node`、`proper-crossing`、`micro-segment` 是硬门。

#### 它的硬边界（踩过）

- **边不能穿过无关节点。** archify 直接报
  `crosses component "xxx" (unrelated to this relationship)`，==它不会帮你绕过去==。
  先改布局，或手填 `route` / `via`。不要因为线穿过节点，就把本属一个整体的东西拆开。彼此独立的，按原则 ② 本来就不是一张图。
- **先区分「长图」和「被页面放大」。** 过去小图会被页面拉大，字一起变大。`arch.maxScale` 可选，必须是有限正数，默认 1；默认只缩小、不放大，显式大于 1 时会允许等比放大。新整体图需要铺开时，优先重排源 spec 的画布、节点和路由，不靠放大小图补信息。进程和线程首图的 0.87 只属于那一张。
  因果或顺序为主的一列层叠优先 `lane-stack`；真实的空间拓扑可以是长图，不能仅因长宽比就拆。
- **`architecture` 有两种排法：写 `layout`（网格），或者给每个组件写 `pos`。**
  **两条路二选一**，都不写才报错：

  `Component "x" must include pos [x, y] when layout.mode is omitted`

  ```compare
  first: 排法
  head: [怎么写, 什么时候用]
  rows:
    - 网格: ["顶层写 `layout`，组件只写 `row` / `col`", "零件少、排得规整"]
    - "**手工坐标**": ["顶层**不写** `layout`，每个组件写 `pos: [x, y]`", "整体图用手工坐标。`production-deployment.architecture.json` 是 12 个零件的小图，不是整体图的尺寸标准"]
  ```

  不要把「支持网格」理解成「必须用网格」。密集整体图需要手工安排节点与走线；
  网格排不下时，先切换到 `pos`，不要直接判定工具不支持。
- **组件尺寸是每个显式声明的**（默认 120×60），不随 `layout.cellW` 变。
  标签长了要么裁文案，要么给它加 `size`。
- **`label` / `sublabel` 里不能写我们的行内标记。** archify 不解析 `==` `**` `++`，
  它会**原样显示**这些标记，而不是渲染成强调样式。
  ==写进去之前先把标记去掉。==
- **跨行的边要显式写 `fromSide: "bottom"` / `toSide: "top"`。**
  上下相邻两行的节点，自动推断可能给出 `fromSide: "left"`，然后报
  `first segment does not honor inferred fromSide "left"` ——
  ==错误里说的方向和你看到的走向对不上，直接写上 bottom/top 最省事。==
- **写了 `via` 的手工坐标，首点要对齐起点边的中心线，末点要对齐终点边的中心线。**
  左右边对齐 y，上下边对齐 x；斜着进入某条边会报 `does not honor fromSide/toSide`。
  先按节点 `pos` + `size` 算出边中心，再拐弯。
- **画布底部要给图例留一条带。** 节点或区域框压到画布底时，报
  `legend needs N rows ... above the available legend band`；加高 `meta.viewBox`，
  不要靠挪节点挤图例。
- **`boundaries` 里的 `kind` 只有 `region` 和 `security-group` 两种**，
  而 `security-group` 画出来是**红色虚线框**。红色在别处一律表示「出事了」，
  知识图里没有这个含义，++默认用 `region`++。
- **边有几何下限**：微段短于 8px、两条边挤在同一条走廊里，都会判失败。
- **嵌套区域要量完整包围盒和标题带。** 旧笔记把 pad 的经验范围误写成能力上限。
  进程 / 线程原型实测三层 pad 为 40 / 78 / 122；前提是画布上方和四周有余量。
  生成器曾把父子底边截到同一个 y，校验却通过。`tools/lib/arch-frames.mjs` 现在恢复成员包围盒
  + pad，并在声明 `frames` 时检查父框完整包含、同级不相交、父子标题至少间隔 24 画布单位。
  内框 pad 太小会让标题藏在节点后面；不能靠 `pad: 10` 或缩小字号解决。最后仍要截图量图。
- 产出是**静态 SVG**，不跟着容器宽度重排。
- **`lifecycle` 的 lane 语义是写死的**，别拿它画通用状态机。
  `render-lifecycle.mjs` 里写死了：`lane: main` → 上排「阶段带」（5 列，y=126）、
  `lane: terminal` → 下排「结局带」（3 列，y=450）、**其它所有 lane 全挤在中间那条
  「事件带」**（只有 3 列，y=278，靠 `yOffset` 上下分开）。
  几何常量也是死的（`phaseXs: [94,248,402,556,710]`、`eventXs: [402,556,710]`）。

  ==拿「进程七态」试过：四个状态要横排、还要跨三行画挂起，label 碰撞报了二十几条。==
  **状态机用 `flow` + `shape: pill`，别用 `lifecycle`。**
  `lifecycle` 留给「一条主路径 + 几个中断 + 几个结局」那种形状。

#### 怎么调（已封装好）

```bash
# 1. 写 archify 的 JSON spec 放 archify/ 目录
#    参考 ~/.agents/skills/archify/examples/*.<type>.json（5 种类型都有例子）
# 2. 生成并抠图
node tools/archify.mjs archify/<名字>.json <名字>
# 3. 在 note.md 里用 arch 积木
```

```text
svg: <名字>              # 必填，对应 assets/arch/<名字>.svg
caption: 这张图说明什么    # 可选，图注
```

**抠出来的 SVG 自带「聚焦 + 关系追踪」**（点节点只看它和它连出去的关系）——
因为 archify 的 SVG 里留了 `data-node-id` / `data-edge-from` / `data-edge-to`，
`app.js` 按属性筛一遍就行。键盘也能用（Enter / Esc）。

**`tools/archify.mjs` 做了三件事**（这三件事不做会踩坑）：

1. 调 archify 的 `validate` + `deliver`（校验不过会直接报出诊断）
2. **只抠 SVG**（archify 的 HTML 有 600KB，但 SVG 本体只有 ~20KB）
3. **给它的 CSS 变量加 `--af-` 前缀** ——
   ==archify 在 `:root` 定义了 32 个变量，名字和我们完全一样（`--bg` / `--text` / `--panel`），
   直接嵌会把我们整页变成深色。==

两边都用 `data-theme` 属性，所以**深浅色天然同步**，不用额外处理。

#### 维护 SVG 节点后处理时的边界

普通笔记只配置 `bodies`、`frames` 等字段，不手改生成 SVG。下面只用于维护 `tools/lib/node-body.mjs` 这类构建期后处理逻辑。

替换节点内容时，节点内部可能还有图标等嵌套 `<g>`。找节点结束位置要计算嵌套深度，把节点自己的外层也算进去；不能把第一个 `</g>` 当成整个节点的结尾，否则会漏删旧文字或使新内容错位。修改后用有图标和丰富内容的节点验证，再检查最终页面。

#### archify 的校验值不值得用

**值得，而且这是它最值钱的部分。** 它会精确告诉你：

```text
Label "用户认证与鉴权流程" (~132px) is wider than component "gateway" (120px)
Label "请求" overlaps component "gateway"
  label rect: [286, 120, 48, 14]
  component "gateway" rect: [250, 80, 120, 60]
  Suggested fix: labelAt [310, 154] or labelDy +24
```

它**测量了文字宽度**、**检测了碰撞**、**给了具体坐标**。我们的积木完全不做这些。

## 版面与样式

### 按问题选择修改层

设计和验收统一按原则 ⑩；这里说明实现落点，不另设画幅或字号标准。先区分单张图的数据布局、共享积木能力和全站外壳，不把所有局部问题都改成全站 CSS。

所有页面共用 `assets/theme.css` + `assets/blocks.css` + `assets/app.js`，但每张图的源 spec 和内容由本图负责：

| 症状 | 改哪 |
|---|---|
| 全站图列过窄或外壳留白异常 | 核对 `theme.css` 的 `--shell` / `--prose` / `--gutter` 与 main 实际宽度，不把单图内容少当成全站问题 |
| 单张图内部空、挤或关系未铺开 | 检查本图内容与数据布局；补实际缺失的信息、调整节点与路由，不为了填空拉大图或改全站样式 |
| 整体图要更宽、内容要铺开 | 改这张图源 spec 的 `meta.viewBox`，同时重排 `pos`、`size` 和路由。不要只扩空画布或用 CSS 放大小图 |
| 小图被页面拉大，字号跟着变大 | 核对本图 `arch.maxScale` 与实际 SVG 显示尺度，不为限制图字改全站正文 |
| 共享积木在窄屏被不可恢复地裁掉、关键控件不可达 | `blocks.css` 里做安全降级；优先局部滚动，不为手机重做图义 |
| 目录 / 交互别扭 | `app.js` + `lib/page.mjs` |
| 颜色不对 | `theme.css` 的 token |

`raw` 可以用现有类、主题变量和局部行内属性表达一次性结构，不在 `note.md` 新塞 `<style>`。新增通用样式放在共享层并按既有协作流程处理，不为某一篇覆盖全站版心；单图拥挤先改本图数据和布局。

### 当前版面实现与维护边界

当前 `theme.css` 用 `--shell: 2400px` 限制外壳最大宽度，`main` 伸展到可用列；`--prose: 1200px` 限制文字元素行宽，不限制所有图。当前没有 `--wide` 或 main 的 1280px 固定上限。这些是现有实现值，不是每张图必须采用的画布尺寸。

当前 grid 版面保留 main 的伸展与 `max-width: 100%`，不要在这里加 `margin-inline: auto` 改成按内容定宽。此处曾让整列停在较窄的文字宽度，外壳加宽也没有让图获得空间。维护时分别量视口、main 和图的实际宽度，确认图列没有被正文行宽锁住；不要把这个项目的约束泛化为所有 CSS 布局中 auto 都会出错。

`arch` 画布宽度上限来自 SVG viewBox 宽 × `maxScale`；默认倍率 1，空间不足时按组件实际策略缩小或提供局部滚动，显式大于 1 允许等比放大。画布扩大要重排源 spec，不手改 SVG。获批原型保留本图尺度，例如进程和线程首图的 0.87，不把它当全站倍率。

底图几何、缩放和正文宽度分别维护。具体字段在 `references/blocks.md` 的 `arch`，完成后按原则 ⑩ 检查目标视口与对应回归范围。

### 行内强调与颜色：别让一种标记承担所有重点

| 写法 | 语义 | 颜色 |
|---|---|---|
| `==文字==` | 关键结论 / 最该记住的一句 | 蓝 |
| `!!文字!!` | 坑 / 反直觉 / 注意 | 橙 |
| `++文字++` | 正确做法 / 推荐 | 绿 |
| `**文字**` | 句子内的重音（降级用） | 加粗不变色 |

强调的选择按原则 ⑪，这里说明标记语义。一屏最多三处 `==`，并结合每段最多一处、每节通常两三处控制重点；不能用另一种颜色把所有剩余文字再强调一遍，也不为凑数量删必要内容。

#### `callout` 的颜色也一样 —— 别让红色承担所有重点

```callout
tone: red
icon: ⚠
text: |
  ==**提示颜色表达风险，不是表达作者觉得它重要。**==

  例如「这篇介绍三种方案」只是内容说明，不需要红色警告；
  「这个命令会删除未提交文件」才是具体风险，需要显著提示和确认。
  普通说明也用警告色，会让真正的风险难以分辨。
```

**按这句话选颜色：这条是「会出错」，还是只是「值得知道」？**

| tone | 什么时候用 | 判据 |
|---|---|---|
| `red` | **真的会出事** | 会丢数据 / 会被拦 / 会静默出错 |
| `amber` | 注意、已知局限、容易忽略的规则 | 不遵守会返工，但不会立刻炸 |
| `violet` | **结论 / 洞察**（「所以…」） | 读到这里该记住的一句话 |
| `green` | 正确做法 / 已验证 | 照着做就对了 |
| `blue` | 入口提示（「先读第 0 步」这类导航） | 很少用 |
| `muted` | 纯事实陈述 | 不劝你做任何事 |

> 拿不准时问自己：**如果读者跳过这条，会发生什么？**
> 答「没影响，只是不知道」→ 不配红。

### 代码块：**先分行，再谈分色**

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==**粘一段单行 SQL 进笔记，等于没写。**==

  子句、权限、条件全挤在一行，读者要在脑子里自己断句。
  这跟「把图挤成一团」是同一种偷懒 —— 只是不容易被截图抓出来。
```

**两条规矩，按优先级：**

#### ① 分行 —— 一个子句一行，嵌套的缩进

```compare
first: 写法
head: [读者要做什么, 什么时候必须分行]
rows:
  - 一整行塞完:
      - { text: "在脑子里断句、数括号、找 AND 在哪", tone: red }
      - "永远不要。除非真的只有 `SELECT 1` 这么短"
  - 一个子句一行:
      - { text: "从上往下读，一眼看出结构", tone: green }
      - "SELECT / FROM / WHERE / GROUP BY 各占一行"
  - 嵌套再缩进:
      - { text: "子查询、AND 续行看层级", tone: green }
      - "子查询整体缩进两格；`AND` 接在下一行、再缩两格"
```

下面是排版示意：查询订单表，把已支付订单的金额按用户汇总。两种写法内容相同，分行后更容易找到筛选和汇总步骤。

```text
❌ 全挤在一行
SELECT user_id, SUM(amount) AS total FROM orders WHERE paid = 1 GROUP BY user_id;

✅ 按子句分行
SELECT user_id, SUM(amount) AS total
FROM orders
WHERE paid = 1
GROUP BY user_id;
```

有子查询时，再按嵌套层次缩进，不需要为了展示排版引入另一套业务术语。

```callout
tone: amber
icon: ⚠
text: |
  **但如果原文就是这样（比如真编译器的输出），分行之后要说明。**

  ==读者会以为「真代码就长这样」。==

  正确做法是分行展示 + 一句注明：

  > 原始输出是一整行，这里只在子句之间换行以便阅读。
  > 不改变语句内容，也不改字符串或注释中的换行。
```

#### ② 分色 —— 分的是**来源**，不是语法

```callout
tone: violet
icon: 💡
quote: true
text: |
  ==**不要做语法高亮（SELECT 蓝、字符串橙）—— 那是编辑器的事，不是笔记的事。**==

  笔记里分色的价值在另一件事：**一段代码里混了多个「来源」时，
  用颜色把来源分开。**
```

例如一个订单查询同时包含三种来源：账号只能看所属组织的订单，用户选择查询条件，系统再计算实付金额。颜色要帮助读者分清这三件事：

```compare
first: 颜色
head: [代表什么, 为什么值得一色]
rows:
  - 琥珀:
      - "**权限条件** —— 当前账号能访问哪个组织的数据"
      - "它不是用户选择的筛选条件，必须和用户输入区分"
  - 白（默认）:
      - "**筛选条件** —— 用户在界面上选择的"
      - "主体，不需要额外颜色"
  - 紫:
      - "**计算表达式** —— 展示值由其他字段计算得到"
      - "例如实付金额 = 原价 − 优惠，需要让人看出它不是直接读取的单个字段"
```

**判据**：一段代码里如果有 **2 个以上来源不同**的东西混在一起，
分色讲得清；只有一种来源就别上色（纯噪音）。

#### ③ 做成交互时，把来源和文字一起生成

生成查询结果时，让每个片段同时带上「权限条件、用户筛选、计算表达式」这类来源标签，再按标签着色。具体数据格式以所用控件为准，不另手抄一份带颜色的输出。

切换账号或筛选条件后，重新生成文字和来源标签，并核对颜色对应的含义。这样颜色跟着数据变化，不会出现文字更新了、颜色还指向旧条件的情况。

> 写这类 demo 时：**先想清楚有几种语义来源，再定颜色。**
> 不要先挑颜色再往里塞内容。

### 响应式：宽屏完整呈现，窄屏安全降级

下面是现有外壳的视口断点，不是判断用户在电脑还是手机上的规则：

- **视口宽度 ≥1081px**：目录是一列，点顶栏 ☰ 可收成 0；图和交互按完整形态呈现
- **视口宽度 ≤1080px**：目录变成左侧抽屉，点遮罩或 Esc 关闭
- 状态记在 `<html data-toc>` 上，样式全在 `theme.css`，JS 只切属性
- 复杂图和交互不要求改成竖排；可以保留桌面画布，在自身容器内滚动

#### 什么时候检查窄屏

统一按原则 ⑩ 的验收表：普通笔记验证目标桌面和固定布局回归；共享积木、共享控件或外壳改动增加一次窄屏安全冒烟。只有用户明确要求手机使用时才扩展完整设计，不另在这里设第二套标准。

已有响应式重排不等于新做移动版；只能在组件实际支持的通道中到达完整内容。没有安全通道的裁切要报告并处理，不能凭「窄屏可滚动」的文案当作已支持。

#### 常见布局故障与排查入口

| 症状 | 根因 |
|---|---|
| 图整体错位，节点被推下去 414px | 用脚本「**区间替换**」改 CSS，把区间里的 `.flowd-svg { position: absolute }` 一起删了 |
| 区域框溢出到上面的段落里 | **设计缺陷**：框比节点大一圈，第一行就是被分组节点时框顶跑到容器外 |
| 加 padding 后所有图错位 | **坐标系不统一**：节点坐标相对 `.flowd-grid`，SVG/区域框相对 `.flowd` |
| 两个区域框重叠 | **每行独立居中** → 同组节点跨行会水平错位，两组包围盒几乎相接，框一往外扩就重叠 |
| `cards` 里的 `<pre>` 撑破容器 | **grid item 默认 `min-width: auto`**，不会缩到内容宽度以下 |
| **切换深浅色后，某个色块停在旧主题的颜色上** | `transition: background` + `background: color-mix(...)` —— 见下面「换主题后色块停在旧颜色」 |
| **点了按钮再截图，样式还是点击前的** | `--virtual-time-budget` 下过渡不推进 —— 见下面「点击后截图仍显示旧样式」 |

#### 点击后截图仍显示旧样式

````callout
tone: red
icon: 📸
text: |
  **点一下控件再截图，截到的是点击前的样式 —— 而 DOM 里 class 已经是对的。**

  当时一个控件有 A、B 两个状态按钮。点击 B 后，表示选中的 `.on` 类已经从 A 移到 B，
  但截图中的背景颜色仍停在点击前。观察结果可以概括为：

  ```
  按钮 A：没有 .on，却仍显示选中颜色
  按钮 B：有 .on，却仍显示普通颜色
  ```
````

**当时的原因**：测试用 Chrome 的 `--virtual-time-budget` 推进虚拟时间，CSS 过渡却停在起点。遇到类似现象，先比较 DOM 状态与计算样式，并用禁用过渡的截图作对照，不直接认定业务状态切换失败。

**怎么确认是它**：注入 `* { transition: none !important }` 之后再读一次计算样式，样式立刻归位。
上面那个例子，关掉过渡后两个按钮的颜色正好对调回来。

**已经修在工具里**：`tools/block.mjs` 生成的预览页现在带一条

```css
*, *::before, *::after { transition: none !important; animation: none !important; }
```

==过渡只在值**改变**时触发，初次渲染不受影响== —— 所以量静态布局的 `visual-check` 基本不受影响，
只有「点一下再截图」这条路会踩到。

自己写状态截图脚本时也补上这条测试样式。它用于得到稳定的状态画面，不是要求从实际页面删除动画。

#### 换主题后色块停在旧颜色

```callout
tone: red
icon: 🌗
text: |
  **曾在换主题测试中遇到：主题变量已切成浅色，使用 `color-mix(...)` 和背景过渡的色块仍停在深色。**

  这种问题需要实际切换主题才能发现，不能用静态布局检查的通过来排除。
  下方给出排查办法，不把这次观察当成所有浏览器版本都必然发生的行为。
```

下面是这种问题的排查顺序；关键是区分主题变量没变，还是过渡让最终颜色没有更新：

| 检查 | 当时的结果 | 能排除或定位什么 |
|---|---|---|
| 读取主题变量 | 已经是浅色值 | 不是主题状态没切换 |
| 读取色块的实际背景 | 仍是旧的深色 | 变量与最终显示结果不一致 |
| 临时禁用背景过渡后再读 | 恢复正确浅色 | 继续检查颜色过渡，不先改主题变量 |

当时先确认主题变量已更新，再禁用 `background` 过渡，色块便恢复正确颜色，因而把问题定位到颜色过渡，而不是主题状态。遇到同类症状也用这个对照验证；当前浏览器的实际行为仍以测试为准。

++规矩：给「背景是 `color-mix`」的元素写 transition 时，只写具体属性，不写 `background`、更不要写 `all`。++

```css
/* ❌ 换主题会卡住 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent); transition: .18s; }

/* ✅ 只过渡真正会动的东西 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent);
        transition: color .18s, box-shadow .18s; }
```

**查法**（一条命令扫全站）：

```bash
python3 - <<'EOF'
import re, pathlib
css = pathlib.Path('assets/blocks.css').read_text()
for sel, body in re.findall(r'([^{}]+)\{([^}]*)\}', css):
    if 'transition' not in body: continue
    if not any('color-mix' in l for l in body.split(';') if l.strip().startswith('background')): continue
    t = re.search(r'transition:\s*([^;]+)', body).group(1).strip()
    if 'background' in t or re.fullmatch(r'\.?\d+(\.\d+)?(m?s)?', t):
        print(sel.strip()[:60], '→', t)
EOF
```

==写新控件时顺手跑一次，比等用户在浅色模式下发现便宜得多。==

#### archify 图出现黑色三角形：检查共用 CSS

```callout
tone: red
icon: ⚠
text: |
  ==`assets/archify-embed.css` 是全站共用的，但它是**每次跑 archify 时重新导出**的。==

  导出时会按「`assets/arch/` 下所有 SVG 用到的 class」筛规则。
  一旦筛漏，图里的元素就掉样式 —— 而且**构建、visual-check 全是绿的**。
```

**真实事故**：CSS 丢了 `.a-dashed` / `.a-security`（少 `fill: none`），
图里的虚线边被**填成黑色三角形**，压在节点上。

| 症状 | 根因 |
|---|---|
| 图里出现大块黑色三角/色块 | `archify-embed.css` 缺了某个 class 的规则，`fill` 回退成黑色 |
| 只丢了某类图元的颜色或边线 | 该图元的 CSS 规则可能未被导出，核对 SVG class 与共用样式 |

````callout
tone: green
icon: ✅
text: |
  **修法**：重跑任意一张图，它会按并集重新导出共用 CSS。

  ```bash
  node tools/archify.mjs archify/<名字>.json <名字>
  ```

  `npm run check` 有专门检查（对比 SVG 用到的 class 和 CSS 里定义的 class），
  缺了会直接报出来并告诉你重跑哪条命令。
````

#### 改共享样式的约束

1. **改一条 CSS 规则就替换那一条，别用大区间。** 非要大改，改完 grep 一遍原来的选择器。
2. **绝对定位的装饰元素要考虑「会不会超出容器」。** 加了就配 padding。
3. **坐标计算必须统一参照系。** 容器一有 padding，相对不同父元素量的坐标就会错开。
4. **放进 grid / flex 的元素要设 `min-width: 0`**，否则内容会把容器撑破。
5. **`background: color-mix(...)` 的元素，别写 `transition: background` 或 `transition: .2s`。**
   换主题时 Chrome 插值不了两个 `color-mix` 计算值，颜色会卡在旧主题上 ——
   静态 `visual-check` 不切主题，仍要实际验证深浅色切换。详见上面「换主题后色块停在旧颜色」。
6. **不该占布局尺寸的提示框，关闭时用 `display: none`。** 只设 `opacity: 0` 会保留尺寸，可能使容器量图报溢出；不要把「看不见」等同于「退出布局」。
7. **维护 `flow` 群组布局时，对齐框的外扩量和容器留白。** `app.js` 的 `PAD_X_MAX` 与 `blocks.css` 的横向 padding 要配套，不能只让 SVG 向外画框而不给容器留位置。长群组标签也要限宽折行；具体尺寸读当前实现，不把某次测量值当作所有图的模板。

## 依赖策略：默认零依赖

页面要能离线单文件打开。外部库会增加内联体积和维护成本，不能因为某个局部效果顺手就默认引入。

| 需求 | 用什么 | 要不要库 |
|---|---|---|
| 高亮、淡入、位移 | CSS transition / animation | 不要 |
| 元素沿路径移动 | CSS `offset-path` | 不要 |
| 流程连线 | 测量 + 内联 SVG（见 `flow` 积木） | 不要 |
| 数字滚动、按步播放 | Web Animations API / setTimeout | 不要 |
| 复杂时间轴编排、物理弹簧 | —— | 到这一步再说 |

**先零依赖做到极限。** 真不够时再讨论装什么，并且要把决定写回这一节。

## 变体：源码通读

用户说「读 xxx 代码，画出架构」时，**不要从 README 开始读** —— README 经常过期。

```callout
tone: amber
icon: ⚠
text: |
  **源码通读也先按原则 ⑦ 对齐读者起点。** 从零理解时，先给领域概念与例子，
  再讲组织和实现；已有基础的源码问题，直接补相关机制和代码位置，不重写整套入门章节。

  缺少的前置要补齐，不能只给一张堆代码名字的图。
```

按这个顺序读：

1. **摸依赖图** —— 一条命令看出谁依赖谁：
   ```bash
   find . -name '*.ts' -not -path '*/node_modules/*' | while read f; do
     echo "$f → $(grep -oE "from '[^']+'" "$f" | sed "s/from '//;s/'//" \
       | grep -E '^(\.|src|@)' | tr '\n' ' ')"
   done
   ```
   横切的（被所有层依赖）和纵深的（依赖所有层）一眼可见。
2. **按行数排序找候选** —— 大文件值得优先看，但行数不等于复杂度；配置、生成代码和重复表格也可能很长。
3. **读入口** —— `index.ts` / `context.ts` / 工厂，它们定义了架构骨架。
4. **找反直觉的实现** —— 这是最值钱的卡点。信号：
   - 注释里出现「为什么不用 X」的解释
   - 有一行代码做了意料之外的事
   - 到处都在 `?? new XxxDefault()` 兜底（往往是个真实的坑）
   - 常量里出现取模 / 哈希分片
   - 有一个 `switch` 的 `default` 直接 `throw`
5. **确认，不要猜** —— 断言「这里会 throw」之前，先把那几行读出来。

结构与机制都按原则 ⑧ 选择表达，按原则 ⑨ 选择或扩展工具。有包边界与多种归属时用适合的结构图，只有短顺序时可以用 `lane-stack`；不预先断定所有结构都能被同一个积木表达。

### 需要确认函数输出时，写一个小测试脚本

这里只用于用户提供本地源码、需要核对函数行为的任务。测试脚本也叫探针：它导入待核对的函数，传入一组明确样例，打印返回值和相关状态，不是另做一个演示页面。

本地 TypeScript 项目已有 `tsx` 时，先在 `/tmp/probe.ts` 编写这个脚本，用绝对路径导入目标源码，再从被核对的项目目录运行：

```bash
./node_modules/.bin/tsx /tmp/probe.ts
```

`/tmp/probe.ts` 不是仓库自带文件，需要先写；命令中的运行器必须已经存在。不为验证一个函数自动安装或升级依赖。执行前按原则 ⑤ 检查副作用，脚本放在 `/tmp` 并不能保证调用安全；不能运行时读实现并说明验证边界。

模块测试与页面截图不同：前者可以绝对路径导入源码，后者还依赖页面和样式的相对位置，不把同一套临时路径约定直接套过去。

判据很直接：**代码里有 `switch` / `if-else` 分派的地方，就是该画图的地方。**

### 笔记会静默过期

**源码通读类笔记必然会过期，而且没有工具会发现。**

例如一次代码重构可能造成这些变化；这里看的是过期类型，不需要知道某个旧项目：

| 笔记原来说明的 | 重构后可能发生的变化 |
|---|---|
| 某函数是唯一入口 | 新增另一条处理路径，旧函数不再被所有调用者使用 |

| 某个缺陷需要绕过 | 缺陷已修复，旧绕过办法不再适用 |

## 变体：拆解一个东西

用户说「拆解一下 X」时，用这六个问题收集要解释的事实。输入、输出和职责可写成 `spec` 速查；处理过程涉及关系、顺序或状态时，按原则 ⑧ 再配图，不能把填完六栏当作机制已经讲清楚：

| 维度 | 问什么 |
|---|---|
| **输入** | 喂给它什么？什么类型、什么形态？ |
| **处理** | 中间做了什么？有哪几步？ |
| **输出** | 吐出什么？给谁用？ |
| **怎么调用** | 别人实际怎么用它？贴一段真实调用代码 |
| **为什么这么设计** | 作者为什么这样选？**注释里常藏着答案** |
| **业务价值** | 它到底解决了什么问题？没有它会怎样？ |

```callout
tone: amber
icon: ⚠
text: |
  ==但不是所有东西都值得拆。==
```

**详略按用户的问题和对象的作用判断。** 调用次数用于寻找使用场景，不是值得解释的门槛；一个只调用一次的关键分支也可能需要讲透。

- 只需速查职责或简单用法 → 一行对照或短卡片可以讲清，不凑六段。
- 要理解机制或主干作用 → 给实际调用、输入输出和过程，缺前置按原则 ⑦ 补，不因调用少省略。
- `src/` 里没有直接调用 → 继续查导出、注册、构建或间接使用，不能仅凭搜索为空断定它没有输入输出。

不适用的维度说明原因即可。取舍理由仍保留，正文组织和语气按原则 ⑪ 写，不以整齐六栏代替内容判断。

### 先搞清楚：这不是分支的问题

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==多个会话**共用一个工作目录**，才是根因。==

  开分支解决不了 —— `git checkout -b` 只改 HEAD 指向哪，
  **工作区里的文件一个都没变**。两个 agent 在同一目录里，改的还是同一批文件。
```

例如两个会话共用目录：A 改自己的笔记，B 正在写另一篇。A 执行 `git add -A` 时，两篇的改动都会进入暂存区，B 的半成品也可能被提交。历史上发生过这种误带；关键风险是共享工作区，不是提交号或文件数量。

三个设计放大了它 —— 它们本身都没错，错的是**假设只有一个改动人**：

| 设计 | 本意 | 共用目录时 |
|---|---|---|
| `git add -A` | 提交一个自洽快照 | **仓库级** —— 分不清谁改的 |
| 产物是全量的 | clone 下来就能开 | 我 build 会重建**所有人**的产物 |
| 保存即有竞态 | —— | A 保存、B 正在 build → B 构建出 A 的半成品 |

### 先做这件事：每个会话一个 worktree

```bash
cd ~/works/codes/knowledge-html
git worktree add ~/works/codes/kh-<会话名> -b <会话名>
cd ~/works/codes/kh-<会话名>
ln -s ~/works/codes/knowledge-html/node_modules node_modules
```

每个目录是**完整独立的工作区**：文件互不可见，`git add -A` 只会扫到自己的改动。
==误提交从根上消失。==

**常见的工作区与路径问题**：

| 坑 | 怎么办 |
|---|---|
| `node_modules` 不跟着 worktree 来 | 软链过去（上面那条），或各自 `npm install` |
| 软链显示成 `?? node_modules` | `.gitignore` 里写的是 `node_modules/`（带斜杠 = 目录），**匹配不上软链** —— 改成 `node_modules` |
| 全局 skill 的符号链接指向主仓库 | worktree 中的副本会参与该工作区的检查；全局加载的是主仓库副本。两者的区别见下文 |
| **习惯性 `cd` 回主仓库** | 开了 worktree 之后，每条命令都要从 worktree 目录起。==习惯性的 `cd ~/works/codes/knowledge-html` 会把改动全写回共享目录==，而自己的 worktree 干净得可疑 —— `git status` 一片空白就是信号 |

````callout
tone: amber
icon: 🪢
text: |
  **分清全局 Agent 加载的 Skill 与当前工作区检查的 Skill。**

  真实布局是这样：

  ```
  ~/.agents/skills/knowledge-html  ──软链──→  <主仓库>/.agents/skills/knowledge-html
                                              <worktree>/.agents/skills/knowledge-html   ← 独立副本
  ```

  `.agents/skills/**` 是**进仓库的跟踪文件**，所以每个 worktree 各有一份。
  你按直觉去改 `~/.agents/skills/knowledge-html/SKILL.md`，==改的其实是**主仓库的工作区**==，
  而 `npm run check` 读的是 **worktree 里那份** —— 于是：

  | 你看到的 | 实际发生的 |
  |---|---|
  | 文件确实改了，内容也对 | 主仓库工作区脏了（别的会话会看到） |
  | `npm run check` 还是报「SKILL.md 说 20 个控件」 | worktree 那份没动 |

  ++正确做法：在 **worktree 里**改 `.agents/skills/knowledge-html/SKILL.md`。++
  主仓库那份等分支合并时自然更新。

  ==这次先改错了地方，`check` 报的却是「代码 22 个 vs 文档 20 个」，
  完全看不出是「改的是另一个副本」。==
````

### 用完的 worktree 也要收（删之前有四道门）

工作区不会因为分支已合并就自动删除。清理前要区分：已完成且可恢复的目录、还有未提交内容的目录，以及用户明确要保留的目录。目录数量和占用空间只是提示，不是删除许可。

```bash
npm run worktree-audit        # 只读：分类 + 给出待执行的命令 + 报数
```

它只做三件事：分类、把命令写出来、把 `df -h` 的数字摆出来。
==删除不可逆，所以它自己不删 —— 「可删候选」是建议，不是许可。== 四道门：

| 门 | 为什么 |
|---|---|
| 路径只从 `git worktree list` 读，不手打 | 手打的路径会漏掉开在别处的工作区 |
| 主仓库和当前所在的工作区永远不进候选 | 删掉当前目录，会话当场死 |
| `wip:N`（有未提交的改动）**停下来问人** | 删掉干净的工作区可以从分支恢复，未提交的东西不能 |
| 板子上最后一次提到它的时间一起打出来 | 哪个会话你钉着，只有你知道 |

**钉住的会话不进候选。** 脚本算不出「你还想留着哪个」——
它把候选和命令行摆出来，由你点名。删掉一个已并入 main 的工作区，
`git branch -d` 会跟着把分支收掉；**报错就说明判断错了，停下来重看一遍。**

**合并时冲突面比想象的小**。量过：==全仓库只有 `index.html` 一个文件是全量的==
（`dist/<slug>.html` 和 `notes/<slug>/index.html` 都是**每篇一个文件**，只有作者会动）：

| 文件 | 合并时 |
|---|---|
| `dist/<slug>.html`、`notes/<slug>/index.html` | 各改各的 → **不冲突** |
| `index.html`（首页树视图） | 所有人都动 → **必然冲突** |

`index.html` 冲突时**别手动 merge** —— 它是生成的：

```bash
git checkout --theirs index.html   # 随便选一边，反正是生成的
npm run build:standalone           # 用合并后的源重建
git add index.html && git commit
```

### 没条件开 worktree 时：点名 add，别用 `-A`

```callout
tone: amber
icon: ⚠
text: |
  ==把 `git add -A` 换成 `git add <具体路径>`。==
```

```bash
git add notes/<你的 slug>/ archify/<你的名字>.json assets/arch/<你的名字>.svg
git add assets/blocks.css assets/app.js      # 只在你确实改了它们时
git add index.html dist/                     # 产物是全量的，必须一起带上
```

**为什么这样更安全**：`-A` 是仓库级的，它不问「这是谁改的」。
点名 add 只带走你确认过的东西。

### 还有第二个矛盾：产物是全量的

即使分了 worktree，合并时还有一道坎。

```callout
tone: amber
icon: ⚠
quote: true
text: |
  ==构建产物是**全量**的。==

  `index.html`、`dist/*.html` 里包含**所有人的内容**。
  所以你没法「只提交自己的部分」—— 那样仓库就停在「产物新、源旧」的不一致状态，
  pre-push 钩子会直接拦下。
```

**推论**：提交 = **提交一个自洽快照** = 当前所有源 + 由它们构建出的所有产物。

这意味着**你必然会把别人的改动一起提交**。这不是错误，是设计。关键是把这件事做**安全**。

### 三类文件

| 类别 | 例子 | 谁负责 |
|---|---|---|
| **共享产物** | `index.html`、`dist/*.html`、`notes/<任意 slug>/index.html`、**`skill/*.html`** | **每次提交都要带上全部** |
| **共享源** | `assets/theme.css` `blocks.css` `app.js`、`tools/*.mjs`、`package.json`、`.agents/skills/**` | 谁改谁提交，但**要小心** |
| **私有源** | `notes/<你的 slug>/`、`archify/<你的名字>.json`、`assets/arch/<你的名字>.svg` | 只有你改 |

### 开工前（30 秒）

```bash
npm run status
```

它会把你工作区的改动**分类列出来**（临时文件 / 共享产物 / 共享源 / 笔记源），
并标出每项的修改时间。

!!这一步只说明「开工那一刻」。!! 别的会话可能在你干活期间才开始 ——
开工时干净不等于全程干净。

```compare
first: 场景
head: [怎么办]
rows:
  - 短活（一篇笔记，半小时内）: ["直接干。收尾再跑一次 `status` 就够"]
  - 长活，或要改共享源（`assets/` `tools/` `plans/` `SKILL.md`）: ["开 worktree。==写共享源之前重跑一次 `status`== —— 这一条是真实事故换来的，见下"]
```

> **真实事故**：改 `plans/insight.yaml` 加完节点几分钟后，同一个文件被另一个会话写回，
> 我的改动**静默消失**（`git log -S` 查不到，像从没写过）。两个会话都「开工时干净」。
> 共享源的写入冲突是这样的 —— 不报错、不留痕，只是你写的东西没了。

- 干净 → 直接干活
- **有别人的改动** → 两种走法：
  - 你在 worktree 里 → 与你无关，但合并时要注意
  - 你在共用目录里 → 记住它们，但**不要用 `-A`**，点名 add
- 有别人的改动**且明显是半成品**（写了一半、构建不过）→ **先问用户**

### 干活时

1. **只改自己的文件。** 不要顺手改别人的 `note.md`，哪怕发现它写错了 —— 报告，不擅自改。
2. **改共享源要小步。** `blocks.css` / `app.js` 有别人在用：
   - ==改一条 CSS 规则就替换那一条，别用大区间替换==
   - 加控件 / 积木用**新名字**，别改别人的
   - 改完尽快提交，别攒着
3. **临时文件进 `.gitignore`。** 预览副本、截图、草稿别留在 `notes/` 里。
   约定：以 `_` 开头的文件是临时的（`_p.html`、`_wip.html`）。

### 提交时

```bash
npm run status              # ① 分类看清 —— 这一条不能省
npm run check               # ② 校验（含 skill 一致性）
npm run build:standalone    # ③ 重建全部产物
npm run skill               # ③b 重建 skill/（改了 skill 文档才需要）
npm run visual-check        # ④ 量图
git add <点名清单>          # ⑤ 优先点名；确认过才用 `-A`
node tools/status.mjs --cached   # ⑥ 再看一遍 staged 的
```

```callout
tone: amber
icon: ⚠
quote: true
text: |
  ==第 ⑤ 步优先点名 add。==

  共用目录里 `git add -A` 会把你**没看过的**东西一起带走 ——
  包括别人正在写的半成品。它不问「这是谁改的」。

  只有在你确实逐项确认过（第 ① 和 ⑥ 步都看过）时，`-A` 才可以。
```

```callout
  半成品 = 明显写了一半、或构建不过。

```

### 别人的改动怎么处理

| 情况 | 怎么办 |
|---|---|
| 别人的源完整、构建能过 | **一起提交**，提交信息里注明来源 |
| 别人的源是半成品 | **停下来问用户** |
| 只有别人的产物、没有源 | 说明源被漏了 → 找到源一起提交，或者问用户 |
| 别人改了共享源（`blocks.css`） | 一起提交，**在信息里说明你确认过它的改动** |

**提交信息里的注明格式**（已有先例）：

```text
来自并行会话（非本次工作，为保持产物与源一致一并提交）：
- notes/flink-source-transform-sink/（Flink 算子笔记）
- tools/visual-check.mjs（加 .keyby-viz 容器 + JSON 解析错误上下文）
```

### 构建和提交之间的竞态（真实踩过）

```callout
tone: red
icon: ⚠
text: |
  **`npm run build` 和 `git add` 之间，别人的文件可能又变了。**

  于是你提交的是「**源是新的、产物是旧的**」——
  pre-push 钩子一重建就发现对不上，直接拦下。
```

**时间线**（真实发生）：

```text
① 我 npm run build:standalone   → 从 note.md 的版本 A 构建出产物 A
② 我 git add -A && commit       → 期间别人保存了版本 B
                                  结果提交的是：源 B + 产物 A   ← 不一致
③ pre-push 重建                 → 从 B 构建出产物 B ≠ 产物 A → 拦下
```

**修法**：源已经提交了，只是产物过期 —— 重建后 amend：

```bash
npm run build:standalone
git add -A
git commit --amend --no-edit
git push
```

```callout
tone: amber
icon: ⚠
text: |
  ==如果这样还反复被拦，说明别人正在持续编辑。==

  那就别再重试了 —— **停下来问用户**，等对方告一段落。
  反复 amend 只会把你的提交变成「别人半成品的快照」。
```

#### 第三种拦法：别人改了共享源，而你的提交本身是干净的

````callout
tone: amber
icon: ⚠
text: |
  **症状**：已提交的快照只包含自己的完整改动，但共用工作区又有别人未提交的共享源变化，推送时被拦。

  钩子重建的是当前工作区，而不是隔离的提交快照。未提交的 `assets/blocks.css` / `assets/app.js`
  会进入重新生成的页面，使产物与提交中的版本不同。先用 `status` 分清工作区变化和已提交快照，
  不把「我的提交不含别人的改动」误说成「当前工作区干净」。

  ==这跟你的提交无关，但钩子分辨不出来 —— 它只看「重建之后工作区有没有差异」。==
````

**修法：在干净 worktree 里推**（谁的文件都不用改）：

```bash
# ① 在已提交的 HEAD 上开一个干净 worktree —— 等价于「只有我的提交」的状态
git worktree add ~/works/codes/<repo>-push -b <tmp-branch>
ln -s "$PWD/node_modules" ~/works/codes/<repo>-push/node_modules   # 省一次装依赖

# ② 里面重建，确认产物与提交一致
cd ~/works/codes/<repo>-push && npm run build:standalone
git status --short     # 应当只列出「你曾用别人脏源构建过的那几个产物」

# ③ 从干净 worktree 推，然后收掉
git add <那几个产物> && git commit --amend --no-edit
git push origin <tmp-branch>:main

# ④ 主工作区跟上去。**别用 reset --hard** —— 它会冲掉别人未提交的文件
git update-ref refs/heads/main <新 commit>
git reset -q HEAD -- <你改过的路径>      # 只刷自己那几个文件的索引
```

````callout
tone: red
icon: 🩸
text: |
  ==顺序反了会把产物提交坏。==

  先在主工作区（别人的脏源生效）里构建再提交，你的 `dist/<slug>.html` 里就
  **内联了别人还没提交的样式** —— 你机器上好看，别人拉到的产物却与源码对不上。
  干净 worktree 里重建出的那几份产物，`--amend` 进原提交即可。
````

### 别人的文件坏了，阻塞了共享构建

```callout
tone: amber
icon: ⚠
text: |
  ==`npm run check` 是全仓库的。别人一篇笔记写坏，你这边也过不了。==
```

**先分清是哪一类**：

| | 例子 | 怎么办 |
|---|---|---|
| **机械性问题** | YAML 裸标量以反引号开头 · 积木名拼错 · 引号没闭合 | ✅ **可以修**。工具自己会给出修法，改的是语法不是意思 |
| **语义性问题** | 内容写错了 · 数字不对 · 结构乱 | ❌ **不碰**。报告用户 |

```callout
tone: green
icon: ✅
text: |
  **判断标准：这个修改会不会改变别人想表达的意思？**

  加一对引号不会。改一个数字会。

  机械性修复要在提交信息里**单独列出来并注明**，别混在自己的改动里。
```

**真实案例**：并行会话的 Flink 笔记里有两行 `- q: \`xxx\` 是什么？` ——
YAML 里裸标量不能以反引号开头，整个仓库的 `check` 都挂了。
预检工具直接给出了修法（外面包一层双引号），修它零风险。

### 冲突处理

| 冲突的文件 | 怎么办 |
|---|---|
| `index.html`、`dist/*`、`notes/*/index.html` | **重新构建**，不要手动 merge。产物是生成的，冲突无意义 |
| `package.json` | 通常两边都加了 script → **两边都保留** |
| `blocks.css` / `app.js` | 真冲突，逐条看，**两边的改动都要留** |
| `note.md` | 不该发生。如果发生，说明两个会话改了同一篇 → **问用户** |

### 推送被拦下来怎么办

pre-push 会重建 + 量图。**它拦下来通常不是你的问题。**

```text
✗ 构建产物有变化（note.md 改了但没提交构建结果）
```
→ 有人（可能是你）改了源没重建。`git add` 上产物，`--amend` 重新提交。

```text
✗ 有图被画坏了
```
→ 看是哪个积木、哪一篇。**如果是别人笔记里的图坏了，报告用户，别去改别人的内容。**

### git 与多会话：五条硬规矩

1. **优先开 worktree。** 没条件就在共用目录里点名 `git add`，别用 `-A` ——
   共用目录里 `-A` 会带走别人正在写的半成品。
2. **产物和源必须一起提交。** 只交产物 → 来源不明；只交源 → 构建过期。
3. **不替别人改东西。** 发现问题 → 报告，不擅自改。
4. **提交前跑 `npm run status` —— 而且要看完。**
   别 `| head -45` 只扫前面一截就往下走。
5. **收工把 worktree 收掉。** 用完不删的会一直堆着，而且没人敢删 ——
   跑 `npm run worktree-audit` 拿分类，`wip` 的先问人。

## 硬约束

==这张表随时要用，所以留在这一页。==

| ❌ 不要 | ✅ 应该 |
|---|---|
| 为了「符合积木规范」而扭曲表达 | **怎么讲清楚怎么来**。积木是省力工具，不是验收标准 |
| 为了手机一屏放下而删节点、隐藏关键标签、把图改成简陋卡片或缩减交互 | 按原则 ⑩ 保留图义和操作，在组件实际支持的通道内安全降级，不假定所有积木都可缩放 |
| 因为 400px 下很挤就判断图太复杂 | 按原则 ⑩ 在目标桌面视口判断解释效果，固定回归另做，不因窄屏自动拆图或删信息 |
| 为普通笔记反复做移动端截图和调试 | 按原则 ⑩ 的范围验收；共享组件或外壳一次窄屏冒烟，明确手机需求时才扩展完整设计 |
| 硬把内容塞进最接近的积木 | 按原则 ⑨ 的适用条件选择组合、加字段、新建或 `raw`，不把考虑顺序当成必须逐级执行 |
| 编辑 `notes/*/index.html` | 那是产物，会被覆盖。只改 `note.md` |
| 跨笔记链接写成 `notes/<slug>.html` 或根绝对路径 | 源文写 `../<slug>/`。notes 产物指向兄弟笔记目录，dist 产物自动改为同目录 `<slug>.html`。回站点根的链接写 `../../`，dist 出口改成 `../`。遵循这套改写约定，才能让两种产物都指向正确位置 |
| 在单篇 `note.md` 里塞 `<style>` | 按原则 ⑨⑩ 复用已有类与主题变量；需要新通用样式时改共享层，单图数据布局仍改本图源 |
| 在正文写 `# 一级标题` | 标题只写在 `meta.json` 的 `title` |
| `meta.json` 里自己填 `verified: "日期"` | 它会进页面的溯源条，==那是「有人核对过」的声明==。agent 生成的一律留空 |
| 没挂树的笔记不填 `topic` | 填一个 —— 否则它在首页的「未归类」里落进「其他」组 |
| 原样搬用户的原文 | 先砍到骨架，再决定哪几段变成图 |
| 写「它不是 X，而是 Y」这类否定句 | **读者没听过 X**。除非 X 是读者真会有的误解，否则直接说 Y 是什么 |
| 写「这一步我之前没讲」「这张图我第一版画错了」 | **读者不知道你迭代过几轮**，这些话只对你有意义。直接陈述事实 |
| 图上的编号和正文对不上 | 正文用编号指代时，**图上必须真有那个编号**（archify 的边标签、积木的 badge 都要对得上） |
| 图上有文字被压住 | ==字还在、只是读不通，所以最容易滑过去。== `npm run visual-check` 会报「文字压文字」，改完图必须跑 |
| 一张图内部的 id（`arrowhead` / `grid` / `fa` / `s-fill`）按图固定 | 同页第二张图会去引用第一张的定义（读屏还会把图名念成第一张的）。内联时给 id 加图名前缀；`npm run check` 会报「页面上有重复的 id」 |
| 把 SQL / 代码粘成一整行 | 一个子句一行，嵌套的缩进。原文本来就在一行时（如编译器输出）要注明「换行只是排版」 |
| 把语法高亮当成分色 | 笔记里分的是**来源**（权限 / 条件 / 派生）—— 不要连 `SELECT` 都要上色 |
| 在允许裸 HTML 的单元格 / 字段里写字面 HTML 标签（如展示示例代码） | 它会真的成为元素；script 开标签会吞掉 app.js 全页静默全灭。++展示标签一律写 `&lt;` `&gt;` 实体++ |
| YAML 裸标量里出现 `: `（冒号+空格） | 加引号，或用 `|-` 块标量 |
| YAML 裸标量以反引号 `` ` `` 开头 | 加引号 |
| YAML 裸标量以 `*` `&` `!` `%` `@` 开头 | 加引号（会被当成别名/锚点/标签） |
| YAML 里 `mode: 234` 这种数字值到控件里是 number，不是字符串 | 控件里先 `String(cfg.mode)` 再比；否则静默走默认分支，`check` / `visual-check` 都不报 |
| 值里有 `[` 或 `{` 却没加引号 | 加引号（`Rule[]` 里的方括号会被当数组起始） |
| 担心 `**「术语」**` 这类中文加粗失效 | 已经修好了，不用管；但 `**` 跨行仍然不生效 |
| 只给卡点画图，其余照搬原文 | ==用户已经有文字版了==。有「空间 / 顺序 / 状态 / 归属 / 对比」就用图、控件或表。是不是卡点只决定先做哪一块、哪里加交互。见原则 ① |
| 因为「没有现成积木」就把关系和过程退回段落 | 按原则 ⑨ 组合或扩展表达，不丢结构；判断、依据和取舍理由仍按原则 ⑧⑪ 保留文字 |
| 先甩一个抽象判断，再用破折号复述一遍 | 两句话说的是同一件事。==直接从具体的东西说起，把结论留给读者== |
| 写只有报幕作用的过渡句 | 按原则 ⑪ 保留能说明问题转换或前置关系的承接，删无信息的报幕，不把所有过渡都删掉 |
| 没依据的绝对化（唯一 / 全都 / 永远 / 根本 / 只能） | 多半不准，读者找到反例就整篇不信了。==真能举出反例说「没有」时才用== |
| 一段里堆 `==` 和加粗 | 强调与文字组织按原则 ⑪；标记语义见「行内强调与颜色」，不为计数删掉必要信息 |

**每篇结尾必须有 `quiz`。** 这不是可选项 —— 知识库头号死因是「收藏代替理解」，
攒到 30 篇时自己都不记得里面有什么。2~3 题，逼自己合上答案复述一遍。

**`meta.json` 的 `sources` / `generated` / `model` / `verified` 会渲染成页内的溯源条。**
漂亮的 HTML 会自带「这应该是对的」的暗示，而它可能只是某次对话的产物。

> `status` 这个字段保留但**不再渲染**了。它以前驱动页顶那条琥珀色横幅
> （`status=draft` 就显示「尚未人工核对」）—— 后来删除了这条横幅，因为大多数页面长期处于 draft，
> ==一条永远亮着的警告等于没有警告==，只剩每页一条的噪音。
> 想看「哪篇核对过」就填 `verified`，它会在溯源条里显示成「核对 2026-09-24」。

### 改了「站点外壳」要多做一步

外壳 = `tools/lib/home.mjs`（首页）、`assets/theme.css` / `blocks.css`。
下面两个坑 **`npm run check` 一个都报不出来**，而且都是**静默**的：属性设上了、JS 里读也是对的，只有屏幕上不对。

````callout
tone: red
icon: ⚠
text: |
  **一、内联在模板字符串里的浏览器 JS，语法检查查不出 `ReferenceError`。**

  首页那段 `<script>` 是拼在 JS 模板字符串里的，`node --check` 看不到它。
  我重构时把旧函数整个换掉，**连同里面声明的 `var mode` 一起删了** ——
  语法完全合法，表现是「排序按钮点下去毫无反应」。

  → 在真实页面里跑一遍，并把 `window.onerror` 收上来（否则连报错都看不到）。

  ++这条已经收成一条命令了++：==`npm run probe:home`==。
  17 项：抽屉开关 / 排序是否真的重排 / 遮罩有没有色 / 右缘贴不贴边 /
  横向溢出 / 焦点进出 / `window.onerror`。失败退出码 1，并把你没过的项逐个打出来。

  它自己也是被验过的 —— 故意注入一个悬空变量，它会报两项失败（历史真发生过这个：
  重构时把 `var mode` 跟着旧函数一起删了，排序按钮哑了而 `node --check` 是绿的）。
````

````callout
tone: red
icon: ⚠
text: |
  **二、`el.hidden = true` 会被作者样式里的 `display` 盖掉。**

  浏览器自带的 `[hidden] { display: none }` 在 **UA 样式表**里，
  而 **作者样式表里任何一条 `display` 都会盖掉它** —— 跟优先级无关。

  所以 `.tnode { display: grid }` 一写，`n.hidden = true` 就完全失效：
  属性在、`el.hidden` 读出来是 `true`、屏幕上还画着。
  首页的**搜索和标签筛选因此哑了很久**（实测：32 个节点全被标了 `hidden`，32 个全在显示）。

  `theme.css` 里已经加了兜底，==站内新写的组件不用再操心==：

  ```css
  [hidden] { display: none !important; }
  ```

  但要是哪天自己写页面 / 导出 HTML，记得补上这条。
````

|---|---|
| `npm run status` | **开工前 / 提交前先跑这个** —— 把改动分类列出来 |
| **`npm run probe:home`** | **首页外壳的冒烟探针** —— `check` / `visual-check` 都盖不到首页（内联 JS + 浏览器运行时状态）。改了 `tools/lib/home.mjs` 必跑，见「改了站点外壳」 |

| `npm run check` | 校验积木语法 + YAML + 约定 + skill 与代码一致 + **skill 文档自己能不能渲染** |
| `npm run view -- <slug>` | 构建单篇 + 打开（**默认就开**，它的用途就是这个；agent 验证时加 `--no-open`）。单篇构建**不动 `index.html`**：只有这一篇是渲染过的，其余篇的搜索正文会退化成原始 markdown。 |
| **`npm run block -- <slug> <n>`** | **只看第 n 个积木**：量高 + 截图，打印截图路径。==默认不开浏览器==（人要看加 `--open`） |

| `npm run build:standalone` | 重建全部产物（`dist/*.html` + 首页） |
| **`node tools/render.mjs --standalone --only <slug>`** | **只重建这一篇的 `dist/`** —— 量图回路从 ~70s 降到 0.2s，而且**不会动别人的产物**（共用目录里尤其重要）。跑完接 `npm run visual-check <slug>`。⚠ 它的前置区块会把其它篇显示成「待产出」（`existingSlugs` 只含本篇），==以全量 `build:standalone` 为准==，不是自己的问题 |
| `npm run visual-check [slug]` | 用固定 **1280×900 视口**检查布局回归，不代替目标桌面视口的可读性和交互验收。==读的是 `dist/`==，不是 `notes/`；给了 slug 就只量那一篇 |

| `npm run skill` | 把这份 skill 渲染到 **`skill/`**（**进仓库**，首页链得到）+ 三个页面互链。默认不开浏览器，加 `--open` |
| `npm run new -- <slug>` | 新建一篇笔记 |
| `npm run serve` | 起本地服务器 |

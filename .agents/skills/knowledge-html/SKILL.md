## 触发与项目位置

用户以 **【图解】** 开头（后面可接内容、飞书链接、或「看上面」）。

项目固定在：

```
~/works/codes/knowledge-html
```

## 原则 ① · 讲透卡点，不是搬运内容

**你的任务不是「把内容搬进 HTML」，是「把用户卡住的那个环节讲透」。**

用户粘过来的原文通常有 60% 是铺垫、重复、客套。原样搬进去只会得到一个更长的、
仍然看不懂的页面。用户要的是**图和交互** —— 这是 HTML 相对纯文本唯一不可替代的价值。

所以：**先找卡点，再决定画什么图，最后才写文字。**

```compare
first: 不是
head: [搬运式, 讲透式]
rows:
  - 结构: ["照着原文分段", "按「卡点」重新组织"]
  - 篇幅: ["原文多长就多长", "砍到骨架，该删的删"]
  - 图: ["配几张插图", "把讲不清的地方变成图或交互"]
  - 判据: ["「内容都在了」", "「用户看完能说出所以然」"]
```

## 原则 ② · 积木是词汇，不是语法

**画图是为了让用户理解内容、思想、设计、意图。怎么好呈现就怎么来，不要拘泥。**

`lane-stack` / `journey` / `compare` … 这些积木的作用是
**让你不用每次从零写 CSS**，不是**限制你能表达什么**。

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==最危险的失败模式：读完积木清单，然后把内容硬塞进最接近的那一个。==

  结果是「合规但没讲清楚」—— 比不画图更糟，因为看起来做了工作。
```

表达不顺手时，**四条路，按优先级**：

| 优先级 | 做法 | 什么时候用 |
|---|---|---|
| 1 | **组合** | 现有积木拼一拼就能表达（大多数情况） |
| 2 | **加字段** | 方向对但缺一个能力。例：给 `demo` 加 `html` 字段支持自定义布局 |
| 3 | **新建积木** | 同一类表达反复出现（见 `references/extend.md`） |
| 4 | **`raw` 直接写 HTML/CSS** | 一次性排版。**这是合法选择，不是投降** |

判断标准只有一条：

> **这样呈现，用户能不能秒懂？** 而不是「这符合积木规范吗」。

`theme.css` 的变量（`--tone` / `--surface` / `--border` / `--blue` …）随你用，
深色模式自动跟着走。唯一底线：**不写死色值**，否则换肤会坏。

交互也一样：`demo` 积木的 `html` 字段可以放任意自定义控件，
`WIDGETS` 注册表里加一个函数就行。别因为「没有现成控件」就放弃一个能讲清楚的交互。

## 原则 ③ · 先对齐理解层次

**同一份材料，不同的人卡在不同层次。写之前先判断读者在哪一层。**

```
概念  →  组织 / 层面  →  架构
是什么    怎么组织      代码怎么实现
```

- **概念层**：这个领域有哪些词？每个词对应现实中的什么？
- **组织层**：这些概念怎么被组织成一个整体？
- **架构层**：代码怎么实现它？

**判断方法**：读者说「没接触过」「完全不懂」「看不懂」「有点抽象」
→ **他卡在概念层**，从最具体的场景和真实数据开始，**不要从架构开始**。

### 概念层的三条硬规矩

| ❌ 不要 | ✅ 应该 |
|---|---|
| 出现类型名 / 类名 / 文件名 | 用业务词汇 + 真实数据举例 |
| 「输入是 X 树，输出是 Y」这种抽象定义 | 「运营要发券给最近 7 天加购的 VIP」这种场景 |
| 直接上表结构 / 字段名 | 先给一行**真实数据**长什么样 |

> **类型名是架构词汇，不是概念。**
> 概念层出现 `XxxTree` / `XxxStruct` / `XxxBuilder` 这类东西就是劝退。

概念讲清楚了，读者自己会问「那为什么需要写个库」—— 那时才进组织层。

### 一个自检方法

写完开头，问自己：**一个完全不懂这个领域的人，读完前三节能说出「这东西是干嘛的」吗？**
说不出就是概念层没写够。

## 原则 ④ · 表格是排版，图是表达空间关系

**最容易犯的错：用表格的思维做图。**

| | 表达什么 | 用什么 |
|---|---|---|
| **表格 / 卡片** | 并列的、离散的信息 | `compare` `cards` `spec` |
| **图** | 空间关系：东西在哪、怎么流动、状态怎么变 | `lane-stack` `flow` `journey` `timeline` |

**判断方法**：

- 只能用「第一行是 X，第二行是 Y」描述 → **表格**
- 能用「A 指向 B」「A 变成 B」「A 和 B 汇合到 C」描述 → **图**

```callout
tone: amber
icon: ⚠
text: |
  ==`spec` 是拆解卡，看起来像图，本质还是两栏文字。==

  它适合**速查**（10 个文件各是什么、6 个依赖各是什么），
  **不适合讲机制**（这个东西怎么工作）。讲机制一定要画图。
```

### 讲机制的正确顺序

用户的原话：**「先介绍概念，让我对概念建立认识；再用图把概念连起来。」**

1. **拆成 3~6 个原子概念**，每个概念一两句话
2. **每个概念配一张图** —— 不要吝惜图，几张十几张都行
3. **概念讲完再上交互** —— 让用户亲手跑一遍

反例（错误做法）：直接上「输入 / 处理 / 输出」的表格，用户看完还是不知道它怎么工作。

## 工作流

### 第 0 步 · 判断：用户要的是「一个点」还是「一个面」

**不要看到【图解】就开始画图。先判断用户要的是哪一种。**

| 用户的说法 | 他要的是 | 你怎么做 |
|---|---|---|
| 「这个函数干什么」「A 和 B 有什么区别」「这段代码为什么这么写」 | **一个具体问题的答案** | 直接跳到第 2 步 |
| 「理解这个项目」「搞懂这一章」「从零学 X」「理解 X 的架构」 | **一条理解路径** | **必须先走第 1 步** |

**判断信号**：用户说的是「一个点」还是「一个面」。
说「面」的时候，**不要急着产出内容，先产出「脉络」**。

```callout
tone: red
icon: ⚠
text: |
  ==用户说「给我架构图」不等于「我只需要架构图」。==

  他可能是想「理解这个项目」，而架构图只是**他以为的入口**。
  直接给架构图，他会发现到处都缺前置知识，然后东补一块西补一块。
```

**不确定时，直接问**：一句「你是想快速要一张图，还是要从零搞懂它？」
能省掉后面好几轮来回。

### 第 1 步 · 梳理知识树（只在「一个面」时做）

#### 1.1 画一棵「要理解什么」的树

```
理解 X
├─ ① 业务背景 —— 为什么需要它、解决什么问题
├─ ② 概念    —— 有哪些词、每个词对应现实中的什么
├─ ③ 组织    —— 它由什么组成、怎么分类
├─ ④ 架构    —— 它怎么工作
├─ ⑤ 设计取舍 —— 为什么这么设计、不这样会怎样
└─ ⑥ 代码细节 —— 具体到文件 / 模块 / 函数
```

**每个节点标三样：**

| 标什么 | 为什么 | 例子 |
|---|---|---|
| **依赖** | 理解它之前必须先理解谁（决定顺序） | `依赖: ②概念` |
| **深度** | 概念 / 组织 / 架构 / 代码（决定详略） | `深度: 架构` |
| **产物** | 值得单独一篇，还是并入上一篇（决定切分） | `产物: 单独一篇` |

#### 1.2 这棵树是**递归**的

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==六层不是某个项目的专属结构，而是「理解任何东西」的通用结构。==
```

所以每一层里的**模块**，只要大到需要单独理解，就要**自己再走一遍这六层**：

```
理解一个 Web 框架
├─ ① 业务背景
├─ ② 概念
│   └─ 中间件 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它是什么、为什么需要
│       ├─ 组织：有哪几种（普通 / 错误处理 / 路由级）
│       ├─ 架构：next() 怎么把它们串起来
│       └─ 细节：代码在哪
├─ ③ 组织
│   └─ 核心包 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它负责什么
│       ├─ 组织：由哪些文件组成
│       ├─ 架构：怎么工作
│       └─ 细节：路由 ──────→ 再递归一次！
├─ ④ 架构
├─ ⑤ 设计取舍
└─ ⑥ 代码细节
```

```callout
tone: violet
icon: 💡
text: |
  **所以产物不是「一篇 HTML」，而是一棵嵌套的、互相链接的产物树。**

  每篇笔记对应树上的**一个节点**，节点之间有 `needs` 关系（前置依赖）。
  读者沿着树走，每篇开头都写清楚「读这篇之前需要知道什么」。
```

#### 1.3 判断一个节点要不要单独成篇

| 单独成篇 | 并入父节点 |
|---|---|
| 它有**自己的概念**要解释 | 它只是父节点的一个属性 |
| 它**大到需要分几节** | 一两段能说完 |
| **其他节点会引用它**（是别人的前置） | 只有父节点用到它 |

> 用最后一条最准：==一个节点被别的节点 `needs` 引用了，它就必须独立成篇==，
> 否则读者会被迫跳进另一篇的中间去找。

#### 1.4 梳理时不断拷问自己

**这一步是 AI 拷问自己，不是拷问用户。** 每个节点问四个问题：

1. 要理解这个节点，读者**必须先知道什么**？那个前置知识在哪一层？
2. 有没有**循环依赖**？（A 需要 B，B 又需要 A → 拆法有问题，要重新切）
3. 哪些是**可以推迟的细节**？（不放进第一轮）
4. 有没有**用户已经知道的**？（他的背景里已经有了，跳过）

#### 1.5 和用户确认

**把树给用户看**，问三个问题：

1. 这个脉络对吗？有没有多余的、有没有漏的？
2. 顺序对吗？
3. 先做哪一块？

```callout
tone: green
icon: ✅
text: |
  ==确认脉络花的 2 分钟，能省掉后面来回补窟窿的 2 小时。==

  用户看到树之后，往往能立刻指出「这块我已经懂了」「这块才是重点」——
  这些信息你猜不到。
```

#### 1.6 最后才决定产物切分

**一棵树 ≠ 一篇文档，也不等于 N 篇。**

按「**一块能独立读懂**」来切：

- 前置知识自足的一块 → 一篇
- 太短的合并
- 太长的再拆
- **每篇开头写清楚「读这篇之前需要知道什么」**

```callout
tone: amber
icon: ⚠
text: |
  **跳过这一步会怎样？**

  读者每看完一篇就发现「这里缺一块」，于是回头补；补的时候又发现另一块缺，再补。
  ==好几轮来回，全在补第一轮就该规划好的窟窿。==

  **根因**：把「用户要的产物」当成了「用户的目标」。
  **信号**：如果用户连续三轮都在问「那 X 是什么」，说明第一轮就该梳理脉络。
```

#### 1.7 落地：把树写成 `plans/<topic>.yaml`

```callout
tone: red
icon: ⚠
text: |
  ==确认的脉络不要只留在对话里。==

  对话会滚走，脉络会丢。写进文件，它才能驱动页面、才能在几周后还看得见。
```

```bash
# 树的唯一真相源
plans/<topic>.yaml
```

```yaml
topic: sql-builder-v2
title: 理解 sql_builder_v2
summary: 从零理解这个「把业务圈人需求翻译成 SQL」的库
source: sources/gitlab/sql_builder_v2 @ 2c500b2

nodes:
  - id: concepts                    # needs 里引用它
    title: 概念
    layer: 概念                     # 概念 / 组织 / 架构 / 模块
    needs: []                       # 前置节点 —— 理解它之前必须先理解谁
    artifact: sql-builder-v2-concepts   # 对应的笔记 slug（还没写也先填）
    status: planned                 # planned / drafted / done
    blurb: 圈人是什么、有哪些词、两套词汇
    children: []                    # 子节点，递归

  - id: core
    title: core 篇
    layer: 模块
    needs: [organization, architecture]
    artifact: sql-builder-v2-core
    status: planned
    blurb: 通用层：递归六层讲一遍
    children:
      - id: core-rule
        title: Rule[]
        layer: 概念
        needs: [core]
        artifact: sql-builder-v2-core-rule
        status: planned
        blurb: 四种形态 + buildWhere 怎么处理它
        children: []
```

**笔记那边只写两行**（`meta.json`）—— 层级和依赖关系**不在两处维护**：

```json
{ "tree": { "topic": "sql-builder-v2", "id": "core-rule" } }
```

**自动得到两样东西**：

| 得到什么 | 从哪来 |
|---|---|
| 首页的**树视图**（我在哪、下一步看什么、哪些还没写） | plan 的整棵树 |
| 每篇顶部的**「前置」区块** | plan 的 `needs` |

```
读这篇之前，你需要先知道
  ← 1. 概念    圈人是什么、有哪些词、两套词汇
  ← 2. 组织    仓库形状、三个包的分工、改哪里速查
```

**两个自动行为**（不用你操心）：

- 前置节点**还没写出来**时，显示成灰色的「待产出」，**不做成 404 死链接**
- `needs` 引用了不存在的 id → **`npm run check` 直接报错**，不会静默少一条

> **没挂树的笔记照常存在**，在首页显示在「未归类」区。
> 一棵树不是必须的 —— 只讲一个点的时候（「这个函数干什么」），不需要建树。

### 第 2 步 · 找到卡点

用户可能明说（「Flink CDC 和 CDC 有什么区别」），也可能没说（只粘了一篇文档）。

没说的时候，从这些信号里找：

- 原文里**篇幅最长但最抽象**的那一段
- 用户**加粗、划线、单独贴出来**的部分
- 出现了**三个以上并列概念**的地方
- **流程/链路**类描述（「先…然后…再…」）
- 任何**反直觉**的结论

一句话：**卡点通常是「需要读者在脑子里维护状态或追踪顺序」的地方。**

### 第 3 步 · 拆骨架

把内容切成 **3~7 个 h2 章节**，每章回答一个具体问题。

写之前先问自己：**如果只留 5 段，留哪 5 段？** 其余的删掉。

**如果走过了第 1 步，骨架直接来自知识树的节点**，不用重新想。

### 第 4 步 · 决定哪里必须画图

> 下面的表是**起点，不是清单**。找不到合适的就改积木、拼组合、或自己画，
> 别把内容削足适履地塞进表里。

| 原文里出现的是 | 用什么 | 为什么 |
|---|---|---|
| 「先 A，再 B，然后 C」的链路/分层 | `lane-stack` | 顺序用文字描述，读者要自己排队 |
| 有**分支或汇合**的流程 | `flow` | 一条直线讲不了「分两路再合起来」 |
| 「某东西从 X 变成了 Y」 | `journey` | 状态变化是文字最大的盲区 |
| 三个以上方案/概念的横向对比 | `compare` | 表格比排比句快十倍 |
| 一堆**没有先后关系**的并列概念 | `cards` | 用文字排会很平，卡片能一眼扫完 |
| 「2020 年…2022 年…」的演进 | `timeline` | 时间顺序需要视觉锚点 |
| 调用链、握手过程 | `seq` | 参与者 + 消息顺序 |
| 决策定位（重要度 × 紧急度） | `matrix` | 两维定位用表格看不出来 |
| 类层次、目录树、对象嵌套 | `tree` | 层级关系需要缩进感 |
| 反直觉的点、坑、一句话结论 | `callout` | 需要跳出正文节奏 |
| 正例/反例清单 | `checklist` | 勾叉比「应该/不应该」直观 |

### 第 5 步 · 决定哪里必须做成交互

1. `assets/app.js` 的 `WIDGETS` 里注册一个控件函数
2. 在 `note.md` 里用 `demo` 积木声明外壳和分栏
3. 两边靠 `log` 这个 key 对接

> 如果只是**顺序**，别做交互，画 `lane-stack` 就够。
> 交互有成本，只在「静态图讲不清」时才用。

### 第 8 步 · 交付前的四次复盘

改稿多轮之后内容一定会「长歪」。**每次都有具体动作，不是「再读一遍」。**

#### 复盘 ① · 术语审计

**用任何术语前，读者知道这是什么吗？**

把正文里的代码标识符列出来，看哪些没在概念章节出现过：

```bash
grep -oE '`[A-Za-z_][A-Za-z0-9_.]{2,}`' notes/<slug>/note.md | sort -u
```

**判断标准**：术语如果在「定义它」之前就被使用了，就是堵塞点。
处理：在开头加一个「先搞清几个词」的章节。

#### 复盘 ①b · 数字和事实回源码核实

**凡是写进文档的数字，都要回源码数一遍。**

真实事故：文档里写「这个接口有 14 个方法」，实际 **17 个**。
同一个错误在架构图、正文、速查表里各出现一次，**三轮都没人发现**。

容易写错的几类数字：**接口方法数、文件行数、枚举取值数、调用点数量**。

```bash
grep -cE '^\s+[a-zA-Z]+\(' <接口文件>     # 数方法
wc -l <文件>                              # 数行数
grep -c '^\s*[A-Z_]* =' <枚举文件>        # 数枚举值
```

> 数字错了比文字错了更危险 —— ==读者会信数字，而且不会去数==。

#### 复盘 ② · 每个概念必须配例子

```callout
tone: red
icon: ⚠
text: |
  ==只给定义不给例子，等于没定义。==

  「软删除是一种标记删除的机制」—— 读者完全不知道那是什么。
```

**每个概念至少给三样**（以「软删除」为例）：

| 给什么 | 例子 |
|---|---|
| 一句话定义 | 「删除时不真删，只打个标记」 |
| **长什么样**（最重要） | `{ id: 7, deleted_at: '2026-03-01 10:00:00' }` |
| 和相邻概念的区别 | 「普通删除是行没了；软删除是行还在，查询要额外加 `where deleted_at is null`」 |

用 `cards` 的 `code` 字段放例子最省事。

#### 复盘 ③ · 小白通读

**假装你只能看到这份 HTML，看不到任何代码。** 从头读，每段问：

- 这里出现的词，我前面见过定义吗？
- 「它」「这个」指代清楚吗？
- 这张图 / 表，不看正文能理解吗？
- 有没有结论来得太突然的地方？

**记下所有卡住的位置，回到原文补。**

#### 复盘 ④ · 结构复盘

**改过三轮以上，目录一定会乱。**

```bash
grep -nE '^#{2,4} ' notes/<slug>/note.md
```

检查四件事：

| 检查 | 典型症状 |
|---|---|
| **层级** | 某个 h3 其实是上一个 h3 的下级，却平级了 |
| **归属** | 内容跑到了别的章节（A 的讲解跑进了 B 里） |
| **顺序** | 先讲「怎么工作」后讲「由什么组成」 |
| **编号** | 改稿后编号重了或跳号 |

```callout
tone: violet
icon: 💡
text: |
  读者的路径应该是：==这是什么 → 由什么组成 → 怎么工作==。
  先看零件清单，再看零件怎么配合。
```

### 加新积木时的两条硬要求

### 图的视觉规范

图的「丑」通常不是配色问题，是**结构太单一**。四条规矩：

#### ① 节点用语义类型，不要纯文字盒子

用 `kind` 标出节点是什么（`backend` / `database` / `cloud` / `security` …）——
它会自动带图标和配色。==读者看图标就知道这是数据库还是服务，不用读文字。==

#### ② 用区域框表达归属

几个节点属于同一个 VPC / 同一个部署单元 / 同一层？用 `groups` 圈起来。

```callout
tone: violet
icon: 💡
text: |
  ==「结构单一」的最大来源就是没有区域框。==
  平铺的节点看不出「谁和谁是一伙的」，读者要自己在脑子里分组。
```

#### ③ 开背景网格

`grid: true`。给图「工程图纸」的质感，也让大片空白不那么飘。

#### ④ 边要有语义

- 同步实线、异步虚线 —— 别混用
- 关键路径用 `tone` 上色（比如绿色的 HTTPS、红色的鉴权）
- **每条边都该有标签**（协议、动作、方向），除非两端完全自明

```callout
tone: green
icon: ✅
text: |
  这套规范学自 `archify` skill（`~/.agents/skills/archify`）。
  它的图值得当参照 —— 需要更复杂的图时，可以去读它的 SKILL.md 和 examples。
```

### 复杂图：调用 archify skill

==不要把 archify 当兜底。== 容易把它读成「图太复杂、我们积木画不下时用它」—— 不是。
它是一套完整的图渲染系统，提供的是我们自己的积木**根本没有**的能力：
节点的**语义类型**（声明是 database / messagebus / cloud，自动带图标、配色和图例）、
**精确区域框**、**真边路由**，以及一个会量文字宽度、检测碰撞的校验器。

我们自己的积木确实是「半自动」的 —— 你给 `row`，它排位置，但不做标签避让和碰撞检测。
那是**两套工具的差别，不是能力强弱**。

#### 它能画 5 种图

由 spec 里的 `diagram_type` 决定（`tools/archify.mjs` 会自动读）：

| diagram_type | 画什么 | 结构数组 |
|---|---|---|
| `architecture` | 系统组成、部署拓扑、依赖关系 | components · boundaries · connections |
| `workflow` | 跨角色的流程 | lanes · phases · mainPath · nodes · edges |
| `sequence` | 调用链、握手、时序 | participants · messages · activations |
| `dataflow` | 数据流水线 | stages · nodes · flows |
| `lifecycle` | 状态机、生命周期 | lanes · states · transitions |

写法参考 `~/.agents/skills/archify/examples/*.<type>.json`。

#### 什么时候该调 archify

==判据是「这张图需要什么」，不是「我们的积木行不行」。==

| 用 archify | 用我们自己的积木 |
|---|---|
| 有**区域/边界**要表达归属（「这几个在同一个 VPC」） | 没有归属关系，就是一根轴或一列卡片 |
| 节点有**语义类型**（这是数据库、那是队列） | 节点就是纯文字盒子 |
| 需要**图例** | 不需要图例 |
| 形状是 DAG / 状态机 / 泳道 / 时序 / 阶段流水线 | 形状是时间轴 / 状态对照 / 两列匹配 / 行列表 |
| 要作为**独立图**交付、反复引用 | 图文混排成一节，要跟着页面换肤和重排 |

#### 它的硬边界（踩过）

- **边不能穿过无关节点。** archify 直接报
  `crosses component "xxx" (unrelated to this relationship)`，==它不会帮你绕过去==。
  遇到这种拓扑只能拆图、改布局、或手填 `route`/`via` 航点。
- **组件尺寸是每个显式声明的**（默认 120×60），不随 `layout.cellW` 变。
  标签长了要么裁文案，要么给它加 `size`。
- **边有几何下限**：微段短于 8px、两条边挤在同一条走廊里，都会判失败。
- 产出是**静态 SVG**，不跟着容器宽度重排。

#### 怎么调（已封装好）

```bash
# 1. 写 archify 的 JSON spec 放 archify/ 目录
#    参考 ~/.agents/skills/archify/examples/*.architecture.json
# 2. 生成并抠图
node tools/archify.mjs archify/<名字>.json <名字>
# 3. 在 note.md 里用 arch 积木
```

```text
svg: <名字>              # 必填，对应 assets/arch/<名字>.svg
caption: 这张图说明什么    # 可选，图注
```

**`tools/archify.mjs` 做了三件事**（这三件事不做会踩坑）：

1. 调 archify 的 `validate` + `deliver`（校验不过会直接报出诊断）
2. **只抠 SVG**（archify 的 HTML 有 600KB，但 SVG 本体只有 ~20KB）
3. **给它的 CSS 变量加 `--af-` 前缀** ——
   ==archify 在 `:root` 定义了 32 个变量，名字和我们完全一样（`--bg` / `--text` / `--panel`），
   直接嵌会把我们整页变成深色。==

两边都用 `data-theme` 属性，所以**深浅色天然同步**，不用额外处理。

#### archify 的校验值不值得用

**值得，而且这是它最值钱的部分。** 它会精确告诉你：

```text
Label "用户认证与鉴权流程" (~132px) is wider than component "gateway" (120px)
Label "请求" overlaps component "gateway"
  label rect: [286, 120, 48, 14]
  component "gateway" rect: [250, 80, 120, 60]
  Suggested fix: labelAt [310, 154] or labelDy +24
```

它**测量了文字宽度**、**检测了碰撞**、**给了具体坐标**。我们的积木完全不做这些。

## 版面与样式

### 改 theme.css，不要改单篇笔记

所有页面共用 `assets/theme.css` + `assets/blocks.css` + `assets/app.js`。
遇到这些症状，**改共享文件，一次全站生效**：

| 症状 | 改哪 |
|---|---|
| 屏幕利用率低 / 留白太多 | `theme.css` 的 `--shell` / `--prose` / `--gutter` |
| 某个积木在窄屏塌得不好 | `blocks.css` 里那个积木的 `@media` |
| 目录 / 交互别扭 | `app.js` + `lib/page.mjs` |
| 颜色不对 | `theme.css` 的 token |

**不要为了某一篇笔记在 `note.md` 里塞 `<style>`** —— 那是把全局问题当局部问题修，
下一篇还得再修一遍。

### 版面原则：文字窄，图宽

屏幕越宽，**不要把文字拉长**（长行伤可读性），而是把多出来的宽度给图。

`theme.css` 里三层控制：

- `--prose`（880px）管**文字元素**（`p` / `h2` / `h3` / `ul` / `.callout` / `.quiz`）
- `main` 的 `max-width`（1280px）管**整列上限**，防 4K 屏上积木被拉飞
- **积木不受 `--prose` 限制**，自动用满整列

判断一个新积木该不该限宽：**它主要是文字还是图形？** 文字限，图形不限。

### 行内强调：别让加粗承担所有重点

| 写法 | 语义 | 颜色 |
|---|---|---|
| `==文字==` | 关键结论 / 最该记住的一句 | 蓝 |
| `!!文字!!` | 坑 / 反直觉 / 注意 | 橙 |
| `++文字++` | 正确做法 / 推荐 | 绿 |
| `**文字**` | 句子内的重音（降级用） | 加粗不变色 |

**一屏之内不要超过 3 个 `==`** —— 到处都是重点等于没有重点。
写完后扫一眼：如果整页加粗密密麻麻，说明该用彩色标记做取舍了。

### 响应式：宽屏和竖屏都要能读

- **宽屏（≥1081px）**：目录是一列，点顶栏 ☰ 可收成 0
- **窄屏 / 竖屏（≤1080px）**：目录变成左侧抽屉，点遮罩或 Esc 关闭
- 状态记在 `<html data-toc>` 上，样式全在 `theme.css`，JS 只切属性

加新积木时**必须看一眼 400px 宽和深色模式** —— 这是最容易崩的两个地方。

### 改样式之后必须量图

```bash
npm run visual-check
```

用无头浏览器真的去量每个积木容器：子元素有没有溢出边界、有没有横向滚动。
**已经接进 pre-push 钩子，推送前自动跑。**

#### 四次踩坑记录

| 症状 | 根因 |
|---|---|
| 图整体错位，节点被推下去 414px | 用脚本「**区间替换**」改 CSS，把区间里的 `.flowd-svg { position: absolute }` 一起删了 |
| 区域框溢出到上面的段落里 | **设计缺陷**：框比节点大一圈，第一行就是被分组节点时框顶跑到容器外 |
| 加 padding 后所有图错位 | **坐标系不统一**：节点坐标相对 `.flowd-grid`，SVG/区域框相对 `.flowd` |
| 两个区域框重叠 | **每行独立居中** → 同组节点跨行会水平错位，两组包围盒几乎相接，框一往外扩就重叠 |
| `cards` 里的 `<pre>` 撑破容器 | **grid item 默认 `min-width: auto`**，不会缩到内容宽度以下 |

#### 第五次：archify 的共用 CSS 被削薄

```callout
tone: red
icon: ⚠
text: |
  ==`assets/archify-embed.css` 是全站共用的，但它是**每次跑 archify 时重新导出**的。==

  导出时会按「`assets/arch/` 下所有 SVG 用到的 class」筛规则。
  一旦筛漏，图里的元素就掉样式 —— 而且**构建、visual-check 全是绿的**。
```

**真实事故**：CSS 丢了 `.a-dashed` / `.a-security`（少 `fill: none`），
图里的虚线边被**填成黑色三角形**，压在节点上。

| 症状 | 根因 |
|---|---|
| 图里出现大块黑色三角/色块 | `archify-embed.css` 缺了某个 class 的规则，`fill` 回退成黑色 |

```callout
tone: green
icon: ✅
text: |
  **修法**：重跑任意一张图，它会按并集重新导出共用 CSS。

  ```bash
  node tools/archify.mjs archify/<名字>.json <名字>
  ```

  `npm run check` 有专门检查（对比 SVG 用到的 class 和 CSS 里定义的 class），
  缺了会直接报出来并告诉你重跑哪条命令。
```

#### 三条硬规矩

1. **改一条 CSS 规则就替换那一条，别用大区间。** 非要大改，改完 grep 一遍原来的选择器。
2. **绝对定位的装饰元素要考虑「会不会超出容器」。** 加了就配 padding。
3. **坐标计算必须统一参照系。** 容器一有 padding，相对不同父元素量的坐标就会错开。
4. **放进 grid / flex 的元素要设 `min-width: 0`**，否则内容会把容器撑破。

## 依赖策略：默认零依赖

页面要能**单文件发人**，所以每加一个库都在增加分发成本。

| 需求 | 用什么 | 要不要库 |
|---|---|---|
| 高亮、淡入、位移 | CSS transition / animation | 不要 |
| 元素沿路径移动 | CSS `offset-path` | 不要 |
| 流程连线 | 测量 + 内联 SVG（见 `flow` 积木） | 不要 |
| 数字滚动、按步播放 | Web Animations API / setTimeout | 不要 |
| 复杂时间轴编排、物理弹簧 | —— | 到这一步再说 |

**先零依赖做到极限。** 真不够时再讨论装什么，并且要把决定写回这一节。

icon: ⚠
text: |
  **也不要直接从架构开始写。** 源码通读同样要先过原则 ③ 的三层：
  先讲清楚**这个领域的概念**（有哪些词、对应什么现实事物），
  再讲**怎么组织**，最后才是**代码怎么实现**。

  跳过概念层，得到的就是一份只有作者看得懂的架构图。
```

按这个顺序读：

1. **摸依赖图** —— 一条命令看出谁依赖谁：
   ```bash
   find . -name '*.ts' -not -path '*/node_modules/*' | while read f; do
     echo "$f → $(grep -oE "from '[^']+'" "$f" | sed "s/from '//;s/'//" \
       | grep -E '^(\.|src|@)' | tr '\n' ' ')"
   done
   ```
   横切的（被所有层依赖）和纵深的（依赖所有层）一眼可见。
2. **按行数排序** —— 最大的文件就是复杂度所在，也是卡点所在。
3. **读入口** —— `index.ts` / `context.ts` / 工厂，它们定义了架构骨架。
4. **找反直觉的实现** —— 这是最值钱的卡点。信号：
   - 注释里出现「为什么不用 X」的解释
   - 有一行代码做了意料之外的事
   - 到处都在 `?? new XxxDefault()` 兜底（往往是个真实的坑）
   - 常量里出现取模 / 哈希分片
   - 有一个 `switch` 的 `default` 直接 `throw`
5. **确认，不要猜** —— 断言「这里会 throw」之前，先把那几行读出来。

**结构用现有积木就能画好**（`lane-stack` + 分组正好表达包的边界）。
真正需要新表达的是**机制**，不是结构 —— 力气花在那里。

## 变体：拆解一个东西

用户说「拆解一下 X」时，用这六个问题逐条回答，写进 `spec` 积木：

| 维度 | 问什么 |
|---|---|
| **输入** | 喂给它什么？什么类型、什么形态？ |
| **处理** | 中间做了什么？有哪几步？ |
| **输出** | 吐出什么？给谁用？ |
| **怎么调用** | 别人实际怎么用它？贴一段真实调用代码 |
| **为什么这么设计** | 作者为什么这样选？**注释里常藏着答案** |
| **业务价值** | 它到底解决了什么问题？没有它会怎样？ |

```callout
tone: amber
icon: ⚠
text: |
  ==但不是所有东西都值得拆。==
```

**先判断该不该拆**：在代码里搜一下它被调用几处。

- **调用很多（几十处）或位于主干** → 值得拆，六个维度都写
- **只有 1~3 处调用** → 用 `compare` 一行说清就够，硬拆六个维度是凑字数
- **`src/` 里根本搜不到** → 它是被动依赖（编译期 / 间接），没有输入输出可言，
  归到一张表里说明「为什么在 deps 里」即可

> 判断依据不是「用户让我拆」，是**这个东西本身有没有那么多可讲的**。
> 拆一个只有两处调用的工具库，写出来的六段全是废话。

## 多会话协作

**这个仓库会被多个 agent 会话同时编辑** —— 用户会同时开好几个窗口，每个窗口一个 agent。

这不是假设，是常态。所以有一套规则必须共同遵守。

### 先说清矛盾在哪

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==构建产物是**全量**的。==

  `index.html`、`dist/*.html` 里包含**所有人的内容**。
  所以你没法「只提交自己的部分」—— 那样仓库就停在「产物新、源旧」的不一致状态，
  pre-push 钩子会直接拦下。
```

**推论**：提交 = **提交一个自洽快照** = 当前所有源 + 由它们构建出的所有产物。

这意味着**你必然会把别人的改动一起提交**。这不是错误，是设计。关键是把这件事做**安全**。

### 三类文件

| 类别 | 例子 | 谁负责 |
|---|---|---|
| **共享产物** | `index.html`、`dist/*.html`、`notes/<任意 slug>/index.html` | **每次提交都要带上全部** |
| **共享源** | `assets/theme.css` `blocks.css` `app.js`、`tools/*.mjs`、`package.json`、`.agents/skills/**` | 谁改谁提交，但**要小心** |
| **私有源** | `notes/<你的 slug>/`、`archify/<你的名字>.json`、`assets/arch/<你的名字>.svg` | 只有你改 |

### 开工前（30 秒）

```bash
npm run status
```

它会把你工作区的改动**分类列出来**（临时文件 / 共享产物 / 共享源 / 笔记源），
并标出每项的修改时间。

- 干净 → 直接干活
- **有别人的改动** → 记住它们，提交时要一起带上（见下）
- 有别人的改动**且明显是半成品**（写了一半、构建不过）→ **先问用户**

### 干活时

1. **只改自己的文件。** 不要顺手改别人的 `note.md`，哪怕发现它写错了 —— 报告，不擅自改。
2. **改共享源要小步。** `blocks.css` / `app.js` 有别人在用：
   - ==改一条 CSS 规则就替换那一条，别用大区间替换==
   - 加控件 / 积木用**新名字**，别改别人的
   - 改完尽快提交，别攒着
3. **临时文件进 `.gitignore`。** 预览副本、截图、草稿别留在 `notes/` 里。
   约定：以 `_` 开头的文件是临时的（`_p.html`、`_wip.html`）。

### 提交时

```bash
npm run status              # ① 分类看清
npm run check               # ② 校验（含 skill 一致性）
npm run build:standalone    # ③ 重建全部产物
npm run visual-check        # ④ 量图
git add -A                  # ⑤ 此时已确认全部安全
git commit                  # ⑥ 信息里注明哪些是别人的
```

**为什么这里可以用 `git add -A`**：因为第 ① 步已经确认了每一项都该提交。
之前踩的坑不是「用了 `-A`」，是**没看清就 `-A`**。

```callout
tone: amber
icon: ⚠
text: |
  **但有一条例外：如果别人的源是半成品，不要提交。**

  半成品 = 明显写了一半、或构建不过。

  这时**停下来问用户**，别替别人改，也别把它带上。
  ==替别人提交一个坏文件，比漏提交更糟 —— 它会被当成「已经完成」。==
```

### 别人的改动怎么处理

| 情况 | 怎么办 |
|---|---|
| 别人的源完整、构建能过 | **一起提交**，提交信息里注明来源 |
| 别人的源是半成品 | **停下来问用户** |
| 只有别人的产物、没有源 | 说明源被漏了 → 找到源一起提交，或者问用户 |
| 别人改了共享源（`blocks.css`） | 一起提交，**在信息里说明你确认过它的改动** |

**提交信息里的注明格式**（已有先例）：

```text
来自并行会话（非本次工作，为保持产物与源一致一并提交）：
- notes/flink-source-transform-sink/（Flink 算子笔记）
- tools/visual-check.mjs（加 .keyby-viz 容器 + JSON 解析错误上下文）
```

### 构建和提交之间的竞态（真实踩过）

```callout
tone: red
icon: ⚠
text: |
  **`npm run build` 和 `git add` 之间，别人的文件可能又变了。**

  于是你提交的是「**源是新的、产物是旧的**」——
  pre-push 钩子一重建就发现对不上，直接拦下。
```

**时间线**（真实发生）：

```text
① 我 npm run build:standalone   → 从 note.md 的版本 A 构建出产物 A
② 我 git add -A && commit       → 期间别人保存了版本 B
                                  结果提交的是：源 B + 产物 A   ← 不一致
③ pre-push 重建                 → 从 B 构建出产物 B ≠ 产物 A → 拦下
```

**修法**：源已经提交了，只是产物过期 —— 重建后 amend：

```bash
npm run build:standalone
git add -A
git commit --amend --no-edit
git push
```

```callout
tone: amber
icon: ⚠
text: |
  ==如果这样还反复被拦，说明别人正在持续编辑。==

  那就别再重试了 —— **停下来问用户**，等对方告一段落。
  反复 amend 只会把你的提交变成「别人半成品的快照」。
```

### 别人的文件坏了，阻塞了共享构建

```callout
tone: red
icon: ⚠
text: |
  ==`npm run check` 是全仓库的。别人一篇笔记写坏，你这边也过不了。==
```

**先分清是哪一类**：

| | 例子 | 怎么办 |
|---|---|---|
| **机械性问题** | YAML 裸标量以反引号开头 · 积木名拼错 · 引号没闭合 | ✅ **可以修**。工具自己会给出修法，改的是语法不是意思 |
| **语义性问题** | 内容写错了 · 数字不对 · 结构乱 | ❌ **不碰**。报告用户 |

```callout
tone: green
icon: ✅
text: |
  **判断标准：这个修改会不会改变别人想表达的意思？**

  加一对引号不会。改一个数字会。

  机械性修复要在提交信息里**单独列出来并注明**，别混在自己的改动里。
```

**真实案例**：并行会话的 Flink 笔记里有两行 `- q: \`xxx\` 是什么？` ——
YAML 里裸标量不能以反引号开头，整个仓库的 `check` 都挂了。
预检工具直接给出了修法（外面包一层双引号），修它零风险。

### 冲突处理

| 冲突的文件 | 怎么办 |
|---|---|
| `index.html`、`dist/*`、`notes/*/index.html` | **重新构建**，不要手动 merge。产物是生成的，冲突无意义 |
| `package.json` | 通常两边都加了 script → **两边都保留** |
| `blocks.css` / `app.js` | 真冲突，逐条看，**两边的改动都要留** |
| `note.md` | 不该发生。如果发生，说明两个会话改了同一篇 → **问用户** |

### 推送被拦下来怎么办

pre-push 会重建 + 量图。**它拦下来通常不是你的问题。**

```text
✗ 构建产物有变化（note.md 改了但没提交构建结果）
```
→ 有人（可能是你）改了源没重建。`git add` 上产物，`--amend` 重新提交。

```text
✗ 有图被画坏了
```
→ 看是哪个积木、哪一篇。**如果是别人笔记里的图坏了，报告用户，别去改别人的内容。**

### 三条硬规矩

1. **产物和源必须一起提交。** 只交产物 → 来源不明；只交源 → 构建过期。
2. **不替别人改东西。** 发现问题 → 报告，不擅自改。
3. **提交前跑 `npm run status`。** 别凭记忆判断哪些是自己的。

## 硬约束

| ❌ 不要 | ✅ 应该 |
|---|---|
| 为了「符合积木规范」而扭曲表达 | **怎么讲清楚怎么来**。积木是省力工具，不是验收标准 |
| 硬把内容塞进最接近的积木 | 组合 / 加字段 / 新建 / `raw` 直接写 —— 四条路任选 |
| 编辑 `notes/*/index.html` | 那是产物，会被覆盖。只改 `note.md` |
| 在单篇 `note.md` 里塞 `<style>` | 改 `theme.css` / `blocks.css` —— 一次全站生效 |
| 在正文写 `# 一级标题` | 标题只写在 `meta.json` 的 `title` |
| `meta.json` 里写 `status: "verified"` | agent 生成的内容一律 `draft`。`verified` 是**人工核对过**的信号 |
| 原样搬用户的原文 | 先砍到骨架，再决定哪几段变成图 |
| 写「这一步我之前没讲」「这张图我第一版画错了」 | **读者不知道你迭代过几轮**，这些话只对你有意义。直接陈述事实 |
| 图上的编号和正文对不上 | 正文用编号指代时，**图上必须真有那个编号**（archify 的边标签、积木的 badge 都要对得上） |
| YAML 裸标量里出现 `: `（冒号+空格） | 加引号，或用 `|-` 块标量 |
| YAML 裸标量以反引号 `` ` `` 开头 | 加引号 |
| YAML 裸标量以 `*` `&` `!` `%` `@` 开头 | 加引号（会被当成别名/锚点/标签） |
| 值里有 `[` 或 `{` 却没加引号 | 加引号（`Rule[]` 里的方括号会被当数组起始） |
| 担心 `**「术语」**` 这类中文加粗失效 | 已经修好了，不用管；但 `**` 跨行仍然不生效 |
| 每段都想画图 | 图是稀缺资源。**只有卡点值得画图** |

**每篇结尾必须有 `quiz`。** 这不是可选项 —— 知识库头号死因是「收藏代替理解」，
攒到 30 篇时自己都不记得里面有什么。2~3 题，逼自己合上答案复述一遍。

**`meta.json` 的 `status` / `sources` 会渲染成页内的溯源头。**
漂亮的 HTML 会自带「这应该是对的」的暗示，而它可能只是某次对话的产物。
半年后你必须能一眼看出哪个结论没人核对过。

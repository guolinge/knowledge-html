# 把知识变成能看懂的 HTML

## 触发与项目位置

用户以 **【图解】** 开头（后面可接内容、飞书链接、或「看上面」）。

项目固定在：

```
~/works/codes/knowledge-html
```

## 第一原则

**你的任务不是「把内容搬进 HTML」，是「把用户卡住的那个环节讲透」。**

用户粘过来的原文通常有 60% 是铺垫、重复、客套。原样搬进去只会得到一个更长的、
仍然看不懂的页面。用户要的是**图和交互** —— 这是 HTML 相对纯文本唯一不可替代的价值。

所以：**先找卡点，再决定画什么图，最后才写文字。**

---

## 工作流

### 第 1 步 · 找到卡点

用户可能明说（「Flink CDC 和 CDC 有什么区别」），也可能没说（只粘了一篇文档）。

没说的时候，从这些信号里找：

- 原文里**篇幅最长但最抽象**的那一段
- 用户**加粗、划线、单独贴出来**的部分
- 出现了**三个以上并列概念**的地方
- **流程/链路**类描述（「先…然后…再…」）
- 任何**反直觉**的结论

一句话：**卡点通常是「需要读者在脑子里维护状态或追踪顺序」的地方。**

### 第 2 步 · 拆骨架

把内容切成 **3~7 个 h2 章节**，每章回答一个具体问题。

```
## 01 · 数据库：服务「在线业务」
## 02 · 数据仓库：服务「数据分析和报表」
## 03 · 最核心的区别
...
```

写之前先问自己：**如果只留 5 段，留哪 5 段？** 其余的删掉。

### 第 3 步 · 决定哪里必须画图

| 原文里出现的是 | 用什么 | 为什么 |
|---|---|---|
| 「先 A，再 B，然后 C」的链路/分层 | `lane-stack` | 顺序用文字描述，读者要自己排队 |
| 「某东西从 X 变成了 Y」 | `journey` | 状态变化是文字最大的盲区 |
| 三个以上方案/概念的横向对比 | `compare` | 表格比排比句快十倍 |
| 一堆**没有先后关系**的并列概念 | `cards` | 用文字排会很平，卡片能一眼扫完 |
| 「2020 年…2022 年…」的演进 | `timeline` | 时间顺序需要视觉锚点 |
| 反直觉的点、坑、一句话结论 | `callout` | 需要跳出正文节奏 |
| 正例/反例清单 | `checklist` | 勾叉比「应该/不应该」直观 |

### 第 4 步 · 决定哪里必须做成交互

判据：**用一句话说不清「A 和 B 差在哪」，但让用户亲手跑一遍就秒懂 → 做 `demo`。**

典型：轮询 vs CDC、乐观锁 vs 悲观锁、B+ 树插入 vs 删除、
不同隔离级别的并发异常。

写 demo 需要三步（详见 `references/blocks.md`）：
1. `assets/app.js` 的 `WIDGETS` 里注册一个控件函数
2. 在 `note.md` 里用 `demo` 积木声明外壳和分栏
3. 两边靠 `log` 这个 key 对接

> 如果只是**顺序**，别做交互，画 `lane-stack` 就够。
> 交互有成本，只在「静态图讲不清」时才用。

### 第 5 步 · 写 note.md

```bash
cd ~/works/codes/knowledge-html
npm run new -- <slug>          # slug 用小写英文连字符，如 mysql-index-internals
```

然后编辑 `notes/<slug>/note.md`，填 `notes/<slug>/meta.json`。

**积木的完整语法见 [`references/blocks.md`](references/blocks.md)，
可运行示例见 `notes/blocks-cheatsheet/note.md`（写之前先读一遍）。**

### 第 6 步 · 校验、构建、打开

```bash
npm run check              # 先校验。会指出第几行哪个积木有问题
npm run view -- <slug>     # 构建 + 在浏览器打开
```

`npm run check` 必须过。它报的每一类问题都对应一个真实踩过的坑：

- **积木名拼错** → 会静默退化成普通代码块，页面看着正常但图没了
- **YAML 语法错** → 定位到文件和行号，并回显原始内容
- **缺 `quiz`** → 违反本仓库约定（见下）

---

## 硬约束

| ❌ 不要 | ✅ 应该 |
|---|---|
| 手写 HTML 拼排版 | 用积木；积木不够就**加一个**（见 `references/extend.md`） |
| 编辑 `notes/*/index.html` | 那是产物，会被覆盖。只改 `note.md` |
| 在正文写 `# 一级标题` | 标题只写在 `meta.json` 的 `title` |
| `meta.json` 里写 `status: "verified"` | agent 生成的内容一律 `draft`。`verified` 是**人工核对过**的信号 |
| 原样搬用户的原文 | 先砍到骨架，再决定哪几段变成图 |
| YAML 裸标量里出现 `: `（冒号+空格） | 加引号，或用 `|-` 块标量 |
| 每段都想画图 | 图是稀缺资源。**只有卡点值得画图** |

**每篇结尾必须有 `quiz`。** 这不是可选项 —— 知识库头号死因是「收藏代替理解」，
攒到 30 篇时自己都不记得里面有什么。2~3 题，逼自己合上答案复述一遍。

**`meta.json` 的 `status` / `sources` 会渲染成页内的溯源头。**
漂亮的 HTML 会自带「这应该是对的」的暗示，而它可能只是某次对话的产物。
半年后你必须能一眼看出哪个结论没人核对过。

## 写完检查

- [ ] `npm run check` 零问题
- [ ] 用户说的那个卡点，**有没有变成一张图或一个交互**？（这是唯一的成功判据）
- [ ] 原文里的铺垫、重复、客套删掉了没有
- [ ] 结尾有 `quiz`
- [ ] `meta.json` 的 `status` 是 `draft`，`sources` 填了原文出处

# 把知识变成能看懂的 HTML

这份文档说明图解的讲解原则、制作流程和协作约定。
积木语法见 [`references/blocks.md`](references/blocks.md)，扩展方法见 [`references/extend.md`](references/extend.md)。

<span id="触发与项目位置"></span>

## 用途与开始方式

输入可以是粘贴的文字、文档链接、代码路径，或对话中已经提供的材料。
用户以【图解】开头或明确提出图解需求时，先按当前请求确定工作范围：
讨论材料、审阅内容、修改已有页面，还是制作新页面。前缀本身不表示必须新建 HTML。

主仓库在 `~/works/codes/knowledge-html`。实际编辑和构建在当前会话的工作区进行，
并行编辑优先使用独立 worktree。准备修改文件时，先读会话板并运行 `npm run status`，
确认已有改动和本次负责的范围。具体协议见[多会话协作](#多会话协作)。

构建可能更新多个页面。提交前检查变更范围，保持源文件与产物一致，
不把其他会话的未完成内容带进提交。

<span id="全景"></span>

## 流程概览

制作或修改页面时，写作与检查可以往返进行；只讨论或审阅时，不进入制作流程。

```text
第 0 步：确认范围和交付方式
  ├─ 讨论／审阅 → 阅读并给出意见
  └─ 制作／修改
       ↓
第 1 步：需要时梳理主题和依赖
       ↓
第 2～5 步：确定问题、结构、图和交互
       ↓
第 6 步：写作 ⇄ 第 7 步：构建检查
       ↓
第 8 步：整体验收
       ↓
交付页面；按约定提交、发布
       ↓
第 9 步：记录可复用的改进
```

详细动作见[工作流](#工作流)。

<span id="原则-①-图是这个产品的本体不是配图"></span>

## 原则 ① · 让图承担主要讲解

读者往往已经有文字材料。图解要帮助他看见对象的位置、归属、连接和变化，
减少在脑子里拼结构、追踪过程的负担。

这份文档里，「图解」指图、表格、卡片和交互共同构成的讲解方式；
「关系图」指用位置、框、连线等表达关系的图。下面单说「图」时，指关系图。
表格和卡片可以参与图解，但不能代替没有画出的连接和过程。

### 哪些内容用图

涉及多个对象的位置、归属、分支或状态变化时，用图呈现。
例如进程与文件描述符的关系、请求走过的几个服务、任务从等待到运行的变化。
正文可以解释图中的条件和细节，关键关系应当在图上看得到。

原文已经用一段文字解释过，并不意味着这里可以省略图。
如果读者仍然需要想象对象怎么摆、事情怎么发生，就把这部分画出来。

设计理由、经验判断和取舍通常用文字说明；其中涉及的结构或流程可以另画图。
简单的操作步骤、过渡句和一句话结论也可以留文字。
比如「分配 pid、分配资源、初始化 PCB」只是操作清单时，直接列出即可；
如果要说明失败分支或资源归属，再补相应的图。

### 怎么安排详略

读者卡住的地方先画、画细，需要时配交互。
其余与理解有关的结构和过程也要呈现，可以用较轻的图；比较和并列信息则用表格或卡片。
具体形式按原则 ⑥ 选择，不按「是不是重点」决定画不画。

<span id="原则-②-整体图"></span>

## 原则 ② · 用整体图连接相关概念

有的问题，把零件一个一个讲是讲不清楚的。

比如「容器到底是什么」。它不是内核里的一个独立对象。
可以先看一个进程，再看它使用的 namespace、它所属的 cgroup，以及它看到的 rootfs。
单独解释其中一项，读者还不知道这些东西怎么配合。
把它们摊在同一张图上，才能看出它们与进程的关系。

这类图叫整体图，用来说明一组对象彼此有什么关系、各属于谁。

### 什么时候用整体图

下面几类问题适合用整体图：

- 一个概念由多种对象共同构成，例如容器。
- 名词在正文中分别讲过，但读者还拼不出归属和联系，例如进程、fd 表与 socket。
- 读者熟悉其中一个对象，希望理解它与其他对象的联系和区别。

如果只想讲一条链怎么走，优先用流程图、时序图或状态快照。
不必把整套系统的零件都放进来。

### 分清关系再连线

| 关系 | 要说明什么 | 怎么画 |
|---|---|---|
| 分类 | 这东西属于哪一类 | 用分区或背景带 |
| 包含 | 这东西在谁里面 | 用框套框 |
| 数量与共享 | 一个对应几个，哪些对象被共同使用 | 在关系线上标基数，共享对象只画一份 |
| 流动 | 谁把什么交给了谁 | 用带动作说明的箭头 |

「用户态 / 内核态」「硬件 / 软件」这些分类可以帮助读者定位对象。
如果还要讲它们怎么配合，就需要同时画出连接，不能只靠分层。

```callout
tone: amber
icon: ⚠
text: |
  容器那篇曾把几种对象画成 `进程 → namespace → cgroup → rootfs`，
  看起来像前一项导致后一项。

  这里应当分别画出进程使用哪个 namespace、属于哪个 cgroup、看到哪个 rootfs，
  而不是把它们串成一条流程。
```

把每条边读一遍，问「这条边代表什么关系」。
能说出指向、交给、属于或包含，就保留相应画法；
如果只是为了让节点排成一列，删掉这条边，改用分组、表格或卡片。

### 每张图回答一个主要问题

一张整体图可以有多种关系，但要分清主次。
讲「谁属于谁」时突出包含框，讲「数据怎么走」时突出路径，其余信息作为背景。

抽象层次也要保持一致。例如系统上下文图主要展示人和系统的关系，
不把 Python 类的实现细节混进去。

### 什么时候拆图

可以把 12~15 个元素作为检查密度的经验提醒，不把它当成固定上限。
还要看标签长度、线的密度，以及读者能否顺着图找到需要的关系。

如果图里同时在回答两个不同的问题，或为了找一条路径要反复绕过无关对象，就考虑拆图。
「谁创建谁」和「谁唤醒谁」可以分别讲；如果两者共同解释同一个问题，也可以在一张图里区分清楚。

图太密时先改结构和布局，不靠把线压在框下、调低透明度来隐藏问题。
聚焦交互可以帮助阅读，但未聚焦的整体图也应能读懂。交付前按[第 8 步](#第-8-步-交付前检查)核对。

### 从读者熟悉的对象进入

用户曾这样描述自己的需要：

> 假如我比较熟悉进程，那么画一个整体图，我很快就能把进程和 socket 的联系和区别
> 记到脑海里。

整体图里可以提供「我熟悉 ___」的入口。
点选后突出这个对象和它的直接邻居，其他对象淡出；再点一个邻居，就以它为新的中心。
这样读者可以从已知对象逐步找到相关对象，不必一开始就认识全部零件。

机制图也要考虑读者已经认识什么，具体见[机制图的具体画法](#机制图的具体画法)。
整体图的工具、字段和布局方法见[结构化图](#结构化图调用-archify-skill)。

<span id="原则-③-关键图要有信息量把名词摆一遍不算图"></span>

## 原则 ③ · 关键图要有信息量

一个框，标题「共享资产」，副标题「代码段 · 堆 · 文件描述符表 · 线程共用」。
这样的图还是一份带框的目录：读者知道有这些名词，却看不到它们在哪、怎么组织、什么时候变。

### 从名词到结构和机制

```compare
first: 层次
head: [图里有什么, 以进程和线程为例]
rows:
  - 名词: ["列出有哪些对象", "代码段、堆、栈、文件描述符表"]
  - 结构: ["画出位置、归属和共享关系", "各线程的栈在进程地址空间里；文件描述符表属于内核对象"]
  - 机制: ["画出对象怎么配合、状态怎么变化", "线程各用自己的栈，访问共享的堆；标出一次调用或一次修改发生在哪里"]
```

目录图可以用来导航。承担关键讲解的图则要有与问题相关的结构；
如果这张图用来讲机制，还要让读者看见过程和变化。

### 看图检查

盖住正文，只看这张图：

- 能看出对象的位置、归属或连接吗？
- 能找到这张图要回答的关键问题吗？讲过程时，能顺着图走完关键步骤吗？
- 如果容量、数量或方向影响结果，图上是否标出了这些信息？

关系本身不依赖尺寸的图，不必为了显得丰富而补数字。
需要补的是理解这个问题所需的信息，而不是更多标签。

### 补充信息时核对边界

画「进程 vs 线程」时，查证带来了这样的变化：

| 只照原文画 | 核实后怎么画 |
|---|---|
| 一个框里列共享资产 | 展开地址空间，标出代码段、数据段、堆和各线程的栈 |
| 把文件描述符表和堆、栈放在同一个内存布局里 | 把 fd 表放到内核一侧，通过关系线连接；它由 `files_struct` / `fdtable` 管理 |
| 没有区分栈的管理方式 | 分别说明系统线程和语言运行时怎样分配、使用栈，再标对应平台和配置下的容量 |

例如，Go 源码中的 `stackMin = 2048` 是最小栈常量，不能用它概括所有 goroutine 的初始栈大小；
Linux NPTL 下的 pthread 默认栈大小也受程序启动时的 `RLIMIT_STACK` 等条件影响，不能直接写成固定 8MB。
出处见 [Go 栈实现](https://go.dev/src/runtime/stack.go)、[pthread_create 手册](https://man7.org/linux/man-pages/man3/pthread_create.3.html)
和 [Linux 文件管理文档](https://docs.kernel.org/filesystems/files.html)。

不确定的信息要核实后再画，具体方法见[资料查证](#资料查证)。
队列、通道、状态和执行资源怎样呈现，见[机制图的具体画法](#机制图的具体画法)。

<span id="原则-④-讲透卡点不是搬运内容"></span>

## 原则 ④ · 围绕读者的问题组织内容

先弄清读者想解决什么问题，再安排内容。
原文里与这个问题无关的铺垫和重复可以删掉，理解所需的前提则要保留。
需要读者想象位置、追踪过程或比较状态的地方，用图或交互来讲；设计理由和取舍可以用文字说明。

一节回答一个具体问题，按理解所需的顺序组织，不必沿用原文的分段。
写之前列出读者读完后应当能回答的问题，再检查每一节是否帮助他回答其中一个。

取舍内容时检查：

- 删掉这一段，读者还能理解接下来的内容吗？不能，就保留或补成前置说明。
- 这一段是否在重复已经讲清楚的信息？是，就合并或删掉。
- 读者卡住的那个环节，有没有得到足够的解释？检查他能否讲清关键关系或步骤，以及成立的条件。

<span id="原则-⑤-先对齐理解层次"></span>

## 原则 ⑤ · 先判断读者需要哪一层解释

同一份材料，不同的人需要的解释不一样。
有的人不认识概念，有的人认识每个概念，却不知道它们怎么组织，还有的人想理解实现。

| 层次 | 读者需要知道什么 | 从哪里开始 |
|---|---|---|
| 概念 | 每个词是什么意思，对应什么现实对象 | 具体场景和数据例子 |
| 组织 | 概念由什么组成，彼此如何联系 | 整体关系和分工 |
| 架构 / 实现 | 系统如何工作，代码怎样实现 | 关键路径，再到模块和函数 |

「没接触过」通常提示需要概念介绍。
但「看不懂」「有点抽象」还不足以判断层次，读者也可能只是接不上某个关系或步骤。
先结合提问和已有背景判断；信息不足时，确认他已经熟悉哪些内容、具体从哪里开始不明白。

### 概念层从具体例子开始

| 写法 | 更适合的起点 |
|---|---|
| 先列 `XxxTree`、`XxxStruct`、文件名 | 先说业务中有什么对象、各做什么，代码标识符等解释实现时再引入 |
| 「输入是 X 树，输出是 Y」 | 「运营要发券给最近 7 天加购的 VIP」这样的场景 |
| 直接列字段和表结构 | 先展示一行数据，说明它记录了什么，再解释字段 |

已有概念介绍可以作为后文的前提，不必每一节重新讲一遍。
读者已经熟悉的部分可以略过，也不必等他问到代码才安排实现层内容。

### 按目标读者检查开头

从开头读一遍，检查目标读者是否能说明这东西做什么，以及例子里的对象是什么意思。
如果文章面向初学者，开头需要把这些概念解释清楚；面向熟悉概念的读者时，可以直接进入他不理解的关系或实现。

<span id="原则-⑥-表格是排版图是表达空间关系"></span>

## 原则 ⑥ · 按要表达的关系选择表格或图

表格可以表达比较、映射和对应关系，卡片适合分组介绍对象，关系图适合连接对象和呈现变化。
先看要讲什么，再选形式。

| 要表达的内容 | 适合的形式 |
|---|---|
| 几个方案按相同维度比较，输入类型与处理规则对应 | 表格 |
| 几个并列概念，各有解释和例子 | 卡片 |
| 对象的位置、包含、连接、分支和流动 | 关系图 |
| 状态随时间或操作变化 | 时间线、状态快照；静态表达不够时再做交互 |

例如，`spec` 适合按固定维度介绍一个对象，也适合速查文件和参数。
如果读者需要理解多个对象怎么配合，一张字段表通常不够，还要把相关对象连起来。

### 先认识对象，再看它们怎么配合

用户的原话：

> 先介绍概念，让我对概念建立认识；再用图把概念连起来。

先用简短解释和例子介绍必要概念，再在图中连接它们。
概念本身涉及结构时配小图，能用一句话或一行数据说明的就不必单独画。
需要比较操作过程或观察不同输入的结果时，再做交互。

用哪个积木，查[积木清单](#积木清单18-个从手上的文字反查)。
机制图需要画出的路径、状态和层次，见[具体画法](#机制图的具体画法)。

<span id="原则-⑦-积木是词汇不是语法"></span>

## 原则 ⑦ · 按表达需要使用和扩展积木

积木提供常用布局和样式，让你不用每次从零写 CSS。
先确定内容需要怎样呈现，再选择能表达它的积木。
如果为了套进某个积木而删掉关键关系或改变顺序，就需要调整呈现方式。

| 做法 | 什么时候用 |
|---|---|
| 组合 | 现有积木拼起来就能表达 |
| 加字段 | 现有积木方向合适，但缺一个能力，例如给 `demo` 加 `html` 字段 |
| 新建积木 | 同一类表达会反复使用，且现有积木难以承担 |
| 用 `raw` 写 HTML/CSS | 一次性的自定义布局 |

通常先试组合和加字段。反复需要的能力可以做成新积木，一次性布局则可以直接用 `raw`。
扩展方法见 [`references/extend.md`](references/extend.md)。

检查呈现结果时，看读者能否找到对象之间的关系、讲清关键步骤。
积木语法通过校验后，仍然要看实际渲染有没有表达出这些信息。

颜色使用 `theme.css` 的变量，如 `--tone`、`--surface`、`--border`、`--blue`。
**不写死色值**，否则切换主题时颜色不会跟着变。

交互需要自定义布局时，可以用 `demo` 的 `html` 字段，并在 `WIDGETS` 注册控件函数。
没有现成控件时，先确认交互有助于理解，再决定是否扩展。

## 工作流

下面用于制作或修改页面。先确定本次范围，再选择需要的步骤；
写作、查证和检查过程中发现缺口时，可以回到前面的安排，不必等整篇写完。
每一步都要留下能继续工作的结果：问题范围、计划、图解安排、实际页面或检查记录。
篇幅可以调整，关键动作、判断条件和发现问题后的处理办法不能省成一句「自行检查」。

<span id="第-0-步-判断用户要的是一个点还是一个面"></span>

### 第 0 步 · 确认范围和交付方式

先结合用户的请求和已有材料，明确本次要解决的问题、读者背景和交付形式。

| 本次需求 | 怎么继续 |
|---|---|
| 阅读、讨论或审阅材料 | 给出分析和意见，不自动新建页面或修改文件 |
| 制作一篇或修改已有页面 | 确认主题和必要前提，再安排讲解 |
| 系统理解一个主题，预计涉及多篇 | 先梳理主题和依赖，再确定当前要做的部分 |

确认范围时检查：

- 用户要回答哪个具体问题，或者学到什么程度？
- 已经熟悉哪些概念，缺的是定义、对象之间的关系，还是实现过程？
- 本次要讨论意见、单篇页面还是一组笔记？已有页面是否需要沿用？
- 交付是本地预览，还是包含提交和上线？

已有信息足够时直接继续，不为了填写表格反复问用户。
只有歧义会改变讲解范围或交付时才确认，例如「先帮你看哪里没讲清楚，还是直接修改页面？」。
用户说「架构图」时，不自行扩大成从零学习整个项目；「看不懂」也不自动等于概念入门。
把本次范围和已有背景保留在工作记录中，后面的规划和验收都以它为准。

<span id="第-1-步-梳理知识树只在一个面时做"></span>

### 第 1 步 · 需要时梳理主题和依赖

只讲一个具体问题时，列出必要前提即可，不必建树。
主题较大、前置知识多或跨多篇时，用知识树说明要理解哪些内容、先后依赖，以及当前先做什么。
已有确认的计划先复用，不重新猜一套范围。

#### 明确节点和前置知识

业务背景、概念、组成、工作过程、设计取舍和代码细节，是检查是否遗漏内容的几个角度。
按问题需要递归展开模块，不要求每个主题都填满六层，但模块自己的必要概念和前置知识不能省掉。
例如路由需要单独理解时，可以展开它的定义、匹配过程和调用例子：

```text
理解 Web 框架
├─ 请求中的对象
├─ 中间件
│  ├─ 中间件是什么
│  └─ next() 怎样连接处理过程
└─ 路由
   ├─ 路径怎样匹配
   └─ 一次请求走过哪些处理器
```

每个节点至少说明下面这些信息：

| 要记录的内容 | 用来决定什么 |
|---|---|
| 要回答的问题 | 节点的范围，哪些内容不属于这里 |
| 前置依赖 | 先读哪一节或哪一篇，是否有循环依赖 |
| 深度 | 讲概念、组织、机制还是代码，避免在同一节点突然换层次 |
| 产物归属 | 单独成篇、并入哪篇，或只是分组节点 |

逐个节点问四个问题，并处理发现的缺口：

1. 理解它前必须先知道什么，前提在哪个层次？给缺失前提安排位置，或者链接已有说明。
2. 是否 A 依赖 B、B 又依赖 A？提取共同前提或重新划分节点，不让读者来回跳。
3. 哪些细节可以推迟？移到后续节点，不把第一篇写成完整源码手册。
4. 哪些是读者已经知道的？保留必要连接，略去重复入门说明。

#### 确认脉络和切分页面

把影响范围的知识树给用户看，确认有没有多余或遗漏、顺序是否合适、当前先做哪块。
一般局部调整不必反复确认；发现计划要扩大到新的主题或多篇内容时，先说明变化。
追问可以暴露前提缺口，但不能只凭追问次数认定最初规划失败。

拆篇综合判断：

| 单独成篇更合适 | 并入已有篇更合适 |
|---|---|
| 有独立问题，说明前提后能独立读懂 | 只是父主题的一个属性或短定义 |
| 内容需要多节，留在原篇会打断主线 | 只需一两段或一个例子即可接上主线 |
| 多个主题需要复用完整解释 | 只有局部需要，直接链接术语或章节就能定位 |

被 `needs` 引用不是拆篇的唯一依据。短定义可合并；只有一个引用但主题完整的长内容也可以独立。
切分后检查每篇的前提是否自足，不能让读者到另一篇中间猜哪里才是需要的解释。

#### 保存和更新计划

跨多篇的计划写进 `plans/<topic>.yaml`，笔记通过 `meta.json` 的 `tree` 关联。
字段和示例见[知识树与计划文件](#知识树与计划文件)，层级、依赖和进度在计划中维护，不手抄两份。

| 写作中发现的情况 | 怎么更新 |
|---|---|
| 先解释 X 才能继续讲 Y | 给 X 安排前置说明，必要时新增节点并更新 `needs` |
| 某个分支讲了多段仍未完整 | 检查是否有独立问题，再决定扩一节还是拆篇，不按段落数自动新建 |
| 某个分支和主线不是同一件事 | 放到相应旁路节点或后续篇，并说明从哪里进入 |
| 内容在多篇重复 | 核对边界，合并解释或链接同一处，同时更新产物归属 |
| 完成一篇或改变范围 | 更新对应进度、摘要和依赖，检查首页与前置链接 |

`artifact` 可以先填，尚未制作的前置应显示「待产出」，不生成死链接。
正文完成后可更新为 `status: drafted`；计划进度不是笔记的人工核对状态。
改计划后全量构建，检查待产出状态、节点归属和阅读顺序。工具检查引用存在，不替代循环和边界检查。

<span id="第-2-步-找到卡点"></span>

### 第 2 步 · 明确问题和理解难点

先记录用户明确提出的问题，再找材料中可能影响理解的地方。
两者要区分，不能把材料长得复杂直接当成用户的卡点。

| 候选线索 | 要进一步确认什么 |
|---|---|
| 用户加粗、划线或单独贴出一段 | 是否明确表示不懂，还是只是提供背景 |
| 篇幅长但抽象的段落 | 哪个词、前提或过程没有落到具体对象 |
| 多个并列概念 | 读者不认识概念，还是记不住区别、归属和联系 |
| 需要追踪顺序或状态的过程 | 哪一步输入、处理或结果接不上 |
| 反直觉结论 | 缺少什么条件或证据，为什么与读者原有认识不同 |

把候选难点改写成可回答的问题。例如把「socket 很抽象」收敛为「fd 怎样找到内核里的 socket」。
逐个检查是否属于本次范围，给必要概念、关系和过程安排解释。
没有明确卡点时先围绕主题讲必要内容；不同方向会产生明显不同的页面时，再确认先讲哪部分。
这一轮得到的是问题清单和所缺的前提，不是几个随意选出的重点。

<span id="第-3-步-拆骨架"></span>

### 第 3 步 · 安排讲解结构

列出这篇要回答的几个问题，每个问题安排一节，按前置依赖排顺序。
如果走过第 1 步，先用知识树中对应节点的范围安排骨架，再根据实际内容调整。

规划时为每节记录所需前提、要回答的问题、具体例子和读完应当能说明的结果。
这些是作者的工作记录，不必写成每节固定的正文段落。

检查骨架时，把每节暂时拿掉：缺了它主问题讲不清，或下一节缺前提，就保留或重新安排；
只是重复或不相关的铺垫，可以删去。依赖上下文的设计理由放到对应机制旁边，不先抽成孤立的小专题。
改稿增加分支后，重新检查章节的归属和顺序，不只在末尾追加内容。

<span id="第-4-步-逐段过一遍决定画哪些图"></span>

### 第 4 步 · 决定图和表格怎么呈现

逐段检查骨架，不只挑几个重点。为每段记录要回答的问题、涉及的关系、呈现方式和需要核实的信息。
对象的位置、归属、连接、分支和状态变化按原则 ① 用图呈现；
比较和并列信息按原则 ⑥ 选形式，简单清单和判断可以留文字。
具体积木查[积木清单](#积木清单18-个从手上的文字反查)。

需要补容量、位置、归属或机制时，先按[资料查证](#资料查证)核实，再写进图。
选一个具体例子检查路径和状态，标清输入、参与对象和结果，确保图与正文解释的是同一个问题。

#### 检查连线的含义

每条边都要能说出关系。比如接收队列、发送队列和连接状态是 socket 的并列信息，
不能为了排成一列而画成「接收队列 → 发送队列 → 连接状态」。

| 实际想表达的 | 合适的修法 |
|---|---|
| 都属于同一个对象 | 用 `tree` 或包含框表达归属 |
| 并列比较 | 用 `compare` 按维度对照 |
| 一份没有先后关系的清单 | 用 `cards` 分组介绍 |
| 有真实的流动、指向或先后 | 保留连线，必要时标动作和方向 |

关系清楚时标签可以省；只为布局添加的空边要删除。
「从这里开始分叉」是过渡句，不是对象，放在图外说明。

#### 先验证正确用法再判断能力

1. 读所用积木的参考和可运行示例，确认字段与布局方式，不凭名字猜。
2. 用推荐的例子验证工具能做的形状，再用最小的本次需求验证相关能力。
3. 若仍有缺口，记录正确用法、复现输入、诊断和缺少的能力，再决定组合、扩展或用 `raw`。

archify 的分层带、嵌套框和手工坐标已有参考，见[结构化图](#结构化图调用-archify-skill)。
不要因为一种排法没调通就认定工具不支持。替换工具或自写布局也要保留表达需要的关系和信息。

<span id="第-5-步-决定哪里需要交互"></span>

### 第 5 步 · 设计必要的交互

静态图不易说明操作过程或不同输入的结果时，再考虑交互。
先写清操作、状态变化和可见结果，避免只有能点击的控件却没有新的解释。

| 场景 | 交互需要让读者看到什么 |
|---|---|
| 轮询与 CDC | 同一次数据变化，在两种机制下何时被发现，中间变化是否被保留 |
| 乐观锁与悲观锁 | 相同竞争场景中的等待、冲突或重试 |
| B+ 树插入与删除 | 操作前后的节点、分裂或合并过程 |
| 不同隔离级别 | 同一组并发操作下的读取结果与异常条件 |

对比型演示使用相同输入和可比较的条件，区别只来自正在说明的机制。
示意时间、容量或性能数据要标明；真实行为要有对应依据。只展示固定顺序时，静态图通常已经足够。

先查现有控件，能复用就复用。新增控件的接入顺序是：

1. 在 `assets/app.js` 的 `WIDGETS` 注册逻辑，按需要补带独立前缀的样式。
2. 用 `demo` 声明外壳，核对 `widget` 名与注册名一致。
3. 按接口接入数据：日志分栏的 `log` key 要对应；`config` 或自定义布局则使用各自字段和挂载点。
4. 实际操作一次正常输入，再检查边界、重复操作和重置，确认状态与结果一致。

具体用法见 [`references/blocks.md`](references/blocks.md)，扩展约定见 [`references/extend.md`](references/extend.md)。

<span id="第-6-步-写-notemd"></span>

### 第 6 步 · 写作并检查局部效果

在当前 worktree 中操作。新建笔记时运行：

```bash
npm run new -- <slug>   # 小写字母、数字和连字符
```

修改已有页面时，直接编辑对应的 `notes/<slug>/note.md` 和 `meta.json`，不重复新建。
生成的 HTML 不手改。先填标题、摘要、来源和 `draft` 状态，再按需要填 `topic` 或知识树关联。
字段说明见[笔记元信息](#笔记元信息)。实质改写已有人工核对的内容时，不让旧核对状态替新内容背书。

积木语法查对应参考，不熟悉的积木先读 `notes/blocks-cheatsheet/note.md` 中的可运行示例。
按骨架逐节写，必要概念配具体场景或数据例子，示意数据要标明。
一块关键图、复杂布局或交互写好后，先检查局部效果：

```bash
npm run block -- <slug> --list   # 找到块号、语言和行号
npm run block -- <slug> <n>      # 单块渲染和截图，默认不开浏览器
```

确认输出中的块号和行号属于当前内容，再读取本次生成的截图。
没有本次截图，或文件仍是上次结果时，不算看过这一块。
量高失败、回退到固定高度时，另行确认内容是否完整；高图被截断就重新量高或补截，不能只看上半截。
检查标签、连线、容量和状态是否完整可见，发现问题先修该块，再继续。
需要用户查看时加 `--open`；不要为 agent 自检反复留标签页给用户清理。

局部预览不更新 `dist/`，交互还要在整页中实际操作。
改了前文概念、共享样式或图的布局时，回头检查受影响的旧内容，不只看新写的部分。
有计划的主题，写完一篇后核对进度和新前置；有变化才更新计划并全量构建。

<span id="第-7-步-校验构建量图"></span>

### 第 7 步 · 构建和验证

先运行 `npm run check`，按文件、行号和积木名处理诊断，再按修改范围构建。
指定篇检查时，确认对应产物存在，且输出确实列出了该篇；退出码为零不证明检查覆盖了目标。

#### 局部预览

只改一篇、且不涉及知识树或共享资源时，可以先检查该篇：

```bash
npm run view -- <slug> --no-open   # 重建该篇单文件版，不打开浏览器
npm run visual-check -- <slug>    # 检查刚生成的 dist/<slug>.html
```

`block` 截图和 `npm run build` 不更新 `dist/`，不能拿它们替代这一步的单文件构建。
`view` 也会更新首页，暂存前检查生成差异。

#### 全站和知识树

改了共享样式、控件、计划文件或需要检查跨篇依赖时，先全量构建：

```bash
npm run build:standalone
npm run visual-check
```

挂知识树的笔记在交付前也要全量构建，查看首页节点、前置链接和「待产出」状态。
改了 skill 文档时还要运行 `npm run skill` 并检查生成页面；`visual-check` 不覆盖 `skill/`。
保留本次命令、目标和结果，确认实际页面来自当前工作区，而不是另一份源或上次构建。

#### 按失败类型处理

| 看到的情况 | 检查和处理 |
|---|---|
| 未知积木、YAML 解析或围栏错误 | 核对对应行、积木名、字段、引号和缩进，再重跑 `check`；不能因为页面有代码块就认为图已生成 |
| 缺 `quiz` 或元信息 | 按本篇问题补自测和字段，来源与核对状态按事实填写 |
| 没有 SVG、图为空或少一部分 | 查看浏览器异常与实际 DOM，核对注册名、输入和资源；格式通过仍需修运行问题 |
| 标签重叠、边穿无关节点、容器溢出 | 对照诊断和截图，改关系结构、位置、间距或标签，不能仅靠隐藏问题通过 |
| 未取得探针数据或检查不稳定 | 核对资源、临时文件、浏览器和探针异常，保留日志；不能猜一个根因后标通过 |
| 命中既有基线 | 核对是已确认的限制，说明影响；新问题不靠加基线绕过 |

实际阅读宽屏与约 400px 的窄屏，切换深浅主题，并操作关键控件。
工具默认检查宽屏布局，不替代这些动作；完整判据、工具局限和排障方法见[检查工具与排障](#检查工具与排障)。

<span id="第-8-步-交付前的九次复盘复盘清单"></span>

### 第 8 步 · 交付前检查

第 7 步确认页面能构建和运行，这一步检查讲解是否正确、完整、能沿着读者的路径读懂。
先回到第 0 步的范围和问题清单，再逐项检查下面的细则。
可以在一次通读中收集多项结果，但不能把它们合成一句「已自检，无问题」。

每项记录检查的位置、发现的问题、处理办法和修后结果。
不适用的项目说明原因；未解决问题记录为待处理，不算通过。
这是作者复查，不冒充实际用户验收，也不把自检写成已人工核对。

#### 复盘 ① · 术语与前置知识

列出正文、图标签、代码例子和控件中出现的术语，找出目标读者不熟悉的部分。
反引号标识符可以先用下面的命令列候选；中文术语、缩写、别名和图内文字仍要主动补查。

```bash
grep -oE '`[A-Za-z_][A-Za-z0-9_.]*`' notes/<slug>/note.md | sort -u
```

逐个核对首次使用的位置：读者已经知道它，前文解释过，还是有明确可达的前置链接？
不能因为作者熟悉就默认读者认识，也不要求把已知词都重新定义。

| 问题 | 处理办法 |
|---|---|
| 未定义术语先出现在主线或图里 | 在首次使用前补简短解释和例子；缺一组概念时再加概念章节 |
| 前置说明在后面，读者需要倒着找 | 前移必要解释，或调整章节顺序 |
| 一篇的前提藏在另一篇中间 | 提供准确章节链接；需要完整前置篇时更新计划和 `needs` |
| 同一对象换了名字或缩写 | 首次说明对应关系，后文统一称呼，图和正文同步改 |

检查通过时，读者沿正文就能找到必要前提，不必依赖作者口头补充。

#### 复盘 ①b · 数字、事实和机制

把事实断言列出来，包括数字、数量、位置、归属、默认值、版本行为，以及「因为」「所以」后的机制解释。
正文、图、速查表和演示里重复的同一个断言要一起核对，不能只修正文。

| 要核实的内容 | 具体动作 |
|---|---|
| 方法数、行数、枚举值、调用点 | 到对应版本源码枚举或计数，明确统计范围；文本搜索是候选，不保证覆盖全部语法 |
| 上限、容量、默认值和性能数据 | 查原始资料或实际配置，标平台、版本、单位和条件 |
| 位置、归属和共享关系 | 沿对象结构、创建或引用路径检查，不能从名词相邻推导关系 |
| 机制和因果关系 | 沿输入、判断分支、状态变化和输出读代码或一手说明，确认它是否真的这样发生 |
| 设计动机 | 区分可观察行为和作者意图；没有注释、文档或其他证据时，不把合理推断写成作者的理由 |
| 示意数字 | 标明示意及假设，不当作真实默认值或测量结果 |

记录断言、原始出处、适用条件和核对结果。`wc -l` 可核对文件行数，接口方法等则要先确认声明范围。
知道文件名不等于核实当前实现；来源也不能只写「查过了」。

以前曾把 `countSql` 的包装解释成「展示列 LEFT JOIN 后需要去重」，但核对发现：

| 原解释 | 核对结果 |
|---|---|
| 展示列参与计数并产生重复行 | 计数使用 `uidsSql`，展示列不参与那条路径 |
| 包一层就完成去重 | 包装本身不会去重 |

这个例子需要读完整路径，数对方法或字段不能证明解释成立。
写下「因为」时问：这是读到的行为或理由，还是推出来的？推断应核实或标明依据与不确定性。
没有证据的数字或机制，要查证、删去不必要断言，或明确为未确认，不能靠顺畅的措辞补齐。
方法见[资料查证](#资料查证)。

#### 复盘 ② · 新概念的例子

逐个找出本篇引入的新概念，核对读者能否把定义对应到一个具体对象或过程。
只写「某种机制」往往不够；例子还需要表现出它的关键特征。

以软删除为例，三类信息分别起作用：

| 信息 | 示例 |
|---|---|
| 简短定义 | 删除时保留记录，用字段标记删除状态 |
| 具体形态 | 示意记录 `{ id: 7, deleted_at: '2026-03-01 10:00:00' }` |
| 与易混概念的区别 | 普通删除后记录不在了；软删除后记录仍在，读取有效记录时需要相应过滤 |

检查例子是否实际使用了这个概念，和图、字段、状态及结论是否一致。
容易混淆时补对照；不用为所有概念强凑三栏，也不重复定义读者已经熟悉的词。

缺具体形态就补数据、场景或小图；例子过大就保留关键字段和步骤，并标明简化。
用 `cards` 的 `code` 字段可以放短数据例子，复杂机制仍需图或过程说明。
不能把示意数据当成从真实系统取得的数据。

#### 复盘 ③ · 按目标读者通读

只看准备交付的 HTML，从头读，不借助源码、对话里的解释或尚未交付的草稿补缺口。
对每段及相邻图表检查：

- 这里的词是否已经认识，或能找到前置解释？
- 「它」「这个」「上述」明确指哪个对象，图中同名对象能否区分？
- 从上段到这段是否有未说明的跳步，结论需要的条件是否出现？
- 图或表在保留必要标题、图例的情况下，能否独立说明关键关系？
- 沿具体例子走一遍，能否说明每一步输入、参与对象和结果？

记录读不下去的位置和原因，不只写「需要更易懂」。
缺概念补定义，缺关系补图，指代不明写对象名，结论突然就补条件或调整顺序。
缺事实依据时回原文或源码核实，不能凭常识编一个过渡解释。
修完重新读相关段落，确认补丁没有引入新的术语和跳步。

#### 复盘 ④ · 目录、归属和编号

列出源文档的标题，再对照渲染目录检查层级、归属、顺序和编号。

```bash
grep -nE '^#{2,4}[[:space:]]' notes/<slug>/note.md
```

| 检查项 | 典型问题 | 修法 |
|---|---|---|
| 层级 | 下级内容写成与父主题平级的标题 | 调整标题级别，重新检查渲染目录 |
| 归属 | A 的机制说明插在 B 的章节里 | 移到对应位置，补连接句或必要链接 |
| 顺序 | 先使用概念，再解释概念；例子依赖后文 | 按真实依赖前移前提，或重排章节 |
| 编号 | 图、正文和步骤号重号、跳号或错位 | 核对每个引用和标签，成组更新 |

初学内容通常先认识对象再看配合；熟悉概念的读者可以从当前问题切入，不机械套同一目录。
检查前置篇、章节链接、目录和返回入口是否可达，尤其是拆篇和改标题之后。
改了计划要全量构建，不只看这一篇的目录。

#### 复盘 ⑤ · 主线与篇幅

把第 2 步的问题清单逐个对应到章节，检查主要问题是否真正得到解释。
暂时拿掉一节：主问题讲不清或后文缺前提，就保留或调整；只少了旁支知识，则可以压缩或移后。
需要比较篇幅时，可以列出二级章节的起始行，用相邻位置估算区间，再到实际页面核对：

```bash
grep -nE '^##[[:space:]]' notes/<slug>/note.md
```

这是标题候选，围栏中的标题示例不能当正文目录。YAML 和代码也占源码行数，
所以区间只帮助定位异常，不决定哪节有价值，不能替代阅读图、例子和实际内容。

遇到旁支很长、主线很薄时，回主线选一个具体输入走一遍，找出缺对象、缺步骤还是缺条件。
先补这些缺口，再判断旁支是否应缩短，不能只把主线扩写到行数超过旁支。

`insight-dsl` 的一次改稿中，「三段管道」136 行，独立的设计章节256行、测试章节177行。
这些是当时的源码排版数据。问题不是数字大小，而是几处拼 SQL 的设计被抽离了实际步骤，
导致主线缺细节，设计说明也失去上下文。把依赖具体步骤的解释并回去后，过程才完整。

检查设计说明是否脱离触发条件、例子和实际路径；属于主线步骤的放回相应位置。
主线讲完后的延伸或独立比较可以单列。文章回答「有什么区别」「为什么这样选」时，主线不必是机制。
修完再对照问题清单，确认关键回答没有因移动或删减而丢失。

#### 复盘 ⑥ · 语气与行文

通读正文、图标签和控件说明，用下面的表逐句处理；不把所有有力措辞一律删掉。

| 候选问题 | 检查和处理 |
|---|---|
| 大判断后用破折号重复一次 | 合并重复，或直接从具体内容讲起 |
| 「下面来看」「再补一条」等空转过渡 | 不承载信息就删掉，必要的逻辑连接保留 |
| 「不是 A，而是 B」 | A 是读者的真实误解时保留对照，否则直接解释 B |
| 「唯一」「永远」「一定」 | 核对依据和适用范围，经验判断补条件，明确约束可以直接说 |
| 讨论中的辩护、编排说明和元叙述 | 删去只解释作者写作过程的内容；与主题有关的设计理由和取舍仍要保留 |
| 强调过密 | 只突出关键结论和风险，不靠给每句加粗表示重要 |

可以先搜索候选句：

```bash
grep -nE '——|注意|其实|必须|唯一|永远|一定' notes/<slug>/note.md
```

命中不表示错误，数字阈值也不能验收语气。
改写时保留条件、因果、对照和执行要求，不能为了去 AI 味把重要说明压成空泛短句。
完整规范见[怎么写](#怎么写笔记正文和-skill-文档都适用)。

#### 复盘 ⑦ · 图解缺口与关键图的信息量

先查段落有没有该画未画，再逐张检查图是否讲够，两项都要完成。
用 `npm run gaps -- <slug>` 列正文候选段落后，还要补查它没有完整覆盖的列表、引用、图注和控件说明。

为候选内容记录「位置 → 要说明的关系或过程 → 对应图 → 是否覆盖」。
已经有相关图时核对实际覆盖，避免机械地为同一句关系重复作图。

| 内容类型 | 怎么处理 |
|---|---|
| 多对象的位置、归属、指向、分支或状态变化 | 沿原句核对图，缺哪条关系、状态或步骤就补哪项 |
| 方案比较、映射和并列介绍 | 用表格或卡片整理；需要连接和过程时另补关系图 |
| 因果论证、经验判断和取舍 | 留文字，涉及的结构与机制不能因放在理由里就省略 |
| 简单操作清单、过渡和一句话结论 | 可以留文字，不按关键词强制画图 |

漏图返工曾涉及一个程序文件与多个进程、任务等待 I/O 时执行对象的切换，以及轮询到中断的演进。
分别对应关系图、过程图和时间线，不因为它们不是主要卡点就退回文字。

再逐张打开关键图，盖住正文，但保留图自己的标题、图例和必要标签：

1. 图在回答哪个问题？能否看出位置、归属和连接，而不只是名词列表？
2. 讲机制时，具体输入能否沿图走到结果？队列、执行者、状态和层次在哪里？
3. 数量、容量、方向影响结果时是否标清，真实值与示意值是否区分？
4. 图中对象是否是读到这里的读者已认识的，图与正文的条件、字段和编号是否一致？

关键图只列名字就补与问题相关的结构；路径停在未知抽象上就补必要对象或前置解释。
容量和方向不影响问题时不强补数字，缺事实依据先查证，不能靠增加标签装饰信息量。
图太复杂则调整范围或拆图，不能用删掉关键关系换可读性。
修完回到原句和具体例子，重新完成一次覆盖与路径检查。

#### 复盘 ⑧ · 密度与必要关系的可见性

对整体图、密集流程图和有聚焦功能的图，分别检查默认状态与聚焦状态。
默认图至少能看见对象、层次和必要关系；聚焦用来帮助追踪，不用来藏掉默认布局的问题。

选一条关键路径从头走到尾，再检查其他必要关系：是否有线穿过无关对象、标签被挡、
文字挤成一句、边因淡化而无法辨认，或重要结果只能在图外文字里找到？

| 问题 | 优先处理 |
|---|---|
| 不同关系全用同一种箭头，路径难辨 | 分清包含、归属、共享和流动，换成对应形状 |
| 必要对象或连线太密 | 调整范围、分组、间距或拆图，保留跨图的连接说明 |
| 标签比可用间隙宽 | 调布局或标签位置，必要时精简冗余，不把关键条件说残 |
| 只在聚焦后才看得见关键关系 | 修默认表达，或清楚声明这是分步导览，并提供可追踪的完整路径 |

把线压在框下、降低透明度或仅在点击后显示，并不自动是错误；
判断这些动作是否让必要关系更容易理解，还是只让碰撞不容易被发现。
检查器通过仍要查看实际截图。修完在同一条路径和默认状态下复查，不只验证聚焦按钮能点击。

#### 复盘 ⑨ · 工具用法和能力判断的证据

第 4 步是在选图时试正确用法，这里检查本次是否真的执行过它，不只留下「参考已读」的结论。

- 用了不熟悉的积木，是否看过对应可运行示例，并核对字段和实际渲染？
- 声称工具做不到某种图，是否有正确用法下的最小复现、诊断和具体缺少的能力？
- 改用 `raw` 或自写布局后，原本需要的关系、容量、状态和层次是否仍在？
- 工具报错后，是否换了用法、加了基线或改了检查，却没有证明内容变正确？

曾因为没有试推荐布局，就判断 archify 不支持分层带和嵌套框。
这些能力实际已有参考，试了几次失败不等于工具没有能力。
缺证据就补参考例子和最小需求验证；是用法错误先改用法，确有局限再记录替代方案。
不要求为了凑证据运行与当前需求无关的工具。

#### 交互、主题与自测

静态截图不能证明交互正确。对本篇控件至少执行一个正常场景，并检查本次机制有关的边界：

- 改输入或切方案后，数据、图、日志和结论是否一致？
- 重复点击、回到初始状态或重置后，是否残留上次结果？
- 没有数据、容量满、冲突或异常等相关状态，是否与已说明的条件一致？
- 操作在窄屏和深浅主题下是否可见可用？新增控件的按钮和输入是否能用键盘访问？

不适用的边界说明原因；没实际操作就记未验证，不由截图或没有报错推定通过。
若比较两个方案，复查它们输入和条件相同，差异确实来自正在说明的机制。

本仓库笔记结尾要有 `quiz`。合上答案，尝试只凭页面回答本篇的关键问题，再打开答案核对。
题目应检测主线关系、过程或成立条件，不用无关记忆题凑数。
答案依赖未讲信息时补讲解或改题；答案与正文不一致时一起核实和修正。

#### 检查记录与修改后的回查

用工作记录保存各项结果，不必把整份复盘写进笔记正文。
最少包含检查项、位置、证据或复现动作、结果、处理办法和复查结果，例如：

```text
术语｜第2节和图A｜发现 fd 表尚未解释
处理：第1节补定义和数据例子，图A统一名称
复查：从第1节读到图A，前置和指代已能对应

机制｜第3节的“因为...”｜尚未找到源码依据
结果：待处理；先核实对应路径，不标通过
```

共享同一轮通读或截图证据可以，但每项仍要有对应结果。
内容错误、关键关系缺失、证据未确认或运行失败，先处理，不以「已知限制」笼统放过。
既有基线与未覆盖项分别说明范围、影响和后续动作。

修改术语要回查图和控件，修改机制要回查表、例子和 `quiz`，移动章节要回查前提、目录和链接。
图或控件改了后重建并复查相关状态；共享样式改了要检查受影响页面。
验收通过的条件是相关问题已修复并复查；仍有关键缺口时报告待处理，不标成已完成。
不能只计已勾了多少项，也不能因为写了限制说明就把未完成内容当成已验收。

#### 交付与发布

交付时提供页面或文件路径，说明本次改了什么、验证了哪些范围，以及仍有哪些限制。
核对标题、摘要、来源、时间和主题归属；源码来源记录对应版本，不填虚构链接。
新生成或实质改写的笔记保持 `draft`，不让旧人工核对状态替新内容背书。

需要提交时，先检查会话板和工作区，按本次负责的源文件与重建产物点名暂存，
查看 staged diff，确认无他人未完成内容、临时文件或来源不明的产物，再提交。
必要的全量构建用于保证一致性，不是代提交他人内容的理由，具体约定见[多会话协作](#多会话协作)。

本仓库推送 `main` 会更新站点。约定包含上线时，完成推送并核对线上标题、正文和关键链接，
必要时与本地产物对比，不能把远端提交收到等同于页面已经发布。
只要求本地预览或暂不发布时，遵守已确认的范围。失败时报告阻塞、当前提交和页面状态，不绕过检查。

### 第 9 步 · 记录可复用的改进

交付后回看哪些环节重复耗时，区分内容、用法、输入数据、环境和工具问题。
次数和症状是线索，先保存复现条件和证据，再判断原因，不能把合理猜测直接写成工具限制。

#### 改进线索与处理

| 看到的线索 | 先核对什么 | 确认后的改进方向 |
|---|---|---|
| 同一条命令反复重试 | 输入是否正确，诊断是否一致，资源或环境是否变化 | 用法问题补说明；诊断缺信息才改工具输出 |
| 一块内容反复截图仍不对 | 是否试过推荐字段和布局，是否加载当前产物 | 先修用法或结构；证明能力不足后再扩展或替换 |
| 反复计算坐标、尺寸 | 手工布局是否正是所需，换屏或数据后是否失效 | 可复用测量问题才考虑自动化，不一律禁止手工坐标 |
| 「改—构建—截图—看」回路很长 | 是否可用现有单块预览，哪一环节真在重复 | 缩小验证对象或改反馈方式，同时保留整页验收 |
| 绕过现有工具手写代码 | 是一次性合理表达，还是同一缺口反复出现 | 一次性可用 `raw`；共性能力再评估做成积木或参数 |
| 留下标签页、临时文件需用户清理 | 是否是本次需要，默认行为能否安全调整 | 改默认或增加明确选项，并保留主动查看入口 |
| 同类表达多次手写 | 内容与接口是否有稳定的共同部分 | 优先复用或加字段，确实独立再新建积木 |
| 文档与实际工具行为不一致 | 对应版本、默认值和适用范围是什么 | 修错误的一边，同步示例与验证，不默认认定文档错 |
| 并行会话改坏同一文件 | 是否共用工作区或可变临时路径，是否声明范围 | 隔离和协调，补可执行约定，不只追加提醒 |
| 同一个问题再次出现 | 规则是否可找到，是否有正确例子和失败检查 | 放到使用位置或补检查，不把每次事故变成新口号 |
| 页面能生成但看着不对 | DOM、样式、图形和文字到底哪一部分异常 | 可机械判定时补探针；依赖语义时保留实际阅读检查 |

#### 验证修法，再写回

记录症状、复现输入、环境与版本、证据、影响范围和拟采取的办法。
确认是本篇内容问题就修本篇；是工具共性问题才评估改工具。
小修在范围内验证后说明，大改共享工具或交付目标先单独提出，不自动扩大任务。

例如块预览不需要每次打开标签页，而 `view` 的用途就是给人看。
改默认值前核对各命令的用途，不把「默认不开」推广到所有工具。
截图缺下半截时，先确认是否量高失败或高度写死，再验证先量后截的修法，不只是增大固定高度。

改完用实际出问题的页面、最复杂的一块，以及共享能力的其他代表页面验证。
检查截图是否完整、命令是否报告正确目标、原来正常的用法是否仍有效，并重新执行相关第 7、8 步。

| 改进涉及什么 | 写回哪里 |
|---|---|
| 积木或控件的用法 | 对应参考、可运行例子和需要的限制说明 |
| 新的共性能力 | 扩展文档、积木清单和例子；注册信息从实际注册表取，不手抄另一份名单 |
| 命令默认值或输出 | 命令说明和检查范围，核对文档与实际行为 |
| 流程规则 | 使用它的步骤旁边，给触发条件、动作和失败处理 |
| 协作约定 | 多会话协作与会话板协议，说明共享状态的边界 |

规则与工具检查各有作用：能机械检查的错误交给工具拦，语义判断仍需要清楚的方法和例子。
不能只修这一篇，遗漏共性用法的说明；也不能只追加规则，不验证工具或原问题是否修好。

#### 改写 skill 时核对信息保留

修改说明文字同样需要验收。改前列出原内容的关键动作、适用条件、判据、失败修法和重要例子，
改后逐项对应到新内容或明确的详细章节。

| 要核对的情况 | 怎么处理 |
|---|---|
| 只是换标题或语气 | 检查条件、因果和执行要求仍完整，不用短句替代原方法 |
| 合并或移到其他章节 | 给出准确的新位置，调用处保留足够动作和直达链接，不能只保留一个历史案例 |
| 删除重复或错误规则 | 说明重复位置或错误依据，保留其中仍成立的目的和处理方法 |
| 命令或例子被替换 | 验证新例子能表达同一关键问题，不恢复已知错误用法 |

用「原要求 → 新位置 → 处理理由 → 验证结果」核对覆盖。
关键词出现、旧锚点存在和构建通过，只能验证局部形式，不能证明重要信息没有丢。
通过条件是下一次使用者仍能知道何时做、怎么做、做完怎么看结果，以及出问题怎样修。
审计发现关键方法只剩概括时，先补回具体方法，再提交发布，不按压缩比例决定是否完成。

## 知识树与计划文件

知识树用于安排跨篇内容，`plans/<topic>.yaml` 保存主题、依赖和进度。
单篇说明也可以只用章节骨架，不必为了使用 skill 建计划文件。

### 规划角度和内容切分

| 检查角度 | 可能需要回答的问题 |
|---|---|
| 业务背景 | 为什么需要它，解决什么问题 |
| 概念 | 有哪些词，分别对应什么对象 |
| 组成与组织 | 由什么组成，怎样分类和联系 |
| 工作过程 | 对象怎样配合，请求或数据怎样流动 |
| 设计取舍 | 为什么这样选，适用条件和代价是什么 |
| 代码细节 | 相关模块、文件或函数怎样实现 |

按当前问题选择这些角度，不机械递归。
例如理解中间件可能需要概念、`next()` 的过程和一个调用例子，不一定需要独立的业务背景或设计史。

先按问题切分知识范围，再确定页面和分组节点。
一个主题完整、篇幅较大的节点可以单独成篇；几个短知识点可以合成一个节点和一篇。
多处复用是拆篇的考虑因素，不是硬门槛；被引用的短定义也可以通过章节或术语链接定位。

### 计划文件结构

下面是两篇笔记的示意计划，`artifact` 填笔记的 slug：

```yaml
topic: service-request
title: 理解一次服务请求
summary: 先认识对象，再沿请求路径理解它们怎样配合
source: 原始材料链接或源码版本
nodes:
  - id: concepts
    title: 请求中的几个对象
    layer: 概念
    needs: []
    artifact: service-request-concepts
    status: planned
    blurb: 客户端、服务和数据库各负责什么
    children: []
  - id: flow
    title: 一次请求的路径
    layer: 架构
    needs: [concepts]
    artifact: service-request-flow
    status: planned
    blurb: 从请求进入服务到返回结果
    children: []
```

| 字段 | 含义 |
|---|---|
| `topic` / `title` / `summary` | 计划标识、展示标题和范围说明 |
| `source` | 材料来源，源码类计划记录对应版本 |
| `nodes[].id` | 节点标识，在同一计划中保持唯一 |
| `layer` | 讲解层次或模块标签，按主题填写 |
| `needs` | 本节点的前置节点 id，不是页面 slug |
| `artifact` | 对应笔记的 slug，可以先规划，后制作 |
| `status` | 计划进度，如 `planned`、`drafted`、`done`；不是人工核对状态 |
| `blurb` / `children` | 节点摘要和需要展开的子节点 |

笔记的 `meta.json` 通过 `tree` 关联计划：

```json
{ "tree": { "topic": "service-request", "id": "flow" } }
```

首页树视图来自计划，笔记顶部的前置区块来自该节点的 `needs`。
构建时前置笔记尚未存在，会显示「待产出」，不生成死链接；
`needs` 引用不存在的 id 时，`npm run check` 会报错。
节点唯一性、循环依赖、笔记关联和阅读顺序仍要主动核对，不能把存在性检查当成完整规划校验。

### 写作中维护计划

完成一篇后检查计划是否仍与内容一致，更新相应进度。
发现缺失前提时，先判断是补一节、引用已有说明，还是新增节点和笔记。
发现重复时调整节点范围和引用，不只把多个 `artifact` 指向同一页来掩盖边界问题。

要合并或拆分篇时，同步更新节点、`needs` 和笔记的 `tree` 关联，再全量构建查看首页和前置链接。
只有关系或进度变化时才修改计划，避免为了完成一次例行步骤而制造无意义变更。

## 笔记元信息

`notes/<slug>/meta.json` 保存标题、来源、状态和归类信息，正文写在同目录的 `note.md`。
新建命令会提供模板；修改已有笔记时保留仍然有效的信息，更新受本次修改影响的字段。

### 常用字段

| 字段 | 怎么填 |
|---|---|
| `title` | 页面标题，正文不再重复写一级标题 |
| `summary` | 说明这篇解决什么问题，用于首页摘要 |
| `sources` | 原始材料链接或源码路径与版本，按实际来源填写 |
| `status` | 新生成或实质改写的内容为 `draft`，不自行标成 `verified` |
| `topic` | 未挂知识树时的单一主题分组，例如「Flink」 |
| `tree` | 挂树时填写对应计划的 `topic` 和节点 `id` |
| `tags` / `eyebrow` | 可选标签和栏目说明，不用来替代主分组 |
| `generated` / `updated` / `model` | 按实际生成、修改时间和模型信息记录，不猜测 |
| `verified` | 人工核对日期，仅在有实际核对依据时填写 |

例如一篇未挂树的笔记，可以在模板上补这些字段：

```json
{
  "title": "一次请求怎样到达数据库",
  "summary": "沿请求路径理解客户端、服务和数据库的分工。",
  "topic": "服务请求",
  "status": "draft",
  "sources": ["原始材料链接或源码路径 @ commit"]
}
```

`status` 和 `sources` 用于提醒读者内容来自哪里、是否经过人工核对。
已有人工核对状态不作为本次新内容的背书，实质改写后需要重新核对。

### 主题与标签

未挂树的笔记按 `topic` 分组，`tags` 用于筛选。
一篇可以有多个标签，但主分组只填一个；组名应当让读者知道这一组在讲什么。
不规定每组固定篇数，按主题边界和实际浏览是否方便调整。

不填 `topic` 的笔记仍会显示，但落在「其他」组。
`tags[0]` 可能是随手添加的标签，`eyebrow` 也可能每篇不同，都不适合代替稳定的主分组。
历史统计见[实践记录](#实践记录)，它说明当时的选择，不作为长期阈值。

## 检查工具与排障

先确认工具读的是哪个工作区和产物，再检查问题。
本节说明现有行为与局限，不把退出码为零等同于内容正确。

### 检查范围和输出

| 命令 | 实际范围和输出 |
|---|---|
| `npm run check` | 校验笔记约定、计划引用、skill 与代码的一致性及 skill 渲染；不写入页面，不核实知识事实 |
| `npm run block -- <slug> <n>` | 单块渲染和截图，默认不打开浏览器；它的局部预览不更新 `dist/` |
| `npm run view -- <slug> --no-open` | 构建该篇的 `notes/<slug>/index.html`、`dist/<slug>.html`，同时更新首页；不打开浏览器 |
| `npm run build:standalone` | 全量重建笔记页面、单文件版和首页，适用于依赖与共享资源变更后的检查 |
| `npm run visual-check -- <slug>` | 检查指定 `dist/<slug>.html`；无参数时检查全部 `dist/` |
| `npm run skill` | 重建 `skill/` 的文档页面，默认不开浏览器；页面还需单独阅读和检查 |

`view` 不带 `--no-open` 会打开浏览器；`block` 和 `skill` 需要 `--open` 才打开。
单篇预览构建不能代替跨篇依赖验证，交付前用全量构建确认知识树和首页。

### 机器检查与人工检查

`visual-check` 默认在 1280px 宽页面运行，不替代窄屏、主题切换或交互操作检查。
它检查的对象和需要人工补看的内容分别是：

| 检查对象 | 能发现什么 | 还需要补看什么 |
|---|---|---|
| 积木容器和整页 | 子元素溢出、横向滚动 | 是否显得拥挤，阅读范围是否合适 |
| 支持的流程图和时序图 | SVG 缺失或绘制内容过少 | 图是否表达了完整机制，其他图形是否正确 |
| 流程边和标签 | 边穿无关节点、标签压节点或互相重叠 | 边含义是否真实，标签是否易混 |
| 支持块中的文字 | 文字墨迹互相重叠 | 看似分开但读成一句，或条件被裁掉 |
| 控件挂载块 | 部分上下块间隙不足 | 实际操作后状态、结果与重置是否正确 |

图有自己的校验器时，也要看它在整页中的嵌入效果；不能把两个工具的检查范围混为一谈。
检查器中的约 2px 重叠容差不是推荐文字间距。
曾有两个标签间隔 9px，检测通过，阅读时却像一句话。
把相邻标签连起来读，容易误合时调整间距、位置或冗余文字，不能直接删关键条件。
机器不核实知识事实，也不保证图的信息层次合适，这些按第 8 步继续验收。

### 不稳定结果和探针失败

| 结果 | 现有工具怎么报告 | 交付前怎么处理 |
|---|---|---|
| 首次检查干净 | 通过 | 继续检查内容与实际阅读 |
| 重试后才干净 | 报检查不稳定，脚本不阻塞 | 复核相关页面，记录复现条件 |
| 多次得到一致的新诊断 | 报新问题并阻塞 | 定位内容、布局或工具原因后修正 |
| 多次诊断不一致 | 报结果不稳定，脚本不阻塞 | 不能直接判为负载问题，也不能当作检查完成 |
| 未得到有效探针数据 | 报失败并阻塞 | 检查浏览器、资源、探针语法和运行异常 |

现有工具最多重试三次。每次的页名、问题集合和是否取得探针数据都要保留；
中途失败后才通过，不能只留下最后一次的零错误结论。
诊断不同只能说明结果不稳定。页面的异步状态、工具实现、运行环境或共享文件都可能有关，
要结合日志和复现证据判断。缺少证据时报告未确认，不推测一个根因后继续发布。

没有回数据时，先确认实际加载的文件、资源是否成功、探针是否完整和浏览器有没有运行异常。
命令退出成功、甚至原页面可见，都不能证明探针执行过。
重跑后取得有效结果，再核对问题位置；真实内容错误修内容，环境与工具失败分别定位。

### 已知问题基线

`tools/visual-baseline.json` 保存已经确认的工具限制，命中时仍报告，但不阻塞脚本。
新问题不在基线里时要处理；稳定检查确认条目已失效时，删除对应基线。

加入基线前，先用参考示例和正确用法确认缺少的能力，说明复现条件和影响。
内容错误、错误用法、尚未定位的问题或单纯不想修的布局，不作为新增基线的理由。

| 基线状态 | 要做的动作 |
|---|---|
| 新诊断未在基线中 | 定位并修复，不为了发布顺手新增豁免 |
| 稳定命中已知限制 | 说明局限，判断是否影响关键讲解，必要时换形状或拆图 |
| 稳定检查确认条目已失效 | 删除对应条目，再跑检查确认没有遗漏其他问题 |
| 所属页面结果不稳定或未取得数据 | 先取得可信结果，不凭未命中清理基线 |

基线中的条目不是内容正确的证明。关键讲解仍受影响时，第 8 步不能因为脚本不阻塞就验收通过。

### 共享临时文件

`visual-check` 曾使用固定的 `.vc-tmp.html`，而多个 worktree 共用软链的 `node_modules`。
会话 B 写入另一页后，会话 A 的浏览器读到它，导致另一篇的节点被记到当前篇头上。
这次问题通过给临时路径加 PID 解决，不能据此把所有测量异常都归因于负载。

写临时页面时使用每次运行独立的路径，并确认实际加载的文件与当前工作区一致。
`block` 目前仍用固定预览路径，共用 `node_modules` 时不要并行运行多个块预览；
这是现有局限，不把它写成所有工具已完成隔离。

## 实践记录

下面保留几次改进的来由。记录用于帮助判断，不把当时的数字和选择转成所有任务的固定要求。

### 内容范围在写作中调整

写 `sql_builder_v2` 方言说明时，逐方法对照中遇到 `getStringArrayRule`。
当时的代码阅读记录包括：

- 它不在 `SqlDialect` 接口里，而是在 `utils.ts` 按数据库类型分派。
- 有 ByteHouse、Doris、MySql 分支，还接受 `columnType` 来区分 array 和 string。
- 当时只有 `relation.ts` 一处调用，与接口里的 `jsonArrayContainsRule` 是两条并存路径。

这些是那次阅读的版本观察，引用当前行为时仍要回到源码核对；
也不能只因有 MySql 分支，就推断这段代码具体写于哪个历史阶段。
把两条机制塞进同一份方法列表会丢掉调用条件和分工，因此后来按问题拆出说明。
这里需要拆的是独立机制，不是因为某节超过固定段落数。

写 `notes/insight-dsl` 时，独立的设计和测试章节占了较多篇幅，请求处理主线反而缺少细节。
把依赖上下文的设计说明放回对应步骤后，过程更容易读懂。
这个例子提醒检查主线是否讲够，不表示每篇都应让机制章节最长。

### 数字与因果解释分别核实

一次接口说明写了 14 个方法，核对源码后是 17 个。
另一次把 `countSql` 的包装解释成展示列 LEFT JOIN 后需要去重，
但展示列不参与那条路径，包装本身也不会去重。
数量核对不能代替机制核实；因果解释要沿实际路径检查。

### 从定义到具体例子

解释软删除时，只写「标记删除机制」不容易建立认识。
可以展示示意记录 `{ id: 7, deleted_at: '2026-03-01 10:00:00' }`，
再说明普通删除是记录消失，软删除是记录仍在，查询需要相应过滤。
具体例子帮助理解，不要求每个已知词都重新配一整套定义。

### 图解与工具使用

一次漏图返工涉及程序与进程的关系、I/O 等待时的执行切换，以及轮询到中断的演进。
这些分别需要关系、过程和时间表达，不能因为不在主要卡点里就省略。

另一张整体图曾用淡化和压线隐藏拥挤，未解决必要路径难以追踪的问题。
聚焦本身可以帮助阅读，要检查它是否在辅助理解，还是让缺陷更难被发现。

试 archify 时曾没有打开参考示例，就认定它不支持分层带和嵌套框。
后来发现是用法和布局问题。判断工具限制前，需要先试它支持的正确用法。

### 主题分组的历史快照

2026-09-30 的一次统计中，11 篇未归类笔记有 51 个标签，去重后 37 个；
每篇平均 4.6 个标签，覆盖至少两篇的标签只有 11 个。
当时按标签分组容易让一篇出现在多个组里，按 `eyebrow` 分组也过于零散，因此使用单一 `topic`。
这些数字只是那次快照，长期规则是分组与筛选分工，不是固定的组大小。

### 缩短检查回路

一次笔记写完才集中查看，22 个积木用了 19 张截图，暴露 8 个问题。
把关键块写好就检查，可以较早发现需要重画的形状。
检查次数应与复杂度和风险相称，不规定每一块必须反复截图。

块预览曾每次打开标签页，给用户留下清理工作，后来改成默认只生成截图，人要看时加 `--open`。
高积木曾因截图高度写死而缺下半截，后来改成先量高度再截。
两次改进都来自可复现的问题，改完用实际页面验证，再同步命令说明。

### 把共性问题写回用法和检查

下面这些改进不仅修了当前页面，也需要让下一次使用者找到正确动作：

| 问题 | 保留下来的方法 |
|---|---|
| 围栏套围栏后，后文被吞成代码块 | 外层反引号数量大于内层；生成后检查渲染，不只看源文档 |
| 新积木加入后，块号和截图对应错误 | 清单从实际渲染器注册表推导，避免工具各手抄一份 |
| YAML 块标量缩进错，但错误没有直说原因 | 对照字段和内容缩进；保留能定位输入位置的诊断与正确例子 |
| 文档能写却不能渲染，直到生成才发现 | `check` 包含 skill 源文档渲染检查，改后仍要生成并看实际页面 |
| 图里文字互相压住，而构建通过 | 用文字碰撞检查定位，再看实际布局，语义层面不能只靠探针 |

围栏、缩进与积木字段的具体写法见 [`references/blocks.md`](references/blocks.md)。
改工具不只更新数字或一句「以后注意」，还要核对正确用法、例子、检查范围和实际故障是否已经修复。

## 资料查证

从原文补成一张图时，常常还需要补位置、归属、容量和机制。
这些信息应核实后再写进图和正文。

用户的原话：

> 你是从少量文字然后画一个丰富的图嘛，中间你是需要补充信息的。
> 然后这信息呢，如果你 100% 从你知识库里面肯定是对的，你就使用；
> 如果你不肯定的话，你就得使用联网搜索。

### 核实事实与适用条件

| 手上的信息 | 怎么处理 |
|---|---|
| 已经核实的一手资料或源码 | 据此使用，记录出处，并确认适用条件没有变化 |
| 只凭印象，想不起出处 | 先找资料或源码核实 |
| 数字、版本、上限、默认值 | 回资料或源码核对，说明相关平台、版本和配置 |
| 机制和因果解释 | 沿实际代码路径或一手说明核实；推断要说明依据，不能直接写成确定事实 |

记得一个文件名，不等于核实了当前版本的行为。
例如 `runtime/stack.go` 中的 `stackMin` 是什么、哪些条件影响栈分配，需要读对应实现。
交付前按[第 8 步](#第-8-步-交付前检查)检查事实数字、示意数据和机制依据。

### 怎么查：用什么语言、信谁、用哪个工具

先找与问题对应的原始资料，再核对具体断言，最后记录出处和适用条件。

#### 搜索语言

技术标准、机制和报错优先用英文关键词查，便于找到内核文档、RFC、官方文档和源码。
需要找中文线索时，中英文一起搜；产品行为以该产品的官方资料为准，不按语言判断可信度。

| 场景 | 搜索起点 |
|---|---|
| 原理、标准、规范 | 英文术语，查标准或官方说明 |
| 数字、默认值、版本行为 | 术语加平台和版本，查官方资料或源码 |
| 报错信息 | 保留原始报错文本，并加产品或组件名 |
| 国内产品或中文社区约定 | 从对应的官方中文文档或原始讨论查起 |

不知道英文术语时，可以先搜「中文名 英文」，确认对应词后再深入。
例如先找到「快表」对应 TLB，再查 `TLB flush context switch`。

#### 行文术语

正文沿用读者手上材料的术语，首次出现时按需要附上英文，方便与资料对应。
例如「快表（TLB）」「只读层（read-only layer）」。
如果原文术语不准确，说明差异后统一用词，不直接换成读者不熟悉的一套名称。

#### 来源与限定条件

| 来源 | 怎么用 |
|---|---|
| 标准、官方文档、对应版本源码 | 作为事实依据，核对适用范围 |
| 维护者的 issue 或讨论 | 看是否有确认结论、对应版本和可复现证据，区分讨论中的猜测 |
| 博客、教程、问答、AI 回答 | 用来找线索和关键词，重要断言回原始资料核实 |

来源是否可靠，要看发布者、出处和证据，不能根据句子有没有限定条件来判断它是不是一手。
找到资料后仍要检查条件是否在转述中被省略。

例如查 OverlayFS 的合并规则时，曾参考的材料只说「上层盖住下层」，容易被理解成上层目录完全遮住下层目录。
[内核文档](https://docs.kernel.org/filesystems/overlayfs.html#directories)写的是：

> If a given name appears in both upper and lower filesystems and refers to a non-directory in either, then the lower object is hidden.

上下层同名且任一边不是目录时，下层对象被隐藏；两边都是目录时，通常合并目录条目。
不透明目录等例外也要按文档核对。画图时不能只留下「上层覆盖下层」这个概括。

#### 工具分工

| 工具 | 什么时候用 |
|---|---|
| `web_search` | 还没有找到合适资料时，用 2~4 个不同角度的 query 找来源和线索 |
| `source_check` | 有具体断言需要核实，用 passage 级引文对照证据 |
| `fetch_content` | 已经知道是哪一页，直接读内容；也可以用 `mode: answer` 只根据该页回答问题 |

核实后的出处可以写进笔记的 `sources`，让读者能回到原始资料。

### 控件里要写强调文字时，用 `richText`

处理的，控件跑在浏览器里拿不到它 —— 所以 `app.js` 里有一份最小的 `richText(host, text)`。

```js
richText(el('p', 'my-note'), '这一步 ==很关键==，注意 `read()` 的返回值');
```

==不写它就直接 `textContent` 的话，页面上会字面显示 `==很关键==`。==
它只认那三种标记，别往里加东西 —— 两边逻辑越像，越容易漂移。

### 机制图的具体画法

讲调度、流转或加工过程时，先确定要解释哪一段路径，再把参与对象、状态和结果画出来。

用户曾描述自己的需要：

> 我需要一个丰富的图去理解它，落实到一些具体的结构上，
> 让我感受到「原来它现实中是这样经过的」，在硬件上它是这样表现的。

#### 画到读者熟悉的对象

图要覆盖正在解释的关键过程，并接到读者能理解的对象或结果。
如果读者还不知道「少量线程」如何执行任务，就继续画到内核调度和 CPU 核；
如果这些前提已经讲清楚，这一节可以从已知对象开始，不必每张图都追到硬件。

以任务调度为例，可以沿下面的路径检查缺口：

```text
任务 → 在哪排队 → 谁取出任务 → 交给系统线程 → 内核调度到 CPU 核 → 运行结果
```

熟悉的对象取决于读者背景，也包括前文已经解释过的概念：

| 起点或落点 | 例子 |
|---|---|
| 物理部件 | CPU 核、内存、磁盘、网卡 |
| 生活经验 | 用饭堂窗口类比并行处理，并说明只是类比 |
| 读者用过的东西 | git 仓库中的 `.git` 目录 |
| 前文定义过的概念 | 前面讲过页表，后文可以从页表继续解释 |

#### 画出队列中的内容和容量

需要解释排队时，用格子或条目展示当前有哪些任务、取出顺序是什么，
以及满了或空了会发生什么。容量影响结果时，标出容量和超出后的处理。

示意图中画几格不等于实现中就有几格，示意容量要标明。
要介绍真实容量时先查证；实现支持可变容量时，再按实际行为说明。

#### 把路径连起来

让读者能从起点沿连线走到结果，连线上的标签说明传递了什么、发生了什么动作。
例如任务如何交给线程、线程如何经过内核调度在 CPU 核上运行。
只在框旁写 `submit` 或「多路复用」，还不足以说明这些对象怎么配合。

#### 在图上标出状态

哪个任务在运行、哪个在等待、哪个核暂时空闲，用标签和颜色、虚实等一起区分。
结果应能从图上看见，图注补充它在什么条件下成立。

#### 标清层次和边界

涉及用户态、内核态和硬件时，标出对象各在哪一层，以及跨层时发生的操作，
例如系统调用或中断。不要把分层背景当成完整路径，连接仍要画清楚。

#### 沿图讲一遍具体过程

选一个具体输入，沿着图说明它在哪里排队、谁取出它、谁执行，以及结果在哪里出现。
哪一步在图上找不到，就补哪一步；遇到未解释的名词，先补必要的概念。

例如，示意场景中有六个可运行任务、三条系统线程和六个 CPU 核。
在某个时刻，三条线程分别在三个核上执行任务，另外三个核暂时空闲。
图上要能找到这些任务、线程和核，并区分这一时刻的运行与等待状态。
这种示意不表示真实机器的其他任务也都停止了。

现有积木缺少所需能力时，按原则 ⑦ 组合或扩展。例如连续地址空间可以用 `memmap`，
不要因为选定了流程积木，就省略需要的容量、位置和共享关系。

#### 根据内容调整画布

几个节点铺在很宽的画布上时，先检查是否缺了理解所需的位置、容量、方向或状态。
缺信息就补；信息已经足够，就收紧画布和间距，不为填满空白而增加内容。

同类对象的大小、归属或状态影响结果时，在图上区分这些差异。
一句话能概括一张图，不表示图没有价值；要看它有没有帮助读者找到关系。
如果图只是把同一句话换成一个框，改成简短说明即可。

### 图的视觉规范

先检查图的结构和关系，再调整配色。

#### ① 节点用语义类型，不要纯文字盒子

用 `kind` 标出节点是什么（`backend` / `database` / `cloud` / `security` …）——
它会自动带图标和配色。==读者看图标就知道这是数据库还是服务，不用读文字。==

#### ② 用区域框表达归属

几个节点属于同一个 VPC / 同一个部署单元 / 同一层？用 `groups` 圈起来。

```callout
tone: violet
icon: 💡
text: |
  ==「结构单一」的最大来源就是没有区域框。==
  平铺的节点看不出「谁和谁是一伙的」，读者要自己在脑子里分组。
```

#### ③ 开背景网格

`grid: true`。给图「工程图纸」的质感，也让大片空白不那么飘。

#### ④ 边要有语义

- 同步实线、异步虚线 —— 别混用
- 关键路径用 `tone` 上色（比如绿色的 HTTPS、红色的鉴权）
- **每条边都该有标签**（协议、动作、方向），除非两端完全自明

#### ⑤ 文字不许互相压

用户点名过的一条，原话：

> 你在画图的时候要注意文字互相重叠的情况。
> 线可能你判断线的重叠比较有难度，==但判断文字重叠应该比较轻松，对吧？==
> 尽量不要出现文字被挡到的情况。

**为什么单拎出来**：字被压住不会报错，**字还在，只是读不通**。
它比「图没画出来」隐蔽得多 —— 出图看着是成功的，只是有一行字废了。

**最常见的成因只有一条：标签比它所在的那条缝还宽。**

```
   ┌──────────┐            ┌──────────┐
   │  节点 A   │   这条缝    │  节点 B   │
   └──────────┘            └──────────┘
        └──── 标签比缝宽就压到框上 ────┘
```

`flow` 里还有一种固定搭配会撞：**群组框的标签画在框的左上角，
而边标签默认落在那条缝的水平中点** —— 缝一窄，两个标签就叠在一起。

修法按优先级：

| 修法 | 说明 |
|---|---|
| 调节点位置 | 让缝变宽（改 `row`，或把节点拆开） |
| **`edges[].labelDx` / `labelDy`** | ==手动把边标签挪开。工具算不出「那里已经有群组标签了」，但作者一眼就知道该往哪挪== |
| 把标签改短 | 最后手段。**别为了塞下标签而把话说残** |

```callout
tone: green
icon: 🤖
text: |
  **这条已经进了探针，不用靠眼睛。**

  `npm run visual-check` 会报 `文字压文字：「…」↔「…」（重叠 Npx）`。
  它用 `Range` 取每个**文本节点自己的墨迹矩形**（不是父元素的盒子）——
  父盒子带 padding、跨行时是一整块，都会把「挨着」误判成「压着」。

  ++改完图一定要跑它。==构建通过 ≠ 画对了，这条踩过五次。==++
```

```callout
tone: amber
icon: ⚖
text: |
  **不查什么：文字被线 / 边框穿过。**

  那要判断「这条线是不是本来就应该在那儿」—— 机器判不了，
  人工排查的成本也高于收益（用户原话：==「如果是线和文字重叠，排查比较费时间的话，就不用管了」==）。

  所以探针只查**文字 vs 文字**：这条能机械判定，而且它才是真的读不通。
```

```callout
tone: green
icon: ✅
text: |
  这套规范学自 `archify` skill（`~/.agents/skills/archify`）。
  它的图值得当参照 —— 需要更复杂的图时，可以去读它的 `SKILL.md` 和 examples。
```

### 结构化图：调用 archify skill

archify 是一套完整的图渲染系统，能力**超出**我们自己的积木：节点的**语义类型**
（声明是 database / messagebus / cloud，自动带图标、配色和图例）、**精确区域框**、
**真边路由**，以及一个会量文字宽度、检测碰撞的校验器。

我们自己的积木是「半自动」的 —— 你给 `row`，它排位置，不做标签避让和碰撞检测。
两套工具各管一段，**按图的形状选**。

#### 它能画 5 种图

由 spec 里的 `diagram_type` 决定（`tools/archify.mjs` 会自动读）：

| diagram_type | 画什么 | 结构数组 |
|---|---|---|
| `architecture` | 系统组成、部署拓扑、依赖关系 | components · boundaries · connections |
| `workflow` | 跨角色的流程 | lanes · phases · mainPath · nodes · edges |
| `sequence` | 调用链、握手、时序 | participants · messages · activations |
| `dataflow` | 数据流水线 | stages · nodes · flows |
| `lifecycle` | 状态机、生命周期 | lanes · states · transitions |

写法参考 `~/.agents/skills/archify/examples/*.<type>.json`。

#### 什么时候该调 archify

| 用 archify | 用我们自己的积木 |
|---|---|
| 有**区域/边界**要表达归属（「这几个在同一个 VPC」） | 没有归属关系，就是一根轴或一列卡片 |
| 节点有**语义类型**（这是数据库、那是队列） | 节点就是纯文字盒子 |
| 需要**图例** | 不需要图例 |
| 形状是 DAG / 状态机 / 泳道 / 时序 / 阶段流水线 | 形状是时间轴 / 状态对照 / 两列匹配 / 行列表 |
| 要作为**独立图**交付、反复引用 | 图文混排成一节，要跟着页面换肤和重排 |

#### 画整体图（原则 ② 的做法层）

什么时候需要整体图，见[原则 ②](#原则-②-用整体图连接相关概念)。这里说明工具和布局。

##### 一 · 安排位置和间距

整体图可以用 `pos` 手工安排位置。相邻零件横向约 200px、纵向 100~150px 可以作为起点，
再按标签长度和连线调整。零件少、布局规整时也可以用网格模式。

```json
{ "components": [
    { "id": "clients", "pos": [38, 300],  "size": [150, 56] },
    { "id": "edge",    "pos": [230, 300], "size": [150, 56] },
    { "id": "gateway", "pos": [430, 300], "size": [150, 56] } ] }
```

参考 `examples/production-deployment.architecture.json`（12 零件 / 4 框，
就是这个尺寸感）。**注意它顶层没有 `layout`。**

##### 二 · 按关系选择字段

| 关系 | 用什么 | 怎么处理 |
|---|---|---|
| 分类 | `boundaries` 包住同类节点 | 作为分区背景；分类本身是主题时可以突出 |
| 包含 | 嵌套 `boundaries` | 用成员集合表达包含，外层框按成员范围生成 |
| 数量与共享 | 在 `connections` 的 `label` 中标基数 | 标清两端分别对应几个对象，共享对象只画一份 |
| 流动 | `connections` | 标出传递的内容或动作；跨行时按路径显式设置 `fromSide` / `toSide` |

同一类对象有多个实例时，可以用一个代表节点加基数表达，避免重复画同一种关系。
如果需要比较各实例的不同状态，就分别画实例和必要的连接，不把它们合成一条无区别的边。

##### 三 · 检查主次和密度

- 每张图回答一个主要问题，其他关系作为背景或辅助说明，见原则 ②。
- 元素接近 12~15 个时检查密度，还要看标签长度、连线和实际阅读路径。
- 同时回答多个问题，或追踪路径时要反复绕过无关对象，就考虑拆图；不按元素数或边的类型机械拆分。

##### 四 · 拆完之后，先看它自己的校验过不过

`tools/archify.mjs` 会先跑 `archify validate`，不过就不出图。它报的
`edge-through-node` / `proper-crossing` / `micro-segment` 是**硬门**，
不是风格建议 —— 见下一节。

#### 它的硬边界（踩过）

- **边不能穿过无关节点。** archify 直接报
  `crosses component "xxx" (unrelated to this relationship)`，==它不会帮你绕过去==。
  遇到这种拓扑只能拆图、改布局、或手填 `route`/`via` 航点。
- **竖长的分层图别用 `architecture`，用 `lane-stack`。**
  `.archfig svg { width: 100% }` 会把 SVG 拉满容器宽度 ——
  一张 745×1483 的「五层堆叠」图放进 1280 宽的正文里，会变成 **2549px 高**，
  文字被放大到很夸张。==archify 适合宽高比接近 1:1 的拓扑图，不适合一列到底的层叠图。==

  这次画「谁能看见谁」（CPU / 内核 / 进程 / runtime / G 五层）就撞上了，
  改用 `lane-stack` 一次过 —— 它本来就是为「一层接一层」设计的，横着排，不拉高。
- **`architecture` 有两种排法：写 `layout`（网格），或者给每个组件写 `pos`。**
  **两条路二选一**，都不写才报错：

  `Component "x" must include pos [x, y] when layout.mode is omitted`

  ```compare
  first: 排法
  head: [怎么写, 什么时候用]
  rows:
    - 网格: ["顶层写 `layout`，组件只写 `row` / `col`", "零件少、排得规整"]
    - "**手工坐标**": ["顶层**不写** `layout`，每个组件写 `pos: [x, y]`", "==整体图用这个== —— 官方 `examples/production-deployment.architecture.json` 就是这么写的"]
  ```

  !!这条原来写的是「**必须**写 `layout`」，是错的 —— 而且正是它把我带到沟里：!!
  我照它用网格模式去排一张密集的整体图，挤成一团、校验不过，
  然后得出「archify 画不了整体图」的结论。==其实该走的是另一条路。==
- **组件尺寸是每个显式声明的**（默认 120×60），不随 `layout.cellW` 变。
  标签长了要么裁文案，要么给它加 `size`。
- **`label` / `sublabel` 里不能写我们的行内标记。** archify 不解析 `==` `**` `++`，
  它会**原样显示**成 `**它不干活**`。它只认自己的 `meta.legend`。
  ==写进去之前先把标记去掉。==
- **跨行的边要显式写 `fromSide: "bottom"` / `toSide: "top"`。**
  上下相邻两行的节点，自动推断可能给出 `fromSide: "left"`，然后报
  `first segment does not honor inferred fromSide "left"` ——
  ==错误里说的方向和你看到的走向对不上，直接写上 bottom/top 最省事。==
- **`boundaries` 里的 `kind` 只有 `region` 和 `security-group` 两种**，
  而 `security-group` 画出来是**红色虚线框**。红色在别处一律表示「出事了」，
  知识图里没有这个含义，++默认用 `region`++。
- **边有几何下限**：微段短于 8px、两条边挤在同一条走廊里，都会判失败。
- **嵌套的 boundary，两层标签会叠在一起。** 外框和内框包的是同一批零件时，
  它们的上边界只差 `pad 之差`。外框的 pad 又被限制在 **34px 左右**
  —— 再大就报 `extends outside the viewBox`，而且**加大 `meta.viewBox` 不管用**
  （它按成员的实际footprint 判，不看你写的 viewBox）。

  ==出路的反直觉之处：把**内框**的 pad 收紧（`pad: 10`），而不是把外框撑大。==
  这样两层标签能差出 24px 左右，够放下两行字。
- 产出是**静态 SVG**，不跟着容器宽度重排。
- **`lifecycle` 的 lane 语义是写死的**，别拿它画通用状态机。
  `render-lifecycle.mjs` 里写死了：`lane: main` → 上排「阶段带」（5 列，y=126）、
  `lane: terminal` → 下排「结局带」（3 列，y=450）、**其它所有 lane 全挤在中间那条
  「事件带」**（只有 3 列，y=278，靠 `yOffset` 上下分开）。
  几何常量也是死的（`phaseXs: [94,248,402,556,710]`、`eventXs: [402,556,710]`）。

  ==拿「进程七态」试过：四个状态要横排、还要跨三行画挂起，label 碰撞报了二十几条。==
  **状态机用 `flow` + `shape: pill`，别用 `lifecycle`。**
  `lifecycle` 留给「一条主路径 + 几个中断 + 几个结局」那种形状。

#### 怎么调（已封装好）

```bash
# 1. 写 archify 的 JSON spec 放 archify/ 目录
#    参考 ~/.agents/skills/archify/examples/*.<type>.json（5 种类型都有例子）
# 2. 生成并抠图
node tools/archify.mjs archify/<名字>.json <名字>
# 3. 在 note.md 里用 arch 积木
```

```text
svg: <名字>              # 必填，对应 assets/arch/<名字>.svg
caption: 这张图说明什么    # 可选，图注
```

**抠出来的 SVG 自带「聚焦 + 关系追踪」**（点节点只看它和它连出去的关系）——
因为 archify 的 SVG 里留了 `data-node-id` / `data-edge-from` / `data-edge-to`，
`app.js` 按属性筛一遍就行。键盘也能用（Enter / Esc）。

**`tools/archify.mjs` 做了三件事**（这三件事不做会踩坑）：

1. 调 archify 的 `validate` + `deliver`（校验不过会直接报出诊断）
2. **只抠 SVG**（archify 的 HTML 有 600KB，但 SVG 本体只有 ~20KB）
3. **给它的 CSS 变量加 `--af-` 前缀** ——
   ==archify 在 `:root` 定义了 32 个变量，名字和我们完全一样（`--bg` / `--text` / `--panel`），
   直接嵌会把我们整页变成深色。==

两边都用 `data-theme` 属性，所以**深浅色天然同步**，不用额外处理。

#### archify 的校验值不值得用

**值得，而且这是它最值钱的部分。** 它会精确告诉你：

```text
Label "用户认证与鉴权流程" (~132px) is wider than component "gateway" (120px)
Label "请求" overlaps component "gateway"
  label rect: [286, 120, 48, 14]
  component "gateway" rect: [250, 80, 120, 60]
  Suggested fix: labelAt [310, 154] or labelDy +24
```

它**测量了文字宽度**、**检测了碰撞**、**给了具体坐标**。我们的积木完全不做这些。

## 版面与样式

### 改 theme.css，不要改单篇笔记

所有页面共用 `assets/theme.css` + `assets/blocks.css` + `assets/app.js`。
遇到这些症状，**改共享文件，一次全站生效**：

| 症状 | 改哪 |
|---|---|
| 屏幕利用率低 / 留白太多 | `theme.css` 的 `--shell` / `--prose` / `--gutter` |
| 某个积木在窄屏塌得不好 | `blocks.css` 里那个积木的 `@media` |
| 目录 / 交互别扭 | `app.js` + `lib/page.mjs` |
| 颜色不对 | `theme.css` 的 token |

**不要为了某一篇笔记在 `note.md` 里塞 `<style>`** —— 那是把全局问题当局部问题修，
下一篇还得再修一遍。

### 版面原则：文字窄，图宽

屏幕越宽，**不要把文字拉长**（长行伤可读性），而是把多出来的宽度给图。

`theme.css` 里三层控制：

- `--prose`（880px）管**文字元素**（`p` / `h2` / `h3` / `ul` / `.callout` / `.quiz`）
- `main` 的 `max-width`（1280px）管**整列上限**，防 4K 屏上积木被拉飞
- **积木不受 `--prose` 限制**，自动用满整列

判断一个新积木该不该限宽：**它主要是文字还是图形？** 文字限，图形不限。

### 行内强调与颜色：别让一种标记承担所有重点

| 写法 | 语义 | 颜色 |
|---|---|---|
| `==文字==` | 关键结论 / 最该记住的一句 | 蓝 |
| `!!文字!!` | 坑 / 反直觉 / 注意 | 橙 |
| `++文字++` | 正确做法 / 推荐 | 绿 |
| `**文字**` | 句子内的重音（降级用） | 加粗不变色 |

**一屏之内不要超过 3 个 `==`** —— 到处都是重点等于没有重点。
写完后扫一眼：如果整页加粗密密麻麻，说明该用彩色标记做取舍了。

#### `callout` 的颜色也一样 —— 别让红色承担所有重点

```callout
tone: red
icon: ⚠
text: |
  ==**这份 skill 自己踩过这个坑。**==

  有一轮自检时统计：48 个 `callout` 里 **36 个是红/橙**（75%）。
  然后逐条看内容 —— 红的那 20 个里**有一半根本不是警告**：

  | 写的内容 | 它其实是 |
  |---|---|
  | 「六层不是某个项目的专属结构」 | **结论** |
  | 「构建产物是全量的」 | **事实** |
  | 「`npm run check` 是全仓库的」 | **事实** |
  | 「多个会话共用一个工作目录才是根因」 | **诊断** |
  | 「每次交付完回头问一遍」 | **方法** |
  | 「优先点名 add」 | **规则** |

  ++红色一多，「这里真的会出事」就没人当回事了。++
```

**按这句话选颜色：这条是「会出错」，还是只是「值得知道」？**

| tone | 什么时候用 | 判据 |
|---|---|---|
| `red` | **真的会出事** | 会丢数据 / 会被拦 / 会静默出错 |
| `amber` | 注意、已知局限、容易忽略的规则 | 不遵守会返工，但不会立刻炸 |
| `violet` | **结论 / 洞察**（「所以…」） | 读到这里该记住的一句话 |
| `green` | 正确做法 / 已验证 | 照着做就对了 |
| `blue` | 入口提示（「先读第 0 步」这类导航） | 很少用 |
| `muted` | 纯事实陈述 | 不劝你做任何事 |

> 拿不准时问自己：**如果读者跳过这条，会发生什么？**
> 答「没影响，只是不知道」→ 不配红。

### 代码块：**先分行，再谈分色**

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==**粘一段单行 SQL 进笔记，等于没写。**==

  子句、权限、条件全挤在一行，读者要在脑子里自己断句。
  这跟「把图挤成一团」是同一种偷懒 —— 只是不容易被截图抓出来。
```

**两条规矩，按优先级：**

#### ① 分行 —— 一个子句一行，嵌套的缩进

```compare
first: 写法
head: [读者要做什么, 什么时候必须分行]
rows:
  - 一整行塞完:
      - { text: "在脑子里断句、数括号、找 AND 在哪", tone: red }
      - "永远不要。除非真的只有 `SELECT 1` 这么短"
  - 一个子句一行:
      - { text: "从上往下读，一眼看出结构", tone: green }
      - "SELECT / FROM / WHERE / GROUP BY 各占一行"
  - 嵌套再缩进:
      - { text: "子查询、AND 续行看层级", tone: green }
      - "子查询整体缩进两格；`AND` 接在下一行、再缩两格"
```

**实测对照**（`notes/insight-dsl` 那个交互）：

```text
❌ 挤成一行（真编译器就是这么输出的）
SELECT COUNT(*) AS `count` FROM (SELECT `u`.`uid` AS `uid` FROM `user_portraits_wide` AS `u` WHERE `u`.`staff_id` = 101 AND (TIMESTAMPDIFF(YEAR, `u`.`birthday`, CURRENT_DATE()) >= 18)) AS `t`

✅ 按子句分行
SELECT COUNT(*) AS `count`
FROM (
  SELECT `u`.`uid` AS `uid`
  FROM `user_portraits_wide` AS `u`
  WHERE `u`.`staff_id` = 101
    AND (TIMESTAMPDIFF(YEAR, `u`.`birthday`, CURRENT_DATE()) >= 18)
) AS `t`
```

```callout
tone: amber
icon: ⚠
text: |
  **但如果原文就是这样（比如真编译器的输出），分行之后要说明。**

  ==读者会以为「真代码就长这样」。==

  正确做法是分行展示 + 一句注明：

  > 语句内容跟真输出逐字相同；真输出是一整行（省字节），这里换了行。
  > **换行只是排版，不改变语义 —— SQL 本来就不看换行。**
```

#### ② 分色 —— 分的是**来源**，不是语法

```callout
tone: violet
icon: 💡
quote: true
text: |
  ==**不要做语法高亮（SELECT 蓝、字符串橙）—— 那是编辑器的事，不是笔记的事。**==

  笔记里分色的价值在另一件事：**一段代码里混了多个「来源」时，
  用颜色把来源分开。**
```

**照 `notes/insight-dsl` 那个交互的做法**：

```compare
first: 颜色
head: [代表什么, 为什么值得一色]
rows:
  - 琥珀:
      - "**权限** —— 演员身份决定的"
      - "它不是用户圈出来的，==读者最容易把它当成条件的一部分== "
  - 白（默认）:
      - "**用户圈的条件** —— 界面上点出来的"
      - "主体，不需要额外颜色"
  - 紫:
      - "**派生表达式** —— 逻辑字段到物理列的变换"
      - "`age` → `TIMESTAMPDIFF(YEAR, birthday, ...)`，==这是最反直觉的一层=="
```

**判据**：一段代码里如果有 **2 个以上来源不同**的东西混在一起，
分色讲得清；只有一种来源就别上色（纯噪音）。

#### ③ 做成交互时，分色是**自动**的

那个演示不是手写的 HTML —— 它按语义片段拼出来：

```js
[['SELECT ', 'kw'], ['`u`.`uid`', 'cond'], ['WHERE ', 'kw'], ['`u`.`staff_id` = 101', 'perm']]
//                    ↑ 默认色            ↑ 关键字          ↑ 琥珀（权限）
```

所以**换身份、勾条件、切 include/exclude 时颜色一直是对的**，
不需要作者维护两套东西。

> 写这类 demo 时：**先想清楚有几种语义来源，再定颜色。**
> 不要先挑颜色再往里塞内容。

```bash
npm run visual-check
```

用无头浏览器真的去量每个积木容器：子元素有没有溢出边界、有没有横向滚动。

#### 七次踩坑记录

| 症状 | 根因 |
|---|---|
| 图整体错位，节点被推下去 414px | 用脚本「**区间替换**」改 CSS，把区间里的 `.flowd-svg { position: absolute }` 一起删了 |
| 区域框溢出到上面的段落里 | **设计缺陷**：框比节点大一圈，第一行就是被分组节点时框顶跑到容器外 |
| 加 padding 后所有图错位 | **坐标系不统一**：节点坐标相对 `.flowd-grid`，SVG/区域框相对 `.flowd` |
| 两个区域框重叠 | **每行独立居中** → 同组节点跨行会水平错位，两组包围盒几乎相接，框一往外扩就重叠 |
| `cards` 里的 `<pre>` 撑破容器 | **grid item 默认 `min-width: auto`**，不会缩到内容宽度以下 |
| **切换深浅色后，某个色块停在旧主题的颜色上** | `transition: background` + `background: color-mix(...)` —— 见下面第六次 |
| **点了按钮再截图，样式还是点击前的** | `--virtual-time-budget` 下过渡不推进 —— 见下面第七次 |

#### 第七次：`--virtual-time-budget` 下 CSS 过渡不会被推进 —— 截图会骗你

````callout
tone: red
icon: 📸
text: |
  **点一下控件再截图，截到的是点击前的样式 —— 而 DOM 里 class 已经是对的。**

  实测：一个「选中态」按钮。点第二个之后，
  ==class 和计算样式完全对调== —— 掉了 `.on` 的那个显示成选中态，加上 `.on` 的显示成未选中。

  ```
  0 [nw-seg-btn]     bg=rgb(234,241,255)   ← 看起来是选中的，其实不是
  1 [nw-seg-btn on]  bg=rgb(255,255,255)   ← 明明是选中的
  ```
````

**根因**：所有无头截图都跑在 `--virtual-time-budget` 下，而**那个模式下 CSS 过渡（transition）不会随虚拟时间推进** ——
元素停在过渡的起点，再也不会动。

**怎么确认是它**：注入 `* { transition: none !important }` 之后再读一次计算样式，样式立刻归位。
上面那个例子，关掉过渡后两个按钮的颜色正好对调回来。

**已经修在工具里**：`tools/block.mjs` 生成的预览页现在带一条

```css
*, *::before, *::after { transition: none !important; animation: none !important; }
```

==过渡只在值**改变**时触发，初次渲染不受影响== —— 所以量静态布局的 `visual-check` 基本不受影响，
只有「点一下再截图」这条路会踩到。

**自己写截图脚本时也要记得加这条**，否则会像我一样，花时间去找一个根本不存在的 CSS bug。

#### 第五次：archify 的共用 CSS 被削薄

```callout
tone: red
icon: 🌗
text: |
  **写过 `transition: background` 的元素，只要它的背景是 `color-mix(...)`，
  换主题时颜色会卡在旧主题上。**

  不是过渡一下就到了 —— 是**永远不更新**，直到这个元素因为别的原因重新布局。

  ==这个 bug 只在切主题时出现，`npm run check` / `visual-check` 全是绿的。==
  （它们不切主题，只量布局。）
```

**真实经过**（写「三种 IPC 数据流」那个控件时）：

| | |
|---|---|
| 症状 | 浅色模式下，未激活的格子渲染成深色；但同一张卡片的外壳是白的 |
| 第一反应 | 以为变量作用域错了 —— 打印 `--surface-2`，发现是 `#f2f4f7`（正确的浅色） |
| 打印元素的实际值 | `oklab(0.283 0.003 -0.029)` —— 一个**暗色**，和变量对不上 |
| 排除法 | 把 `transition: background .2s` 删掉，**立刻正确**（`rgb(234,231,246)`，正是手算出来的淡紫） |

**根因**：元素在 `data-theme` 还是 `dark` 时完成首次渲染，主题切成 `light` 后
背景值要变，但 Chrome 对**两个 `color-mix()` 计算值之间的插值**处理不了，
于是停在起点。改成普通 `var(--x)` 的颜色不会中招（那是两个具体颜色之间的插值）。

++规矩：给「背景是 `color-mix`」的元素写 transition 时，只写具体属性，不写 `background`、更不要写 `all`。++

```css
/* ❌ 换主题会卡住 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent); transition: .18s; }

/* ✅ 只过渡真正会动的东西 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent);
        transition: color .18s, box-shadow .18s; }
```

**查法**（一条命令扫全站）：

```bash
python3 - <<'EOF'
import re, pathlib
css = pathlib.Path('assets/blocks.css').read_text()
for sel, body in re.findall(r'([^{}]+)\{([^}]*)\}', css):
    if 'transition' not in body: continue
    if not any('color-mix' in l for l in body.split(';') if l.strip().startswith('background')): continue
    t = re.search(r'transition:\s*([^;]+)', body).group(1).strip()
    if 'background' in t or re.fullmatch(r'\.?\d+(\.\d+)?(m?s)?', t):
        print(sel.strip()[:60], '→', t)
EOF
```

==写新控件时顺手跑一次，比等用户在浅色模式下发现便宜得多。==

#### 第五次：archify 的共用 CSS 被削薄

```callout
tone: red
icon: ⚠
text: |
  ==`assets/archify-embed.css` 是全站共用的，但它是**每次跑 archify 时重新导出**的。==

  导出时会按「`assets/arch/` 下所有 SVG 用到的 class」筛规则。
  一旦筛漏，图里的元素就掉样式 —— 而且**构建、visual-check 全是绿的**。
```

**真实事故**：CSS 丢了 `.a-dashed` / `.a-security`（少 `fill: none`），
图里的虚线边被**填成黑色三角形**，压在节点上。

| 症状 | 根因 |
|---|---|
| 图里出现大块黑色三角/色块 | `archify-embed.css` 缺了某个 class 的规则，`fill` 回退成黑色 |
| 控件里几块**贴在一起** | `gap` 写在某个 wrapper 上，而控件**没套它** —— 直接 append 到 `[data-mount]` 上了 |

````callout

  ```bash

  ```

  `npm run check` 有专门检查（对比 SVG 用到的 class 和 CSS 里定义的 class），
````

#### 改共享文件的四条硬规矩

1. **改一条 CSS 规则就替换那一条，别用大区间。** 非要大改，改完 grep 一遍原来的选择器。
2. **绝对定位的装饰元素要考虑「会不会超出容器」。** 加了就配 padding。
3. **坐标计算必须统一参照系。** 容器一有 padding，相对不同父元素量的坐标就会错开。
4. **放进 grid / flex 的元素要设 `min-width: 0`**，否则内容会把容器撑破。
5. **`background: color-mix(...)` 的元素，别写 `transition: background` 或 `transition: .2s`。**
   换主题时 Chrome 插值不了两个 `color-mix` 计算值，颜色会卡在旧主题上 ——
   `visual-check` 抓不到（它不切主题）。详见上面「第六次」。

## 怎么写：笔记正文和 skill 文档都适用

这一节是给**写文字**的，不是给排版的。起因是用户看过一版 skill 之后说：

> 有些语句充满了 AI 味道，我希望所有的语句都平实、自然、连贯一些。

下面五条用于改稿，笔记正文和 skill 文档都可以对照着看。

### 一、别先甩一个判断，再用破折号复述一遍

这是最像 AI 的一种句式：先给一个大的、抽象的判断，然后破折号，
再把同一个意思用具体一点的话说一遍。两句话说的是同一件事。

```compare
first: 写法
head: [例子]
rows:
  - ❌ 改前: ["==本体里有一类图，它给的理解是别的什么都替代不了的 —— 把一堆东西和它们的关系一次铺开。=="]
  - ✅ 改后: ["有的问题，把零件一个一个讲是讲不清楚的。\n比如「容器到底是什么」。它不是一个对象 —— 内核里没有叫「容器」的东西。"]
```

改后的版本直接从具体的东西开始（「容器到底是什么」），读者自己就能得出那个大判断。
==把结论留给读者，比替他下结论更可信。==

### 二、删掉空转的过渡句

「这一条接着说下一层」「下面我们来看」「值得一提的是」这类话不承载信息，
只是在标记「我要换话题了」。**直接换话题就行。**

```compare
first: 写法
head: [例子]
rows:
  - ❌ 改前: ["原则 ① 立的是「图是这个产品的本体」。这一条接着说下一层："]
  - ✅ 改后: ["（整句删掉）"]
```

### 三、去掉没依据的绝对化

「唯一」「全都」「永远」「根本」「只能」—— 这些词让句子更有力，但**多半不准**，
而且读者一旦发现反例，整篇的可信度都掉。

```compare
first: 写法
head: [例子]
rows:
  - ❌ 改前: ["这是它**唯一**的强项", "后者**只能**由整体图给"]
  - ✅ 改后: ["这是它擅长的", "这类问题得把东西放在一起看"]
```

适用范围明确、可以核实的事实和操作约束，可以直接说。
例如「不写死色值，否则切换主题时颜色不会跟着变」规定了行为，也说明了后果。
经验判断则要写清条件，不为了增强语气而说满。

### 四、对举句要看前半句是不是读者的真实误解

「不是 A，而是 B」这个句式本身没问题，问题在 A 是不是读者真会以为的东西。

| | |
|---|---|
| ✅ 可以用 | 「原文里已经有一段文字在解释它」**不是**不画图的理由，==恰恰是该画图的信号== —— 因为「有文字就不用画」是很多人的真实想法 |
| ❌ 别用 | 「它不是简单地把 X 存起来，而是……」—— 读者没以为过 X，这个否定是空的 |

### 五、加粗和 `==` 要省着用

skill 自己有一条规矩：**全文都是加粗的时候，等于没有重点**。
写 skill 文档时同样适用 —— ==一段最多一处 `==`，一节最多两三处。==

改稿时可以数一下：一节里 `==` 超过 5 处、`**` 超过 10 处，基本就是超了。

## 依赖策略：默认零依赖

页面要能**单文件发人**，所以每加一个库都在增加分发成本。

| 需求 | 用什么 | 要不要库 |
|---|---|---|
| 高亮、淡入、位移 | CSS transition / animation | 不要 |
| 元素沿路径移动 | CSS `offset-path` | 不要 |
| 流程连线 | 测量 + 内联 SVG（见 `flow` 积木） | 不要 |
| 数字滚动、按步播放 | Web Animations API / setTimeout | 不要 |
| 复杂时间轴编排、物理弹簧 | —— | 到这一步再说 |

**先零依赖做到极限。** 真不够时再讨论装什么，并且要把决定写回这一节。

## 变体：源码通读

用户说「读 xxx 代码，画出架构」时，**不要从 README 开始读** —— README 经常过期。

```callout
tone: amber
icon: ⚠
text: |
  源码通读也按原则 ⑤ 确认读者需要的解释层次。
  读者不熟悉领域时，先介绍必要概念和具体例子，再讲组织与实现；
  已经熟悉概念时，可以直接进入他关心的关系或代码路径。
```

按这个顺序读：

1. **摸依赖图** —— 一条命令看出谁依赖谁：
   ```bash
   find . -name '*.ts' -not -path '*/node_modules/*' | while read f; do
     echo "$f → $(grep -oE "from '[^']+'" "$f" | sed "s/from '//;s/'//" \
       | grep -E '^(\.|src|@)' | tr '\n' ' ')"
   done
   ```
   横切的（被所有层依赖）和纵深的（依赖所有层）一眼可见。
2. **按行数排序** —— 最大的文件就是复杂度所在，也是卡点所在。
3. **读入口** —— `index.ts` / `context.ts` / 工厂，它们定义了架构骨架。
4. **找反直觉的实现** —— 这是最值钱的卡点。信号：
   - 注释里出现「为什么不用 X」的解释
   - 有一行代码做了意料之外的事
   - 到处都在 `?? new XxxDefault()` 兜底（往往是个真实的坑）
   - 常量里出现取模 / 哈希分片
   - 有一个 `switch` 的 `default` 直接 `throw`
5. **确认，不要猜** —— 断言「这里会 throw」之前，先把那几行读出来。

**结构用现有积木就能画好**（`lane-stack` + 分组正好表达包的边界）。
真正需要新表达的是**机制**，不是结构 —— 力气花在那里。

### 把「分派逻辑」图形化

源码通读最值钱的产出，是**把代码里的分派点变成一张表或一个交互**。

判据很直接：**代码里有 `switch` / `if-else` 分派的地方，就是该画图的地方。**

```compare
first: 代码里是什么
head: [变成什么, 例子]
rows:
  - 一个 switch 分派节点类型:
      - "一张「输入形态 → 生成什么」的表"
      - "`compileNode` 的四种叶子各编译成什么"
  - 一个 op 分派:
      - "一张「操作符 → SQL 片段」的表"
      - "`applyComparison` 按 op 分派到 where / whereIn / whereBetween / whereRaw"
  - 一个「按输入挑分支」的校验器:
      - "一个「喂坏输入，看它在哪一步被拦」的交互"
      - "`validateStructure` / `validateSemantics` 各自拦什么"
  - 一条「输入 → 几道处理 → 输出」的链:
      - "一个分步执行的交互"
      - "「一个条件走完三段管道」"
```

```callout
tone: violet
icon: 💡
text: |
  ==**「分派」是代码里信息密度最高的地方。**==

  一个函数如果有 8 个分支，读代码要来回跳 8 次；
  画成一张表，一眼扫完。

  ++而且表能顺带回答「漏了哪个分支」—— 代码里看不出来，表里缺一行就很显眼。++
```

**反过来也成立**：如果一个东西没有分派，别硬画。

```compare
first: 情况
head: [怎么办]
rows:
  - 一条直线流程、没有分支:
      - "用 `lane-stack` 或直接文字说清，不用做交互"
  - 一个纯数据结构:
      - "用 `tree` 或一张字段表"
  - 一段几十行的顺序逻辑:
      - "值得做 `stepper` —— 但先问「读者会想单步走一遍吗」"
```

## 变体：拆解一个东西

用户说「拆解一下 X」时，用这六个问题逐条回答，写进 `spec` 积木：

| 维度 | 问什么 |
|---|---|
| **输入** | 喂给它什么？什么类型、什么形态？ |
| **处理** | 中间做了什么？有哪几步？ |
| **输出** | 吐出什么？给谁用？ |
| **怎么调用** | 别人实际怎么用它？贴一段真实调用代码 |
| **为什么这么设计** | 作者为什么这样选？**注释里常藏着答案** |
| **业务价值** | 它到底解决了什么问题？没有它会怎样？ |

```callout
tone: amber
icon: ⚠
text: |
  ==但不是所有东西都值得拆。==
```

**先判断该不该拆**：在代码里搜一下它被调用几处。

- **调用很多（几十处）或位于主干** → 值得拆，六个维度都写
- **只有 1~3 处调用** → 用 `compare` 一行说清就够，硬拆六个维度是凑字数
- **`src/` 里根本搜不到** → 它是被动依赖（编译期 / 间接），没有输入输出可言，
  归到一张表里说明「为什么在 deps 里」即可

> 判断依据不是「用户让我拆」，是**这个东西本身有没有那么多可讲的**。
> 拆一个只有两处调用的工具库，写出来的六段全是废话。

## 多会话协作

**这个仓库会被多个 agent 会话同时编辑** —— 用户会同时开好几个窗口，每个窗口一个 agent。

这不是假设，是常态。所以有一套规则必须共同遵守。

````callout
tone: green
icon: 📌
text: |
  **开工第一件事：读会话板。**

  ```bash
  BOARD="$(dirname "$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")")/.kh-board.md"
  tail -30 "$BOARD"
  ```

  ==那是几个会话之间唯一的通信渠道。== 谁在改什么、谁要推了、谁给你留了话，都在上面。

  完整协议见 [`references/multi-session-board.md`](https://github.com/guolinge/knowledge-html/blob/main/.agents/skills/knowledge-html/references/multi-session-board.md)，
  一句话版：**看 `tail -30`；发 `printf '...\n' >> "$BOARD"`；永远不要重写整个文件。**

  **动共享源之前、推送之前，各读一次。** 这个板子不会通知你 —— 只有你去读的时候才生效。
````

### 先搞清楚：这不是分支的问题

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==多个会话**共用一个工作目录**，才是根因。==

  开分支解决不了 —— `git checkout -b` 只改 HEAD 指向哪，
  **工作区里的文件一个都没变**。两个 agent 在同一目录里，改的还是同一批文件。
```

**真实发生过**（2026-09-29）：

```text
提交 8575596
信息：crm-local-stack：命令速查提到 01 节，原理和流程图往后挪

实际：44 个文件，+39461 行，其中包括
  notes/data-admin-to-ui/note.md        428 行   ← 另一个会话 17:41 建的
  dist/data-admin-to-ui.html           6382 行
  archify/data-admin-flow.json          112 行
  assets/arch/data-admin-flow.svg       138 行
```

反向也一样：另一个提交用 `git add -A` 把别人做到一半的 13 个 `meta.json` 一并带走了。

三个设计放大了它 —— 它们本身都没错，错的是**假设只有一个改动人**：

| 设计 | 本意 | 共用目录时 |
|---|---|---|
| `git add -A` | 提交一个自洽快照 | **仓库级** —— 分不清谁改的 |
| 全量构建 | clone 下来就能开 | 共用目录时可能读取其他会话尚未完成的源 |
| 保存即有竞态 | —— | A 保存、B 正在 build → B 构建出 A 的半成品 |

### 先做这件事：每个会话一个 worktree

```bash
cd ~/works/codes/knowledge-html
git worktree add ~/works/codes/kh-<会话名> -b <会话名>
cd ~/works/codes/kh-<会话名>
ln -s ~/works/codes/knowledge-html/node_modules node_modules
```

各 worktree 的跟踪文件独立，修改和暂存不会自动带入另一个工作区的内容。
共享的软链目录仍需单独注意，提交前也要检查本工作区的差异。

**三个实测出来的坑**：

| 坑 | 怎么办 |
|---|---|
| `node_modules` 不跟着 worktree 来 | 软链过去（上面那条），或各自 `npm install` |
| 软链显示成 `?? node_modules` | `.gitignore` 里写的是 `node_modules/`（带斜杠 = 目录），**匹配不上软链** —— 改成 `node_modules` |
| skill 的符号链接固定在主目录 | worktree 里改 skill **不生效**。skill 只有一份，这是好事 |

````callout
tone: amber
icon: 🪢
text: |
  **但「worktree 里改 skill 不生效」这句话会误导人走错一步。**

  真实布局是这样：

  ```
  ~/.agents/skills/knowledge-html  ──软链──→  <主仓库>/.agents/skills/knowledge-html
                                              <worktree>/.agents/skills/knowledge-html   ← 独立副本
  ```

  `.agents/skills/**` 是**进仓库的跟踪文件**，所以每个 worktree 各有一份。
  你按直觉去改 `~/.agents/skills/knowledge-html/SKILL.md`，==改的其实是**主仓库的工作区**==，
  而 `npm run check` 读的是 **worktree 里那份** —— 于是：

  | 你看到的 | 实际发生的 |
  |---|---|
  | 文件确实改了，内容也对 | 主仓库工作区脏了（别的会话会看到） |
  | `npm run check` 还是报「`SKILL.md` 说 20 个控件」 | worktree 那份没动 |

  ++正确做法：在 **worktree 里**改 `.agents/skills/knowledge-html/SKILL.md`。++
  主仓库那份等分支合并时自然更新。

  ==这次先改错了地方，`check` 报的却是「代码 22 个 vs 文档 20 个」，
  完全看不出是「改的是另一个副本」。==
````

不同笔记的源和产物通常可以分别合并。共享资源变化时，多篇产物也可能同时更新：

| 文件 | 合并时 |
|---|---|
| `dist/<slug>.html`、`notes/<slug>/index.html` | 只改各自笔记时通常独立；共享资源变化后按合并后的源重建 |
| `index.html`（首页树视图） | 汇总全站内容，可能冲突；用合并后的源重建 |

`index.html` 冲突时**别手动 merge** —— 它是生成的：

```bash
git checkout --theirs index.html   # 随便选一边，反正是生成的
npm run build:standalone           # 用合并后的源重建
git add index.html && git commit
```

### 没条件开 worktree 时：点名 add，别用 `-A`

```callout
tone: amber
icon: ⚠
text: |
  ==把 `git add -A` 换成 `git add <具体路径>`。==
```

```bash
git add notes/<你的 slug>/ archify/<你的名字>.json assets/arch/<你的名字>.svg
git add assets/blocks.css assets/app.js      # 只在你确实改了它们时
```

**为什么这样更安全**：`-A` 是仓库级的，它不问「这是谁改的」。
点名 add 只带走你确认过的东西。

### 保持源文件和产物一致

全量构建会处理多篇笔记，不表示每个文件都会变化，也不表示必须代提交其他会话的源文件。
独立 worktree 中只包含本工作区的修改和已有提交；合并后再从合并的源重建产物。

提交要包含本次相关源文件，以及这些修改产生的全部已变化产物。
只交源会留下旧页面；产物若依赖未提交的他人内容，也不能独立带走。
在共享目录中遇到这种情况，先隔离或协调完成范围，不拿全量构建作为扩大提交范围的理由。

### 三类文件

| 类别 | 例子 | 怎么处理 |
|---|---|---|
| 生成产物 | `index.html`、`dist/*.html`、`notes/<slug>/index.html`、`skill/*.html` | 重建后检查差异，提交本次相关的全部变化，不手改 |
| 共享源 | `assets/*`、`tools/*.mjs`、`package.json`、`.agents/skills/**` | 改前读会话板，控制范围并检查受影响页面 |
| 本篇源 | `notes/<slug>/note.md`、`meta.json`、`archify/<名字>.json` | 在声明的范围内修改，避免与别的会话同时写同一篇 |

### 开工前（30 秒）

```bash
npm run status
```

它会把你工作区的改动**分类列出来**（临时文件 / 共享产物 / 共享源 / 笔记源），
并标出每项的修改时间。

- 干净 → 直接干活
- **有别人的改动** → 两种走法：
  - 你在 worktree 里 → 与你无关，但合并时要注意
  - 你在共用目录里 → 记住它们，但**不要用 `-A`**，点名 add
- 有别人的改动**且明显是半成品**（写了一半、构建不过）→ **先问用户**

### 干活时

1. **只改自己的文件。** 不要顺手改别人的 `note.md`，哪怕发现它写错了 —— 报告，不擅自改。
2. **改共享源要小步。** `blocks.css` / `app.js` 有别人在用：
   - ==改一条 CSS 规则就替换那一条，别用大区间替换==
   - 加控件 / 积木用**新名字**，别改别人的
   - 改完尽快提交，别攒着
3. **临时文件进 `.gitignore`。** 预览副本、截图、草稿别留在 `notes/` 里。
   约定：以 `_` 开头的文件是临时的（`_p.html`、`_wip.html`）。

```bash
npm run skill               # ③b 重建 skill/（改了 skill 文档才需要）

```

```callout
  包括别人正在写的半成品。它不问「这是谁改的」。
```

### 别人的改动怎么处理

| 情况 | 怎么办 |
|---|---|
| 别人的改动已经独立提交 | 合并提交后重建，检查本次影响 |
| 别人的源未提交但完整 | 不默认代提交；先用独立 worktree，或确认联合提交的范围 |
| 别人的源尚未完成 | 不暂存、不替其完成；影响本次构建时先协调 |
| 产物变化依赖别人的未提交源 | 确认来源并隔离，不能只提交产物制造不一致 |
| 双方确认需要联合提交 | 核对每项内容和产物，在提交信息中注明来源 |

确认联合提交时，可以采用下面的注明格式：

```text
来自并行会话（非本次工作，为保持产物与源一致一并提交）：
- notes/flink-source-transform-sink/（Flink 算子笔记）
- tools/visual-check.mjs（加 .keyby-viz 容器 + JSON 解析错误上下文）
```

### 构建和提交之间的竞态（真实踩过）

```callout
tone: red
icon: ⚠
text: |
  **`npm run build` 和 `git add` 之间，别人的文件可能又变了。**

  于是你提交的是「**源是新的、产物是旧的**」——
  pre-push 钩子一重建就发现对不上，直接拦下。
```

**时间线**（真实发生）：

```text
① 我 npm run build:standalone   → 从 note.md 的版本 A 构建出产物 A
② 我 git add -A && commit       → 期间别人保存了版本 B
                                  结果提交的是：源 B + 产物 A   ← 不一致
③ pre-push 重建                 → 从 B 构建出产物 B ≠ 产物 A → 拦下
```

先检查本次提交和当前工作区，确认源属于已经约定的范围。
仅在最近的未推送提交是自己的、且需要补产物时，重建并点名暂存对应产物，再 amend。
已经推送的提交不靠改写历史来修，另建修复提交。

```bash
npm run build:standalone
git diff --stat
git add <已核对的产物路径>
git commit --amend --no-edit   # 仅适用于上述未推送的本次提交
```

```callout
tone: amber
icon: ⚠
text: |
  如果重建后仍反复出现差异，先查看具体变更，检查是否有并行写入或非稳定的构建输出。
  不能仅凭重试失败认定是其他会话在编辑。没有确认范围前，不继续暂存或反复 amend。
```

### 别人的文件坏了，阻塞了共享构建

```callout
tone: amber
icon: ⚠
text: |
  ==`npm run check` 是全仓库的。别人一篇笔记写坏，你这边也过不了。==
```

**先分清是哪一类**：

| | 例子 | 怎么办 |
|---|---|---|
| **机械性问题** | YAML 裸标量以反引号开头 · 积木名拼错 · 引号没闭合 | ✅ **可以修**。工具自己会给出修法，改的是语法不是意思 |
| **语义性问题** | 内容写错了 · 数字不对 · 结构乱 | ❌ **不碰**。报告用户 |

```callout
tone: green
icon: ✅
text: |
  **判断标准：这个修改会不会改变别人想表达的意思？**

  加一对引号不会。改一个数字会。

  机械性修复要在提交信息里**单独列出来并注明**，别混在自己的改动里。
```

**真实案例**：并行会话的 Flink 笔记里有两行 `- q: \`xxx\` 是什么？` ——
YAML 里裸标量不能以反引号开头，整个仓库的 `check` 都挂了。
预检工具直接给出了修法（外面包一层双引号），修它零风险。

### 冲突处理

| 冲突的文件 | 怎么办 |
|---|---|
| `index.html`、`dist/*`、`notes/*/index.html` | **重新构建**，不要手动 merge。产物是生成的，冲突无意义 |
| `package.json` | 通常两边都加了 script → **两边都保留** |
| `blocks.css` / `app.js` | 真冲突，逐条看，**两边的改动都要留** |
| `note.md` | 不该发生。如果发生，说明两个会话改了同一篇 → **问用户** |

### 推送被拦下来怎么办

pre-push 会重建并检查布局。被拦时查看具体文件和诊断，不先假定问题属于哪个会话。

```text
✗ 构建产物有变化（note.md 改了但没提交构建结果）
```
→ 检查源和产物的差异，在约定范围内重建并点名暂存。未推送的本次提交可以补产物，已推送的另建修复提交。

```text
✗ 有图被画坏了
```
→ 看是哪个积木、哪一篇。**如果是别人笔记里的图坏了，报告用户，别去改别人的内容。**

### 四条硬规矩

1. **优先开 worktree。** 没条件就在共用目录里点名 `git add`，别用 `-A` ——
   共用目录里 `-A` 会带走别人正在写的半成品。
2. **产物和源必须一起提交。** 只交产物 → 来源不明；只交源 → 构建过期。
3. **不替别人改东西。** 发现问题 → 报告，不擅自改。
4. **提交前跑 `npm run status` —— 而且要看完。**
   别 `| head -45` 只扫前面一截就往下走。

## 硬约束

==这张表随时要用，所以留在这一页。==

| ❌ 不要 | ✅ 应该 |
|---|---|
| 为了「符合积木规范」而扭曲表达 | **怎么讲清楚怎么来**。积木是省力工具，不是验收标准 |
| 硬把内容塞进最接近的积木 | 组合 / 加字段 / 新建 / `raw` 直接写 —— 四条路任选 |
| 编辑 `notes/*/index.html` | 那是产物，会被覆盖。只改 `note.md` |
| 在单篇 `note.md` 里塞 `<style>` | 改 `theme.css` / `blocks.css` —— 一次全站生效 |
| 在正文写 `# 一级标题` | 标题只写在 `meta.json` 的 `title` |
| `meta.json` 里写 `status: "verified"` | agent 生成的内容一律 `draft`。`verified` 是**人工核对过**的信号 |
| 没挂树的笔记不填 `topic` | 填一个 —— 否则它在首页的「未归类」里落进「其他」组 |
| 原样搬用户的原文 | 围绕读者的问题组织，删无关铺垫和重复，保留必要前提；关系和过程按原则 ① 呈现 |
| 写「它不是 X，而是 Y」这类否定句 | **读者没听过 X**。除非 X 是读者真会有的误解，否则直接说 Y 是什么 |
| 写「这一步我之前没讲」「这张图我第一版画错了」 | **读者不知道你迭代过几轮**，这些话只对你有意义。直接陈述事实 |
| 图上的编号和正文对不上 | 正文用编号指代时，**图上必须真有那个编号**（archify 的边标签、积木的 badge 都要对得上） |
| 图上有文字被压住 | ==字还在、只是读不通，所以最容易滑过去。== `npm run visual-check` 会报「文字压文字」，改完图必须跑 |
| 把 SQL / 代码粘成一整行 | 一个子句一行，嵌套的缩进。原文本来就在一行时（如编译器输出）要注明「换行只是排版」 |
| 把语法高亮当成分色 | 笔记里分的是**来源**（权限 / 条件 / 派生）—— 不要连 `SELECT` 都要上色 |
| YAML 裸标量里出现 `: `（冒号+空格） | 加引号，或用 `|-` 块标量 |
| YAML 裸标量以反引号 `` ` `` 开头 | 加引号 |
| YAML 裸标量以 `*` `&` `!` `%` `@` 开头 | 加引号（会被当成别名/锚点/标签） |
| 值里有 `[` 或 `{` 却没加引号 | 加引号（`Rule[]` 里的方括号会被当数组起始） |
| 担心 `**「术语」**` 这类中文加粗失效 | 已经修好了，不用管；但 `**` 跨行仍然不生效 |
| 只给卡点画图，其余照搬原文 | 卡点决定详略；理解所需的位置、归属、分支和变化也要画，比较和并列信息可以用表格或卡片。见原则 ①、⑥ |
| 需要关系图，却因为没有现成积木而省略 | 按原则 ⑦ 组合 / 加字段 / 新建积木 / 用 `raw`；简单清单和判断可以留文字 |
| 先甩一个抽象判断，再用破折号复述一遍 | 合并重复，或直接从具体内容讲起 |
| 写空转的过渡句（「这一条接着说下一层」） | 不承载信息就删掉 |
| 没依据的绝对化（唯一 / 全都 / 永远 / 根本 / 只能） | 核对适用范围。明确约束可以保留，经验判断要说明条件 |
| 一段里堆 `==` 和加粗 | 只突出重要信息，避免重复强调。见[写作规范](#怎么写笔记正文和-skill-文档都适用) |

**每篇笔记结尾必须有 `quiz`。** 这是仓库约定，用 2~3 题检查读者能否回答本篇的关键问题。
题目与主要讲解对应，不用无关知识凑数。

**`meta.json` 的 `status` / `sources` 会渲染成页内的溯源头。**
漂亮的 HTML 会自带「这应该是对的」的暗示，而它可能只是某次对话的产物。
半年后你必须能一眼看出哪个结论没人核对过。

### 改了「站点外壳」要多做一步

外壳 = `tools/lib/home.mjs`（首页）、`assets/theme.css` / `blocks.css`。
下面两个坑 **`npm run check` 一个都报不出来**，而且都是**静默**的：属性设上了、JS 里读也是对的，只有屏幕上不对。

````callout
tone: red
icon: ⚠
text: |
  **一、内联在模板字符串里的浏览器 JS，语法检查查不出 `ReferenceError`。**

  首页那段 `<script>` 是拼在 JS 模板字符串里的，`node --check` 看不到它。
  我重构时把旧函数整个换掉，**连同里面声明的 `var mode` 一起删了** ——
  语法完全合法，表现是「排序按钮点下去毫无反应」。

  → 在真实页面里跑一遍，并把 `window.onerror` 收上来（否则连报错都看不到）。

  ```bash
  # ==探针文件必须写在仓库根目录==，再让 python 把 <script> 注入进去。
  # 放 /tmp 跑的话，相对路径引的 assets/*.css 全断了 ——
  # 你会测出「样式没生效」的假象，然后去修一个根本不存在的 CSS 问题。（真踩过）
  cp index.html .probe.html   # 注入探针
  chrome --headless=new --virtual-time-budget=6000 \
    --dump-dom "file://$PWD/.probe.html" | grep -o 'class="PROBE">[^<]*'
  ```
````

````callout
tone: red
icon: ⚠
text: |
  **二、`el.hidden = true` 会被作者样式里的 `display` 盖掉。**

  浏览器自带的 `[hidden] { display: none }` 在 **UA 样式表**里，
  而 **作者样式表里任何一条 `display` 都会盖掉它** —— 跟优先级无关。

  所以 `.tnode { display: grid }` 一写，`n.hidden = true` 就完全失效：
  属性在、`el.hidden` 读出来是 `true`、屏幕上还画着。
  首页的**搜索和标签筛选因此哑了很久**（实测：32 个节点全被标了 `hidden`，32 个全在显示）。

  `theme.css` 里已经加了兜底，==站内新写的组件不用再操心==：

  ```css
  [hidden] { display: none !important; }
  ```

  但要是哪天自己写页面 / 导出 HTML，记得补上这条。
````

| 命令 | 干什么 |
|---|---|
| `npm run status` | **开工前 / 提交前先跑这个** —— 把改动分类列出来 |
| `npm run gaps -- <slug>` | 列出正文候选段落和字数，辅助定位图解缺口；统计比值不作为验收门槛 |
| `npm run check` | 校验积木语法 + YAML + 约定 + skill 与代码一致 + **skill 文档自己能不能渲染** |
| `npm run view -- <slug>` | 构建单篇 + 打开（**默认就开**，它的用途就是这个；agent 验证时加 `--no-open`） |
| **`npm run block -- <slug> <n>`** | **只看第 n 个积木**：量高 + 截图，打印截图路径。==默认不开浏览器==（人要看加 `--open`） |
| `npm run block -- <slug> --list` | 列出这一篇的块（编号 + 行号 + 语言） |
| `npm run build:standalone` | 重建全部产物（`dist/*.html` + 首页） |
| `npm run visual-check` | 检查全部 `dist/` 的布局；加 `-- <slug>` 检查指定篇，不检查 `skill/` |
| `npm run build` | 重建 `notes/*/index.html` 和首页，不更新 `dist/` |
| `npm run skill` | 把这份 skill 渲染到 **`skill/`**（**进仓库**，首页链得到）+ 三个页面互链。默认不开浏览器，加 `--open` |
| `npm run new -- <slug>` | 新建一篇笔记 |
| `npm run serve` | 起本地服务器 |
### 文档

- `plans/<topic>.yaml` —— **嵌套产物树的唯一真相源**（树 + 依赖 + 进度）
- `tools/lib/plan.mjs` —— 读 plan、生成「前置」区块
- `tools/lib/home.mjs` —— 首页：树视图 + 未归类区
- [`references/blocks.md`](references/blocks.md) —— 积木的完整 DSL
- [`references/extend.md`](references/extend.md) —— 积木不够用时怎么加一个
- `skill/` —— **skill 文档渲染出来的站点页**（`npm run skill` 生成，进仓库）
- `tools/skill-view.mjs` —— 渲染 skill 到 `skill/`；`.preview/` 留给临时预览（不进仓库）
- `tools/probe/visual-check.js` —— 浏览器探针（独立文件，不是模板字符串）
- `tools/visual-baseline.json` —— 已知问题基线（积木画不了的那些）
- `notes/blocks-cheatsheet/note.md` —— 可运行的积木示例
- `notes/data-warehouse-cdc-flink/note.md` —— 长文转图的实战案例

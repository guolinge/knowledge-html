用户以 **【图解】** 开头（后面可接内容、飞书链接、或「看上面」）。

项目固定在：

```
~/works/codes/knowledge-html

## 原则 ① · 图是这个产品的本体，不是配图

**判据只有一句话：这一段描述的，有没有「空间 / 顺序 / 状态 / 归属」？**

| 这段文字在说什么 | 该用什么 |
|---|---|
| 谁指向谁、谁包含谁、谁和谁并列 | `tree` / `flow` / `arch` |
| 先发生什么、后发生什么、谁在等谁 | `seq` / `lane-stack` / `flow` |
| 某个东西从 X 变成了 Y | `journey` / `flow`（`shape: pill`） |
| 按时间演进 | `timeline` |
| 几个东西按维度对比 | `compare` / `matrix` |
| 同一条轴上多种方案的差异 | `demo` 控件 |
| **纯因果论证、经验判断、取舍理由** | **文字。这是图替代不了的** |

### 反直觉的那一条

> ==**「原文里已经有一段文字在解释它」不是不画图的理由，恰恰是该画图的信号。**==

理由很直接：那一整段文字用户已经读过了。你再搬一次，他得到的是**同一份信息换了个字体**。

反过来，一段文字如果**只有**在这里才说得清（比如「为什么用链表而不是数组」），
那才是真正该留给文字的东西 —— 因为它是个判断，不是个结构。

### 什么样的东西**不**该画

这条是防「机械执行」的。下面三类留在文字里是对的：

```compare
first: 情况
head: [为什么留文字, 例子]
rows:
  - 清单式的操作步骤: ["①②③④ 之间没有空间关系，画成图反而要多绕一层", "「分配 pid → 分配资源 → 初始化 PCB」"]
  - 真正的判断和理由: ["它回答的是「为什么」，不是「长什么样」", "「PCB 是有限的，申请不到就直接失败」"]
  - 一句话的过渡和结论: ["它本来就是用来断句的", "「到这里是五个状态」"]
```

### 这条规矩和「图是稀缺资源」怎么共存

```compare
first: 说法
head: [什么意思]
rows:
  - ~~「只有卡点值得画图」~~: ["❌ 这句话把优先级当成了门槛，结果 60% 的内容退回文字", { text: "见一次删一次", tone: red }]
  - "卡点优先，其余照画": [{ text: "✅ 卡点画得深、配交互；其余的用 `cards` / `compare` / 一张小图带过", tone: green }]
```

==一张 `cards` 也是图。== 判断标准不是「这算不算大图」，
而是「读者扫一眼能不能拿到结构，不用逐字读」。

## 原则 ② · 关键图要有信息量，「把名词摆一遍」不算图

**反例长这样**：一个框，标题「共享资产」，副标题「代码段 · 堆 · 文件描述符表 · 线程共用」。

那不是图，那是**带框的目录**。它只告诉你有这么几个名词，
没告诉你它们在哪、多大、怎么摆、什么时候变。

### 一张图的信息量分三层

```compare
first: 层次
head: [图里有什么, 同一个概念的三种画法]
rows:
  - 名词: [{ text: "❌ 只是列名字", tone: red }, "「代码段 · 堆 · 文件描述符表」"]
  - 结构: ["在哪、多大、谁挨着谁、朝哪长", "在地址空间里从高到低排开：栈向下长、堆向上长，中间夹着 mmap 区"]
  - 机制: [{ text: "✅ 关键图至少要到这里", tone: green }, "栈随线程走、堆随进程走；pthread 栈 8MB 定死，goroutine 2KB 起步自己长"]
```

**判据**：把正文全部盖住，只看这张图 ——

- 它能回答一个「**为什么**」吗？
- 它给出了「**多大 / 多少 / 在哪**」这类具体的量吗？
- 换一个尺寸或数量级，这张图会变吗？（**不会变 = 它只是个名字列表**）

三条都答不上来，就是名词层，重画。

### 从「一段文字」到「一张丰富的图」，中间那截信息从哪来

这是这个 skill 里最容易出问题的一步，也是用户点名说过的一条：

> 你是从少量文字然后画一个丰富的图嘛，中间你是需要补充信息的。
> 然后这信息呢，==如果你 100% 从你知识库里面肯定是对的，你就使用；
> 如果你不肯定的话，你就得使用联网搜索==。

**门槛是「我确不确定」，不是「这张图重不重要」。**
不确定就查，跟它是不是关键图无关 —— 因为你在图上写下的每个数字都会被读者当真。

```compare
first: 你手上的信息
head: [怎么做]
rows:
  - 100% 确定（教科书级常识）: [{ text: "直接用。比如「x86-64 用户空间是 47 位」", tone: green }]
  - "**想起来是这样，但说不出出处**": [{ text: "联网查。这就是「不肯定」的判据", tone: amber }]
  - 数字 / 版本 / 上限 / 默认值: [{ text: "一律查。这类最容易被记成错的", tone: red }]
  - 机制（「因为…所以…」）: [{ text: "查，或者去读代码。==推出来的机制最危险，因为它看着最顺== ", tone: red }]
```

```callout
tone: amber
icon: ⚖
text: |
  ==「不肯定」的自我判据只有一条：**能不能说出出处。**==

  「我记得栈是 8MB」—— 说不出出处 → 查。
  「Go 的 `_StackMin` 是 2048」—— 能说出是 `runtime/stack.go` → 可以用。

  这和「复盘 ①b」里那条是同一个东西：
  ++写下「因为…」之前，问自己「我是读到的，还是推出来的？」++
  **推出来的，就得回去查。**
```

**这一次的真实对照**（画「进程 vs 线程」那张图）：

| 只照原文画 | 查完之后 |
|---|---|
| 一个框：共享资产 =「代码段 · 堆 · 文件描述符表」 | 整张虚拟地址空间：内核空间 / 三块线程栈 / mmap 区 / 堆 / BSS / 数据段 / 代码段，带地址和增长方向 |
| 「线程共享文件描述符」 | ==查完发现 fd 表根本不在地址空间里== —— 它在内核的 `files_struct`。原文那句话本身没错，但塞进「内存布局」这张图里就是错的 |
| 栈大小没提 | Go `_StackMin = 2048` 字节起步；pthread 默认 8MB 且定死 |

中间那一列，**全部来自联网查，不是从原文推的**。

### 怎么查：用什么语言、信谁、用哪个工具

上面说「不确定就查」。但**怎么查**是另一回事 —— 这一节补三个具体的决定。

#### ① 默认英文查，而且中英一起搜

原理、标准、数字、报错 —— ==一律先英文。==

理由是一手的资料基本都在英文那边：内核文档、RFC、POSIX、各家官方 docs、
GitHub issue 和源码。中文内容大多是**转述**，而转述会丢限定条件。

```callout
tone: red
icon: 🩸
text: |
  **一个真实的例子**（查 OverlayFS 的合并规则）：

  中文的两份材料都说「上层文件盖住下层」。照着画出来的图会说
  `ls /etc` 只能看到上层那几个文件。

  换成英文去查内核文档，第一条就是：

  > If a name refers to a **non-directory** in either layer, the lower object is hidden.

  ==「非目录才隐藏」—— 这句话把目录排除在外了。== 目录是**合并**的。

  那两份中文材料不是写得差，是**转述时把限定条件丢了**。这就是二手信息的固有损耗。
```

| 场景 | 用哪种 | 为什么 |
|---|---|---|
| 原理 / 标准 / 规范 | **英文** | 一手资料：内核文档、RFC、POSIX、W3C |
| 数字 / 默认值 / 上限 / 版本行为 | **英文** | 这些**只在**一手资料里是准的 |
| 报错信息 | **英文** | 把报错**原样**贴进去搜，命中率最高 |
| 国内产品的行为（飞书、微信、阿里云） | 中文 | 官方文档只有中文 |
| 中文社区特有的约定 | 中文 | 比如面试题对概念的划分方式 |

++不知道英文怎么叫的时候，先搜「<中文名> 英文」拿到对应词，再用那个词深挖。++
例：`快表 英文` → `TLB` → 再搜 `TLB flush context switch`。

#### ② 写进笔记时，用原文的术语

**查证用英文，行文用原文的术语** —— 读者要能对得上他手上那份原文。

第一次出现时括号附英文，之后就不用了：

```text
快表（TLB）          ← 原文叫「快表」，读者是照这个词对上原文的
阻塞挂起（blocked-suspend）
只读层（read-only layer）
```

!!不要因为「英文更准」就把正文里所有术语都换成英文。!! 那是拿查证语言替换行文语言，
读者会更难对上原文。

#### ③ 认来源：一手 / 二手分两档

```compare
first: 档次
head: [哪一类, 怎么用]
rows:
  - 一手: ["`kernel.org` · `docs.*.com` · RFC 编号 · `github.com/<org>/<repo>` 的 issue 和源码", { text: "用它定事实", tone: green }]
  - 二手: ["个人博客、教程、问答站、另一个 AI 的回答", { text: "只用来找线索和关键词，**不用来定事实**", tone: amber }]
```

看一条到手的信息属于哪档，有个快办法：**它有没有提到限定条件。**

「上层盖住下层」是一手的说法吗？不是 —— 一手说的是「非目录才隐藏」。
==带限定条件的说法通常来自一手，不带的那种多半是转述时被磨平了。==

#### ④ 三个工具，分工不同

| 工具 | 什么时候用 |
|---|---|
| `web_search` | **还不知道该信谁**的时候，铺开找。给它 2~4 个不同角度的 query，别只搜一条 |
| `source_check` | **手上有一个具体断言要验**。它会返回 passage 级的引文 —— 正好喂给「复盘 ①b」那条「回源码核实」，而且引文是可以贴进笔记 `sources` 的 |
| `fetch_content` | **已经知道是哪一页**，直接读它（比如那一页 `overlayfs.html`）。也能用 `mode: answer` 让它只根据这一页回答问题 |

### 更狠的一条：关键图要画到「读者已经认识的锚点」为止

上面说信息量分三层（名词 → 结构 → 机制）。但对**调度 / 流转 / 加工**这一类概念，
还有一层更高的要求，用户的原话：

> 我需要它一个任务线程，要把 CPU 画出来，然后上面有几个核心也画出来。
> 然后任务线程是怎么穿过、怎么利用 CPU 核心的这个管道我想画出来。
> 任务是怎么排队、队列长什么样、用户态调度器在哪、最后的结果是怎么样的，也画出来。
>
> ==**我需要一个丰富的图去理解它，落实到一些具体的结构上，
> 让我感受到「原来它现实中是这样经过的」，在硬件上它是这样表现的。**==

翻译成可操作的五条：

#### ① 画到底，不许停在半截

任何一个「东西从 A 流到 B」的概念，链条要一路画到**最后那个物理部件**：

```
输入 → 在哪排队 → 谁在挑 → 执行者 → 落在哪块物理资源上 → 结果长什么样
```

停在中间（比如只画到「少量线程」就收笔）就是半截图。

```callout
tone: red
icon: 🔌
text: |
  **判据：这条链的最后那个东西，读者是不是已经认识？**

  ==停在一个「读者还不认识的抽象」上，就是半截图。==

  最常见的锚点是**物理的**，因为它人人都认识，不会骗人：

  物理锚点 · CPU 核 · 内存条 · 磁盘 · 时钟 · 网卡 · 光电信号

  ==但物理不是唯一的一类。== 下面这些都算落地：

  | 锚点类型 | 例子 |
  |---|---|
  | 物理部件 | 落到「4 个核里有 3 个空着」 |
  | 生活经验 | 落到「饭堂三个窗口只开了一个」 |
  | 读者用过的东西 | 落到「一个 git 仓库的 `.git` 目录」 |
  | **本篇前面已经定义过的概念** | 第 2 节讲过「页表」，第 5 节就能拿它当锚点 |

  最后一行很关键：**锚点是相对的，不是绝对的**。
  「页表」对刚翻开这篇的人是抽象，对读完第 2 节的人就是锚点。
  所以判断的是「**读到这里的人**认不认识」，不是「外行认不认识」。
```

#### ② 容器要画出「容量」

队列不能画成一个写着「队列」的框。要画成**一排看得见的格子**：

- 有几格
- 现在装着什么
- 满了 / 空了往哪去

==这三件事画出来，「排队」这件事才成立。== 写一个「队列」的框，读者只能记住这个词。

#### ③ 通道要画成「一条通路」

「任务怎么利用核心」要画成**从线程穿到核的那条线**，
而不是在箭头旁边写一个词（`submit`、`多路复用`）。

++读者要能顺着线走一遍。++ 标签是注解，线才是路径。

#### ④ 状态要落在图上，不要落在图下面那句话里

哪个在跑、哪个在等、哪个核空着 —— 这些是**结果**。

结果要能**从图上直接看出来**（颜色 / 虚实 / 标注），
不能靠下面那段文字告诉他「所以有些核会闲着」。

#### ⑤ 有「层」的概念，每层要标出「谁的地盘」

用户态 / 内核态 / 硬件是三个不同的世界。谁在哪一层、
跨层的时候发生了什么（系统调用 / 中断），是这类图最容易丢的信息。

#### 一条终极判据：能不能顺着这张图讲一个 30 秒的故事

> 「六个任务排在队列里 → 用户态调度器一次挑一个 → 交给三条线程 →
> 三条线程占住三个核 → 剩下三个核从头到尾闲着。」

**能讲出来 = 图到位了；讲不出来 = 还缺东西。**
照着这句话回头补图，缺什么补什么。

注意这个故事里的每一个名词 —— 任务、队列、线程、核 ——
**读到这里的人都认识**。只要有一个不认识，故事就卡住了，那张图就还没落地。

```compare
first: 反过来的做法
head: [会怎样]
rows:
  - 画到「少量线程」就收笔: ["读者知道有这回事，但想象不出它长什么样、在哪儿发生", { text: "补上 CPU 和核", tone: amber }]
  - 队列写成一个框: ["「排队」变成一句需要相信的话，而不是看见的事实", { text: "画成一排格子", tone: amber }]
  - 通道只写一个词: ["读者拿不到「谁穿过什么、往哪去」的路径感", { text: "画成线", tone: amber }]
  - 结果写在图注里: ["图只负责输入，结论全靠文字 —— 那要图干什么", { text: "让结果在图上可见", tone: amber }]
```

```callout
tone: violet
icon: 🏗
text: |
  **积木画不了这种图的时候，要做积木，不要缩减表达。**

  这就是原则 ⑥ 说的四条路（组合 / 加字段 / **新建积木** / `raw`）。
  实践中真的会出现「现成积木都装不下这个形状」的情况 ——
  那个时刻不要去削内容，++去加工具++。

  这次为了画地址空间加了 `memmap`，为了画 GMP 到核的拓扑，
  又发现 `flow` 的箭头承载不了「排队 → 收敛 → 铺开」这种漏斗形状。
```

### 顺带一条：别让画布空着

五个节点铺在 1400px 上，四周全是空白，读者会先看到「空」再看到节点。

```compare
first: 症状
head: [怎么办]
rows:
  - 几行节点、大片留白: ["往图里**加信息**，不是把图放大。缺的通常是「量」和「方向」"]
  - 节点的 `sub` 只有 2~4 个字: [{ text: "那是标题，不是说明。把机制写进 `sub`", tone: amber }]
  - 同类节点长得一模一样: ["差异化 —— 谁共享谁独享、谁大谁小、谁先谁后，都该在图上有痕迹"]
  - 一句话概括得了整张图: ["那它就不该是图。改成 `callout`，把版面让给真正需要画的东西"]
```

## 原则 ③ · 讲透卡点，不是搬运内容

**你的任务不是「把内容搬进 HTML」，是「把用户卡住的那个环节讲透」。**

用户粘过来的原文通常有 60% 是铺垫、重复、客套。原样搬进去只会得到一个更长的、
仍然看不懂的页面。用户要的是**图和交互** —— 这是 HTML 相对纯文本唯一不可替代的价值。

所以：**先找卡点，再决定画什么图，最后才写文字。**

```compare
first: 不是
head: [搬运式, 讲透式]
rows:
  - 结构: ["照着原文分段", "按「卡点」重新组织"]
  - 篇幅: ["原文多长就多长", "砍到骨架，该删的删"]
  - 图: ["配几张插图", "把讲不清的地方变成图或交互"]
  - 判据: ["「内容都在了」", "「用户看完能说出所以然」"]
```

---

## 原则 ④ · 先对齐理解层次

**同一份材料，不同的人卡在不同层次。写之前先判断读者在哪一层。**

```
概念  →  组织 / 层面  →  架构
是什么    怎么组织      代码怎么实现
```

- **概念层**：这个领域有哪些词？每个词对应现实中的什么？
- **组织层**：这些概念怎么被组织成一个整体？
- **架构层**：代码怎么实现它？

**判断方法**：读者说「没接触过」「完全不懂」「看不懂」「有点抽象」
→ **他卡在概念层**，从最具体的场景和真实数据开始，**不要从架构开始**。

### 概念层的三条硬规矩

| ❌ 不要 | ✅ 应该 |
|---|---|
| 出现类型名 / 类名 / 文件名 | 用业务词汇 + 真实数据举例 |
| 「输入是 X 树，输出是 Y」这种抽象定义 | 「运营要发券给最近 7 天加购的 VIP」这种场景 |
| 直接上表结构 / 字段名 | 先给一行**真实数据**长什么样 |

> **类型名是架构词汇，不是概念。**
> 概念层出现 `XxxTree` / `XxxStruct` / `XxxBuilder` 这类东西就是劝退。

概念讲清楚了，读者自己会问「那为什么需要写个库」—— 那时才进组织层。

### 一个自检方法

写完开头，问自己：**一个完全不懂这个领域的人，读完前三节能说出「这东西是干嘛的」吗？**
说不出就是概念层没写够。

## 原则 ⑤ · 表格是排版，图是表达空间关系

**最容易犯的错：用表格的思维做图。**

| | 表达什么 | 用什么 |
|---|---|---|
| **表格 / 卡片** | 并列的、离散的信息 | `compare` `cards` `spec` |
| **图** | 空间关系：东西在哪、怎么流动、状态怎么变 | `lane-stack` `flow` `journey` `timeline` |

**判断方法**：

- 只能用「第一行是 X，第二行是 Y」描述 → **表格**
- 能用「A 指向 B」「A 变成 B」「A 和 B 汇合到 C」描述 → **图**

```callout
tone: amber
icon: ⚠
text: |
  ==`spec` 是拆解卡，看起来像图，本质还是两栏文字。==

  它适合**速查**（10 个文件各是什么、6 个依赖各是什么），
  **不适合讲机制**（这个东西怎么工作）。讲机制一定要画图。
```

### 讲机制的正确顺序

用户的原话：**「先介绍概念，让我对概念建立认识；再用图把概念连起来。」**

1. **拆成 3~6 个原子概念**，每个概念一两句话
2. **每个概念配一张图** —— 不要吝惜图，几张十几张都行
3. **概念讲完再上交互** —— 让用户亲手跑一遍

反例（错误做法）：直接上「输入 / 处理 / 输出」的表格，用户看完还是不知道它怎么工作。

## 原则 ⑥ · 积木是词汇，不是语法

**画图是为了让用户理解内容、思想、设计、意图。怎么好呈现就怎么来，不要拘泥。**

`lane-stack` / `journey` / `compare` … 这些积木的作用是
**让你不用每次从零写 CSS**，不是**限制你能表达什么**。

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==最危险的失败模式：读完积木清单，然后把内容硬塞进最接近的那一个。==

  结果是「合规但没讲清楚」—— 比不画图更糟，因为看起来做了工作。
```

表达不顺手时，**四条路，按优先级**：

| 优先级 | 做法 | 什么时候用 |
|---|---|---|
| 1 | **组合** | 现有积木拼一拼就能表达（大多数情况） |
| 2 | **加字段** | 方向对但缺一个能力。例：给 `demo` 加 `html` 字段支持自定义布局 |
| 3 | **新建积木** | 同一类表达反复出现（见 `references/extend.md`） |
| 4 | **`raw` 直接写 HTML/CSS** | 一次性排版。**这是合法选择，不是投降** |

判断标准只有一条：

> **这样呈现，用户能不能秒懂？** 而不是「这符合积木规范吗」。

`theme.css` 的变量（`--tone` / `--surface` / `--border` / `--blue` …）随你用，
深色模式自动跟着走。唯一底线：**不写死色值**，否则换肤会坏。

交互也一样：`demo` 积木的 `html` 字段可以放任意自定义控件，
`WIDGETS` 注册表里加一个函数就行。别因为「没有现成控件」就放弃一个能讲清楚的交互。

## 工作流

### 第 0 步 · 判断：用户要的是「一个点」还是「一个面」

**不要看到【图解】就开始画图。先判断用户要的是哪一种。**

| 用户的说法 | 他要的是 | 你怎么做 |
|---|---|---|
| 「这个函数干什么」「A 和 B 有什么区别」「这段代码为什么这么写」 | **一个具体问题的答案** | 直接跳到第 2 步 |
| 「理解这个项目」「搞懂这一章」「从零学 X」「理解 X 的架构」 | **一条理解路径** | **必须先走第 1 步** |

**判断信号**：用户说的是「一个点」还是「一个面」。
说「面」的时候，**不要急着产出内容，先产出「脉络」**。

```callout
tone: red
icon: ⚠
text: |
  ==用户说「给我架构图」不等于「我只需要架构图」。==

  他可能是想「理解这个项目」，而架构图只是**他以为的入口**。
  直接给架构图，他会发现到处都缺前置知识，然后东补一块西补一块。
```

**不确定时，直接问**：一句「你是想快速要一张图，还是要从零搞懂它？」
能省掉后面好几轮来回。

### 第 1 步 · 梳理知识树（只在「一个面」时做）

#### 1.1 画一棵「要理解什么」的树

```
理解 X
├─ ① 业务背景 —— 为什么需要它、解决什么问题
├─ ② 概念    —— 有哪些词、每个词对应现实中的什么
├─ ③ 组织    —— 它由什么组成、怎么分类
├─ ④ 架构    —— 它怎么工作
├─ ⑤ 设计取舍 —— 为什么这么设计、不这样会怎样
└─ ⑥ 代码细节 —— 具体到文件 / 模块 / 函数
```

**每个节点标三样：**

| 标什么 | 为什么 | 例子 |
|---|---|---|
| **依赖** | 理解它之前必须先理解谁（决定顺序） | `依赖: ②概念` |
| **深度** | 概念 / 组织 / 架构 / 代码（决定详略） | `深度: 架构` |
| **产物** | 值得单独一篇，还是并入上一篇（决定切分） | `产物: 单独一篇` |

#### 1.2 这棵树是**递归**的

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==六层不是某个项目的专属结构，而是「理解任何东西」的通用结构。==
```

所以每一层里的**模块**，只要大到需要单独理解，就要**自己再走一遍这六层**：

```
理解一个 Web 框架
├─ ① 业务背景
├─ ② 概念
│   └─ 中间件 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它是什么、为什么需要
│       ├─ 组织：有哪几种（普通 / 错误处理 / 路由级）
│       ├─ 架构：next() 怎么把它们串起来
│       └─ 细节：代码在哪
├─ ③ 组织
│   └─ 核心包 ──────────────→ 它也要走一遍六层！
│       ├─ 概念：它负责什么
│       ├─ 组织：由哪些文件组成
│       ├─ 架构：怎么工作
│       └─ 细节：路由 ──────→ 再递归一次！
├─ ④ 架构
├─ ⑤ 设计取舍
└─ ⑥ 代码细节
```

```callout
tone: violet
icon: 💡
text: |
  **所以产物不是「一篇 HTML」，而是一棵嵌套的、互相链接的产物树。**

  每篇笔记对应树上的**一个节点**，节点之间有 `needs` 关系（前置依赖）。
  读者沿着树走，每篇开头都写清楚「读这篇之前需要知道什么」。
```

#### 1.3 判断一个节点要不要单独成篇

| 单独成篇 | 并入父节点 |
|---|---|
| 它有**自己的概念**要解释 | 它只是父节点的一个属性 |
| 它**大到需要分几节** | 一两段能说完 |
| **其他节点会引用它**（是别人的前置） | 只有父节点用到它 |

> 用最后一条最准：==一个节点被别的节点 `needs` 引用了，它就必须独立成篇==，
> 否则读者会被迫跳进另一篇的中间去找。

#### 1.4 梳理时不断拷问自己

**这一步是 AI 拷问自己，不是拷问用户。** 每个节点问四个问题：

1. 要理解这个节点，读者**必须先知道什么**？那个前置知识在哪一层？
2. 有没有**循环依赖**？（A 需要 B，B 又需要 A → 拆法有问题，要重新切）
3. 哪些是**可以推迟的细节**？（不放进第一轮）
4. 有没有**用户已经知道的**？（他的背景里已经有了，跳过）

#### 1.5 和用户确认

**把树给用户看**，问三个问题：

1. 这个脉络对吗？有没有多余的、有没有漏的？
2. 顺序对吗？
3. 先做哪一块？

```callout
tone: green
icon: ✅
text: |
  ==确认脉络花的 2 分钟，能省掉后面来回补窟窿的 2 小时。==

  用户看到树之后，往往能立刻指出「这块我已经懂了」「这块才是重点」——
  这些信息你猜不到。
```

#### 1.6 最后才决定产物切分

**一棵树 ≠ 一篇文档，也不等于 N 篇。**

按「**一块能独立读懂**」来切：

- 前置知识自足的一块 → 一篇
- 太短的合并
- 太长的再拆
- **每篇开头写清楚「读这篇之前需要知道什么」**

```callout
tone: amber
icon: ⚠
text: |
  **跳过这一步会怎样？**

  读者每看完一篇就发现「这里缺一块」，于是回头补；补的时候又发现另一块缺，再补。
  ==好几轮来回，全在补第一轮就该规划好的窟窿。==

  **根因**：把「用户要的产物」当成了「用户的目标」。
  **信号**：如果用户连续三轮都在问「那 X 是什么」，说明第一轮就该梳理脉络。
```

#### 1.7 落地：把树写成 `plans/<topic>.yaml`

```callout
tone: amber
icon: ⚠
text: |
  ==确认的脉络不要只留在对话里。==

  对话会滚走，脉络会丢。写进文件，它才能驱动页面、才能在几周后还看得见。
```

```bash
# 树的唯一真相源
plans/<topic>.yaml
```

```yaml
topic: sql-builder-v2
title: 理解 sql_builder_v2
summary: 从零理解这个「把业务圈人需求翻译成 SQL」的库
source: sources/gitlab/sql_builder_v2 @ 2c500b2

nodes:
  - id: concepts                    # needs 里引用它
    title: 概念
    layer: 概念                     # 概念 / 组织 / 架构 / 模块
    needs: []                       # 前置节点 —— 理解它之前必须先理解谁
    artifact: sql-builder-v2-concepts   # 对应的笔记 slug（还没写也先填）
    status: planned                 # planned / drafted / done
    blurb: 圈人是什么、有哪些词、两套词汇
    children: []                    # 子节点，递归

  - id: core
    title: core 篇
    layer: 模块
    needs: [organization, architecture]
    artifact: sql-builder-v2-core
    status: planned
    blurb: 通用层：递归六层讲一遍
    children:
      - id: core-rule
        title: Rule[]
        layer: 概念
        needs: [core]
        artifact: sql-builder-v2-core-rule
        status: planned
        blurb: 四种形态 + buildWhere 怎么处理它
        children: []
```

**笔记那边只写两行**（`meta.json`）—— 层级和依赖关系**不在两处维护**：

```json
{ "tree": { "topic": "sql-builder-v2", "id": "core-rule" } }
```

**自动得到两样东西**：

| 得到什么 | 从哪来 |
|---|---|
| 首页的**树视图**（我在哪、下一步看什么、哪些还没写） | plan 的整棵树 |
| 每篇顶部的**「前置」区块** | plan 的 `needs` |

```
读这篇之前，你需要先知道
  ← 1. 概念    圈人是什么、有哪些词、两套词汇
  ← 2. 组织    仓库形状、三个包的分工、改哪里速查
```

**两个自动行为**（不用你操心）：

- 前置节点**还没写出来**时，显示成灰色的「待产出」，**不做成 404 死链接**
- `needs` 引用了不存在的 id → **`npm run check` 直接报错**，不会静默少一条

> **没挂树的笔记照常存在**，在首页显示在「未归类」区。
> 一棵树不是必须的 —— 只讲一个点的时候（「这个函数干什么」），不需要建树。

> **没挂树的笔记也要填 `topic`** —— 见「第 6 步 · 写 note.md」那一节。

#### 1.8 树是**边写边长**的，不是一次画完的

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==**第一次读代码，你只看得见「结构」，看不见「哪个分支信息量大」。**==

  信息量是在**写的时候**才暴露的 —— 写到某一节发现「这里塞不下」，
  那说明它是一个**新节点**。
```

**真实例子**（写「方言篇」时遇到的）：

```text
写到「17 个方法逐条对照」这一节，遇到 getStringArrayRule：

  · 它不在 SqlDialect 接口里，而在 utils.ts 里按 dbType if/else
  · 它有 ByteHouse / Doris / MySql 三个分支
  · 它还要一个 columnType 参数（array / string）
  · 它只在 relation.ts 一处被调用
  · 它和接口里的 jsonArrayContainsRule 是**两套并存的机制**
  · 它里面有 MySql 分支 —— 说明写于「还支持三个库」的年代

  → 这一节写不下。==它不是「方言层的一个方法」，它是一条独立的架构裂缝。==
```

#### 1.8.1 什么时候该长出新节点

```compare
first: 写作时的信号
head: [意味着什么, 怎么办]
rows:
  - 「这里得先说清 X 才能讲 Y」: ["X 是 Y 的**前置**", "给 X 一个节点，加进 needs"]
  - 「这一节写了三段还没讲完」: ["它**大到需要分几节**", "给它一个节点"]
  - 「这个分支和主线不是一回事」: ["它是**旁路**", "给它一个节点，或并入已有的旁路节点"]
  - 「这个词在别处也会用到」: ["它会被别的节点 needs", "**必须独立成篇**"]
  - 「这里和前面某一节重复了」: ["两个节点**边界划错了**", "合并或重新切"]
```

#### 1.8.2 怎么维护

```callout
tone: green
icon: ✅
text: |
  **每写完一篇，回头改一次 `plans/<topic>.yaml`。**

  - 发现新节点 → 加进去，填 `needs` 和 `blurb`
  - 发现两篇重复 → 合并，把 `artifact` 指到同一处
  - 发现某篇太大 → 拆成两个节点
  - 写完了 → `status: drafted`

  ==plan 不是「开工前画的图」，是**一直在改的施工图**。==
```

```callout
tone: amber
icon: ⚠
text: |
  **但要克制。** 不是每个「写不下」都要开新篇。

  先问：**它能被别的节点 `needs` 吗？**
  - 能 → 独立成篇（否则读者要跳进另一篇中间找）
  - 不能，而且只有父节点用它 → 就是父节点的一节，写长点没关系

  ==新节点要有「别人也需要它」这个理由，不能只是「它挺大」。==
```

### 第 2 步 · 找到卡点

用户可能明说（「Flink CDC 和 CDC 有什么区别」），也可能没说（只粘了一篇文档）。

没说的时候，从这些信号里找：

- 原文里**篇幅最长但最抽象**的那一段
- 用户**加粗、划线、单独贴出来**的部分
- 出现了**三个以上并列概念**的地方
- **流程/链路**类描述（「先…然后…再…」）
- 任何**反直觉**的结论

一句话：**卡点通常是「需要读者在脑子里维护状态或追踪顺序」的地方。**

### 第 3 步 · 拆骨架

把内容切成 **3~7 个 h2 章节**，每章回答一个具体问题。

写之前先问自己：**如果只留 5 段，留哪 5 段？** 其余的删掉。

**如果走过了第 1 步，骨架直接来自知识树的节点**，不用重新想。

### 第 4 步 · 逐段过一遍，决定画哪些图

**这一步不是「挑几个重点画图」，是「把每一段都过一遍」。**

做法：把骨架里的每一段读一遍，对每一段问一句 ——

> **这一段描述的是「空间 / 顺序 / 状态 / 归属」吗？**
> 是 → 它为什么还是文字？

命中就画。判据和反例见「原则 ①」。==这一步的产出是一张「哪几段要画图」的清单，
而不是「挑三个卡点」。==

> 下面的表是**起点，不是清单**。找不到合适的就改积木、拼组合、或自己画（原则 ⑥），
> 别把内容削足适履地塞进表里 —— 但也别因为「没有现成积木」就退回文字。

| 原文里出现的是 | 用什么 | 为什么 |
|---|---|---|
| 「先 A，再 B，然后 C」的链路/分层 | `lane-stack` | 顺序用文字描述，读者要自己排队 |
| 有**分支或汇合**的流程 | `flow` | 一条直线讲不了「分两路再合起来」 |
| 「某东西从 X 变成了 Y」 | `journey` | 状态变化是文字最大的盲区 |
| 三个以上方案/概念的横向对比 | `compare` | 表格比排比句快十倍 |
| 一堆**没有先后关系**的并列概念 | `cards` | 用文字排会很平，卡片能一眼扫完 |
| 「2020 年…2022 年…」的演进 | `timeline` | 时间顺序需要视觉锚点 |
| 调用链、握手过程 | `seq` | 参与者 + 消息顺序 + **自动激活条** + 时间段框 |
| 决策定位（重要度 × 紧急度） | `matrix` | 两维定位用表格看不出来 |
| 类层次、目录树、对象嵌套 | `tree` | 层级关系需要缩进感 |
| 反直觉的点、坑、一句话结论 | `callout` | 需要跳出正文节奏 |
| 正例/反例清单 | `checklist` | 勾叉比「应该/不应该」直观 |

#### 陷阱：拿箭头当排版用

==规则表告诉你「并列的概念该用 `cards`」，但真正会犯的错不是选错积木，
而是**积木挑对了、箭头却多画了**。==

````callout
tone: red
icon: ↗
text: |
  几个**并列**的东西（一个结构体的成员、一个容器的几项属性、同一层的几种选择），
  被一条条边串起来 —— 读起来立刻变成「A 导致 B」或者「先 A 后 B」。

  **我犯过一次，被用户当场指出来。** 原因很具体，值得记：

  我想让三个并列的成员待在一个 `groups` 框里、排成一列，
  而 **`flow` 只给「同一列且首尾相连」的节点画那个框** ——
  于是就顺手补了两条**空边**，纯为了布局，没有任何语义。

  ```
  struct sock 下面挂着：接收队列 / 发送队列 / 连接状态
  它们完全并列  →  却画成了  接收队列 → 发送队列 → 连接状态
  ```

  **换 `tree` 就对了**：它用缩进和肘形线，天然表达归属而不是先后，
  节点还支持 `tone`（可以把「两条队列」染成同一个色）。

  | 你其实想说 | 别用 | 用 |
  |---|---|---|
  | 这几个东西**都属于** X | `flow` + 空边 | `tree` |
  | 这几个东西**并列对比** | `flow` + 空边 | `compare` |
  | 这几个东西是**一份清单** | `flow` + 空边 | `cards` |
````

**自检**：把每条边读一遍，问自己「**这条边代表什么关系**」。

- 说得出来（指向 / 导致 / 然后 / 交给）→ 留着，**空 `label` 不是罪**
  （一条 ①②③④ 的链，边不带标签也成立，因为你仍然说得出那个「然后」）
- 说不出来 → 它就是排版边。删掉，或者按上表换积木。

!!顺带一条：**别拿节点当旁白**。!!「从这里开始分叉」这种话不是一个东西，
它是一个**过渡句**。把它做成节点、再用箭头指过去，等于在图里插了一句正文 ——
该写在图外面。

### 第 5 步 · 决定哪里必须做成交互

判据：**用一句话说不清「A 和 B 差在哪」，但让用户亲手跑一遍就秒懂 → 做 `demo`。**

典型：轮询 vs CDC、乐观锁 vs 悲观锁、B+ 树插入 vs 删除、
不同隔离级别的并发异常。

写 demo 需要三步（详见 `references/blocks.md`）：
1. `assets/app.js` 的 `WIDGETS` 里注册一个控件函数
2. 在 `note.md` 里用 `demo` 积木声明外壳和分栏
3. 两边靠 `log` 这个 key 对接

> 如果只是**顺序**，别做交互，画 `lane-stack` 就够。
> 交互有成本，只在「静态图讲不清」时才用。

#### `meta.json` 填什么

**没挂树的笔记，记得填 `topic`。**

「未归类」区默认**按主题分组**，分组轴就是 `meta.json` 里的 `topic`：

```json
{ "topic": "Flink" }
```

```callout
tone: amber
icon: ⚠
text: |
  ==**为什么不用 tags 分组？**==

  因为这个仓库的实测数据（**2026-09-30 快照**）：

  | | |
  |---|---|
  | 11 篇未归类笔记 | **51 个标签**（去重 37 个）|
  | 每篇平均 | **4.6 个标签** |
  | 覆盖 ≥2 篇的标签 | 只有 11 个 |

  而且大标签是**横切**的 —— 一篇「算子和函数」的标签是
  `Flink · 算子 · StreamOperator · 状态 · Checkpoint`，
  按标签分组它要出现在 **5 个组**里，反而比平铺还乱。

  ++标签适合**筛选**（首页已经有标签 chip 了），不适合**分组**。++

```

写 `topic` 的三条规矩：

| 规矩 | 为什么 |
|---|---|
| **一篇一个** | 它是单一归属。多归属会让同一张卡片重复出现 |
| **写得像人话** | 它是给人看的分组标题，不是给机器匹配的 key |
| **≈ 3 篇一组最舒服** | 一组一篇也能接受，但超过七八组就该合了 |

```compare

head: [好处, 代价]
rows:

```

> 不填 `topic` 的会落在「其他」组里 —— **不会报错，也不会丢**，
> 但别人就看不出它属于哪一块。

### 第 7 步 · 校验、构建、量图

```bash

npm run view -- <slug>     # 构建 + 在浏览器打开
npm run visual-check       # 无头浏览器真的去量每个积木有没有溢出

#### 但真正的回路是「写完一块就看一块」

```bash
npm run block -- <slug> --list    # 这一篇有哪些块（编号 + 行号 + 语言）

```

```callout
tone: red
icon: ⚠
quote: true
text: |

  一篇 22 个积木的笔记，问题会**一次性**暴露，然后每个都要单独一轮
  「改 → 构建 → 截图 → 看」。实测：22 个积木、19 张截图、8 个问题。

  所以写图的时候不要往下写 —— **停一下，跑 `npm run block` 看一眼**。
```

`npm run check` 必须过。它报的每一类问题都对应一个真实踩过的坑：

- **积木名拼错** → 会静默退化成普通代码块，页面看着正常但图没了
- **YAML 语法错** → 定位到文件和行号，并回显原始内容
- **缺 `quiz`** → 违反本仓库约定（见「硬约束」）

```callout

  ==构建通过 ≠ 画对了。== 这条踩过五次，每次 `npm run check` 都是绿的。

  **改了样式之后必须跑 `visual-check`，再截图看一眼。**
```

#### 但它量不了「挤不挤」

````callout
tone: amber
icon: ⚠
text: |
  ==`visual-check` 判的是**有没有重叠**（TOL = 2px），不是**读起来顺不顺**。==

  真实例子：一张 `flow` 上有两条边标签，横向间隙 **9px** —— 检测器判 ✓，
  但两条语义不同的标签读起来像**一句**（「只能进「值」的位置 决定这支行不行」）。

  ```
  只影响「值」      决定行不行        ← 间隙 9px，检测器过，但读着像一句
  ```

  ++所以「检测器过了」不等于「这图好看」。还得自己看一眼。++

  一个实用的经验判据：**把相邻的标签连起来读一遍**。
  如果读成了一句有语义的话，就该把其中一个改短（或删）。
````

#### 绿灯是怎么做到「真的对」的

`visual-check` 不只看溢出。它还会查这些**所谓「渲染出来但不是你想的那样」**：

| 查什么 | 不查会怎样 |
|---|---|
| `flow` 的边有没有穿过无关节点 | 看着像流程真的从那个节点走过 |
| 边标签有没有压在节点上 | 字被框挡住 |
| 两个边标签有没有叠在一起 | 叠成乱码（「podmup.pod重建down」） |
| 有没有真的画出来 | 绘制抛异常 → 空 SVG，而布局检查全绿 |
| **控件自己拼的几块之间有没有留白** | 没套那层带 `gap` 的 wrapper → 四块**紧贴着**，而所有检查都是绿的 |

#### ⚠️ `visual-check` 曾经会串页 —— 真凶是共用的临时文件

````callout
tone: red
icon: 🩸
text: |
  **症状**：==报出来的问题属于**别的笔记**。==

  最清楚的一次：报 `sql-builder-v2-crowd` 有「边 `rv→expr` 穿过了节点 `rc`」——
  而 crowd 那张图里**根本没有** `rv` / `rc` / `expr` 这些节点，
  它们是 `sql-builder-v2-core-rule` 的。

  还有：同一份代码连跑三次，分别挂 **2 处 / 1 处 / 0 处**，每次挂的是**不同的笔记**。

  **误诊了很久。** 当时的解释是「机器满载、布局还没稳定」。
  加载慢最多让**测量**有噪声；==把整页搞错，只能是文件被换了。==
````

**真凶**：临时页面用的是固定路径。

```js
const tmp = path.join(ROOT, 'node_modules', '.vc-tmp.html');   // ❌ 全局唯一
```

而 worktree 的 `node_modules` 是**软链到主仓库**的 ——
**这正是本 skill 推荐的省事做法**：

```
kh-ipc/node_modules        ──软链──→  knowledge-html/node_modules
kh-os/node_modules         ──软链──→  knowledge-html/node_modules
                                          ↑ 两边都写 .vc-tmp.html
```

于是：

```
会话 A 写入 crowd 的页面
会话 B 写入 core-rule 的页面      ← 覆盖掉 A 刚写的
会话 A 的 Chrome 加载 file://…/.vc-tmp.html   ← 读到的是 core-rule 的页面
```

A 的探针忠实地量了 core-rule 的图，然后把这些结果**记在 crowd 头上**。
整个过程没有任何报错。

```callout
tone: amber
icon: 🧱
text: |
  **两条要记住的：**

  ① ==**任何写临时文件的工具，路径必须带 PID 或随机后缀。**==
  一个「全局唯一」的临时路径，在单会话时代永远是对的，
  在多会话时代永远会串 —— 而且不报错。

  ② **一个省事的约定（软链 `node_modules`）制造了一份跨会话的共享可变状态。**
  ==推荐一个约定的时候，要顺手想一想它把什么东西变成了共享的。==
```

修完之后的判定规则（`ATTEMPTS = 3`）仍然保留 —— 噪声还在，只是不再是主因：

| 三次的结果 | 判定 |
|---|---|
| 任一次干净 | ✅ 通过。中途挂过就报一条 `⚠ 第 N 次才通过`（不阻塞） |
| 三次都挂、诊断**一样** | ✗ 真的，阻塞 |
| 三次都挂、诊断**不一样** | ⚠ 负载导致，**不阻塞** |
| 三次都没拿到数据 | ✗ 阻塞（探针自己坏了） |

```

### 第 8 步 · 交付前的六次复盘

改稿多轮之后内容一定会「长歪」。**每次都有具体动作，不是「再读一遍」。**

#### 复盘 ① · 术语审计

**用任何术语前，读者知道这是什么吗？**

把正文里的代码标识符列出来，看哪些没在概念章节出现过：

```bash
grep -oE '`[A-Za-z_][A-Za-z0-9_.]{2,}`' notes/<slug>/note.md | sort -u
```

**判断标准**：术语如果在「定义它」之前就被使用了，就是堵塞点。
处理：在开头加一个「先搞清几个词」的章节。

#### 复盘 ①b · 数字和事实回源码核实

**凡是写进文档的数字，都要回源码数一遍。**

> **手边没有源码、只能靠查的时候**，怎么查（用什么语言、信哪些来源、哪个工具干哪件事），
> 见「原则 ②」的[「怎么查」](#怎么查用什么语言信谁用哪个工具)一节。
> 那一节还讲了一件事：==二手转述会丢掉限定条件== —— 这正是下面这类事故的根因。

真实事故：文档里写「这个接口有 14 个方法」，实际 **17 个**。
同一个错误在架构图、正文、速查表里各出现一次，**三轮都没人发现**。

```callout
tone: red
icon: ⚠
text: |
  ==**但光数数字不够 —— 机制也要核。**==

  第二个真实事故：文档里写「`countSql` 包一层是因为展示列会 LEFT JOIN 出重复行」。
  数字都对、术语都对、句子通顺 —— **但机制是编的**。

  回源码一看，两个错：

  | 我写的 | 事实 |
  |---|---|
  | 展示列会 LEFT JOIN 出重复行 | 展示列**根本不参与** `countSql`，它用的是 `uidsSql` |
  | 包一层才数的是人不数行 | ==包一层**不会去重**==；而且这里也没有东西需要去重 |

  怎么发现的？别人看了图觉得不对，去问了一圈才确认。
  ==靠外部反馈才发现，说明自己那一轮核实是缺的。==
```

**两类要核的东西，别只核第一类：**

```compare
first: 写下的东西
head: [长什么样, 怎么核]
rows:
  - 数字:
      - "「14 个方法」「1700 行」「5 种类型」"
      - "`grep -c` / `wc -l` —— 命令一跑就知道"
  - "**机制**（因果关系）":
      - "「包一层**因为**…」「校验分两段**是因为**…」"
      - { text: "==把那条代码路径读出来，看它到底会不会那样==", tone: amber }
```

```callout
tone: violet
icon: 💡
text: |
  **机制比数字危险，因为它看着更有道理。**

  数字错了读者会怀疑（「真的 17 个？」），但机制错了读者**会信** ——
  因为它语法通、逻辑顺、还带着解释力。

  ++判别方法：写下「因为…」之前，问自己「我是读到的，还是推出来的？」++
  推出来的，就得回去读。
```

容易写错的几类数字：**接口方法数、文件行数、枚举取值数、调用点数量**。

```bash
grep -cE '^\s+[a-zA-Z]+\(' <接口文件>     # 数方法
wc -l <文件>                              # 数行数
grep -c '^\s*[A-Z_]* =' <枚举文件>        # 数枚举值
```

> 数字错了比文字错了更危险 —— ==读者会信数字，而且不会去数==。

#### 复盘 ② · 每个概念必须配例子

```callout
tone: red
icon: ⚠
text: |
  ==只给定义不给例子，等于没定义。==

  「软删除是一种标记删除的机制」—— 读者完全不知道那是什么。
```

**每个概念至少给三样**（以「软删除」为例）：

| 给什么 | 例子 |
|---|---|
| 一句话定义 | 「删除时不真删，只打个标记」 |
| **长什么样**（最重要） | `{ id: 7, deleted_at: '2026-03-01 10:00:00' }` |
| 和相邻概念的区别 | 「普通删除是行没了；软删除是行还在，查询要额外加 `where deleted_at is null`」 |

#### 复盘 ⑤ · 篇幅复盘

**改过几轮之后，篇幅一定会往「好写的方向」歪，不是往「读者需要的方向」。**

真实数据（写 `notes/insight-dsl` 那次）：

```text

**读者最想看的那节只排第五，而「测试」排第二。**

根因不是偷懒 —— 是**「反直觉」「测试」这类内容每一点都能独立成段，好写；而「怎么工作」要讲清一条链上的每一步，难写**。写着写着就歪了。

      - "短"
  - 删掉之后主题就讲不明白了:
      - "它是主线"
      - { text: "==最长==", tone: green }

```bash

  78 行   06 · 怎么保证它是对的  ← 从 177 压到 78

#### 复盘 ⑦ · 图解缺口审计

==这是和复盘 ⑤ 并列的最重要一步，因为它直接决定「这份东西为什么存在」。==

**做法：把正文里所有描述「空间 / 顺序 / 状态」的句子捞出来，逐条问一句「它为什么还是文字」。**

```bash
# 把这些「叙述性信号词」全 grep 出来 —— 命中的每一行都是缺口候选
grep -nE '先|然后|接着|之后|最后|变成|指向|包含|位于|上一层|下一层|依次|交替' notes/<slug>/note.md \
  | grep -v '^\s*[0-9]*:\s*[|>#]'
```

命中之后，按三种情况处理：

```compare
first: 情况
head: [怎么办]
rows:
  - 确实在讲顺序/位置/状态: [{ text: "补图。优先用现成积木；没有合适的就按原则 ⑥ 的四条路走", tone: green }]
  - 是个判断或理由（「为什么不用 X」）: ["留着。这是图替代不了的"]
  - 是操作清单（①②③④）: ["留着。它没有空间关系，画成图更绕"]
```

**还有一个更快的自检**：写完一篇之后，把所有的 `` ``` `` 围栏块和正文段落**分别数一遍**。

```bash
grep -c '^```' notes/<slug>/note.md          # 图/积木用了多少个
awk 'BEGIN{n=0} /^```/{f=!f; next} !f && NF && $0 !~ /^[#>|-]/ {n++} END{print n}' notes/<slug>/note.md
```

> 正文段落数 ÷ 2 就是「多少段配一张图」。
> ==如果这个比值大于 3，回头看看是不是有几段该画没画。==

**第二条检查：关键图的信息量（原则 ②）。**

逐个打开这一篇的图，问三句：里面有没有「量」？有没有「方向」？盖住正文它还讲得通吗？
答不上来的那张，回去查原理重画。

### 控件里要写强调文字时，用 `richText`

积木那边的 `==强调==` / `**重音**` / `` `代码` `` 是**构建期**由 `tools/lib/blocks.mjs`
处理的，控件跑在浏览器里拿不到它 —— 所以 `app.js` 里有一份最小的 `richText(host, text)`。

```js
richText(el('p', 'my-note'), '这一步 ==很关键==，注意 `read()` 的返回值');
```

==不写它就直接 `textContent` 的话，页面上会字面显示 `==很关键==`。==
它只认那三种标记，别往里加东西 —— 两边逻辑越像，越容易漂移。

### 加新积木时的两条硬要求

1. **`flow` 的能力边界要记住**：它是「测量 + 直连」，没有边路由。
   稠密图会翻车 —— 翻车就拆图、改用 `compare` 列表格、或换 `arch`。
2. **`flow` 横向边上的标签，宽度上限是 30px。**
   行内间隙默认 `.flowd-row { gap: 30px }`，而 `.flowd.has-groups .flowd-row`
   才是 72px —— 也就是说：**写了 `groups`（哪怕只有一个）才有地方放横向标签。**

   所以「创建 → 就绪 → 运行」这种横排链，标签一超过 3 个汉字就会被两边的框压住。
   两条出路：

   - **给这个 flow 加一个 `groups`**（一个框住全部节点也行）—— 顺便拿到「这几个是一伙的」这层信息
   - **把横排改竖排** —— `.flowd-grid { gap: 58px }`，竖向标签有 58px

   ==这次画「进程五态」时，横排四个状态 + 六条标签，前两版全被压住；加了 `groups` 才一次过。==
3. **`flow` 里单节点的 `groups` 会把标签挤没。**
   框只包住一个窄节点时，`groups[].label` 会折成两三行、盖住下面的连线。
   要么把 label 压到 3~4 个字，要么让这个组包住**整张图的所有节点**（框顶就跑到最上面去了）。

   ==但「包住所有节点」也有翻车的时候==：节点分两三行时，框会变成一个盖住整张图的大色块，
   比不画还难看。这次画「索引数据块 → 数据块」时试过，最后退回**不加 groups**。
4. **两个区域框水平相邻、又各自跨多行时，会重叠。**
   这次画「两条修复路径」时，两个 `groups` 各包 2~3 行，实测重叠了 40px。
   出路：让每个组只包**一行**节点，或者干脆**拆成两张图** ——
   图上写着「路径一 / 路径二」的两块东西，本来也常常该是两张图。

5. **不同 row 的节点连向同一个下游，同样会穿过中间那一行。**
   不只是「同一 row 的两个节点各自往下连」会翻车 —— 排成两行的 M1、M2
   各自连向下游的 GRQ 时，`M1 → GRQ` 一样会从 `M2` 身上穿过去。
   ++把并列的节点放进同一 row。++

6. **`flow` 画不了「跳过中间那一层」的拓扑。**
   想表达「A 到 C，但绕过了中间的 B」，边必然穿过 B，`visual-check` 会直接报
   `边 A→C 穿过了无关节点「B」`。

   ++改用 `journey` 表达「数据少坐了一站」++ —— 每一站是一个 `tag`，
   绕过的那一站就是不写它。语义上比硬画一条穿越线清楚得多。
7. **响应式目前按视口宽度写（`@media`）**。如果积木可能被放进窄容器
   （比如并排两栏），应该改用 **container queries**（Chrome 105 / FF 110 / Safari 16，
   已广泛可用）。当前所有积木都还没改。

### 图的视觉规范

图的「丑」通常不是配色问题，是**结构太单一**。四条规矩：

#### ① 节点用语义类型，不要纯文字盒子

用 `kind` 标出节点是什么（`backend` / `database` / `cloud` / `security` …）——
它会自动带图标和配色。==读者看图标就知道这是数据库还是服务，不用读文字。==

#### ② 用区域框表达归属

几个节点属于同一个 VPC / 同一个部署单元 / 同一层？用 `groups` 圈起来。

```callout
tone: violet
icon: 💡
text: |
  ==「结构单一」的最大来源就是没有区域框。==
  平铺的节点看不出「谁和谁是一伙的」，读者要自己在脑子里分组。
```

#### ③ 开背景网格

`grid: true`。给图「工程图纸」的质感，也让大片空白不那么飘。

#### ④ 边要有语义

- 同步实线、异步虚线 —— 别混用
- 关键路径用 `tone` 上色（比如绿色的 HTTPS、红色的鉴权）
- **每条边都该有标签**（协议、动作、方向），除非两端完全自明

#### ⑤ 文字不许互相压

用户点名过的一条，原话：

> 你在画图的时候要注意文字互相重叠的情况。
> 线可能你判断线的重叠比较有难度，==但判断文字重叠应该比较轻松，对吧？==
> 尽量不要出现文字被挡到的情况。

**为什么单拎出来**：字被压住不会报错，**字还在，只是读不通**。
它比「图没画出来」隐蔽得多 —— 出图看着是成功的，只是有一行字废了。

**最常见的成因只有一条：标签比它所在的那条缝还宽。**

```
   ┌──────────┐            ┌──────────┐
   │  节点 A   │   这条缝    │  节点 B   │
   └──────────┘            └──────────┘
        └──── 标签比缝宽就压到框上 ────┘
```

`flow` 里还有一种固定搭配会撞：**群组框的标签画在框的左上角，
而边标签默认落在那条缝的水平中点** —— 缝一窄，两个标签就叠在一起。

修法按优先级：

| 修法 | 说明 |
|---|---|
| 调节点位置 | 让缝变宽（改 `row`，或把节点拆开） |
| **`edges[].labelDx` / `labelDy`** | ==手动把边标签挪开。工具算不出「那里已经有群组标签了」，但作者一眼就知道该往哪挪== |
| 把标签改短 | 最后手段。**别为了塞下标签而把话说残** |

```callout
tone: green
icon: 🤖
text: |
  **这条已经进了探针，不用靠眼睛。**

  `npm run visual-check` 会报 `文字压文字：「…」↔「…」（重叠 Npx）`。
  它用 `Range` 取每个**文本节点自己的墨迹矩形**（不是父元素的盒子）——
  父盒子带 padding、跨行时是一整块，都会把「挨着」误判成「压着」。

  ++改完图一定要跑它。==构建通过 ≠ 画对了，这条踩过五次。==++
```

```callout
tone: amber
icon: ⚖
text: |
  **不查什么：文字被线 / 边框穿过。**

  那要判断「这条线是不是本来就应该在那儿」—— 机器判不了，
  人工排查的成本也高于收益（用户原话：==「如果是线和文字重叠，排查比较费时间的话，就不用管了」==）。

  所以探针只查**文字 vs 文字**：这条能机械判定，而且它才是真的读不通。
```

```callout
tone: green
icon: ✅
text: |
  这套规范学自 `archify` skill（`~/.agents/skills/archify`）。
  它的图值得当参照 —— 需要更复杂的图时，可以去读它的 SKILL.md 和 examples。
```

### 结构化图：调用 archify skill

archify 是一套完整的图渲染系统，能力**超出**我们自己的积木：节点的**语义类型**
（声明是 database / messagebus / cloud，自动带图标、配色和图例）、**精确区域框**、
**真边路由**，以及一个会量文字宽度、检测碰撞的校验器。

我们自己的积木是「半自动」的 —— 你给 `row`，它排位置，不做标签避让和碰撞检测。
两套工具各管一段，**按图的形状选**。

#### 它能画 5 种图

由 spec 里的 `diagram_type` 决定（`tools/archify.mjs` 会自动读）：

| diagram_type | 画什么 | 结构数组 |
|---|---|---|
| `architecture` | 系统组成、部署拓扑、依赖关系 | components · boundaries · connections |
| `workflow` | 跨角色的流程 | lanes · phases · mainPath · nodes · edges |
| `sequence` | 调用链、握手、时序 | participants · messages · activations |
| `dataflow` | 数据流水线 | stages · nodes · flows |
| `lifecycle` | 状态机、生命周期 | lanes · states · transitions |

写法参考 `~/.agents/skills/archify/examples/*.<type>.json`。

#### 什么时候该调 archify

| 用 archify | 用我们自己的积木 |
|---|---|
| 有**区域/边界**要表达归属（「这几个在同一个 VPC」） | 没有归属关系，就是一根轴或一列卡片 |
| 节点有**语义类型**（这是数据库、那是队列） | 节点就是纯文字盒子 |
| 需要**图例** | 不需要图例 |
| 形状是 DAG / 状态机 / 泳道 / 时序 / 阶段流水线 | 形状是时间轴 / 状态对照 / 两列匹配 / 行列表 |
| 要作为**独立图**交付、反复引用 | 图文混排成一节，要跟着页面换肤和重排 |

#### 它的硬边界（踩过）

- **边不能穿过无关节点。** archify 直接报
  `crosses component "xxx" (unrelated to this relationship)`，==它不会帮你绕过去==。
  遇到这种拓扑只能拆图、改布局、或手填 `route`/`via` 航点。
- **竖长的分层图别用 `architecture`，用 `lane-stack`。**
  `.archfig svg { width: 100% }` 会把 SVG 拉满容器宽度 ——
  一张 745×1483 的「五层堆叠」图放进 1280 宽的正文里，会变成 **2549px 高**，
  文字被放大到很夸张。==archify 适合宽高比接近 1:1 的拓扑图，不适合一列到底的层叠图。==

  这次画「谁能看见谁」（CPU / 内核 / 进程 / runtime / G 五层）就撞上了，
  改用 `lane-stack` 一次过 —— 它本来就是为「一层接一层」设计的，横着排，不拉高。
- **`architecture` 必须写顶层 `layout`，不写报的错完全看不出是这件事。**

  ```json
  "layout": { "mode": "grid", "origin": [60, 104], "cols": 4,
              "gapX": 48, "gapY": 84, "cellW": 186, "cellH": 62 }
  ```

  漏了它，六条报错全是 `Component "x" must include pos [x, y] when layout.mode is omitted`
  加 `has non-finite pos/size` —— ==它让你去给每个组件写坐标，但真正缺的是那个 `layout`。==
- **组件尺寸是每个显式声明的**（默认 120×60），不随 `layout.cellW` 变。
  标签长了要么裁文案，要么给它加 `size`。
- **跨行的边要显式写 `fromSide: "bottom"` / `toSide: "top"`。**
  上下相邻两行的节点，自动推断可能给出 `fromSide: "left"`，然后报
  `first segment does not honor inferred fromSide "left"` ——
  ==错误里说的方向和你看到的走向对不上，直接写上 bottom/top 最省事。==
- **`boundaries` 里的 `kind` 只有 `region` 和 `security-group` 两种**，
  而 `security-group` 画出来是**红色虚线框**。红色在别处一律表示「出事了」，
  知识图里没有这个含义，++默认用 `region`++。
- **边有几何下限**：微段短于 8px、两条边挤在同一条走廊里，都会判失败。
- 产出是**静态 SVG**，不跟着容器宽度重排。
- **`lifecycle` 的 lane 语义是写死的**，别拿它画通用状态机。
  `render-lifecycle.mjs` 里写死了：`lane: main` → 上排「阶段带」（5 列，y=126）、
  `lane: terminal` → 下排「结局带」（3 列，y=450）、**其它所有 lane 全挤在中间那条
  「事件带」**（只有 3 列，y=278，靠 `yOffset` 上下分开）。
  几何常量也是死的（`phaseXs: [94,248,402,556,710]`、`eventXs: [402,556,710]`）。

  ==拿「进程七态」试过：四个状态要横排、还要跨三行画挂起，label 碰撞报了二十几条。==
  **状态机用 `flow` + `shape: pill`，别用 `lifecycle`。**
  `lifecycle` 留给「一条主路径 + 几个中断 + 几个结局」那种形状。

#### 怎么调（已封装好）

```bash
# 1. 写 archify 的 JSON spec 放 archify/ 目录
#    参考 ~/.agents/skills/archify/examples/*.<type>.json（5 种类型都有例子）
# 2. 生成并抠图
node tools/archify.mjs archify/<名字>.json <名字>
# 3. 在 note.md 里用 arch 积木
```

```text
svg: <名字>              # 必填，对应 assets/arch/<名字>.svg
caption: 这张图说明什么    # 可选，图注
```

**抠出来的 SVG 自带「聚焦 + 关系追踪」**（点节点只看它和它连出去的关系）——
因为 archify 的 SVG 里留了 `data-node-id` / `data-edge-from` / `data-edge-to`，
`app.js` 按属性筛一遍就行。键盘也能用（Enter / Esc）。

**`tools/archify.mjs` 做了三件事**（这三件事不做会踩坑）：

1. 调 archify 的 `validate` + `deliver`（校验不过会直接报出诊断）
2. **只抠 SVG**（archify 的 HTML 有 600KB，但 SVG 本体只有 ~20KB）
3. **给它的 CSS 变量加 `--af-` 前缀** ——
   ==archify 在 `:root` 定义了 32 个变量，名字和我们完全一样（`--bg` / `--text` / `--panel`），
   直接嵌会把我们整页变成深色。==

两边都用 `data-theme` 属性，所以**深浅色天然同步**，不用额外处理。

#### archify 的校验值不值得用

**值得，而且这是它最值钱的部分。** 它会精确告诉你：

```text
Label "用户认证与鉴权流程" (~132px) is wider than component "gateway" (120px)
Label "请求" overlaps component "gateway"
  label rect: [286, 120, 48, 14]
  component "gateway" rect: [250, 80, 120, 60]
  Suggested fix: labelAt [310, 154] or labelDy +24
```

它**测量了文字宽度**、**检测了碰撞**、**给了具体坐标**。我们的积木完全不做这些。

## 版面与样式

### 改 theme.css，不要改单篇笔记

所有页面共用 `assets/theme.css` + `assets/blocks.css` + `assets/app.js`。
遇到这些症状，**改共享文件，一次全站生效**：

| 症状 | 改哪 |
|---|---|
| 屏幕利用率低 / 留白太多 | `theme.css` 的 `--shell` / `--prose` / `--gutter` |
| 某个积木在窄屏塌得不好 | `blocks.css` 里那个积木的 `@media` |
| 目录 / 交互别扭 | `app.js` + `lib/page.mjs` |
| 颜色不对 | `theme.css` 的 token |

**不要为了某一篇笔记在 `note.md` 里塞 `<style>`** —— 那是把全局问题当局部问题修，
下一篇还得再修一遍。

### 版面原则：文字窄，图宽

屏幕越宽，**不要把文字拉长**（长行伤可读性），而是把多出来的宽度给图。

`theme.css` 里三层控制：

- `--prose`（880px）管**文字元素**（`p` / `h2` / `h3` / `ul` / `.callout` / `.quiz`）
- `main` 的 `max-width`（1280px）管**整列上限**，防 4K 屏上积木被拉飞
- **积木不受 `--prose` 限制**，自动用满整列

判断一个新积木该不该限宽：**它主要是文字还是图形？** 文字限，图形不限。

### 行内强调与颜色：别让一种标记承担所有重点

| 写法 | 语义 | 颜色 |
|---|---|---|
| `==文字==` | 关键结论 / 最该记住的一句 | 蓝 |
| `!!文字!!` | 坑 / 反直觉 / 注意 | 橙 |
| `++文字++` | 正确做法 / 推荐 | 绿 |
| `**文字**` | 句子内的重音（降级用） | 加粗不变色 |

**一屏之内不要超过 3 个 `==`** —— 到处都是重点等于没有重点。
写完后扫一眼：如果整页加粗密密麻麻，说明该用彩色标记做取舍了。

#### `callout` 的颜色也一样 —— 别让红色承担所有重点

```callout
tone: red
icon: ⚠
text: |
  ==**这份 skill 自己踩过这个坑。**==

  有一轮自检时统计：48 个 `callout` 里 **36 个是红/橙**（75%）。
  然后逐条看内容 —— 红的那 20 个里**有一半根本不是警告**：

  | 写的内容 | 它其实是 |
  |---|---|
  | 「六层不是某个项目的专属结构」 | **结论** |
  | 「构建产物是全量的」 | **事实** |
  | 「`npm run check` 是全仓库的」 | **事实** |
  | 「多个会话共用一个工作目录才是根因」 | **诊断** |
  | 「每次交付完回头问一遍」 | **方法** |
  | 「优先点名 add」 | **规则** |

  ++红色一多，「这里真的会出事」就没人当回事了。++
```

**按这句话选颜色：这条是「会出错」，还是只是「值得知道」？**

| tone | 什么时候用 | 判据 |
|---|---|---|
| `red` | **真的会出事** | 会丢数据 / 会被拦 / 会静默出错 |
| `amber` | 注意、已知局限、容易忽略的规则 | 不遵守会返工，但不会立刻炸 |
| `violet` | **结论 / 洞察**（「所以…」） | 读到这里该记住的一句话 |
| `green` | 正确做法 / 已验证 | 照着做就对了 |
| `blue` | 入口提示（「先读第 0 步」这类导航） | 很少用 |
| `muted` | 纯事实陈述 | 不劝你做任何事 |

> 拿不准时问自己：**如果读者跳过这条，会发生什么？**
> 答「没影响，只是不知道」→ 不配红。

### 代码块：**先分行，再谈分色**

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==**粘一段单行 SQL 进笔记，等于没写。**==

  子句、权限、条件全挤在一行，读者要在脑子里自己断句。
  这跟「把图挤成一团」是同一种偷懒 —— 只是不容易被截图抓出来。
```

**两条规矩，按优先级：**

#### ① 分行 —— 一个子句一行，嵌套的缩进

```compare
first: 写法
head: [读者要做什么, 什么时候必须分行]
rows:
  - 一整行塞完:
      - { text: "在脑子里断句、数括号、找 AND 在哪", tone: red }
      - "永远不要。除非真的只有 `SELECT 1` 这么短"
  - 一个子句一行:
      - { text: "从上往下读，一眼看出结构", tone: green }
      - "SELECT / FROM / WHERE / GROUP BY 各占一行"
  - 嵌套再缩进:
      - { text: "子查询、AND 续行看层级", tone: green }
      - "子查询整体缩进两格；`AND` 接在下一行、再缩两格"
```

**实测对照**（`notes/insight-dsl` 那个交互）：

```text
❌ 挤成一行（真编译器就是这么输出的）
SELECT COUNT(*) AS `count` FROM (SELECT `u`.`uid` AS `uid` FROM `user_portraits_wide` AS `u` WHERE `u`.`staff_id` = 101 AND (TIMESTAMPDIFF(YEAR, `u`.`birthday`, CURRENT_DATE()) >= 18)) AS `t`

✅ 按子句分行
SELECT COUNT(*) AS `count`
FROM (
  SELECT `u`.`uid` AS `uid`
  FROM `user_portraits_wide` AS `u`
  WHERE `u`.`staff_id` = 101
    AND (TIMESTAMPDIFF(YEAR, `u`.`birthday`, CURRENT_DATE()) >= 18)
) AS `t`
```

```callout
tone: amber
icon: ⚠
text: |
  **但如果原文就是这样（比如真编译器的输出），分行之后要说明。**

  ==读者会以为「真代码就长这样」。==

  正确做法是分行展示 + 一句注明：

  > 语句内容跟真输出逐字相同；真输出是一整行（省字节），这里换了行。
  > **换行只是排版，不改变语义 —— SQL 本来就不看换行。**
```

#### ② 分色 —— 分的是**来源**，不是语法

```callout
tone: violet
icon: 💡
quote: true
text: |
  ==**不要做语法高亮（SELECT 蓝、字符串橙）—— 那是编辑器的事，不是笔记的事。**==

  笔记里分色的价值在另一件事：**一段代码里混了多个「来源」时，
  用颜色把来源分开。**
```

**照 `notes/insight-dsl` 那个交互的做法**：

```compare
first: 颜色
head: [代表什么, 为什么值得一色]
rows:
  - 琥珀:
      - "**权限** —— 演员身份决定的"
      - "它不是用户圈出来的，==读者最容易把它当成条件的一部分== "
  - 白（默认）:
      - "**用户圈的条件** —— 界面上点出来的"
      - "主体，不需要额外颜色"
  - 紫:
      - "**派生表达式** —— 逻辑字段到物理列的变换"
      - "`age` → `TIMESTAMPDIFF(YEAR, birthday, ...)`，==这是最反直觉的一层=="
```

**判据**：一段代码里如果有 **2 个以上来源不同**的东西混在一起，
分色讲得清；只有一种来源就别上色（纯噪音）。

#### ③ 做成交互时，分色是**自动**的

那个演示不是手写的 HTML —— 它按语义片段拼出来：

#### 第七次：`--virtual-time-budget` 下 CSS 过渡不会被推进 —— 截图会骗你

````callout
tone: red
icon: 📸
text: |
  **点一下控件再截图，截到的是点击前的样式 —— 而 DOM 里 class 已经是对的。**

  实测：一个「选中态」按钮。点第二个之后，
  ==class 和计算样式完全对调== —— 掉了 `.on` 的那个显示成选中态，加上 `.on` 的显示成未选中。

  ```
  0 [nw-seg-btn]     bg=rgb(234,241,255)   ← 看起来是选中的，其实不是
  1 [nw-seg-btn on]  bg=rgb(255,255,255)   ← 明明是选中的
  ```
````

**根因**：所有无头截图都跑在 `--virtual-time-budget` 下，而**那个模式下 CSS 过渡（transition）不会随虚拟时间推进** ——
元素停在过渡的起点，再也不会动。

**怎么确认是它**：注入 `* { transition: none !important }` 之后再读一次计算样式，样式立刻归位。
上面那个例子，关掉过渡后两个按钮的颜色正好对调回来。

**已经修在工具里**：`tools/block.mjs` 生成的预览页现在带一条

```css
*, *::before, *::after { transition: none !important; animation: none !important; }
```

==过渡只在值**改变**时触发，初次渲染不受影响== —— 所以量静态布局的 `visual-check` 基本不受影响，
只有「点一下再截图」这条路会踩到。

**自己写截图脚本时也要记得加这条**，否则会像我一样，花时间去找一个根本不存在的 CSS bug。

#### 第五次：archify 的共用 CSS 被削薄

```callout
tone: red
icon: 🌗
text: |
  **写过 `transition: background` 的元素，只要它的背景是 `color-mix(...)`，
  换主题时颜色会卡在旧主题上。**

  不是过渡一下就到了 —— 是**永远不更新**，直到这个元素因为别的原因重新布局。

  ==这个 bug 只在切主题时出现，`npm run check` / `visual-check` 全是绿的。==
  （它们不切主题，只量布局。）
```

**真实经过**（写「三种 IPC 数据流」那个控件时）：

| | |
|---|---|
| 症状 | 浅色模式下，未激活的格子渲染成深色；但同一张卡片的外壳是白的 |
| 第一反应 | 以为变量作用域错了 —— 打印 `--surface-2`，发现是 `#f2f4f7`（正确的浅色） |
| 打印元素的实际值 | `oklab(0.283 0.003 -0.029)` —— 一个**暗色**，和变量对不上 |
| 排除法 | 把 `transition: background .2s` 删掉，**立刻正确**（`rgb(234,231,246)`，正是手算出来的淡紫） |

**根因**：元素在 `data-theme` 还是 `dark` 时完成首次渲染，主题切成 `light` 后
背景值要变，但 Chrome 对**两个 `color-mix()` 计算值之间的插值**处理不了，
于是停在起点。改成普通 `var(--x)` 的颜色不会中招（那是两个具体颜色之间的插值）。

++规矩：给「背景是 `color-mix`」的元素写 transition 时，只写具体属性，不写 `background`、更不要写 `all`。++

```css
/* ❌ 换主题会卡住 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent); transition: .18s; }

/* ✅ 只过渡真正会动的东西 */
.pill { background: color-mix(in srgb, var(--blue) 14%, transparent);
        transition: color .18s, box-shadow .18s; }
```

**查法**（一条命令扫全站）：

```bash
python3 - <<'EOF'
import re, pathlib
css = pathlib.Path('assets/blocks.css').read_text()
for sel, body in re.findall(r'([^{}]+)\{([^}]*)\}', css):
    if 'transition' not in body: continue
    if not any('color-mix' in l for l in body.split(';') if l.strip().startswith('background')): continue
    t = re.search(r'transition:\s*([^;]+)', body).group(1).strip()
    if 'background' in t or re.fullmatch(r'\.?\d+(\.\d+)?(m?s)?', t):
        print(sel.strip()[:60], '→', t)
EOF
```

==写新控件时顺手跑一次，比等用户在浅色模式下发现便宜得多。==

#### 改共享文件的四条硬规矩

1. **改一条 CSS 规则就替换那一条，别用大区间。** 非要大改，改完 grep 一遍原来的选择器。
2. **绝对定位的装饰元素要考虑「会不会超出容器」。** 加了就配 padding。
3. **坐标计算必须统一参照系。** 容器一有 padding，相对不同父元素量的坐标就会错开。
4. **放进 grid / flex 的元素要设 `min-width: 0`**，否则内容会把容器撑破。
5. **`background: color-mix(...)` 的元素，别写 `transition: background` 或 `transition: .2s`。**
   换主题时 Chrome 插值不了两个 `color-mix` 计算值，颜色会卡在旧主题上 ——
   `visual-check` 抓不到（它不切主题）。详见上面「第六次」。

## 变体：源码通读

用户说「读 xxx 代码，画出架构」时，**不要从 README 开始读** —— README 经常过期。

```callout
tone: amber
icon: ⚠
text: |
  **也不要直接从架构开始写。** 源码通读同样要先过原则 ④ 的三层：
  先讲清楚**这个领域的概念**（有哪些词、对应什么现实事物），
  再讲**怎么组织**，最后才是**代码怎么实现**。

  跳过概念层，得到的就是一份只有作者看得懂的架构图。
```

按这个顺序读：

1. **摸依赖图** —— 一条命令看出谁依赖谁：
   ```bash
   find . -name '*.ts' -not -path '*/node_modules/*' | while read f; do
     echo "$f → $(grep -oE "from '[^']+'" "$f" | sed "s/from '//;s/'//" \
       | grep -E '^(\.|src|@)' | tr '\n' ' ')"
   done
   ```
   横切的（被所有层依赖）和纵深的（依赖所有层）一眼可见。
2. **按行数排序** —— 最大的文件就是复杂度所在，也是卡点所在。
3. **读入口** —— `index.ts` / `context.ts` / 工厂，它们定义了架构骨架。
4. **找反直觉的实现** —— 这是最值钱的卡点。信号：
   - 注释里出现「为什么不用 X」的解释
   - 有一行代码做了意料之外的事
   - 到处都在 `?? new XxxDefault()` 兜底（往往是个真实的坑）
   - 常量里出现取模 / 哈希分片
   - 有一个 `switch` 的 `default` 直接 `throw`
5. **确认，不要猜** —— 断言「这里会 throw」之前，先把那几行读出来。

**结构用现有积木就能画好**（`lane-stack` + 分组正好表达包的边界）。
真正需要新表达的是**机制**，不是结构 —— 力气花在那里。

### 把「分派逻辑」图形化

源码通读最值钱的产出，是**把代码里的分派点变成一张表或一个交互**。

判据很直接：**代码里有 `switch` / `if-else` 分派的地方，就是该画图的地方。**

```compare
first: 代码里是什么
head: [变成什么, 例子]
rows:
  - 一个 switch 分派节点类型:
      - "一张「输入形态 → 生成什么」的表"
      - "`compileNode` 的四种叶子各编译成什么"
  - 一个 op 分派:
      - "一张「操作符 → SQL 片段」的表"
      - "`applyComparison` 按 op 分派到 where / whereIn / whereBetween / whereRaw"
  - 一个「按输入挑分支」的校验器:
      - "一个「喂坏输入，看它在哪一步被拦」的交互"
      - "`validateStructure` / `validateSemantics` 各自拦什么"
  - 一条「输入 → 几道处理 → 输出」的链:
      - "一个分步执行的交互"
      - "「一个条件走完三段管道」"
```

```callout
tone: violet
icon: 💡
text: |
  ==**「分派」是代码里信息密度最高的地方。**==

  一个函数如果有 8 个分支，读代码要来回跳 8 次；
  画成一张表，一眼扫完。

  ++而且表能顺带回答「漏了哪个分支」—— 代码里看不出来，表里缺一行就很显眼。++
```

**反过来也成立**：如果一个东西没有分派，别硬画。

  - 一段几十行的顺序逻辑:

## 变体：拆解一个东西

用户说「拆解一下 X」时，用这六个问题逐条回答，写进 `spec` 积木：

| 维度 | 问什么 |
|---|---|
| **输入** | 喂给它什么？什么类型、什么形态？ |
| **处理** | 中间做了什么？有哪几步？ |
| **输出** | 吐出什么？给谁用？ |
| **怎么调用** | 别人实际怎么用它？贴一段真实调用代码 |
| **为什么这么设计** | 作者为什么这样选？**注释里常藏着答案** |
| **业务价值** | 它到底解决了什么问题？没有它会怎样？ |

```callout
tone: amber
icon: ⚠
text: |
  ==但不是所有东西都值得拆。==
```

**先判断该不该拆**：在代码里搜一下它被调用几处。

- **调用很多（几十处）或位于主干** → 值得拆，六个维度都写
- **只有 1~3 处调用** → 用 `compare` 一行说清就够，硬拆六个维度是凑字数
- **`src/` 里根本搜不到** → 它是被动依赖（编译期 / 间接），没有输入输出可言，
  归到一张表里说明「为什么在 deps 里」即可

> 判断依据不是「用户让我拆」，是**这个东西本身有没有那么多可讲的**。
> 拆一个只有两处调用的工具库，写出来的六段全是废话。

### 先搞清楚：这不是分支的问题

```callout
tone: violet
icon: ⚠
quote: true
text: |
  ==多个会话**共用一个工作目录**，才是根因。==

  开分支解决不了 —— `git checkout -b` 只改 HEAD 指向哪，
  **工作区里的文件一个都没变**。两个 agent 在同一目录里，改的还是同一批文件。
```

**真实发生过**（2026-09-29）：

```text
提交 8575596
信息：crm-local-stack：命令速查提到 01 节，原理和流程图往后挪

实际：44 个文件，+39461 行，其中包括
  notes/data-admin-to-ui/note.md        428 行   ← 另一个会话 17:41 建的
  dist/data-admin-to-ui.html           6382 行
  archify/data-admin-flow.json          112 行
  assets/arch/data-admin-flow.svg       138 行
```

反向也一样：另一个提交用 `git add -A` 把别人做到一半的 13 个 `meta.json` 一并带走了。

三个设计放大了它 —— 它们本身都没错，错的是**假设只有一个改动人**：

| 设计 | 本意 | 共用目录时 |
|---|---|---|
| `git add -A` | 提交一个自洽快照 | **仓库级** —— 分不清谁改的 |
| 产物是全量的 | clone 下来就能开 | 我 build 会重建**所有人**的产物 |
| 保存即有竞态 | —— | A 保存、B 正在 build → B 构建出 A 的半成品 |

### 先做这件事：每个会话一个 worktree

```bash
cd ~/works/codes/knowledge-html
git worktree add ~/works/codes/kh-<会话名> -b <会话名>
cd ~/works/codes/kh-<会话名>
ln -s ~/works/codes/knowledge-html/node_modules node_modules
```

每个目录是**完整独立的工作区**：文件互不可见，`git add -A` 只会扫到自己的改动。
==误提交从根上消失。==

**三个实测出来的坑**：

| 坑 | 怎么办 |
|---|---|
| `node_modules` 不跟着 worktree 来 | 软链过去（上面那条），或各自 `npm install` |
| 软链显示成 `?? node_modules` | `.gitignore` 里写的是 `node_modules/`（带斜杠 = 目录），**匹配不上软链** —— 改成 `node_modules` |
| skill 的符号链接固定在主目录 | worktree 里改 skill **不生效**。skill 只有一份，这是好事 |

````callout
tone: amber
icon: 🪢
text: |
  **但「worktree 里改 skill 不生效」这句话会误导人走错一步。**

  真实布局是这样：

  ```
  ~/.agents/skills/knowledge-html  ──软链──→  <主仓库>/.agents/skills/knowledge-html
                                              <worktree>/.agents/skills/knowledge-html   ← 独立副本
  ```

  `.agents/skills/**` 是**进仓库的跟踪文件**，所以每个 worktree 各有一份。
  你按直觉去改 `~/.agents/skills/knowledge-html/SKILL.md`，==改的其实是**主仓库的工作区**==，
  而 `npm run check` 读的是 **worktree 里那份** —— 于是：

  | 你看到的 | 实际发生的 |
  |---|---|
  | 文件确实改了，内容也对 | 主仓库工作区脏了（别的会话会看到） |
  | `npm run check` 还是报「SKILL.md 说 20 个控件」 | worktree 那份没动 |

  ++正确做法：在 **worktree 里**改 `.agents/skills/knowledge-html/SKILL.md`。++
  主仓库那份等分支合并时自然更新。

  ==这次先改错了地方，`check` 报的却是「代码 22 个 vs 文档 20 个」，
  完全看不出是「改的是另一个副本」。==
````

**合并时冲突面比想象的小**。量过：==全仓库只有 `index.html` 一个文件是全量的==
（`dist/<slug>.html` 和 `notes/<slug>/index.html` 都是**每篇一个文件**，只有作者会动）：

| 文件 | 合并时 |
|---|---|
| `dist/<slug>.html`、`notes/<slug>/index.html` | 各改各的 → **不冲突** |
| `index.html`（首页树视图） | 所有人都动 → **必然冲突** |

`index.html` 冲突时**别手动 merge** —— 它是生成的：

```bash
git checkout --theirs index.html   # 随便选一边，反正是生成的
npm run build:standalone           # 用合并后的源重建
git add index.html && git commit
```

### 没条件开 worktree 时：点名 add，别用 `-A`

```callout
tone: amber
icon: ⚠
text: |
  ==把 `git add -A` 换成 `git add <具体路径>`。==
```

```bash
git add notes/<你的 slug>/ archify/<你的名字>.json assets/arch/<你的名字>.svg
git add assets/blocks.css assets/app.js      # 只在你确实改了它们时
git add index.html dist/                     # 产物是全量的，必须一起带上
```

**为什么这样更安全**：`-A` 是仓库级的，它不问「这是谁改的」。
点名 add 只带走你确认过的东西。

### 还有第二个矛盾：产物是全量的

即使分了 worktree，合并时还有一道坎。

```callout
tone: amber
icon: ⚠
quote: true
text: |
  ==构建产物是**全量**的。==

  `index.html`、`dist/*.html` 里包含**所有人的内容**。
  所以你没法「只提交自己的部分」—— 那样仓库就停在「产物新、源旧」的不一致状态，
  pre-push 钩子会直接拦下。
```

**推论**：提交 = **提交一个自洽快照** = 当前所有源 + 由它们构建出的所有产物。

这意味着**你必然会把别人的改动一起提交**。这不是错误，是设计。关键是把这件事做**安全**。

### 三类文件

| 类别 | 例子 | 谁负责 |
|---|---|---|
| **共享产物** | `index.html`、`dist/*.html`、`notes/<任意 slug>/index.html`、**`skill/*.html`** | **每次提交都要带上全部** |
| **共享源** | `assets/theme.css` `blocks.css` `app.js`、`tools/*.mjs`、`package.json`、`.agents/skills/**` | 谁改谁提交，但**要小心** |
| **私有源** | `notes/<你的 slug>/`、`archify/<你的名字>.json`、`assets/arch/<你的名字>.svg` | 只有你改 |

### 开工前（30 秒）

```bash
npm run status
```

它会把你工作区的改动**分类列出来**（临时文件 / 共享产物 / 共享源 / 笔记源），
并标出每项的修改时间。

- 干净 → 直接干活
- **有别人的改动** → 两种走法：
  - 你在 worktree 里 → 与你无关，但合并时要注意
  - 你在共用目录里 → 记住它们，但**不要用 `-A`**，点名 add
- 有别人的改动**且明显是半成品**（写了一半、构建不过）→ **先问用户**

### 干活时

1. **只改自己的文件。** 不要顺手改别人的 `note.md`，哪怕发现它写错了 —— 报告，不擅自改。
2. **改共享源要小步。** `blocks.css` / `app.js` 有别人在用：
   - ==改一条 CSS 规则就替换那一条，别用大区间替换==
   - 加控件 / 积木用**新名字**，别改别人的
   - 改完尽快提交，别攒着
3. **临时文件进 `.gitignore`。** 预览副本、截图、草稿别留在 `notes/` 里。
   约定：以 `_` 开头的文件是临时的（`_p.html`、`_wip.html`）。

### 提交时

```bash
npm run status              # ① 分类看清 —— 这一条不能省
npm run check               # ② 校验（含 skill 一致性）
npm run build:standalone    # ③ 重建全部产物
npm run skill               # ③b 重建 skill/（改了 skill 文档才需要）
npm run visual-check        # ④ 量图
git add <点名清单>          # ⑤ 优先点名；确认过才用 `-A`
node tools/status.mjs --cached   # ⑥ 再看一遍 staged 的
```

```callout
tone: amber
icon: ⚠
quote: true
text: |
  ==第 ⑤ 步优先点名 add。==

  共用目录里 `git add -A` 会把你**没看过的**东西一起带走 ——
  包括别人正在写的半成品。它不问「这是谁改的」。

  只有在你确实逐项确认过（第 ① 和 ⑥ 步都看过）时，`-A` 才可以。
```

```callout
tone: amber
icon: ⚠
text: |
  **但有一条例外：如果别人的源是半成品，不要提交。**

  半成品 = 明显写了一半、或构建不过。

  这时**停下来问用户**，别替别人改，也别把它带上。
  ==替别人提交一个坏文件，比漏提交更糟 —— 它会被当成「已经完成」。==
```

### 别人的改动怎么处理

| 情况 | 怎么办 |
|---|---|
| 别人的源完整、构建能过 | **一起提交**，提交信息里注明来源 |
| 别人的源是半成品 | **停下来问用户** |
| 只有别人的产物、没有源 | 说明源被漏了 → 找到源一起提交，或者问用户 |
| 别人改了共享源（`blocks.css`） | 一起提交，**在信息里说明你确认过它的改动** |

**提交信息里的注明格式**（已有先例）：

```text
来自并行会话（非本次工作，为保持产物与源一致一并提交）：
- notes/flink-source-transform-sink/（Flink 算子笔记）
- tools/visual-check.mjs（加 .keyby-viz 容器 + JSON 解析错误上下文）
```

### 构建和提交之间的竞态（真实踩过）

```callout
tone: red
icon: ⚠
text: |
  **`npm run build` 和 `git add` 之间，别人的文件可能又变了。**

  于是你提交的是「**源是新的、产物是旧的**」——
  pre-push 钩子一重建就发现对不上，直接拦下。
```

**时间线**（真实发生）：

```text
① 我 npm run build:standalone   → 从 note.md 的版本 A 构建出产物 A
② 我 git add -A && commit       → 期间别人保存了版本 B
                                  结果提交的是：源 B + 产物 A   ← 不一致
③ pre-push 重建                 → 从 B 构建出产物 B ≠ 产物 A → 拦下
```

**修法**：源已经提交了，只是产物过期 —— 重建后 amend：

```bash
npm run build:standalone
git add -A
git commit --amend --no-edit
git push
```

```callout
tone: amber
icon: ⚠
text: |
  ==如果这样还反复被拦，说明别人正在持续编辑。==

  那就别再重试了 —— **停下来问用户**，等对方告一段落。
  反复 amend 只会把你的提交变成「别人半成品的快照」。
```

### 别人的文件坏了，阻塞了共享构建

```callout
tone: amber
icon: ⚠
text: |
  ==`npm run check` 是全仓库的。别人一篇笔记写坏，你这边也过不了。==
```

**先分清是哪一类**：

| | 例子 | 怎么办 |
|---|---|---|
| **机械性问题** | YAML 裸标量以反引号开头 · 积木名拼错 · 引号没闭合 | ✅ **可以修**。工具自己会给出修法，改的是语法不是意思 |
| **语义性问题** | 内容写错了 · 数字不对 · 结构乱 | ❌ **不碰**。报告用户 |

```callout
tone: green
icon: ✅
text: |
  **判断标准：这个修改会不会改变别人想表达的意思？**

  加一对引号不会。改一个数字会。

  机械性修复要在提交信息里**单独列出来并注明**，别混在自己的改动里。
```

**真实案例**：并行会话的 Flink 笔记里有两行 `- q: \`xxx\` 是什么？` ——
YAML 里裸标量不能以反引号开头，整个仓库的 `check` 都挂了。
预检工具直接给出了修法（外面包一层双引号），修它零风险。

### 冲突处理

| 冲突的文件 | 怎么办 |
|---|---|
| `index.html`、`dist/*`、`notes/*/index.html` | **重新构建**，不要手动 merge。产物是生成的，冲突无意义 |
| `package.json` | 通常两边都加了 script → **两边都保留** |
| `blocks.css` / `app.js` | 真冲突，逐条看，**两边的改动都要留** |
| `note.md` | 不该发生。如果发生，说明两个会话改了同一篇 → **问用户** |

### 推送被拦下来怎么办

pre-push 会重建 + 量图。**它拦下来通常不是你的问题。**

```text
✗ 构建产物有变化（note.md 改了但没提交构建结果）
```
→ 有人（可能是你）改了源没重建。`git add` 上产物，`--amend` 重新提交。

```text
✗ 有图被画坏了
```
→ 看是哪个积木、哪一篇。**如果是别人笔记里的图坏了，报告用户，别去改别人的内容。**

### 四条硬规矩

1. **优先开 worktree。** 没条件就在共用目录里点名 `git add`，别用 `-A` ——
   共用目录里 `-A` 会带走别人正在写的半成品。
2. **产物和源必须一起提交。** 只交产物 → 来源不明；只交源 → 构建过期。
3. **不替别人改东西。** 发现问题 → 报告，不擅自改。
4. **提交前跑 `npm run status` —— 而且要看完。**
   别 `| head -45` 只扫前面一截就往下走。

## 硬约束

| ❌ 不要 | ✅ 应该 |
|---|---|
| 为了「符合积木规范」而扭曲表达 | **怎么讲清楚怎么来**。积木是省力工具，不是验收标准 |
| 硬把内容塞进最接近的积木 | 组合 / 加字段 / 新建 / `raw` 直接写 —— 四条路任选 |
| 编辑 `notes/*/index.html` | 那是产物，会被覆盖。只改 `note.md` |
| 在单篇 `note.md` 里塞 `<style>` | 改 `theme.css` / `blocks.css` —— 一次全站生效 |
| 在正文写 `# 一级标题` | 标题只写在 `meta.json` 的 `title` |
| `meta.json` 里写 `status: "verified"` | agent 生成的内容一律 `draft`。`verified` 是**人工核对过**的信号 |
| 没挂树的笔记不填 `topic` | 填一个 —— 否则它在首页的「未归类」里落进「其他」组 |
| 原样搬用户的原文 | 先砍到骨架，再决定哪几段变成图 |
| 写「它不是 X，而是 Y」这类否定句 | **读者没听过 X**。除非 X 是读者真会有的误解，否则直接说 Y 是什么 |
| 写「这一步我之前没讲」「这张图我第一版画错了」 | **读者不知道你迭代过几轮**，这些话只对你有意义。直接陈述事实 |
| 图上的编号和正文对不上 | 正文用编号指代时，**图上必须真有那个编号**（archify 的边标签、积木的 badge 都要对得上） |
| 图上有文字被压住 | ==字还在、只是读不通，所以最容易滑过去。== `npm run visual-check` 会报「文字压文字」，改完图必须跑 |
| 把 SQL / 代码粘成一整行 | 一个子句一行，嵌套的缩进。原文本来就在一行时（如编译器输出）要注明「换行只是排版」 |
| 把语法高亮当成分色 | 笔记里分的是**来源**（权限 / 条件 / 派生）—— 不要连 `SELECT` 都要上色 |
| YAML 裸标量里出现 `: `（冒号+空格） | 加引号，或用 `|-` 块标量 |
| YAML 裸标量以反引号 `` ` `` 开头 | 加引号 |
| YAML 裸标量以 `*` `&` `!` `%` `@` 开头 | 加引号（会被当成别名/锚点/标签） |
| 值里有 `[` 或 `{` 却没加引号 | 加引号（`Rule[]` 里的方括号会被当数组起始） |
| 担心 `**「术语」**` 这类中文加粗失效 | 已经修好了，不用管；但 `**` 跨行仍然不生效 |
| 只给卡点画图，其余照搬原文 | ==用户已经有文字版了==。卡点是**排序**不是**取舍**：其余那些「空间 / 顺序 / 状态」的段落照样要画，只是可以画轻（`cards` / `compare` 也算图）。见原则 ① |
| 因为「没有现成积木」就退回文字 | 原则 ⑥ 给了四条路：组合 / 加字段 / 新建积木 / `raw`。==退回文字是第五条路，也是最贵的那条== |

**每篇结尾必须有 `quiz`。** 这不是可选项 —— 知识库头号死因是「收藏代替理解」，
攒到 30 篇时自己都不记得里面有什么。2~3 题，逼自己合上答案复述一遍。

**`meta.json` 的 `status` / `sources` 会渲染成页内的溯源头。**
漂亮的 HTML 会自带「这应该是对的」的暗示，而它可能只是某次对话的产物。
半年后你必须能一眼看出哪个结论没人核对过。

### 改了「站点外壳」要多做一步

外壳 = `tools/lib/home.mjs`（首页）、`assets/theme.css` / `blocks.css`。
下面两个坑 **`npm run check` 一个都报不出来**，而且都是**静默**的：属性设上了、JS 里读也是对的，只有屏幕上不对。

````callout
tone: red
icon: ⚠
text: |
  **一、内联在模板字符串里的浏览器 JS，语法检查查不出 `ReferenceError`。**

  首页那段 `<script>` 是拼在 JS 模板字符串里的，`node --check` 看不到它。
  我重构时把旧函数整个换掉，**连同里面声明的 `var mode` 一起删了** ——
  语法完全合法，表现是「排序按钮点下去毫无反应」。

  → 在真实页面里跑一遍，并把 `window.onerror` 收上来（否则连报错都看不到）。

  ```bash
  # ==探针文件必须写在仓库根目录==，再让 python 把 <script> 注入进去。
  # 放 /tmp 跑的话，相对路径引的 assets/*.css 全断了 ——
  # 你会测出「样式没生效」的假象，然后去修一个根本不存在的 CSS 问题。（真踩过）
  cp index.html .probe.html   # 注入探针
  chrome --headless=new --virtual-time-budget=6000 \
    --dump-dom "file://$PWD/.probe.html" | grep -o 'class="PROBE">[^<]*'
  ```
````

````callout
tone: red
icon: ⚠
text: |
  **二、`el.hidden = true` 会被作者样式里的 `display` 盖掉。**

  浏览器自带的 `[hidden] { display: none }` 在 **UA 样式表**里，
  而 **作者样式表里任何一条 `display` 都会盖掉它** —— 跟优先级无关。

  所以 `.tnode { display: grid }` 一写，`n.hidden = true` 就完全失效：
  属性在、`el.hidden` 读出来是 `true`、屏幕上还画着。
  首页的**搜索和标签筛选因此哑了很久**（实测：32 个节点全被标了 `hidden`，32 个全在显示）。

  `theme.css` 里已经加了兜底，==站内新写的组件不用再操心==：

  ```css
  [hidden] { display: none !important; }
  ```

  但要是哪天自己写页面 / 导出 HTML，记得补上这条。
````

| `npm run skill` | 把这份 skill 渲染到 **`skill/`**（**进仓库**，首页链得到）+ 三个页面互链。默认不开浏览器，加 `--open` |
| `npm run new -- <slug>` | 新建一篇笔记 |
| `npm run serve` | 起本地服务器 |

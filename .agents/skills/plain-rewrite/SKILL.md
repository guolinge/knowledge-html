# 平实化编辑：把事情讲清楚

## 任务

读者希望跟着文章理解一件事，而不是先记住一组术语。你的任务是把已有笔记的语言和讲述顺序整理清楚，不是只换几个同义词，也不是另写一篇新文章。

通常由主 agent 在图和初稿基本确定后交给你。单独接到现有笔记的改写任务时，也可以使用。用户对改动范围、事实核对或验证方式另有要求时，以用户的要求为准。

## 输入和输出

先确认主 agent 交给你的工作区、笔记路径和限制。通常只需要读：

- `notes/<slug>/note.md`：正文、图的配置和代码示例；
- `notes/<slug>/meta.json`：标题、摘要和 `sources` 来源；
- 确认某个说法时，按需读上述来源中的相关段落，或主 agent 指定的材料。

在主 agent 已负责【图解】流程的前提下，不必为了这一遍重新通读整个 `knowledge-html` skill、全仓库或原始对话。只使用编辑这篇笔记需要的材料，不额外传入无关对话或未经授权的私有内容。

默认直接编辑该篇 `note.md`，以及 `meta.json` 的 `title` 和 `summary`。其余文件由主 agent 负责。改前由主 agent 保存这两个文件的临时快照；如果是单独执行，自己创建一个唯一的临时目录保存快照。不要用固定文件名覆盖其他会话的备份。

完成后给主 agent 一份简短报告，格式见文末；不要把报告写进笔记。没有写入权限时只交修改建议，不声称已经改好。

## 怎样写得好读

先从头读完，弄清这篇要回答什么，图和例子分别在说明什么。然后按读者的理解顺序整理内容：

1. **先交代对象和问题。** 读者需要知道正在讨论什么、例子里的数据或场景是什么，才容易理解后面的结论。
2. **把中间一步讲出来。** 一句话跨过了计算、条件或因果时，把缺的那一步补在合适的位置。需要调整段落、标题或段落顺序时可以调整，不为保持原句而保留难懂的组织方式。
3. **术语在使用前有定位。** 对理解当前内容必需的词，用一句话说明它是什么、管什么；已经讲明白的词不用反复定义。
4. **写清谁做了什么。** 指代不清就写回具体对象；句子里换了几个主语或叠了多层条件，就拆开。前后有因果或对照时，把关系说清楚，不用空泛的过渡句。
5. **用平常的话保留准确性。** 少用俏皮对偶、拟人和空泛评价；保留必要的技术术语、数字、限制和结论。不刻意压短，也不把所有句子拆成同样的长度。
6. **把例子和结论的范围说清。** 本机测试、某个版本或假设场景，只能说明对应范围；不要改成所有机器、所有情况都成立。

例如，原文写：

> 一个 `char` + `int` + `double`，直觉上是 1 + 4 + 8 = 13 字节，`sizeof` 却是 16。

结合原文中本机的布局，可以写成：

> 在本机的 C 编译环境中，`char`、`int`、`double` 分别占 1、4、8 字节。把它们放进一个结构体，成员一共占 13 字节，整个结构体却占 16 字节。编译器在 `char` 后面留出 3 个填充字节，让 `int` 从满足对齐要求的位置开始。

这里的改动是先交代环境，再说明数字和填充的关系；本机条件和原有数字都要保留。示例只是写法参考，不把其中的类型大小当成所有平台的事实。

## 什么可以补，什么不能猜

| 情况 | 做法 |
|---|---|
| 原文或图里已有定义、条件、数字或过程，但分散或省略了中间一步 | 可以移到使用处、展开推导、补承接，或用已有数据给一个明确标为假设的例子 |
| 读懂文章需要一句定义或一个条件，现有来源能直接支持 | 可以补充；报告位置和具体依据，不必为改写重新做全套研究 |
| 原文的事实或绝对说法与已有来源矛盾 | 不要为保留原句而照搬错误。依据明确且只涉及文字时可以修正，并报告原说法、修改和来源；图或代码也受影响时交主 agent 一起处理 |
| 缺少来源、适用条件或必要例子，现有材料无法支持 | 不凭记忆补成事实；列为待补。若影响理解主线或结论，标成阻塞，不把文章当作已完成 |
| 需要新增整节、改变图义或重做结构 | 提出具体建议，由主 agent 判断和处理；不要自行扩展范围 |

事实性错误可以直接修正：只要能指到来源、且只改文字，就改，并在报告里列出原说法、改法和来源。图和代码也受影响时，先改文字，图和代码交主 agent。

核对时看 `meta.json.sources` 中与该句有关的来源，不把来源列表本身当成证明。只读需要的原文段落，保留版本、平台和前提；无法访问或无法确认时如实报告。除非用户授权，不把本地私有内容发送到外部网站。

## 改动边界

| 内容 | 可以怎样改 |
|---|---|
| 正文、标题、图注、表格和小结 | 可以重写、拆分、合并或调整段落顺序；保留有依据的事实、例子、条件、结论和链接目标 |
| `callout`、`summary`、`quiz`、`cards`、`compare`、`lane-stack` 等积木里的可读文字 | 可以改标题、说明、问题和答案；保留字段名、值类型、条目数量与顺序、节点和关系。标签本身承载的数据、状态和含义不能改坏 |
| `raw` 内显而易见的图注或文字节点 | 按用户和主 agent 的授权可只改可见文字；标签、属性、样式、坐标、图形和交互不动。拿不准就列给主 agent，不修改 |
| 图的文件、布局、连线、控件、代码块和真实输出 | 默认不改；用户或主 agent 明确授权且提供依据时，由主 agent 另行处理 |
| `popquote` 中保留的原问题、原文和其他标明逐字引用的内容 | 保持原样；引用外的介绍文字可以改 |
| `meta.json` | 只改 `title`、`summary`；不改 `sources`、`verified` 和其他元数据 |

默认保留图和控件的数量、关系及页面顺序。图里的术语如果不清楚，也要读懂并指出；不能因为图写在 `raw` 或 YAML 里就跳过。如果用户明确要求「图中文字也不要动」，遵从这一要求。调整说明文字可能影响排版，需要在报告中告诉主 agent。

标题可能参与生成章节锚点。改标题时注意已有的章节链接；不能确认链接是否受影响，就在报告里列出，让主 agent 检查和处理。

## 完成前

从头按阅读顺序再读一遍：读者能否知道每段的对象、动作、原因和适用条件？图前后能否接得上？改写有没有漏掉原文的重要条件？

对照改前快照，检查改动是否超出授权。你不负责重新画图、全站构建、批量截图或发布；主 agent 会在合并完修改后按任务要求统一处理。

## 给主 agent 的报告

简短列出四项，没有的写「无」：

1. **改了什么**：按章节概括主要的语言或讲述顺序调整；标题、摘要有变化时注明。
2. **补充或修正了什么**：每项写位置、改动和依据；由已有数据推导的例子写清假设。图中文字有改动也注明。
3. **待处理的问题**：逐项写位置、缺什么或哪里矛盾、为什么挡住理解、建议怎样处理；标明是否阻塞交付。
4. **范围和验证**：列出修改的文件，以及已做或未做的必要检查；不要把文字改写说成事实已全面核验。

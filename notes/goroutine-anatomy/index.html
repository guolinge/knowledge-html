Goroutine 到底是什么 · 2KB 的栈和两个值的上下文

它不是「更小的进程」，而是把线程的「执行流」那一半职责拆出来交给应用自己管。三态与线程同构，栈从 2KB 起步按需增长，上下文只有两个值。

01它只是把线程的执行流那一半拆出来了

官方 FAQ 的原话是最好的定义：

goroutine 的核心想法，是把独立执行的函数 —— 协程 —— 多路复用到一组线程上。当某个协程阻塞时，运行时自动把同一 OS 线程上的其他协程搬到另一个可运行的线程。程序员完全看不到这些，这正是重点。

拆出三个关键词：独立执行的函数、多路复用、程序员看不到。它替代的是线程「承担执行流」的那一半职责，不是进程「承担隔离」的职责。

硬件 CPU 核 它看见的只有线程
不知道进程是什么 更不知道 G 是什么
谁上核由内核决定 Go 在这一层说不上话
往上内核这一层
操作系统管的
OS 内核 只认识两样东西 进程与线程
进程 页表 = 隔离边界 资源容器
线程 内核可见的执行实体 调度单位
Goroutine 完全不在它的视野里 不认识
再往上换一个视角
进程 资源容器 地址空间、FD、权限
页表把这一圈围起来 外面的东西碰不到里面
线程共享这里的一切 共享的代价是数据竞争自己扛
进到进程内部这里的调度者换了人
Go 自己管的
Go runtime 看见 G、P、M 但它指挥不动 CPU
P 决定谁能跑 Go 代码 「运行 Go 代码的许可」 许可
M 怎么上核 仍然归内核管 管不着
再往下最下面这层只有它看得见
Goroutine 逻辑执行流 只被 runtime 看见
没有公开的 ID 匿名的工人
上下文只有两个值 栈指针 + 指向 g 结构的指针 所以便宜

它的生命周期，和线程的「阻塞 / 就绪 / 运行」完全同构。唯一变化的是调度者：线程的状态由内核切换，G 的状态由 runtime 切换。

G 的三态 —— 和线程同构，只是换了个调度者
Runnable 想要 M 上的一个时间片
Executing 正在某个 M 上跑
Waiting 在等系统调用或同步原语

整个状态机里，「阻塞」就是一次状态改写加一次入队，没有任何内核参与。这是后面那套东西能跑起来的前提。

还有一个刻意的设计：Goroutine 没有公开的 ID。

世界怎么组织并发问题出在哪
pthread 世界按身份组织 —— 查 thread id 分活，靠 TLS 读自己那份配置身份即契约：谁是谁，决定了怎么交互，程序结构被身份耦合
Go 世界按通信组织 —— G1 从 channel 收任务，G2 把结果发出去匿名。真正需要区分身份时用 channel，而不是查「我在几号线程」

02栈：2KB 起步，不够就长

线程 创建时一次定死 8MiB 预留
创建时按最坏情况预留 8MiB
运行时内核不会帮你搬家，只能用这么多
结果大部分根本用不到，但额度已经被占住

预留锁死了数量上限，而且把「最坏情况是多少」压给了开发者估算

G 把这份估算责任收回了 runtime不够就现场扩容
Goroutine 2KB 起步，按需增长 运行时源码 stackMin = 2048
起步2KB对比线程的 8MiB
不够时现场分配一块 2 倍大的连续栈
上限64 位 1GB / 32 位 250MB

同一个线程的预留，能装 4096 个初始 G —— 这就是「开几十万个很现实」的内存基础

扩容的机制和哈希表扩容同构。难的只有一步：修正栈内指针。

旧栈 2KB
新栈 4KB
局部变量在旧地址上 整体拷贝
内容原样搬过来 分配 2 倍大的连续内存
栈内指针全部悬空 它们还指着旧地址
指针全部改指新地址 靠 GC 记录的「哪里是指针」

runtime 能修指针，是因为 GC 扫描栈时本来就要记录「哪里是指针」。 内核做不到，因为内核根本不懂栈里哪一格是整数、哪一格是指针。这也是 Go 的栈和 GC 深度耦合的原因。

方案怎么接续热路径开销什么时候在用
分段栈不够就链一块新段，栈变成链表每次跨段边界都有开销Go 1.3 之前
连续栈分配 2 倍大的一块，整体搬过去热路径零开销，只在扩容时付一次拷贝Go 1.3 起至今

这次演进本身就是一次 why-not：省拷贝的方案，败给了热路径稳定的方案。 而且 2 倍扩容的摊销成本是均摊常数 —— 每 KB 栈空间平均只被搬过一次，和哈希表扩容把单次插入均摊到常数时间是同一个道理。

可增长不代表无限。上限是 64 位 1GB、32 位 250MB（debug.SetMaxStack 可调），涨栈越界程序直接崩溃。这面墙的意义是给失控递归立个界 —— 栈增长永远发生在最深的调用链上，那条链往往就是 bug 所在。

最后是切换的基础：上下文小到只剩两个值。

切换时要搬什么线程Goroutine
上下文全套寄存器 + 信号掩码一个栈指针 + 一个指向 g 结构的指针
出处内核的 PCB / TCBruntime 团队原话：「真的只有两个值」

但小栈只是入场券。栈内存 KB 对 KB 那个差距被叙事放大了，真正的魔法是用户态调度器与非阻塞 I/O 的深度集成 —— 调度器比内核更懂每个 G 在等什么。 那是下一篇和第五篇的事。

03三层，不是三档

「轻量」这个词会诱导人把进程、线程、goroutine 排成「重、中、轻」三档。它们是三层：

三层各自回答不同的问题，不存在替代链
进程 解决资源容器与隔离
线程 内核可见的执行实体
Goroutine runtime 可见的逻辑执行实体
M（真线程） G 最终还是要落在某条 M、某个核上

G 没有自己的页表，也没有文件描述符表 —— 隔离职责它根本没接。 所以「G 替代线程、线程替代进程」这条链不成立；能被替代的只有「谁承担执行流」这一件事。

回到那个 HTTP/2 的类比收个尾：stream 有独立的流控与生命周期，承载它的 TCP 连接只有几条；G 有独立的栈与状态，承载它的线程只有核数那么多。逻辑独立，承载复用。

Goroutine 为什么没有公开的 ID？

官方理由是：一旦给工人命名、围绕名字建立模型，它就变得特殊，程序结构会被身份耦合扭曲。 真正需要区分身份时应该用 channel 通信，而不是查「我在几号线程」。 这和 pthread 世界形成鲜明对照 —— 那边靠线程 ID 与 TLS 组织业务，Go 把这条路主动关掉了。

为什么线程没法用小栈加动态扩容，而 G 可以？

因为线程栈的大小在创建时一次定死，内核不会在运行中帮你搬家，所以只能按最坏情况预留。 G 的栈由 runtime 管：不够就分配一块两倍大的连续内存，整体拷过去，再修正栈内指针。 runtime 敢修指针，是因为 GC 扫描栈时本来就记录了「哪里是指针」；内核没有这份信息。

进程、线程、Goroutine 为什么说是「三层」而不是「三档」？

因为三者回答的是不同的问题：进程解决资源容器与隔离，线程是内核可见的执行实体， G 是 runtime 可见的逻辑执行实体。G 没有自己的页表和文件描述符表，隔离职责它根本没接。 所以不存在「G 替代线程、线程替代进程」的替代链，被替代的只有「谁承担执行流」这一件事。

## 01 · 先认清三种节点

上一篇的结论是：让树矮下来的第二条路，是一个节点里多装几个键。这篇把这个模型讲透 —— 因为红黑树后面每一个动作，都是从这里来的。

2-3-4 树的节点有三种，区别只在装了几个键（以及相应的分支数）：

```demo
widget: rbtree-lab
actions: false
title: 三种节点
config:
  mode: 234
  trees:
    - { cap: 2-节点：1 个键、2 个孩子, tree: "20:(_,_)" }
    - { cap: 3-节点：2 个键、3 个孩子, tree: "20|30:(10:(_,_),_,40:(_,_))" }
    - { cap: 4-节点：3 个键、4 个孩子, tree: "20|30|40:(_,_,_,_)" }
```

下面这些图里，虚线框就代表**一个节点**：框里排着几个键，它就是几-节点。孩子挂在两个键之间的缝上 —— 3 个键的节点有 4 根分支。

名字里的 2、3、4 说的是**孩子数**，不是键数。虽然两者差一，但记住「几-节点 = 最多几个孩子」更接近它的本意。

## 02 · 在节点内部怎么找

一个节点里可能有 1~3 个键。查找时先在节点内部比完这几个键，再决定下到哪根分支：

```lane-stack
- badge: 在 3-节点里找 25
  title: 节点 {20, 30} 有三个孩子
  desc: 先和 20 比，再和 30 比 —— 最多两次比较就决定了往哪根分支下钻
  tone: blue
  nodes:
    - { title: 25 < 20 ？不是, sub: 往右看下一个键, tag: 第 1 次比较 }
    - { title: "25 < 30 ？是", sub: "落在这两个键之间的缝里 → 走中间那根分支", tag: 第 2 次比较 }
```

一次节点内部最多比较 3 次（4-节点）。比 BST 的「一次比较一层」多，但这是一次连续内存里的比较，代价很低。换来的是整棵树变矮 —— 这才是它值钱的地方。

```callout
tone: violet
icon: 🧭
quote: true
text: |
  ==一个节点多装几个键，就是拿「每层多比几次」换「少下几层」。==
  这个交换划不划算，取决于树有多高 —— 而 2-3-4 树的高度是被结构限死的。
```

## 03 · 为什么所有叶子必然同深

2-3-4 树有一条别的树没有的性质：==不管怎么插入、删除，所有叶子都在同一层。==

这不是靠旋转调出来的，而是靠两条动作维持的：

- **插入**只在最底下发生，装不下就分裂，多出来的键往上传；
- **删除**只在最底下发生，空了就借或合并，缺的键从上面或者旁边补。

两个动作都不改变「叶子同深」。于是树高有了一个硬上界：

```
每个节点至少 2 个孩子  →  第 d 层最多 2^d 个节点
装 n 个键的树有 n+1 个叶子位置（每个键贡献一个分叉）
2^d ≤ n + 1   →   d ≤ log₂(n+1)
```

100 万个键 → 深度最多 19 层、层数最多 20。这个上界不需要任何旋转来维持。

## 04 · 插入：装得下就完事

插入总是走到最底层的某个节点，把键放进这个节点：

| 目标节点原本是 | 放进去之后 | 要做什么 |
|---|---|---|
| 2-节点（1 个键） | 3-节点（2 个键） | 什么都不用做 |
| 3-节点（2 个键） | 4-节点（3 个键） | 什么都不用做 |
| 4-节点（3 个键） | 装不下了 | 分裂：中间的键推给父节点，两边各自成节点 |

前两种是白捡的 —— 这就是「一个节点多装几个键」的好处：树有富余，小插入不惊动上层。==也就是说，绝大多数插入只做一步就够了。==

## 05 · 装不下的时候：分裂，可能一路往上传

只有碰到 4-节点才需要动手。下面可以一步步看（点「下一步」）：

```demo
widget: rbtree-lab
actions: false
title: 往 4-节点里插 65：分裂 + 上推
config:
  mode: 234
  insert: 65
  tree: "20|40:(10,30,50|60|70)"
```

三步：

1. **塞进去** —— {50,60,70} 变成 {50,60,65,70}，红框会亮起来告诉你「4 个键装不下了」（4-节点最多 3 个键）；
2. **分裂** —— 中间的 60 推给父节点，剩下的拆成 {50,65} 和 {70}；
3. **完成** —— 父节点接过 60 之后还有余量，到此为止。

但如果父节点本来也是满的呢？看这个：

```demo
widget: rbtree-lab
actions: false
title: 插进一个满的根：树长高一层
config:
  mode: 234
  insert: 50
  tree: "20|30|40"
```

根装了 4 个键 → 分裂 → 中间的 30 成为新的根。==这是 2-3-4 树唯一长高的方式：从根往上长。==所以所有叶子一起下沉一层，永远同深。

分裂一路往上推的完整样子，可以用红黑树的演示反过来看（同一个动作在二叉树上长什么样）：

```callout
tone: amber
icon: ⚠
text: |
  分裂最多推到根。**如果父节点也满，它会继续分裂，一直向上。**
  这条「往上传」的路径，就是红黑树插入修复里「情形 1 反复执行」的原因 ——
  下一篇会看到它们的一一对应。
```

## 06 · 删除：借一个键，或者合并

删除也是从最底层拿掉一个键：

| 这个节点原本是 | 拿掉之后 | 要做什么 |
|---|---|---|
| 4-节点（3 个键） | 3-节点（2 个键） | 什么都不用做 |
| 3-节点（2 个键） | 2-节点（1 个键） | 什么都不用做 |
| 2-节点（1 个键） | 空了 | 从兄弟那里借一个键，或者和兄弟合并 |

一个节点空了要救它，看它的兄弟手里有没有富余：

```compare
first: 兄弟的情况
head: [借位（兄弟有 2 或 3 个键）, 合并（兄弟也只有 1 个键）]
rows:
  - 动作: ["通过父节点周转：父节点的一个键降下来，兄弟最靠边的一个键升上去", "父节点的一个键降下来，和这两兄弟合成一个节点"]
  - 树高: ["不变", "这一层少一个节点，可能让上层也缺键"]
  - 副作用: ["父节点少了一个键，但借来的键补上了位置", "父节点自己少了一个键 —— 如果它也只剩 1 个键，问题继续往上"]
```

```demo
widget: rbtree-lab
actions: false
title: 借位：兄弟有富余
config:
  mode: 234
  trees:
    - { cap: "删 10 之前：左边 {10} 只有 1 个键，右边兄弟 {40,50} 有 2 个", tree: "30:(10:(_,_),40|50:(_,_,_))" }
    - { cap: "借位：40 升到父节点，30 降下来补位", tree: "40:(30:(_,_),50:(_,_))" }
```

```demo
widget: rbtree-lab
actions: false
title: 合并：兄弟也只有 1 个键
config:
  mode: 234
  trees:
    - { cap: "删 10 之前：两边各只有 1 个键，都借不出来", tree: "30:(10:(_,_),40:(_,_))" }
    - { cap: "合并：30 降下来和 40 合成 {30,40}，这一层少了一个节点", tree: "30|40:(_,_,_)" }
```

合并会让上一层少一个键，那个节点可能因此也变成「空的 2-节点」，于是问题继续往上走 —— 和插入的分裂上推是对称的。一路合并到根时，根被拆掉，**树矮一层**。

==插入往上推分裂，删除往上推合并：高度变化全都发生在根这一端。==

## 07 · 这个模型为什么值得先学

把它当成红黑树的前置，是因为红黑树要做的动作，这里已经全部出现过：

| 这里做的事 | 红黑树里对应的 |
|---|---|
| 4-节点装不下 → 分裂，中间键上推 | 插入的「情形 1」：父与叔变黑、祖父变红上推 |
| 3-节点里新键落在内侧 → 把键摆成中间在上的形状 | 插入的「情形 2 + 情形 3」：先掰直，再转一次 |
| 2-节点空了 → 从兄弟借一个键 | 删除的「情形 4」：远侄是红的，借一个键过来 |
| 2-节点空了、兄弟也穷 → 和兄弟合并，问题往上 | 删除的「情形 2」：兄弟变红，欠黑上移 |

红黑树并没有发明新的动作。它只是换了一种**记录方式**：把「这几个键在同一个节点里」这件事，写成二叉树上的颜色。

```quiz
- q: 2-3-4 树里，一次插入什么时候会改变树高？
  a: |
    只有当分裂一路推到根、根也装不下的时候。根分裂成两个节点、中间键成为新的根，
    树高加一层。其余情况（插进 2-节点、3-节点，或者分裂在中途被某个祖先接住）
    都不改变高度。

- q: 一个节点空掉时，什么时候能借、什么时候只能合并？
  a: |
    看兄弟手里有几个键：兄弟是 3-节点或 4-节点（还有富余）就借 ——
    通过父节点周转，父节点一个键下来、兄弟最靠边的一个键上去；
    兄弟也只有 1 个键（2-节点）就得合并 —— 父节点一个键下来和两兄弟合成一个节点，
    代价是上层少一个键，问题可能继续往上。

- q: 为什么绝大多数插入只做一步就结束了？
  a: |
    因为 2-节点和 3-节点都还有空位：插进 2-节点变 3-节点、插进 3-节点变 4-节点，
    都不需要分裂。只有目标恰好是 4-节点（3 个键都占满）时才要动手。
    这个「富余」正是「一个节点多装几个键」带来的好处。

- q: 为什么说 2-3-4 树的「所有叶子同深」不是旋转挣来的？
  a: |
    插入和删除都只在最底层发生，动的是分裂（往上推）和借位/合并（往上推或补位），
    没有任何一个动作会单独加长某一条分支。叶子同深是这个结构加这两套动作的
    自然结果，不是每次改完再去校正。
```

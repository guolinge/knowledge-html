锁不仅表示「只允许一个线程进入」，还要保证：加锁后能看见前一个线程在临界区中的修改；解锁前，当前线程的修改已经正确发布。这会限制 CPU 和编译器对内存操作的重排，减少一部分优化空间。

这段话里最容易被跳过的，是「限制重排」为什么算性能损耗。答案不玄：锁除了「只许一个线程进」，还得保证「上一个人的写，下一个人一定看得见」。为了这个保证，CPU 和编译器在锁的前后都得收着点 —— 收着的这部分，就是白花掉的那部分性能。

先把答案放这：

加锁不是一句「请排队」。它至少是三件事：一条原子指令把锁字改成「有人占用」，一次 acquire 把后面的读拦住，一次 release 把前面的写发出去。三件事不一定对应三条指令——一条带序的原子指令能一次干两件；但它们都不便宜，而且没人抢的时候也得付。

本机（Apple M1 Max，10 核，128 字节一行）实测几个数，先有个量级：

动作 一次多久
没人抢的互斥锁，加锁+解锁一对 ~9 ns
原子加一（不带顺序） 2.2 ns
原子加一（带全局顺序） 7.2 ns
抢不到、真的睡下去再被叫醒 ~1.8 µs

最后一格比第一格贵 200 倍。中间那些数字为什么差这么多，就是这篇要拆的东西。

01硬件真相：CPU 并不直接读写内存

先纠正一个默认假设。你写 x = 1，CPU 并不是「把 1 写进内存」就完事。真实的路径是：

  1. x 所在的一整行（本机 128 字节）得先在这个核的缓存里，而且得是这个核独占的副本；
  2. 如果别的核手里有这一行，得先把它们的副本作废，等它们回话；
  3. 写可以先记在核自己的写缓冲里，不必等第 2 步完成 —— 不然每条写都要卡一百多个周期。

第 3 条就是一切麻烦的源头：「指令执行完了」和「别人能看见了」是两件不同的事。

这四样东西各有一个反直觉的地方，值得单独记住：

本机 128 字节

缓存行 cache line

缓存和内存之间搬东西的最小单位

改一个字节，也要把整行弄到手。一行里如果放了两个线程各自要改的变量，这两个变量就会互相拖累 —— 这就是伪共享（false sharing）。

§06 量了：4 个线程加同一个计数器比各加各的慢 20 倍，差别只在这一行归谁。

写的前提

独占（M 状态 / 所有权）

想写，先让别人的副本作废

写不是「改自己缓存里那份」就行。别的核可能也有这一行，你得先让它们的副本失效，自己拿到独占。

一致性协议（MESI）给每行记四种状态：M 本核独占且改过、E 独占但干净、S 多核共享、I 无效。锁和共享变量只在 M 和 I 之间来回。

所以「谁写谁独占」翻译成硬件动作，是一整行在核之间搬来搬去。

让写变快

写缓冲 store buffer

写指令退休了，数据可能还没出核

写先记在自己的缓冲里，CPU 继续跑后面的指令；等独占拿到了再写进缓存。

本核再读同一个地址时，会先查写缓冲（写转发），所以 a = 1; b = a + 1 一定得 2。但别的核看不到你的写缓冲。

让作废变快

失效队列 invalidate queue

收到作废请求，先回执，稍后真作废

为了不让发请求的核干等，收到请求先回 ack，把真正的作废排进队列。

于是「我已经回执了」不等于「我这边的旧副本已经删了」。读屏障要等的就是这个队列。

单核的补丁

写转发 store forwarding

自己读自己刚写的，得从写缓冲里拿

载入时先查写缓冲、再查缓存。它是「单核看起来顺序执行」的一部分。

它只保证本核自洽，不帮别的核 —— 别的核该看到旧值还是旧值。

锁的地基

原子读改写 RMW

读、改、写三步之间，别人插不进来

CAS、xchg、fetch_add 都是这一类。硬件保证这几步之间这一行归你独占，别的核改不了。

锁的「只许一个线程进」，落到机器上就是一条 RMW 成功了；抢不到就是失败了。

02重排不是一种，是四种

「CPU 会乱序」这句话太粗。工程上把它拆成四种，因为每种要不同的屏障去挡：

重排意思谁允许它典型架构
LoadLoad后面的读，跑到前面读之前乱序执行 + 失效队列ARM / POWER 允许；x86 不允许
LoadStore后面的写，跑到前面读之前乱序执行ARM 允许；x86 不允许
StoreStore后面的写，跑到前面写之前写缓冲ARM 允许；x86 不允许
StoreLoad后面的读，跑到前面写之前写缓冲：读的时候写还没发布x86 也允许，所以它最贵也最常被讨论

三个来源，各自干各自的：

  • 编译器：只要不改变单线程语义，它可以把写挪后、把读挪前。这一层靠编译器屏障挡（C/C++ 里的 atomic_signal_fence，或者内核里的 barrier()）。
  • CPU 乱序执行：两条不相干的指令，谁先算完谁先走。寄存器重命名、乱序发射都在这一层。
  • 内存系统：指令按顺序执行了，但写缓冲让写晚发布、失效队列让作废晚生效。这一层最阴，因为代码顺序看起来完全正常。

x86 的模型强一些：只有 StoreLoad 一种重排是允许的，普通读自带 acquire、普通写自带 release。ARM（包括本机的 arm64）四种都可能，所以需要 dmb / ldar / stlr 这些指令。§06 会把两边编译出来的指令摆在一起。

03两个核都读到 0：把重排画出来

经典例子，两个核各写一个变量、各读对方的变量：

// 初始 x = 0, y = 0
// Core 0                    // Core 1
x = 1;                       y = 1;
r1 = y;                      r2 = x;

// 跑完可能得到 r1 == 0 && r2 == 0

按代码顺序，两边都先写后读，怎么可能都读到 0？把它们放进写缓冲就说得通了：

Core 0x = 1; r1 = y
Core 0 的写缓冲还没发布
缓存行 / 内存一致性点
Core 1 的写缓冲还没发布
Core 1y = 1; r2 = x
1store x = 1
2store y = 1
3load x
4读到 0
5load y
6读到 0
7排空：x = 1
8排空：y = 1

逐条读：

  1. 核 0 的 x = 1 先落进自己的写缓冲 —— 指令退休了，数据没走。
  2. 核 1 的 y = 1 同理。
  3. 核 1 读 x，缓存里没有新的 x，读到 0。
  4. 返回 0。
  5. 核 0 读 y，同样读到 0。
  6. 返回 0。
  7. 两条写缓冲这时才排空。

两个核都没有「违反程序顺序」，它们只是各自把写推迟了。 但这已经足够让外面的世界看到「先读后写」的效果。

要让这段代码给出你期待的答案，至少有一边得在两条操作之间插一条 StoreLoad 屏障（也就是全屏障）。只挡另外三种不够 —— 这正是 Preshing 特意指出的：lwsync 那种「除 StoreLoad 外都挡」的屏障在这段代码里不解决问题。锁能替代它，是因为加锁那条原子读改写自带完整顺序，而且互斥保证两个临界区不重叠。锁的工作，就是把「谁先谁后」变成一个有名有姓的事实。

04屏障到底在等什么

「内存屏障」这个名字容易让人以为它在刷缓存。它真正做的是等：等前面的写真的发出去，等该收的作废真的生效，然后才允许后面的操作动。

一个 store 从「执行完」到「所有核都看见」，要经过这几步：

① 执行 store x = 1 只有本核看得见
去哪了写缓冲
缓存里可能还是旧值
本核再读写转发拿到 1

指令已经「退休」（retire：执行完、结果确定、可以从流水线里撤掉），数据还没离开这个核。

要写，先得拿到这一整行的独占
② 发失效请求 invalidate 别的副本 要等回执
发给别的核的缓存
等什么每个核回一个 ack
期间后面的指令可以继续跑

这是「写」变慢的根源：写要等别人确认，而读不用。

回执齐了，才轮到自己独占
③ 拿到独占 写进 L1 本核最新
行状态M（脏、独占）
别的核副本已作废
内存还是旧值

到这里，数据仍然只在核 0 的缓存里。

别的核想读，得先来找这一行
④ 别人来读 核 1 要这一行 先作废，再给数据
谁处理一致性点转发请求
核 1 的失效先进失效队列
风险回执早于真正作废

失效队列把「我作废了」变成「我登记了，等会儿作废」。

屏障就是在这里插进来等的
⑤ 屏障 dmb ish / mfence / lock 等前面全部完成
等谁写缓冲排空 + 失效队列处理完
阻止后面的读写越过它
代价空转里几乎免费（实测 +0.2 ns），有东西要等时才贵

屏障不清缓存，它只是「排队，等前面的做完」。

做完这一步，才算发布
⑥ 发布完成 所有核都看到 x = 1 这才叫可见
谁能读到任何核
保证来自屏障 + 原子操作
锁的 unlock就落在这里

解锁的成本，主要花在走到这一步上。

按「挡哪种重排」，屏障分四类；高级语言里的 acquire / release 就是它们的组合：

屏障它保证什么高级语义本机（arm64）怎么出现
LoadLoad后面的读不会提到前面读之前acquire 的一半一条带 acquire 语义的 load 同时管住前两种
LoadStore后面的写不会提到前面读之前acquire 的一半同上
StoreStore后面的写不会提到前面写之前release 的一半一条带 release 语义的 store 同时管住后两种
StoreLoad前面的写必须先发布，后面的读才允许执行全屏障 / seq_cstdmb ish，或 ldaddal 这类带序的原子读改写

三个词，对应三种用法：

  • acquire（获取）：加在读之后。它保证「看到这个标志之后，标志之前发布的写我都看得见」。锁的加锁就是 acquire。
  • release（发布）：加在写之前。它保证「我发布这个标志之前，前面的写都已经发出去了」。锁的解锁就是 release。
  • full fence（全屏障）：四种都挡，还要等写缓冲和失效队列。seq_cst 用这个，最贵。

JSR-133 的 FAQ 里有一句流传很广的话：「退出同步块会把缓存刷到主存，进入同步块会让本地缓存失效」。这句话是概念上的简写，FAQ 自己也补了一句「这是对若干可能效果的简写」。硬件层面真正发生的是上面这六步 —— 不是清缓存，是等队列。

有个反直觉的实测结果值得先记住：在空转里插一条 dmb ish，几乎测不出成本（+0.2 ns）。屏障贵，不是贵在指令本身，而是贵在「它要等的东西」：

写法（同一段代码，只换内存序） 实测 差在哪
原子加一，relaxed 2.2 ns 只要独占，不要顺序
原子加一，seq_cst 7.2 ns 多出的 ~5 ns，是等「写真的发出去」

05锁是这些零件拼出来的

一把锁在硬件里只占两样东西：一行缓存（锁字）+ 一个等待队列（抢不到时去哪）。

用 C11 写一把最朴素的锁，能看清这几条指令分别落在哪：

#include <stdatomic.h>

typedef struct { _Atomic int word; } lock_t;   // 0 = 空闲，1 = 已占用

static void lock(lock_t *l) {
    int expected = 0;
    // 原子地比较并交换。成功时的 acquire 语义：后面的读写不能上移
    while (!atomic_compare_exchange_weak_explicit(
               &l->word, &expected, 1,
               memory_order_acquire, memory_order_relaxed)) {
        expected = 0;   // 抢不到就重试（真实实现会先自旋、再睡）
    }
}

static void unlock(lock_t *l) {
    // release 语义：前面的读写不能下移，且必须先发布
    atomic_store_explicit(&l->word, 0, memory_order_release);
}
  • 加锁 = 一条带 acquire 的原子读改写。CAS 成功意味着这一行已经在你手里独占；acquire 让临界区里的读不能跑到它前面。
  • 解锁 = 一条 release store。release 让临界区里的写不能跑到它后面，而且必须发布出去。真实实现还会在这条 store 后面唤醒等待者。
  • 抢不到：CAS 失败，说明锁字不是 0，有人占着。还有一种更常见的情况是 CAS 成功但变慢：这一行在别人手里，要先把整行搬过来。
  • 等待策略：先自旋重试，超过阈值才进内核睡。

futex 的手册把这条分界线写得很清楚：无竞争时，原子指令「完全在用户态执行，内核不保存任何关于锁状态的信息」；只有可能睡下去时，才把锁字地址当键进内核排队。macOS 上对应的机制叫 ulock，分界线一样。

06把开销拆开量

把上面所有东西换成数字。都是本机实测（M1 Max，clang -O2，5 次运行取范围；机器上还有别的活，会有抖动）。

表里最容易被忽略的是前两行的差别：变量之间根本没有逻辑冲突（各加各的数），只要落在同一行，硬件就当成同一个东西抢。

第三行往后才是锁本身：临界区只有几纳秒时，几个线程还能靠自旋扛住；临界区稍微长一点，线程就会从自旋转成睡觉，直接跳进最后一行的量级。

最后是同一段 C 代码在两个架构上编译出来的指令（本机 clang，-O2）：

源码里的写法arm64（本机）x86-64（交叉编译）
relaxed storestrmov
release storestlrmov（和 relaxed 一模一样）
acquire loadldaprmov（和 relaxed 一模一样）

先认一下这几条 arm64 指令：str 是普通写，stlr 是带 release 语义的写，ldapr 是带 acquire 语义的读，dmb ish 是屏障（ish = inner shareable，同一颗芯片里所有核的范围），ldaddal 是带 acquire+release 的原子加。

这张表把「x86 只允许 StoreLoad 重排」落到了指令上：x86 的普通读写本来就带 acquire/release 语义，所以源码里写 release 和写 relaxed 编出来是同一条 mov；ARM 的普通读写什么都不保证，才需要 stlr、ldar、dmb。Linux 内核的 arm64 头文件里，smp_mb() 就是 dmb ish、smp_rmb() 是 dmb ishld、smp_wmb() 是 dmb ishst。

07四个误解

常见说法实际是怎么回事
屏障会把缓存清空屏障作用在写缓冲和失效队列上：等它们排空/处理完。缓存怎么保持一致是一致性协议一直在做的事，不是屏障才做的。「刷缓存」是概念简写，不是硬件动作。
没竞争的锁不用付钱一条原子 CAS 要把锁字那一行拿到独占，再加一条 release store。实测 ~9 ns。JEP 374 移除偏向锁，省掉的就是这条 CAS。
锁慢都是因为线程切换无竞争时根本没有切换。只有抢不到、自旋超时、睡进内核，才有一次唤醒 —— 实测 ~1.8 µs。两笔账要分开算。
加锁只是「改个标志位」标志位在一行缓存里：改它要先独占，换手要整行搬。锁的争用，本质是这一行在核之间来回搬。

顺手记住两个数字的量级关系，比记定义有用：

  • 无竞争锁 ≈ 9 ns，一次内核唤醒 ≈ 1.8 µs —— 差 200 倍。
  • 同一行上的假争用能让 4 个线程的吞吐掉到 1/20 —— 比锁本身贵得多。

一句话总结

锁的开销不是「等别人」，而是「确认顺序」：一条原子指令拿到缓存行的独占，一条 release 把前面的写发出去，一条 acquire 把后面的读拦住。 没竞争时这笔钱是几纳秒；有竞争时，多出来的是缓存行搬家（几十纳秒）和内核唤醒（几微秒）。

为什么「加锁只允许一个线程进入」这件事，会影响到内存操作的重排？

因为光有互斥不够：线程 A 退出临界区时，它对 x 的写可能还躺在自己的写缓冲里； 线程 B 进来读 x，可能读到旧值。所以加锁要带 acquire（挡住后面的读写上移）， 解锁要带 release（把前面的写发布出去），这两条都会限制重排。

一条 dmb ish 本身贵不贵？那锁的开销到底花在哪？

空转里插一条 dmb 几乎测不出来（+0.2 ns）。它贵在「有东西要等」： 等写缓冲排空、等失效队列处理完。原子加一从 relaxed 换到 seq_cst，2.2 ns 变 7.2 ns， 差的那 5 ns 就是等的钱。再往上才是缓存行换手和内核唤醒。

4 个线程各加各的计数器（没有共享逻辑），为什么也会慢 20 倍？

因为缓存按行一致性：四个计数器如果落在同一行，每次写都要把这行抢到独占， 行就在核之间来回搬。把它们各放一行（padding），吞吐从 ~80 M 回到 ~1700 M 次/秒。 这就是伪共享。

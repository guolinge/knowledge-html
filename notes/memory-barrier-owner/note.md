> 「写屏障保证屏障之前的写必须先于屏障之后的写可见」——这句话里的「可见」没说是谁看，「不能挪到后面」也没说和谁比。三类屏障的定义读起来绕，是因为它们省掉了同一个东西：**这一对操作分别是什么，谁在观察**。
>
> 补上这两项，三句话就变成：写屏障管「写 → 写」，读屏障管「读 → 读」，交叉的两格只有全屏障管。再往下是两个问题：这些屏障由谁提供、你写业务代码时要不要碰；以及为什么连 `return a.balance` 这种读也要加锁。

## 01 · 三个名字，先翻译成「哪一对不许换位」

三类屏障的区别只有一件事：它挡住的是哪两个方向之间的换位。下面三段各用一小段代码，看它夹在哪两个操作之间。

**写屏障**，夹在两次写之间：

```text
data = 42
写屏障
ready = 1
```

屏障之前的**写**，必须先于屏障之后的**写**被别的核看到。它不管读：既不要求前面的读先完成，也不要求后面的读等谁。

**读屏障**，夹在两次读之间：

```text
if ready == 1 {
    读屏障
    x = data
}
```

屏障之前的**读**，必须先于屏障之后的**读**生效。它不管写。

**全屏障**，两侧的读写都不许越过去。它比前两个多管两件事：前面的写不能越到后面的读之后，前面的读也不能越到后面的写之后。

三类放在一张表里，看的是「前一个操作 × 后一个操作」：

```compare
first: 前一个操作
head: [后一个操作是写, 后一个操作是读]
rows:
  - "是写":
      - { text: 写屏障, tone: green }
      - { text: 只有全屏障, tone: amber }
  - "是读":
      - { text: 只有全屏障, tone: amber }
      - { text: 读屏障, tone: green }
```

只有对角两格有专门的屏障。交叉的两格（写 → 读、读 → 写）没有对应的「半屏障」，只能上全屏障。这就是「全屏障最强」的具体含义，不是一句形容词。

```callout
tone: violet
icon: 🧭
text: |
  **名字说的是核心用途，不是精确的覆盖面。**

  C++ 标准里的 release fence 比「只管写 → 写」再宽一点：它要求屏障前的**所有读写**都不能越到屏障后的**写**之后；acquire fence 对称。Linux 内核的 `smp_wmb` / `smp_rmb` 是更窄的版本，上面那张表按它画。

  Go 不给你选这些，所以这层差异平时碰不到；读 cppreference 时别被绕进去。
```

## 02 · 「看到 ready，却没看到 data」是怎么发生的

生产者写 `data = 42`，再写 `ready = 1`；消费者看到 `ready == 1` 之后去读 `data`。直觉是「通知都到了，货应该也到了」。有至少三种情况会让它不成立：

```cards
cols: 3
items:
  - title: 编译器重排
    tag: 源码 → 机器码
    tone: amber
    desc: 只要单线程结果不变，它可以把 `ready` 的写提到 `data` 前面
  - title: CPU 乱序执行
    tag: 指令 → 执行
    tone: blue
    desc: 两条不相干的指令，谁先算完谁先走
  - title: 写缓冲与失效队列
    tag: 执行完 → 别人看见
    tone: violet
    desc: 指令退休了，数据还躺在自己的写缓冲里；作废请求也可能只是记了个账
```

三种原因里的任何一种，都足以让消费者看到 `ready == 1`、`data` 还是旧值。屏障管的就是这三种「插队」：在它这一条线上，前面的先发出去，后面的才准走。

写缓冲怎么排空、失效队列怎么让「作废」晚生效、两个核怎么都读到 0 —— 完整时序在 [锁为什么慢：写缓冲、失效队列和内存屏障](../lock-memory-barriers/) 的 §03 和 §04，这里只留结论。

```callout
tone: amber
icon: 🧱
text: |
  **屏障不让代码暂停，也不刷缓存。**

  它做的是等：等前面的写真的发出去，等该收的作废真的生效，然后才放后面的操作过去。所以空转里插一条屏障几乎测不出成本（另一篇在 M1 Max 上量到 +0.2 ns）；贵的是它要等的那笔账。
```

## 03 · 谁提供：四层，你只碰最上面一层

「内存屏障是谁提供的」这个问题，答案要分四层。最底下的能力在 CPU，最上面的接口在你手里，中间有两层平时看不见。

```lane-stack
- badge: LAYER 01

  desc: 只表达意图：这两步有依赖
  tone: blue

    - { title: "atomic.Add / Store", sub: "sync/atomic", tag: 原子 }

- badge: LAYER 02

  next: "编译器按目标机器挑指令"

- badge: LAYER 03
  title: 编译器 / 运行时
  desc: 可以重排、合并、提前读

  nodes:

    - { title: 缓存行所有权, tag: 谁能写 }
    - { title: 另一个核, tag: 观察者 }
```

第二层值得单独说一句：**语言内存模型才是「你能依赖什么」的清单**。它告诉你 `Unlock` 到下一次 `Lock` 之间有一条完整的顺序、`send` 到对应的 `receive` 之间有一条、atomic 操作按顺序一致排。你照清单写，就不用管底下的指令长什么样。

第三层有本机的直接证据。Go 的 `sync.Mutex` 在这里编出来是这样（Go 1.26.2 · Apple M4 · otool）：

```text
; Lock 快路径
casal   w27, w2, [x3]      ; 比较并交换；al = acquire + release
; Unlock 快路径
ldaddal w2, w4, [x3]       ; 原子加；同样带 acquire + release
```

里面没有一条名字叫 barrier 的指令。顺序语义被编进了指令的变体名：后缀 `al` 就是 acquire + release。选哪条指令、要不要额外插一条 `dmb`，由编译器和运行时按目标架构决定。同一份源码在没有 LSE 的机器上会走 `ldaxr` / `stlxr` 那一对，语义一样，指令不同。

```callout
tone: violet
icon: 🧭
text: |
  **操作系统不在这条链上。**

  它管调度（哪个线程上哪个核）和虚拟内存；「这条写什么时候对另一个核可见」由 CPU、缓存和编译器决定。Go runtime 在抢不到锁时会请操作系统把线程挂起，那是另一件事，在 [一把锁是怎么一层层长出来的](../lock-layers/) 里。
```

## 04 · 业务代码里什么时候轮到你自己写屏障

基本轮不到。先看「你要做什么」和「该用什么」的对应：

```compare
first: 你要做的事
head: [用什么, 它顺便保证了什么, 什么时候要换别的]
rows:
  - 把一个结果交给另一个 goroutine: ["channel", "发送之前的写，接收方看得见", "要广播，或者数据很大"]
  - 几个字段按一条规则一起变: ["Mutex", "临界区互斥；Unlock 到下一次 Lock 之间有完整顺序", "临界区里要等 IO，或者读远多于写"]
  - 一个计数、一个标志: ["atomic", "单次操作原子；Go 的原子操作按 seq_cst 排", "两条操作要一起成立（比如「小于 0 就不扣」）"]
```

这三样工具都包含了屏障，只是没写在你面前。唯一会轮到你自己写屏障的场合，是你在写运行时、驱动或者无锁数据结构 —— 那时你关心的已经不是业务逻辑，而是这套工具本身怎么实现。Go 内存模型对这件事的态度写在文档开头：

```callout
tone: violet
icon: 💬
quote: true
text: |
  If you must read the rest of this document to understand the behavior of your program, you are being too clever. Don't be clever.

  （要是你得读完这份文档才能判断自己程序的行为，那你太聪明了。别这样。）
```

这句话是设计目标的一部分：你只需要判断「这两步之间有没有同步」，不需要判断「底层要不要插屏障」。

```callout
tone: amber
icon: ⚠
text: |
  **atomic 不是「只保证原子」。**

  Go 文档写的是：所有原子操作「as though executed in some sequentially consistent order」，和 C++ 的 `seq_cst`、Java 的 `volatile` 同一档。也就是说它自带屏障效果。

  但「单次操作有顺序」不等于「你的两条操作合起来是对的」。两条 atomic 之间的业务规则（先检查再改、两个字段一起变）仍然要放进同一个同步区间，或者用一条能同时判定的原子操作。
```

## 05 · 读一个变量，为什么也要加锁

先看余额的读接口：

```go
func (a *Account) Balance() int {
	a.mu.Lock()
	defer a.mu.Unlock()

	return a.balance
}
```

`return a.balance` 不是「把变量本身交出去」。它至少做两件事：先把 `a.balance` 读进一个临时值，再把这个值交回调用方。规范里写的顺序是「带结果的 return 会先给结果参数赋值，然后才执行 deferred 函数」，所以读的那一刻锁还握着。问题不在 `defer` 的时机，而在读本身：**它是一次共享访问，和写一样会撞车**。

把 `Balance` 的锁去掉，用 `-race` 跑一遍（本机 Go 1.26.2）：

```text
==================
WARNING: DATA RACE
Read at 0x00c00019e008 by goroutine 10:
  main.(*Account).Balance()
Previous write at 0x00c00019e008 by goroutine 7:
  main.(*Account).Deposit()
```

工具把两行都指出来了：一次读、一次写，中间没有同步。Go 内存模型对数据竞争的定义是「一个写，和同一个地址上的另一个读或写并发发生，而且这些访问不全是原子访问」—— 一边只读，照样算。

```compare
first: 对比项
head: [不加锁, 加锁]
rows:
  - 别人正在写的时候: ["可能读到旧值；多字的值可能半新半旧", "等这一轮写完再读"]
  - 两次访问之间有顺序吗: ["没有", "Unlock 到下一次 Lock 之间有"]
  - Go 内存模型怎么判: ["data race：程序就是错的", "没有竞争"]
  - 工具会说什么: ["`-race` 打印 DATA RACE", "什么都不打印"]
```

「写了一半」不是吓唬人：Go 文档明确说，接口值、map、切片、字符串内部是 `(指针, 长度)` 或 `(指针, 类型)` 这样的两字组合，竞争下的读可能拿到新类型配旧指针，后果是内存损坏。

**什么时候可以不加锁**：

- 这个对象只在一个 goroutine 里用，没有并发。
- 初始化完成之后只读，没有人再写。关键是把「初始化完成」这件事通过同步发布出去（`sync.Once`、channel，或者启动前做完）。
- 单个值，读写都走 `atomic`。

```callout
tone: amber
icon: ⚠
text: |
  **返回引用出去，锁就白加了。**

  `return a.balance` 返回的是值，安全。`return a.items`（切片）或 `return &a.balance` 返回的是「还在被别人改的那块东西」：锁只保护了取到切片头的那一瞬间，元素照样会在你遍历的时候被改。要安全，就让调用方在锁里用，或者返回一份拷贝。
```

## 06 · 三条带走

1. 屏障限制的是**一对操作**的先后，不是时间。它不暂停、不刷缓存，只等前面该完成的完成。
2. 能力在 CPU，指令由编译器和运行时挑，语义由语言内存模型定义。操作系统不在这条链上。
3. 业务代码不写屏障：channel、Mutex、atomic 已经把它包在里面。**读和写一样要进同步区间。**

```summary
title: 一句话
text: |
  三类屏障各管对角的一格：写—写、读—读；交叉的两格只有全屏障管。
  你写 Go 时碰不到它们 —— 但「碰不到」的前提是用对了工具，==包括每一次读==。
```

```quiz
- q: 写屏障能保证「前面的写不会排到后面的读之后」吗？
  a: |
    不能。写屏障只对写和写之间的顺序负责，读屏障只对读和读负责。
    「前面的写 → 后面的读」这一格没有半屏障，只能上全屏障（或者一条带全屏障效果的原子操作）。
    这也是全屏障比分屏障贵的原因：它要等的东西更多。
- q: 插一条内存屏障，会让 CPU 停下来等一会儿吗？
  a: |
    不会让它暂停执行。屏障做的是限制这一对操作的先后：前面的写要真的发出去、该收的作废要真的生效，
    后面的操作才准走。没有东西要等的时候它几乎免费（那篇在 M1 Max 上实测 +0.2 ns），有东西要等时才贵。
    它也不刷缓存 —— 缓存一致是协议一直在做的事。
- q: sync/atomic 和内存屏障是什么关系？
  a: |
    Go 的原子操作按顺序一致（seq_cst）排，和 C++ 的 seq_cst、Java 的 volatile 同一档，
    所以它自带屏障效果，不需要你另外插。
    但它保证的是单次操作和它周围的顺序：两条 atomic 之间的业务规则（先检查再改、两个字段一起变）仍然要自己保证。
- q: Balance() 里是先读 balance 再解锁，还是先解锁再读？为什么读也要锁？
  a: |
    先读，再执行 defer 里的 Unlock。带结果的 return 会先把结果参数赋值，然后才跑 deferred 函数，
    所以读的时候锁还在手上。
    读也要锁，是因为读和写会并发：只要有一个写没有同步，这次读就是 data race。
    普通整数可能读到旧值；接口、切片这类两字组合，还可能读到新类型配旧指针。
```

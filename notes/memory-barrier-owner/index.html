内存屏障：限制什么，由谁提供

内存屏障限制哪些读写的顺序？从 data 和 ready 的例子讲起，再看 Go 的锁、原子操作和 channel 如何提供同步，以及共享变量为什么读的时候也可能需要加锁。

标签 内存屏障 happens-before Go 内存模型 Mutex atomic 数据竞争

两个 goroutine 共享数据时，一个先写数据、再写「准备好了」的标志，另一个看到标志后，却不一定能读到新数据。要让读写之间有可靠的顺序，程序需要使用同步操作。

这篇先用一个例子解释写屏障、读屏障和全屏障，再看 Go 的 channel、锁和原子操作如何提供同步，以及为什么共享变量的读取也可能需要加锁。

00原来的四个问题

问题原文四个问题和三条原始定义

这里保留原问题，下面逐个解释。

1 · 三句定义看不懂

  1. 写屏障（Store Barrier / Write Barrier）保证：屏障之前的「写」，必须先于屏障之后的「写」对其他 CPU 可见。

  2. 读屏障（Load Barrier / Read Barrier）保证：屏障之前的「读」，不能被挪到屏障之后；屏障之后的读不能被提前到之前。

  3. 全屏障（Full Barrier）保证屏障两侧的读写都不能随意跨越。

能翻译成人话吗，有点看不懂。

2 · 为什么锁和原子操作会跟屏障扯上关系

Go 里的 sync.Mutex、sync/atomic，这个不是锁和原子操作吗，为什么跟内存屏障扯上关系了？

3 · 屏障是谁提供的

内存屏障这个逻辑是谁提供的，是编程语言吗，还是操作系统？我在写业务代码的时候需要调用特定的接口吗，还是编程语言帮我抹除了这层差异？

01三类屏障分别限制什么顺序

假设 data 和 ready 一开始都是 0。写入方先把 data 改成 42，再把 ready 改成 1，表示数据准备好了。读取方看到 ready 是 1 之后，再读取 data。

没有合适的同步时，读取方可能看到新的 ready，却还没看到新的 data。内存屏障用于限制特定读写操作的顺序，让其他处理器按要求观察这些操作。

下面的代码是说明屏障作用的示意，不是可以直接运行的 Go 代码。在 Go 中直接用普通变量并发读写会产生数据竞争；第 04 节介绍实际应该使用的同步工具。

写屏障：限制两次写的顺序。 例如，写入方在两次写之间放一个写屏障：

data = 42
写屏障
ready = 1

写屏障要求 data 的写排在 ready 的写之前。要让读取方据此可靠地读到 data，读取方也需要配套的同步；只在写入方放屏障还不够。

读屏障：限制两次读的顺序。 例如，读取方在两次读之间放一个读屏障：

if ready == 1 {
    读屏障
    x = data
}

读屏障要求读取 ready 排在读取 data 之前。它约束的是读与读之间的顺序，不能代替写入方的同步。

全屏障：限制两侧的读写顺序。 除了写和写、读和读，它还约束前面的写与后面的读，以及前面的读与后面的写。

下表只比较这三种基础屏障：行是屏障前的操作，列是屏障后的操作。表里的「只有全屏障」是指在这三类屏障之中；其他同步操作也可能提供所需的顺序保证。

前一个操作后一个操作是写后一个操作是读
是写写屏障只有全屏障
是读只有全屏障读屏障

例如，屏障前后都是写操作时，写屏障就能约束这一对写；前面是写、后面是读时，在这三类里面需要全屏障。实际编程时还可以使用提供其他顺序保证的同步操作，不必把每种情况都归到这三类里。

🧭

acquire 和 release 是另外两种常见的顺序语义。

以 C++ 的 release fence 为例，它约束屏障前的读写与屏障后的写之间的顺序；acquire fence 约束相反的方向。这些语义需要配合适当的原子操作，才能在线程之间建立同步。

上表采用的是 Linux smp_wmb 和 smp_rmb 所代表的写屏障、读屏障分类。Go 的业务代码通常不直接选择这些屏障，而是使用后面介绍的同步工具。

02为什么源码中的顺序不一定够用

在刚才的例子中，源码先写 data，再写 ready。但源码顺序不一定就是另一个处理器观察到的顺序，原因可能出在下面几个环节：

源码 → 机器码

编译器重排

编译器可以在语言规则允许的范围内调整读写顺序

指令 → 执行

CPU 乱序执行

处理器可能提前执行或推迟完成没有依赖的操作

执行完 → 别人看见

写缓冲与失效队列

写入和缓存失效通知的生效时间，也会影响其他核读到的结果

写缓冲暂时保存处理器发出的写入；缓存失效通知用于告知其他核，它们持有的旧副本需要失效。这些机制是否会让读取方看到不同的顺序，取决于处理器架构和程序使用的同步方式。

锁为什么慢：写缓冲、失效队列和内存屏障 的 §03 和 §04 展开了这些过程。这篇只需要记住：不能仅凭源码里的先后顺序，推断另一个 goroutine 一定能读到什么。

🧱

屏障限制的是顺序，不是固定的等待时间。

处理器可能需要等待某些操作，具体代价取决于架构和当时的工作。屏障不要求之前的所有访问在屏障结束时都已经完成，也不等于清空缓存。

另一篇在 M1 Max 上的空载测试测得约 +0.2 ns；这个数字只适用于当次测试，不能代表所有屏障的开销。

03同步由谁提供

Go 程序里的同步可以分成四层：代码调用同步工具，语言内存模型规定这些工具的保证，编译器和运行时选择实现，CPU 执行相应的指令。

图中的 happens-before 可以理解为语言规则保证的先后关系。它用来判断一个 goroutine 的写和另一个 goroutine 的读之间，是否建立了可靠的顺序。

另一个核 观察者

语言内存模型规定了程序可以依赖哪些先后关系。 例如，同一把锁的 Unlock 与之后成功的 Lock 之间有同步关系；一次 channel 发送先于对应的接收完成。一个原子操作观察到另一个原子操作的结果时，两者也建立同步关系。

Go 的原子操作按顺序一致（seq_cst）的方式执行：所有原子操作的效果，都可以按一个符合各 goroutine 程序顺序的总顺序来理解。

编译器和运行时负责在目标机器上实现这些规则。本机编译后的 sync.Mutex 快路径如下（Go 1.26.2 · Apple M4 · otool）：

; Lock 快路径
casal   w27, w2, [x3]      ; 比较并交换；al = acquire + release
; Unlock 快路径
ldaddal w2, w4, [x3]       ; 原子加；同样带 acquire + release

这段代码没有单独的屏障指令：casal 和 ldaddal 的 al 后缀表示指令本身带有 acquire 和 release 语义。编译器和运行时会根据目标架构选择实现；没有 LSE 指令扩展时，可以使用 ldaxr / stlxr 这组指令。不同机器上的指令可能不同。

🧭

普通 Go 代码通常不需要调用操作系统来设置屏障。

编译器和运行时配合 CPU 指令实现同步顺序。锁竞争时，运行时也可能借助操作系统让线程等待或唤醒；这部分和内存顺序的具体指令属于不同环节，见 一把锁是怎么一层层长出来的。

04Go 业务代码应该用什么

写 Go 业务代码通常不需要自己插入内存屏障。先确定哪些数据会被多个 goroutine 访问，再为这些访问选择合适的同步方式：

要做的事用什么提供什么保证还要考虑什么
把一个结果交给另一个 goroutinechannel发送前的写对完成对应接收的 goroutine 可见传递引用后，仍要防止并发修改
几个字段按一条规则一起变Mutex同一把锁保护临界区，建立读写顺序读远多于写时可考虑 RWMutex
一个计数、一个标志atomic单次操作是原子的；Go 原子操作按顺序一致执行多个步骤要一起成立时，需要额外设计

例如，可以用原子变量发布前面提到的 data。下面假设只有一个写入方，写完 data 后不再修改；两个片段分别在不同的 goroutine 中运行：

var data int
var ready atomic.Bool

// 写入方
data = 42
ready.Store(true)

// 读取方
if ready.Load() {
    fmt.Println(data)
}

当 Load 读到写入方存入的 true 时，两次原子操作建立了同步关系。data = 42 发生在 Store 之前，读取 data 发生在 Load 之后，因此这次读取能得到 42。如果 Load 读到 false，这个例子不会读取 data。如果写入方之后还会修改 data，这些后续读写仍需要同步。

这些工具提供了各自的同步保证，底层不一定有一条单独的屏障指令。编写运行时、驱动或无锁数据结构时，才更可能需要直接考虑目标架构的屏障和指令。Go 内存模型的文档开头建议：

💬

If you must read the rest of this document to understand the behavior of your program, you are being too clever. Don't be clever.

（要是你得读完这份文档才能判断自己程序的行为，那你太聪明了。别这样。）

实际写业务代码时，应先找出共享数据的读写，再用 channel、锁或原子操作建立需要的同步关系。

⚠

Go 的原子操作既保证单次操作的原子性，也提供顺序保证。

Go 文档规定，原子操作按顺序一致的方式执行，其语义与 C++ 的 seq_cst 原子操作、Java 的 volatile 一致。

但多个原子操作不会自动合成一个整体。例如「先检查余额，再扣减」之间，其他 goroutine 仍可能修改余额。这样的规则需要用锁保护，或者用能够正确重试的 CAS 方案。

05读共享变量为什么也可能需要加锁

下面是一个读取余额的函数。假设所有并发修改 a.balance 的代码，也都使用同一把 a.mu：

func (a *Account) Balance() int {
	a.mu.Lock()
	defer a.mu.Unlock()

	return a.balance
}

return a.balance 会先读取余额，作为返回值；随后才执行 defer 里的 Unlock。因此，这次读取发生时锁还没有释放。

读取也需要同步，是因为其他 goroutine 可能同时修改同一个余额。如果读取和写入之间没有建立同步关系，就可能发生数据竞争。

本机用 Go 1.26.2 运行存取款示例：去掉 Balance 里的锁后，-race 报告了一次读写竞争：

==================
WARNING: DATA RACE
Read at 0x00c00019e008 by goroutine 10:
  main.(*Account).Balance()
Previous write at 0x00c00019e008 by goroutine 7:
  main.(*Account).Deposit()

报告指出 Balance 在读，Deposit 在写，而且这两次访问没有正确同步。对同一个位置的并发访问，只要至少有一次是写，且访问没有都使用原子操作或其他同步方式，就可能构成数据竞争。

下面的对比假设写入方始终使用 a.mu：

对比项读取时不加锁读写都用同一把锁
与写入并发可能读到旧值；多字值可能不一致同一时刻只有一方持锁访问
读写之间的顺序没有建立同步关系解锁与之后的加锁建立同步关系
数据竞争可能发生受同一把锁保护的访问没有竞争
竞态检测器执行到竞争路径时可能报告 DATA RACE不会报告这组受锁保护的访问

-race 只能检查运行时实际经过的路径；一次运行没有报告，不代表程序中一定没有其他数据竞争。

多字值发生竞争时，读到的内容还可能不属于任何一次完整写入。例如，接口值中的类型和指针，或切片中的指针和长度，可能分别来自不同的写入。Go 内存模型指出，这类不一致可能导致内存损坏。

不一定需要加锁的情况：

  • 数据只由一个 goroutine 使用，没有并发访问。
  • 数据初始化后不再修改，并且通过 sync.Once、channel 等同步方式，或在启动其他 goroutine 前完成发布。
  • 一个单独的值，其并发读写都正确使用 atomic。
⚠

锁不能保护解锁之后对共享数据的访问。

return a.balance 返回的是整数值；按照上面的约定读取时持锁，返回后就不再访问原来的余额。return a.items 返回的切片仍指向原来的底层数组，return &a.balance 返回的指针也仍指向原变量。调用方之后访问这些共享数据时，仍然需要同步。

一种做法是在持锁时复制需要的数据，再返回副本。如果副本里还有指向共享数据的指针，也需要继续保护这些数据。

06小结

  1. 内存屏障限制特定读写操作的顺序；它不是固定延时，也不等于清空缓存。
  2. Go 内存模型规定同步保证，编译器和运行时选择实现，CPU 执行相应指令。锁竞争时，运行时还可能借助操作系统让线程等待或唤醒。
  3. Go 业务代码通常使用 channel、锁或原子操作来同步。共享数据的读写都要遵守同一套同步规则；只读数据或没有并发访问的数据不一定需要加锁。

一句话

写屏障约束写与写，读屏障约束读与读，全屏障还约束两侧的其他读写组合。 Go 代码通常不直接选择屏障，而是正确使用同步工具，让共享数据的读写有可靠的顺序。

写屏障能保证「前面的写不会排到后面的读之后」吗？

按第 01 节的分类，不能。写屏障约束写与写，读屏障约束读与读；在这三类基础屏障中，全屏障也约束写与读。 acquire 和 release 等其他同步语义也能提供特定的顺序保证，实际使用要看对应规则。

插入内存屏障，会让 CPU 停下来等一会儿吗？

可能需要等待，具体取决于处理器和当时的工作，但屏障不是等待固定时间的指令。 它限制访问顺序，不要求之前所有访问在屏障结束时都已经完成，也不等于清空缓存。 另一篇在 M1 Max 上测得的空载开销约为 +0.2 ns，只代表那次测试。

sync/atomic 和内存屏障是什么关系？

Go 的原子操作按顺序一致（seq_cst）执行，提供单次操作的原子性和相应的顺序保证，业务代码不需要再自行插屏障。 多次原子操作不会自动组成一个整体；先检查再修改、同时维护多个字段等规则，仍需要锁或正确设计的原子方案。

Balance() 里先读 balance 还是先解锁？为什么读取也需要同步？

先读取 balance 并设置返回值，再执行 defer 里的 Unlock，所以读取时仍持有锁。 如果另一个 goroutine 可能同时修改余额，读和写都需要按同一套规则同步，否则可能产生数据竞争。 多字值发生竞争时，读到的不同部分还可能来自不同的写入。

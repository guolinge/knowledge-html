epoll：把名单留在内核

两张表加一条回调路径。登记时把 ep_poll_callback 挂到每个 fd 自己的等待队列上，数据到达时回调在当场把 epitem 写进就绪表。热路径不查树、不遍历名单，这才是 epoll 快的地方。

上一篇留下的题目是两句话：内核要记住「谁在关心什么」，还要记住「谁已经就绪」。

epoll 的答案就是这两张表。这一篇拆开看，重点不在数据结构，在一个容易被讲反的地方：是谁把「就绪」这件事写进表里的。

01三个调用，各管一件事

调用做什么和 poll 的差别
epoll_create1建一个 eventpoll 对象，返回一个 fd 指向它poll 没有这一步。实例本身就是一个可以长期存在的内核对象
epoll_ctlADD / MOD / DEL：把 fd 登记进这个实例，可以设关心哪些事件名单交一次就一直有效，不用每轮重交
epoll_wait取走这一刻就绪的事件，最多 maxevents 个只取就绪的那几个，不扫全部登记项

注意 epoll_create1 返回的也是一个 fd。它和普通 fd 一样可以放进别的 epoll 实例里被监视，只是很少有人这么做。

03登记：把回调挂到别人的队列上

epoll_ctl(ADD) 的内核路径里，有一件事决定了 epoll 的全部性能：

ep_insert()
  ├─ 建 epitem，插进红黑树 rbr
  ├─ 调一次这个 fd 的 poll 方法，看它现在是否已经就绪
  │    如果已经就绪 → 直接挂进就绪表
  └─ 通过 poll_wait 协议，把 ep_poll_callback 挂到这个 fd 的等待队列上
       init_waitqueue_func_entry(&pwq->wait, ep_poll_callback);
       add_wait_queue(whead, &pwq->wait);

对比一下第 ② 篇里阻塞 read 挂上去的东西：

挂在 socket 等待队列上的条目阻塞 readepoll
funcwoken_wake_function：把 task 改回可运行ep_poll_callback：把 epitem 挂进就绪表
private指向那个 task指向 eppoll_entry，里面记着 epitem 和 epoll 实例
被唤醒时的代价要调度一个线程，等调度器挑中它执行一段常数时间的代码，跑完就返回
谁持有它线程自己。read 返回时摘掉epoll 实例。DEL 或关闭 fd 时才摘掉

同一个队列，同一种节点，只是换了一个函数指针。

这就是「epoll 不用遍历名单」的机制来源。不是因为它有一棵更聪明的树，而是因为「谁在等」从「一个要被调度的线程」变成了「一段在数据到达上下文里就能跑完的函数」。

还有两个容易忽略的点：

  • 回调挂在每个 fd 自己的等待队列上，不是集中挂在 epoll 实例里。所以连接 B 有 B 的一份，A 有 A 的一份。
  • 同一个 fd 可以被多个 epoll 实例监视，那它就会挂多份回调。回调只对自己那个实例负责。

04数据到达：回调干了三件小事

连接 A 收到数据，协议栈把 skb 放进接收队列，然后调用 sk_data_ready（TCP 默认是 sock_def_readable），它唤醒这个 socket 的等待队列。队列上的条目逐个执行自己的 func。

轮到 ep_poll_callback 时，它做的是：

第一件 看这个事件我关不关心 登记时设过事件掩码
key 是唤醒时带的事件位 EPOLLIN / EPOLLOUT / ...
和 epi->event.events 按位与，不关心就退出 关心 EPOLLIN 的连接不会被一次 EPOLLOUT 吵醒
关心 继续
第二件 把自己挂进就绪表 只挂一次
epi 不在链表上，list_add_tail 到 rdllist 同一轮里来十份数据，也只占一个位置
已经在了就不重复挂 链表位置就是「还没被取走」的标记
挂好了 看看有没有人在等
第三件 叫醒可能睡着的线程 没有人睡就跳过
ep->wq 上有等待者，wake_up(&ep->wq) 把睡在 epoll_wait 里的线程叫醒

三件事都是常数时间，而且都在数据到达的那个内核上下文里完成：可能是软中断，可能是收包的内核线程。整个过程中没有调度你的线程，也没有遍历登记表。

💡

这就是「O(1)」真正的落点：一次事件的处理量，跟登记了多少个 fd 无关。

第一万零一条连接的事件，和第一条连接的事件，走的是同样三段代码。

05收割：epoll_wait 取走这一批

epoll_wait 进来先看就绪表：

  • 非空：直接开始取，不睡。
  • 空：睡到 ep->wq 上。等待项是 exclusive 的，所以多个线程共用一个实例时，一次唤醒只会叫醒其中一个。

取的时候，内核不是把回调当时记下的事件原样交给你，而是对每个就绪的 epitem 再问一次它的 fd「现在到底什么状态」，把最新的掩码拷进你的 events 数组。这一步在 ep_send_events 里完成。

取完之后，按模式决定要不要放回就绪表：

模式取走后结果
水平触发 LT（默认）只要还就绪，就把 epitem 放回就绪表下一次 epoll_wait 还会报它，直到你真的把数据读空
边缘触发 ET不放回。等下一次状态变化，回调再挂进来这一轮没读完的数据，可能永远不会再触发通知

LT 和 ET 的分歧、以及「为什么必须先读到 EAGAIN」，是下一篇的全部内容。

06那棵红黑树到底干什么

很多人把 epoll 的快归因于红黑树。这棵树确实存在，但它不在热路径上：

操作走不走红黑树
epoll_ctl(ADD / MOD / DEL)走。插入、查找、删除都是 O(log n)，n 是登记的 fd 数
数据到达不走。回调直接拿 epitem，挂进就绪表
epoll_wait 取事件不走。只遍历就绪表，长度等于这一刻真有事的那几个

树的作用是让登记这件事可控：支持去重（同一个 fd 重复 ADD 会得到 EEXIST）、支持按 fd 快速找到并修改或删除、支持关闭 fd 时清理。它是一个账本。

让它比 poll 快的，是通知路径不碰这个账本。

顺带一个数量级：man7 里写，每个登记的 fd 在内核里大约占 90 字节（32 位内核）到 160 字节（64 位内核）。这是一笔和连接数成正比的固定开销，很小，但也是为什么 max_user_watches 会有上限。

07和 poll 并排看一次事件

步骤select / pollepoll
事件发生前线程把 N 个 fd 的名单拷进内核，挂 N 个临时条目没有动作。登记的条目和回调一直待命
数据到达socket 唤醒线程挂的那些条目 → 线程被唤醒socket 唤醒回调 → 回调把 epitem 挂进就绪表
找出是哪个 fd线程醒来后重扫 N 个 fd不用找。就绪表里就是
返回给用户就绪个数 + 每个 fd 的 revents就绪事件数组，最多 maxevents 个
返回后要清理什么拆掉 N 个临时条目；名单下次重交没有。登记表还在，就绪表按模式处理
✅

epoll 把「谁就绪」这件事，从「醒来以后找」提前到了「事件发生时就记下来」。

这一步提前，发生在数据到达的内核上下文里，不需要你的线程参与。

下一篇把「就绪」这个词拆开。它是理解 LT、ET，以及理解线上为什么会「连接还在、但再也不响应」的关键。

epoll 挂在 socket 等待队列上的是什么？它和阻塞 read 挂的东西有什么共同点？

挂的是 ep_poll_callback 这个函数指针，外面包一个 eppoll_entry。 共同点是它们都是 wait_queue_entry：阻塞 read 的 func 唤醒 task， epoll 的 func 把 epitem 挂进就绪表。同一个队列、同一种节点，换了 func。

数据到达时，ep_poll_callback 做了哪三件事？

先按事件掩码过滤，看这个事件是否在登记时关心； 再把自己这个 epitem 挂进就绪表（已经在表里就不重复挂）； 最后如果有人在 ep->wq 上等，wake_up 叫醒它。

epoll 为什么快？红黑树在其中起什么作用？

快在通知路径：一次事件只做常数工作，跟登记了多少 fd 无关。 红黑树只服务 epoll_ctl 的增删改查和去重，事件到达和取事件都不走它。

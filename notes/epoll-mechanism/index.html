01三条需求，三样东西

《轮询》把题目列了出来，《select / poll》 还了第 ③ 条。剩下的，在 epoll 这里一一对上：

需求谁去满足它它做到了什么
① 内核得记住我关心哪些 fdepoll_create + epoll_ctl在内核里建一个对象，把 fd 登记进去。登记一次，长期有效
② 内核得只把就绪的还给我epoll_wait它返回的是就绪的那几个本身，不是「整份名单 + 几个标记位」
③ 等待不能再占用执行资源①② 合起来名单存在内核里、谁就绪内核自己知道，线程才能真的睡到有事为止

第三条是目的，前两条是手段。 这个顺序别搞反，反过来就会把 epoll 记成三个 API。

开头那张整体图就是三条需求的运行时样子：①是红黑树，②是就绪链表加拷回，③是 epoll_wait 睡在 ep->wq 上。上一篇 select / poll 的「拉」走到哪一步都全是内核在挨个查 —— 那张图和这张图对着看，分水岭会自己浮出来。

02内核里它就是两张表

这是 epoll 的全部。左边的表登记，右边的表就绪：

epoll 的全部就是这两张表 未开始

三个要点，都能从上面点出来：

登记表（interest list）：epoll_ctl 往里加，一直在

它对应轮询篇的第一条需求。因为内核那头一直记着， 所以调用一次之后你不需要再交代一遍，这正是 select / poll 做不到的事。

就绪表（ready list）：谁有数据了，谁自己挂进来

它不是内核遍历找出来的，是回调放进去的。这一条是下一篇的主线， 这里先记住：放进去这个动作发生在「数据到的那一刻」，不是「你问的那一刻」。

epoll_wait 只是把就绪表拿走

它不清空登记表，上面点完 epoll_wait 之后格子会回到左边， 因为登记还在，只是不再"就绪"了。这两张表的职责完全不同，别混。

注意右边那张表永远是短的。 不是「短一点」，是量级上的不同，它只装这一刻真有事的那几个。

03分水岭：谁把 fd 放进就绪表

前面所有差别到这里收束成一件事。

谁主动什么时候干活成本跟什么成正比一句话
select / poll · 拉你调用的那一刻，内核才挨个去查你登记了多少条问了才知道
epoll · 推数据到的那一刻，内核顺手把它挂进就绪表这一刻真有几个就绪谁好了谁来排队

这是整棵树上最该记住的一句：从「我去查」变成「你来告诉我」。

一旦换过来，两件事同时变好：

  • 你不用每轮重交名单了（内核记着）
  • 内核不用每轮遍历全部了（只有真就绪的才发生那次「挂进链表」）

上一版那个「白问」也没了：没人再问，就没人白问。

🔁

「推」是怎么实现的，看开头那张图上『回调』那两个动作就够：

每个 socket 上本来就挂着一个等待队列。epoll_ctl 登记的时候， 经由这个 fd 自己的 poll 方法，把 ep_poll_callback 挂到 它自己的等待队列上 —— 每个登记的 fd 一份； 数据一来，内核敲这个队列，回调被调用，它做两件事： 把对应的 epitem 挂进就绪表，顺手 wake_up(&ep->wq) 叫醒正在 epoll_wait 的线程。

所以「挂进就绪表」不是 epoll 主动做的，是事件经过时顺手做的。 epoll 只是提供了两张表、一份常驻回调，和一条能让线程睡着睡醒的队列。

顺带把「内核在整条链上干了什么」一次说清，因为这事散在图的每个格子里：收包中断、按四元组找到 socket、敲它自己的等待队列、跑回调记账、睡和醒你的线程、把就绪事件拷回你的数组 —— 六件事全部在内核。你的代码只出现在两端：登记，和收货。

04复杂度要怎么说才诚实

几乎每篇讲 epoll 的文章都会写「O(1)」。这句话的方向对，但说满了。

说法对不对该怎么讲
epoll 是 O(1)不严谨登记要走红黑树、回调要加锁、事件要拷贝到用户态，这些都有成本
epoll 不随监听的 fd 总数变差准这才是它和 select/poll 的真正分野，那两位的成本必然和登记数成正比

对比着看就很清楚：

成本跟什么走
select / poll 登记了多少条，每次都全拷、全遍历
epoll 这一刻真有几个就绪，返回量只跟这个走

记住的是这个函数关系，不是那个「1」。 面试答「不随 fd 总数增长」比答「O(1)」准确，而且显得你真读过实现。

05三个调用分别管什么

epoll_create()，建那个内核对象

它返回的也是一个 fd。epoll 实例本身就是一个文件描述符， 所以能进 select、能被子进程继承、能被 close。 常见误解：以为 epoll 是个「全局的机制」—— 它是你建出来的一个对象，一个进程可以有好几个。

epoll_ctl()，改登记表

三个动作：ADD 加一条、MOD 改关注的事件、DEL 删一条。 它就是轮询篇那三条需求里第一条的落地：名单交一次就够了， 以后要改，改的也是内核里那份，不是重新交一份。

epoll_wait()，把就绪表拿走

它一次返回一批就绪事件（一个数组），不是一个。 常见误解：以为它像 read 一样「取走」就绪状态。 实际上取走之后那个 fd 还在登记表里，而且下一篇会看到： LT 模式下它可能马上又被挂回就绪表。

06到这里，还剩一个词没交代

上面每一句都用了「就绪」：就绪表、就绪事件、这个 fd 就绪了。

但你有没有想过：epoll 说「可读」的时候，数据已经在你手里了吗？

没有。那是下一篇要抠开的那个词，而 epoll 最有名的两个触发模式（LT / ET），争的也正是这件事。

epoll 的三个系统调用分别对应轮询篇留下的哪条需求？

epoll_create + epoll_ctl 对应「内核得记住我关心哪些 fd」—— 在内核里建一个对象，把 fd 登记进去（红黑树），登记一次长期有效。 epoll_wait 对应「内核得只把就绪的还给我」——返回的是就绪的那几个本身。 第三条「等待不该占用执行资源」是目的：线程睡在 ep->wq 上， 事件之间不占 CPU。

「拉」和「推」的区别，一句话怎么说？

select/poll 是拉：你调用的那一刻内核才挨个去查，成本跟「登记了多少条」成正比。 epoll 是推：数据到的那一刻内核顺手把它挂进就绪表， 成本跟「这一刻真有几个就绪」成正比。 从「我去查」变成「你来告诉我」——白问也没了，因为没人再问。

「回调挂在目标 fd 的等待队列上」——每个 fd 挂几份？挂在哪里？怎么知道队列在哪？

每个登记的 fd 一份。epoll_ctl 登记时先建这个 fd 的 epitem（进红黑树）， 然后调它自己的 poll 方法；驱动按 poll_wait 协议把自己等待队列的头交出来， ep_ptable_queue_proc 就把 ep_poll_callback 挂上去（pwq->base = epi， 记住我为哪个 fd 服务）。挂一次一直在，直到 DEL 或 fd 关闭。 A 的挂在 A 的队列上，B 的挂在 B 的队列上，互不相干。

epoll_wait 是什么时候拿走就绪列表的？是谁通知它的？

先查再睡：epoll_wait 进来先看 ep_events_available —— 就绪表非空就直接 ep_try_send_events 拷回用户数组返回； 空才把自己挂到 epoll 实例自己的等待队列 ep->wq 上睡觉。 通知者是 ep_poll_callback：它往就绪表挂完 epitem 之后顺手 wake_up(&ep->wq)。记账的和敲门的是同一个函数， 所以不需要任何额外的通知机制。

为什么说「epoll 是 O(1)」不够严谨？该怎么讲？

因为登记要走红黑树、回调要加锁、事件要拷贝到用户态，这些都有成本。 准确的说法是：epoll 的成本不随监听的 fd 总数变差， 而 select/poll 的成本必然和登记数成正比。 记住这个函数关系，而不是那个「1」。

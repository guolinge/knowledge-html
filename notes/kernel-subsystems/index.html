内核子系统：谁拥有这个条件，谁负责叫醒

等待队列不是按磁盘、网络、锁分成标准类型。线程等的是某个对象上的条件，对象归某个子系统；子系统用最适合的等待结构（通用等待队列、专用链表、completion、定时器或状态位），条件满足时自己唤醒。

标签 操作系统 Linux 内核 子系统 等待队列
等待队列到底有几种？还有，“子系统”到底指什么？（点开看这次两问两答的原文）

下面是这次讨论的原文：先按“线程在等什么”列出常见情况，再解释“子系统”这个词。正文把两问合成一条线：对象 → 子系统 → 唤醒者。原文里的标题降成了小标题，其余没改。

问

等待队列有哪几种情况，磁盘 i/o、网络数据、定时器、锁，还有吗？

答

有很多种，但要先抓住一个核心：

等待队列不是按“磁盘队列、网络队列、锁队列”固定分成几种标准类型。 它本质上是一种通用机制：线程因为某个条件不满足而不能继续执行，就挂到“负责这个条件的对象”的等待队列上。

所以更准确地说，是：

线程在等什么，就可能有对应的等待队列。

你列的这几种已经覆盖了最常见的大类：

磁盘 / IO
网络数据
定时器
锁

下面按“等待的事件”来整理。

总览图

线程执行时发现条件不满足
             │
             ▼
       进入相应等待队列
             │
             ▼
  条件满足后，由相关子系统唤醒
             │
             ▼
    线程重新进入 CPU 运行队列

常见等待原因：

┌──────────────────────────────┐
│ 1. 等 IO 完成                 │
│ 2. 等网络事件                 │
│ 3. 等锁或同步条件             │
│ 4. 等时间到                   │
│ 5. 等进程/线程状态变化        │
│ 6. 等 IPC 消息或数据          │
│ 7. 等内存或资源可用           │
│ 8. 等设备或驱动事件           │
│ 9. 等文件系统或页面数据准备好 │
│ 10. 等用户指定的事件          │
└──────────────────────────────┘

1. 等磁盘或其他块设备 IO

这是你提到的“磁盘 I/O”。

例如线程调用：

read(fd, buf, size);

但数据不在内存页缓存中，必须从 SSD、硬盘或其他块设备读取：

线程 A 调用 read()
       │
       ▼
数据不在内存中，需要设备读取
       │
       ▼
线程 A 睡眠，等待 IO 完成
       │
       ▼
设备完成读取，中断/驱动通知内核
       │
       ▼
唤醒线程 A

图：

线程 A
  │
  ├── 发起磁盘读取请求
  │
  ▼
磁盘 / SSD / 块设备请求
  │
  ▼
线程 A 在 IO 相关等待队列中睡眠
  │
  ▼
IO 完成
  │
  ▼
唤醒 A → A 回到 CPU 运行队列

这里不只包括物理磁盘，也可能是：

  • SSD、NVMe；
  • USB 存储设备；
  • 网络块设备；
  • 虚拟磁盘；
  • RAID；
  • 文件系统底层读写；
  • 交换分区（swap）读写。

但要注意：

现代 Linux 中，线程不一定是“直接等磁盘请求”；它也可能在等页面加载、页锁、文件系统操作或 IO 完成通知。

2. 等网络数据或网络状态

最典型的是 Socket。

例如：

recv(fd, buf, size, 0);

如果 socket 接收缓冲区中没有数据：

线程 A 调用 recv()
       │
       ▼
Socket 没有可读数据
       │
       ▼
A 加入该 socket 的接收等待队列
       │
       ▼
A 睡眠
       │
       ▼
网卡收到数据包
       │
       ▼
网络协议栈把数据放入 socket 接收缓冲区
       │
       ▼
唤醒 A

图：

Socket 接收缓冲区：空

线程 A ── recv() ──> Socket 的“可读等待队列”
                              │
                              ▼
                           A 睡眠


网络包到达
   │
   ▼
Socket 接收缓冲区：有数据
   │
   ▼
wake_up()
   │
   ▼
线程 A 重新可运行

网络等待不只有“等数据到来”，还包括：

等待的事件 常见系统调用或场景
等待读数据 recv()、read(socket)
等待可写 socket 发送缓冲区满，等待可发送
等待新连接 服务端 accept()
等待连接完成 connect() 非阻塞或相关状态等待
等待连接关闭 等待对端 FIN、错误或超时
等待网络事件 poll()、select()、epoll_wait()

3. 等锁

线程访问共享数据时，可能要先拿锁。

例如：

mutex_lock(&lock);

如果锁已经被别的线程持有：

线程 A 想拿锁
   │
   ▼
锁被线程 B 持有
   │
   ▼
A 加入该锁的等待者队列
   │
   ▼
A 睡眠
   │
   ▼
B 解锁
   │
   ▼
唤醒 A 或其他等待者

图：

mutex L：

持有者：线程 B

等待者队列：
[线程 A] -> [线程 C] -> [线程 D]


线程 B 解锁
   │
   ▼
从等待者中选择可获得锁的线程
   │
   ▼
唤醒 A

常见的同步等待包括：

等待对象 含义
mutex 等互斥锁
rwsem / 读写锁 等读锁或写锁
futex 用户态锁竞争时进入内核等待
completion 等待某个内核任务完成
条件变量 等待某个条件变为真
信号量 semaphore 等待可用计数大于 0
文件锁 等待文件区域锁可用
pipe 缓冲区 等待读端或写端满足条件

注意：

自旋锁（spinlock）通常不是“睡眠等待队列”模式。 拿不到自旋锁时，CPU 往往会短暂循环等待，因为持有自旋锁的时间应该很短，并且持锁期间不能睡眠。

4. 等定时器、超时或延迟结束

线程有时不是等外部资源，而是单纯“等时间到”。

例如：

sleep(1);
usleep(100000);
nanosleep(...);

流程：

线程 A 调用 sleep(1)
       │
       ▼
设置一个 1 秒后的定时器
       │
       ▼
A 进入定时等待状态
       │
       ▼
1 秒到了
       │
       ▼
定时器回调唤醒 A
       │
       ▼
A 回到运行队列

图：

当前时间：10:00:00

线程 A：
“请在 10:00:01 后叫醒我”
       │
       ▼
定时器系统 / timer wheel
       │
       ▼
A 睡眠


当前时间：10:00:01
       │
       ▼
定时器到期
       │
       ▼
唤醒 A

很多“等待事件”的操作也会附带超时：

等网络数据，但最多等 5 秒；
等锁，但最多等 100ms；
等子进程退出，但最多等 10 秒。

这时线程实际是在等两个条件中的任意一个：

事件发生
    或
超时到期

5. 等子进程退出、停止或状态变化

父进程可以调用：

wait();
waitpid();
waitid();

等待子进程发生状态变化，例如：

子进程退出；
子进程被停止；
子进程被继续执行；
子进程因信号终止。

图：

父进程 P
   │
   ├── waitpid(child)
   │
   ▼
子进程 C 还在运行
   │
   ▼
父进程 P 睡眠，等待 C 的状态变化


子进程 C 退出
   │
   ▼
内核记录 C 的退出状态
   │
   ▼
唤醒父进程 P
   │
   ▼
P 获得退出码并回收子进程资源

这也是等待队列思想，只是等的不是硬件 IO，而是另一个进程的生命周期事件。

6. 等 IPC 消息、管道数据或共享资源

进程间通信（IPC）也经常需要等待。

常见例子：

IPC 类型 可能等待什么
Pipe / FIFO 等待读到数据；等待缓冲区有空间可写
Unix Domain Socket 等数据、等连接、等发送空间
消息队列 等待新消息到达
POSIX 消息队列 等待消息或等待队列空间
共享内存 + futex 等另一个进程修改状态并唤醒
eventfd 等计数器变为非 0
信号量 等资源数量大于 0

以 pipe 为例：

读进程：pipe 中没有数据
   │
   ▼
读进程睡眠，等 pipe 可读


写进程：写入数据
   │
   ▼
pipe 中有数据了
   │
   ▼
唤醒读进程

反过来，写 pipe 时如果 pipe 缓冲区满了：

写进程睡眠
   │
   ▼
等待读进程读走一部分数据
   │
   ▼
pipe 有空间后被唤醒

7. 等文件系统或内存页面准备好

这和磁盘 IO 有关，但层次更高，不一定直接等设备。

例如一个文件的内容对应某个内存页面：

线程 A 要读取文件的某一页
   │
   ▼
发现该页不在内存中
   │
   ▼
启动页面读取
   │
   ▼
A 等待“该页变为有效”

也可能发生在缺页异常（page fault）时：

线程 A 访问一个虚拟地址
   │
   ▼
对应内存页不在 RAM 中
   │
   ▼
需要从文件或 swap 读回
   │
   ▼
A 等待页面加载完成

可理解为：

等待“内存页可用”

而不是简单地说：

等待“磁盘”

文件系统中还可能等待：

  • inode 锁；
  • 目录项或元数据加载；
  • 写回完成；
  • 文件锁；
  • 设备或远程文件系统响应；
  • FUSE 用户态文件系统返回结果。

8. 等内存或其他内核资源

有些情况下，线程想申请资源，但资源暂时不足。

例如：

内存不够；
某个对象池空了；
某种内核资源达到上限；
cgroup 资源配额暂时不足。

线程可能选择：

立刻失败；
短暂重试；
进入等待，等资源释放；
触发内存回收后再继续。

例如内存分配时，如果使用允许睡眠的分配方式，内核可能会：

尝试回收内存
   │
   ▼
等待回收或写回过程推进
   │
   ▼
拿到可用内存后继续

但不是所有资源不足都会让线程睡眠；有的场景必须立即失败，例如中断上下文中不能睡眠。

9. 等设备事件

除了磁盘和网卡，很多设备都可能让线程等待：

设备或子系统 线程等待什么
键盘 等按键输入
鼠标 / 触摸屏 等输入事件
终端 TTY 等字符输入、等输出缓冲区可写
摄像头 等下一帧图像
声卡 等音频缓冲区可写或播放完成
GPU 等 GPU 任务完成、栅栏 fence 信号
USB 等设备响应或数据到达
串口 等数据到达、等发送完成
GPIO 等引脚电平变化
虚拟化设备 等宿主机或虚拟设备完成请求

例如读键盘：

程序调用 read(/dev/input/...)
   │
   ▼
暂时没有按键事件
   │
   ▼
程序睡眠，等输入设备事件
   │
   ▼
用户按键
   │
   ▼
驱动收到中断，产生输入事件
   │
   ▼
唤醒程序

10. 等 poll、select、epoll 监控的任一事件

这类很重要，因为它本质上是在：

同时等待多个对象中的任意一个变得“可处理”。

例如：

epoll_wait(epfd, events, maxevents, timeout);

线程可能同时关心：

Socket A 有没有数据；
Socket B 能不能写；
Pipe C 有没有数据；
eventfd D 是否被通知；
定时器是否到期。

图：

                  Socket A 可读？
                 /
线程 T ── epoll_wait
                 \
                  Pipe C 可读？
                 /
                eventfd D 有信号？
                 \
                  超时到了？

当其中任意一个事件发生：

任意一个事件触发
      │
      ▼
唤醒 epoll_wait 中的线程 T

严格说，epoll 不是自己“等网络”或“等 pipe”，而是把自己挂接到多个对象的事件通知机制上。

11. 等信号、调试器或进程控制事件

线程也可能因为进程控制原因停止或等待：

  • 等待信号；
  • 被 SIGSTOP 停止；
  • 被调试器 ptrace 暂停；
  • 等待继续执行；
  • 等待某个信号处理流程完成。

例如调试器单步执行时，目标进程经常处于：

TASK_TRACED

它不是在等磁盘、网络或锁，而是在等调试器发出下一步指令。

12. 等内核后台任务完成

内核内部经常有“发起工作 → 等待结果”的模式。

例如：

线程 A 发起异步操作
   │
   ▼
后台 worker / 驱动 / 另一个 CPU 执行工作
   │
   ▼
A 等待 completion
   │
   ▼
后台任务完成
   │
   ▼
complete()
   │
   ▼
唤醒 A

这种等待通常会使用：

completion（完成量）

它很适合表示：

“我不关心谁完成，只关心这件事完成后通知我。”

典型场景：

  • 设备初始化完成；
  • 驱动命令完成；
  • 内核工作线程完成某项任务；
  • 某个 CPU 完成跨 CPU 操作；
  • 模块加载或卸载流程；
  • DMA 传输完成。

一张分类总表

等待类别 等待什么 常见例子
块设备 / IO 读写完成 磁盘、SSD、NVMe、swap
网络 数据、连接、发送空间 recv()、accept()、connect()
锁与同步 锁、条件、完成信号 mutex、futex、semaphore、completion
定时 到某个时间、等待超时 sleep()、nanosleep()
进程管理 子进程状态改变 waitpid()
IPC 消息、pipe 数据、共享状态 pipe、FIFO、消息队列、eventfd
文件系统 / 内存 页数据、页锁、文件元数据 缺页、page cache、FUSE
资源可用性 内存、对象、配额等 内存回收、对象池、资源限制
设备事件 输入、GPU、音频、串口等 键盘、摄像头、声卡、GPU
多路事件 多个 fd 任一就绪 select()、poll()、epoll_wait()
控制类事件 信号、调试器、停止/继续 SIGSTOP、ptrace
内核任务完成 后台操作结束 completion、驱动工作完成

最后一个很重要的补充

不是所有“等”都会进入等待队列。

有些等待方式不同：

自旋等待：
    不睡眠，持续检查。
    常用于自旋锁、极短时间等待。

忙等：
    用户或内核不断轮询。
    通常浪费 CPU，除非等待极短或硬件场景需要。

异步操作：
    发起请求后不等待结果，之后再通过回调、事件或轮询获得结果。

可运行但暂时没 CPU：
    这不是等待队列，而是在 CPU 运行队列里等调度。

最简记忆方式：

等“外部条件” → 通常进等待队列；
等“CPU 时间”   → 进 CPU 运行队列；
等得极短且不能睡 → 可能自旋；
不想等结果      → 用异步通知。

问

“条件满足后，由相关子系统唤醒”——等一下，什么叫子系统？我第一次听说这个概念。

答

“子系统”可以先理解成：

操作系统内核里，按职责划分的一组功能模块。

它不是一个进程，也不一定是一个单独的程序；更像是内核中的一个“部门”或“功能区域”。

1. 为什么需要“子系统”？

操作系统内核要做的事情太多：

管理 CPU 调度
管理内存
管理文件
管理磁盘
管理网络
管理设备
管理进程
管理进程间通信
管理安全权限
……

如果把所有功能混成一大团代码，会非常难维护。

所以内核会按工作内容分工：

Linux 内核
│
├── 调度子系统：决定哪个线程使用 CPU
├── 内存管理子系统：管理内存、虚拟内存、缺页等
├── 文件系统子系统：管理文件、目录、权限、缓存
├── 网络子系统：处理 TCP/IP、Socket、网络包
├── 块设备 / IO 子系统：处理磁盘、SSD 等读写请求
├── 设备驱动子系统：和网卡、键盘、GPU、USB 等硬件打交道
├── IPC 子系统：管道、消息队列、共享内存等
├── 定时器子系统：sleep、超时、定时唤醒
└── 同步机制：锁、futex、信号量、completion 等

这里的“子系统”，就是这些负责不同事情的内核组成部分。

2. 用公司部门类比

可以把内核想成一家公司：

公司 = Linux 内核

人事部       → 管理进程、线程生命周期
调度部       → 决定谁使用 CPU
仓储部       → 管理内存和缓存
物流部       → 管理磁盘读写
通信部       → 管理网络通信
设备部       → 管理网卡、键盘、硬盘等硬件
闹钟服务部   → 管理定时器、超时

线程就像员工。

一个线程说：

“我要读网络数据。”

那么它不是去找 CPU 调度器解决，而是由“网络相关部分”处理：

网络子系统：
    当前没数据？
       那你先在这个 Socket 的等待队列里休息。

数据来了：
       把数据放进 Socket 缓冲区，
       再通知调度器：这个线程可以重新参与 CPU 调度了。

3. “由相关子系统唤醒”到底是什么意思？

更精确的说法其实是：

哪个内核组件发现“线程等待的条件已经满足”，哪个组件就负责发出唤醒。

它通常会调用类似这样的内核唤醒机制：

wake_up(...)

或在更底层最终让线程变成：

TASK_RUNNING

然后把线程放入某个 CPU 的运行队列。

完整链条：

线程在等待队列中睡眠
        │
        │ 条件终于满足
        ▼
发现条件满足的内核组件
        │
        │ 执行唤醒操作
        ▼
线程状态：睡眠 → TASK_RUNNING
        │
        ▼
线程进入某个 CPU 的运行队列
        │
        ▼
调度器未来选择它运行

注意：

“唤醒线程”
不等于
“线程立刻开始执行”

唤醒后，它通常只是获得了“可以运行”的资格，还要等待 CPU 调度。

后来网络包到达：

7. 最准确、最好记的一句话

你可以把之前那句话改记为：

线程因为某个条件不成立而睡眠；
谁负责检测这个条件，
谁就在条件成立时通知并唤醒线程；
被唤醒的线程再交给 CPU 调度器安排执行。

例如：

网络数据到了 → 网络相关代码唤醒线程
磁盘读取完成 → IO / 文件系统相关代码唤醒线程
锁释放了     → 解锁代码唤醒线程
定时器到期   → 定时器相关代码唤醒线程
子进程退出   → 进程管理相关代码唤醒线程

01子系统不是一个进程

「由相关子系统唤醒」这句话里，「子系统」是最容易被当成一个东西的词。先把定义收紧：

子系统是内核里按职责划分的一组代码和数据结构。它拥有一类对象，以及这些对象的操作；它不是一个进程，也不是一个单独的程序。

网络子系统拥有 socket、协议栈、收发包路径；内存管理拥有 folio、页表、回收器；块层拥有 bio 和请求队列；同步机制拥有 mutex、futex、completion。它们都编在内核里，跟着内核一起跑。

kswapd、kworker 这些内核线程不是子系统本身：它们是某个子系统创建出来干活的线程。把子系统想成一个部门，线程是部门里的员工；部门不是一个员工。

🏢

判断一个东西是不是子系统，看它是否同时满足两条：

  • 它拥有一类对象（socket、folio、bio、mutex、task……）；
  • 它负责这些对象上的规则和状态，包括谁在等、什么时候唤醒。

只有代码、没有对象和状态的，通常只是一个工具函数库；只有线程、没有对象的，通常只是它养的一个 worker。

02一张树：对象拥有等待结构

「等待队列有几种」这个问题，换成「线程等的对象归谁」，就有结构了。下面这棵树按所有权排，不按队列类型排：

  • 内核子系统 代码 + 对象 + 规则 按“谁拥有对象”排，不按“队列类型”排
    • 网络 net/ 拥有 socket、协议栈、收包路径
      • struct sock / socket sk_wq->wait 可读 / 可写 / 连接变化；sock_def_readable() 唤醒
    • 内存管理 mm/ 拥有 folio、页表、回收器
      • folio（页） folio_wait_table 等 uptodate / lock 位；读页完成或解锁时唤醒
    • 文件系统 fs/ 拥有 inode、dentry、页缓存
      • inode i_rwsem 等 inode 锁 / 元数据；不是 wait_queue_head_t
    • 块 IO block/ 拥有 bio、请求队列、完成路径
      • bio completion submit_bio_wait() 用 completion 等完成；驱动完成中断 → bio_endio
    • 同步 locking/ + kernel/futex/ 拥有 mutex、rwsem、semaphore、futex、completion
      • mutex / rwsem / semaphore 自己的等待者链表 unlock / up 的持有者直接唤醒
      • futex 哈希桶上的 wait queue FUTEX_WAKE 或 unlock 时唤醒
      • completion swait_queue_head complete() → swake_up
    • 定时 / 时间 kernel/time/ 拥有 hrtimer、timer wheel
      • hrtimer 回调 hrtimer_wakeup() → wake_up_process；不走等待队列
    • 进程管理 kernel/exit.c 拥有 task 状态、父子关系
      • signal_struct wait_chldexit wait4() / waitpid() 在这里等；子进程退出 __wake_up_parent
    • IPC ipc/ + fs/pipe.c 拥有 pipe、消息队列、eventfd
      • pipe_inode_info rd_wait / wr_wait 读端 / 写端各自等；对端读写后唤醒
    • 设备 / 驱动 drivers/ 拥有 input、TTY、GPU fence 等对象
      • 具体设备对象 各自的 wait queue / fence 中断或完成回调唤醒
    • 调度 kernel/sched/ 拥有 rq、task 的调度状态
      • struct rq 运行队列 这里等的是 CPU 时间，不是某个条件；不叫等待队列

看到 socket，就知道队列是网络子系统的；看到 folio，就是内存管理的；看到 inode，就是文件系统的；看到 mutex，就是同步机制的。队列不是一种全局资源，它是对象的一部分。

🔀

同一个线程会在不同分支之间移动。 等 socket 时在网络分支，等 folio 时在内存分支，等 CPU 时在调度分支。换对象就换队列，不是换了一种「队列类型」。

最后一行 rq 是对照：它里面等的是 CPU 时间，不是某个条件。它和等待队列长得像，职责不同；展开在 线程此刻在哪排队。

03十二种等待，挂在什么上

原文按「等什么事件」列了 12 类。把每一类补上「谁拥有对象、用什么等、谁唤醒」，才是机制层面的答案：

等待的事 谁拥有对象 等待结构 谁唤醒
块设备 IO 完成 块层 bio 上的 completion（submit_bio_wait） 驱动完成 → bio_endio → complete()
文件页可用 内存 / FS folio_wait_table 哈希等待队列（等 uptodate / lock 位） 读页完成 / 解锁 folio
socket 可读、可写、连接变化 网络 sk_wq->wait（wait_queue_head_t） sock_def_readable / sock_def_write_space / 状态回调
mutex / rwsem / semaphore 同步 各自的等待者链表 unlock / up 的持有者
futex 同步 futex 哈希桶上的 wait queue FUTEX_WAKE 或 unlock
completion 同步 swait_queue_head + done 计数 complete() → swake_up
sleep() / 超时 定时 hrtimer 回调直接 wake_up_process；带超时的 wait 是队列 + timer hrtimer 到期
子进程状态 进程管理 signal->wait_chldexit 子进程退出 → __wake_up_parent
pipe / FIFO IPC rd_wait / wr_wait 对端读 / 写
poll / select / epoll 多路事件 ep->wq + 每个 fd 的 poll wait 任一 fd 就绪的 poll 回调
设备事件 驱动 input / TTY / GPU fence 各自的等待结构 中断 / 完成回调
控制事件（SIGSTOP、ptrace） 进程管理 不是队列：TASK_STOPPED / TASK_TRACED 状态位 信号 / 调试器改状态
🧭

按对象分是 12 种，按机制分只有 5 类：

  1. 通用等待队列（wait_queue_head_t）：socket、pipe、folio、子进程、eventfd、futex 哈希桶、epoll
  2. 专用等待者链表：mutex、rwsem、semaphore
  3. completion（swait_queue_head + done）：bio、内核任务
  4. 定时器回调：sleep()、hrtimer 到期
  5. 状态位：TASK_STOPPED、TASK_TRACED，不是队列

所以「等待队列有几种」没有标准答案，取决于按哪根轴分。 按业务事件分，可以列十几类；按内核机制分，只有这五类。

04一条唤醒链：socket 收包

把「谁唤醒」落到一条线上。下面把中断 / NAPI 的细节压成一条消息，只看责任：

线程 ATASK_INTERRUPTIBLE
socket 等待队列sk_wq->wait
网络子系统TCP/IP + socket
网卡驱动中断 / NAPI
调度器 / rqtry_to_wake_up
recv()：缓冲区空
挂 entry，改状态
schedule()：让出 CPU
收包，交给协议栈
数据入接收缓冲区
wake_up() → 入 rq
pick 到 A，恢复现场

这条链上三个角色各做各的：

  • 网卡驱动把包从硬件搬到内存，交给协议栈；它不碰 socket 的等待队列。
  • 网络子系统解析 TCP/IP，把数据放进 socket 接收缓冲区，再调 sock_def_readable() → wake_up_interruptible_sync_poll(&wq->wait, ...)。
  • 调度器把 A 从睡眠改成 TASK_RUNNING，放进某颗核的 rq；它不关心 A 等的是 socket 还是 pipe。

唤醒不等于立刻执行。 A 只是重新有资格被挑，什么时候上 CPU 由调度器决定。

05磁盘读：线程可能睡在哪一层

read() 一个文件，不一定「睡在磁盘上」。下面这条栈里，线程可能停在不同的层，等待的对象也不同：

L1 应用 / 系统调用 线程要文件里的第 N 页
read(fd, buf, n) 返回值要等数据 用户态
进入内核 VFS先看页缓存
VFS / 文件系统 fd → file → inode → 页
generic_file_read_iter() 在 page cache 里找这一页 可能命中
缺页才往下 page cache miss命中就直接返回
页缓存 / 内存管理 等 folio 的 uptodate / lock 位
folio_wait_table[hash] 线程挂在这页的等待队列上 可能睡这里
下发 IO block layer组 bio
块 IO 层 bio / request
submit_bio_wait() 同步读用 completion 等 也可能睡这里
交给驱动 driverNVMe / SCSI / virtio
驱动 / 硬件 完成中断 → bio_endio
bio_endio() 完成中断里调用 唤醒者

如果页已经在 page cache 里，线程根本不会睡：VFS 层就返回了。只有缺页才会往下走。走到底之后，它可能睡在 folio 的等待队列上，也可能睡在同步读的 completion 上——取决于它停在哪一层。

🛏

同一个 read() 可能睡在 folio 的 uptodate 位，也可能睡在 bio 的 completion 上。 看它走到哪一层。

这不是实现细节：睡在 folio 上，唤醒者可能是读页完成的代码；睡在 bio 上，唤醒者是 bio_endio()。「磁盘子系统唤醒」只是把这一串压成了一个名字。

06子系统会互相借道：NFS read

「子系统」不是几个互不相干的盒子。读一个 NFS 文件，请求会穿过好几层，完成再沿原路返回：

层它负责什么这一层可能等什么
应用 / read要文件内容，等 read 返回返回值（数据或错误）
VFSfd → file → inode → 页缓存inode 锁、页缓存
NFS client把读请求变成 RPCRPC 回复
网络栈TCP/IP、socket 缓冲socket 可读 / 可写
网卡驱动收发网络包硬件中断 / 完成
服务端读它自己的磁盘服务端自己的 IO

线程最后睡在哪一层，就由那一层的代码唤醒。「网络子系统唤醒」只在这条链的某一层成立；它不是整条链的中央调度者。

🧩

边界是责任，不是隔离。 一个 read() 可以穿过 VFS、NFS、网络栈、驱动，完成再沿原路返回。

所以「哪个子系统唤醒」要看线程最后睡在哪一层，不能只看它调用了什么系统调用。

07驱动、子系统、调度器、等待结构

这几个概念最容易混。把「拥有什么 / 负责 / 不负责」拆开，边界就清楚了：

角色拥有什么负责不负责
硬件电信号 / 网络包 / 磁盘块真正执行 IO不懂线程、文件、socket
驱动设备寄存器、中断、DMA和硬件对话，把数据搬进内核不懂 socket / 文件语义
子系统一类对象 + 规则 + 等待结构维护对象、判断条件、唤醒等待者不决定线程何时上 CPU
等待结构等待者名单记录谁在等不判断条件，也不选 CPU
调度器rq、task 的调度状态把可运行线程放上 CPU不管条件是否满足

把这张表和 §04 的链对上：驱动把包交给网络子系统；网络子系统改 socket 并唤醒；调度器只看到 A 变成可运行，不关心中间发生了什么。

08不是所有「等」都在等待队列里

原文最后把自旋、忙等、异步、等 CPU 单独点出来；这里补上纯 sleep，凑成五种：

方式线程在做什么典型场景代价
睡眠等待挂到对象的等待结构，让出 CPUsocket、pipe、mutex、bio两次上下文切换 + 唤醒路径
自旋不睡，循环检查spinlock、极短临界区占着 CPU，持锁期间不能睡
忙等反复轮询极短等待、部分硬件场景浪费 CPU
异步发起后不等，回调 / 事件通知AIO、io_uring、信号编程复杂，结果晚到
等 CPU已可运行，在 rq 里排队所有被唤醒的线程不是等条件

纯 sleep() 连等待队列都不一定用：hrtimer 回调 hrtimer_wakeup() 直接 wake_up_process()。只有 wait_event_timeout() 这类才是「等待队列 + 定时器」两个条件。

09五条判断

把前面所有内容收成五条，每条都对应一个具体机制：

判断落在哪个机制上
子系统是职责边界，不是进程代码 + 对象 + 规则；kswapd 是它养的线程
对象拥有等待结构socket、folio、bio、mutex；换对象就换队列
谁检测条件，谁唤醒协议栈、解锁者、驱动、定时器各自 wake_up；没有中央分发
机制随对象选wait queue、专用链表、completion、timer、状态位
边界是责任，不是隔离NFS 跨 VFS / 网络 / 驱动；完成沿原路返回

一句话

等待队列不是一张类型表：线程等的是对象上的条件，对象归某个子系统；子系统用最适合的等待结构记录等待者，并在条件满足时自己唤醒。

等待队列有几种标准类型？

没有标准类型。按业务事件分，磁盘、网络、锁、定时、IPC、设备……可以列十几类； 按内核机制分，只有五类：通用 wait queue、专用等待者链表、completion、定时器回调、状态位。

wake_up() 之后线程立刻执行吗？

不会。它只是被改成 TASK_RUNNING，进入某颗核的 rq；什么时候真正上 CPU， 还要等调度器挑到它。唤醒是“重新有资格”，不是“立刻运行”。

网络包到了，谁唤醒 recv() 的线程？

网卡驱动把包交给协议栈；协议栈把数据放进 socket 接收缓冲区后， 调 sock_def_readable() → wake_up(&wq->wait, ...)。驱动不直接碰 socket 的等待队列，它只负责把包送进网络子系统。

为什么 sleep(1) 不一定用等待队列？

sleep() 走的是 hrtimer：到期回调 hrtimer_wakeup() 直接 wake_up_process()， 没有“某个对象的等待队列”。wait_event_timeout() 才是“等待队列 + 定时器”两个条件。

mutex 和 socket 的等待结构一样吗？

不一样。mutex 用自己的等待者链表；socket 用 sk_wq->wait（wait_queue_head_t）； completion 又用 swait_queue_head。同一个“等待”概念，不同的对象选不同的结构。

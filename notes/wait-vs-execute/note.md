## 01 · 最直觉的答案

上一篇留下的问题是：**「等这 N 条队列」该由谁来做？**

最直觉的答案是「谁开的连接谁等」：

```text
for (;;) {
    conn_fd = accept(listen_fd, ...);
    pthread_create(&t, NULL, handle, &conn_fd);   // 一个连接一个线程
}
```

每个线程里写的是**阻塞式**的代码：

```text
read(conn_fd, buf, 4096);    // 卡在这，等数据来
```

==代码非常好读，它就是一段顺着写的顺序逻辑。== 这个方案在 C10K 之前是标准答案。

## 02 · 先拆掉一句流传很广的错话

讲到「为什么一连接一线程不行」，几乎所有人都会甩出这个算式：

> 一万个线程 × 每个栈 8MB = **80 GB 内存**，当然撑不住。

==这个算式是错的。==

**8MB 是 `ulimit -s` 给的虚拟地址空间预留，不是真实占用的内存。** 栈页是**按需分配**的，一个只用到 32KB 栈的线程，真正占住的就只有那 32KB，剩下的一直是没映射的地址空间。

真实的每线程开销是这几项：

```cards
cols: 3
items:
  - title: "内核栈"
    tone: violet
    desc: "约 8 KB（通常一页），依 `THREAD_SIZE` 配置"
  - title: "`task_struct`"
    tone: violet
    desc: "约 6–8 KB，就是调度器要维护的那个实体"
  - title: "用户栈实际用量"
    tone: violet
    desc: "通常几十 KB，不是预留的那 8MB"
```

拿这个控件自己拖一下就看得见：

```demo
widget: thread-audit
title: 一连接一线程，亏的到底是什么
hint: 拖连接数，盯住「内存」和「调度器要管的实体」这两行的差别
config:
  conn: { min: 100, max: 50000, step: 100, def: 10000 }
```

!!拖到一万条：按实算才 **几百 MB**，一点都不吓人。!! 内存这一栏是绿色的，因为**它不是问题所在**。

## 03 · 真正亏的是这个

```compare
first: 方案
head: [一万条连接时，有多少「执行单位」, 这些执行单位在干什么]
rows:
  - 一连接一线程: [{ text: "10000 个线程", tone: red }, "其中 9900 个在睡，但它们==全都在调度器的名单里=="]
  - 事件驱动: [{ text: "1 个线程", tone: green }, "它只在真有事的时候干活"]
```

要看清这笔账，得先问一句：**线程是什么？**

线程是**执行的单位**：它有一份栈、一组寄存器、一个被调度器排队的身份。它被造出来就是为了**跑代码**。

而一万条连接里，任何时刻真需要跑的只有几个。==剩下的时间，那些线程什么也没干，但它们占着一个执行单位该有的全部东西。==

!!所以亏的不是内存，是你在**用「执行资源」去买「等待」**。!!

## 04 · 那代价具体表现成什么

```compare
first: 代价
head: [为什么贵, 量级]
rows:
  - 上下文切换: ["每次唤醒/挂起都要切，切的时候**缓存会凉**", "纳秒级一次，但乘以极高的频率"]
  - 调度器的记账: ["它要维护的实体数", "实体越多，单次调度越慢"]
  - 内存占用: ["内核栈 + task_struct + 真实用到的用户栈", { text: "十几 KB × N，通常不是瓶颈", tone: green }]
```

==这三条都不是「不能」的理由，是「不划算」的理由。== 这一点很重要，它意味着答案是**换一种做法**，而不是「线程不够用了要扩容」。

```callout
tone: amber
icon: ⚖
text: |
  **说句公道话：一连接一线程不是错的，是「配不上」。**

  如果连接数只有几百、每条连接都很忙，它完全可以跑得很好，
  而且代码比事件驱动简单得多，这是它一直被用的原因。

  它出问题是在**连接很多、但每条连接大部分时间没事干**的时候：
  长连接、推送、IM、网关。这时候「等待」的总量远远超过「执行」的总量，
  而你还在按「执行」的规模去准备资源。

  ==换句话说：它错在把「有多少事要做」当成了「有多少东西要等」。==
```

## 05 · 于是判据浮出来了

把这一篇和上一篇合起来，整棵树的那句话就成形了：

> **等待不该占用执行资源。**

它同时是：

- 这一篇的诊断结论（一连接一线程把它俩绑死了）
- 后面所有方案的**验收标准**（不是「更快」，而是「有没有把等待从执行里摘出去」）
- 也解释了后面每一步为什么那样设计

那怎么让等待不占线程？最直接的一步是：**别让线程等，让它去问。**

这是下一篇的事。

---

```quiz
- q: 「一万个线程 × 8MB 栈 = 80GB」这个算式错在哪？
  a: |
    8MB 是 ulimit -s 给的虚拟地址空间预留，不是真实占用的内存。
    栈页按需分配，一个只用 32KB 栈的线程就只占 32KB。
    真实每线程开销是内核栈（约 8KB）+ task_struct（约 6-8KB）
    + 实际用到的用户栈（几十 KB）。一万个线程是几百 MB 量级，不是爆内存。
- q: 那一连接一线程真正亏在哪？
  a: |
    亏在「用执行资源去买等待」。线程是执行的单位 ——
    有栈、有寄存器、要被调度器排队。但一万条连接里任何时刻真需要跑的只有几个，
    剩下 9900 个线程什么也没干，却占着执行单位的全部东西。
    具体表现是上下文切换（切的时候缓存会凉）和调度器的记账。
- q: 为什么说一连接一线程「不是错的，是配不上」？
  a: |
    因为如果连接数只有几百、每条都很忙，它跑得很好，而且代码简单得多。
    它出问题是在连接很多、但每条连接大部分时间没事干的时候（长连接、推送、IM）。
    这时候等待的总量远超执行的总量，而你还按执行的规模准备资源。
    它错在把「有多少事要做」当成了「有多少东西要等」。
- q: 这个系列的验收标准是哪一句话？
  a: |
    「等待不该占用执行资源。」
    它既是这一篇的诊断结论，也是后面所有方案的验收标准 ——
    判断一个方案好不好，不是看它「更快」，而是看它有没有把等待从执行里摘出去。
- q: 下一步最直接的做法是什么？
  a: |
    别让线程等，让它去问，非阻塞 + 轮询。
    这样线程就不再被某一个连接绑住，一个线程能招呼很多连接。
    但它会欠下新的债（白问 + 名单每次重交），那是下一篇的内容。
```

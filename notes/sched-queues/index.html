如果你是 CPU 调度器，面对一条线程的 task_struct，怎么决定要不要让它跑？后来又冒出一堆队列，它们分别是什么？（点开看这次三问三答的原文）

下面是这次讨论的原文：先讲调度器怎么判断一条线程能不能跑，再把几个队列画清楚，最后收成设计取舍。正文把三问合成一条线，并换成了源码里的名字；原文里的伪代码和个别函数名只是示意。

问

如果你是 cpu 调度器，你如何根据线程的 task_struct 决定要不要调用一个线程？

答

可以把 CPU 调度器想成一个“值班经理”，每个线程对应一个 task_struct，里面记录了这个线程的状态、优先级、能跑在哪些 CPU 上等信息。

调度器要解决的问题不是“直接调用一个线程”，而是：

在合适的时机，从所有能运行的线程里，选出当前最该占用 CPU 的那一个；如果它不是当前线程，就切换过去执行。

下面用更直白的方式完整说明。

一、先看线程有没有资格运行

线程的状态记录在：

p->__state

其中最重要的是：

TASK_RUNNING

只有 TASK_RUNNING 的线程，才有资格被 CPU 调度执行。

但 TASK_RUNNING 有两种含义：

  1. 线程正在某个 CPU 上运行；
  2. 线程没有运行，但已经准备好了，正在运行队列里等 CPU。

其他常见状态表示“暂时不能执行”：

状态 简单含义
TASK_INTERRUPTIBLE 可中断睡眠，例如在等 IO、等锁、等事件
TASK_UNINTERRUPTIBLE 不可中断睡眠，常见于某些内核等待或设备 IO
TASK_STOPPED 被暂停了，例如收到停止信号
TASK_TRACED 正在被调试器跟踪，暂时停住
EXIT_ZOMBIE 线程已经退出，等待父进程回收信息
EXIT_DEAD 已经彻底结束
TASK_WAKING 正在从睡眠状态唤醒、准备放进运行队列

概念上可以写成：

if (p->__state != TASK_RUNNING)
    不运行这个线程;

不过真实内核不能这样随便直接读取和修改，因为线程状态可能正被其他 CPU 改动。例如一个 CPU 正在唤醒线程，另一个 CPU 同时在调度它，必须依靠原子操作、锁和运行队列规则防止竞争。

二、确认它能不能在“这颗 CPU”上运行

即使线程是 TASK_RUNNING，也不表示任何 CPU 都能运行它。

task_struct 中有 CPU 亲和性相关信息，例如：

p->cpus_ptr          // 允许在哪些 CPU 上运行
p->nr_cpus_allowed   // 一共允许使用多少个 CPU
p->migration_disabled // 是否暂时不允许迁移到其他 CPU

例如当前调度器准备让线程跑在 cpu 上，会先检查：

if (!cpumask_test_cpu(cpu, p->cpus_ptr))
    不能让它在这颗 CPU 上运行;

一个线程可能不能在某颗 CPU 上运行，常见原因有：

  • 用户通过 sched_setaffinity() 指定了 CPU 亲和性；
  • cpuset 或 cgroup 限制了它能用的 CPU；
  • 该 CPU 已经 offline，或正处于 CPU 热插拔（hotplug）过程中；
  • 线程暂时禁止迁移，例如 migration_disabled；
  • 调度器考虑 NUMA 内存访问距离，希望线程靠近它常用的内存；
  • 调度器考虑负载均衡，不想让某颗 CPU 过载；
  • CPU 被 isolcpus、nohz_full 等机制隔离；
  • 使用 Core Scheduling 时，同一个物理核心上的超线程可能需要满足安全 cookie 匹配；
  • Deadline 或 RT 实时线程还可能受到带宽和准入限制。

所以，真正的条件是：

线程处于可运行状态
并且它允许在当前 CPU 上运行
并且当前 CPU 处于可用状态
并且没有被相关策略限制

三、线程要在运行队列里等待

每个 CPU 通常有自己的运行队列，叫作 runqueue，常写成：

struct rq;

可以把它理解成：

每颗 CPU 前面都有一个候选线程队列，CPU 从自己的队列中挑下一个线程。

线程刚被唤醒时，通常会经历：

线程被唤醒
  ↓
select_task_rq()：选择适合它的 CPU
  ↓
enqueue_task()：放入那颗 CPU 的运行队列
  ↓
等待被调度

task_struct 中与此有关的信息包括：

p->on_rq        // 是否在某个运行队列中
p->on_cpu       // 是否正在某个 CPU 上运行
p->sched_class  // 它属于哪种调度规则/调度类别

简单理解：

if (p->on_rq || task_curr(p))
    它可以参与调度竞争;
else
    它目前不在候选集合里;

其中：

  • p->on_rq：线程正在运行队列中排队；
  • task_curr(p)：线程就是某颗 CPU 当前正在运行的线程。

同样，真实内核中不能无锁地随便检查或修改 on_rq，因为线程可能正在入队、出队、迁移到其他 CPU，需要在对应 rq 的锁保护下操作。

四、不是所有线程平等：先看调度类别

Linux 不会把所有线程放到一个大队列里比较，而是先按“调度类别”分级。

大致优先级顺序是：

stop 调度类
  >
deadline 调度类
  >
RT 实时调度类
  >
fair 普通调度类
  >
idle 调度类

有些内核配置下还可能存在：

sched_ext

即允许通过 BPF 等机制扩展调度策略。

task_struct 中常用的相关字段有：

p->sched_class   // 调度类别
p->policy        // 调度策略，如 SCHED_FIFO、SCHED_NORMAL
p->prio          // 内部动态优先级
p->static_prio   // 静态优先级
p->normal_prio   // 常规优先级
p->rt_priority   // 实时优先级

下面分别解释。

1. Stop 调度类：内核紧急任务

这是最高优先级，普通用户线程通常不会属于这一类。

它主要用于内核内部任务，例如：

  • 停止某个 CPU；
  • CPU 热插拔；
  • 其他必须优先完成的 CPU 控制操作。

如果 stop 任务出现，普通线程、实时线程通常都要让路。

2. Deadline 调度类：必须赶在截止时间前完成

这类线程使用：

SCHED_DEADLINE

它适合周期性、时间要求很严格的任务，例如音视频处理、工业控制等。

它通常需要设置：

runtime：每个周期允许使用多少 CPU 时间
period：周期多长
deadline：必须在多久内完成

调度器通常优先选择：

截止时间最早的可运行 Deadline 线程。

这接近 EDF（Earliest Deadline First，最早截止时间优先）策略。

不过不是 Deadline 线程就一定能无限运行，还要检查：

  • 它是否还有剩余运行预算，即 runtime 是否用完；
  • 是否因为带宽限制被节流；
  • 系统是否允许它的参数组合，即 Deadline 准入控制是否通过。

如果它的运行预算耗尽，即使截止时间很近，也可能暂时不能继续执行。

3. RT 实时调度类：优先级越高越先运行

实时线程通常使用：

SCHED_FIFO
SCHED_RR

实时优先级一般是：

1 到 99

数值越大，用户层面理解的实时优先级越高。

规则可以简单理解为：

更高实时优先级的线程，优先运行；
同一优先级的 FIFO 线程，通常先来的先运行；
同一优先级的 RR 线程，按时间片轮流运行。

例如：

  • 一个优先级 80 的实时线程唤醒；
  • 当前运行的是优先级 50 的实时线程；

那么优先级 80 的线程会抢占当前线程。

不过内核内部的 p->prio 数值规则容易和直觉相反：

p->prio 数值越小，内部优先级通常越高。

所以内核代码中经常是：

if (new->prio < current->prio)
    new 的优先级更高;

不要单纯根据数字大小猜测优先级，必须看字段的语义。

4. Fair 普通调度类：让普通线程长期公平地分享 CPU

大多数普通用户线程属于这一类，例如：

SCHED_NORMAL
SCHED_BATCH
SCHED_IDLE

传统上，人们常用 CFS 的说法解释：

选择虚拟运行时间 vruntime 最小的线程。

意思是：

  • 一个线程已经运行很多了，它的“虚拟运行时间”会增加；
  • 一个线程很久没获得 CPU，它的虚拟运行时间相对较小；
  • 调度器倾向于选后者，避免有人长期饿死。

不过现代 Linux 的公平调度已逐步使用 EEVDF 思路。简单理解为：

调度器会综合线程权重、已经运行了多久、等待了多久、虚拟运行时间和虚拟截止期，选择“现在最应该获得 CPU”的普通线程。

公平调度相关信息通常保存在：

p->se

这里的 se 可以理解为线程在公平调度器中的“调度档案”。

普通线程的 nice 值也会影响它获得 CPU 的比例：

nice 值越小，例如 -20
    → 权重越高
    → 长期来看获得更多 CPU 时间

nice 值越大，例如 19
    → 权重越低
    → 长期来看获得更少 CPU 时间

普通线程之间不是“优先级最高者永远先跑”，而是尽量实现长期的 CPU 时间公平分配。

5. Idle 调度类：实在没人可跑时才运行

如果前面的队列都没有可运行线程，CPU 才会运行 idle 线程。

idle 线程的作用通常包括：

  • 让 CPU 进入低功耗等待；
  • 等待中断；
  • 等待新的线程被唤醒。

五、一个新线程出现后，要不要立刻抢占当前线程？

线程被唤醒、加入运行队列，不代表 CPU 必须立刻切换到它。

调度器还要问：

它是否比当前正在运行的线程更值得立刻执行？

如果答案是“是”，调度器会标记当前线程需要重新调度。

常见标记类似：

set_tsk_need_resched(current);

之后会在适合的时机调用：

schedule();

或者在内核支持抢占的地方调用：

preempt_schedule();
通常会发生抢占的情况

以下情况通常会让调度器尽快切换线程：

1. 新线程属于更高调度类别

例如：

当前线程：普通 fair 线程
新线程：RT 实时线程

或：

当前线程：RT 实时线程
新线程：Deadline 线程

更高类别通常会优先。

2. 新线程是更高优先级的 RT 实时线程

例如：

当前 RT 线程优先级：50
新 RT 线程优先级：80

新线程通常会立即抢占。

3. 当前线程自己放弃 CPU

例如当前线程：

  • 等待锁；
  • 等待 IO；
  • 等待网络数据；
  • 主动休眠；
  • 退出；
  • 显式调用 schedule()。

它不再处于可运行状态后，调度器必须选别人运行。

4. 当前线程的时间片或公平配额用完

对普通线程来说，如果它运行得太久，已经不再是“最该运行”的那个，调度器会换另一个普通线程。

对于 SCHED_RR 实时线程，同优先级线程之间也会按时间片轮转。

5. 中断、系统调用或内核可抢占点返回时

调度器不一定能在任何一条指令后立刻切换。

常见做法是：

  1. 设置“需要重新调度”标记；
  2. 等从中断返回、系统调用返回，或者到达一个允许抢占的内核位置时；
  3. 再执行调度和上下文切换。

六、哪些情况不应该马上切换？

即使出现了一个可运行线程，也可能暂时不切换。

常见情况包括：

1. 新线程优先级更低

当前线程更重要，就继续运行当前线程。

2. 当前是不可抢占的实时线程，新线程不够重要

例如：

当前线程：高优先级 SCHED_FIFO
新线程：低优先级普通线程

普通线程不能抢占它。

如果新线程也是实时线程，但优先级没有更高，通常也不能抢占。

3. 内核当前禁止抢占

例如内核正处于不允许切换的关键区域。

此时即使调度器发现更合适的线程，也往往只能先设置“需要调度”的标志，等安全时再切。

4. 当前正持有自旋锁，或位于中断上下文

在这些场景中通常不能直接做上下文切换。

因为：

  • 自旋锁要求持锁期间不能睡眠；
  • 中断上下文不是普通线程上下文；
  • 随便切换可能导致锁无法释放、状态不一致或死锁。
5. 新线程不能在当前 CPU 上运行

例如它被 CPU 亲和性限制到了其他 CPU。

此时调度器可能把它放到另一颗 CPU 的运行队列，再通过跨 CPU 通知让那颗 CPU 尽快调度。

6. 新线程所在 cgroup 被 CPU 配额节流

即使线程本身是可运行的，它所在的 cgroup 也可能已经用完本周期的 CPU 配额。

这时该组中的线程会被暂时限制，直到新的配额周期到来。

7. 当前 CPU 不适合运行它

例如：

  • 另一个 CPU 更空闲；
  • 另一个 CPU 的缓存中可能还保留该线程的数据；
  • 另一个 CPU 与它使用的 NUMA 内存更近；
  • 当前 CPU 被隔离，尽量不放普通任务进去。

这时调度器可能选择不让它抢当前 CPU，而是迁移到其他 CPU。

七、一次完整调度大致怎么发生？

可以把一次调度想成下面的流程：

1. 当前线程还能不能继续运行？
2. 如果不能，把它从运行队列移走。
3. 从当前 CPU 的候选线程中挑一个最合适的。
4. 如果挑中的还是当前线程，继续运行。
5. 如果挑中的是另一个线程，保存当前线程现场，恢复新线程现场。

概念伪代码：

schedule()
{
    struct task_struct *prev = current;
    struct task_struct *next;

    // 当前线程如果睡眠、退出等，不再参与竞争
    if (prev 不再是 TASK_RUNNING)
        dequeue_task(rq, prev);

    // 按调度类别和各自规则选择下一个线程
    next = pick_next_task(rq, prev);

    // 还是原来的线程，不必切换
    if (next == prev)
        return;

    // 切换 CPU 上下文
    context_switch(prev, next);
}

其中最关键的是：

next = pick_next_task(rq, prev);

它可以简单理解成：

如果有 stop 线程
    选 stop 线程;
否则如果有 deadline 线程
    选截止时间最早的 deadline 线程;
否则如果有 RT 线程
    选实时优先级最高的 RT 线程;
否则如果有普通 fair 线程
    选当前最应该获得 CPU 的普通线程;
否则
    运行 idle 线程;

八、什么叫“上下文切换”？

当：

next != current

时，CPU 才会真正从一个线程切换到另一个线程。

这叫上下文切换（context switch）。

调度器大致会做：

保存旧线程的 CPU 现场
    ↓
保存寄存器、栈位置、程序执行位置等
    ↓
切换地址空间或相关内存上下文（视线程/进程关系而定）
    ↓
恢复新线程以前保存的 CPU 现场
    ↓
CPU 从新线程上次停下的位置继续执行

所以线程不是像普通函数那样“从头调用一次”，而是：

调度器保存当前线程进度，再恢复另一个线程此前暂停的进度。

九、一个非常简化的判断代码

如果只想用最容易理解的伪代码表达，可以写成：

bool task_can_run_on_cpu(struct task_struct *p, int cpu)
{
    // 1. 它必须处于可运行状态
    if (p->__state != TASK_RUNNING)
        return false;

    // 2. 它必须允许在这颗 CPU 上运行
    if (!cpumask_test_cpu(cpu, p->cpus_ptr))
        return false;

    // 3. 这颗 CPU 必须在线
    if (!cpu_online(cpu))
        return false;

    // 4. 它不能正被带宽或 cgroup 等机制节流
    if (task_is_throttled(p))
        return false;

    // 5. 如果使用 Core Scheduling，还要满足核心调度安全约束
    if (!task_passes_core_sched_constraint(p, cpu))
        return false;

    return true;
}

再判断要不要抢占当前线程：

bool should_preempt(struct task_struct *curr,
                    struct task_struct *p)
{
    // 新线程连当前 CPU 都不能跑，就不能抢占
    if (!task_can_run_on_cpu(p, smp_processor_id()))
        return false;

    // 新线程调度类别更高，例如 RT 抢占普通线程
    if (p->sched_class 优先级高于 curr->sched_class)
        return true;

    // 都是 RT 时，实时优先级更高者抢占
    if (同为 RT 类 && p 的实时优先级高于 curr)
        return true;

    // 都是普通线程时，公平调度器判断谁更该获得 CPU
    if (同为 fair 类 && p 比 curr 更应该获得 CPU)
        return true;

    return false;
}

真实 Linux 内核当然比这个复杂得多，因为还要考虑：

  • 多核 CPU 之间的负载均衡；
  • 多 CPU 同时调度时的锁竞争；
  • 缓存命中率和缓存局部性；
  • NUMA 内存距离；
  • cgroup 和调度组；
  • CPU 性能差异，例如大小核、CPU capacity；
  • 能耗感知调度；
  • RT 与 Deadline 的带宽控制；
  • 上下文切换本身的性能成本；
  • 调度时钟；
  • tick 与无 tick（nohz）CPU；
  • 线程唤醒时的竞争；
  • 线程在不同 CPU 之间迁移的竞争。

十、最终记住这 6 个问题就够了

如果我是 CPU 调度器，面对一个 task_struct，我会按这个顺序想：

1. 它现在能运行吗？
   - 是否是 TASK_RUNNING？

2. 它在哪里等着？
   - 是否已经在运行队列里？
   - 或者它就是当前正在运行的线程？

3. 它能在这颗 CPU 上运行吗？
   - CPU 亲和性、cpuset、CPU 是否在线、是否允许迁移等。

4. 它属于哪种调度类别？
   - stop、deadline、RT、fair 还是 idle？

5. 在同一类别中，它的优先级或调度条件如何？
   - Deadline 看截止时间和运行预算；
   - RT 看实时优先级；
   - 普通线程看公平性、权重、等待时间等。

6. 现在适合切换吗？
   - 内核是否允许抢占？
   - 是否持有自旋锁？
   - 是否在中断上下文？
   - 切换是否值得，还是放到其他 CPU 更合适？

最终只有在：

next != current

时，调度器才会真正进行上下文切换，让 CPU 从当前线程转去执行 next 线程。

1. 先建立全局概念：线程可能在哪？

假设线程 A 要读磁盘文件。

它刚开始时是可运行的：

  ▼

  ▼

  │
  ▼

  │
  ▼
A 从 CPU 0 的运行队列移除
  │
  ▼
A 放到“磁盘 IO 等待队列”

TASK_RUNNING

            ▼

            ▼

调度器通常优先从：

当前 CPU 自己的运行队列

中选择下一个线程。

这样做的好处是：

  • 少抢锁，多个 CPU 可以并行调度；
  • 减少线程跨 CPU 迁移；
  • 更容易复用 CPU 缓存中的数据；
  • 对 NUMA 机器更友好。

4. 一个线程通常属于哪一个 CPU 的运行队列？

一个“可运行但没有正在执行”的线程，通常只会在一个 CPU 的运行队列中。

例如：

线程 A 可运行，且被分配到 CPU 2：

CPU 0 rq       CPU 1 rq       CPU 2 rq       CPU 3 rq

┌───────┐      ┌───────┐      ┌───────┐      ┌───────┐
│ B, C  │      │ D, E  │      │ A, F  │      │ G     │
└───────┘      └───────┘      └───────┘      └───────┘
                                     ▲
                                     │
                                  线程 A

它不会同时出现在 CPU 0 和 CPU 2 的队列中，否则可能被两个 CPU 同时执行，这显然是错误的。

5. 运行队列内部不是一个普通 FIFO 队列

每个 CPU 的 rq 看起来像一个队列，但内部实际上分成多个“调度类别的子队列”。

逻辑结构可以理解为：

CPU 0 的 runqueue（rq[0]）
│
├── stop 队列
│     └── 内核紧急控制任务
│
├── deadline 队列
│     └── SCHED_DEADLINE 线程
│
├── RT 队列
│     └── SCHED_FIFO / SCHED_RR 实时线程
│
├── fair 队列
│     └── 普通线程：SCHED_NORMAL / SCHED_BATCH 等
│
└── idle
      └── 没有任何可运行线程时才执行

CPU 选择下一个线程时，从上到下找：

有 stop 线程？
  有：运行 stop 线程
  没有：
    有 deadline 线程？
      有：运行 deadline 线程
      没有：
        有 RT 线程？
          有：运行 RT 线程
          没有：
            有普通 fair 线程？
              有：运行最合适的 fair 线程
              没有：运行 idle 线程

画成优先级金字塔：

优先级最高
     ▲
     │  stop
     │  deadline
     │  RT
     │  fair
     │  idle
     ▼
优先级最低

所以：

哪怕 fair 队列中有 10000 个普通线程，
只要有一个可运行的高优先级 RT 线程，
通常优先执行 RT 线程。

6. Fair 队列：普通线程所在的位置

普通线程，例如浏览器、Shell、Java 服务、Python 程序，大部分属于 fair 调度类。

逻辑上可以把它看成这样：

CPU 0 的 fair 队列

        最应该运行
             │
             ▼
   ┌─────────────────────┐
   │ 线程 C               │
   │ 线程 A               │
   │ 线程 D               │
   │ 线程 B               │
   └─────────────────────┘
             │
             ▼
        最不急 / 已运行较多

但它通常并不是简单的“先进先出链表”。

现代 Linux 的普通任务调度会综合考虑：

  • 线程已经运行了多久；
  • 线程已经等待了多久；
  • nice 值对应的权重；
  • 虚拟运行时间；
  • 虚拟截止期；
  • cgroup 调度组的限制和权重。

可以粗略理解为：

运行得少、等得久、权重高的普通线程
    → 更容易被选中。

例如：

线程 A：nice = 0，已经运行很多
线程 B：nice = 0，很久没获得 CPU
线程 C：nice = -10，权重较高

下一次普通调度时：
B 和 C 通常比 A 更有机会被选中。

内核实现上，fair 队列常用平衡树等结构，而不只是数组或链表；但脑中把它理解为“普通线程候选集合”即可。

7. RT 队列：实时线程所在的位置

RT，即实时线程，常见策略是：

SCHED_FIFO
SCHED_RR

它们有 1 到 99 的实时优先级。

概念上，RT 队列像是 100 个优先级格子：

RT 队列

优先级 99:  [线程 A]
优先级 98:  []
优先级 97:  [线程 B, 线程 C]
...
优先级 50:  [线程 D]
...
优先级 1 :  [线程 E]

调度器的规则很直接：

从最高的、非空的优先级格子中选线程。

例如：

优先级 90：线程 A
优先级 80：线程 B、线程 C
优先级 10：线程 D

那么一定先运行 A。

如果 A、B、C 都不存在，才轮到 D。

同一个优先级内部：

SCHED_FIFO：通常先来的先运行，除非主动让出或被更高优先级任务抢占。
SCHED_RR：同优先级线程按时间片轮流运行。

8. Deadline 队列：按截止时间排序

SCHED_DEADLINE 线程不主要看普通优先级，而是看截止时间。

逻辑上：

Deadline 队列

最早截止                 最晚截止
    │                        │
    ▼                        ▼
[线程 A] -> [线程 C] -> [线程 B]
  10ms       25ms       80ms

调度器通常选择：

截止时间最早的可运行线程。

但前提是它没有耗尽自己的 CPU 运行预算。

例如：

线程 A：
  每 100ms 为一个周期
  最多可运行 20ms
  必须在周期内的 50ms 前完成

如果这一周期的 20ms 已经用完，它可能会暂时被“节流”，不能继续占用 CPU。

9. 当前正在运行的线程在哪里？

假设 CPU 0 当前在执行线程 A。

可以这样理解：

CPU 0 的 rq[0]

┌────────────────────────────┐
│ 当前运行：线程 A             │ ───→ CPU 0 正在执行 A
│                            │
│ RT 候选：线程 R1             │
│ fair 候选：线程 B、C、D      │
└────────────────────────────┘

也就是说，当前线程和这个 CPU 的运行队列是关联的。

从概念上说：

CPU 当前线程：current
CPU 候选线程：该 CPU 的 rq 中其他可运行线程

当发生调度时：

当前：线程 A
候选：线程 B、C、R1

调度器比较后，选出 next = R1

如果 next != current：
    保存 A 的现场
    恢复 R1 的现场
    CPU 开始执行 R1

图示：

切换前：

CPU 0  ──正在执行──> 线程 A

rq[0] 中还有：
  RT：线程 R1
  fair：线程 B、线程 C


切换后：

CPU 0  ──正在执行──> 线程 R1

线程 A：
  若仍可运行，回到 fair 候选集合中等待；
  若它主动睡眠，则进入某个等待队列。

实际内核中，“当前运行任务是否仍标记为在 rq 上”有更细的实现细节；理解时记住：当前线程归当前 CPU 的调度器管理，其他候选线程也归同一个 rq 管理即可。

13. 最后用一句话区分所有“队列”

名称 放的是什么 线程状态 谁来使用
等待队列（wait queue） 正在等某个事件的线程 通常不是 TASK_RUNNING IO、锁、Socket、定时器等子系统
CPU 运行队列（runqueue / rq） 已经能运行、等待 CPU 的线程 TASK_RUNNING CPU 调度器
stop 子队列 内核紧急控制任务 可运行 stop 调度类
deadline 子队列 SCHED_DEADLINE 线程 可运行 Deadline 调度器
RT 子队列 SCHED_FIFO、SCHED_RR 线程 可运行 RT 调度器
fair 子队列 普通线程 可运行 普通公平调度器
idle 没有其他可运行线程时的兜底线程 可运行但优先级最低 idle 调度类

可以记成：

等待队列 = “我现在干不了活，等通知”
运行队列 = “我能干活，等 CPU”
调度类子队列 = “我能干活，但按不同优先级规则排队”

问

上面这些机制有没有体现什么设计思想或者哲学思维？

答

有，而且很明显。CPU 调度器里的这些队列、状态和规则，不只是“为了把线程跑起来”，背后体现了很多操作系统和工程设计思想。

可以先用一句话概括：

调度器不是在寻找“绝对最好的线程”，而是在资源有限、任务类型不同、CPU 很多、并发很高的情况下，用分层和规则来做“足够公平、足够及时、足够高效、而且不会出错”的权衡。

下面结合前面的队列和机制来看。

1. 状态机思想：先明确“线程现在能不能做事”

线程不会只有“运行”和“不运行”两种模糊状态，而是有明确状态：

正在运行
可运行，等待 CPU
等待 IO
等待锁
被暂停
退出中
已退出

可以抽象成状态机：

                  被调度
     ┌─────────────────────────┐
     │                         ▼
[可运行，等 CPU] ─────────> [正在运行]
     ▲                         │
     │                         │ 时间片到 / 被抢占
     │                         │
     │      被唤醒             ▼
[等待某事件] <────────── [等待 IO / 锁 / 网络]
     │
     └── IO 完成、锁释放、超时、事件到来

这体现的思想是：

不要用一个模糊的“是否活着”描述对象，而要用明确状态表达它当前允许做什么。

例如：

  • TASK_RUNNING：可以参与 CPU 调度；
  • 睡眠状态：不能参与 CPU 调度；
  • EXIT_DEAD：完全不能再执行。

这样调度器不需要猜：

“这个线程是不是大概可以运行？”

而是能明确判断：

“它现在是否具备运行资格？”

这是很多系统都会用到的思想，例如：

  • 网络连接状态：建立中、已连接、关闭中；
  • 订单状态：待支付、已支付、已发货、已取消；
  • 数据库事务：运行中、提交、回滚；
  • Kubernetes Pod：Pending、Running、Succeeded、Failed。

2. 分离关注点：等待队列和运行队列分开

这是最核心的设计之一。

等待队列：
“我现在不能干活，因为我在等事件。”

运行队列：
“我已经能干活，只是在等 CPU。”

图：

等待队列                           运行队列

等磁盘 IO                          等 CPU 时间
等网络数据                         已经可执行
等锁                               TASK_RUNNING
等定时器到期

为什么一定要分开？

因为“等事件”和“等 CPU”根本是两类不同问题。

如果不分开，会发生什么？

假设所有线程都放在一个大队列：

[A：等磁盘]
[B：等网络]
[C：能运行]
[D：等锁]
[E：能运行]

CPU 每次挑线程，都得判断：

A 的磁盘数据到了吗？
B 的网络包到了吗？
D 的锁释放了吗？

这很浪费。

更合理的方式是：

磁盘子系统只管理等磁盘的线程；
网络子系统只管理等网络的线程；
锁只管理等这把锁的线程；
调度器只管理已经能运行的线程。

于是：

磁盘完成
  → 唤醒等待磁盘的线程
  → 放入 CPU 运行队列
  → CPU 调度器只负责决定什么时候运行它

这体现了经典原则：

每个模块只处理自己真正关心的事情。

也就是常说的：

Separation of Concerns（关注点分离）

3. 事件驱动思想：没事做就睡，不要空转

线程等磁盘、等网络、等锁时，不应该一直占着 CPU 检查：

while (!数据到了) {
    不断检查;
}

这叫忙等（busy waiting）。

忙等的问题是：

CPU 被浪费；
其他线程得不到运行机会；
功耗升高；
系统负载看似很高，但其实没有有效工作。

更好的做法是：

线程发现数据没到
  ↓
把自己放进等待队列
  ↓
主动让出 CPU
  ↓
等事件真的发生时，再被唤醒

图：

错误方式：忙等

线程 A：
while (网络数据没到)
    一直占 CPU 检查


正确方式：阻塞等待

线程 A：
网络数据没到
    ↓
进入 Socket 等待队列
    ↓
让出 CPU
    ↓
网络包到达
    ↓
网络子系统唤醒 A
    ↓
A 重新竞争 CPU

这体现的思想是：

不要轮询一个不知道何时发生的事件；让事件发生时主动通知你。

这种事件驱动思想也出现在：

  • epoll；
  • JavaScript 的事件循环；
  • 消息队列；
  • GUI 点击事件；
  • 中断机制；
  • 异步 IO；
  • 条件变量 condition_variable。

4. 分治与去中心化：每个 CPU 有自己的运行队列

多核 CPU 下，Linux 不使用一个全局运行队列，而是：

CPU 0 → rq[0]
CPU 1 → rq[1]
CPU 2 → rq[2]
CPU 3 → rq[3]

图：

            ┌─────────┐
CPU 0 ────> │ rq[0]   │
            └─────────┘

            ┌─────────┐
CPU 1 ────> │ rq[1]   │
            └─────────┘

            ┌─────────┐
CPU 2 ────> │ rq[2]   │
            └─────────┘

这体现的是：

尽量让每个 CPU 管好自己的事情，不要让所有 CPU 都去争抢同一份全局数据。

如果只有一个全局队列：

CPU 0 ─┐
CPU 1 ─┼── 抢同一个全局锁 ──> 全局运行队列
CPU 2 ─┤
CPU 3 ─┘

问题是：

  • CPU 越多，争锁越严重；
  • 一个 CPU 在调度时，其他 CPU 可能被迫等待；
  • 很难扩展到几十、几百个 CPU；
  • 修改同一块共享内存，会造成缓存一致性开销。

每 CPU 一个运行队列后：

CPU 0 主要操作 rq[0]
CPU 1 主要操作 rq[1]
CPU 2 主要操作 rq[2]

大部分时间不需要互相打扰。

这叫：

分治（Divide and Conquer）
局部化（Locality）
去中心化（Decentralization）
减少共享状态（Minimize Shared State）

这也是高并发系统的常见原则。

5. 局部性优先：不要无意义地迁移线程

线程理论上可以从 CPU 0 跑到 CPU 3，但调度器不会无脑迁移。

原因是 CPU 有缓存。

CPU 0 缓存中：
  线程 A 最近访问的数据
  线程 A 的代码
  线程 A 的栈

如果 A 一直在 CPU 0 执行：

CPU 0 能直接利用缓存

如果突然把 A 搬到 CPU 3：

CPU 3 的缓存没有这些数据
  ↓
需要重新从更慢的缓存或内存加载
  ↓
性能可能变差

因此调度器倾向于：

能在原来的 CPU 上跑，就尽量别搬；只有负载不平衡或其他收益足够大时，才迁移。

图：

较优：

线程 A  → CPU 0 → CPU 0 → CPU 0
           缓存持续命中


可能较差：

线程 A  → CPU 0 → CPU 3 → CPU 1 → CPU 2
           缓存不断失效

这体现：

局部性原理（Locality）
迁移有成本
“少移动数据，不只是少移动代码”

NUMA 系统里更明显：

线程 A 常访问 CPU 0 附近的内存
    ↓
尽量让 A 在靠近该内存的 CPU 上运行

6. 分层思想：先分大类，再在类内比较

调度器不是把所有线程放在一起做一次“大排序”。

而是先分层：

stop
  ↓
deadline
  ↓
RT
  ↓
fair
  ↓
idle

然后在每一层内部使用不同规则：

Deadline：
    比谁的截止时间更早

RT：
    比谁的实时优先级更高

Fair：
    比谁等得更久、运行得更少、权重更高

Idle：
    只有没人可运行时才执行

为什么这样设计？

因为这些线程的目标不同。

线程类型 真正关心什么
Deadline 能否在截止时间前完成
RT 高优先级任务能否快速响应
Fair 普通任务 长期 CPU 分配是否公平
Idle 无事可做时是否低功耗等待

如果强行只用一个规则，例如“所有线程按 FIFO 排队”：

实时任务可能等太久；
普通任务可能饿死；
有截止时间的任务可能错过期限；
系统交互体验变差。

因此它体现的是：

不同目标不能强行用同一个指标优化；应该先分类，再为每类使用合适策略。

这和现实世界类似：

急诊病人：按紧急程度处理；
预约门诊：按预约顺序处理；
普通排队：按先来后到处理；
没人时：工作人员休息。

7. 公平不等于平均：普通线程按“权重”分 CPU

普通线程使用 Fair 调度思想，但“公平”不等于每个线程拿到完全一样的 CPU 时间。

例如：

线程 A：nice = -10，权重高
线程 B：nice = 0
线程 C：nice = 10，权重低

长期来看，可能是：

A 获得较多 CPU 时间；
B 获得正常 CPU 时间；
C 获得较少 CPU 时间。

这不是不公平，而是“按权重公平”。

类似于：

公司奖金不是每个人完全一样，
而是按岗位、责任、贡献或约定比例分配。

普通调度器通常还会关注：

谁已经运行得太多；
谁等待得太久；
谁的权重更高；
谁所在的 cgroup 应该获得更多或更少 CPU。

它的目标不是：

“下一毫秒绝对公平”

而是：

“拉长时间看，大致按规则公平，且没人长期饿死”

这是一种很重要的工程思想：

局部时刻可能不完美，但长期统计结果要合理。

8. 优先级与公平性是冲突的，需要承认并管理

例如有一个实时线程不断运行：

RT 线程一直有活干

那么普通线程可能一直得不到 CPU。

这不是普通公平调度器算法差，而是因为规则本身决定了：

实时性优先于普通公平性。

因此系统必须面对真实的冲突：

低延迟 vs 公平
实时性 vs 吞吐量
缓存局部性 vs 负载均衡
功耗 vs 性能
简单性 vs 精确性

没有一种调度策略可以同时做到：

绝对公平
绝对低延迟
绝对实时
绝对高吞吐
绝对低功耗
零调度开销

所以调度器的哲学不是：

找到完美方案。

而是：

明确不同场景的目标和优先级，并让用户或系统选择愿意接受的权衡。

例如：

SCHED_NORMAL：
    默认的通用公平策略。

SCHED_FIFO / SCHED_RR：
    为实时任务牺牲一部分普通任务公平性。

SCHED_DEADLINE：
    为截止时间保证引入运行预算、周期和准入控制。

CPU affinity：
    为局部性或隔离性牺牲一部分负载均衡能力。

9. “限制比承诺更重要”：Deadline 的预算和准入控制

SCHED_DEADLINE 很有代表性。

它不是简单说：

“这是一个紧急任务，永远优先。”

而是要求线程声明：

我每个周期需要多少 CPU 时间；
我的周期多长；
我最晚什么时候完成。

例如：

每 100ms 周期；
最多运行 20ms；
要求在 50ms 内完成。

然后系统要检查：

所有 Deadline 线程加起来，会不会超过 CPU 能提供的能力？

如果所有任务都说自己紧急：

线程 A：我要 80% CPU
线程 B：我要 70% CPU
线程 C：我要 60% CPU

总共 210%，那就不可能保证所有人的截止时间。

因此调度器需要准入控制：

做不到的承诺，宁可一开始就不接受。

这体现了很成熟的系统设计思想：

资源是有限的。与其承诺一个无法实现的保证，不如明确限制请求。

类似场景还有：

  • 数据库连接池限制连接数；
  • 云服务限制 QPS；
  • 消息队列限制消费者速率；
  • 网络 QoS 限速；
  • Kubernetes 资源 request / limit；
  • 信用卡额度或银行风控。

10. “快速路径优先”：绝大多数情况应当简单、快

实际系统中，绝大多数线程并不是实时线程，也不是 Deadline 线程，而是普通线程。

所以调度器通常会让常见路径尽量高效：

普通线程睡眠
  ↓
普通线程被唤醒
  ↓
放入合适 CPU 的普通运行队列
  ↓
按公平规则选择

而更复杂的逻辑只在需要时参与：

RT 优先级检查；
Deadline 预算；
跨 CPU 迁移；
NUMA；
cgroup 限制；
core scheduling；
CPU hotplug。

这体现：

常见操作必须快；复杂能力可以存在，但不应拖慢所有人。

也常被称为：

Make the common case fast
让常见路径足够快

11. 并发系统里，“正确性”比“看起来合理”更难

多个 CPU 可以同时做这些事情：

CPU 0：正在执行线程 A；
CPU 1：准备唤醒线程 A；
CPU 2：想把线程 A 迁移走；
CPU 3：正在改变 A 的 CPU affinity。

如果处理不严谨，可能出现灾难：

线程 A 同时被两个 CPU 执行；
线程 A 被唤醒后丢失；
线程 A 明明已经睡眠却还留在运行队列；
线程 A 已经退出却又被调度。

因此调度器会使用：

运行队列锁；
原子状态修改；
内存屏障；
严格的入队/出队规则；
跨 CPU 通知机制。

这体现：

在并发系统中，不仅要关心“逻辑上该选谁”，还要关心“多个 CPU 同时修改状态时，结果是否仍然正确”。

也就是说，调度算法只是表面；真正难的是并发正确性。

12. 最终可以把调度器理解为一个“多目标资源管理器”

CPU 调度器不是单纯的队列管理器，而是在管理稀缺资源：

CPU 时间
缓存
内存局部性
功耗
响应时间
实时性
多核之间的平衡

它需要同时满足很多目标：

普通用户希望：
    程序别卡顿、别饿死。

服务器希望：
    吞吐量高、延迟稳定。

实时任务希望：
    高优先级任务尽快执行。

移动设备希望：
    少耗电、少唤醒 CPU。

多核系统希望：
    不要都挤在一个 CPU 上，
    但也不要频繁迁移导致缓存失效。

所以最终的设计哲学可以总结为：

1. 用状态机消除模糊；
2. 用等待队列和运行队列分离不同问题；
3. 用事件唤醒代替无意义轮询；
4. 用每 CPU 队列减少共享和锁竞争；
5. 用局部性减少迁移和缓存损失；
6. 用调度分类处理不同目标；
7. 用长期公平代替机械平均；
8. 承认目标冲突，并允许策略选择；
9. 用预算和准入控制避免无法兑现的承诺；
10. 在高并发下，把正确性放在首位。

如果把它拟人化，CPU 调度器像一个大型医院的分诊系统：

急诊患者优先；
有明确手术时间的患者按截止时间安排；
普通患者按公平规则排队；
还没到医院的人不会占候诊位；
每个诊室主要处理自己的队伍；
患者尽量不要频繁换诊室；
医院不能承诺超过自身能力的预约；
任何时候都要确保一个患者不会被两个医生同时做同一台手术。

这基本就是操作系统调度器背后的“工程哲学”。

01先把问题摆正：调度器不「调用」线程

「要不要调用一个线程」这个问法里藏着一个错误的前提。线程不是函数，调度器不会从头调用它一次。它做的是一件更窄的事：

在某个时刻，从这颗 CPU 能挑的线程里选出一条，如果它不是当前那条，就把 CPU 的现场从旧的换到新的。

所以真正要回答的是四个问题，而且它们不在同一层：

问题 性质 由谁回答
它现在有资格运行吗？ 布尔门 p->__state
它允许在这颗 CPU 上运行吗？ 布尔门 p->cpus_ptr、CPU 是否 active
在都有资格的里面，谁最该跑？ 排序 p->sched_class，再按类内规则
现在就换吗？ 时机 TIF_NEED_RESCHED 在哪个安全点被兑现

前两个问题不通过，第三条根本轮不到比较。 把它们混成一句「谁优先级高」，就会得到「实时线程为什么没跑」这类想不通的问题：它可能根本不在候选集合里。第 04 节会把这条线拆成调度器实际走的六道闸。

02一张图：线程平时待的三个地方

先看一张地图。左边是等事件的队列，右边是等 CPU 的队列，中间那条路是线程从左边回到右边的过程。

先记住三句话：

  1. 等待队列不是一种队列，是每个事件一个。 「线程在等 IO」这句话，落到内核里是某个具体子系统的链表上多了一个 entry。线程可以同时挂在几个上，但这时它通常已经不在任何 rq 里了。
  2. 运行队列是按核分的。 一个可运行线程只在某一颗核的 rq 上；不存在一个所有核共享的全局队列。
  3. rq->curr 不是第六种队列。 它就是这颗核当前选中的那条，on_rq 仍是 1，但它已经不在红黑树/链表里排队了。

「一个线程只在一个地方」对运行队列成立，对等待队列不成立。 poll() 一次等多个 fd，同一个 task 会同时挂在几个等待队列上；一旦它被唤醒、变成可运行，就只会在某一颗核的 rq 上。

03调度器只读 task_struct 里的几组字段

一个 task_struct 有上百个字段，但没有一个函数会从头扫到尾。调度器按固定的顺序读几组，每组回答一个问题。下面按「读它的顺序」排，不是按结构体的字段顺序：

字段 取值 调度器问它什么 在哪一步读
__state TASK_RUNNING = 0；睡眠 = 1 / 2（位掩码，可叠加）；TASK_WAKING = 0x200 有资格运行吗 唤醒、schedule() 开头
on_rq 0 / QUEUED = 1 / MIGRATING = 2 在某一颗核的候选里吗 入队、出队、迁移
on_cpu 0 / 1 是不是正在某颗核上执行 switch_to 前后
sched_class stop / dl / rt / fair / ext / idle 先去哪一层找 pick_next_task()
prio、normal_prio、rt_priority、static_prio 0…139 类内怎么排、权重多少 RT、fair
policy SCHED_OTHER / FIFO / RR / BATCH / IDLE / DEADLINE / EXT 用哪一套规则 __setscheduler_class()
cpus_ptr、nr_cpus_allowed、migration_disabled 一个 cpumask 和两个计数 允许在哪颗核上跑 select_task_rq()、is_cpu_allowed()
se vruntime、deadline、slice、load.weight fair 层里排第几 pick_eevdf()
dl runtime、deadline、period、剩余 runtime dl 层里排第几、还有多少预算 pick_task_dl()、throttle

字段名对不上时，先看它属于哪一组：资格、位置、层级还是类内排序。 比如「为什么这条线程没被选中」如果发生在 cpus_ptr 上，去比较优先级永远找不到原因。

🔒

这几组字段大多不能无锁地读改。 它们的注释直接写清了各自的协议（kernel/sched/core.c 里有一段集中说明）：

  • __state 由线程自己用 set_current_state() 改，或由 try_to_wake_up() 拿着 p->pi_lock 改。TASK_WAKING 是唤醒过程中的临时态，用来避免「唤醒丢了」。
  • on_rq 只在 rq->lock 下由 activate_task() / deactivate_task() 改。迁移时先置成 MIGRATING，表示 task_cpu(p) 暂时不可信，别人别在这颗核上重复入队。
  • on_cpu 在 prepare_task() 里置 1，在 finish_task() 里清 0。try_to_wake_up() 会用 smp_cond_load_acquire(&p->on_cpu, !VAL) 等它落下，再挑核；否则一条线程可能在两颗核上同时跑。

还有一处容易读错：on_rq = 1 不严格等于「现在可运行」。 EEVDF 会把刚睡下的任务暂时留在队列里（se.sched_delayed），等它下次被挑到再出队；释放 CPU 的延迟出队也是类似的处理。判断「可运行」要看 task_is_runnable()，不是只看一个 on_rq。

04五道闸：从 task_struct 到「下一条跑谁」

把这几个字段串起来，就是调度器每次挑人时走的顺序。每一道闸不通过，后面就不用看了：

① 状态 __state == TASK_RUNNING？
② 候选 on_rq = QUEUED，或它就是 curr？
③ 亲和性 cpus_ptr 允许这颗核？CPU 是 active？
④ 层级 从 stop 往下，第一个有活的类
⑤ 类内排序 DL 看 deadline，RT 看优先级，fair 看虚拟截止期
⑥ next == curr？ 是 → 继续跑；否 → context_switch()

每道闸不通过时会发生什么，写在节点的 sub 里；这里再补两句：

  • ① 不通过：它留在等待队列里，调度器不会「顺便看一眼」它。
  • ② 不通过：它刚被创建或被唤醒，还没入队；先 enqueue_task()，再谈挑不挑。
  • ③ 不通过：不是「优先级不够」，而是这颗核根本不允许；select_task_rq() 会换一颗，或者等 CPU 上线。
  • ④ 不通过：五层全空才会走到 idle；idle 永远可运行，所以 pick_next_task() 不会返回空。
  • ⑤ 不通过：预算用完的 DL 线程、被 cgroup 节流的 fair 组，可能仍然可运行，但这一轮不参与。
  • ⑥：只有 next != curr，才会真的换栈、换寄存器。
⚡

语义上是五层从上往下，代码里有一个快路径。 __pick_next_task() 先判断：当前这条不比 fair 高、并且 rq->nr_running == rq->cfs.h_nr_queued（所有可运行线程都在 fair 层）时，直接调 pick_task_fair()，不遍历五个类；否则才 for_each_active_class() 逐层找。

常见情况是「全是普通线程」，所以这条快路径值得单独写。分层是语义，不是每次都要跑满五次函数调用。

05六层各自按什么排

上一层说「从 stop 往下找」，这一节看每一层内部到底按什么键排序。stop、deadline、RT、fair、idle 这五层是内核固定的调度类，ext 是编译期可选的扩展：

层 谁在里面 队列长什么样 排序键 / 规则 硬限制
stop rq->stop 一个指针，不排队 最高；它抢一切，自己不被抢 只有 stop_machine() 的 stopper 线程
deadline SCHED_DEADLINE dl_rq 红黑树 绝对 deadline 最早先跑 准入控制；每周期 runtime 用完就 throttle
RT SCHED_FIFO / SCHED_RR 100 条优先级链 + 一个位图 位图取最高非空级；同级 FIFO 或 RR 默认 RT 带宽 95%
fair SCHED_OTHER / BATCH / IDLE cfs_rq 红黑树 EEVDF：先 eligible（lag ≥ 0），再取虚拟截止期最早 权重、cgroup 配额
ext BPF 调度器接管的线程 由 BPF 程序决定 由 BPF 程序决定 启用 all 模式时 fair 整层被跳过
idle rq->idle 一个指针 兜底 每核一条，永远可运行

三个容易踩的地方：

一、SCHED_IDLE 不是 idle 调度类。 它仍然挂在 fair 层，只是权重被设成 3（nice 0 是 1024）；idle 调度类里只有每颗核那条 idle 线程。名字像，位置完全不同。

二、p->prio 和用户看到的实时优先级是反的。 用户给 RT 线程的 sched_priority 是 1–99，越大越急；内核里 p->prio = 99 - rt_priority，所以 RT 80 对应 p->prio 19。stop 在比较里是 -2，DL 是 -1，fair 是 120 + nice。看内核代码时按「数值小 = 更急」读，别拿用户层的数字直接比。

三、DL 的「最早截止期」不是无条件的。 线程声明了 runtime / period / deadline 之后，系统先做准入控制：所有 DL 线程的带宽加起来超过上限，sched_setattr() 直接失败。跑起来之后，这一周期预算用完也会被 throttle 到下一个周期。它保证的是「按声明给」，不是「永远优先」。

07能跑不等于马上换：抢占要等一个安全点

线程被唤醒、入了队，只说明它重新有资格。要不要立刻从当前线程手里拿走 CPU，是另一件事。

ttwu_do_activate() 里，activate_task() 之后紧接着调用 wakeup_preempt()。它判断的是一件事：要不要给当前线程打 TIF_NEED_RESCHED。

  • 新线程和当前线程在同一层：调这一层的 wakeup_preempt()。fair 比虚拟截止期，RT 比实时优先级，DL 比 deadline。
  • 新线程的层比当前高：直接 resched_curr()，再把 rq->next_class 改成新的层。

打了标记不等于马上切。内核要等到一个能安全切换的点：

场景 接下来发生什么
新线程层级更高，或同层 RT 优先级更高 打 TIF_NEED_RESCHED，发 IPI 叫目标核尽快调度
同层 fair，虚拟截止期更早 由 fair 的 wakeup_preempt() 决定，通常也打标记
当前线程正持自旋锁、或关着抢占 只能先记着，等 preempt_enable() / 解锁时再切
当前在中断上下文 不在中断里直接切；中断退出时走 preempt_schedule_irq()
新线程的亲和性不允许这颗核 不在这颗核上抢；select_task_rq() 换核，或等
新线程所在的 cgroup 配额用完 整组被 throttle，线程可运行也先不给跑
内核是 lazy 抢占，且新线程是 fair 只打 TIF_NEED_RESCHED_LAZY；回用户态或下一个 tick 才切

最后一行是 6.13 起才有的模式。它把「内核里正跑到一半的活」尽量跑完，减少「刚放下锁就被抢走、缓存又被冲掉」的情况；实时线程不受这个延迟影响，仍然用 TIF_NEED_RESCHED。

抢占模型内核代码什么时候能让出 CPU代价
none只在显式 cond_resched() / 阻塞点内核路径简单，但延迟不可控
voluntarynone + might_sleep() 处兼顾一点延迟和吞吐
full没有显式关抢占的地方都能切延迟低，切换更频繁
lazyfull + fair 的请求延到回用户态或下个 tick兼顾响应和缓存，实时任务不走这条

「不能切」不是调度器犹豫，是切了会坏。 自旋锁要求持锁期间不睡眠；中断上下文没有普通线程的栈和状态可换；preempt_count 不为 0 时切走，锁的释放顺序就乱了。所以这些地方只打标记，等安全点。

08真正切过去时，切的是什么

next != curr 之后，context_switch() 做两件事：如果是跨进程，换地址空间（switch_mm_irqs_off()）；然后 switch_to() 换栈和寄存器。x86-64 的底层核心是这几行（省掉了返回栈缓冲和 canary 的几条）：

__switch_to_asm:
    pushq %rbp
    pushq %rbx
    pushq %r12
    pushq %r13
    pushq %r14
    pushq %r15
    movq  %rsp, TASK_threadsp(%rdi)   # 保存旧线程的栈指针
    movq  TASK_threadsp(%rsi), %rsp   # 换成新线程的栈
    popq  %r15
    ...
    jmp   __switch_to

保存的是 callee-saved 寄存器 + 栈指针。用户态寄存器早在系统调用或中断入口就压进了内核栈上的 pt_regs，不需要在这里再存一遍。

换了 没换
内核栈指针（thread.sp） 用户态寄存器（在 pt_regs 里）
rbp / rbx / r12–r15 用户栈的内容
current、rq->curr、on_cpu 同一进程的页表（线程切换不换 CR3）
跨进程时的地址空间和 PCID 缓存和 TLB：跟着核走，换核才变冷

所以线程不是被「调用」一次。它上次在 switch_to() 里被换下，这次从同一个位置返回，继续执行 finish_task_switch() 之后的代码。调度器保存的是「停在哪」，不是「从头开始」。

09这些机制背后的十条取舍

把前面所有机制收成一张表。每一行都是「用某个结构解决一个问题，同时接受一个代价」：

取舍在这个内核里落在哪付出的代价
先问资格，再问排序__state、cpus_ptr 是布尔门；不通过就不进比较多几步判断，换来语义不混
等事件和等 CPU 分开wait_queue 归子系统，rq 归调度器唤醒要跨模块调用
睡下去，不空转阻塞 + wake_up()，不轮询一次上下文切换和一条唤醒路径
每颗核管自己的队列每 CPU 一个 rq、一把 rq 锁要额外做负载均衡
能不动就不动唤醒优先同核 / 热缓存，迁移要过亲和性和收益短时间可能不均
不同目标不进同一个比较器stop / dl / rt / fair / idle 分层高类能饿死低类，只能靠带宽限制兜底
公平是加权的长期账nice 权重、EEVDF 的 lag 和虚拟截止期单次调度不保证最公平
承认冲突，把选择权交出去抢占模型、RT 95%、cgroup quota、affinity配错了比默认更慢
承诺前先算账DL 准入控制 + 每周期 runtime throttle做不到的请求直接拒绝，或留出余量
常见路径快，正确性优先fair 快路径、on_rq=MIGRATING、on_cpu 屏障代码复杂，读起来费劲

这些取舍会互相打架。想要低延迟，就得让实时线程压住普通线程；压得太狠，普通线程会饿，于是有了 95% 的 RT 带宽上限。想要缓存热，就别迁移；都不迁移，负载又会歪，于是有了唤醒挑核和周期性的负载均衡。想要内核路径简单，就别到处抢占；延迟要求上来了，又得加 PREEMPT 和 lazy。

没有一组参数能同时把延迟、吞吐、公平、功耗都做到最好。 内核的做法是选一组默认值，再把旋钮交出去：nice、sched_setattr()、cgroup 的 cpu.max、taskset、preempt=。调度器的任务不是找最优解，是在给定约束下选一组能接受的解。

11最后记六个问题

如果只留一张速查，就留这六问，按顺序问：

  1. 它有资格吗？ __state == TASK_RUNNING。
  2. 它在候选里吗？ on_rq 已置位，或者它就是 curr。
  3. 它能在这颗核上跑吗？ cpus_ptr 允许，CPU 是 active。
  4. 它在哪一层？ sched_class：stop → dl → rt → fair → ext → idle。
  5. 层内怎么排？ DL 看绝对 deadline，RT 看优先级，fair 看虚拟截止期，idle 兜底。
  6. 现在就换吗？ need_resched 在哪个安全点被兑现。

只有第 6 问的答案是「换」，才会走到 context_switch()；否则当前线程继续跑。线程不是被「调用」起来的，它是在某个安全点上被恢复的。

线程睡在磁盘等待队列里时，__state 和 on_rq 大概是什么？

__state 是 TASK_INTERRUPTIBLE（或 TASK_UNINTERRUPTIBLE），不是 TASK_RUNNING； on_rq 是 0——它在 schedule() 里已经被 deactivate_task() 摘下去了。 这两个字段不是一起变的：改状态在前，出队发生在真正让出 CPU 时。

rq->curr 还在运行队列上吗？为什么它不在红黑树里？

在。on_rq 仍是 QUEUED，所以 task_on_rq_queued() 为真；但它已经被选中， 是 cfs_rq->curr，不在红黑树里等。被换下时，如果它还可运行就回到树里， 如果它睡了就出队去等待队列。

一条 RT 线程被唤醒并入队了，为什么可能没有立刻抢占当前线程？

先确认它是不是真的更高：同层 RT 要比 rt_priority，跨层才无条件更高。 再看环境：当前可能正持自旋锁、关着抢占，或在中断上下文，只能先打 TIF_NEED_RESCHED；也可能它的亲和性不允许这颗核，select_task_rq() 把它放到了别的核上。

SCHED_IDLE 和 idle 调度类是一回事吗？

不是。SCHED_IDLE 是 fair 层里的一种策略，权重只有 3（nice 0 是 1024）， 仍然和其他普通线程一起比较；idle 调度类里只有每颗核那条 rq->idle 线程， 它是前面几层都没活时的兜底。

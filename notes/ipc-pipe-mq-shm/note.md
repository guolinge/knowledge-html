## 01 · 你的直觉对了一半

> 我的理解是，它们都是把一些信息放在一块公共内存上而已。

这句话里**「缓冲区在哪」说对了，「谁能碰它」说错了。**

```compare
first: 机制
head: [缓冲区在哪, 进程能直接访问吗, 数据怎么过去]
rows:
  - 共享内存: ["同一块物理内存", { text: "能。这才是它唯一的卖点", tone: green }, "不用过去 —— A 写进去，B 直接就看到"]
  - 管道: ["内核内存里的环形队列", { text: "不能。进程碰不到那块内存", tone: red }, "让内核拷贝两次"]
  - 消息队列: ["内核内存里的一段", { text: "不能。同上", tone: red }, "让内核拷贝两次"]
```

==管道和消息队列的缓冲区确实在内核内存里，但那是内核的内存，不是「公共内存」。== 进程只能通过系统调用请内核帮你搬。

这个区别的后果很具体：**拷贝次数从 2 变成 0。**

## 04 · 消息队列：也是两次拷贝，但一条一条有边界

```journey
- tag: 第 1 站
  tone: blue
  name: 进程 A 装好一条消息
  badge: 拷贝 0 次
  fields:
    - { k: type, v: "1" }
    - { k: data, v: "order#99" }
  note: 消息是一个带类型标记的完整单位，不是一串字节
  next: "A 调 msgsnd() :: :: 陷入内核"
- tag: 第 2 站
  tone: violet
  name: 消息队列（内核里）
  badge: 拷贝 1 次
  fields:
    - { k: 排队, v: "type=1 order#99" }
    - { k: 后面还排着, v: "type=2 hello" }
    - { k: 还能按 type 分拣, v: "B 可以选择只取某一种", note: 管道做不到, tone: ok }
  note: 队列是有序的，消息之间的边界被完整保留
  next: "B 调 msgrcv() :: :: 再陷入内核一次"
- tag: 第 3 站
  tone: green
  name: 进程 B 收到一整条
  badge: 拷贝 2 次
  fields:
    - { k: 拿到的, v: "type=1 · order#99", note: 边界还在, tone: ok }
  note: 取走就没了，像从邮局取走信件
```

==拷贝次数和管道一样，但它多给你一样东西：边界和类型。==

## 05 · 共享内存：零拷贝，但内核什么都不管

```journey
- tag: 第 1 站
  tone: blue
  name: 两个进程各自 shmat()
  badge: 拷贝 0 次
  fields:
    - { k: A 的虚拟地址, v: "0x7f001000" }
    - { k: B 的虚拟地址, v: "0x7f009000", note: 地址不一样, tone: warn }
    - { k: 指向的物理内存, v: "同一块", note: 关键就在这, tone: ok }
  note: 页表把两个不同的虚拟地址翻译到同一块物理内存上
  next: "A 开始写 :: :: 之后就不需要内核了"
- tag: 第 2 站
  tone: green
  name: A 写 ptr[0]
  badge: 拷贝 0 次 · 系统调用 0 次
  fields:
    - { k: 这是一条什么指令, v: "就是最普通的内存写", note: 不是系统调用, tone: ok }
    - { k: 数据去了哪, v: "直接落在了那块共享的物理内存上" }
  note: 没有拷贝 —— 因为它写的就是最终目的地
  next: "B 去读 :: :: 也不需要内核"
- tag: 第 3 站
  tone: green
  name: B 读 ptr[0]
  badge: 全程 0 拷贝
  fields:
    - { k: 拿到的, v: "'H' —— 它直接看到了", note: 中间没有任何搬运, tone: ok }
    - { k: 代价, v: "内核不帮你保证任何秩序" }
  note: 像两个人在同一块黑板上写字和看字
```

但**快不等于好。** 内核在这里什么都不管，包括「A 写到一半 B 就来读」：

```flow
grid: true
groups:
  - { id: race, label: "共享内存里没有「一条消息」这个概念，只有裸的内存", tone: red }
nodes:
  - { id: a1, label: "A 写了 count = 42", sub: "结构体的第一个字段", row: 0, tone: green, group: race }
  - { id: switch, label: "A 还没写 name 就被换下了", sub: "时间片到了", row: 1, tone: amber, group: race }
  - { id: b, label: "B 读到了 count = 42", sub: "新数据", row: 2, tone: red, group: race }
  - { id: b2, label: "但 name 是旧值或垃圾", sub: "内核不会阻止这件事发生", row: 3, tone: red, group: race }
edges:
  - { from: a1, to: switch, label: "" }
  - { from: switch, to: b, label: "B 不知道它只写了一半" }
  - { from: b, to: b2, label: "" }
```

==这就是为什么共享内存几乎总是和信号量一起用。== 那份「谁该等谁」的秩序，得你自己补上。

## 07 · 三个区别各自意味着什么

### 区别一：拷贝次数的差距，会随数据量放大

```compare
first: 数据量
head: [拷贝的代价, 于是瓶颈落在哪]
rows:
  - 小数据（几十字节）: ["拷贝两次也就几百纳秒，感知不到", "==两次陷入内核的固定成本反而更显眼=="]
  - 大数据（视频帧、大文件）: [{ text: "同样两次拷贝，但要搬几 MB", tone: red }, { text: "内存带宽直接成了瓶颈 —— 共享内存的优势在这里才体现", tone: green }]
```

```callout
tone: violet
icon: 📐
text: |
  **所以「共享内存最快」这句话只在数据量大时才成立。**

  小消息场景里，省下来的那次拷贝可能还不如「共享内存要自己加信号量」带来的复杂度。

  ==选它的理由应该是「数据大」或「访问频繁」，而不是「它最快」。==
```

### 区别二：字节流 vs 消息 vs 自由格式

**管道不保留边界**，这件事在写得比读得快的时候会立刻暴露：

```journey
- tag: A 这边
  tone: blue
  name: 三次 write，三次都是一小段
  badge: 写入方很清楚边界
  fields:
    - { k: 第 1 次, v: "write(fd, \"aaa\", 3)" }
    - { k: 第 2 次, v: "write(fd, \"bb\", 2)" }
    - { k: 第 3 次, v: "write(fd, \"cccc\", 4)" }
  note: 在 A 看来，这是三个逻辑上独立的东西
  next: "写进了同一条字节流 :: :: 边界在这就没了"
- tag: B 这边
  tone: red
  name: 一次 read，全糊在一起
  badge: 边界丢失
  fields:
    - { k: read(fd, buf, 100), v: "\"aaabbcccc\"" }
    - { k: B 想知道的, v: "哪里是第一段的结尾？", note: 读不出来了, tone: warn }
  noteTone: bad
  note: ==管道不保证「写三次就读三次」。== 想要边界，就得自己在协议里划（长度前缀、分隔符）
```

消息队列把这件事替你做掉了：

```compare
first: 机制
head: [边界, 能不能挑着收]
rows:
  - 管道: [{ text: "没有。「三次写」可能被一次读全拿走", tone: red }, "不能，只能按顺序读"]
  - 消息队列: [{ text: "有。一条就是一条，边界完整保留", tone: green }, { text: "能。可以只取 type=1 的那些", tone: green }]
  - 共享内存: ["你自己在内存里怎么摆就有怎么样的边界", "无所谓边界，你直接读结构体"]
```

### 区别三：内核帮不帮你管秩序

```compare
first: 情况
head: [管道 / 消息队列, 共享内存]
rows:
  - 空了: [{ text: "read 自动阻塞，等数据来", tone: green }, { text: "读到一半的旧数据，你自己保证", tone: red }]
  - 满了: [{ text: "write 自动阻塞，等对方取走", tone: green }, "根本没有「满」的概念"]
  - 写了一半被换下: ["不可能 —— 一次 write 是原子的（小于 PIPE_BUF 时）", { text: "完全可能，B 会看到半成品", tone: red }]
  - 你还要写多少代码: [{ text: "几乎不用", tone: green }, { text: "一套信号量或互斥锁，而且很容易写错", tone: amber }]
```

==这三种机制是「内核替你担了多少责任」的三档。== 管道和消息队列把它全担了；共享内存一点都不担，换来的是那两次拷贝。

```cards
  - title: 共享内存 = 公共黑板

    tone: green
    desc: 直接在黑板上写，但别人也可能同时在写

      - **不需要中间人**：省掉了搬运

```

## 09 · 什么时候用哪个

```matrix

y: { label: 你能接受多少复杂度, from: 越省心越好, to: 愿意自己管同步 }
cells:
  - { title: 管道就够了, desc: "父子进程传个命令、shell 管线。字节流、有背压，代码三行", tone: blue }
  - { title: 消息队列, desc: "要边界、要按类型分拣。内核帮你排队和阻塞，省心", tone: violet }
  - { title: 管道也够用, desc: "小数据下两次拷贝感知不到，别为省这点开销背上一套锁", tone: muted }
  - { title: 共享内存 + 信号量, desc: "视频帧、大缓冲区、高频共享表。零拷贝的收益在这里才划算", tone: green }
```

```callout
tone: violet
icon: 🎯
text: |
  **一句话记住这三者的定位。**

  - 管道：==内核帮你搬数据==，字节流，有背压，简单省心
  - 消息队列：==内核帮你搬数据==，一条一条的，还能按类型取
  - 共享内存：==不搬数据==，两个进程直接看同一块内存，最快但最危险

  ++它们不是「都放在公共内存上」。前两个是「让内核当快递员帮你搬」，
  只有第三个是「真正的公共黑板，你们自己直接读写」。++
```

```quiz
- q: 管道和消息队列的缓冲区也在内核内存里，那为什么不能说它们是「共享内存」？
  a: |
    因为「在哪」和「谁能碰」是两件事。缓冲区确实在内核内存里，但那是内核的内存，
    进程没有权限直接访问，也没有映射到自己的地址空间里。
    进程能做的只是递一个指针给内核，请它帮忙搬，于是有了两次拷贝。
    共享内存是把同一块物理内存映射进两个进程的地址空间，两边都能直接读写，所以是零拷贝。
- q: 共享内存比管道快，是不是应该尽量用共享内存？
  a: |
    要看数据量。小消息场景下，省掉的那次拷贝可能还不如系统调用的固定开销显眼，
    而共享内存要自己补一整套信号量或锁，复杂度和出错概率都上去了。
    它真正的优势在大数据量（视频帧、大缓冲区）或高频访问时才体现出来。
    选它的理由应该是「数据大」或「访问频繁」，不是「它最快」。
- q: 为什么共享内存几乎总是和信号量一起用？
  a: |
    因为内核在这里什么都不管。管道和消息队列满了会阻塞、空了会阻塞，
    而且一次 write 或 msgsnd 是原子的；共享内存里没有「一条消息」这个概念，
    只有裸的内存。A 写完结构体的第一个字段就被换下，B 就可能读到半成品。
    这份「谁该等谁」的秩序内核不会给你，只能自己用信号量或互斥锁补上。
- q: 往管道里 write 三次，另一端 read 一次会把三次的内容一起读走吗？
  a: |
    可能会。管道是字节流，不保留写入的边界，三次写进去的内容在缓冲区里是连成一片的。
    一次 read 完全可能把三段的拼接一起拿走，读的人没法从数据本身判断哪里是第一段的结尾。
    想要边界，要么自己在协议里加长度前缀或分隔符，要么改用消息队列。
```

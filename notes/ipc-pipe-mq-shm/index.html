管道 / 消息队列 / 共享内存 · 三种 IPC 到底差在哪

「它们都是把信息放在一块公共内存上」—— 这句话对了一半。管道和消息队列的缓冲区确实在内核里，但进程碰不到它；只有共享内存是真正两个进程在看同一块内存。差别全在拷贝次数、边界、以及内核帮不帮你管秩序。

01你的直觉对了一半

我的理解是，它们都是把一些信息放在一块公共内存上而已。

这句话里「缓冲区在哪」说对了，「谁能碰它」说错了。

机制缓冲区在哪进程能直接访问吗数据怎么过去
共享内存同一块物理内存能。这才是它唯一的卖点不用过去 —— A 写进去，B 直接就看到
管道内核内存里的环形队列不能。进程碰不到那块内存让内核拷贝两次
消息队列内核内存里的一段不能。同上让内核拷贝两次

管道和消息队列的缓冲区确实在内核内存里，但那是内核的内存，不是「公共内存」。 进程只能通过系统调用请内核帮你搬。

这个区别的后果很具体：拷贝次数从 2 变成 0。

02数据怎么走：三种并排跑一遍

把三种机制摆在同一排，同步推进，看数据停在哪一格、计数怎么变：

同一份数据，三种走法 点「下一步」或「自动跑」

三列的上格和下格长得一样（发送方 / 接收方的用户空间）。有差别的只有中间那格。

03管道：两次拷贝，A 和 B 永远看不到那个缓冲区

第 1 站 进程 A 的缓冲区 拷贝 0 次
内容hello
谁能看见只有 A 自己

这就是一块普通的用户态内存，跟内核没关系

A 调 write()陷入内核，请内核帮忙搬
第 2 站 管道缓冲区（内核里） 拷贝 1 次
结构环形队列
谁能看见只有内核。A 和 B 都不知道它长什么样关键

数据到这里就已经被搬过一次了。但还没到 B 手上

B 调 read()再陷入内核一次
第 3 站 进程 B 的缓冲区 拷贝 2 次
内容hello和 A 写进去的一样
管道缓冲区空了 —— 水已经流过去了

读完就没了，像水流过水管

谁来搬次数说明
拷贝2 次A 的用户态 → 内核，内核 → B 的用户态
系统调用2 次write() 一次，read() 一次。每次都要陷入内核
进程直接碰缓冲区碰不到它只能递一个指针给内核，剩下的内核办

管道的格式是「字节流」，没有边界。 这一点后面单独说，它会造成一个很实际的麻烦。

04消息队列：也是两次拷贝，但一条一条有边界

第 1 站 进程 A 装好一条消息 拷贝 0 次
type1
dataorder#99

消息是一个带类型标记的完整单位，不是一串字节

A 调 msgsnd()陷入内核
第 2 站 消息队列（内核里） 拷贝 1 次
排队type=1 order#99
后面还排着type=2 hello
还能按 type 分拣B 可以选择只取某一种管道做不到

队列是有序的，消息之间的边界被完整保留

B 调 msgrcv()再陷入内核一次
第 3 站 进程 B 收到一整条 拷贝 2 次
拿到的type=1 · order#99边界还在

取走就没了，像从邮局取走信件

拷贝次数和管道一样，但它多给你一样东西：边界和类型。

05共享内存：零拷贝，但内核什么都不管

第 1 站 两个进程各自 shmat() 拷贝 0 次
A 的虚拟地址0x7f001000
B 的虚拟地址0x7f009000地址不一样
指向的物理内存同一块关键就在这

页表把两个不同的虚拟地址翻译到同一块物理内存上

A 开始写之后就不需要内核了
第 2 站 A 写 ptr[0] 拷贝 0 次 · 系统调用 0 次
这是一条什么指令就是最普通的内存写不是系统调用
数据去了哪直接落在了那块共享的物理内存上

没有拷贝 —— 因为它写的就是最终目的地

B 去读也不需要内核
第 3 站 B 读 ptr[0] 全程 0 拷贝
拿到的'H' —— 它直接看到了中间没有任何搬运
代价内核不帮你保证任何秩序

像两个人在同一块黑板上写字和看字

但快不等于好。 内核在这里什么都不管，包括「A 写到一半 B 就来读」：

共享内存里没有「一条消息」这个概念，只有裸的内存
A 写了 count = 42 结构体的第一个字段
A 还没写 name 就被换下了 时间片到了
B 读到了 count = 42 新数据
但 name 是旧值或垃圾 内核不会阻止这件事发生

这就是为什么共享内存几乎总是和信号量一起用。 那份「谁该等谁」的秩序，得你自己补上。

06三者核心区别一览

维度管道消息队列共享内存
数据拷贝2 次2 次0 次
需要系统调用搬数据每次 read/write 都要进内核每次 msgsnd/msgrcv 都要进内核只在建立映射时；之后就是普通内存读写
速度中等中等最快
数据格式字节流，没有边界一条一条的消息，有边界有类型随便你，结构体数组都行
内核帮你管秩序吗管。读空自动阻塞，写满自动阻塞管。队列空/满都自动阻塞不管。要自己配信号量
数据持久性读完就没了，像水流过水管取走就没了，像取走信件一直在那里，直到你覆盖或删除

07三个区别各自意味着什么

区别一：拷贝次数的差距，会随数据量放大

数据量拷贝的代价于是瓶颈落在哪
小数据（几十字节）拷贝两次也就几百纳秒，感知不到两次陷入内核的固定成本反而更显眼
大数据（视频帧、大文件）同样两次拷贝，但要搬几 MB内存带宽直接成了瓶颈 —— 共享内存的优势在这里才体现
📐

所以「共享内存最快」这句话只在数据量大时才成立。

小消息场景里，省下来的那次拷贝可能还不如「共享内存要自己加信号量」带来的复杂度。

选它的理由应该是「数据大」或「访问频繁」，而不是「它最快」。

区别二：字节流 vs 消息 vs 自由格式

管道不保留边界，这件事在写得比读得快的时候会立刻暴露：

A 这边 三次 write，三次都是一小段 写入方很清楚边界
第 1 次write(fd, "aaa", 3)
第 2 次write(fd, "bb", 2)
第 3 次write(fd, "cccc", 4)

在 A 看来，这是三个逻辑上独立的东西

写进了同一条字节流边界在这就没了
B 这边 一次 read，全糊在一起 边界丢失
read(fd"aaabbcccc"
B 想知道的哪里是第一段的结尾？读不出来了

管道不保证「写三次就读三次」。 想要边界，就得自己在协议里划（长度前缀、分隔符）

消息队列把这件事替你做掉了：

机制边界能不能挑着收
管道没有。「三次写」可能被一次读全拿走不能，只能按顺序读
消息队列有。一条就是一条，边界完整保留能。可以只取 type=1 的那些
共享内存你自己在内存里怎么摆就有怎么样的边界无所谓边界，你直接读结构体

区别三：内核帮不帮你管秩序

情况管道 / 消息队列共享内存
空了read 自动阻塞，等数据来读到一半的旧数据，你自己保证
满了write 自动阻塞，等对方取走根本没有「满」的概念
写了一半被换下不可能 —— 一次 write 是原子的（小于 PIPE_BUF 时）完全可能，B 会看到半成品
你还要写多少代码几乎不用一套信号量或互斥锁，而且很容易写错

这三种机制是「内核替你担了多少责任」的三档。 管道和消息队列把它全担了；共享内存一点都不担，换来的是那两次拷贝。

08用类比一次说清

单向、连续

管道 = 水管

倒进去的是水，接出来的也是水，看不出你倒了几杯

  • 单向流动：一端写，另一端读
  • 连续的水流：没有「一份一份」的概念
  • 有背压：管满了就倒不进去，管空了就接不到
  • 水流过去就没了，不能再取一次
一件一件

消息队列 = 邮局

每封信是独立的，还能按类型分拣

  • 每封信独立：边界完整，取一次就是完整的一封
  • 可以按类型取：先拿紧急的那封
  • 取走就没了
  • 经过邮局中转：内核帮你搬，但你看不到中转仓
大家都看得见

共享内存 = 公共黑板

直接在黑板上写，但别人也可能同时在写

  • 不需要中间人：省掉了搬运
  • 没有边界、没有顺序、没有背压：一块内存而已
  • 两个人同时写就会打架（竞态）
  • 所以几乎总是配一把锁（信号量）

09什么时候用哪个

你能接受多少复杂度
愿意自己管同步
管道就够了 父子进程传个命令、shell 管线。字节流、有背压，代码三行
消息队列 要边界、要按类型分拣。内核帮你排队和阻塞，省心
管道也够用 小数据下两次拷贝感知不到，别为省这点开销背上一套锁
共享内存 + 信号量 视频帧、大缓冲区、高频共享表。零拷贝的收益在这里才划算
越省心越好
小消息大数据 / 高频访问
数据量
🎯

一句话记住这三者的定位。

  • 管道：内核帮你搬数据，字节流，有背压，简单省心
  • 消息队列：内核帮你搬数据，一条一条的，还能按类型取
  • 共享内存：不搬数据，两个进程直接看同一块内存，最快但最危险

它们不是「都放在公共内存上」。前两个是「让内核当快递员帮你搬」， 只有第三个是「真正的公共黑板，你们自己直接读写」。

管道和消息队列的缓冲区也在内核内存里，那为什么不能说它们是「共享内存」？

因为「在哪」和「谁能碰」是两件事。缓冲区确实在内核内存里，但那是内核的内存， 进程没有权限直接访问，也没有映射到自己的地址空间里。 进程能做的只是递一个指针给内核，请它帮忙搬，于是有了两次拷贝。 共享内存是把同一块物理内存映射进两个进程的地址空间，两边都能直接读写，所以是零拷贝。

共享内存比管道快，是不是应该尽量用共享内存？

要看数据量。小消息场景下，省掉的那次拷贝可能还不如系统调用的固定开销显眼， 而共享内存要自己补一整套信号量或锁，复杂度和出错概率都上去了。 它真正的优势在大数据量（视频帧、大缓冲区）或高频访问时才体现出来。 选它的理由应该是「数据大」或「访问频繁」，不是「它最快」。

为什么共享内存几乎总是和信号量一起用？

因为内核在这里什么都不管。管道和消息队列满了会阻塞、空了会阻塞， 而且一次 write 或 msgsnd 是原子的；共享内存里没有「一条消息」这个概念， 只有裸的内存。A 写完结构体的第一个字段就被换下，B 就可能读到半成品。 这份「谁该等谁」的秩序内核不会给你，只能自己用信号量或互斥锁补上。

往管道里 write 三次，另一端 read 一次会把三次的内容一起读走吗？

可能会。管道是字节流，不保留写入的边界，三次写进去的内容在缓冲区里是连成一片的。 一次 read 完全可能把三段的拼接一起拿走，读的人没法从数据本身判断哪里是第一段的结尾。 想要边界，要么自己在协议里加长度前缀或分隔符，要么改用消息队列。

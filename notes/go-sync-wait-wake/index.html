Go channel、信号量与 Mutex：等待、唤醒和调度

从传数据、限制并发和保护共享数据三个场景出发，串起 channel 的等待队列、Mutex 使用的运行时信号量，以及 goroutine 从挂起到再次执行的全过程。

三个 goroutine 同时遇到了麻烦：一个在等 channel 里的数据，一个在等空闲名额，另一个在等 Mutex。它们都“等住了”，但等的条件不同，登记的位置也不同。

这篇要把这些问题连起来：谁负责登记等待者？谁改变条件并唤醒它？唤醒后又是谁安排它继续执行？先看使用场景，再沿着一份整体图和三个分步例子往下走。

文中的 G1、G2 等名字是为了说明过程而选的示意场景，不是承诺调度器一定按这个顺序运行。运行时内部实现以本机 Go 1.26.2 为例；语言和标准库保证的行为会单独说明，内部字段、队列和调度策略可能随版本变化。

01三个东西，各解决什么问题？

channel · 交接数据或通知

一个 goroutine 发送，另一个接收。没有可接收的数据时，接收操作可能需要等待。

ch := make(chan int)
value := <-ch

信号量 · 限制同时使用的人数

假设只有两个名额，第三个使用者要等有人归还名额。带缓冲的 channel 可以实现这种应用层限流。

slots := make(chan struct{}, 2)
slots <- struct{}{} // 占一个名额
<-slots             // 归还一个名额

Mutex · 保护共享数据

多个 goroutine 修改同一份数据时，用 sync.Mutex 让受保护的代码段互斥执行。

mu.Lock()
count++
mu.Unlock()

这三个东西有联系，但不是同义词：channel 本身可以传值；计数信号量描述“最多同时占用多少份资源”；Mutex 主要用于互斥访问。容量为 2 的信号量不等于互斥锁，因为它允许两个人同时进入，不能单靠它保护两个人共同修改的普通变量。

使用缓冲 channel 只是实现应用层信号量的一种选择。下面还会看到 golang.org/x/sync/semaphore，以及名字相近但作用不同的 runtime 内部信号量。

先认 G、M、P

名称 这里把它理解成什么
G 一个 goroutine，以及 runtime 为它保存的状态
M 执行 Go 代码的操作系统线程
P 执行 Go 代码所需的一组运行时资源和调度许可；不是一个 CPU 核心

**Go runtime（运行时）**是随 Go 程序一起工作的部分，负责 goroutine 调度、内存管理等事情。一个正在执行 Go 代码的 G，通常由持有 P 的 M 执行。G 因 channel 或 sync.Mutex 等待而挂起后，调度器可以安排其他可运行的 G；这不保证整个程序或操作系统线程永远不会因其他原因阻塞。

先认识图中的一张“登记单”：sudog 是 runtime 用来记录某个 G 正在参与等待的对象。它不是 goroutine 本身；一个 G 在 select 中可能同时有多张等待登记单。

03等待、可运行、运行：G 走过哪几种状态？

以下是一次典型的阻塞和恢复过程，不包含超时、取消、系统调用等所有分支：

① 运行 G 正在执行 调用 channel 接收、发送或 Mutex.Lock
G _Grunning 正在执行
M + P 运行当前 G 执行资源
条件不满足登记等待，再调用 gopark
② 等待 G 暂时不能继续 等待记录放在对应同步对象的等待结构里
G _Gwaiting 不在运行队列
等待记录 sudog → G 等待条件
别的操作改变条件取出等待者并调用 goready
③ 可运行 G 已经有资格继续 状态变为 runnable，等待调度器选择
G _Grunnable 还没执行
运行队列 runnext / P 的队列等 等 CPU
调度器选择 G某个 M 持有 P 执行它
④ 再次运行 G 恢复执行 从原来暂停的调用附近继续；是否取得锁要看具体机制
G _Grunning 已被调度
M + P 执行 G 的代码 继续

gopark 和 goready 是 runtime 内部接口，不需要在普通业务代码中直接调用。Go 1.26.2 中，gopark 经过 park_m 把当前 G 变成 waiting；goready 经过 ready 把它变成 runnable，再交给可运行队列。

图里的 runnext 是 P 上一个可以优先考虑的槽位；除此之外还有 P 的本地运行队列和全局运行队列。G 最终放在哪里、什么时候运行取决于当时状态，不是“放进 runnext 就一定立即运行”。

💡

唤醒 = 从等待变为可运行。 调度器什么时候选中它是下一步；对于普通模式的 Mutex，即使它随后运行，也未必已经获得锁。

04channel：接收方没数据，谁把它叫醒？

假设 ch := make(chan int)，是一个无缓冲 channel。G接收先执行 <-ch，G发送稍后发送 42。下面只描绘一个可能的顺序，省略其他 G 和 P。

接收 → 排队 → 发送 → 唤醒 → 继续 点下一步，对照 channel 等待队列与可运行队列

Go 1.26.2 的 chanrecv 在需要阻塞时把记录放入 recvq，然后调用 gopark(chanparkcommit, ...)。匹配的发送路径从 recvq 取出记录，完成数据交接，释放 channel 内部锁，再调用 goready。

反方向也类似：发送方不能完成时进入该 channel 的 sendq，匹配的接收方可以解除它的等待。close(ch) 也会唤醒等待者，但结果不同：等待的接收者按关闭规则返回，等待的发送者恢复后会 panic。

完整的缓冲区和发送分支可回看 channel 的组成与三条发送路径。

05Mutex：有人占着锁，等待者会去哪？

先看无争用：Lock 尝试用原子操作改变锁状态，成功就直接进入受保护的代码。这里的 **CAS（比较并交换）**可以理解为“只有当前值等于预期值，才把它原子地改成新值”。例如锁状态为 0 时，多个 G 同时尝试把它改成已加锁状态，只有一个能成功。

只有争用时才可能走到等待路径；Go 1.26.2 在合适条件下还可能先短暂自旋。自旋就是暂时占用 CPU、反复尝试获取锁，而不是立刻挂起；能否自旋以及持续多久由运行时当时的条件决定。

下面假设处于 Mutex 的普通模式。G1 在示例里先取得锁，G2 等待，后来 G3 也来竞争；这只是一种可能的执行顺序。

普通模式：被唤醒不等于已经拿到锁 点下一步，观察 Mutex、等待队列和可运行队列

Go 1.26.2 的 Mutex 还实现了饥饿模式：等待时间较长时，可能改变竞争方式并将锁交给等待者。源码中的约 1 毫秒阈值是实现细节，不是“最多等待 1 毫秒”的保证，也不是业务代码能依赖的公平性契约。

06Mutex 里的 runtime 信号量，和应用限流是什么关系？

sync.Mutex 在 Go 1.26.2 中包含一个内部实现，后者维护 state 和 sema 字段。state 记录锁及等待相关状态；sema 的地址用于运行时等待与唤醒。

  • runtime 的 semtable（全局散列表） 输入 &m1.sema，经地址映射找到一个桶；这张表不属于 m1
    • semaRoot：散列表中的一个桶 Go 1.26.2 中按地址查找；不同地址可能映射到同一个桶
      • 地址 &m1.sema 对应该地址的等待记录，例如 sudog → G2 / G3
      • 地址 &m2.sema 示意另一个地址碰巧落在同一桶；仍是不同的等待对象

具体实现使用按地址组织的树和等待记录链表；图里的 m1、m2 和“落在同一桶”是示意。等待者不直接排在 Mutex 对象内部；sema 的地址用来找到对应的 runtime 等待记录。

runtime/sema.go 的注释特别强调：这组内部函数主要为其他同步原语提供配对的睡眠与唤醒，即使唤醒和睡眠发生竞争也要避免遗漏。它不是业务代码直接调用的公共计数信号量 API。

如果“唤醒”比“准备睡觉”更早到呢？

以某个 runtime 信号量的一个等待者为例，假设同一桶里没有其他等待者，简化成两种先后顺序：

顺序释放先到等待登记先到
第一次检查等待者发现计数暂时不可用，准备登记等待者发现计数暂时不可用，准备登记
发生竞争释放方先增加计数；此时没有已登记等待者等待者在 root 锁下登记、再次检查，随后入队并挂起
如何继续等待者在 root 锁下再次检查，发现并消费已增加的计数，不再入睡释放方看到有等待者，按地址取出它并唤醒

Go 1.26.2 的 semacquire1 会在持有 semaRoot 的锁时先登记 nwait、再检查一次计数；semrelease1 先增加计数，再判断和查找等待者。这样上面两种竞态都不会因为“通知太早”而无期限睡下去。真实实现还处理其他竞争、队列顺序和交接细节。

07应用层计数信号量：用 channel 限制两个名额

下面约定：向 slots 发送一个空值表示占用名额；从中接收一个空值表示归还。这个方向是本例的约定，也可以设计成相反方向。

var slots = make(chan struct{}, 2)

func work() {
    slots <- struct{}{}         // 取得一个名额；满时等待
    defer func() { <-slots }() // work 返回时归还

    // 使用受限资源
}

图中的两个圆点是逻辑上的两个占用名额。struct{} 是零大小类型，不能据此推断 channel 一定分配了两个存数据的物理字节。

容量为 2：第三个工作者怎样等到名额？ 从占满名额走到等待者恢复执行

另一种实现：x/sync/semaphore.Weighted

golang.org/x/sync/semaphore 是单独的模块，不是 Go 标准库。它提供可以一次申请多个名额、并能用 context 取消等待的 Weighted。以 v0.18.0 源码为例，它把几种东西组合在一起：

  • semaphore.Weighted 一个应用层计数信号量实现，不是 runtime/sema.go 里的内部设施
    • size / cur 总名额与当前已占用的权重
    • mu · sync.Mutex 保护计数和等待者列表的并发修改
    • waiters · 等待者列表 下面展开其中一个等待者；列表可以有多个
      • 一个 waiter
        • n 此等待者申请的名额数
        • ready · channel 条件满足后关闭，用于通知对应等待者

在这个版本中，Acquire 不能立即取得名额时，会登记等待者，再通过 select 等待其 ready 或传入的 context.Done()；后者是外部取消信号，不是 waiter 的字段。Release 更新占用数并通知可满足的等待者。这是这个库的一种实现，不是说所有信号量都必须由 Mutex 和 channel 实现。

08两把容易混淆的锁，以及内存可见性

channel 内部也有一个叫 lock 的字段，但它的类型是 runtime 内部的 mutex，不是业务代码中的 sync.Mutex。它负责短暂保护 hchan 及相关等待记录；channel 操作因为“没数据 / 没空间”而等待，则是上面看到的登记 sudog 和 gopark 路径。

对比sync.Mutexruntime 内部 mutex
主要使用者应用代码和标准库Go runtime 内部
保护什么调用者约定的共享数据runtime 的内部共享结构，例如 hchan
竞争等待可能自旋，再通过 runtime 信号量挂起 G内部锁竞争时可能直接阻塞 M
可否直接当业务 API可以，属于标准库不可以，属于内部实现

所以，不能简单地说“所有锁都只会挂起 G，也绝不会影响线程”。对于本篇的 channel 收发等待和 sync.Mutex 慢路径，G 可以通过调度器挂起；但 runtime 内部锁、系统调用等情况的线程行为不同。

同步还涉及数据可见性，不只是“谁先执行”：

  • channel 的一次发送，按 Go 内存模型发生在对应接收完成之前。
  • 对同一把 sync.Mutex，前面的 Unlock 与后续的 Lock 建立文档规定的同步关系。
  • 信号量容量大于 1 时，多个人可以同时进入；对其中共享变量的并发读写，仍要有合适的同步。

10遇到问题时，先问哪一层？

现象或疑问先检查什么不要直接推断什么
channel 发送或接收一直不返回是否有匹配方、缓冲区是否满或空、channel 是否为 nil、退出和取消路径所有 goroutine 都在占用 CPU
Mutex 等待很久持锁代码是否做了慢操作，是否存在高竞争；结合 mutex / block profile 和 trace每个等待者醒来都会按 FIFO 取得锁
信号量限流卡住成功取得的名额是否都能归还，取消时是否会退出等待channel 缓冲区只要非空就一定有 goroutine 在执行
已经收到唤醒G 是否只是 runnable，是否仍在等待被调度或重新竞争锁唤醒等于立刻运行、等于 Mutex 已经拿到手

排查时可以结合 goroutine 栈、block profile、mutex profile 和 go tool trace；这些工具观察的是具体运行情况，采集方式和开销各不相同。不要只根据一次快照判断所有 goroutine 的完整生命周期。

把三条线收回来

channel 负责交接数据；应用层信号量负责表达可用名额；sync.Mutex 负责互斥。它们的等待条件和登记位置不同：channel 等待者属于 channel，Mutex 慢路径等待者通过 runtime 信号量按地址登记。

共同的后半段是：解除等待 → G 变为 runnable → 调度器选择 → G 继续执行。

自测

channel 的 recvq、Mutex 的 runtime 信号量等待结构和 P 的运行队列是同一条队列吗？

不是。前两者记录还在等条件的 G；P 的运行队列用于保存可运行的 G。条件满足并唤醒后，G 才会进入调度器的可运行状态。

被 Mutex 唤醒的 G 是不是一定马上运行，并且已经拿到锁？

不是。唤醒首先让 G 变成 runnable；之后才由调度器选择。在 Go 1.26.2 的普通模式下，恢复后仍可能与后来者竞争。饥饿模式有不同的交接策略。

容量为 2 的 channel 已满，第三个发送者正在等待。有人接收后，为什么占用数可能仍是 2？

在 Go 1.26.2 的满缓冲接收路径中，runtime 可以把队头元素交给接收方，同时把等待发送者的元素补到槽位，再唤醒发送者。接收方已完成交接，但被唤醒的 G 还要等待调度，发送调用才会返回。

为什么 runtime 信号量的唤醒即使先于等待登记，也不会简单地丢失？

释放方先增加计数；等待方登记后在 root 锁下再次检查计数。如果释放先发生，等待方可以消费已有计数而不入睡；如果等待登记先完成，释放方可以找到并唤醒等待者。

channel 或 sync.Mutex 让一个 G 等待，是不是说明所有情况下操作系统线程都不会阻塞？

不是。它们的典型 goroutine 等待路径可以通过 gopark 让 G 挂起，M 和 P 可调度其他 G；但 runtime 内部锁、系统调用等其他情况可能阻塞线程。

MySQL 一条 SQL 的执行流程（图解）

线上告警：一条 select * from user where id=1 平时 5ms，某天突然 3 秒。慢查询日志里，同一句 SQL 有时走索引、有时全表扫描。要解释这个，得知道这条 SQL 从客户端发出之后，在 MySQL 内部究竟经过谁的手。

本页跟着这条 select 走完全程，再看 update 多出来的剧情。主干是一张带入口和导览的整体图（02 节），后面每一章是图上一个站点的放大。

01先搞清几个词

后面反复出现的东西先摆在这里，每个都能用一句话说出来。

Server 层

管连接、解析 SQL、优化、内置函数。处理的是「语义与决策」，不碰数据页

存储引擎层

管数据怎么存怎么取。InnoDB 是 5.5 起的默认引擎，以插件形式可替换

handler 接口

两层之间的契约。执行器只会喊「给我下一行」，引擎懂存储不懂 SQL

解析树

分析器的产物，SQL 字符串按文法组装成的树

执行计划

优化器的产物。用哪个索引、join 谁驱动，EXPLAIN 看到的就是它

WAL

Write-Ahead Logging，先顺序写日志再慢慢刷数据页，随机写变顺序写

脏页

Buffer Pool 里改过、还没刷回磁盘的数据页，每页 16KB

两阶段提交

redo 先 prepare，binlog 写完再 commit，让两份日志同生共死

02整体图：一条 SQL 穿过哪些关卡

一张图装下全部主线：实线是 select 的读路径；虚线里 ①→⑤ 标出 update 的时序——先改页、再记 redo、写 binlog、redo 才 commit、从库重放；另一条虚线是查询缓存的命中短路。Server 层五道关卡各管一段，跨过 handler 接口才碰到数据和存储。

这条结构和 HTTP 请求的处理链同构。你脑子里已经有那条链，把新名字套到旧位置上就行。

位置HTTP 请求链MySQL 链

唯一的差别：HTTP 链的每一层都是你自己写的代码，MySQL 这条链是数据库替你搭好的，一层都改不了，只能理解它。

再看那条 Server 层与引擎层的边界线。前四站流通的「货币」是同一样东西：SQL 文本及其衍生结构（解析树、执行计划），直到执行器才第一次碰到行数据。线上是语义与决策，线下是数据与存储。MySQL 为什么能换引擎、日志为什么分两层（binlog 在上、redo 在下），都从这条线来。

03连接器：进门与权限快照

客户端
连接器
权限表mysql 系统库
1TCP 三次握手
2用户名 + 密码
3读出全部权限
4全局权限和密码固化进连接
5认证通过，分配线程

8.0 起默认认证插件是 caching_sha2_password（SHA-256，需要 SSL 或 RSA 密钥交换）。权限按全局、库级、表 / 列级三档存在 mysql 系统库的几张权限表里（user、db、tables_priv / columns_priv），建连时读出来。读出来放在哪，三档不一样，改权限什么时候生效就跟着不一样：

管理员改了什么这份权限放在哪已建立的连接什么时候受影响
全局权限和密码复制一份进连接，连接自己留着用不受影响，重连才生效
库级权限不预先复制；切库（USE）时把「当前库」的库级权限记进连接下一次 USE db_name 生效
表 / 列级权限（REVOKE 一张表的 SELECT）不进连接；每次请求对着服务端内存里的权限缓存现查下一次请求就生效

为什么表 / 列级不用等重连？因为「快照绑定到连接」这个模型只对全局权限和密码成立。全局权限在连接里留了自己的副本，判断时只看副本，管理员改了权限表、副本不会跟着变，重连才重新读。表 / 列级从来没有进过连接：每次请求的权限判断都对着服务端全局的权限缓存，而 REVOKE 执行的那一刻服务端就把这份缓存重建了（手册原话：loads the grant tables into memory again immediately）——下一次请求查到的已经是新缓存。无论哪一档，判断都是内存比对，不再查权限表；差别只在查的是连接自己那份，还是服务端全局那份。

USE db_name 就是切换当前数据库的那条命令（客户端里敲的 use xxx）。库级权限夹在中间：连接里记着「当前库」的库级权限（源码里的成员叫 m_db_access，注释是 Privileges for current db），切库的那一刻重新记一份——所以 REVOKE 之后，要等下一次 USE 才刷新。

「改了权限要重连才生效」只对全局权限和密码成立。 判断口诀：看这份权限连接里有没有自己的副本——有（全局、密码）就等重连；没有（表 / 列级）下一次请求就生效；库级记的是「当前库」那份，等下一次 USE。线上回收权限先分清档位；要立即断掉全局权限的用户，光改权限表不够，得把活跃连接 KILL 掉。

连接分长短两种，取舍在开销和内存之间。

短连接长连接
建连开销每条请求都付：TCP + 认证 + 线程分配只付一次
内存风险低，断开即释放临时内存挂在连接上，越积越多
适用低频访问高频常驻（连接池）

长连接的坑很具体：执行过程中的临时内存，排序缓冲、临时表、结果集，都挂在连接对象上。一次用了 64MB 排序缓冲的查询结束后，这 64MB 不还给操作系统，等连接断开才一次性结清。长连接跑得越久涨得越多，MySQL 内存只涨不跌，直到被系统 OOM kill。「MySQL 内存越用越高」一半的答案在这里。

两个解法：定期主动断开；5.7+ 用 mysql_reset_connection 重置连接，不重建连接但释放临时内存。 连接池配置里的 maxLifetime 就是「定期断开」的自动化。另有 max_connections 管连接数上限（打满拒绝新连接）、wait_timeout 管空闲超时（默认 28800 秒 = 8 小时）。

04查询缓存：一个被删掉的功能

SQL 进来
查询缓存 key = SQL 全文逐字节
直接返回结果集 返回前单独查一次权限
走完整链路 分析器 → 优化器 → 执行器 → 引擎

它在分析器之前，是整条链的第一道拦截。key 是 SQL 语句文本，逐字节严格匹配；value 是上次执行的完整结果集。「逐字节」苛刻到什么程度：

客户端发来的 SQL和缓存里的 key 比
SELECT * FROM user WHERE id=1一模一样，命中
select * from user where id=1大小写不同，miss
SELECT * FROM user WHERE id=1多一个空格，miss
SELECT * FROM user WHERE id=2换个参数值，miss

为什么用整条文本做 key？查询缓存要的就是快，连分析器都不想经过，自然拿不到解析结果，只能用最原始、最便宜的东西当 key：字符串本身。代价是连「语义相同」都识别不了。

命中也不是无脑返回：缓存里存的是「别人的结果集」，返回前要校验当前用户有权读这些表。命中路径跳过了分析器、没解析出表名列名，所以这次校验只能放在返回前单独做（§06 的 precheck 是它的正规版本）。

死因是三条叠加的：

  • 失效粒度太粗：表上任意一次更新，这张表的全部缓存条目同时清空
  • key 匹配太苛：逐字节比对，连语义相同都识别不了
  • 维护成本照付：每次查询要算 hash、加锁访问缓存结构

写多读少的场景，缓存刚建好就被下一个 update 冲掉，命中率趋近零，hash 和加锁的成本却一笔不少付。清空本身也要加锁，高并发写时它从加速器退化成全局热点。缓存的通用教训：成败不在命中率，在失效粒度；粒度控不住，缓存就是负债。

05分析器与优化器：从字符串到执行计划

select * from user where id=1 一段字符串
词法分析 SELECT · * · FROM · user · WHERE · id · = · 1
语法分析 按 SQL 文法组装解析树
ERROR 1064 You have an error in your SQL syntax
预处理 表 / 列是否存在 · 展开 select *
优化器 选索引 · 定 join 顺序 · 代价估算
执行计划 EXPLAIN 看到的就是它

这套流水线就是编译器前端：词法负责贴标签（这段文本是关键字还是标识符），语法负责排座位。拆两步的理由也和编译器一样：每个阶段只认一种规则，出错才能报准阶段和位置。排障的基本功是分清「解析期错误」（1064，SQL 根本没跑）和「执行期错误」（表不存在、权限不足，跑起来了但被拦）。

优化器回答「怎么执行最快」。SQL 是声明式语言，只声明「要什么」，「怎么做」全由它定。一个 join 的例子：

计划执行方式代价
计划 1 · 大表驱动全表扫 A（100 万行），逐行去 B 找匹配100 万次随机访问 · 毫秒变分钟
计划 2 · 小表驱动全表扫 B（1000 行），用索引逐行查 A1000 次索引查询 · 低几个数量级

A 表 100 万行、B 表 1000 行，谁做驱动表，代价差几个数量级。毫秒和分钟，只差一个「谁驱动谁」的决定。

「优化器选最优」是「按它的估算选最优」。 代价模型的输入是统计信息：总行数、索引基数（一列有多少个不同值）、数据分布，由后台采样更新。表数据大变之后、统计更新之前存在一个失准窗口，它选出的「最优」计划可能比全表扫还慢。EXPLAIN 的 type、rows、key 是排障第一眼：先看它选了哪个索引、预估扫多少行，再和实际数据量对照。

06执行器：真正干活的人

where 过滤：符合 → 进结果集

这就是迭代器协议：执行器是不停调 next() 的消费者，引擎是惰性产出行的 iterator，像 generator 的 yield，要一行才产一行。逐行拉取的理由很实际：结果集可能上百万行，一次全取直接撑爆内存；流式处理，内存里只装当前行加结果集。

循环圈数就是这条 SQL 的代价。走不走索引、索引区分度高不高、要不要回表，全折算成圈数。优化器在 05 节费尽心思选的「最便宜的路」，便宜在让这个循环转得最少。贵的操作（取数）放引擎用索引控制次数，便宜的操作（where 过滤）放 Server 层纯内存随便做。

权限在这里有第二道闸：

连接时 粗粒度：这个用户能不能连
分析器 解析出表名、列名
执行器 precheck 细粒度：这张表这些列能不能读
开工取数

为什么查两次？粒度不同：连接时查不到「这张表的这些列」，必须等分析器解析出表名列名。precheck 卡在优化器开工之前：名字已解析完、计划还没定，是拦下无权查询最便宜的时刻。

07更新语句：两份日志与两阶段提交

select 走完执行器就返回了；update 在执行器修改数据之后，还要写日志。两份日志分工不同：

redo log · InnoDBbinlog · Server 层
记录内容物理：哪个数据页做了什么修改逻辑：哪条语句 / 哪行怎么变
写入方式循环写，写满回头覆盖追加写，完整留档
属于谁InnoDB 特有，别的引擎没有所有引擎共用
用途crash-safe 崩溃恢复主从复制、数据恢复

为什么不直接刷盘、要先写 redo？看两种写法的差别：

直接刷脏页WAL（先写 redo）
写什么每次更新写回整个 16KB 页只追加一条小记录
IO 形态随机写，磁头来回寻道顺序写，只动磁头一次
时机同步，更新就得等盘异步，后台择机刷脏页
崩溃时丢掉没刷盘的修改重放 redo 找回已提交的修改

顺序写和随机写的差距是磁盘物理特性决定的。 redo 的形态差异也来自用途：循环写是因为只管崩溃恢复，最近一段就够，能覆盖的前提是被覆盖位置的脏页已刷盘（checkpoint）；binlog 追加写是因为从库要回放完整历史流水，覆盖掉就断了。落盘时机各有旋钮：innodb_flush_log_at_trx_commit=1 是每次提交都刷（最安全最慢），binlog 对应 sync_binlog。binlog 另有 statement / row / mixed 三种记录格式，主从复制里各有各的坑，是往外挖的钩子。

update 的提交时序：

执行器协调者
InnoDBredo log
Server 层binlog
崩溃点 A改内存页（脏页）+ 写 redo，标记 prepare
崩溃点 B写 binlog（完整事件 + XID 收尾）
崩溃点 Credo 标记 commit
完成，返回客户端「成功」

两份日志分属两层、独立写入，两次写入之间崩溃怎么办？先看两个朴素方案的死穴：

  • 方案一「先写 redo 直接提交」：redo 写完崩溃，binlog 没写 → 主库恢复出新值，从库没有 → 主从分裂
  • 方案二「先写 binlog」：binlog 写完崩溃，redo 没写 → 从库执行了，主库没有 → 凭空多数据

两个方案各有一个崩溃窗口，窗口里的后果都不可接受。所以要两阶段提交：把 redo 的提交拆成 prepare 和 commit，中间夹着 binlog 的写入。下面亲手在每个崩溃点断一次电：

在三个崩溃点分别断电，看恢复规则怎么兜底 点一个崩溃点（或不崩，走完）

断电那一刻 两份日志的状态
重启后 恢复规则怎么判

模拟器里的判定就是这条恢复规则：

重启，扫描 redo log
状态是 commit?
直接生效
拿 XID 查 binlog：完整? 完整事件 + XID 事件收尾
提交该事务
回滚该事务

三个崩溃点对号入座：A（redo prepare、binlog 无）→ 回滚，主从都没有；B（binlog 完整、redo 停在 prepare）→ 提交，主从都有；C（redo 已 commit）→ 直接生效，主从都有。三种结局都是两边一致。XID 是贯穿两份日志的事务身份证，恢复时靠它把两份日志里的同一个事务对上号；「binlog 完整」的判断标准是完整的事件序列、并以 XID 事件收尾，半截的 binlog 不算。

⚖

夹心顺序为什么是「redo prepare → binlog → redo commit」，不是反过来？ prepare / commit 是 InnoDB 自己的状态位，想标就标；binlog 是 Server 层的日志， 没有中间态，写了就是写了。有状态位的一方承担两阶段，另一方只在夹心处一次性写完整。

为什么不用一份日志？redo 要页级物理重放，只有 InnoDB 懂；binlog 要跨引擎、跨版本传递逻辑操作，只有 Server 层能做。用途不同决定粒度不同，粒度不同决定两套不能合并。这套机制在 MySQL 内部叫 internal XA，官方文档确认它保证了 binlog 与 InnoDB 数据文件的同步。

08回到开头那句时快时慢的 SQL

现在你有了完整的定位图。同一句 SQL 时快时慢，变量从来不在 SQL 文本本身，在这几站：

连接器

优化器

选错计划

执行器

圈数暴涨

索引退化、区分度崩了、回表变多，循环圈数就是代价

下次别对着 SQL 文本干瞪眼，按站排除。

一条 SQL 的旅程，前半段所有语句共享，后半段只有写语句续费：读是一次「取」，写是一次「取」加一次「记」，记的这笔账要经得起断电。想再往下挖：数据页在 InnoDB 里怎么组织成 B+ 树，见 innodb-index-visual；再远一点是 MVCC 与 undo log、Buffer Pool 刷脏时机、redo 的 group commit、binlog 三种格式的复制陷阱。

查询缓存为什么被 8.0 删掉？说出至少两条死因。

三条：失效粒度太粗（表上任意一次更新清空这张表的全部缓存）；key 逐字节匹配太苛 （大小写、空格、参数一变就 miss，连语义相同都识别不了）；维护成本照付（每次查询算 hash、加锁）。 写多读少场景命中率趋近零，纯负优化。另外它删掉的是「结果集」缓存， InnoDB 的 Buffer Pool（数据页缓存）不受影响。

两阶段提交的崩溃点 B（binlog 已写完、redo 停在 prepare）断电，重启后主库和从库各是什么状态？

恢复规则：redo 停在 prepare，就拿事务的 XID 去查 binlog。binlog 有完整事件、 以 XID 事件收尾 → 提交该事务。主库追上新值，从库重放这条 binlog 也有新值， 两边都有、一致。

管理员 REVOKE 了某用户对一张表的 SELECT，这条用户已建立的连接什么时候开始被拒？

下一次请求就生效。表 / 列级权限不进连接，每次请求对着服务端内存里的权限缓存现查， REVOKE 执行的那一刻这份缓存就被重建了。「要重连才生效」只适用于连接里留了副本的 全局权限和密码；库级权限介于中间——连接里记的是「当前库」那份，等下一次 USE 刷新。 想立即断掉某人的全局权限，光改权限表不够，得把活跃连接 KILL 掉。

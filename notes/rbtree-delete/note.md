## 01 · 先分清要删的是谁

删除的入口比插入麻烦一点，因为要删的键可能坐在一个有两个孩子的节点上。按孩子的个数分三种：

```compare
first: 要删的节点有
head: [怎么摘, 摘完之后]
rows:
  - 0 个孩子: ["直接摘掉，让空位顶上来", "那个位置欠一个黑（如果删的是黑节点）"]
  - 1 个孩子: ["摘掉它，让唯一的孩子顶上来", "同样是那个位置欠一个黑"]
  - 2 个孩子: ["用右子树里最小的键（后继）顶替它，再删掉后继原来的位置", "被删掉的键是原来那个，但「欠黑」的位置在后继原来待的地方"]
```

后继一定没有左孩子（它已经是右子树里最小的了），所以把它搬走永远是最省事的那一种 —— 这也是为什么选后继，不是随便挑一个键来顶替。

```demo
widget: rbtree-lab
actions: false
title: 删一个有两个孩子的键：先找后继
config:
  mode: delete
  keys: [40, 30, 20, 10]
```

点预设「两个孩子的删除：先找后继」，删掉 30 —— 它的两个孩子是 20 和 40，不能直接摘。逐步翻：找后继、让后继落到被删键的位置、接着处理欠黑。

==注意「欠一个黑」的位置一直不在被删的那个键上，而在后继原来待的地方。==

## 02 · 双黑：一笔账，不是一个颜色

摘完之后看摘掉的是什么颜色：

| 摘掉的颜色 | 黑高 | 要做什么 |
|---|---|---|
| 红 | 每条路径的黑节点数没变 | 什么都不用做，结束了 |
| 黑 | 这一侧的路径少了一个黑 | 把那个「欠着的黑」记在这个位置上 —— 这就是双黑 |

双黑不是一个真的颜色，是一笔账：**这个位置（可能是个真实的节点，也可能是空位）背了两个黑**。一个位置背着两个黑，就等于它所在的那条路径比别人少了一个黑 —— 性质 ⑤ 不成立了。

```journey
- tag: ① 摘掉
  tone: amber
  name: 那个位置
  badge: 欠一个黑
  badgeTone: red
  fields:
    - { k: 是什么, v: "一个真实的节点，或者一个空位" }
    - { k: 账, v: "背了两个黑", note: 比兄弟多一个, tone: warn }
  note: 修复的目标只有一个：把这笔账消掉 —— 或者真的借到一个黑，或者把问题上推、直到某个红节点接手。
- tag: ② 兄弟有富余
  tone: green
  name: 借一个键过来
  badge: 借位
  badgeTone: green
  fields:
    - { k: 条件, v: "兄弟是 3-节点或 4-节点", note: 有 2~3 个键 }
    - { k: 动作, v: "父节点周转一次", note: 见情形 4, tone: ok }
  note: 借到一个黑，双黑当场消掉。
- tag: ③ 兄弟也穷
  tone: red
  name: 合并
  badge: 合并上推
  badgeTone: red
  fields:
    - { k: 条件, v: "兄弟是 2-节点", note: 只有 1 个键 }
    - { k: 动作, v: "兄弟变红，欠黑上移一层", note: 见情形 2, tone: warn }
  note: 问题沿着树往上走，最多到根。
```

修复的循环做的事就是：**看兄弟手里有没有富余**。有就借一个黑过来；没有就把问题上推一层。

## 03 · 情形 1：兄弟是红的

```
兄弟 w 是红的 → w 变黑、父节点变红，绕父节点转一次，然后重新看新兄弟
```

兄弟是红的，说明它和父节点住在同一个 2-3-4 节点里 —— 这种情况下它没法做「兄弟」该做的事（借不到键）。先转一次把它们拆开：兄弟变成独立节点，原来的父节点降下去。

==这一步不解决问题，只是把问题变成后面三种之一。==

```demo
widget: rbtree-lab
actions: false
title: 情形 1：先把兄弟拆出来
config:
  mode: delete
  keys: [20, 50, 10, 60, 30, 40]
```

点预设「情形 1 · 兄弟是红的」，删掉 10：兄弟 50 是红的，转一次之后问题变成情形 4（远侄 40 是红的）并当场解决。

## 04 · 情形 2：兄弟也穷 —— 合并，把问题上推

```
兄弟 w 是黑的、它的两个孩子都黑 → w 变红，把双黑移到父节点上，继续循环
```

兄弟是个只有 1 个键的 2-节点，一个键都借不出来。那就合并：把父节点的一个键降下来和兄弟凑成一个节点（兄弟变红就是这件事在二叉写法里的样子）。代价是父节点自己少了一个键 —— 欠一个黑的位置跟着上移一层。

```demo
widget: rbtree-lab
actions: false
title: 情形 2：借不到，合并上推
config:
  mode: delete
  keys: [20, 40, 10, 60, 30, 80, 50, 70]
```

点预设「情形 2 · 借不到，合并上推」，删 30：兄弟 10 也是黑的、两个孩子也黑，只能合并。

这一步做完，全局仍然合法（三条性质都满足），只是「欠黑」被推到了上一层。如果上一层也只剩一个键，循环会再做一次情形 2。一路推到根时，双黑挂在根上，**整棵树的黑高减一**就够了。

## 05 · 情形 3 和 4：兄弟有红孩子 —— 借一个键过来

兄弟有两个键（3-节点）或者三个键（4-节点）时就有富余，可以借。但借位只能从**远端**那个键走，所以要分两步看：

```compare
first: 兄弟的孩子
head: [动作, 做完之后]
rows:
  - "近侄红、远侄黑": ["绕兄弟转一次，把近侄换到远端去", "变成情形 4，接着借"]
  - "远侄红": ["兄弟的颜色换成父节点的颜色、父节点变黑、远侄变黑，然后绕父节点转一次", "借位完成，双黑当场消掉，循环结束"]
```

翻译成 2-3-4 树：兄弟升上去当父节点，父节点降下来和兄弟原来的位置合并，远侄补上兄弟的位置 —— 这就是「从兄弟那里借一个键」的标准动作，父节点那个键只是中间周转了一下。

```demo
widget: rbtree-lab
actions: false
title: 情形 3 + 4：近侄红要先换位
config:
  mode: delete
  keys: [10, 40, 30, 20]
```

```demo
widget: rbtree-lab
actions: false
title: 情形 4：远侄是红的，直接借
config:
  mode: delete
  keys: [20, 30, 10, 40]
```

两个演示放在一起看能看出区别：删 40 那一次，红的侄子 20 在近端，所以先转一次（情形 3）才借（情形 4）；删 10 那一次，红的侄子 40 本来就在远端，一步就成。

## 07 · 回看 2-3-4：真正改变结构的只有两个动作

把四种情形按「真实动作」归类，删除就清楚了：

| 情形 | 真实动作 | 在 2-3-4 树里 |
|---|---|---|
| 情形 2 | 合并 | 兄弟也只有 1 个键 → 父节点降下来和两兄弟并成一个节点，问题上移 |
| 情形 4 | 借位 | 兄弟有富余键 → 父节点周转，借一个过来 |
| 情形 1 | 形状整理 | 兄弟和父还在同一个节点里，先拆开才能谈借 |
| 情形 3 | 形状整理 | 兄弟有富余键，但红的在近端 —— 先换到远端 |

==只有情形 2 和情形 4 在真正改变 2-3-4 树；情形 1 和 3 只是二叉写法带来的形状问题。==这也解释了为什么删除比插入难记：四种情形里两种是「编码的副作用」，不落到 2-3-4 的动作上，单独背就要背四套。

数量上也和插入对称：情形 1 一次旋转、情形 3 一次旋转、情形 4 一次旋转（之后结束），中间不旋转的情形 2 负责把问题上推 —— 所以**一次删除最多 3 次旋转**（CLRS 13.4 节）。比插入多一次，因为删除要先花一两次把形状摆对。

## 08 · 为什么删除比插入难

三个原因，说清了就不会觉得它「玄」：

| 原因 | 具体是什么 |
|---|---|
| 入口多一个岔 | 插入永远挂在叶子；删除要先判断「0 / 1 / 2 个孩子」，有两个孩子时还要先找后继 |
| 负债要记在一个看不见的位置 | 插入的问题是一个真实存在的红节点；删除的问题可能落在一个**空位**上（双黑），得靠哨兵节点记着它是谁的哪一侧 |
| 借位要看「远端」 | 插入看叔叔颜色就够了；删除要看兄弟的两个孩子，而且只有远端的那个红键才能直接借 |

第三条最容易被忽略。**「远侄」就是兄弟离双黑更远的那个孩子** —— 借位必须从远端走，因为转动之后它会正好补上兄弟原来的位置；近端的红键先得换到远端去（这就是情形 3 存在的理由）。

```callout
tone: violet
icon: 🧭
quote: true
text: |
  ==记住一句话就够了：兄弟有富余就借，没有就合并，其余都是形状问题。==
  插入和删除在这里是对称的 —— 插入是「多了就分裂」，删除是「少了就借或合并」。
```

```quiz
- q: 双黑是什么？它为什么可能落在「空位」上？
  a: |
    双黑不是颜色，是一笔账：这个位置背了两个黑，也就是它所在的路径比兄弟少了一个黑。
    删掉一个黑节点、又没有红孩子接手时，欠下的黑就记在那个位置上 ——
    如果被删的位置本来就是叶子（没有孩子），那笔账自然记在一个空位上。
    修复就是把账消掉：要么借到一个黑，要么把问题上推，要么让一个红节点接手（染黑即消）。

- q: 四种情形里，哪两种不改变 2-3-4 树？
  a: |
    情形 1（兄弟红）和情形 3（近侄红）。它们只是把二叉树摆成能借位的形状 ——
    2-3-4 树里对应的是「先把这个节点的几个键重新排一下」。
    真正改变 2-3-4 树的是情形 2（合并，少一个节点）和情形 4（借位，把一个键从兄弟挪过来）。

- q: 删除有两个孩子的节点时，为什么「欠黑」的位置不在被删的那个键上？
  a: |
    因为有两个孩子的键不能被直接摘掉（会断成两半），得先让后继顶替它的位置。
    真正被从树上摘走的是**后继原来待的那个位置** —— 那里才是缺了一个节点的地方。
    被删键的位置只是换了个键坐上去，一个黑都没少。

- q: 为什么一次删除最多三次旋转，而插入最多两次？
  a: |
    插入的情形 1 只变色不旋转，最多是情形 2 + 情形 3 各转一次。
    删除多了一次：如果兄弟是红的（情形 1）或红的侄子在近端（情形 3），
    都要先转一次把形状摆对，再转一次完成借位 —— 摆形状加借位，最多三次。
```

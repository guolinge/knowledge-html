## 01 · 一句「一切皆文件」底下有什么

文件系统是操作系统里负责**持久化数据**的那部分。它管的事情很具体：把用户的东西存到磁盘上，让断电之后它们还在。

基本单位是**文件**。文件怎么组织、怎么命名、怎么摆到磁盘上，不同的组织方式就是不同的文件系统（Ext4、XFS、NTFS……）。

Linux 有一句名言：

> **一切皆文件。**

这不只是修辞。普通文件、目录、块设备、管道、socket，在 Linux 里都归文件系统统一管，都通过同一套 `open` / `read` / `write` / `close` 来操作。`/dev/sda` 是一块硬盘，但你 `dd if=/dev/sda of=x` 的时候，用的就是读文件的方式。

好处很实在：==多出来的设备类型不用再各造一套 API。== 学一次 `read`，什么都能读。

那这样一套东西，底下的基本零件是什么？

## 02 · 三样东西拼出一个文件

一个文件在操作系统眼里，是由三部分组成的：

```arch
svg: fs-inode-dentry
caption: 名字在内存里，元信息和内容在磁盘上。两个目录项可以指向同一个 inode，这就是硬链接。
```

### 索引节点（inode）

inode 记的是**文件的元信息**：

```spec
title: inode
subtitle: 文件本体在操作系统里的档案
tone: violet
rows:
  - k: 我是谁
    v: |
      **inode 编号**。每个文件一个，在同一个文件系统里唯一。

      你在终端敲 `ls -i` 看到的第一列就是这个数。
  - k: 我长什么样
    v: |
      文件大小、访问权限（rwx）、创建时间、修改时间、最后访问时间……

      `ls -l` 显示出来的那堆东西，几乎全部来自 inode。
  - k: 我的内容在哪
    v: |
      **数据块的位置**。这是 inode 最重要的一项 ——
      文件真正的内容不在 inode 里，inode 只记「去哪儿找」。

      第 ③ 篇整篇都在讲这一项怎么记。
```

==inode 是文件的唯一标识，而且它存在磁盘上。== 也就是说 inode 自己也要占空间，也要被管理。一个文件系统能存多少个文件，取决于它能分出多少个 inode —— 这是格式化的时候就定下来的。

### 目录项（dentry）

目录项记的是**文件的名字**，以及它指向哪个 inode。

它和 inode 有一个根本区别：

```compare
first: 对比项
head: [索引节点 inode, 目录项 dentry]
rows:
  - 记什么: ["文件的元信息 + 数据块位置", "文件的名字 + 指向哪个 inode"]
  - 存在哪: [{ text: "磁盘上，持久保存", tone: blue }, { text: "内存里，内核维护的一个缓存", tone: amber }]
  - 占磁盘空间吗: ["占，inode 区是磁盘上单独的一块区域", "不占，它只活在内存"]
  - 一一对应吗: ["一个 inode 对应一个文件", { text: "多个目录项可以指向同一个 inode", tone: violet }]
```

最后一行就是硬链接的全部原理：**给同一个文件多起几个名字，只需要多写几条目录项。**

### 目录项不是目录

这两个词长得像，但完全是两回事，很容易看错：

```cards
cols: 2
items:
  - title: 目录
    desc: 一种文件，持久存在磁盘上
    tag: 磁盘
    tone: blue
    body: |
      它有自己的 inode，inode 指向自己的数据块，数据块里装的是
      「名字 → inode 号」的对照表。

      因为它是个文件，所以你能 `vim` 打开它，也能给它设权限。
  - title: 目录项
    desc: 内核的一个内存结构，缓存解析结果
    tag: 内存
    tone: amber
    body: |
      路径解析很贵：`/a/b/c/d` 要读四次目录。所以内核把已经解析过的
      「这个名字对应哪个 inode」记在内存里，下次直接用。

      ==它不是磁盘上的东西，重启就没了。==
```

目录项记录的不一定是目录，也可以是一个普通文件。它的作用就是「记住一个名字解析到了哪儿」。

## 03 · 一次读写的最小单位：扇区与块

磁盘读写的最小单位是**扇区**，传统上只有 `512` 字节。

但文件系统不按扇区干活。原因很直接：

```compare
first: 单位
head: [大小, 如果按它读写会发生什么]
rows:
  - 扇区: ["512 字节", { text: "每读 1KB 要发 2 次请求，还要等两次寻道和旋转，效率极低", tone: red }]
  - 逻辑块: ["4KB（Linux 默认）", { text: "一次请求读写 8 个扇区，磁盘的机械动作被摊薄了", tone: green }]
```

Linux 会把多个扇区组成一个**逻辑块**（也叫数据块），文件系统内部一律按块来算：

```flow
grid: true
groups:
  - { id: block, label: "一个逻辑块 = 4KB = 8 个扇区", tone: blue }
nodes:
  - { id: s1, label: 扇区 1, sub: "512B", row: 0, tone: muted, group: block }
  - { id: s2, label: 扇区 2, sub: "512B", row: 0, tone: muted, group: block }
  - { id: s3, label: 扇区 3, sub: "512B", row: 0, tone: muted, group: block }
  - { id: s4, label: "…… 一直到扇区 8", sub: "剩下的都一样", row: 1, tone: muted, group: block }
  - { id: use, label: "文件系统只认块", sub: "分配、定位、记账都按 4KB 来", row: 2, tone: green }
edges:
  - { from: s4, to: use, label: "8 个扇区打包成一个块" }
```

这个 `4KB` 后面会反复出现：inode 里记的是块号不是扇区号，位图里一位管的是一个块，一个索引块能装 1024 个块号（4096 ÷ 4）。==换一个块大小，后面所有数字都要重算。==

## 04 · 磁盘被格式化成的三个区

格式化的时候，磁盘（或分区）会被划成三块区域：

```lane-stack
- badge: 区域 1
  title: 超级块
  desc: 整个文件系统的说明书
  tone: violet
  nodes:
    - { title: 块总数, sub: "这个文件系统一共多少块" }
    - { title: 块大小, sub: "一块多少字节" }
    - { title: inode 总数, sub: "最多能存多少个文件" }
    - { title: 空闲块数, sub: "现在还剩多少" }
  next: "什么时候进内存 :: :: 挂载的时候"
- badge: 区域 2
  title: inode 区
  desc: 所有 inode 排在一起
  tone: amber
  nodes:
    - { title: inode 1, sub: "某个文件的全部元信息" }
    - { title: inode 2, sub: "另一个文件的" }
    - { title: "……", sub: "格式化时就分好的固定数量" }
  next: "什么时候进内存 :: :: 这个文件被访问的时候"
- badge: 区域 3
  title: 数据块区
  desc: 文件真正的内容
  tone: blue
  nodes:
    - { title: 数据块, sub: "4KB 一块" }
    - { title: 数据块, sub: "目录的内容也放这" }
    - { title: "……", sub: "占磁盘的绝大部分" }
```

==这三个区进内存的时机不一样，这一点容易忽略：==

```compare
first: 区域
head: [什么时候加载进内存, 为什么]
rows:
  - 超级块: [{ text: "文件系统被挂载时", tone: violet }, "操作系统一上来就得知道这个文件系统有多大、块多大，不然没法用"]
  - inode 区: [{ text: "某个文件被访问时", tone: amber }, "文件那么多，全加载进内存不现实，用哪个载哪个"]
  - 数据块区: ["读写到哪一块就载哪一块", "按需读，通常还会在内存里留一份副本（页缓存）"]
```

没人会把整个 inode 区加载进内存 —— 一个有 100 万个文件的文件系统，光 inode 就要占掉几十上百 MB，而同一时刻真正在用的可能只有几百个。

---

```quiz
- q: 修改一个文件的名字，需要改它的 inode 吗？
  a: |
    不需要。名字记在目录项里，inode 记的是元信息和数据块位置，里面没有文件名。
    改名就是把原目录里那条「名字 → inode」改成新名字，inode 一个字节都不用动。
    目录项为了效率经常缓存在内存里，改名字就更快了。
- q: inode 为什么必须存在磁盘上，而目录项可以只在内存里？
  a: |
    inode 是文件的唯一标识，它记着数据块在哪 —— 这个信息丢了文件就找不回来了，必须持久化。
    目录项只是「某个名字解析到了哪个 inode」这个结果的缓存，
    丢了可以重新读目录再解析一遍，所以不需要落盘。
- q: 为什么文件系统不直接按扇区（512 字节）读写？
  a: |
    因为磁盘最贵的动作是寻道和旋转。按 512B 读写会让每个小块都要付一次机械代价，
    效率极低。把 8 个扇区合成一个 4KB 的逻辑块，一次请求就能拿走 8 倍的数据，
    机械开销被摊薄了。这也是后续所有「块号、位图、索引数量」都以块为单位的原因。
```

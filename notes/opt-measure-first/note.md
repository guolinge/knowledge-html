一个程序跑十秒，你想让它变快。此时手里有十几种优化手段，全都「看起来有用」。真正的问题不是哪一条更聪明，而是**这十秒花在哪**。这篇按这个顺序讲：先看时间分布，再算收益上限，然后才谈手段，包括那些看起来跟编译器无关的手段（算法、数据结构、内存布局）。

## 01 · 十秒钟里，哪一百毫秒值得动

假设这十秒的分布是这样：

```text
函数 A   9.5s   ← 一个热点循环
函数 B   0.4s   ← 批量转换
函数 C   0.1s   ← 启动时建了一个表
```

三种努力，换来的整体收益差得很远：

```compare
first: 你做的事
head: [新总耗时, 整体提升]
rows:
  - 把 C 优化到完全不花时间: [{ text: "9.9s", tone: muted }, 1.0%，几乎不可测]
  - 把 B 快一倍: [{ text: "9.8s", tone: amber }, 2.0%]
  - 把 A 快一倍: [{ text: "5.25s", tone: green }, 47.5%]
```

==C 已经优化到「零成本」这种极端程度，也只值 1%。== 而 A 只要快一倍，整体就快一半。这就是为什么「先测量」不是习惯问题，而是算术问题：**在没测之前，你不知道自己正在优化的是 A 还是 C。**

同一件事换个角度看更清楚：一次优化能带来的整体收益，上限由它占的时间比例决定。这就是下一节的定律。

## 02 · 阿姆达尔定律：上限由没动的那部分决定

把「占总时间的比例」记作 P，把这部分加速的倍数记作 S，整体加速比是：

```text
Speedup = 1 / ( (1 - P) + P / S )
```

拖这根滑块看：热点占比越高，能被放大的空间越大；而不管 S 给多大，上限都死死卡在 `1/(1-P)`。

```demo
widget: tuner
title: 同样的加速倍数，落在不同占比上
actions: false
config:
  param: { label: 热点占比 P, unit: "%，往右拖", values: [20, 40, 60, 80, 95] }
  outputs:
    - { label: 把这块快 2 倍, unit: "倍", values: [1.11, 1.25, 1.43, 1.67, 1.9] }
    - { label: 快 4 倍, unit: "倍", values: [1.18, 1.43, 1.82, 2.5, 3.48] }
    - { label: 快到不花时间（S = ∞）, unit: "倍", values: [1.25, 1.67, 2.5, 5.0, 20.0], tone: amber }
```

几个可以直接读出来的结论：

- 占比 20% 的代码，**即使优化到零耗时，整体也只快 25%**。这是上限，不是估算。
- 占比 1% 的代码，再怎么努力都停在 1% 附近。多花的力气不会变成结果。
- 反过来，占比 95% 的热点，只要快一倍，整体就快近一倍。这也是为什么编译器把力气全砸在循环上。

```callout
tone: amber
icon: ⚠
text: |
  ==阿姆达尔定律说的是「上限」，它不告诉你「能不能做到」。==

  占比 95% 的热点里，可能有 60% 的时间在等一次网络往返。那部分即使你把循环优化到极致，
  也不会变快。先测时间去哪了，再测**这些时间在等什么**，顺序不能反。
```

## 03 · 「过早优化是万恶之源」的原话，和它没说的后半句

这句话出自 Knuth 1974 年的《Structured Programming with go to Statements》，原句比流传的版本长：

> We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%.

翻过来是两句话：**大约 97% 的场合该忘掉小的效率**；**但不要放过关键 3% 里的机会**。流传时几乎总是只剩前半句，于是它被读成「不要优化」。

Knuth 当时反对的不是优化，是在**不知道瓶颈在哪**的时候，为了想象中的性能去牺牲结构、可读性、正确性。他给的理由很具体：那些改动会让程序更难理解、更难改，而换来的收益在 97% 的情况下根本测不出来。

!!「这段代码我猜是瓶颈」和「这段代码在 profiler 里占 62%」是两种完全不同的信息。!! 前一种只能靠事后验证，而后验证的成本通常比一开始就测一遍高得多。

## 04 · 从猜测到测量：profiler 能告诉你什么

工具分三类，各自回答不同的问题：

```lane-stack
- badge: 采样
  title: 采样式 profiler
  desc: 每隔几毫秒中断一次，记下当时的调用栈
  tone: blue
  nodes:
    - { title: perf record / py-spy, sub: "看栈顶落点", tag: 低开销 }
    - { title: 火焰图, sub: "宽度 = 占比", tag: 找热点 }
  next: "知道时间落在哪些函数 :: :: 不告诉你为什么慢"

- badge: 插桩
  title: 插桩式 profiler
  desc: 在函数出入口塞计时器或计数器
  tone: violet
  nodes:
    - { title: gprof / 自定义埋点, sub: "调用次数 + 累计耗时", tag: 精确计数 }
    - { title: 代价, sub: "调用密集时开销很大", tag: 会改变时序, tone: amber }
  next: "知道每个函数被调了多少次 :: :: 高频小函数会被放大"

- badge: 硬件计数
  title: 硬件性能计数器
  desc: 直接读 CPU 里的计数器，回答「为什么慢」
  tone: green
  nodes:
    - { title: "`perf stat`", sub: "IPC、cache-miss、分支失败", tag: 靠 PMU }
    - { title: 判读, sub: "IPC 低 + L1 miss 高 → 在等内存", tag: 需要经验 }
  next: "知道流水线在等什么 :: :: 不告诉你业务上该不该这么写"
```

```compare
first: 你看到的现象
head: [先看哪个指标, 典型原因]
rows:
  - 热点函数自己算得很多: [IPC、指令数, 计算密集，或者循环里有冗余计算]
  - 热点函数没算多少但很慢: [L1/LLC miss、stalled cycles, 在等内存，或者别名导致的假依赖]
  - 时间均匀散在很多函数里: [调用次数、栈深度, 可能是抽象层太厚，或每次调用都在做重复工作]
  - 单线程快、多线程不涨: [CPU 利用率、锁等待, 串行部分没消掉（回到阿姆达尔）]
  - 延迟高但 CPU 不高: [off-CPU 时间、I/O 等待, 在等锁、等磁盘、等网络]
```

关键是最后一栏：profiler 告诉你**时间在哪**，不告诉你**为什么在那**。火焰图上最宽的那一块可能是 `memcpy`，原因却可能是你按列遍历了一个行优先存储的矩阵，那是下一节的下半部分要讲的。

## 05 · 收益梯度：算法 > 内存 > 并行 > 指令

同一份代码，能从不同层次变快。层次越靠上，倍数越大，但也越依赖人来判断：

```lane-stack
- badge: 第一层
  title: 算法与数据结构
  desc: 换掉解法，复杂度变了
  tone: green
  nodes:
    - { title: 嵌套循环 → 哈希表, sub: "O(n²) → O(n)", tag: 10~1000× }
    - { title: 重复排序 → 一次排序, sub: "每轮都排一遍", tag: 常数级删减 }
  next: "倍数最大 :: :: 需要业务语义，编译器做不了"

- badge: 第二层
  title: 内存访问方式
  desc: 数据怎么排、按什么顺序碰
  tone: blue
  nodes:
    - { title: 行优先遍历, sub: "顺着缓存行走", tag: 2~10× }
    - { title: 结构体拆成并行数组, sub: "AoS → SoA", tag: 也是向量化的前提 }
  next: "经常比算法更值得动 :: :: 要看数据规模和缓存大小"

- badge: 第三层
  title: 并行与向量化
  desc: 同一时刻干更多份活
  tone: violet
  nodes:
    - { title: 多线程 / 分片, sub: "上限受串行部分限制", tag: 回到阿姆达尔 }
    - { title: SIMD, sub: "一次 4/8/16 个元素", tag: 编译器可自动做 }
  next: "要结构配合 :: :: 数据有依赖时做不了"

- badge: 第四层
  title: 局部指令优化
  desc: 少几条指令、少一次跳转
  tone: muted
  nodes:
    - { title: 强度削弱、常量折叠, sub: "编译器自动", tag: 几个百分点 }
    - { title: 手写内联汇编, sub: "通常不值得", tag: 极少 }
```

为什么编译器不替你跳到第一层？把 `for i for j if (a[i]==b[j])` 改成哈希表，要决定哈希函数、要接受内存上涨、要处理相等语义和顺序，这些是**业务决策**，不是语义保持的变换。==编译器只能在「不改变你写下的行为」这个圈里活动，算法在圈外。==

所以分工是清楚的：**算法与数据结构由人选，具体实现由编译器优化。** 你写冒泡排序，它最多帮你把冒泡排得更快一点，不会帮你换成快排。

## 06 · 热点路径：99% 的那条路应该连续

程序里的路径不是等价的。一个请求 99.9% 走成功分支，0.1% 走错误处理，两条路的待遇不该一样：

```flow
grid: true
nodes:
  - { id: in, label: 一次调用, sub: "拿到的参数绝大多数合法", row: 0, tone: blue }
  - { id: check, label: 校验, sub: "长度、边界、类型", row: 1, shape: note, tone: violet }
  - { id: hot, label: 正常路径, sub: "紧接在校验之后，跳转最少", row: 2, tone: green }
  - { id: cold, label: 错误路径, sub: "挪到函数尾部，独立一段", row: 2, tone: amber }
  - { id: ret, label: 返回, sub: "两条路都汇到这里", row: 3, tone: muted }
edges:
  - { from: in, to: check }
  - { from: check, to: hot, label: 99.9% }
  - { from: check, to: cold, label: 0.1% }
  - { from: hot, to: ret }
  - { from: cold, to: ret, dashed: true }
```

把常见路径放在一起，换来的是四件事：指令缓存的命中更稳定、跳转次数更少、分支预测器更容易学对、编译器更愿意把这条路上的调用内联。低频路径挪远，代价只是它在真的发生时多跳一次。

这也是为什么带了频率信息的 CFG 比不带更有用：同样一张图，边上写着 99.9% 和 0.1% 时，布局和优化优先级就完全不同了。PGO 采集的正是这些数字（第 5 篇）。

```callout
tone: red
icon: ⚠
text: |
  !!「罕见」不要写成「不可能」。!!

  把错误路径标成「不可达」等于告诉编译器「这里不会发生」。一旦真的发生，
  程序的行为就落到未定义行为里，而不是「多跳一次」。优化假设要写成承诺，
  就得确认它真的永远成立。
```

## 07 · 局部性：少一条加法，可能不值一次缓存未命中

到这一层，成本的数量级差得很远。下面这些数字是**数量级**，具体机器各不相同，但相互之间的比例关系稳定：

```compare
first: 一次操作
head: [大致代价, 说明]
rows:
  - 寄存器里的加法: [{ text: "约 1 个周期", tone: green }, 现代 CPU 一个周期能并行做好几条]
  - L1 命中: [{ text: "约 4 个周期", tone: green }, 每核几十 KB]
  - L2 命中: [{ text: "十几到二十个周期", tone: blue }, 每核几百 KB 到 1 MB]
  - L3 命中: [{ text: "几十个周期", tone: amber }, 多核共享，几 MB 到几十 MB]
  - 主存一次访问: [{ text: "约上百纳秒", tone: red }, 相当于几百个周期]
  - 分支预测失败: [{ text: "几十个周期", tone: amber }, 要清空流水线重来]
```

表里最关键的一行是最后两行的对比：==一次缓存未命中的代价，够你在寄存器里做几百次加法。== 所以「少执行一条加法」和「少一次未命中」不在同一个量级上，后者通常更值钱。

三种局部性对应三种不同的改法：

```compare
first: 局部性
head: [它要求什么, 典型改法]
rows:
  - 时间局部性: [刚碰过的数据，尽快再碰一次, 复用一个中间结果，而不是重新算；把循环拆成「先算完再统一用」]
  - 空间局部性: [尽量碰相邻的地址, 数组按行遍历；把一起用的字段放进同一个结构体；结构体数组改成数组结构体]
  - 指令局部性: [常一起执行的代码放在一起, 热冷分离；错误处理挪到函数末尾；避免为了小分支把热路径切碎]
```

一个最小的例子。同样是遍历 100 万个整数：

```c
// 数组：每 16 个元素才碰到一条新的缓存行（64 字节 / 4 字节）
for (int i = 0; i < n; i++) sum += a[i];

// 链表：每个节点都可能是一次新的缓存行，还要先读指针再读数据
for (Node *p = head; p; p = p->next) sum += p->value;
```

数组版本除了第一个元素之外，后面 15 次访问都落在已经取回来的那条缓存行里；链表版本每个节点至少一次未命中，而且「读 `p->next` 才能知道下一个在哪」这件事让预取器也无从下手。**两种写法在指令条数上差不多，实际耗时可能差一个数量级。**

## 08 · 速查

```checklist
items:
  - 先拿到时间分布，再决定动哪里；没测之前，一切「看起来是瓶颈」都只是假设
  - 用 `1/((1-P)+P/S)` 算上限：占比 20% 的热点，优化到零也只有 1.25 倍
  - 「过早优化」反对的是「不知瓶颈就动手」，不是「优化」；那关键的 3% 要抓
  - profiler 只告诉你时间落在哪，不告诉你为什么；「为什么」要靠硬件计数器和代码结构去推
  - 收益梯度自上而下：算法 → 内存布局 → 并行/向量化 → 局部指令；越往下倍数越小
  - 热点路径要连续，冷路径要挪远；但「罕见」不等于「不可能」
  - 一次缓存未命中的量级，抵得上几百条 ALU 指令
  - 每次改完都要重测：优化之间会互相影响，测的是端到端
```

## 09 · 自测

```quiz
- q: 一段代码占总时间 20%，把它优化到耗时为零，整体能快多少？
  a: |
    `1 / (1 - 0.2) = 1.25`，也就是最多 25%。这是阿姆达尔定律给的上限，
    不是「大概能到」，而是「再强的优化也超不过」。

    占比越大，上限越高；这也是为什么先测时间分布比先学优化手段更重要。
- q: Knuth 那句话被漏掉的后半句是什么？为什么重要？
  a: |
    后半句是「但不要放过那关键 3% 里的机会」。他只反对「在不知道瓶颈时为了想象中的性能
    牺牲结构」，不反对在真正的热点上做优化。

    少了后半句，这句话很容易被读成「优化不重要」，而真实结论恰好相反：
    优化的力气要集中在测出来的那 3% 上。
- q: 为什么把错误处理挪到函数末尾、正常路径连续排列会更快？
  a: |
    常见路径的指令挨在一起，指令缓存命中更稳定，跳转更少，分支预测器更容易学对，
    编译器也更愿意内联。低频路径挪远后，它真的发生时才多付一次跳转。

    前提是知道哪条路常见。没有实测或 profile 数据时，这个判断很容易搞反。
- q: 数组遍历和链表遍历，指令条数差不多，为什么耗时能差一个数量级？
  a: |
    缓存行是 64 字节。数组一次未命中就把后面十几个元素一起取回来，后续访问都命中；
    链表每个节点都可能跨在一条新缓存行上，而且必须读到 `next` 才知道下个地址，
    预取器无法提前工作。瓶颈在内存，不在算术。
- q: 为什么编译器不会把一个 O(n²) 的循环自动改成哈希表？
  a: |
    因为那不是语义保持的变换：要选哈希函数、要接受额外内存、要定义元素相等语义、
    还要决定顺序是否重要。这些是业务决策。

    编译器只能在「不改变可观察行为」的范围内做变换，算法选择在这个范围之外，
    所以它由人选，具体实现由编译器优化。
```

先测量再优化：阿姆达尔定律决定上限，局部性决定下限

十秒里九秒半花在函数 A，把只占 0.1 秒的函数 C 优化到零，整体只从 10 秒变 9.9 秒。这篇讲优化收益从哪来：阿姆达尔定律给出的上限、算法与数据结构的收益梯度、热点路径为什么要连续排列、以及现代机器上「少一条指令」和「少一次缓存未命中」的差距。附 Knuth 那句「过早优化」的原话与它常被漏掉的后半句、三种 profiler 各自能看到什么。

读这篇之前，你需要先知道

一个程序跑十秒，你想让它变快。此时手里有十几种优化手段，全都「看起来有用」。真正的问题不是哪一条更聪明，而是这十秒花在哪。这篇按这个顺序讲：先看时间分布，再算收益上限，然后才谈手段，包括那些看起来跟编译器无关的手段（算法、数据结构、内存布局）。

01十秒钟里，哪一百毫秒值得动

假设这十秒的分布是这样：

函数 A   9.5s   ← 一个热点循环
函数 B   0.4s   ← 批量转换
函数 C   0.1s   ← 启动时建了一个表

三种努力，换来的整体收益差得很远：

你做的事新总耗时整体提升
把 C 优化到完全不花时间9.9s1.0%，几乎不可测
把 B 快一倍9.8s2.0%
把 A 快一倍5.25s47.5%

C 已经优化到「零成本」这种极端程度，也只值 1%。 而 A 只要快一倍，整体就快一半。这就是为什么「先测量」不是习惯问题，而是算术问题：在没测之前，你不知道自己正在优化的是 A 还是 C。

同一件事换个角度看更清楚：一次优化能带来的整体收益，上限由它占的时间比例决定。这就是下一节的定律。

02阿姆达尔定律：上限由没动的那部分决定

把「占总时间的比例」记作 P，把这部分加速的倍数记作 S，整体加速比是：

Speedup = 1 / ( (1 - P) + P / S )

拖这根滑块看：热点占比越高，能被放大的空间越大；而不管 S 给多大，上限都死死卡在 1/(1-P)。

同样的加速倍数，落在不同占比上

几个可以直接读出来的结论：

  • 占比 20% 的代码，即使优化到零耗时，整体也只快 25%。这是上限，不是估算。
  • 占比 1% 的代码，再怎么努力都停在 1% 附近。多花的力气不会变成结果。
  • 反过来，占比 95% 的热点，只要快一倍，整体就快近一倍。这也是为什么编译器把力气全砸在循环上。
⚠

阿姆达尔定律说的是「上限」，它不告诉你「能不能做到」。

占比 95% 的热点里，可能有 60% 的时间在等一次网络往返。那部分即使你把循环优化到极致， 也不会变快。先测时间去哪了，再测这些时间在等什么，顺序不能反。

03「过早优化是万恶之源」的原话，和它没说的后半句

这句话出自 Knuth 1974 年的《Structured Programming with go to Statements》，原句比流传的版本长：

We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%.

翻过来是两句话：大约 97% 的场合该忘掉小的效率；但不要放过关键 3% 里的机会。流传时几乎总是只剩前半句，于是它被读成「不要优化」。

Knuth 当时反对的不是优化，是在不知道瓶颈在哪的时候，为了想象中的性能去牺牲结构、可读性、正确性。他给的理由很具体：那些改动会让程序更难理解、更难改，而换来的收益在 97% 的情况下根本测不出来。

「这段代码我猜是瓶颈」和「这段代码在 profiler 里占 62%」是两种完全不同的信息。 前一种只能靠事后验证，而后验证的成本通常比一开始就测一遍高得多。

04从猜测到测量：profiler 能告诉你什么

工具分三类，各自回答不同的问题：

采样 采样式 profiler 每隔几毫秒中断一次，记下当时的调用栈
perf record / py-spy 看栈顶落点 低开销
火焰图 宽度 = 占比 找热点
知道时间落在哪些函数不告诉你为什么慢
插桩 插桩式 profiler 在函数出入口塞计时器或计数器
gprof / 自定义埋点 调用次数 + 累计耗时 精确计数
代价 调用密集时开销很大 会改变时序
知道每个函数被调了多少次高频小函数会被放大
硬件计数 硬件性能计数器 直接读 CPU 里的计数器，回答「为什么慢」
perf stat IPC、cache-miss、分支失败 靠 PMU
判读 IPC 低 + L1 miss 高 → 在等内存 需要经验
知道流水线在等什么不告诉你业务上该不该这么写
你看到的现象先看哪个指标典型原因
热点函数自己算得很多IPC、指令数计算密集，或者循环里有冗余计算
热点函数没算多少但很慢L1/LLC miss、stalled cycles在等内存，或者别名导致的假依赖
时间均匀散在很多函数里调用次数、栈深度可能是抽象层太厚，或每次调用都在做重复工作
单线程快、多线程不涨CPU 利用率、锁等待串行部分没消掉（回到阿姆达尔）
延迟高但 CPU 不高off-CPU 时间、I/O 等待在等锁、等磁盘、等网络

关键是最后一栏：profiler 告诉你时间在哪，不告诉你为什么在那。火焰图上最宽的那一块可能是 memcpy，原因却可能是你按列遍历了一个行优先存储的矩阵，那是下一节的下半部分要讲的。

05收益梯度：算法 > 内存 > 并行 > 指令

同一份代码，能从不同层次变快。层次越靠上，倍数越大，但也越依赖人来判断：

第一层 算法与数据结构 换掉解法，复杂度变了
嵌套循环 → 哈希表 O(n²) → O(n) 10~1000×
重复排序 → 一次排序 每轮都排一遍 常数级删减
倍数最大需要业务语义，编译器做不了
第二层 内存访问方式 数据怎么排、按什么顺序碰
行优先遍历 顺着缓存行走 2~10×
结构体拆成并行数组 AoS → SoA 也是向量化的前提
经常比算法更值得动要看数据规模和缓存大小
第三层 并行与向量化 同一时刻干更多份活
多线程 / 分片 上限受串行部分限制 回到阿姆达尔
SIMD 一次 4/8/16 个元素 编译器可自动做
要结构配合数据有依赖时做不了
第四层 局部指令优化 少几条指令、少一次跳转
强度削弱、常量折叠 编译器自动 几个百分点
手写内联汇编 通常不值得 极少

为什么编译器不替你跳到第一层？把 for i for j if (a[i]==b[j]) 改成哈希表，要决定哈希函数、要接受内存上涨、要处理相等语义和顺序，这些是业务决策，不是语义保持的变换。编译器只能在「不改变你写下的行为」这个圈里活动，算法在圈外。

所以分工是清楚的：算法与数据结构由人选，具体实现由编译器优化。 你写冒泡排序，它最多帮你把冒泡排得更快一点，不会帮你换成快排。

06热点路径：99% 的那条路应该连续

程序里的路径不是等价的。一个请求 99.9% 走成功分支，0.1% 走错误处理，两条路的待遇不该一样：

一次调用 拿到的参数绝大多数合法
校验 长度、边界、类型
正常路径 紧接在校验之后，跳转最少
错误路径 挪到函数尾部，独立一段
返回 两条路都汇到这里

把常见路径放在一起，换来的是四件事：指令缓存的命中更稳定、跳转次数更少、分支预测器更容易学对、编译器更愿意把这条路上的调用内联。低频路径挪远，代价只是它在真的发生时多跳一次。

这也是为什么带了频率信息的 CFG 比不带更有用：同样一张图，边上写着 99.9% 和 0.1% 时，布局和优化优先级就完全不同了。PGO 采集的正是这些数字（第 5 篇）。

⚠

「罕见」不要写成「不可能」。

把错误路径标成「不可达」等于告诉编译器「这里不会发生」。一旦真的发生， 程序的行为就落到未定义行为里，而不是「多跳一次」。优化假设要写成承诺， 就得确认它真的永远成立。

07局部性：少一条加法，可能不值一次缓存未命中

到这一层，成本的数量级差得很远。下面这些数字是数量级，具体机器各不相同，但相互之间的比例关系稳定：

一次操作大致代价说明
寄存器里的加法约 1 个周期现代 CPU 一个周期能并行做好几条
L1 命中约 4 个周期每核几十 KB
L2 命中十几到二十个周期每核几百 KB 到 1 MB
L3 命中几十个周期多核共享，几 MB 到几十 MB
主存一次访问约上百纳秒相当于几百个周期
分支预测失败几十个周期要清空流水线重来

表里最关键的一行是最后两行的对比：一次缓存未命中的代价，够你在寄存器里做几百次加法。 所以「少执行一条加法」和「少一次未命中」不在同一个量级上，后者通常更值钱。

三种局部性对应三种不同的改法：

局部性它要求什么典型改法
时间局部性刚碰过的数据，尽快再碰一次复用一个中间结果，而不是重新算；把循环拆成「先算完再统一用」
空间局部性尽量碰相邻的地址数组按行遍历；把一起用的字段放进同一个结构体；结构体数组改成数组结构体
指令局部性常一起执行的代码放在一起热冷分离；错误处理挪到函数末尾；避免为了小分支把热路径切碎

一个最小的例子。同样是遍历 100 万个整数：

// 数组：每 16 个元素才碰到一条新的缓存行（64 字节 / 4 字节）
for (int i = 0; i < n; i++) sum += a[i];

// 链表：每个节点都可能是一次新的缓存行，还要先读指针再读数据
for (Node *p = head; p; p = p->next) sum += p->value;

数组版本除了第一个元素之外，后面 15 次访问都落在已经取回来的那条缓存行里；链表版本每个节点至少一次未命中，而且「读 p->next 才能知道下一个在哪」这件事让预取器也无从下手。两种写法在指令条数上差不多，实际耗时可能差一个数量级。

08速查

  • 先拿到时间分布，再决定动哪里；没测之前，一切「看起来是瓶颈」都只是假设
  • 用 1/((1-P)+P/S) 算上限：占比 20% 的热点，优化到零也只有 1.25 倍
  • 「过早优化」反对的是「不知瓶颈就动手」，不是「优化」；那关键的 3% 要抓
  • profiler 只告诉你时间落在哪，不告诉你为什么；「为什么」要靠硬件计数器和代码结构去推
  • 收益梯度自上而下：算法 → 内存布局 → 并行/向量化 → 局部指令；越往下倍数越小
  • 热点路径要连续，冷路径要挪远；但「罕见」不等于「不可能」
  • 一次缓存未命中的量级，抵得上几百条 ALU 指令
  • 每次改完都要重测：优化之间会互相影响，测的是端到端

09自测

一段代码占总时间 20%，把它优化到耗时为零，整体能快多少？

1 / (1 - 0.2) = 1.25，也就是最多 25%。这是阿姆达尔定律给的上限， 不是「大概能到」，而是「再强的优化也超不过」。

占比越大，上限越高；这也是为什么先测时间分布比先学优化手段更重要。

Knuth 那句话被漏掉的后半句是什么？为什么重要？

后半句是「但不要放过那关键 3% 里的机会」。他只反对「在不知道瓶颈时为了想象中的性能 牺牲结构」，不反对在真正的热点上做优化。

少了后半句，这句话很容易被读成「优化不重要」，而真实结论恰好相反： 优化的力气要集中在测出来的那 3% 上。

为什么把错误处理挪到函数末尾、正常路径连续排列会更快？

常见路径的指令挨在一起，指令缓存命中更稳定，跳转更少，分支预测器更容易学对， 编译器也更愿意内联。低频路径挪远后，它真的发生时才多付一次跳转。

前提是知道哪条路常见。没有实测或 profile 数据时，这个判断很容易搞反。

数组遍历和链表遍历，指令条数差不多，为什么耗时能差一个数量级？

缓存行是 64 字节。数组一次未命中就把后面十几个元素一起取回来，后续访问都命中； 链表每个节点都可能跨在一条新缓存行上，而且必须读到 next 才知道下个地址， 预取器无法提前工作。瓶颈在内存，不在算术。

为什么编译器不会把一个 O(n²) 的循环自动改成哈希表？

因为那不是语义保持的变换：要选哈希函数、要接受额外内存、要定义元素相等语义、 还要决定顺序是否重要。这些是业务决策。

编译器只能在「不改变可观察行为」的范围内做变换，算法选择在这个范围之外， 所以它由人选，具体实现由编译器优化。

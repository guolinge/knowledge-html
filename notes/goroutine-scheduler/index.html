01为什么不是一条大队列

最省脑子的实现是：所有可运行 G 放一条全局队列，任何 M 都从这里取。它会挨两刀，刀刀致命。

一条全局队列 + 一把锁
M1 要取 G
M2 也要取 G
M3 … 都要取 G M 越多，锁越烫
全局队列 GRQ 所有人抢同一把锁
第一刀：锁竞争 取 G 这件事本身成了瓶颈
第二刀：缓存失配 G 上次在核 0 跑，这次被核 7 取走

这两刀都有历史证据：Go 1.1 之前真的只有一条全局队列，当时的调度 trace 里锁竞争一望便知。今天的 per-P 本地队列就是那个教训的产物。

改进来自内核自己的教科书 —— 学 per-CPU 运行队列：

每个 P 一条本地队列：平时只碰自己那份
P0 M0 绑定
LRQ: G1 G2 G3 无锁或低竞争
P1 M1 绑定
LRQ: G8 G9 同样无锁
GRQ 降级为兜底队列 只在本地空了的时候才看

但局部性会带来新毛病：负载不均。任务长短不一，新 G 又都由 go 语句创建在本地 P —— 一个扇出型任务会把一百个新 G 全灌进创建者的队列，别的 P 却空转。

⚖️

负载不均不需要极端场景。

一个扇出任务在新 G 落进本地队列的那一刻，不均衡就已经注定了。

所以在多核上，工作窃取不是锦上添花的优化，而是这套设计的常态机制。

空闲的 P 主动去偷 —— 一次拿走一半
P1 的 LRQ G1 G2 G3 G4 G5 G6
P2 的 LRQ: 空 M2 先原地自旋一小会儿
偷走 G4 G5 G6 只偷一半
为什么偷一半 摊薄「动别人队列」的同步成本，也避免为一个小任务反复上门

干这事的 M 在源码里叫 spinning M。它自旋时不是盲转，同时盯着其他 P 的队列和 netpoller，一有货立即出手。

02取下一个 G 的顺序

一个 M 要取材时，按这个顺序找下去
runnext 单槽缓存：刚刚让出的那个 G
本 P 的 LRQ 本地优先：无锁 + 缓存友好
全局队列 GRQ 每 61 次取 G 才查一次
偷其他 P 的 LRQ 拿一半
netpoller 都没有了，看网络事件唤醒了谁

runnext 值得单独说一句。 它放的是「刚刚变得可运行的那个 G」—— 比如刚从一次短阻塞里醒来。调度器优先取它，是因为这个 G 最可能马上要接着跑，它的数据还热在缓存里。优先取它，等于白捡一次局部性。

1/61 这个比例也有它的道理。 局部性与公平性是对头：LRQ 偏袒局部性，GRQ 维护公平性。定期抽查一次全局队列，既防止 GRQ 里的 G 被饿死，又不让 GRQ 成为常态竞争点。

换个熟悉的锚点：这和 git 的对象访问同构 —— 平时只看本地对象库，隔一段时间 fetch 一次 origin，1/61 就是那个「定期 fetch」的节流阀。

🔧

这个顺序和 1/61 都是 runtime 实现细节，随时可变。

业务代码不应依赖它们。理解它的价值在于知道「平衡点在哪」—— 而不是把它当成一份稳定的 API 契约。

03正在跑的 G 不撒手怎么办

队列决定「取谁」，抢占解决「上一个赖着不走」。先纠正一句过时的话：「Go 调度器是协作式的」对 Go 1.14 之后的紧循环已经不成立。

协作抢占（Go 1.2 起）：给栈守卫下毒
sysmon 后台监控线程，发现某 G 跑超 10ms
把 stackguard0 改成毒值 stackPreempt
等 G 走到下一次函数序言 序言本来就要检查栈边界
触发 morestack，发现守卫被下毒 当作它自己调了 Gosched，让出 P

妙处是零额外成本：栈检查本来就要做，抢占只是搭便车。

为什么不能任意点切换说明
栈可能正在搬迁上一节说的连续栈扩容，拷贝到一半把 G 换下去，指针修正就乱套了
GC 可能正在扫描栈找指针扫到一半换人，GC 的记录和实际栈就对不上了
所以需要「安全点」安全点就是「这些不变量都不处于中途」的代码位置

但协作抢占有一个死穴，而且非常致命：

没有函数调用的紧循环，毒值永远没人查收
for { i++ } 一个函数调用都没有
没有序言可查 毒值躺在守卫里，没人看
P 被占死 其他 G 饿死，GC 的 STW 也拖不动

Go 1.14 官方发布说明承认了这件事：紧循环「可能饿死调度器或严重拖延 GC」。

于是有了异步抢占：

异步抢占（Go 1.14 起）：直接发信号打断
sysmon 发 SIGURG 选它正因为它是「无事发生」型信号
信号处理器确认在异步安全点 不在 runtime 关键段里
把 PC 改成 asyncPreempt 入口 一段汇编：保存全部用户寄存器
转入 gopreempt_m，让出 P 紧循环不再可能饿死调度器
Go 1.2 · 2013

协作抢占

靠函数序言里的栈边界检查搭便车。成本几乎为零，但紧循环会饿死 GC

Go 1.14 · 2020

异步抢占兜底

用 SIGURG 打断任意用户态代码点。紧循环饿死成为历史，代价是每次打断要保存全套寄存器

维度协作抢占异步抢占
触发G 自己跑到安全点runtime 发 SIGURG 打断
时机函数序言、同步操作处任意用户态代码点（异步安全点）
代价几乎为零（搭栈检查的便车）每次打断要保存全部寄存器
边界紧循环永不触发runtime 关键段与信号处理中不可打断

副作用要知道：Unix 下信号会打断慢速系统调用，使它们更常以 EINTR 失败。

标准库的多数调用已经按契约自动重试了，但自己写 raw syscall 或包装 C 库时，要保留「错误是 EINTR 就重试」的循环。

所以今天准确的定性是：协作为主、异步抢占兜底。正常代码在安全点自己让出（便宜），长期不合作者被信号打断（兜底）。

🎲

这也解释了一个观感：Go 的调度「看起来像抢占式、行为不可预测」。

因为决策权在 runtime 手里，不在开发者手里 —— 你永远不知道 G 会在哪两条语句之间被换下去。

sysmon 除了抢占，还负责：把 GRQ 里的 G 灌给空闲 P、唤醒休眠的 M、 驱动 netpoll、回收空闲资源。它是调度器里唯一「不管业务」的角色。

为什么每个 P 要有一条自己的本地队列，而不是共用一条全局队列？

因为共用一条会挨两刀：一是锁竞争（每个 M 每次取 G 都要抢同一把锁，M 越多越烫）， 二是缓存局部性差（G 上次在核 0 跑，下次被核 7 取走，工作集刚被逐出又要重建）。 本地队列让 M 平时只碰自己那份，无锁且缓存友好。代价是负载不均，于是有了工作窃取。

工作窃取为什么偷一半，而不是偷一个？

偷一个的话，每次本地队列空了都要上门一次，而「动别人队列」本身有同步成本 —— 为一个小任务反复上门不划算。一次拿一半把这份同步成本摊薄了， 同时也让被偷的 P 还能剩下一些活干。

Go 1.14 之前，一个 for { i++ } 为什么能把调度器饿死？

因为协作抢占只在安全点生效，而安全点之一是函数序言里的栈边界检查。 紧循环里没有任何函数调用，也就没有序言 —— sysmon 把 stackguard0 改成毒值后，那个毒值永远没人查收，P 被占死， 其他 G 饿死，GC 的 STW 也拖不动。 Go 1.14 起改用 SIGURG 直接打断，这个问题才消失。

@insight/combination 候选值两条管道：从下拉框到数据源再回来

组件手里只有一个 metadata —— 那只是字段字典，里面只有 setKey / resolverKey 两个引用键，没有候选值。候选值是点开下拉那一刻现取的：一条走共享值集合接口，一条走动态候选接口。这篇把两条链路从鼠标点击追到 MySQL 的那一行、再追回 el-option，含每一层的形状变化、注入契约和四处竞态票据。

组件篇讲了受控数据流和控件决策，配置层讲了 metadata 从哪来。这一篇只回答一个问题：点开下拉框的那一下，候选值是从哪来的。

先给结论：metadata 里没有候选值，只有两个引用键，fieldType.setKey 和 fieldType.resolverKey。真正的取值是那一刻现取的，走两条不同的管道，各自穿过五层。两条管道的形状也不同：值集合是「字段被选中时自动拉一次，之后一直用」，动态候选是「每次输入关键词都发一次请求」。

01先看全图：一次取值穿过五层

每一层只做一件事：组件决定「用哪个 key」，注入层转发函数，宿主决定「缓存还是发 HTTP」，适配层把 pb 变形，服务端读内存投影或查常量表。

上面是地图（谁在哪、归谁、两条链路在哪分叉）；下面这张是分层流程 —— 同一批零件，换成从上到下的顺序，每一层挂着哪几个零件一眼扫完。

这一层只做一件事坏了会怎样

直觉代码里实际是什么结果
metadata 接口里带着候选值只带 setKey / resolverKey 两个引用键；CUSTOM 才会把 items 一起带 —— 而 pb 投影已经不产出 CUSTOM 了字典和值是两次请求

02链路 A · 值集合：点一下字段，十一行时序回来

2.1 触发点是「换字段」，不是「换操作符」

PortraitRow 把 feature.valueSource 交给 useStoredItems，values.ts 里 watch 的就是这个 source：

// packages/combination/src/values.ts —— 值集合分支
watch(source, async (next) => {
  const current = ++ticket;
  if (!next || next.type === 'NONE' || next.type === 'DYNAMIC') { items.value = []; return; }
  if (next.type === 'CUSTOM') { items.value = next.items; return; }
  items.value = [];
  const loaded = await loadValueSet(next.setKey).catch(() => []);   // ← 只有 VALUE_SET 走到这
  if (current === ticket) items.value = loaded;
}, { immediate: true });

所以：同一个字段上改操作符、改值，都不会再拉一次；换成另一个字段（或另一个 setKey）才会拉。 ticket 是防串道的票据：快速连换两次字段时，先发的响应回来晚了会被丢掉。

2.4 关系属性走的是另一条路：批量预取

RelationRow 不用 useStoredItems。一条关系可能挂好几个枚举属性，它索性在一个 watch 里把所有 VALUE_SET 属性一起拉回来，结果存在 propSetItems：

// packages/combination/src/components/RelationRow.vue —— 换关系时一次性拉齐
watch(relationDef, async (relation) => {
  const next: Record<string, ResolvedOption[]> = {};
  const ticket = ++propLoadToken;
  for (const prop of relation?.properties ?? []) {
    if (prop.valueSource.type !== 'VALUE_SET') continue;
    const items = await loadValueSet(prop.valueSource.setKey).catch(() => []);
    next[prop.key] = items.map((item) => ({ value: item.value, label: label(item.label), disabled: item.status === 'DISABLED' }));
  }
  if (ticket === propLoadToken) propSetItems.value = next;
}, { immediate: true });

对象（客体）的候选又是第三条路：DYNAMIC 走远程搜索，CUSTOM 用 metadata 自带 items，NONE 直接空数组，分支落在 propItemsFor() 里。

04函数是怎么「注入」进去的

组件和宿主之间是一份四行的契约：三个函数 prop + 三个 injection key。组件不 import 宿主，宿主也不 import 组件。

注入契约InsightCombiner.vue（154 行）里的三行 provide
组件侧消费

壳侧转发
// InsightCombiner.vue:59-61

宿主侧实现

为什么这么设计

组件包不绑定具体 HTTP 接口：它要的只是「给我 setKey 的候选值」，至于你从哪儿取、要不要缓存、什么时候清，都是宿主的事。 代价是多一层转发；好处是同一个组件包换一个宿主（另一个页面、另一种鉴权、甚至 mock 数据）不用改代码。

三个 prop 的来源接口不一样，第一个和第三个尤其容易混：

prop谁给的打哪个接口
metadataGET /api/crowd/metadata字段字典。里面只有 setKey / resolverKey
loadValueSet宿主 useValueSets → getValueSetGET /api/crowd/value-sets?setKey=
searchValues宿主 loadSearch → api.searchValuesGET /api/crowd/resolver-options?resolverKey=&keyword=&limit=
lookupValues宿主 loadLookup → api.lookupValuesGET /api/crowd/resolver-options?resolverKey=&values=（可重复）

4.1 那为什么不把 pb 直接当组件模型

方案代价结果
组件内部直接用 pb 形状pb 的字段全部可选（proto 生成类型就是 optional），每个消费点都要兜底：fieldType?.dataType ?? string、name?.zhCn ?? ''、status === 0 判断是否停用省掉一个 300 行的 resolve，换来模板和 computed 里到处都是 ??
组件内部用规范化模型（现在的做法）多一次转换（resolveCrowdMetadata + api.ts 的 toValueItems）子树只认穷尽联合 { type: VALUE_SET, setKey }，模板里不用兜底

真正的理由不是「不好改组件内部模型」，而是线路形状还没定稿。

技术方案自己写着：字段名按 proto 走 snake_case，但「HTTP 序列化后是否转成 camelCase、I18nText 的键是不是 zh-CN，待确认」；value 现在还是 JSON 标量字符串（proto 里用 string 传标量的通用约定）。如果把组件的公开模型钉死在这些还没定的线路细节上，协议一改成 snake_case 或 zh_cn，组件、宿主、测试就得跟着改一轮。

🧭

组件对外 prop 收的确实是 pb（metadata: CrowdMetadata），但那是入口处一次性 resolve。 注入函数的返回值用的是组件自己的 ValueItem —— 这两个位置性质不同：前者是「进来的数据要翻译一次」， 后者是「公开契约不该被某个协议的当前写法绑住」。适配层就是那条缝：线路怎么变，只改一处。

两个 GET，都没有 body。区别在参数语义和数据的住处。

setKey 必填。

处理

5.1 那两个接口读的「内存快照」是什么

上面说 value-sets 从「内存快照」里取集合 —— 这份快照就是六张元数据表的全量读模型（MetadataRows），服务端进程里只留一份，5 秒过期。它由 getMetadataRows() 维护：

// apps/server/src/metadata/source.ts
const CACHE_TTL_MS = 5_000;

export async function getMetadataRows(): Promise<MetadataRows> {
  if (cached && Date.now() < expiresAt) return cached;   // 5 秒内：直接用快照
  if (inflight) return inflight;                          // 并发请求复用同一个查询
  const pending = loadMetadataRows({ enabledOnly: false }) // 六张表全量读一次
    .then(rows => { assertMetadataRows(rows); cached = rows; expiresAt = Date.now() + CACHE_TTL_MS; return rows; });
  inflight = pending;
  return pending;
}

三个字段各管一件事：cached 是快照本身，expiresAt 是它的死期，inflight 让同一个 5 秒窗口内的并发请求共用一次 MySQL 查询（避免缓存击穿时打出一串重复查询）。

这份快照不只喂 value-sets：/api/crowd/metadata、/api/crowd/catalog、预览（/api/preview）和创建快照（/api/snapshots）读的都是它 —— 所以「改一行 MySQL，最多 5 秒后整条链路一起变」。这也是为什么 demo 里改配置能立刻在界面上看到效果。

位置快照在哪多久变一次
服务端进程（demo）getMetadataRows() 的 cached，全量读本机 MySQL5 秒 TTL，或 resetCatalogCache() 立即失效
线上（技术方案）元数据归 Data Admin，BFF 通过 Metadata API 取；缓存退到 BFF 或 Data Admin 一侧语义不变：不是每个请求都去问上游
浏览器页面重新获得焦点时重新拉一份 metadata；revision 没变就复用原对象、也不清值集合缓存跟着服务端的 5 秒走

宿主那边则是另一层：页面重新获得焦点时刷新字典，revision 没变就不重建对象、也不清缓存。

06边界：六处不那么直觉的地方

停用值要回来

停用是改 status，不是删行

enum_content 里的条目 status: 0 之后仍然出现在响应里，宿主把它映射成 disabled: true。 这样历史条件回显时下拉里还找得到「深圳」，只是新条件选不了它。 如果服务端过滤掉停用值，历史条件会显示成一个裸的 440300。

空关键词 = 空列表

demo 的解析器不返回「默认一批」

if (!needle) return { items: [], nextCursor: null }。打开下拉会发一次空搜索，但结果是空的。 真实解析器可能返回热门项 —— 那是 searchResolver 的实现自由，不是协议的约定。

没有防抖

方案里写了，代码里没有

packages/combination/src/ 里没有 debounce、没有 setTimeout。每次输入都发一次请求， 靠的是 token 丢弃旧响应，而不是合并请求。请求量按流量算，不按意图算。

Element Plus 会自清查询

远程搜索后的那次回调是坑

远程搜索结束后，el-select 会把查询清空并再触发一次 remote-method，回调参数是空串。 不判断的话，刚写进 remoteItems 的结果会被这次空搜索覆盖成空列表。 RelationRow 用 currentObjectQuery() 读真实输入框来挡。

缓存的两级失效

一级在宿主，一级在页面

宿主：staffId 变化或 metadata revision 变化 → reset() 清 cache 与 inflight。 页面：重新获得焦点 → loadMeta()；revision 相同则复用原 metadata 对象，不触发下游 watch。

兜底显示原值

换不到名字也要能看

解析器里查不到那个 value 时，shownItems 用 { value, label: String(value) } 兜底 —— 标签位上显示原始的 00700.HK。宁可难看，不可留空。

为什么 metadata 接口里看不到候选值？

设计和消费解耦：metadata 只是字段字典，回答「这个字段有没有候选值来源、去哪取」（enumType + setKey / resolverKey）。 候选值可能很大、可能是实时的（股票搜索），塞进字典会让每次刷新字典都带上几万条数据。所以值是另一条按需的请求。

值集合字段，改一下操作符会再发一次请求吗？

不会。useStoredItems watch 的是 valueSource，只有换字段（换 setKey）才重新拉。 改 op、改值都只是草稿变化，不触发取值。

动态候选下拉打开后是空的，怎么排查？

先看服务端：searchResolver 对空关键词直接返回空列表，这是当前实现的选择（打开时的空搜索拿不到候选）。 再看请求有没有带上关键词；如果关键词有值仍然是空的，看 values/keyword 是否传混（values 非空会忽略 keyword）。 最后看 remoteItems 是否被 Element Plus 的二次空搜索覆盖。

两个注入函数都返回 undefined 会怎样？

组件不会抛错：inject(key, async () => []) 给了默认空实现，壳里又用 ?? Promise.resolve([]) 兜了一层。 表现是下拉永远为空、搜索无结果 —— 组件可以脱离宿主独立渲染，只是没有候选值。

草稿里有一个搜索不到的历史取值，下拉里会显示成什么？

watch(modelValue, resolveSelected) 会用 values= 向解析器反查一次名字；查到就用中文名，查不到用 String(value) 兜底。 两种情况都能在列表里看到它，不会因为不在候选里就消失。

一句话

metadata 是字典（只有 setKey / resolverKey）；候选值是现取的：值集合一次拉全集并按 setKey 缓存，动态候选每次输入都打一次 resolver-options，两条路都在「宿主 App」这一层落成 HTTP。

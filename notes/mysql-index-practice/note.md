## 01 · 表数据存在哪：InnoDB 用索引来组织数据本身

先别急着背索引规则，问一个更底层的问题：一张表的行数据，物理上存在哪个文件、什么结构里？这个问题的答案决定后面一切。

朴素的方案叫**堆表**：数据按插入顺序无序堆放，索引是独立文件，叶子存的是行指针。MyISAM 就是这么做的。它的麻烦出在主键查找上——先查索引拿到指针，再按指针去数据区捞行，两次 IO 起步；而且行一旦迁移，所有指向它的指针都得跟着改。

InnoDB 否决了这条路，选择让整张表**长**在主键 B+ 树的叶子上：叶子节点直接内联完整行，索引页就是数据页，没有独立的数据区。官方称之为**索引组织表**。

```compare

head: [堆表（MyISAM）, 索引组织表（InnoDB）]
rows:
  - 主键查找: ["索引 → 指针 → 数据区，两跳两次 IO", "主键树直达数据页，一跳"]
  - 数据的组织: ["数据区按插入顺序无序堆放", "整张表按主键排序，「排序」是本体"]
  - 行迁移时: ["所有二级索引里的行指针都要改", "二级索引存主键值，主键终身不变，行随便搬"]
  - 主键范围扫描: ["回无序的数据区随机跳", "==退化成顺序读=="]
  - 表和索引的关系: ["两个独立文件，各自为政", "主键树的叶子页就是数据页，物理上不可分割"]
```

这个选择有一个现成的类比：文件系统的目录项找到 inode，再经间接块找到数据块，是多次间接寻址；InnoDB 押的是内联——对「按主键取行」这个最高频操作，找到索引项即找到数据，少一跳 IO 就是巨大的赢面。

```callout
  全是这一刀在不同视角下的投影。理解了它，后面的名词不再是孤立术语。
```

### 聚簇索引：主键就是数据本身

「整张表长在主键 B+ 树上」有个正式名字：**聚簇索引**。聚簇索引是存储行数据的那棵 B+ 树，有主键时通常就等同主键。

那没有主键的表怎么办？InnoDB 的回退规则是一条决策链，每一步都在凑同一个硬条件——**键必须唯一且非空**，因为数据只能按一种键物理排一次：

```flow

nodes:
  - { id: pk, label: 有 PRIMARY KEY？, sub: 用它做聚簇索引, row: 0, tone: green }
  - { id: uniq, label: 第一个全列 NOT NULL 的 UNIQUE 索引, sub: 索引键不能有 NULL，否则「唯一」名存实亡, row: 1, tone: blue }
  - { id: gen, label: 都没有 → 隐藏的 GEN_CLUST_INDEX, sub: 6 字节单调递增 row id，行按插入顺序排, row: 2, tone: amber }
edges:
  - { from: pk, to: uniq, label: 没有 }
  - { from: uniq, to: gen, label: 也没有 }
```

两个推论直接从物理结构掉出来：

- **每张表有且只有一个聚簇索引。** 行数据只能有一种物理排列顺序，第二个「聚簇」无处安放。「再加一个聚簇索引」在 InnoDB 里根本不存在。
- **主键最好在建表时就定好。** 事后 `ALTER` 改主键等于把整张表按新键重排一遍，大表上是一次代价高昂的全表重建；依赖隐藏 row id 的表，后续任何主键变更都是在为当年的缺省补税。

顺带澄清一个常见混淆：聚簇索引和主键**通常等同但不是同一概念**。有主键时，主键那棵树担任聚簇索引；没主键时，聚簇索引仍然存在（按回退规则产生）。聚簇索引是「存数据的树」这个角色，主键是扮演这个角色最常见的人选。

**为什么存主键值而不存行指针？** 看看存行指针会发生什么：聚簇索引的叶子在页分裂、行迁移时物理位置会变，行每搬一次家，所有二级索引都得跟着改一遍——一笔看不见但持续在付的维护税，漏改就是数据损坏。存主键值则完全免疫：主键终身不变，行怎么搬，二级索引都不用动。

```compare

rows:

  - 写入成本: ["每次页分裂都要维护全部索引", "只多复制一份小主键"]
  - 类比: ["用文件偏移量引用对象", "==git 用 content hash 引用对象==，内容移动引用不失效"]
  - 代价: ["——", "读多走一趟树（回表）"]
```

存完整行也不行——那等于把表复制 N 份（N 个二级索引），写入成本爆炸。存主键值是**写放大与读回表之间的平衡点**：写入只多复制一份小主键，读取多跑一趟树。它还带来一个连带好处：二级索引叶子更小，同样的 16KB 页能装更多条记录，==二级索引树本身更矮==，遍历更快。

### 主键宽度税：短主键、自增主键是结构逼出来的

机制直接给出一条成本公式：**主键宽度税 = 主键宽度 × 二级索引数量 × 行数**。官方原话："If the primary key is long, the secondary indexes use more space"——这不是风格建议，是存储成本的直接换算。

```cards

    tag: 8 字节
    code: "每条二级记录复制 8B"
    desc: 短、自增，是默认最优解。

    tone: amber

    tone: red

    code: "(36 − 8) B × 10⁸ × 5 ≈ 14 GB"
    desc: 这笔税不写在任何账单里，实打实变成磁盘占用和缓存压力。
```

自增主键的第二层好处在**插入位置**：新行永远插在聚簇索引最右端，最后一页持续被填满再分裂，写集中在少数热页上，缓存友好；UUID 随机主键把插入点撒满全树，页分裂频发，同样的写入量 IO 模式劣化一个数量级。业务确实需要全局唯一时，常见的折中是**有序 UUID**（时间戳打头）：保住唯一性，又让插入近似顺序。主键设计是在唯一性、顺序性、宽度三个变量里找平衡——InnoDB 的结构已经把平衡点压到了「短、自增」这一端。

还有一条容易被忽略的推论：**二级索引里的主键值参与排序**。索引列有重复值时（name 相同的多行），InnoDB 靠叶子里的主键值做次级排序，保证记录全序——单列索引 (name) 实际等价于 (name, 主键)。主键不只是顺带携带，还悄悄充当了索引的最终排序键。

## 03 · 覆盖索引：把回表这一步省掉

回表不是一次性的，是**每命中一行回一次**。二级索引每命中一行，就要额外走一趟聚簇索引树：

```compare
first: 命中行数
head: [回表代价, 后果]
rows:
  - 命中 1 行: ["1 次回表", "可忽略"]
  - 命中 100 行: ["100 次回表", "开始能感觉到"]
  - 命中 1 万行: ["1 万次随机 IO 风暴", "==优化器宁可全表顺序扫==——顺序读吞吐高一个数量级"]
```

假设一次二级索引定位 1ms、一次回表 1ms（都按磁盘随机读算），命中 1000 行的查询就是 1ms 定位加 1000ms 回表。这就是为什么有些查询走了索引反而更慢：索引帮你把行定位了，回表又把省下的 IO 加倍还了回去。

先纠正一个最常见的误解：

```callout
tone: red
icon: ⚠
text: |
  ==覆盖索引不是一种新的索引类型。==它是「某个查询恰好被某个现有索引完全满足」的
  运行时状态——索引还是那个普通索引，只是这次查询要的列全在树里。
  同一个索引，对查询 A 是覆盖索引，对查询 B 就不是。==覆盖是查询与索引之间的匹配关系，不是索引自身的属性。==
```

### 判定：三类列全在同一个索引里

判定标准一句话：这个查询用到的全部列都在索引树里，就算覆盖。展开成三类：**SELECT 的列、WHERE 过滤的列、ORDER BY 排序的列**，三者全在同一个索引里才算覆盖。官方最小示例：

```sql
-- 假设有索引 (key_part1, key_part3)
SELECT key_part3 FROM tbl_name WHERE key_part1 = 1;
-- key_part1 用于定位，key_part3 就在索引树里 → 覆盖，无回表

SELECT key_part2 FROM tbl_name WHERE key_part1 = 1;
-- key_part2 不在树里 → 必须回表 → 不覆盖
```

两条查询的差别只有一列，结论天差地别。WHERE 列有**两重身份**：既是定位器（不在索引里则索引连用都用不上），又是覆盖判定的参与者。实践里最常见的破坏者是 `SELECT *`——除非索引恰好包含所有列，否则几乎不可能覆盖；想吃覆盖红利，就得精确列出所需列。

InnoDB 还有一顿**免费午餐**：二级索引叶子天然携带主键列。所以 `SELECT id FROM t WHERE name='Jones'` 这类查询自动被覆盖——主键就躺在叶子里，回表查它自己纯属多余。`SELECT id, name FROM t WHERE name='Jones'` 同样覆盖。评估一个索引能覆盖哪些查询时，永远可以把主键列算进「索引已含列」清单。很多「只取 id」的查询 EXPLAIN 出来是 Using index，不是谁特意设计了覆盖索引，是 InnoDB 白送的。

覆盖生效与否，EXPLAIN 的 Extra 字段会说话：

```compare
first: Extra 里的值
head: [含义, 是不是覆盖]
rows:
  - Using index: ["纯从索引树取值，无回表", "==是=="]
  - Using index condition: ["ICP：部分条件下推到索引层先过滤", "不是——仍可能回表，排查时最常被读反的一行"]
  - （空）: ["走了索引但取了别的列", "不是——最普通的「走索引 + 回表」"]
```

最后一层是权衡：为了覆盖某查询把一堆列塞进联合索引，会撑大索引、拖慢写入。官方也提醒过多索引损害性能。原则是在满足查询需求的前提下最小化列数。覆盖索引是甜点不是主食：高频查询值得专门设计，冷查询别为它扩张索引宽度；折中做法是只把「高频查询真正要的列」追加到已有索引尾部，追加一列的边际成本远低于新建一棵树。动手之前先用 EXPLAIN 盘点现有索引——你手里已有的索引可能早就覆盖了一批查询，只是没用精确列名去查。

一个高频误传顺手澄清：`WHERE first_name='John' AND last_name='Jones'`（条件顺序颠倒）**同样能用**——优化器会重排等值条件。能不能用看的是「列集合是否构成左前缀」，不是 WHERE 里的书写顺序。给 first_name 单独建索引当然也能服务只查 first_name 的查询，但那是另一棵树，和这棵联合索引无关。

### 范围列之后，为什么「断掉」

高频踩坑：索引 (a, b, c)，查询 `WHERE a=1 AND b>10 AND c=5`：b 用了范围后，c 不再参与索引查找。物理原因和上面的「跳列」完全同构：

```arch
svg: idx-range-break
caption: 等值收成点，范围停在区间。b>10 命中一段连续区间，==区间里 c 乱序==（8, 1）——引擎在第一个范围列之后停止用后续列做索引查找，c=5 降级成区间内的逐行过滤。
parts:
  q:
    label: WHERE a=1 AND b>10 AND c=5
    sub: 索引 (a, b, c) · 三列条件
    detail: 三列都有条件，==能参与索引定位的只有前两列==。
  b1:
    label: b = 1
    sub: c = 5
    detail: a=1 的区块里，b 全局有序：1, 5, 12, 20。
  b2:
    label: b = 5
    sub: c = 2
    detail: b 有序是==等值列一层层给出来的==。
  b3:
    label: b = 12
    sub: c = 8
    detail: b>10 命中连续区间 [12, 20]。==区间内 c 是 8, 1，乱序==——有序只到 b 为止。
  b4:
    label: b = 20
    sub: c = 1
    detail: 同一段区间。c 的任何值都可能出现在任何位置，==没有排序保证==。
  cut:
    label: 索引查找停在这里
    sub: 区间内 c 乱序（8, 1）· 只能逐行过滤
    detail: ==第一个范围列之后，索引列断掉==。c=5 仍会被执行，但降级成区间内逐行过滤，不是索引定位。
anchors:
  - { part: q, label: "三列条件的查询" }
tours:
  - id: rangebreak
    label: "三列是怎么断的"
    steps:
```

两个补充把边界钉死：**IN 算范围**：`b IN (10,20,30)` 是多个点的集合而非一个点，命中后 c 同样接不上。**等值链能走满**：`WHERE a=1 AND b=10 AND c=5` 三个等值能一路用到 c。如果查询真的需要「b 范围 + c 等值」，把 c 挪到 b 前面（索引 (a, c, b)）三列全活。最左前缀的完整拼图到此齐了：==从左、连续、且前面全是等值==。

## 05 · 列顺序设计：四条规则与验证

设计列顺序之前，先有两个量化指标。**基数**是列的去重值数量；**选择性**是 `COUNT(DISTINCT col) / COUNT(*)`，越接近 1，一个等值条件越能一刀砍掉更多行。优化器偏爱高选择性索引，本质是偏爱「一刀见血」。

但**平均选择性会骗人**。100 万行里 99% 是 type='user'、1% 是 'admin'：type 列的平均选择性极低（去重只有 2 个值），优化器按平均值可能看不上它；可真查询 `WHERE type='admin'` 一击命中 1 万行，高度有效。

```compare
first: 看哪个数字
head: [列的平均选择性, 具体谓词值的命中效果]
rows:
  - 怎么算: ["COUNT(DISTINCT col) / COUNT(*)", "SELECT COUNT(*) FROM orders WHERE status='pending'"]
  - 数据偏斜时: ["可能极低，优化器看不上", "==你为高频谓词值服务，不为平均统计服务=="]
  - 配套动作: ["SHOW INDEXES 的 Cardinality 列是 MySQL 维护的基数估算", "它是随机采样的，==差一个数量级就 ANALYZE TABLE 刷新=="]
```

四条排序规则，按优先级排：

```cards
cols: 2
items:
  - title: ① 等值列在前，范围列在后
    tone: red
    tag: 硬约束
    desc: 范围列之后的列无法参与索引查找（§04）。范围列殿后，否则它后面的列全废。
  - title: ② 等值列之间，高选择性放前面
    tone: blue
    tag: 早砍行
    desc: 先砍 90% 再砍 50%，中间结果比反过来小得多。收益是逐层叠加的。
  - title: ③ ORDER BY 列紧跟等值列
    tone: green
    tag: 免 filesort
    desc: 等值把结果收窄成一段连续区间，区间内行恰好按排序键排列，排序直接吃索引的有序性。中间夹一个范围列，区间内排序列就乱序了。
  - title: ④ 按最频繁的查询设计
    tone: violet
    tag: 业务规则
    desc: 用慢查询日志或 performance_schema 找真实热点。列顺序只能伺候一种查询模式——让最高频的查询付出最小代价，为一个冷查询精心设计的索引是负资产。
```

一组反例正例把规则一、二、三串起来。订单表高频查询：`WHERE status='pending' AND customer_id=42 ORDER BY created_at`：

```compare
first: 两个候选
head: [反例 (status, created_at, customer_id), 正例 (status, customer_id, created_at)]
rows:
  - 结构: ["范围列 created_at 夹在中间", "等值在前、范围在后"]
  - customer_id: ["接不上，无法参与索引查找", "==三列全干活=="]
  - 排序: ["区间内 created_at 乱序 → Using filesort", "顺序读即有序，无 filesort"]
  - 拆解: ["同样的三个列", "==列顺序设计就是用同一组积木拼出能用的形状=="]
```

filesort 是「排序要另起炉灶」的信号——索引本来有序，排序却被单独做了一遍。它不一定真写磁盘（小结果集在内存排），但「没吃到索引有序性」这一点是确定的。

规则给出方向，EXPLAIN 当裁判。两个候选索引对同一批查询分别 EXPLAIN，对比三处：key（选中谁）、rows（估算扫描行数，越小越好）、Extra（有无 Using filesort）。A/B 结果只对这批查询有效，换一批查询结论可能反转；rows 是估算，两候选接近时分不出高下，上 EXPLAIN ANALYZE 跑真实耗时。验证完把落选的索引删掉，别留冗余。

冗余索引是建索引前的最后一道检查：既然 (a, b) 能服务只查 a 的查询（最左前缀），已有 (a, b) 时再单建 (a) 就是纯浪费——白占空间，还拖慢每次写入。sys schema 的 `schema_redundant_indexes` 视图能帮你找出这类重复。

```checklist
tone: cross
items:
  - 已有 (a, b)，再建 (a)——前缀已经覆盖只查 a 的场景
  - 不看查询就消冗余：把还要单独支撑别的查询的单列索引删了
```

反例也要认清：已有 (a, b) 再建 (b) **不是**冗余——(a, b) 帮不了只按 b 过滤的查询（最左前缀）。冗余判断看的是查询的谓词前缀，不是列集合。每多一个索引，写入就多一份维护成本；先查重，再新建。

## 06 · 索引失效：不是索引坏了，是「不选」或「用不了」

「索引失效」是中文社区最被滥用的词。大多数时候索引并没有坏——它只是没被用。先把问题重新框定，排查才不会走偏：**「我的索引没被用」只有两种原因**：优化器按代价主动不选，或者查询写法破坏了索引成立的前提、索引压根没进候选名单。下面这张分诊地图把两个世界并排放：

### 最危险的一种：隐式类型转换，既慢又错

```sql
-- 危险：id 是 INT，传入 UUID 字符串
SELECT * FROM user WHERE id = '929f9152-0000-0000-0000-000000000000';
-- MySQL 把字符串解析到第一个非数字字符 → 实际比较 id = 929
-- 查询不报错，但可能匹配到完全不相干的一行

-- 正确：参数类型与列一致
SELECT * FROM user WHERE id = 929;
```

它同时是性能问题和正确性问题：索引用不了（比较的是转换后的列值，不是索引里存的原值），还可能悄悄读错行。类型转换规则不对称——字符串与数字比较时字符串转数字，所以坑藏在「列是 INT 还 VARCHAR」的不对称里。防御在应用层：**列是什么类型，参数就传什么类型**；ORM 尤其要盯紧，框架自动把数字序列化成字符串的链路正是高发区，排查时沿序列化链路往上游追。一句话：类型不一致的查询，最坏的情况不是慢，是悄无声息地错。

### EXPLAIN 速查与兜底

```spec
title: EXPLAIN 关键字段速查
subtitle: 健康值对照危险值，五列看完落案
rows:
  - k: possible_keys
    v: 被考虑的索引候选。==有它没选 = 不选；没它 = 用不了==
  - k: key
    v: 实际选中的索引。健康：你期望的索引名；危险：NULL
  - k: type
    v: "const / ref / range 健康；==ALL（全表扫描）==危险"
  - k: rows
    v: 估算扫描行数，越小越好；接近全表行数 = 索引白走
  - k: Extra
    v: "Using index（覆盖）健康；Using filesort / Using index condition 要对照语义看"
```

排查流程收成三步：先 EXPLAIN 看 key / type / rows / Extra 定位嫌疑；再对照上面的病根清单找结构性问题；还解释不通就开 optimizer trace 看优化器的代价账，或用 EXPLAIN ANALYZE 拿真实执行耗时；前者解释「为什么这么选」，后者验证「事实慢在哪」。三步走完，绝大多数「索引为什么没生效」都能落案。

## 07 · 收束：一条物理事实，推完全篇

把五个问题放回最初那条因果链，每个答案都是同一句话的展开：**数据按索引键排序，一切索引规则都从这条物理事实推导出来**。

```summary
title: 一句话收束
text: |
  聚簇索引把整张表按主键排好序；二级索引另排一棵、只存主键值，
  于是有了回表；覆盖索引把回表省掉；最左前缀是拼接排序数组的直接推论；
  列顺序设计是让等值、范围、排序各就各位；而「失效」，
  多半是这个序被查询写法破坏，或者被优化器按代价放弃。
```

```compare
first: 五连问
head: [一句话答案, 出处]
rows:
  - 聚簇索引和二级索引有什么区别？: ["聚簇索引=数据本身；二级索引存「索引列值+主键值」", "§01 §02"]
  - 覆盖索引是不是一种新索引？: ["不是。是查询恰好被现有索引完全满足的运行时状态", "§03"]
  - 最左前缀为什么必须从左？: ["序只存在于从左开始、连续、等值打头的前缀里", "§04"]
  - 联合索引字段顺序怎么定？: ["等值前、范围后、高选择性靠前、排序列紧跟等值，按最频繁查询设计", "§05"]
  - 为什么索引明明建了却没用？: ["先分诊：优化器不选（接受或刷新统计），还是结构性用不了（改写法）", "§06"]
```

想继续深挖，原文留了三个钩子：Index Condition Pushdown（在回表前先过滤，进一步削减回表次数）、Index Merge Optimization（多个索引如何协同）、EXPLAIN ANALYZE 与 optimizer trace（真实耗时与完整决策链）。

```quiz
- q: SELECT name FROM users WHERE name='Jones' 走 (name) 索引，Extra 是什么？换成 SELECT age 呢？
  a: Using index——二级索引叶子天然携带 name 和主键值，这条查询被覆盖。换成 age：age 不在树里，必须回表取整行，Extra 为空（或出现回表相关标记），命中多少行走多少趟。
- q: 索引 (a, b, c)，WHERE a=1 AND c=5 能用到几列？WHERE a=1 AND b>10 AND c=5 呢？
  a: 前者只用 a——跳过 b 之后 c 接不上（前缀必须连续）；后者用到 a、b——b 是范围，区间内 c 乱序，c=5 降级为区间内逐行过滤。有序只存在于「从左、连续、等值打头」的前缀上。
- q: EXPLAIN 里 possible_keys 有 idx_x 但 key 是 NULL，该立刻 FORCE INDEX 吗？
  a: 不。这属于「不选」：先 ANALYZE TABLE 刷新统计，再对照 rows——取行比例高时全表扫本来就更快，FORCE INDEX 是和代价模型打架。如果 possible_keys 里根本没有 idx_x，才是「用不了」，改写法或补索引，加 hint 毫无作用。
```

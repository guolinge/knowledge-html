## 01 · 先看两种你熟悉的写法

一个 Node 服务处理请求，代码大概长这样：

```javascript
async function handle(req, res) {
  const user = await db.getUser(req.params.id);  // 让出执行权
  const orders = await db.getOrders(user.id);    // 再让出一次
  res.json({ user, orders });
}
```

`await` 是一个明确的让出点：数据库没返回时，这段代码停在这里，事件循环去处理别的连接。JVM 的写法是另一条路：

```java
new Thread(() -> handle(conn)).start();
```

每个连接一条线程，`handle` 里可以放心地阻塞 —— 数据库慢，就慢这条线程。

Go 的写法介于两者之间：

```go
func handle(conn net.Conn) {
    buf := make([]byte, 4096)
    n, _ := conn.Read(buf)      // 看起来会阻塞
    conn.Write(process(buf[:n]))
}

// 每个连接一行，不关心线程，也不写回调
go handle(conn)
```

`conn.Read` 的写法是同步的，没有 `await`，也没有线程池。但进程可以同时服务很多连接。要理解这件事，得先回答一个更基础的问题：一条「执行流」到底是什么？

用一句话说：它是一条线性的指令序列，可以暂停，也可以从暂停的地方继续。这个定义对线程、goroutine、Node 的回调都成立。区别只在于：**谁来决定它在哪停、停了之后谁接上。**

## 03 · 一次切换的直接成本

先给这台机器上的实测（Apple M4、macOS 26、Go 1.26.2）：

```text
BenchmarkGPingPong-10      170 ns/op    两个 G 在一个无缓冲 channel 上来回递一次
BenchmarkMPingPong-10    13143 ns/op    两个 G 各自 LockOSThread，跨线程递一次
BenchmarkMemcpy64K-10      934 ns/op    64 KiB 内存拷贝
BenchmarkSyscallGetpid     7.4 ns/op    getpid
BenchmarkGoCreate          128 ns/op    创建一个 G 并等它结束
```

先解释这两行容易误读的数字：

- **G 的 170 ns 是一次往返**，包含两次交接，所以单次约 85 ns。两个 G 可能跑在同一个 M 上，也可能不跨线程，具体取决于调度器把它们放在哪。
- **M 的 13.1 µs 也不是纯粹的内核切换**。两个 G 被锁在不同线程上，一个 G 阻塞、另一个被唤醒，这里面包含的是「唤醒另一条线程」的完整路径，不是一次裸的内核上下文切换。不同系统的唤醒实现差别很大，这个数不能直接和 Linux 上常见的「1~2 µs」比较。

要比较的是量级：==跨线程交接比同一 M 上的 G 交接贵两个数量级。== 但单次微秒级的开销，在大多数业务里感知不到。让线程方案撞墙的不是「一次切换慢」，而是「切换次数 × 任务数」：

```text
10,000 条线程，每条每秒被切换 1,000 次
= 每秒 10,000,000 次切换
× 每次 13 µs（这台机器上跨线程交接的量级）
= 130 秒的切换时间，摊在 1 秒里 —— 还没算干活
```

这个算式只是用来说明规模效应，不代表真实负载的切换频率。它想说的是：单次成本和总成本之间隔着一个「并发任务数」。

## 04 · 间接成本：缓存里的残留

切换的账单有两张。第一张是上面那些微秒；第二张不在切换的耗时里，而在切换之后的执行里。

一条线程在核上跑，它最近用过的指令和数据会被装进 L1/L2，页表项会被装进 TLB。换一条线程上来，缓存里装的是上一条线程的工作集：

- 新线程要用的数据不在 L1/L2，要一条条从更远的层级拉回来；
- 如果换了进程，页表也换了，TLB 里的映射整体作废；
- 如果两条线程在同一个进程里，TLB 还能复用一部分，但数据缓存仍然要重装。

这部分开销和「工作集有多大」「切换有多频繁」都有关，没法用一个固定的微秒数概括。它也是为什么「线程切换只要 1 µs」这句话不能直接推出「开十万条线程没问题」：被乘上任务数的是它，不是那 1 µs。

## 05 · 第二条重量：栈在创建时定死

线程的另一半重量不在切换，在预留。

| 平台 | 默认线程栈 | 说明 |
|---|---|---|
| Linux（glibc pthread） | 常见 8 MiB | 跟随 `RLIMIT_STACK`；`ulimit -s` 默认 8192 KiB |
| macOS（pthread） | 524 KiB（本机实测） | `pthread_get_stacksize_np` 读出来是 524 KiB，含护栏页 |
| JVM（64 位 Linux） | 1 MiB | `-Xss` 的默认值 |

关键区别是「预留」和「常驻」：

```text
10,000 条线程 × 8 MiB = 80 GiB 虚拟地址空间
真正用到多少，才分配多少物理页
```

所以 8 MiB 不会立刻吃掉 80 GiB 内存。但它锁死了数量上限：虚拟地址空间是有限的（32 位进程只有 3 GiB 左右用户空间，2 MiB 一条时一千多条就到顶），而且「最坏情况要多少栈」这份估算被压给了写代码的人 —— 递归深一点、局部数组大一点，就得留够。

线程栈不能在运行中搬家，原因是内核不知道栈里哪一格是整数、哪一格是指针。要扩容就得复制整段栈，再把栈内的指针全部改到新地址；内核没有这份「哪里是指针」的信息，所以做不到。

Go 的 G 把这两件事都换了：栈 2 KiB 起步、不够就换一块两倍大的连续内存再搬（靠 GC 的栈图修正指针），调度也搬到了用户态。本机实测：

```text
100,000 条 G：栈 196 MiB + 堆 61 MiB，进程 RSS 256 MiB，内核线程 11 条
1,000,000 条 G：栈 1954 MiB + 堆 609 MiB，进程 RSS 1800 MiB，内核线程 11 条
```

一百万条执行流、十一条线程。这不是「线程变快了」，是「每条流的固定成本被拆掉了」。

## 06 · 这两条重量，决定了后面要拆哪两样

把上面的账收一下，Go 要解决的是两个具体问题：

1. **切换路径**：线程切换必须进内核。要绕过它，就得在用户态决定「下一条跑谁」—— 这是第 ④、⑥ 篇的 GMP 和调度器。
2. **栈预留**：线程栈创建时定死。要绕过它，就得让栈能按需增长 —— 这是第 ③ 篇的可增长栈。

而在这之前，得先看前人试过什么、为什么没成（第 ② 篇）。否则很容易把「用户态调度」当成 Go 的首创，重复踩一遍旧 M:N 的坑。

  a: |

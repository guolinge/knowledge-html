## 01 · 一条执行流由什么构成

进程和线程的区别，卡在「围栏画在哪里」这一件事上。

```arch
svg: go-thread-layout
caption: 隔离发生在进程层（页表围起来的那一圈），执行流是线程。栈随流走，堆随容器走。
```

那一条执行流本身，拆开来只有三样东西。这三样加起来，就是「暂停一条流时要记下的东西」：

```flow
grid: true
groups:
  - { id: snap, label: "暂停一条执行流，只需要记下这三样（里面没有堆）", tone: blue }
nodes:
  - { id: pc, label: "指令指针 PC", sub: "下一条指令在哪", row: 0, tone: violet }
  - { id: reg, label: "寄存器现场", sub: "算到一半的中间值", row: 1, tone: blue }
  - { id: sp, label: "私有栈", sub: "局部变量、返回地址", row: 2, tone: green }
  - { id: heap, label: "堆", sub: "挂在进程上，不挂在执行流上", row: 3, tone: muted }
edges:
  - { from: pc, to: reg, label: "一起被打包成一份现场" }
  - { from: reg, to: sp, label: "一起被打包成一份现场" }
  - { from: sp, to: heap, label: "恢复时不用搬它", dashed: true }
```

==快照里没有堆，这条分界线是后面一切成本差异的钥匙。==

栈必须跟着执行流走（它是这条流自己的调用链）；堆挂在进程上，谁都不独占。所以线程切换不用搬堆，而进程隔离却要用页表把堆整个隔开。

拿一个熟悉的东西对照一下更容易记住：

```compare

head: [git 那边, 为什么对得上]
rows:
  - 进程: ["一个独立的仓库", "对象库与工作区彼此不可见，隔离由各自的 `.git` 强制"]
  - 共享的堆: ["同一个对象库", "多条操作线共用同一份对象，谁都能改"]
  - 私有栈: ["各自的暂存区", "每条线一份，暂停时连它一起快照"]
  - 指令指针 PC: ["各自的 HEAD 游标", "记着这条线走到哪了"]
```

## 02 · 一次切换，是一趟进出内核的旅程

```seq
grid: true
participants:
  - { id: a, label: 用户态 · 线程 A, sub: 正在 CPU 上, tone: green }
  - { id: k, label: 内核, sub: 调度器在这里, tone: violet }
  - { id: b, label: 用户态 · 线程 B, sub: 在运行队列里等, tone: blue }
messages:
  - { from: a, to: k, label: "时钟中断 / 系统调用：陷入内核", kind: sync, note: 1 }
  - { from: k, to: k, label: "保存 A 的全部寄存器", kind: self, note: 2 }
  - { from: k, to: k, label: "在运行队列里选下一个", kind: self, note: 3 }
  - { from: k, to: k, label: "切换页表、累计运行统计", kind: self, note: 4 }
  - { from: k, to: b, label: "恢复 B 的寄存器，回到用户态", kind: reply, note: 5 }
  - { from: b, to: b, label: "接着跑", kind: self, note: 6 }
```

第 1 到 5 步看得见、测得出，叫直接成本。第 6 步看不见，才是大头 —— B 开始跑的时候，缓存里装的全是 A 的工作集。

## 03 · 一次切换并不算慢

「线程切换慢」是一句被传过头的话。放几个参照系进去看：

```compare
first: 动作
head: [耗时 / 速率, 说明]
rows:
  - 一次线程切换（绑核）: ["1.2 ~ 1.5 μs", "直接成本部分"]
  - 一次线程切换（不绑核）: ["约 2.2 μs", "多了一次核间迁移"]
  - 64 KiB memcpy: ["约 3 μs", { text: "比一次切换还贵", tone: amber }]
  - 管道乒乓: ["约 40 万次 / 秒", "进程间通信的老基准"]
  - Go channel 乒乓: [{ text: "约 280 万次 / 秒", tone: green }, "同一台机器上，快了 7 倍左右"]
```

==单独一次微秒级的切换，在大多数场景里根本感知不到。==

真正杀人的是**规模**：十万个细粒度任务各占一条线程时，切换量随任务数线性增长，第 2 节的「缓存还债」跟着一起放大。慢的不是一次切换，而是「切换次数 × 任务数」。

## 04 · 第二条重量线：栈

线程的另一半重量不在切换，在**预留**。

```demo
widget: tuner
title: Linux 默认 8MiB 线程栈：虚拟预留 vs 实际常驻
actions: false
hint: 拖动滑块换线程数
config:
  param: { label: 线程数, unit: 条, values: [1000, 5000, 10000, 20000, 50000] }
  outputs:
    - { label: 虚拟地址空间预留, unit: GiB, values: [8, 40, 80, 160, 400], tone: amber }
    - { label: 实际常驻（浅栈估算）, unit: MiB, values: [8, 40, 80, 160, 400], tone: green }
```

==8MiB 是虚拟地址空间的预留，不是物理内存。== 页只在真正用到栈的时候才分配，所以 1 万条线程大约是 80GiB 虚拟空间、80MiB 物理内存。

但虚拟空间不是无限的，天花板就在这儿：

```compare
first: 平台
head: [默认线程栈, 把线程数卡在多少]
rows:
  - 32 位 Linux: ["2MiB（用户空间只有约 3GiB）", { text: "约 1500 条", tone: red }]
  - 64 位 JVM: ["1MB 固定", { text: "实测约 1.15 万条就 OOM", tone: red }]
  - 64 位 Linux: ["8MiB 虚拟预留", "虚拟空间宽裕，但物理内存和调度成本仍然在线"]
```

```callout
tone: violet
icon: 🔒
text: |
  **为什么线程不能像 G 那样「小了再长」？**

  因为线程栈的大小在**创建时一次定死**，内核不会在运行中帮你搬家。

  于是线程库只能按**最坏情况**预留 —— 递归深一点、大数组多一点，栈就得留够。
  预留本身不立刻花物理内存，但它锁死了数量上限，
  而且把「最坏情况是多少」这份估算责任，压给了写代码的人。
```

这两条重量线，正好对应后面要拆的两条路线：**切换路径**（第 ⑥ 篇的调度器）和**栈预留**（第 ③ 篇的可增长栈）。

---

```quiz
- q: 为什么说「栈随流走、堆随容器走」？这条分界线决定了什么？
  a: |
    栈是这条执行流自己的调用链，必须跟着它走，所以切换时要保存恢复；
    堆挂在进程上，不属于任何一条流，所以线程切换不用搬堆。
    而进程之间的隔离，恰恰是要用页表把堆整个隔开 ——
    这条分界线决定了「线程切换便宜、进程切换贵」这个成本差异。
- q: 8MiB 的线程栈，开一万条线程会立刻吃掉 80GiB 内存吗？
  a: |
    不会。8MiB 是虚拟地址空间的预留，页是按需分配的 ——
    真正触到那段栈才会分配物理页。一万条浅栈线程大约只占 80MiB 常驻内存。
    但预留仍然有意义：它锁死了虚拟空间能容纳多少条线程。
- q: 既然一次线程切换只要 1 点几微秒，为什么还说线程重？
  a: |
    因为重不在单次，在规模。加一个参照系就看出来了：64KiB 的 memcpy 要 3 微秒，
    比一次切换还贵。真正的问题是有十万个细粒度任务时，
    切换次数随任务数线性增长，而「缓存还债」这部分间接成本会同步放大。
```

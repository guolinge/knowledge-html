一台机器上：Docker / K8s / 容器 / 镜像到底谁压着谁

常见的分层图是错的 —— 它把「谁创建谁」「谁在内存里」「谁管谁」「谁依赖谁的代码」四种关系压成了一根竖轴。真相是两个平面加一个内核：管理平面和容器进程是兄弟，runc 只活一瞬间，而「容器」在内核里根本不是一个对象。

01那张「分层图」错在哪

你手上那份回答，把这几样东西叠成了一根竖轴：

Deployment → Pod → Container → Image → containerd + runc → Linux 内核 → 硬件

这张图里混了四种完全不同的关系，所以越看越糊：

关系谁和谁是长久的吗
谁创建谁镜像 → 容器 → Pod → Deployment创建完就结束了，不是持续关系
谁在内存里跑着dockerd / containerd / kubelet / 容器进程只有这个是「谁压着谁」
谁管谁Deployment 管 Pod，kubelet 管容器常驻的命令关系，但双方不一定在同一台机器上
谁依赖谁的代码containerd 调用 runc代码依赖，不是进程层级

还有一个更根本的错：runc 根本不是一层。 它只在「创建容器」那一瞬间存在，建完就退出了。

t = 2

containerd fork 出 runc

它要干的是调 clone / unshare / setns，把进程建出来

t = 3

runc 就退出了

活了一瞬间。它不是「容器进程运行的依赖」，只是「容器进程的接生婆」

t = 3 之后

真正留下来陪容器的是 containerd-shim

它才是容器进程的父进程，一直活到容器被删

看这条时间轴，比看任何分层图都清楚：一起吃住的和只来一趟的，长度差得很远。

创建、重启、删除：谁在，谁不在 点「下一步」或「自动跑」

02真实的样子：两个平面 + 一个内核

这张图上有三处值得盯着看：

  • containerd 和容器进程之间没有箭头：它们不是父子，是两个各自的进程
  • shim 的箭头是实线加粗的，那才是唯一的父子关系
  • 内核那一段标着 namespace / cgroup / 网络栈，这就是「容器」在系统里的全部痕迹

03那「容器」到底是个什么东西

直说：内核里没有「容器」这个对象。

它是一个纯约定俗成的说法，指代的是这么一组东西：

你在 docker ps 里看到的那一行，在内存里对应的就是这些
一个（组）普通进程 nginx、java，跟你在本机直接跑的一模一样
一组 namespace 标签 决定它能看见哪些别的进程、哪块网卡
一个 cgroup 决定它最多能用多少 CPU、内存、IO
一个 rootfs 镜像叠出来的只读根目录，加上一层可写层

docker run nginx 在你眼里是「启动了一个容器」，在系统眼里是「fork 一个进程，然后给这个进程挂上几样属性」。

这也解释了一件让你困惑的事：为什么 docker ps 看到的容器、ps aux 看到的 nginx 进程、kubectl get pods 看到的 Pod，是同一件事的三个说法。

视角看到的是什么同一个东西的不同包装
docker ps容器 ID + 名字 + 镜像给「那个进程」起了个人类友好的名字
ps auxnginx: master process这才是真实存在的东西：一个进程
lsns / systemd-cglsnamespace 列表 / cgroup 树那个进程身上挂的属性
kubectl get podsPod 名字 + 状态K8s 给一组共享标签的进程打的另一个名字

04一台机器上的进程家族树

按「谁 fork 了谁」画，比按「谁调用谁」画清楚得多：

  • systemd (PID 1) 机器上所有进程的根
    • kubelet 由 systemd 拉起 它不 fork 容器，只跟 containerd 说话
    • containerd 由 systemd 拉起 管理平面。它 fork 的是 shim，不是容器进程
      • containerd-shim 每个运行中的容器一个。它是容器进程真正的父进程
        • nginx 容器进程在这里。
      • containerd-shim 另一个容器的
        • java 它也是别人的孩子，不是你想象的那个层级

runc 不在这棵树里，因为它活不到你能 ps 到它的时候。 它在 shim 被创建的那一刻出现，建完进程就走。

🧬

「容器」和「Pod」都不在这棵树上，因为它们都不是进程。

它们是标签的集合：

  • 容器 = 一个进程 + 那四样属性（namespace / cgroup / rootfs / 自己的 shim）
  • Pod = 几个共享 Network / IPC / UTS namespace 的容器，再加一个 pause 容器当它们的共享骨架

所以「Pod 里有哪些容器」这个问题问得通， 而「Pod 进程的 PID 是多少」问不通：它自己没有 PID。

05那镜像呢

镜像不在内存里。它在磁盘上睡大觉：

第 1 站 镜像仓库（别的机器） 躺着
长什么样registry.example.com/backend:v1
在哪Harbor / Docker Hub / 云厂商的仓库

这一步只在「拉取」时发生，拉完就跟它没关系了

containerd 把它拉下来落到这台机器的磁盘上
第 2 站 节点磁盘 ==睡在这里，不在内存里==
解压后的层/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/
原始压缩包/var/lib/containerd/io.containerd.content.v1.content/
用 Docker 的话/var/lib/docker/overlay2/另一套目录

镜像层是只读的，所有容器共用同一份

创建容器时叠成一个文件系统给进程看
第 3 站 容器进程眼里的根目录 只是挂载视图
看到的是一个完整的根目录 /
实际是几个只读层叠起来 + 一层可写层写时才复制

这一站才和内存有关系。但进内存的是「被读到的那些块」，不是整个镜像

所以「镜像跑起来需要容器吗」这个问题，答案要分两半：

说法对不对准确的问法
镜像运行起来需要容器大致对，但不准确镜像自己永远不会运行。真正运行的是进程，容器只是这个进程的包装说法
一个镜像可以有多个容器对准确说：同一份只读镜像，可以给多个进程当根目录。100 个副本 = 一份镜像 + 100 个进程
容器是镜像的实例对，但别当成面向对象没有「类」和「对象」那种实体；就是同一批只读层被挂到不同的进程上

06Docker 单机 和 K8s 节点，差在哪

有什么只管 Docker 的机器K8s 工作节点
容器进程有有，一模一样
containerd有有
containerd-shim有有，一模一样
runc有，一样是一次性的有，一样是一次性的
dockerd有没有 —— K8s 不需要它
docker CLI有没有
kubelet没有有
pause 容器没有每个 Pod 一个

底下三层完全一样。 K8s 不是「在 Docker 之上加了一层」，而是换掉了最上面那层用户界面：

Docker 单机的入口
K8s 节点的入口
这两边一样
docker CLI 你说 docker run
kubectl 你说 kubectl apply
dockerd 把命令翻译一下，再往下交
kubelet 盯着期望状态，有差距就去补
containerd 一个节点一个
containerd-shim 每个容器一个
容器进程 nginx / java

07Pod 多出来的那个东西

K8s 比 Docker 多出来的核心概念是 Pod，而 Pod 在内存里的实现，靠的是一个几乎什么都不干的容器：

一个 Pod 在内存里 = 一个 pause 容器 + 若干业务容器
pause 容器 镜像只有几百 KB，跑起来就干一件事：sleep
nginx 容器 共享 pause 的 Network namespace
sidecar 容器 共享同一个 Network namespace
为什么要有它 它持有那组共享的 namespace。业务容器崩了重建，Pod 的网络身份不变

所以同一个 Pod 里的两个容器，localhost 能互相访问，因为它们共用同一张网卡，不是因为它们之间有网络。

📦

从这里就能看出 Pod 的定位：它不是「更大的容器」，是「共享命名空间的一小组容器」。

它带来的实际约束是：

  • 同一 Pod 里的容器必须被调度到同一台机器上（因为要共享 namespace）
  • 它们一起生、一起死（生命周期绑在一起）
  • 端口是按 Pod 分的：同一个 Pod 里两个容器不能都监听 80

这三条都不是人为规定，是「共享 namespace」这个实现方式的直接推论。

containerd 和容器进程是什么关系？

不是父子，也不是上下级。containerd 是节点级的管理进程，它 fork 出的是 shim； shim 才是容器进程的父进程（负责 waitpid 收尸、转发 stdio、汇报退出码）。 containerd 直接和容器进程之间没有任何层级关系，它们都只是内核上的普通进程。 这也是为什么重启 containerd 不会影响正在运行的容器：顶着的是 shim。

runc 在系统里长期存在吗？

不存在。它是「一次性」的：containerd 在创建容器时 fork 出它， 它调 clone / unshare / setns 把进程建出来、套上 namespace 和 cgroup， 然后就退出了。它更像接生婆而不是保姆，所以任何把它画成「一层」的图都是错的。

「容器」在 Linux 里对应哪个内核对象？

没有这样一个对象。内核里没有 container 这个东西， 「容器」是一个约定俗成的说法，指代「一个（组）普通进程 + 一组 namespace 标签

  • 一个 cgroup 限额 + 一个 rootfs」这一整包。 所以 docker ps 看到的条目、ps 看到的 nginx 进程、kubectl get pods 看到的 Pod， 是同一个东西的三种不同命名方式。
我一个镜像起了 3 个副本，磁盘上会存 3 份镜像吗？

不会。镜像层是只读的，3 个副本共用同一份。 它们各自的差别只在那一层「可写层」，而且写时才复制。 所以磁盘占用是「一份镜像 + 三份改动」，不是三份镜像。

cd 进一个容器里改的东西，会在别的副本里出现吗？

不会。你改的落在那个容器自己的可写层上，只对该容器可见。 镜像的那些层始终是只读的，这是容器能秒级启动、能复用的前提。 要持久化得挂 volume，要固化成新镜像得 commit / build。

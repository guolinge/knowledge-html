上一篇把现网条件翻成了我们的草稿。这一篇做第一次真正的对拍：拿现网的 SQL 当标准答案，逐字比我们编译出来的谓词。

先看这一篇要用的原料 —— 一条现网记录 crowdFilter 1241598 的两侧：

📦

现网那一行给的东西：

{"op":"=","name":"futu_hk_account_basic_customer_type","value":"Organization"}

select count(1) as `count` from `user_portrait`
 where (`futu_hk_account_basic_customer_type` = 'Organization')

我们编译器对同一条条件写出来的（同一个字段、同一个值）：

SELECT `u`.`uid` AS `uid` FROM `user_portrait` AS `u`
 WHERE ((`u`.`futu_hk_account_basic_customer_type` = 'Organization'))

两边的差异只有三处：表限定名（u.）、两边的括号层数、以及外面套没套 count(1) 的壳。 这张单子就是这一篇要处理的东西。

要抹的就这六条。抹平之后剩下的那一段，就是「字段 + 操作符 + 值」这一层的编译能力 —— 它错了后面全错，所以先验它。

归一化的红线：只改「已登记为表象差异」的东西。

上面六条每一条都能指回一份差异文档。而语义层面的改写（把现网的 not in 改写成 not exists） 一律不做 —— 那等于替编译器作判断，「一致」就变得毫无意义。

02只比「单叶子 + 画像」：另外两种比法都注定失败

能逐字比

单叶子 · 画像

两边都是「这一列怎么比」，只差写法。归一化后应当完全相同 —— 这一篇比的就是它。

不能比文本

单叶子 · 关系

现网写成 uid not in (select uid from 关系表 where …)，我们写成主表上的 NOT EXISTS 子查询 —— 形状不同、语义可以等价。留给第三篇比结果。

不能比文本

多叶子（AND / OR）

现网用 union all + having count = N 表达 AND/OR，我们是单条 WHERE。没有一一对应。也留给第三篇。

还有第三种失败来源：这条记录里有我不想翻、翻不了的叶子。真实例子（现网 tag 846335）：

-- 现网这条记录的 SQL 里，除了特征条件，还混着一个「离线用户群」条件
select uid from user_portrait where (特征条件)
union all select uid from user_portrait where uid in (
  select uid from crowds where (crowd_id = '29178d-20260630095237-crowd' …))
--                                 ↑ 这个条件我们没翻，比出来的差异全是它造成的，必须整条排除

所以本步的取值条件是三个同时成立：翻译后正好一个叶子、该叶子是画像、这条记录里没有翻不了的叶子。

比到后面会发现：不一致的那些大多不是编译器的错，而是记录里还有别的条件，或者两边口径本来就不同。四类都要排除 并计数：

第 ② 步的结论

  • 405 条可比样本，谓词逐字一致 100% —— 「字段 + 操作符 + 值 + 时间窗口」这一层的编译没问题
  • 一致率从 27% 提到 100%，靠的是修 3 个工具 bug + 6 条归一化 + 4 类假差异排除
  • 排除掉的四类都记了数与原因，不是默默丢掉
  • 这一层验不了 OR / 否定 / 计数：它们结构不同，只能靠第三篇比 uid 集合

这一篇的边界（别把它当全绿）：一致只发生在「单叶子 + 画像 + 无跳过叶子」这个交集里；关系与多叶子一条都没验。

07自测

归一化的边界在哪？举一个「绝不能抹」的例子。

只抹平已登记为表象差异的东西：表限定名、括号层数、值引号、UDF 求值时机、关键词大小写、外层包装。 绝不能做的例子：把现网的 uid not in (select uid …) 改写成我们的 NOT EXISTS —— 那是在替编译器作判断，改完之后「一致」就不再证明任何东西了。

一条记录里如果有我们翻不了的叶子，为什么必须整条排除？

因为现网编译那条记录时，把那个叶子也编译进了 SQL（例如 uid in (select uid from crowds …)）。 我们这边没有它，于是两侧比的不是同一件事 —— 差异全来自那个没翻的条件， 留下来只会污染结论。真实的例子是 tag 846335，它的 SQL 里混着一个离线用户群条件。

一致率从 27% 到 100% 的三次修正，分别修的是什么？

① 去壳正则没考虑反引号 → 拿「谓词」比了「整个 uid in (select …) 包装」（27% → 54%）； ② 关键词大小写不一致（not in vs NOT IN）→ 归一化时统一关键词、不碰字符串值（→ 95.8%）； ③ 给 double 套的 CAST(… AS DECIMAL) 与现网裸字面量的差异（→ 100%）。 三次都不是编译器的问题，而是我的比对工具写错了。

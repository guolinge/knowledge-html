## 01 · 两种说法都对，只是站在不同层

问「进程和线程什么关系」，你会听到两种答案：

```compare
first: 说法
head: [谁在说, 它管用在哪]
rows:
  - 「进程包含线程」: ["应用层的**嵌套视角**", "资源生命周期挂在进程上：`kill` 掉进程，它名下所有线程一起消失"]
  - 「多个 task 共享一组资源」: ["内核的**实现视角**", "调度器面前没有进程，只有 task"]
```

==两种说法不矛盾。== 应用层的那个「进程」，就是内核里
**共享同一资源域的那组 task**；「进程」是给这组 task 起的名字。

## 为什么两个视角都得留着

```callout
tone: violet
icon: 👁
text: |
  **应用层视角好用，是因为资源生命周期真的挂在进程上。**

  你 `kill` 一个 PID，内核去遍历它的线程组、把每一个 task 都收掉 ——
  这个动作只有在「进程是一个整体」的视角下才说得通。

  **内核视角才是真相，因为调度器不认识「进程」。**

  它手上是一张运行队列，里面是 task。选下一个跑的时候，
  它不会问「这是哪个进程的线程」，只按 task 自己的权重和时间片决定。

  ++两层同时成立，正是 5.2 节那张坐标图想说的东西。++
```

## 02 · 两个正交维度

把上面两种说法拆开，会得到两个**互相独立**的问题：

```compare
first: 维度
head: [它回答什么, 由什么承载]
rows:
  - 资源域: ["==我拥有什么==", "地址空间、打开文件、凭证、命名空间"]
  - 执行流: ["==我从哪里继续执行==", "PC、寄存器、栈"]
```

「正交」的意思是：**它们可以任意组合**。

```compare
first: 组合
head: [资源域, 执行流, 这是谁]
rows:
  - 各一份: ["一条主栈", "进程"]
  - 共享一份: ["每线程一条", "线程"]
  - 几乎没有: [{ text: "只有内核栈", tone: amber }, "内核线程"]
```

```callout
tone: amber
icon: 📐
text: |
  **两个维度各自的边界也很清楚：**

  | 维度 | 不只是 | 而是 |
  |---|---|---|
  | 资源域 | 不只是内存 | 凭证决定**你是谁**，namespace 决定**你看到哪片世界** —— 它们是权限与容器机制的接口 |
  | 执行流 | 不只是「能跑」 | ==能被内核**独立调度**、**独立阻塞**==，才是它与协程的分界线 |

  ++第二行是关键：协程也能跑、也有栈，但内核不认识它 ——
  用户态调度器让它让出，它就得让出。++
```

## 03 · 把四个概念摆到同一根轴上

```demo
widget: isolation-spectrum
title: 一把尺子上的四个位置
actions: false
hint: 点一个，看它的三行账
config:
  selected: thread
```

点一遍你会发现：这四个概念平时是**分开背的**，但它们其实是
**同一根刻度尺上的四个位置** —— 共享得越来越多，调度得越来越轻。

而两条最容易记混的推论，看图就能分辨：

- ==协程省的是**调度开销**，不是故障域。== 它还是跑在同一个进程里，
  一个协程写坏内存，整个进程陪葬。
- ==容器和线程都「轻」，但轻的完全不是一回事。==
  容器共享的是**内核**、切掉的是**命名空间**；线程共享的是**进程资源域**。

  - 堆 / 全局数据: ["独占", "共享"]

  - 寄存器 / PC: ["一组", "每线程一组"]
  - 文件描述符: ["独立一套", "共享"]
  - 信号处置: ["独立", "共享"]
  - 信号掩码: [{ text: "进程级", tone: amber }, { text: "每线程私有", tone: green }]
  - 调度优先级: [{ text: "进程级", tone: amber }, { text: "每线程可设", tone: green }]
  - CPU affinity: [{ text: "进程级", tone: amber }, { text: "Linux 下每线程", tone: green }]

「内核只认识 task」在接口上的表现。进程级的那个说法是教科书简化。

## 05 · 三条边界：真正决定差异的地方

资源域和执行流的差异，落到工程上就是三条线：

### 边界一 · 故障域

```flow
grid: true
groups:
  - { id: mp, label: "多进程：A 崩了，B 照跑", tone: green }
  - { id: mt, label: "多线程：T1 崩了，可能全进程陪葬", tone: red }
nodes:
  - { id: pa, label: "进程 A", sub: "段错误", row: 0, tone: red, group: mp }
  - { id: pb, label: "进程 B", sub: "完全无感，还能单独重启", row: 1, tone: green, group: mp }
  - { id: t1, label: "线程 T1", sub: "写坏共享堆 / 踩了别人的栈", row: 0, tone: red, group: mt }
  - { id: t2, label: "线程 T2", sub: "读到脏数据，或者一起退出", row: 1, tone: red, group: mt }
edges:
  - { from: pa, to: pb, label: "不波及" }
  - { from: t1, to: t2, label: "会波及" }
```

进程有独立地址空间，非法访问被页表拦下；线程共享堆与栈区，
一个线程写坏共享数据，整个进程陪葬。

> **Chrome 给每个标签页独立进程而不是线程，动机正是这一条。**
> 单个渲染器的 bug 或失控脚本，不应该拖垮整个浏览器 —— 隔离优先于开销。

### 边界二 · 数据一致性

```compare
first: 共享方式
head: [要付出什么, 麻烦在哪]
rows:
  - 进程间 · 走 IPC: ["序列化 + 拷贝 + 协议", "管道、共享内存、消息队列 —— 但**有显式的消息边界**"]
  - 线程间 · 直接读写: [{ text: "数据竞争、锁、原子操作、内存序", tone: red }, "省了拷贝，但**可见性比锁更难缠**"]
```

```callout
tone: red
icon: 👻
text: |
  **「可见性」为什么比锁更难缠？**

  因为线程 B 读到的，**未必是线程 A 刚写的值** ——
  编译优化和 CPU 缓存都可能在中间重排指令。

  ==IPC 好歹有显式的消息边界（收到了就是收到了），共享内存没有。==

  ++这就是「加了锁就万事大吉」这句话不成立的原因：
  锁解决互斥，不解决可见性。++
```

### 边界三 · 调度成本

```compare
first: 项
head: [多进程, 多线程]
rows:
  - 地址空间: ["必换页表", "不换"]
  - TLB: [{ text: "按 PCID / ASID 可以保留", tone: green }, "直接复用"]
  - 缓存工作集: [{ text: "全部重新热身", tone: red }, { text: "**仍然**要重新热身", tone: red }]
  - 创建成本: ["高（资源整套）", "低（只新建执行流）"]
```

```callout
tone: amber
icon: 🧊
text: |
  **结论是「线程更省，但省的主要是地址空间切换那一块」。**

  缓存污染两头都逃不掉：不同线程的**工作集本来就不同**，
  就算省掉了页表切换，新任务的活还是要把旧任务的缓存挤出去。

  ++所以「进程切换比线程切换慢几个数量级」是过度简化 ——
  现代 CPU 用 PCID/ASID 给 TLB 项打进程标签，进程切换不必全量刷 TLB，
  两者差距在缩小。量级参考：线程切换约 1.2~1.5 微秒，
  goroutine 切换约 170 纳秒（完全不进内核）。++
```

## 06 · 谱系：两端是同一条尺子

把坐标拉到底，四个概念排成一条连续的谱：

```compare
first: 位置
head: [共享什么, 由谁调度, 故障传到哪]
rows:
  - ==容器==: ["切出命名空间，共享内核", "内核", "容器内，不波及宿主机"]
  - ==进程==: ["各一份资源域", "内核", "进程内"]
  - ==线程==: ["共享进程资源域", "内核", "同进程的线程共担"]
  - ==协程==: [{ text: "共享一切", tone: red }, { text: "用户态调度器", tone: amber }, { text: "整个进程", tone: red }]
```

==一眼看穿：从容器到协程,是「共享越来越多、调度越来越轻」的连续谱。==

```callout
tone: violet
icon: 🪜
text: |
  **四个概念，四个问题：**

  | 概念 | 回答的问题 |
  |---|---|
  | 进程 | 我**拥有什么** |
  | 线程 | 我**从哪里继续执行** |
  | 协程 | 我**等的时候还能干嘛** |
  | 容器 | **谁和谁**共享一个世界 |

  ++四个问题共用同一把刻度尺：**共享与隔离**。++

  理解了这把尺子，再学调度器、虚拟内存、容器原理的时候，
  每个新概念都能在谱系上找到自己的位置 —— 而不是当一个孤立的知识点记住。
```

```quiz
- q: 「进程包含线程」和「多个 task 共享一组资源」，哪句对？
  a: |
    都对，只是站在不同抽象层。
    「进程包含线程」是应用层的嵌套视角，好用是因为资源生命周期真的挂在进程上 ——
    kill 一个 PID，内核会遍历整个线程组把它收掉。
    「多个 task 共享资源」是内核实现视角，才是真相，因为调度器面前根本没有进程，只有 task。
    两者不矛盾：应用层的「进程」，就是内核里共享同一资源域的那组 task。
- q: 协程和线程都能跑、都有栈，分界线在哪？
  a: |
    在「能不能被内核独立调度、独立阻塞」。
    线程是内核认识的对象，能被内核独立调度、独立阻塞、独立抢占；
    协程内核看不见，让不让出由用户态调度器说了算。
    所以要警惕一个常见误解：协程省的是**调度开销**（goroutine 切换约 170 纳秒，
    完全不进内核），不是故障域 —— 它还是跑在同一个进程里，一个协程写坏内存整个进程陪葬。
- q: 「加了锁就万事大吉」这句话哪里不成立？
  a: |
    锁解决互斥，但不解决可见性。
    线程 B 读到的未必是线程 A 刚写的值 —— 编译优化和 CPU 缓存都可能在中间重排指令。
    进程间走 IPC 反而没这个问题，因为消息有显式的边界（收到了就是收到了）；
    共享内存没有边界，所以除了锁还要处理原子操作与内存序。
    这也是「线程共享省了拷贝、却付出了更难的代价」的具体含义。
- q: 为什么说线程切换「省一点」而不是「省一个数量级」？
  a: |
    线程节省的只是地址空间切换那一块（不换页表），缓存工作集照样要重新热身 ——
    因为不同线程的工作集本来就不同，新任务跑起来还是要把旧任务的缓存挤出去。
    而且现代 CPU 用 PCID/ASID 给 TLB 项打进程标签，
    进程切换不必全量刷 TLB，两者的差距还在缩小。
    量级参考：线程切换约 1.2~1.5 微秒，goroutine 切换约 170 纳秒。
- q: 容器和线程都说「轻」，轻的是同一回事吗？
  a: |
    不是，这是最容易混的一句。
    线程轻，是因为它共享进程资源域 —— 不新建地址空间、不重建文件表，只复制几个指针。
    容器轻，是因为它共享宿主机的**内核** —— 不用为每个容器启动一个操作系统。
    两者的隔离手段也完全不同：线程完全不隔离（共享地址空间），
    容器用 namespace 切出进程视图、文件树和网络栈。
    所以容器是「一组进程的包装」，是进程概念的延伸，不是执行流。
```

CAS 是缓存一致性协议实现的吗

不是一条协议就够了。一致性协议管「此刻谁能写这条缓存行」，原子指令管「比较和写入之间插不进别的核」，一致性系统管「同时来的两个请求谁先」，外层代码管「失败了再来一次」。四层各管一段，缺一段就没有 CAS。附两个核抢同一行的完整时序、MESI 状态怎么走，以及本机反汇编里 CAS 与 LL/SC 两条路。

CAS 失败之后，重新读一遍的那一步写在外层代码里。接着往下问：那一条 CAS 本身的原子性，是谁保证的？

不是一条协议就够。协议管「此刻谁能写这条缓存行」，原子指令管「比较和写入之间插不进别的核」，一致性系统管「同时来的两个请求谁先」，外层代码管「失败了再来一次」。四件事各管一段，缺一段就没有 CAS。

00这次追问的八个问题

问题原文八段答案没有搬进来，每个问题对应下面的一节

问题原样保留，只截掉了过长句子中间的举例。

1 · 从一句晦涩的话开始

「重试」不是等待某个完成标志。CPU1 不需要先读取某个「CPU0 已完成」的标志。每次重试都重新发起相应的缓存访问……

上面这段话在说什么呀？为什么语言组织得这么晦涩？

2 · 底层失败，外层重试

这个过程，我可以理解为是由于缓存一致性协议的存在：假如 CPU A 已经获得了这个内存的独占权，此时 CPU B 想去修改，它就会执行 CAS 操作。但是它会发现缓存已经失效，或者在想修改的时候，一致性调度系统会告诉它现在有人在修改，所以它就直接失败了。

所以这个过程可以分两部分：底层部分，CPU B 在失败之后是不会重试的；业务代码部分，在外面才有逻辑去控制它重试。对吗？

3 · 底层操作和状态转移是一回事吗

CAS 的底层操作，跟我们说的缓存一致性协议具体的状态转移不是同一个东西，对吧？

在底层操作中，只要读了值跟预期的不一样，那这个读到的值肯定是现在已经修改完的值，不可能读到一个旧值，对吧？所以 CAS 的操作一定发生在这个值被别的核心修改完之后，我可以这么理解吗？

4 · 两个核同时读到、同时改

CAS 只是保证读值是预期的，然后修改值，再把值写到原来的那个地址上，这一套流程是完整的。但是，如果两个核心在读值的时候同时读到了值，然后同时修改，那岂不是会发生混乱，不是预期的效果？

5 · A 还没写，B 读到了旧值

比如说 A 发现 X 是 10，准备写入 11 的时候，B 刚好去读这个 X。此时 A 还没写入 11，B 读到发现它还是 10，B 也准备写，怎么办？

6 · 画个时序图

你能画一个时序图吗？把 CAS、业务代码，还有底层缓存一致性这个逻辑的时序画出来。我知道这个东西很复杂，如果一张图画不下，你分开几张来画。

7 · 协议和 CAS 是什么关系

你没有挑明 CAS 跟缓存一致性协议，或者说这个缓存调度器的关系，它们的关系是什么？是 CAS 由它们两个来实现吗？也就是说，缓存一致性协议和缓存调度器的机制是 CAS 的底层机制，我能这么理解吗？

8 · 协议只服务 CAS 吗

我可以理解成，其他的机制也能使用缓存一致性协议，只是缓存一致性协议加上 CAS，能保证这一个原子操作的顺利发生。但是，缓存一致性协议不是专门服务于 CAS 的，对吧？

01四层各管一段

一次成功的 CAS，路径上只有四件事：

  1. 外层代码读到 10，算出 11，发起一条 CAS，把读到的 10 作为 expected（期望值）传进去。
  2. 这条指令要写 x，先要 x 所在缓存行的独占权。
  3. 一致性系统决定这条行现在归谁：本核拿走，别的核的副本作废。
  4. 拿到独占之后，指令完成比较和条件写入，交回 true。

失败只改最后一步：交回 false，外层代码回到第 1 步。整条路径上没有一步在读「另一个核完成了没有」的标志；冲突只在比较那一步暴露出来：值不是 expected，这次尝试就结束。

四层分开看，实际的好处是出问题知道去哪找。「CAS 一直返回 false」和「计数器少了一半」听起来都像并发出了问题，原因却在不同的层：前者是抢的人太多，后者是读和写没包在一起。第 07 节把这份对照列成表。

图上把一致性系统画成一条独立的带，是因为它要同时和两个核打交道。真实的部件分散在各处：一致性点（末级缓存或目录）、互连、每个核的缓存控制器。没有一个叫「缓存调度器」的中央部件，一次请求也不是被它统一调度的。

02它保证写权限，不管你连着做的那三步

一致性协议要保证的，工程上写成两条：

  • 一个核写了某个地址，别的核之后读到的是新值（write propagation）；
  • 同一个地址的多次写，所有核看到的顺序一致（write serialization）。

两条都只谈一个地址的读和写。没有一条谈「你连着做的三个动作要一起生效」。所以下面这段，在一致性协议完全正常的情况下也会丢更新：

var plain int64

for i := 0; i < 8; i++ {
    go func() {
        for j := 0; j < 200000; j++ {
            plain = plain + 1     // 读、加一、写回
        }
    }()
}

本机跑四次（Apple M4 · Go 1.26.2）：

写法四次运行数到的次数丢了多少
8 个 goroutine 各自 plain = plain + 138 万 ~ 54 万106 万 ~ 122 万
同样的加法，改成 CAS 循环160 万，四次都一样0

每次加一都是一次合法的读、一次合法的写，全程都在一致性协议下。丢掉的那部分不是「某次写没生效」，是很多次「读到的值已经被别人改过了」。

本机反汇编里，普通加一就是这样三条：

; 普通 x = x + 1（otool，arm64）
ldr  x1, [x0]        ; 读
add  x1, x1, #1      ; 算
str  x1, [x0]        ; 写

三条指令之间，任何一条别的核的写都可以插进来。一致性协议保证每条 ldr / str 看到的是当时的最新副本，它不保证这三条属于同一次加一。

💡

一致性协议让每一次读、每一次写都是对的；它管不了这些读写要不要一起生效。

⚠

M 状态不等于原子性。

M 只说明这条行此刻只有本核一份可写副本、内存里那份是旧的。它不是一把持续到三步做完的锁：中间别的核可以来要这条行，这份副本被作废；等 str 执行时再把独占拿回来，写下去的就是算旧了的值。

03它不是为 CAS 造的

每一次走缓存的普通读、普通写，它都在工作。它不区分这次访问来自普通读、普通写还是原子指令，只回答「这条行现在在谁那里、别的副本要不要作废」。

  • 缓存一致性协议 管一条缓存行的副本、写权限和访问先后
    • 普通读 没有有效副本就去取；取到的是当前最新那份
    • 普通写 先拿独占，把别的副本置 I，再写
    • 原子读改写 CAS / 交换 / 取加 / test-and-set 都走这条
    • LL/SC 读时打标记，写时检查标记还在不在
    • 锁 mutex 的第一步也是一次原子读改写
    • 伪共享 两个变量同一条行，两边轮流抢写权

这张树里只有「原子读改写」和「LL/SC」两支与 CAS 直接相关（区别在第 06 节）；其余四支跟 CAS 没有关系，协议照样为它们工作。

CAS 是使用者里要求最高的一个。普通写只要「拿到写权限，然后写」；CAS 还要求拿到之后不许交出去。后面这一条不是协议给的，是原子指令执行时加的。

🧭

反过来也不成立：不是有了一致性协议就有了 CAS。

协议只保证同一时刻没有两个核都拿着可写副本，它不会把任意几条指令粘成一条。要在它上面得到 CAS，还得有一条会「占住不放」的原子指令。

04那条指令内部没有缝

现在回到那个具体问题：A 已经发现 x 是 10、准备写 11，B 这时候去读，读到 10，也准备写，怎么办？

先分清 B 的那次读排在哪儿。

B 的读排在哪儿B 看到什么会怎样
A 的 CAS 之前10正常。B 之后自己的 CAS 会被排到 A 后面，那时才决定成败
插进「比较成功、还没写」的中间看不到这个位置这一段对别的核不可分割，只有改前和改后两个状态
A 的 CAS 之后11如果 B 拿 10 当 expected，它的 CAS 必然失败

中间那一行是关键：CAS 的「比较」和「写入」对其他核是一个动作。硬件内部当然要花时间，但在这条行的访问顺序里，别的核的冲突操作只能排在它前面或后面，不能插进中间。

把 CAS 拆成「比较 → 准备写入 → 写入」，是为了讲解。Intel 手册里 CMPXCHG 的伪代码是（accumulator 里放 expected，DEST 是内存里的操作数）：

TEMP := DEST
IF accumulator = TEMP
    THEN ZF := 1; DEST := SRC;
    ELSE ZF := 0; accumulator := TEMP; DEST := TEMP;
FI

加上 LOCK 前缀之后，这一整段是一个原子操作。手册还写了一句容易漏掉的：比较失败时目标操作数也会被写一次（把旧值写回去），「处理器不会只产生 locked read 而不产生 locked write」。所以一次失败的 CAS 也不是一次纯读。

🧱

原子性以缓存行为单位。

操作数落在一条行里，处理器锁的是这条行的副本：P6 之后一般不再拉 LOCK# 总线信号，由缓存一致性机制保证这一条指令对内存是原子的（Intel 手册的原话）。跨两条行，或者内存不可缓存，就只能退回去锁总线；按 Linux 内核文档的记法，这样的代价是几千个周期，还会挡住其他核的访存。

所以对齐、以及「别把热点变量挤在一行」，影响的不只是这一个核的速度。

05两个 CAS 同时到，谁先

两个核可以同时读到 10，也可以同时在寄存器里算出 11。它们不能同时成功，因为两个 CAS 会在一致性点上被排出一个先后。

CPU ACAS(x, 10, 11)
一致性系统仲裁 + 归属 + 失效
CPU BCAS(x, 10, 11)
B 的循环外层代码
1我要这行的独占权
2我也要
3先 A 后 B
4授予 M，B 的副本置 I
510 == 10，写 11
6原子操作结束
7轮到 B，最新值是 11
811 ≠ 10，失败
9交回 false
10重读再算

拆开看只有三件事：请求、先后、数据。B 不是在「想写的时候被告知有人在改」，它是排到后面、拿到 11 之后自己比较出来的。

把两个核的副本状态顺着这条时间线列出来：

时刻 A 的副本 B 的副本 这条行的写权限在谁手上
一开始 S · 10 S · 10 谁都没有
两个核都要写 申请独占 申请独占 一致性点在排先后
A 先拿到 M · 10 I A
A 比较并写入 M · 11 I A
轮到 B I M · 11 B

第 3、4 行：A 拿到独占时，B 的副本已经置 I 了。B 不是从自己那份失效副本里读，也不是一直等下去；它的请求排在 A 这一段之后，拿到的是带 11 的那份。它拿 10 去比，比不上，返回 false。

（x86 上这一次失败的尝试也要过一遍写周期，见第 04 节手册那句。）

🎯

失败不是被拦下来的，是比较出来的。

⚠

「一致性系统告诉它有人在改，所以直接失败」不成立。

仲裁只排先后，不发「有人在改」的通知。CAS 只有两种结局：拿到行之后值等于 expected（写），或者不等于（不写）。两种都要先把行拿到手。

⏱

读到 11 也不等于「拿到了绝对最新的值」。

一致性协议只保证同一个地址的写有一个所有核都遵守的顺序；CAS 看到的是这个顺序里排在它前面的最后一个值。软件拿到 false 的时候，那条行可能已经被改成了 12。

同一件事还有另一面：CAS 只比较值。这条行如果从 10 改成 11 又改回 10，最后那次 CAS 会成功，就像中间什么都没发生。这叫 ABA。要识别它，得让比较的对象带上版本号：把版本号和值塞进同一个字，或者换成带戳的引用。

主内存里可能还是 10。B 不会因此读到 10：协议保证后续的读拿到最新副本，失效的那份不会被读。数据具体从哪里来（另一个核的缓存、共享的末级缓存、内存），取决于实现。

先后只保证有一个顺序，不保证轮流。某个核可能连续输很多次；重试只保证每次尝试有确定的结果，不保证最终能成功。

06CAS 与 LL/SC：两条路，两种失败

前面讲的都是 CAS 类指令：一条指令内部完成「比较 + 条件写」。还有一类实现用两条指令拼出同一个语义，叫 LL/SC（load-linked / store-conditional）。

Arm 的叫法：

  • LDXR：读一个值，同时把这个物理地址标成「我读过」；
  • STXR：只有当标记还在时才写，成功返回 0，没写返回 1。

标记什么时候没了：别的核写了这个地址、中间发生了上下文切换，或者实现自己判断这次不保险。

本机把 atomic.CompareAndSwapInt64 编出来的指令是这样的（注释是后加的）：

ldar   x2, [x0]            ; 读当前值
add    x1, x2, x1          ; 算出 new
ldrb   w3, [x27, #0x4aa]   ; 一个全局的 CPU 特性字节（省了算页地址的 adrp）
tbz    w3, #0, slow        ; 没有 LSE 就走慢路径
mov    x27, x2
casal  x27, x1, [x0]       ; 有 LSE：一条指令完成比较 + 条件写
cmp    x27, x2
cset   x3, eq
b      done
slow:
ldaxr  x27, [x0]           ; 没有 LSE：读，并打下独占标记
cmp    x27, x2
b.ne   give_up
stlxr  w27, x1, [x0]       ; 标记还在才写，返回 0 / 1
cbnz   w27, slow           ; 没写成，回到 ldaxr 再来一次
give_up:
cset   x3, eq
done:
mov    x0, x3
ret

从这段里能读出两件事。

第一，没有 call、没有 svc：最后一条 ret 就回去了。它是一条用户态指令序列，不进内核，失败之后退回的也是你自己那层代码。

第二，同一个 CompareAndSwap 编出了两条路。先查一个 CPU 特性字节：有这个扩展（Armv8.1 的 LSE 原子指令）就走一条 casal；没有就走 ldaxr / stlxr 那一对，写不成时 cbnz 跳回 ldaxr。这两种实现都是 Arm 架构允许的，同一份 Go 代码要同时跑在新旧核上。

对比项CAS 类（x86、arm64 LSE）LL/SC 类（老 Arm、RISC-V）
几条指令1 条2 条
成功条件当前值等于 expected读时打的标记还在
失败的常见原因值已经被改过标记被别的写清掉；也可能无故失败
谁重新读一遍外层代码外层代码；配对重试可能写在编译器生成的序列里
⚠

「CAS 失败 = 有人先改了值」只在 CAS 类指令上成立。

STXR 返回 1 时，值可能根本没变，变的只是标记。C++ 的 compare_exchange_weak 允许无故失败，就是给这类平台留的口子，所以它必须放在循环里。

关于「底层到底重不重试」，要分清三段：

谁在重试 重试的是哪一段 会不会替你重算
硬件 不重试。一次 CAS 就是一次尝试 —
编译器 / 库生成的序列 LL/SC 那一对：ldaxr 读、stlxr 写（本机那条 cbnz） 不会
外层代码 整个循环：重读、重算、再试 会

07三件事别混：一致性、原子性、顺序

这三件事都能让并发代码出错，但由不同的机制保证，症状也不同。

事项它管什么谁保证出问题时的症状
缓存一致性同一条缓存行在多个核里的副本，以及谁能写一致性协议 + 互连读到已经失效的旧副本（正常不该发生）
原子性一次读改写能不能被别的核插进来原子指令 + 独占的那一段两个核都以为自己加了一次，结果只加了一次
内存顺序不同地址的读写，别的核按什么顺序看见acquire / release、屏障、语言内存模型flag 已经可见，flag 指向的 data 还是旧的
重试策略失败了要不要再来、来几次、要不要让出外层代码或库CAS 循环一直空转，CPU 占满但没进展

缓存一致性和原子性都正常，内存顺序照样可以出错：两个核都按自己的代码顺序执行，别的核看到的却是另一个顺序。这一段在 锁为什么慢：写缓冲、失效队列和内存屏障 里拆过。

出问题时，按症状先定位到层：

看到的症状先查哪一层常见原因
计数少了、状态被覆盖原子性读-算-写没包在一条原子操作里
CAS 一直返回 false重试策略抢的人太多、伪共享；换原子加或锁，或者加退避

08自测

一条 CAS 的原子性，是一致性协议保证的吗？

协议只保证一件事：同一时刻没有两个核拿着同一条缓存行的可写副本，一个核写过之后别的核不会读到失效副本。 「比较和写入之间插不进别的核」是原子指令执行时加的：它拿到独占权之后不交出去，直到这一条指令结束。 至于失败了要不要再来，协议和指令都不管，写在最外层那个循环里。合起来才是 CAS。

两个核同时执行 CAS(x, 10, 11)，会不会都成功？

不会。两个核可以同时读到 10，也可以同时算出 11，但两个 CAS 会在一致性点上被排出一个先后。 先到的那个拿到独占权，看到 10，写入 11；后到的那个拿到的行里已经是 11，和 expected 的 10 比不过，返回 false。 最终 x 是 11，不是 12。要让两个加一都生效，失败的那个必须回到外层重新读 11、算 12、再试一次。

A 的 CAS 已经比较成功、还没写入，B 这时候能读到 10 吗？

读不到「这个中间状态」。对别的核来说，比较和写入是一个动作，只有改前和改后两个值。 B 读到 10 是可能的，但那说明 B 的那次读排在 A 的 CAS 之前。这不破坏任何东西：B 之后执行 CAS 时会被排到 A 后面，拿 10 去和 11 比，失败。

LL/SC 上，STXR 返回 1 一定是因为值被改了吗？

不一定。STXR 检查的是 LDXR 打下的那个标记，不是值。别的核写过这条行会让标记失效，但中间发生上下文切换、或者实现自己判断这次不保险，也会让 STXR 返回 1，此时值可能一点没变。 所以 C++ 的 compare_exchange_weak 允许无故失败，必须放在循环里；而「CAS 失败 = 有人先改了值」这句话只对 CAS 类指令成立。

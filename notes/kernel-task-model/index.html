内核里没有「进程对象」

Linux 只有一种结构 task_struct。「进程」和「线程」的差别不在类型，而在 clone() 那一串开关——共享在这里是连续刻度，不是二选一。

01先否掉一个直觉：内核里维护着两个类

要理解「进程和线程到底差在哪」，大多数人脑子里是这样一张图：

// 直觉模型 —— 内核里有两个类
class Process {
  addrSpace: AddrSpace;
  files: FdTable;
  threads: Thread[];        // 进程持有线程列表
}
class Thread {
  pc: number;
  regs: Registers;
  stack: Stack;
  process: Process;         // 线程回指进程
}

这个模型很清楚，而且是错的 —— 至少 Linux 不是这样。它错在代价：

代价两套类意味着什么
两套调度逻辑调度器要分别处理 Process 和 Thread，选下一个跑的时候先得判断「我在调度哪一类」
两套同步逻辑同一种锁要维护两个版本；阻塞、唤醒、优先级继承全都要写两遍
两个类互相引用进程持有线程列表、线程回指进程 —— 任何一次调度决策都要在两套状态之间翻译
边界上的特判「一个进程最后一条线程退出时该做什么」这类问题，在两套模型里永远有缝隙

一句话：两套类会带来两套调度、两套同步，而它们之间还要互相翻译。

02Linux 的答案：只有一种对象

Linux 内核里没有「线程对象」。只有一种数据结构：task_struct。

应用层的叫法内核里实际是什么
进程资源不被共享的那群 task
线程资源被共享的那群 task

差别不在类型，而在指针。task_struct 里存的是指向资源的指针： 共享时只复制指针，不共享时才复制资源。

🧬

用面向对象的话说：进程是深拷贝，线程是浅拷贝。

  • 深拷贝（structuredClone 那种）：taskB.mm = copyOf(taskA.mm) —— 资源翻倍，彼此独立
  • 浅拷贝（对象图只复制引用）：taskB.mm = taskA.mm —— 一份资源，两个引用

但 Linux 比这还细一层：它的「浅拷贝」不是一刀切的， 而是逐资源维度各有一个开关（下一节展开）。

这就是 clone() 的 CLONE_* 标志 —— 把「复制还是共享」变成了一个参数。

另一个主流设计是 Windows 式的分层：线程是独立的数据结构，链接到它所属的进程结构。 两条路线都成立，取舍不同 —— 分层式有显式的进程对象，账目清晰； 统一式消灭了第二类对象，全部机制只服务一种结构。

03它是一张索引图，不是一个仓库

「资源全部内联进一个大结构体」这个模型也不成立。看 task_struct 的实际形态：

为什么必须是索引？

理由为什么不能内联
装不下task_struct 用 pahole 实测约 8KB / 155 个字段，而它指向的地址空间、文件表动辄以 MB 计
要共享同进程的多个线程必须指向同一份地址空间与文件表 —— 内联模型根本表达不了「两份描述共享一份资源」
生命周期不同文件可以提前 close，映射可以 munmap —— 资源的生灭粒度比进程本体细，必须独立成对象

第三条最容易被忽略，但它解释了很多事：

文件描述符可以在进程退出之前就被关掉。 如果 fd 表内联在 task_struct 里，「提前关掉一个 fd」就变成「修改进程结构体的一部分」—— 而它其实只是对象图里断掉一个引用。

一个顺手的类比：inode

这个设计和文件系统是同一个套路：

系统元数据放哪数据放哪共同点
文件系统inode 存大小 / 权限 / 时间戳指向若干数据块的指针都是索引节点，不是容器本体
Linux 进程task_struct 存 pid / 状态 / 优先级指向 mm / files / ns 的指针不内联内容

删除文件只要摘掉元数据与引用，不需要逐一擦除数据块； 清算一个进程也一样 —— 摘掉 task_struct 和它的资源引用，就结束了。

🗂

这张对象图有一份现成的只读投射：/proc/<pid>/。

目录/文件 对应对象图里的哪一根指针
/proc/<pid>/maps mm → mm_struct → 各段 VMA
/proc/<pid>/fd/ files → 打开文件表
/proc/<pid>/status 身份、状态、凭证、内存占用
/proc/<pid>/ns/ nsproxy → 每个命名空间各一个符号链接

内核访问「当前进程」用的是 current 宏 —— 基于 per-CPU 变量实现、免查表。 因为 90% 以上的系统调用第一件事就是取当前进程：系统调用天然是「针对调用者的资源」操作。

04落到系统调用上：fork 和 pthread_create 走同一扇门

前面说的「逐资源开关」不是比喻，它就是 clone() 的参数表。

clone() 的开关面板 勾一勾，看「你造出来的」是什么

四个正向开关，每个守一个维度：

开关共享什么为什么是它
CLONE_VM地址空间（页表指针直接复用）两个 task 看同一片内存 —— 这是「线程」最核心的那一条
CLONE_FILES打开文件表A 打开的 fd，B 立刻看得见，连读写偏移量都共享
CLONE_FS根目录 / 工作目录 / umaskumask 决定新文件的默认权限，属于「文件系统环境」而不是单次调用参数
CLONE_SIGHAND信号处置函数表任一线程改 SIGTERM 的处置，全组立即可见 —— 这是「同一进程」应有的语义
🚪

不带任何 CLONE_* 调用 clone()，等价于 fork()。 四个全带上，等价于创建线程。

fork() 与 pthread_create() 在 Linux 里 走的是同一扇门， 区别只在一串标志位。

这也是为什么 pthread_create 能被实现成一个库调用 —— 它不需要内核里存在一个叫「thread」的东西。

一个反直觉的推论

既然「线程」不是一种类型，那么共享一部分、不共享另一部分也是合法的：

你可以造出一个和父进程共享地址空间、但自己有一套工作目录的 task。 这种组合没有标准名字 —— 但内核完全允许，因为它只是几个开关的不同组合。

在「两套类」的模型里，这种对象根本表达不出来。

05反向开关：容器是从这里长出来的

CLONE_* 里还有一组方向相反的开关：

开关它表示结果
CLONE_NEWNS不共享 mount 命名空间，另立一个自己一套挂载点 —— 容器的文件树从这来
CLONE_NEWPID另立 PID 命名空间容器里看到的 PID 从 1 开始
CLONE_NEWNET另立网络命名空间自己的网卡、路由表、端口空间

注意方向：clone 默认继承父进程的命名空间，带上 NEW* 反而表示「另立一个」。

📦

同一个机制，能在两个方向上画界。

方向 做法 得到
往里合 带正向开关，共享资源 线程
往外切 带反向开关，切出命名空间 容器

所以「容器」不是什么新对象 —— 它是一组不带正向开关、但带了反向开关的 task， 内核用 nsproxy 把 IPC、网络、cgroup、mount、PID、时间这些可分区资源分组管理。

这也解释了容器的「轻」和线程的「轻」为什么不是一回事： 容器共享的是内核，切掉的是命名空间；线程共享的是进程资源域。

06好处不是概念洁癖，是复用

统一模型最直接的收益是创建成本：

动作要做什么
fork()复制整套资源结构 + 新建页表 + 复制文件表
pthread_create()只复制几个指针 + 一个新内核栈

这正是 NPTL 时代线程创建能比旧实现快约 7 倍的结构基础 —— 不是因为优化了什么，而是因为它本来就不需要做那些事。

但更重要的收益是间接的：

调度器、同步原语、内存管理都只面对一种对象。 「共享程度」变成 clone 参数里的连续刻度，而不是两套割裂的实体。

⚠

一次真实的翻车：LinuxThreads。

在 NPTL 之前，Linux 的 LinuxThreads 把每个线程做成了一个独立的轻量级进程 —— 也就是说，它在「一种 task」之上又假装出了一套线程语义。

结果 getpid()、信号、wait() 的行为与 POSIX 要求对不齐， 各处漏风，最终被基于同一 task 模型的 NPTL 取代（内核 2.6 前后落地）。

教训是：把线程硬塞进「每个线程是一个进程」的模型里， 语义裂缝会在每个角落漏出来。

Linux 内核里，「进程」和「线程」在数据结构层面分别是什么？

都不是独立的对象。内核里只有一种结构：task_struct。 「进程」= 资源不被共享的那群 task；「线程」= 资源被共享的那群 task。 区别不在类型，而在 task 里那几个指针（mm / files / sighand / nsproxy） 是指向同一份资源还是各自一份。所以「进程」在内核里其实没有专属对象， 它只是「恰好不共享资源的那组 task 及其资源域」在应用层的投影。

fork() 和 pthread_create() 在内核里有什么区别？

走的是同一扇门 clone()，区别只在一串标志位。 不带任何 CLONE_* 调用 clone() 等价于 fork()；带上 CLONE_VM / CLONE_FILES / CLONE_FS / CLONE_SIGHAND 等价于创建线程。 这也意味着「共享一部分」是合法的 —— 共享在这里是一个连续刻度， 而不是二选一。在「两套类」的内核里，这种对象根本表达不出来。

为什么 task_struct 不把地址空间、文件表直接内联进去，而要存指针？

三个理由，缺一不可。 ① 装不下：task_struct 实测约 8KB / 155 字段，而它指向的资源以 MB 计。 ② 要共享：同进程的多个线程必须指向同一份资源，内联模型表达不了「两份描述共享一份资源」。 ③ 生命周期不同：文件可以提前 close、映射可以 munmap —— 资源的生灭比进程本体细， 必须独立成对象。第三条最容易被忽略，但它解释了为什么关一个 fd 只是对象图上断一根指针。

CLONE_NEWNS 和 CLONE_VM 的方向为什么是反的？

因为 clone() 默认是继承父进程的一切。正向开关（CLONE_VM / FILES / FS / SIGHAND） 表示「把本来会复制的东西改成共享」；反向开关（CLONE_NEW*）表示 「把本来会继承的东西改成另立一个」。 所以同一个 clone() 能在两个方向上画界：往里合得到线程，往外切得到容器。 容器不是什么新对象，它是一组不带正向开关、但带了反向开关的 task。

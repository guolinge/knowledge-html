组合器的两套「字」：界面文案与数据名字

圈选界面上的每个字有两个来源：组件包与宿主自带的界面文案（三语、在本地合并进 global messages、切语言即变）和 Data Admin 下发的数据名字（单语、服务端按 clientLang 翻译、切语言要重拉）。含 vue-i18n global/local 作用域的实测结论与可切换语言的交互 demo。

组合器全景 讲了组件包由哪些文件组成，组件机制 讲了它怎么工作。这一篇回答一个更小的问题：

圈选界面上每一个字，是谁翻译出来的？

答案有两个。组件自带的界面文案（圈选条件、查询）和 Data Admin 配置的数据名字（近30天成交笔数、港股），走的是两条完全不同的链路：一条是本地的三语词条，切语言下一帧就变；另一条是服务端按请求语言挑好的一种名字，切语言要重新拉。混在一起想，就会问出「组件为什么不自己带一套 i18n」这种看着合理、方向错了的问题。

🧭

本篇结构：两种字（00）→ 两条链路对照（01）→ vue-i18n 的两个作用域（02）→ 组件库为什么把词条交出去（03）→ 数据名字那一半（04）→ 检查清单（05）。

作用域结论与数据链路都是实测：SSR 探针跑 vue-i18n 9.14.5，协议取 FService 协议空间 crm-crowd-service v1.0.3（commit 51ede78d）。

00界面上同时住着两种字

一个真实的圈选页上有这样两句话：

圈选条件                              ← 组件包里写死的标题
  近30天成交笔数 >= 12                ← Data Admin 里配置的字段名

它们看起来一样，来源却完全不同。

圈选条件 写在 packages/combination/src/messages.ts 里，和代码一起发布，三个语言各一份。近30天成交笔数 写在 Data Admin 的元数据表里，请求时由服务端按调用方语言挑一种返回，浏览器拿到的时候已经是单语。

界面文案是代码的一部分，数据名字是数据的一部分。 发布节奏、语言份数、刷新时机都不同，所以它们各自有一套翻译机制。

两条链路在本篇的例子里合流到同一个组件：InsightCombiner 用 t('combinerTitle') 取标题，用 label(name) 显示字段名。取法不同，是因为来源不同。

packages/combination/src/messages.ts 实测：zhCN / zhHK / en 三个语言桶各 47 个 key， 合计 141 行词条。三个桶共用同一个 typeof zhCN 约束，漏一个 key 编译不过。

02vue-i18n 的两个作用域

vue-i18n 9 里，useI18n() 有两个作用域，取哪个决定了组件的 t() 去哪里查词条。

global scope：全应用共用一份，子组件天然读得到
local scope：只有声明它的那个实例
宿主 main.ts createI18n + app.use(i18n)
global messages 宿主词条 + combinationMessages
InsightCombiner useI18n() → 默认 global
11 个子组件 useI18n() → 还是 global
某个组件 useI18n({ messages, useScope: 'local' })
它自己的子组件 读 global 那份；local 里没合并 key 就原样显示 key

local 不是「更靠里的 global」，而是一份挂在组件实例上的私有副本：只有调用 useI18n({ useScope: 'local' }) 的那个组件自己的 t() 用它，子组件调用 useI18n() 时拿到的仍然是 global。

一张 20 行的探针就能验证（vue + vue-i18n 9.14.5，SSR 渲染）：

const child = defineComponent({
  setup() {
    const { t } = useI18n();                                    // 不传 options = global
    return () => h('span', `child: combinerTitle=${t('combinerTitle')} | onlyLocal=${t('onlyLocal')}`);
  },
});
const parent = defineComponent({
  setup() {
    const { t } = useI18n({ messages: { 'zh-cn': { onlyLocal: '只写在 local 里' } }, useScope: 'local' });
    return () => h('div', [`parent: ${t('onlyLocal')}`, h(child)]);
  },
});
// 宿主只合并了组件词条里的 combinerTitle，没有 onlyLocal

真实输出：

parent: 只写在 local 里
child:  combinerTitle=圈选条件 | onlyLocal=onlyLocal

三件事一次说清：

观察 说明
父组件 onlyLocal 渲染成 只写在 local 里 local scope 对自己生效
子组件 combinerTitle 渲染成 圈选条件 子组件能从 global 拿到宿主合并进来的组件词条
子组件 onlyLocal 渲染成 onlyLocal 子组件读不到父的 local，vue-i18n 找不到 key 就把 key 原样返回

子组件永远读不到父组件的 local scope。 这不是配置问题，是 vue-i18n 的设计：local scope 只服务于声明它的那个实例，不做树形继承。

笔记里的 useScope: 'local' 常被当成「给这棵子树设置语言」，实际只覆盖当前组件一层。

03组件库的契约：词条交出去，实例借用宿主的

组件的 12 个组件全部用 useLabel()（内部就是 useI18n()），没有一处自建 i18n 实例。这是刻意的：

peerDependency

实例借宿主的

vue-i18n 是 peerDependency，组件不自己 createI18n

packages/combination/package.json 里 vue-i18n、vue、element-plus 都是 peerDependency： 组件用宿主 app.use(i18n) 装好的那一个实例，保证 locale 只有一份真相。

combinationMessages

词条交出去

导出 combinationMessages，由宿主合并进 global

messages.ts 导出 { 'zh-CN': ..., 'zh-HK': ..., en: ... } 三个语言桶共 47 个 key， 宿主把它们并进自己的 global messages，组件再 t() 查。

单一真相

只查不装

组件内部不建自己的 i18n，也不读本地存储

语言由宿主决定（这里来自主应用 context 的 locale）。组件跟着走，不参与语言状态管理。

宿主侧要做的事一共三步，第三句就是合并：

// client/src/locale.ts
import { combinationMessages } from '@futuweb/audience-combination';

export const i18n = createI18n({
  locale: normalizeLocale(getHostContext()?.locale),
  fallbackLocale: LANG.ZH_CN,
  legacy: false,
  messages: {
    [LANG.ZH_CN]: { ...combinationMessages['zh-CN'], ...zhCnMessages },
    [LANG.ZH_HK]: { ...combinationMessages['zh-HK'], ...zhHkMessages },
    [LANG.EN_US]: { ...combinationMessages.en, ...enUsMessages },
  },
});

...combinationMessages['zh-CN'] 在前，宿主自己的词条在后：同名 key 时宿主覆盖组件，业务文案优先。

为什么不让组件自建实例 + local scope？对照一下就清楚了：

做法会发生什么结论
组件自建 createI18n，每个组件带自己的词条一棵组件树里出现多份 locale 状态，宿主切语言要挨个通知；组件包还得自己装一个 vue-i18n 版本，和宿主那份不是同一个实例时会有两份运行时不选
组件用 useScope: 'local' 声明词条local 只覆盖声明它的那个组件一层（02 节实测），11 个子组件要各自声明一遍，47 个 key 抄 12 份不选
词条导出、宿主合并、组件读 globallocale 只有一份真相，子组件天然能查到词条，组件包不锁 vue-i18n 版本当前做法

只 app.use(i18n)、忘了合并 combinationMessages，页面上会直接显示 combinerTitle 这样的 key。 vue-i18n 找不到 key 时返回 key 本身，不报错，也不空白。02 节的探针里 onlyLocal=onlyLocal 就是同一个行为。

04数据名字那一半：由服务端翻译

字段名、关系名、值集合的 label 不归 SDK 管。它们在 Data Admin 里配置，请求时按调用方的语言本地化成单个字符串再下发：

浏览器 · 宿主 + 组件t(key) / label(name)
Node BFFGET /api/crowd/*
Data Admincrm_crowd_service
宿主合并词条
1拉元数据
2header 带 clientLang
3name 已是当前语言
4portraits[].name
文案立刻变
5数据名字要再拉

语言参数不是前端传的 query，而是 BFF 的调用头里带下去的：

// @futu/agudo 的 helper：把当前请求的语言塞进下游 header
const { ..., lang = 0 } = this.ctx.env || {};
return { ..., clientLang: lang };

crm_crowd_service 的 proto 里，name / label 的注释写的就是「当前请求语言下的名称」，形状是一个 string：

message CrowdPortrait {
  optional string key = 1;    // 特征标识 field_key
  optional string name = 2;   // 当前请求语言下的名称
  optional FieldTypeMeta field_type = 3;
  ...
}

所以组件的 label() 现在要接两种入参。这是 03 与 04 两条链路的分界线：

/** string：Data Admin 下发的名称，已本地化，直接透传；I18nText：SDK 自带的本地词条，按 locale 挑键。 */
export type LabelText = string | I18nText | undefined;

function label(text: LabelText): string {
  if (!text) return '';
  if (typeof text === 'string') return text;
  const current = normalizeLabelLocale(locale.value as string);
  return text[current] || text['zh-CN'] || text['zh-HK'] || text.en || '';
}

SDK 自带的操作符表（OPERATOR_DISPLAY 的「等于」「最近 {0} 天」）仍然是三语的 I18nText，走 label() 的第二条分支；Data Admin 下发的名字走第一条分支，不再查 locale。

下面的控件把两条链路放在同一个页面上切一次语言：左栏文案立刻换，右栏的数据名字会先标记成「过期」，等你点重新请求才更新。

切一次语言，看两种字各自怎么变

切语言时不能只按 revision 判断要不要换元数据。 revision 是投影内容哈希，它不保证随语言变化；圈选页的做法是 watch(locale) 时带 force: true 直接换一份新的，并清掉值集合缓存。

05检查清单

  • 页面上出现了 combinerTitle 这样的 key：宿主只 app.use(i18n)，没合并 combinationMessages
  • 切了语言，标题/按钮没变：组件词条没并进 global，或宿主没有响应 locale 变化
  • 切了语言，字段名还是旧语言：元数据要重新拉一次，且不能只靠 revision 判断
  • 英文环境下字段名仍是中文：检查下游 header 的 clientLang 有没有带下去
  • 把 Data Admin 的 name 当 I18nText 查 locale：它是单语字符串，查了也不会变
⏳

时效（2026-10-13）：SDK 的读模型原本按三键（zhCn / zhHk / en）设计， 与当时的 proto 快照一致；Data Admin 确认「按 FRPC header 的语言返回单一语言」后， packages/dsl 已改成 name?: string，BFF 适配层只剩两件事：JSON 标量字符串解成标量、 status 数字转 ENABLED / DISABLED。改动当时在 audience_web 工作区尚未提交， 引用这段结论前先看一眼 packages/dsl/src/audience.ts 的注释。

组件里的 12 个组件都调用 useI18n()，为什么不能各自声明 useScope: 'local' 把自己的词条带进去？

local scope 只对声明它的那个组件实例生效，子组件调用 useI18n() 拿到的还是 global。 12 个组件要各自复制一份 47 个 key 的词条，仍然是各查各的； 把词条导出、宿主合并进 global，才是一份真相喂到所有层。

界面文案和数据名字，切一次语言之后各自多久生效？为什么？

界面文案下一帧就变，因为三语词条都在本地（组件包 + 宿主各一份，合并进 global messages）。 数据名字要重新请求才变，因为 Data Admin 按请求头里的 clientLang 本地化后只下发一种语言， 浏览器手里那份是上一次请求拿到的旧语言。

为什么 BFF 的适配层不把单语言的 name 包装成三键？

包装只是过渡期的权宜。proto 的契约是单语言 name，SDK 已经按它改成 string； 再包一层会让「谁翻译」这件事变得含糊，而且三键里另外两个键填的是同一个值， 切语言也不会变。语言在服务端决定，前端只负责在切语言后重新拉。

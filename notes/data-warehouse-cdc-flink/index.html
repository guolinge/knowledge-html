数据仓库 vs 数据库 · CDC vs Flink

两组最常被混在一起的概念：一个是「业务怎么跑」，一个是「数据怎么分析」；一个是「变化怎么被发现」，一个是「变化怎么被加工」。

01数据库：服务「在线业务」

你平时接触的 MySQL、PostgreSQL、MongoDB 等，通常说的是 数据库。

它主要负责保存并支撑正在发生的业务操作：

数据库在支撑什么 每一件都要求「立刻写对、立刻查到」
用户注册
用户登录
商品查询
提交订单
支付成功
修改收货地址

例如电商数据库里有这样的表：

users
products
orders
order_items

当用户下单时，后端会往 orders 表插入一条订单；用户查看订单时，又从这个表查询数据。

🎯

数据库的核心目标是：保证每一笔业务数据正确地写入、修改和查询。

它通常更关注单个用户、单笔订单这类「小范围、高频、低延迟」的读写操作。

02数据仓库：服务「数据分析和报表」

数据仓库（Data Warehouse，简称数仓），是把来自多个业务系统的数据收集、清洗、统一后， 专门用于分析、报表和商业决策的数据系统。

例如老板或运营会问：

分析类问题 共同点：要扫大量历史数据
今天总销售额多少？
哪个城市订单最多？
各渠道下单转化率？
近 30 天复购率？
哪个商品退款率最高？

这类问题需要扫描、统计大量历史数据，不适合直接频繁地在业务数据库上执行。

完整链路：从业务库到看板

整条链路可以拆成 7 层。左侧是每层的角色，右侧是这一层里真实存在的东西。

LAYER 01 源系统层 数据真正产生的地方，也是唯一「权威」的副本
MySQL 订单库 orders / order_items binlog
MySQL 用户库 users / user_profile binlog
埋点日志 page_view / click Kafka
支付系统 payments / refunds API / DB
抽取 Extract把数据从业务库「拿出来」
LAYER 02 抽取层 决定「多久同步一次」和「能不能拿到删除」
CDC 读 binlog op = INSERT/UPDATE/DELETE 准实时
时间戳增量 WHERE updated_at > ? T+1 / 小时
全量快照 SELECT * 整表拉取 每天一次
日志采集 Flume / Filebeat 实时
落地 Load先原样存下来，不做业务翻译
◈ 数仓内部：分层建模 ODS → DWD → DWS → ADS
LAYER 03 ODS 贴源层 与业务库表一一对应，只做类型转换 + 按天分区
ods_order 订单原样落地
ods_user 用户原样落地
ods_page_view 埋点原样落地
ods_payment 支付原样落地
清洗 Clean去重 · 补空值 · 剔脏数据 · 统一编码/时区/单位
LAYER 04 DWD 明细层 一行 = 一个业务事件，字段已翻译成业务语义
dwd_order_detail 订单事件明细（已 join 用户 / 商品）
dwd_user_basic 用户基础信息
dwd_pay_flow 支付流水明细
聚合 Aggregate按 日期 / 城市 / 渠道 等维度 group by
LAYER 05 DWS 汇总层 一行 = 一个统计口径，明细被压缩成指标
dws_order_city_1d 日 · 城市 · 渠道 的订单与 GMV
dws_user_active_1d 日活 / 留存
dws_channel_funnel_1d 渠道转化漏斗
加工 Serve面向某张具体报表定制口径
LAYER 06 ADS 应用层 直接给报表用的结果表，查询毫秒级
ads_gmv_report GMV 大盘
ads_refund_rank 退款率排行
ads_retention 复购 / 留存看板
查询 QueryBI / 看板 / API 只读结果表，不碰业务库
LAYER 07 应用层 谁来消费这些数据
BI 报表 固定口径的日报周报
数据看板 实时大盘
即席查询 分析师临时取数
数据 API 反哺业务系统
算法特征 喂给推荐 / 风控模型
🧱

为什么要分这么多层？因为每一层只解决一个问题： ODS 保证「拿全了」、DWD 保证「看懂了」、DWS 保证「算快了」、ADS 保证「用着顺手」。 中间任何一层算错，都能回到上一层重跑，而不用去动业务库。

细节：一行订单数据是怎么被搬走的

上面是宏观分层。下面用一条真实订单（id = 1001）走一遍， 看它在每一层的数据形态到底发生了什么变化。

① 源系统 MySQL · orders 只存最终状态
id1001
user_id88
status1魔法数字
amount9900单位：分
updated_at2024-05-20 10:03:12

业务库只关心「现在是什么」：没有城市、渠道、会员等级， 历史状态会被覆盖，而且这台库不能随便跑大统计。

CDC 订阅 binlog只传变化的那一行，不扫全表
② 抽取 binlog event 含 before / after 
{"op": "UPDATE", "table": "orders",
 "before": {"id": 1001, "status": 1},   // 改之前
 "after":  {"id": 1001, "status": 2}}   // 改之后

拿到 before / after 意味着：既知道「改成了什么」，也知道「哪一行被删了」 —— 这正是轮询做不到的。

原样落地不翻译业务语义，先存下来
③ ODS ods_order 只加分区字段
id1001
user_id88
status2
amount9900
updated_at2024-05-20 10:03:12
dt2024-05-20新增分区

只做了字段类型转换和加分区字段 dt，不做任何业务翻译。 好处是：上游口径改了、或者下游算错了，都能回到这一层原样重跑。

清洗 + 统一 + 关联枚举翻译 · 单位换算 · 多次 join
④ DWD dwd_order_detail 业务可读
order_id1001
order_status'已支付'枚举翻译
amount99.00 元分 → 元
city'杭州'join ods_user
channel'APP'join 埋点
user_level'VIP'join 用户标签

到这一层，一行 = 一次订单事件，字段已经能被业务直接读懂。 原来要 join 三张表才能回答的问题，现在查一张表就够。

聚合group by 日期 + 城市 + 渠道
⑤ DWS dws_order_city_1d 明细 → 指标
dt2024-05-20
city'杭州'
channel'APP'
order_cnt1820
gmv182340.00

一行 1001 的订单，在这里被「溶解」成杭州当天 1820 单里的一份子。 数据量通常会下降 2~3 个数量级，但已经无法再还原到单笔订单。

面向看板加工只留报表要用的字段和口径
⑥ ADS ads_gmv_report 毫秒返回
指标今日 GMV
值1,284,930
环比+12.4%
城市 Top1杭州

看板查询从「扫几亿行明细」变成「读几千行结果」，所以能秒开。 代价是这张表只服务于这一个口径，换一个问法就要再建一张。

抽取方式怎么选

「怎么把数据拿出来」是整条链路里最关键的一步。常见有 5 种做法，差别主要在 延迟、能不能感知删除、对业务库的压力。

方式怎么做延迟删除压力适用
全量快照每天 SELECT * 整表拉一遍T+1能高小表、维表
时间戳增量WHERE updated_at > 上次时间分钟 ~ 小时不能中有 update_time 的表
自增 ID 增量WHERE id > 上次最大 id分钟 ~ 小时不能（改也漏）中只追加的流水表
触发器建 trigger 写影子表秒级能高（写放大）老系统兜底
CDC 读 binlog订阅数据库变更日志，只读不写秒级 / 准实时能低现在的主流方案

数据仓库存储的是经过处理、适合分析的数据；它通常面向报表、仪表盘和商业智能场景。

维度数据库数据仓库

05一个容易混淆的点

💡

数据仓库不一定是某个固定产品，而是一类用途 / 架构。

例如这些产品可能被用作数仓或数仓中的查询引擎：

常见选择 它们不都是「数仓」，但都可以充当数仓或数仓里的查询引擎
ClickHouse
Apache Doris
StarRocks
Snowflake
BigQuery
Redshift
Hive

而 MySQL 既是数据库，也能勉强做少量报表；但当数据量、查询复杂度、并发分析需求变大时， 直接在业务 MySQL 上跑大统计很容易影响线上下单、支付等业务。

06CDC 是 Flink 的一个功能吗？

🧩

严格来说：CDC 不是 Flink 独有、也不是只有 Flink 才有的功能。

CDC 是一种通用技术 / 思路，完整名称是 Change Data Capture：变更数据捕获。

它用于捕捉数据库中数据的三种变化：

CDC 捕获什么 对应数据库变更日志里的三种操作
INSERT 新增
UPDATE 修改
DELETE 删除

例如 MySQL 的订单表发生了变化：

新增订单 A001
订单 A001 从“待支付”改为“已支付”
删除一条测试订单

CDC 会把这些变化捕捉出来，作为持续的数据流发给下游。

Flink 和 CDC 的关系

分工 一个负责「发现变化」，一个负责「加工变化」
数据库的变更日志 例如 MySQL binlog
CDC 读取并识别「新增、修改、删除」
Flink 实时清洗、转换、计算、关联、写入目标系统
下游 数仓 / 湖仓 / ES / Kafka / 风控
  • CDC：负责「发现数据库发生了什么变化」
  • Flink：负责「拿到变化后，实时怎么加工和处理」

07那么什么是 Flink CDC？

Flink CDC 是 Flink 生态中的一个 CDC 项目 / 连接器方案。

它可以让 Flink 读取 MySQL、PostgreSQL、Oracle、SQL Server 等数据库的变更， 并把变更作为 Flink 的流数据来处理。其底层常会使用 Debezium 提供的数据库变更捕获连接器。

一个典型用法 MySQL 表变化 → Flink 加工 → 写进各种下游
MySQL users 表变化
Flink CDC 捕获 binlog
Flink 清洗或补充字段
Kafka / ClickHouse / Doris / Iceberg

08为什么不直接定时查数据库，而要 CDC？

不用 CDC 的方式可能是这样：

-- 每隔 10 分钟执行一次
SELECT * FROM orders WHERE update_time > 上次同步时间

这种方式简单，但会有问题：

  • 延迟高，最快也要等下一次轮询
  • 不断查询业务数据库，可能增加压力
  • 更新频繁时，容易漏数据、重复数据
  • 删除数据不容易准确识别
  • 很难做到真正接近实时

CDC 则直接基于数据库的变更日志读取变化，只同步新增、更新、删除的部分， 而不是反复扫描整张表。

订单表变更流 未开始
轮询 定时查表 每 10 分钟一次
延迟高中间状态丢失删除难识别反复压业务库
CDC 订阅变更日志 每条变化实时推送
近实时含删除只读 binlog不反复扫表

09前端类比

把数据库想象成前端的状态：

const user = {
  name: '小明',
  vip: false
}

如果你每隔一秒都重新读取整个对象，看看它有没有变化，这有点像定时轮询查表。

CDC 更像是状态变化时立即收到事件：

// 用户升级会员时，马上收到变化事件
{
  type: 'UPDATE',
  before: { name: '小明', vip: false },
  after:  { name: '小明', vip: true }
}

Flink 则相当于订阅这个事件后继续处理：

if (after.vip === true) {
  // 同步会员系统、更新数据看板、触发营销任务等
}

10一句话总结

记住这条链路

CDC 负责把数据库变化「实时通知出来」；

Flink CDC 是让 Flink 能方便读取这些变化的工具；

Flink 再对这些变化做实时处理和同步。

三句话收尾 三个层次，各管一件事
数据库 面向「正在发生的操作」，要求正确、快、稳
数据仓库 面向「已经发生的历史」，要求能扫、能聚合
CDC + Flink 一个负责发现变化，一个负责加工变化

11自测

数据仓库一定要用某个固定产品吗？

不是。数仓是一类用途 / 架构，不是产品。 ClickHouse、Doris、StarRocks、Snowflake、BigQuery、Hive 都可以充当数仓或数仓里的查询引擎。

CDC 是 Flink 的功能吗？

不是。CDC（Change Data Capture）是通用技术。 Flink CDC 只是 Flink 生态里的一个连接器方案，底层常复用 Debezium。

为什么 ODS 层不做业务翻译？

为了保住「可回溯」。ODS 与业务库一一对应，只做类型转换和分区。 上游口径变了、下游算错了，都能回到这一层原样重跑，而不用重新抽一遍业务库。

定时轮询为什么识别不到删除？

增量轮询的写法是 WHERE update_time > 上次时间，被删掉的行不会再出现在结果集里。 只有整表比对才能发现少了一行，但那等于每次全表扫描。 CDC 读 binlog 能直接拿到 op=DELETE 事件。

DWD 和 DWS 的分界线在哪？

DWD 是明细：一行 = 一个业务事件，字段已翻译成业务语义，但还没聚合。 DWS 是汇总：一行 = 一个统计口径（日期 + 城市 + 渠道），明细已被压缩成指标。 过了 DWS 就回不到单笔订单了。

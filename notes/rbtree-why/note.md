## 01 · 查找走几步，由树高决定

二叉搜索树（binary search tree，BST）只有一条规矩：

> 任何一个节点，左边子树里的键都比它小，右边子树里的键都比它大。

这条规矩的用处是：和当前节点比较一次，就能决定往哪边走 —— 比它小去左边，比它大去右边，相等就找到了。查找因此变成从根开始一路做决定。

于是「查找要比较几次」就等于「从根走到目标，路上经过几个节点」。

| 键的个数 | 形状均匀时的层数 | 最多比较次数 |
|---|---|---|
| 7 | 3 | 3 |
| 1023 | 10 | 10 |
| 100 万 | 20 | 20 |

每往下一层就把候选范围砍掉一半 —— 100 万个键只要 20 次比较，这就是二叉搜索树值钱的地方。

但这份好处有个前提：树得是**矮而宽**的。BST 的规矩只管「谁在谁左边」，不管形状，而形状完全由插入顺序决定。

## 02 · 插入顺序会把树拉成一条链

同一批键，换一个插入顺序，长出来的树完全不同。

按 10、20、30、40、50、60、70 的顺序插进去：每个新键都比之前所有的键大，于是每次都往右走到底，树成了一条右斜的链。

```demo
widget: rbtree-lab
actions: false
title: 同一批键，两种形状
config:
  mode: show
  show234: false
  trees:
    - { cap: 顺序插入 10…70：7 层，查 70 要比 7 次, tree: "10B(,20B(,30B(,40B(,50B(,60B(,70B))))))" }
    - { cap: 换个顺序插：3 层，查任何一个都只要 3 次, tree: "40B(20B(10B,30B),60B(50B,70B))" }
```

两棵树的键一模一样。左边查 70 要沿着这条斜链一路走到底，7 个节点全经过；右边 3 次就到底。

键一多，差距是几个数量级。下面这几个数字是**跑出来的**：把 1、2、3…… 按顺序插进去，普通 BST 每次都往右走到底，100 万个键就是 100 万层；同一批键交给红黑树，只有 37 层。

```compare
first: 顺序插入 1…10⁶
head: [普通 BST, 红黑树]
rows:
  - 树高（层）: [{ text: 1000000, tone: red }, { text: 37, tone: green }]
  - 查最大键要比较: [{ text: 1000000 次, tone: red }, { text: 37 次, tone: green }]
  - 形状: ["一条右斜的链", "矮而宽，黑高 19"]
```

而按键值本身的大小顺序插入，在现实里很常见：==时间戳、自增 id、订单号 —— 按这些列建索引，天然就是最坏的顺序。==

所以问题不在二叉搜索树这个想法，而在**形状没人管**。既然形状取决于插入顺序，那就把形状本身变成一条必须维持的规矩。

## 03 · 让树别长歪，有两条路

```compare
first: 做法
head: [收紧高度差, 让节点多装几个键]
rows:
  - 代表: ["AVL 树", "2-3-4 树（B 树家族）"]
  - 挂什么额外的规矩: ["任何一个节点，左右子树的高度差不超过 1", "一个节点里可以放 2 个或 3 个键"]
  - 树高上界: ["约 1.44·log₂(n+2)", "log₂(n+1)"]
  - 代价: ["插入删除后要沿路检查高度差，可能连续旋转多次", "节点装不下就分裂，空了就借或合并"]
  - 每个节点要额外存: ["高度（或平衡因子）", "键和孩子的数组"]
```

两条路都要在插入、删除之后做修整动作，差别在**修的是什么**：

- AVL 修的是「高度差」—— 每一层的左右子树的层数不能差超过 1，一旦超了就旋转。
- 2-3-4 树修的是「节点装不下」—— 节点满了就分裂，节点空了就从邻居借或和邻居合并。

而且这个差别会传导到全部操作上：AVL 的规矩更严，树更矮（查找略快），但每改一次树都可能要连转好几下；2-3-4 树的规矩更松，树略高，但插入删除只需要处理局部的「装不下」和「空掉」。

红黑树是**第二条路的二叉写法**：它保持二叉搜索树的节点形状 —— 一个节点一个键、最多两个孩子，但用颜色把「哪几个节点算作同一个多键节点」记下来。接下来两篇先讲清那个多键节点的模型和它在二叉树上长什么样，再讲改树时怎么修复。

## 04 · 「一个节点装多个键」长什么样

一个 2-3-4 树的节点最多装 3 个键，这些键按顺序排在一个框里，往下伸出比键数多一根的分支：

```demo
widget: rbtree-lab
actions: false
title: 三种节点
config:
  mode: 234
  trees:
    - { cap: 2-节点：1 个键、2 个孩子, tree: "20:(_,_)" }
    - { cap: 3-节点：2 个键、3 个孩子, tree: "20|30:(10:(_,_),_,40:(_,_))" }
    - { cap: 4-节点：3 个键、4 个孩子, tree: "20|30|40:(_,_,_,_)" }
```

查找时在一个节点内部先比完这几个键（最多 3 次），再决定下到哪一根分支。看起来比二叉搜索树「每层干活更多」，但它换来一件大事：**所有叶子必然在同一层**，树不会长歪。

原因很直接。每个节点至少有 2 个孩子，所以第 d 层最多有 2ᵈ 个节点；反过来，一棵装 n 个键的 2-3-4 树有 n+1 个叶子位置（每个键贡献一个分叉），于是

```
2ᵈ ≤ n + 1        叶子数不超过第 d 层能容纳的节点数
d ≤ log₂(n+1)     所以深度有上界
```

100 万个键的 2-3-4 树，深度不超过 20 层 —— 和形状完美的 BST 一样，而且**不需要任何旋转**，深度这个上界是结构本身保证的。

==一个节点里多装几个键，就是为了让树矮下来。==代价是节点内部的形状变复杂了：插入要分裂，删除要借位或合并。那正是红黑树那五条规则在描述的东西。

## 05 · 接下来

这个系列的走法是：**先把 2-3-4 树这个模型讲透，再看红黑树怎么用一棵二叉树把它记下来**，最后用这个模型去解释插入和删除的每一种情形。

```quiz
- q: 同样 7 个键，为什么一棵树是 7 层、另一棵是 3 层？
  a: |
    二叉搜索树的形状完全由插入顺序决定。按 10、20、30…… 依次插入时，
    每个新键都比之前所有的键大，所以每次都往右走到底，长成一条链；
    换一个中间值先落地的顺序，同一批键会分成左右两部分，每层砍一半。

- q: 「2-3-4 树的深度不超过 log₂(n+1)」这一步，靠的是哪两个事实？
  a: |
    ① 每个节点至少有 2 个孩子 —— 所以第 d 层顶多放 2ᵈ 个节点；
    ② 一棵装 n 个键的 2-3-4 树恰好有 n+1 个叶子位置（每个键贡献一个分叉）。
    两条合起来：2ᵈ ≤ n+1，于是 d ≤ log₂(n+1)。

- q: AVL 和 2-3-4 树都在「维持平衡」，它们维持的东西有什么不同？
  a: |
    AVL 维持的是每个节点的左右子树层数差不超过 1 —— 规矩严、树矮，
    但每次改树都可能要连续旋转多处。
    2-3-4 树维持的是「节点装得下」：满了分裂、空了借或合并。
    规矩松、树略高，但只需要处理改动附近的那几个节点。
```

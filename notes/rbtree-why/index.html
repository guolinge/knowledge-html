二叉搜索树为什么会坏

查找走几步由树高决定，而树高由插入顺序决定。让树别长歪有两条路：收紧左右高度差，或者让一个节点多装几个键。红黑树走的是第二条路的二叉写法。

01一个具体的问题：为什么「有序插入」会把树变成一条链

先不提红黑树。从一个真实会遇到的场景说起。

你在系统里有一张订单表，主键是自增 id，存了 100 万条。有人按 id 建了一棵二叉搜索树来加速查询 —— 因为 id 是自增的，插入顺序天然就是 1、2、3、4……

现在要查 id = 1000000：这条路走了多少个节点？

按 10、20、30…… 的顺序插入，树长这样

7 个键就要比 7 次。100 万个键呢？**100 万次比较。**本来指望用树把「查一条」从 100 万次砍到 20 次，结果一次都没省。

这不是极端情况。凡是「按键值本身的大小顺序插入」都会这样：

什么场景 插入顺序 树的形状
自增主键 / 序列号 1, 2, 3, 4…… 一条右斜的链
时间戳、创建时间 越来越大的时间 一条右斜的链
订单号、流水号 单调递增 一条右斜的链

所以问题很清楚：二叉搜索树的形状没人管，而形状完全由插入顺序决定。

02先把「查找为什么快」讲清楚

要理解它为什么坏，得先看清它凭什么快。

二叉搜索树（binary search tree，BST）只有一条规矩：

任何一个节点，左边子树里的键都比它小，右边子树里的键都比它大。

一棵形状均匀的 BST

这条规矩的用处是：**和当前节点比较一次，就能决定往哪边走。**比它小去左边，比它大去右边，相等就找到了。查找因此变成从根开始一路做决定，每一步都扔掉一半候选。

于是「查找要比较几次」就等于「从根走到目标，路上经过几个节点」：

键的个数 形状均匀时的层数 最多比较次数
7 3 3
1023 10 10
100 万 20 20

每往下一层砍掉一半 —— 这就是「O(log n)」的通俗版本：100 万个键只要 20 次比较。

但这份好处有个前提：树得是矮而宽的。BST 的规矩只管「谁在谁左边」，一个字都没提形状。

04让树别长歪，有两条路

既然形状取决于插入顺序，那就把形状本身变成一条必须维持的规矩。有两个流派：

做法收紧高度差让节点多装几个键
代表AVL 树2-3-4 树（B 树家族）
挂什么额外的规矩任何一个节点，左右子树的高度差不超过 1一个节点里可以放 2 个或 3 个键
树高上界约 1.44·log₂(n+2)log₂(n+1)
代价插入删除后要沿路检查高度差，可能连续旋转多次节点装不下就分裂，空了就借或合并
每个节点要额外存高度（或平衡因子）键和孩子的数组

两条路都要在插入、删除之后做修整动作，差别在修的是什么：

  • AVL 修的是「高度差」—— 每层左右子树的层数不能差超过 1，一超就旋转。
  • 2-3-4 树修的是「节点装不下 / 空了」—— 满了就分裂，空了就从邻居借或合并。

这个差别会传导到全部操作上：AVL 规矩更严、树更矮（查找略快），但每改一次树都可能要连转好几下；2-3-4 树的规矩更松、树略高，但插入删除只需要处理局部的「装不下」和「空掉」。

红黑树走的是第二条路，而且是它的二叉写法：保持「一个节点一个键、最多两个孩子」的形状，但用颜色把「哪几个节点算作同一个多键节点」记下来。

05先看一眼「一个节点装多个键」是什么样

红黑树的前置就是这个模型，所以先花一分钟看清它长什么样。

一个 2-3-4 树的节点最多装 3 个键，这些键按顺序排在一个框里，往下伸出比键数多一根的分支：

三种节点

框里排着几个键，它就是几-节点：1 个键是 2-节点、2 个键是 3-节点、3 个键是 4-节点。查找时在一个节点内部先比完这几个键（最多 3 次），再决定下到哪一根分支。

看起来比 BST「每层干活更多」，但它换来一件大事：所有叶子必然在同一层，树不会长歪。

原因很直接：每个节点至少有 2 个孩子，所以第 d 层最多放 2ᵈ 个节点；而一棵装 n 个键的 2-3-4 树恰好有 n+1 个叶子位置（每个键贡献一个分叉）。于是：

2ᵈ ≤ n + 1        叶子数不超过第 d 层能容纳的节点数
d ≤ log₂(n+1)     所以深度有上界

100 万个键 → 深度不超过 20 层，和形状完美的 BST 一样。而且不需要任何旋转，深度上界是结构本身保证的。

如果只想快速拿一个结论，读到这里就够了：

一句话

红黑树 = 2-3-4 树的二叉写法。 「一个节点最多 3 个键」写成「红节点的孩子必须是黑的」， 「所有叶子同深」写成「每条路径黑节点数相同」。 插入删除的每一种情形，都对应 2-3-4 树里的一次分裂、借位或合并。

同样 7 个键，为什么一棵树是 7 层、另一棵是 3 层？

二叉搜索树的形状完全由插入顺序决定。按 10、20、30…… 依次插入时， 每个新键都比之前所有的键大，所以每次都往右走到底，长成一条链； 换一个中间值先落地的顺序，同一批键会分成左右两部分，每层砍一半。

为什么「按自增 id 插入」是二叉搜索树最坏的输入？

因为每个新 id 都比之前所有 id 大，插入路径永远是「一直往右」， 树退化成一条右斜的链，查找退化成线性扫描。 而自增主键、时间戳、流水号在真实系统里到处都是 —— 这不是极端情况。

「2-3-4 树的深度不超过 log₂(n+1)」这一步，靠的是哪两个事实？

① 每个节点至少有 2 个孩子 —— 所以第 d 层顶多放 2ᵈ 个节点； ② 一棵装 n 个键的 2-3-4 树恰好有 n+1 个叶子位置（每个键贡献一个分叉）。 两条合起来：2ᵈ ≤ n+1，于是 d ≤ log₂(n+1)。

AVL 和 2-3-4 树都在「维持平衡」，它们维持的东西有什么不同？

AVL 维持的是每个节点的左右子树层数差不超过 1 —— 规矩严、树矮， 但每次改树都可能要连续旋转多处。 2-3-4 树维持的是「节点装得下」：满了分裂、空了借或合并。 规矩松、树略高，但只需要处理改动附近的那几个节点。

call / push / ret / leave：把指令拆成微步

01四条指令，拆成同一组原子动作

前两篇停在「一条指令做什么」这一层。这一篇往下走一层：每条指令拆成几个微步。

先约定一件事：下面的微步都从「取指之后」开始。这时 RIP 已经指向下一条指令 —— x86 取指后 RIP 就自增了。这一点决定了三件事：call 压的是什么、ret 跳去哪里、leave 之后为什么刚好能接上 ret。

四条指令拆开，只剩三种动作：改指针、读写指针指向的那一格、改 RIP。

指令第一步第二步第三步
push 源RSP ← RSP − 8[RSP] ← 源—（不跳）
call 目标RSP ← RSP − 8[RSP] ← 下一条地址RIP ← 目标
ret读 [RSP] 得到目标RSP ← RSP + 8RIP ← 目标
leaveRSP ← RBPRBP ← [RSP]RSP ← RSP + 8

ret 和 leave 都是「先读、再抬指针」；push 和 call 都是「先降指针、再写」。这个顺序不是排版问题，下面逐条说。

四条指令的微步

切上面四个页签，一条一条走。走的时候注意两件事：RSP 什么时候动，以及动的是指针还是那一格内存。

02push：先减指针，再写内存

Intel 手册的伪代码就两行：

IF OperandSize = 64 THEN
    RSP := RSP − 8;
    Memory[SS:RSP] := SRC;

顺序反了会怎样？如果先写 [RSP] 再减 8，写进去的就是当前栈顶那一格 —— 而那一格往往正是上一个函数留下的东西，比如刚压进来的返回地址。先把指针降下去，新格子才真正属于这一次压栈。

⚠

push 是「先减再加」里的「先减」，pop 是它的镜像：先读、再加。

pop 的顺序同样不能反：先 RSP += 8 再读，读到的就是上面那一格， 也就是别人还没取走的数据。

push 也可以展开成 sub rsp, 8 + mov [rsp], 源 两条。效果一样，但生产代码里用 push：

  • 一条指令，不会被中断拆开，也不会在中途被信号处理看到「指针已经动、内容还没写」的状态；
  • 编码更短；
  • 不需要额外的临时寄存器。

03call：压「下一条」，然后跳

手册对近调用的描述是明确的一句：

📖

When executing a near call, the processor pushes the value of the EIP register (which contains the offset of the instruction following the CALL instruction) on the stack ... The processor then branches to the address in the current code segment specified by the target operand.

伪代码里压的是 RIP 这个寄存器本身：

tempRIP := RIP + tempDEST;      (* 目标地址：RIP 已经指向下一条 *)
Push(RIP);                      (* 压的就是这个「下一条」 *)
RIP := tempRIP;

本机那份 calc 是活例子：callq _add 在 0x100000373，它的下一条是 0x100000378，被调函数 _add 在 0x100000328。位移是 0x328 − 0x378 = −0x50 —— 从下一条算，不是从 call 自己算。这正好解释了为什么压进去的值，天然就等于「回来接着执行的那条」。

call 是一条指令，不是「push + jmp 两条」。效果上可以那样理解，但有区别：

  • 两条指令之间有一个可以被中断、被观察的缝；call 没有。
  • 回溯和调试把 call 当作调用边界：栈回溯信息（CFI / .eh_frame）、调试器的「上一层」、采样剖析，都按它切帧。
  • 开着 CET 的机器上，硬件还会在 call / ret 时维护一份影子栈。手写的 push + jmp 不会更新它。

04ret：读栈顶、抬指针、跳过去

手册只有一句：

RIP := Pop();            (* 近返回 *)

拆成微步是三步，而且读在最前面：

读 [RSP] → 目标           ; 指针还没动
RSP := RSP + 8           ; 抬起一格
RIP := 目标               ; 跳过去

本机实测这一条：0x100000385 retq 执行完，RIP 变成 0x1000003a9（main 里 callq _calc 的下一条），RSP 从 0x…fa8 抬到 0x…fb0。

ret 还有一个带立即数的形式 ret 16：弹出返回地址之后，再 RSP += 16。这是 32 位时代 stdcall 让被调者顺手清掉参数的做法；x86-64 的 System V 用寄存器传参，这种写法基本见不到了。

💡

返回地址不是特殊数据，它就是栈上普通的一格 —— 谁改了它，谁就改了控制流。

手册的伪代码里因此多了一道检查：开了影子栈（CET）时，ret 会拿栈上的返回地址 和影子栈里的副本比对，不一致就报 #CP(NEAR_RET)。这道检查存在的理由， 就是「返回地址可以被改写」这件事本身。

05leave：把 RSP 拉回 RBP，再弹 RBP

RSP := RBP;              (* 第一步：指针回到帧底 *)
RBP := Pop();            (* 第二步：弹出旧帧底，RSP 顺带 +8 *)

手册的描述也是一句「Set RSP to RBP, then pop RBP」。三步展开就是：RSP ← RBP → RBP ← [RSP] → RSP ← RSP + 8。

顺序同样不能反。先 pop 再改 RSP，弹的就是栈顶的局部变量，RBP 会被写成一个垃圾值 —— 而这个垃圾值马上会被下一层函数当成自己的「上一帧」。

leave 走完，RSP 停在哪？停在返回地址那一格。所以它后面紧跟一条 ret 就能直接接上：

leave        ; RSP 回到返回地址
ret          ; 弹出它，跳走

这两条是一条固定搭配，编译器把它们排在函数末尾不是随手写的。

最后，leave 只在有帧指针时成立。省略帧指针时，编译器不知道帧底在哪，只能写死「加回多少」：

addq $0x10, %rsp   ; 帧大小是编译期常量，直接加回去
popq %rbp          ; 这一步和 leave 的后半条一样

本机 clang -O0 编出来的 calc 就是这三条（addq / popq / retq），效果和 leave; ret 完全一致。

06放一起看：谁动了什么

同一次 lldb 单步，四条指令前后各读一次寄存器：

指令 RSP RIP 其他
callq _add 0x…f90 → 0x…f88 0x…373 → 0x…340 压入 0x100000378
addq $0x10, %rsp 0x…f90 → 0x…fa0 0x…380 → 0x…384 —
popq %rbp 0x…fa0 → 0x…fa8 0x…384 → 0x…385 RBP：0x…fa0 → 0x…fc0
retq 0x…fa8 → 0x…fb0 0x…385 → 0x…3a9 跳到 main + 25

四条指令的动作可以归成两对加一个合并：

  • push / pop：一对镜像。一个降指针再写，一个读再抬指针。
  • call / ret：一对镜像。一个压「下一条」再跳，一个读出来再跳回去。
  • leave：尾声的合并写法，把「RSP 回到帧底」和「弹旧帧指针」压成一条。

一句话

栈上的指令没有魔法：都在动 RSP，都在读写 RSP 指的那一格，需要跳的时候再动 RIP。 顺序只有两条规矩：写之前先降指针，读之后才抬指针。

07速查：容易记反的六件事

  • push 先写内存，再把 RSP 减 8。—— 反了会覆盖当前栈顶那一格。
  • pop 先把 RSP 加 8，再读。—— 反了读到的是上面一格。
  • call 压的是 call 自己的地址。—— 压的是它的下一条。
  • ret 会检查返回值再决定跳哪。—— ret 只看栈顶那个地址，不碰返回值。
  • leave 先 pop RBP，再改 RSP。—— 先 RSP ← RBP，再 pop。
  • leave 之后还得手动把 RSP 抬到返回地址。—— 它走完就已经在返回地址上了。
为什么 push 必须先减指针、再写内存？

因为 [RSP] 指向的是当前栈顶那一格，里面可能正躺着上一个函数留下的数据（比如刚压进来的返回地址）。 先把指针降下去，写进去的才是这一次压栈自己的格子。

call 压进栈的地址，是从哪条指令算出来的？

从「下一条」算。x86 取指后 RIP 就已指向下一条，所以 call 的位移是相对下一条算的， 压进去的也正是这个值 —— 这样返回时才等于「接着往下走」。

leave 执行完，RSP 停在哪一格？

停在返回地址那一格。RSP ← RBP 回到帧底（旧 RBP 那格），pop 之后 RSP 再加 8， 正好落到保存的返回地址上 —— 所以后面紧跟一条 ret 就能接上。

既然 push + jmp 能替代 call，为什么还要用 call？

效果一样，但 call 是一条指令：中间没有可以被中断的缝；回溯信息和调试器按它切调用边界； 硬件的影子栈（CET）也只在 call / ret 上维护。手写替代会把这些都绕过去。

01回头看这一路

三条需求都落地了，代价从「跟登记了多少条成正比」降到了「跟这一刻真有几个就绪成正比」。

但这个变化的名字要叫准：epoll 让等待变便宜了，不是消失了。 有两件事它一点没碰。

02它没治的两件事

① 每次 epoll_wait 还是一次系统调用

名单不用重交了，但「问一声」这个动作本身还是要花钱： 用户态切到内核态、内核走一遍、再切回来。

轮询那篇量过的是「一次调用搬多少」；这一条是「调用本身要多少」。 哪怕一次只搬 3 个就绪事件，你也得为这次往返付钱。

② 数据拷贝还得你自己来

epoll_wait 只告诉你「可以读了」。真正把数据从内核缓冲区 搬到你自己的内存，是你的线程亲自 read 出来的 —— 拷贝那一段的等待一点没省。

这不是实现偷懒，是就绪通知模型本身的天花板。

03io_uring 冲的就是这两点

要一次治两个，就得换模型。区别在名字里：

模型内核告诉你的东西剩下要你做的别人怎么叫
epoll · 就绪通知「这个 fd 现在读不会卡」自己 read，还要自己处理 EAGAIN、短读短写Reactor
io_uring · 完成通知「这件事我替你办完了，结果在这」去完成队列取结果就行Proactor

机制上它做的事是：把「提交」和「取结果」两件事都搬到共享内存里。

同一块内存，用户态和内核都看得见（mmap 出来的）
提交队列 SQ 你往里塞「读 fd 3、读 4KB」这样的请求
内核从 SQ 取走 不用你喊它，它自己看得到
完成队列 CQ 办完了把结果放这：读了几个字节、成没成
你去 CQ 取结果 还是不用喊内核

关键就在「不用喊」这三个字。 epoll_wait 是「你喊一声，内核才动」；SQ/CQ 是一块双方都能读写的内存，动作发生这件事本身就不需要系统调用。

整个 API 只有三个系统调用：

io_uring_setup()，建那两个队列

建 SQ 和 CQ，返回一个 fd。和 epoll_create 一样，它也是个 fd。 建完之后你用 mmap 把这两个队列映射到自己的地址空间，这就是「共享」的实现方式。

io_uring_enter()，提交 / 收割

一次性把 SQ 里攒的一批请求交给内核，顺便等结果。 注意是一批，不是一条，这是它和「一次 read 一个请求」的根本区别。

io_uring_register()，预登记，可选

把常用的缓冲区、文件表提前登记，让内核长期持有引用， 省掉每次的重复检查。可选的：只用前两个也完全能跑。

再往上一步还有 SQPOLL 模式：让内核起一个线程专门盯着 SQ，你连 io_uring_enter 都不用调，那就真的是「零系统调用」提交了。代价是那个内核线程会一直空转，烧一个核。

04但它不是无条件更快

这一条要写清楚，否则前面的介绍会让人以为 io_uring 是「更快的 epoll」。

⚖

有 benchmark 显示：在没开 CPU 漏洞缓解的情况下，io_uring 相对 epoll 没有优势，甚至更慢。

原因不难想：epoll + read/write 的那条短路径（内核缓冲区 → 用户拷贝） 是 cache 友好的，延迟也很低。而 io_uring 多出来的队列管理、task_work 调度，在简单场景里就是纯开销。

网上流传的一组数据（只当量级看，不同来源差很多）：

P50 P99
epoll + read/write ≈ 1.2 μs ≈ 3.5 μs
io_uring 标准模式 ≈ 1.8 μs ≈ 4.2 μs
io_uring SQPOLL ≈ 1.1 μs ≈ 5.8 μs

SQPOLL 的 P50 最好看，P99 却是最差的。 这是「用空间和 CPU 换延迟」的典型代价： 内核线程空转把平均值拉低了，但一旦要唤醒、要排队，尾巴就长。

所以结论不是「io_uring 更好」，而是「它换了一种成本结构」： 用内存和复杂度，换掉系统调用的固定开销。这笔买卖在高并发、大量小 I/O 时才划算。

05接回那两棵树

这个系列不是孤立的，它把两处原本只提了名字的地方填上了：

回到哪一篇那里原来说了什么现在能补上什么
fs-io-models · 六个 I/O 模型「多路复用 + 同步 I/O，因为拷贝还要你等」机制级别的答案：epoll 只通知就绪，read 的拷贝是你的线程做的

最后那一句合起来才是完整的：

epoll 让「等」不再需要一个执行单位；Go 让「执行单位」变得很轻。 两者合起来，才是一个 M 管一万条连接这件事成立的完整理由。

一句话：这一路一直在做的事，是把「等待」从「执行」里一点点剥出去。

epoll 让哪件事变便宜了，哪两件事一点没碰？

变便宜的是「等待」本身，代价从「跟登记了多少条成正比」降到了 「跟这一刻真有几个就绪成正比」。 没碰的两件事：① 每次 epoll_wait 还是一次系统调用， 用户态/内核态的往返还在；② 数据拷贝还得你的线程亲自 read 出来， 拷贝那一段的等待还在。所以是「等待变便宜」，不是「等待消失」。

「就绪通知」和「完成通知」的区别，一句话怎么说？

epoll 是就绪通知（Reactor）：内核告诉你「这个 fd 现在读不会卡」， 剩下 read、EAGAIN、短读短写全是你的事。 io_uring 是完成通知（Proactor）：内核告诉你「这件事我办完了，结果在这」， 你去完成队列取就行。

io_uring 靠什么把系统调用省掉？

靠共享内存。它用 mmap 把提交队列 SQ 和完成队列 CQ 映射到用户态地址空间， 两边都能读写：你往 SQ 里塞请求不用喊内核，内核干完把结果放 CQ， 你去取也不用喊。整个 API 只有三个系统调用 （setup / enter / register），前两个就够用了。

为什么说「io_uring 比 epoll 快」是不准确的？

因为有 benchmark 显示，在没开 CPU 漏洞缓解的情况下 io_uring 没有优势甚至更慢。 epoll + read/write 的短路径 cache 友好、延迟低，而 io_uring 多出来的 队列管理和 task_work 调度在简单场景里是纯开销。 准确的说法是它换了一种成本结构：用内存和复杂度换掉系统调用的固定开销， 在高并发、大量小 I/O 时才划算。

整个系列的主线，用一句话怎么说？

把「等待」从「执行」里一点点剥出去。 一连接一线程是拿执行资源去承载等待； 非阻塞轮询把等换成问，线程自由了但白问太多； epoll 让内核记住名单、就绪才叫你，等待不再需要线程； io_uring 连「喊一声」的系统调用也搬进共享内存省掉了。

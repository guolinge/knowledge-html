## 01 · 新块摆哪

前两篇讲的都是「已经存在的数据怎么组织」。现在换一个方向：

> 我要写一个新块，磁盘上那么多块，该放在哪一块？

最傻的办法是从头扫一遍磁盘，找到空的地方就放。==但这样每写一块都要扫整块盘，一次都不用想就知道不可行。==

所以磁盘的空闲空间本身也得被管理起来。常见的有三种做法，一步步看它们各自补了什么。

---

## 02 · 空闲表法：把空洞列出来

既然只有空洞是重要的，那就专门给空洞建一张表：

| 序号 | 第一个空闲块号 | 空闲块个数 |
|---|---|---|
| 1 | 2 | 3 |
| 2 | 8 | 3 |
| 3 | 13 | 2 |
| … | | |

这张表的意思是：2 到 4 号块空着，8 到 10 号块空着，13 到 14 号块空着。

```flow
grid: true
groups:
  - { id: free, label: "被记下来的三块空闲区", tone: green }
nodes:
  - { id: t, label: 空闲表, sub: "序号 + 起始块 + 块数", row: 0, tone: violet }
  - { id: f1, label: "2 → 4", sub: "3 块连续空闲", row: 1, tone: green, group: free }
  - { id: f2, label: "8 → 10", sub: "3 块连续空闲", row: 1, tone: green, group: free }
  - { id: f3, label: "13 → 14", sub: "2 块连续空闲", row: 1, tone: green, group: free }
  - { id: used, label: "其它块", sub: "已经被文件占了", row: 2, tone: muted }
edges:
  - { from: t, to: f1, label: "一项管一段连续的空闲" }
  - { from: f1, to: used, label: "分配时从这些段里挑一段", dashed: true }
```

!!这张表天生只适合连续分配。!! 每一行记的是「一段连续的空闲区」，所以从里面挑出来的空间一定是连续的。

```compare
first: 什么时候好用
head: [说明]
rows:
  - 空闲区少的时候: [{ text: "表很短，扫描几行就能分配", tone: green }]
  - 空闲区多的时候: [{ text: "表变长，每次分配都要顺序扫一遍，查询效率大幅下降", tone: red }]
```

==它的根本问题是「表的行数 = 空洞的个数」。== 磁盘用久了必然碎片化，洞一多这张表就失控了。

## 03 · 空闲链表法：把空闲块串起来

换个思路：不在内存里维护一张表，而是**让空闲块自己串成一条链**。

每个空闲块里留一个指针，指向下一个空闲块在哪。内存里只要记住链头就行。

```flow
grid: true
nodes:
  - { id: head, label: "内存里一个指针", sub: "指向第一个空闲块", row: 0, tone: violet }
  - { id: f1, label: "空闲块 2", sub: "指针 → 8", row: 1, tone: green }
  - { id: f2, label: "空闲块 8", sub: "指针 → 13", row: 2, tone: green }
  - { id: f3, label: "空闲块 13", sub: "指针 → −1 结束", row: 3, tone: green }
edges:
  - { from: head, to: f1, label: "链头" }
  - { from: f1, to: f2 }
  - { from: f2, to: f3 }
```

分配的时候从链头取，回收的时候把块接到链头上。

```checklist
tone: cross
items:
  - 不能随机访问：想找第 100 个空闲块，得顺着链跳 100 次
  - 每一次跳都可能是一次磁盘 I/O，因为下一个块可能在磁盘的另一头
  - 指针本身占掉了空闲块的空间，可用的部分变少
```

空闲表和空闲链表有一个共同的上限：==它们都随「磁盘大小」线性增长。== 磁盘越大，表或链就越长，最后都会变得不实用。

## 04 · 位图法：一位管一块

第三种做法最省：

> 磁盘上的每一个块，都对应位图里的**一个二进制位**。0 表示空，1 表示已用。

就这么简单。一个 4KB 的块能放 `4 × 1024 × 8 = 32768` 个二进制位，也就是能管 32768 个块。

真实的样子长这样（每 4 位一组只是为了方便看，实际是连续的）：

```text
1111 1100 1111 1111 1000 1110 1101 1111 1111 0011 1...
```

读法：

```
第 1 位 = 1  →  0 号块被占用
第 2 位 = 1  →  1 号块被占用
...
第 7 位 = 0  →  6 号块空着
第 8 位 = 0  →  7 号块空着
```

```compare
first: 对比
head: [空闲表法, 空闲链表法, 位图法]
rows:
  - 占多少空间: ["每段一条记录，随空洞数增长", "每个空闲块多一个指针", { text: "每块一个 bit，固定不变", tone: green }]
  - 找一块空的: ["扫表，找到够大的段", "从链头取", { text: "扫位图找到第一个 0", tone: green }]
  - 能表示连续的块吗: ["能，每段就是连续的", "不能，块的顺序是随意的", "不能，但能立刻看出哪一段是空的"]
  - 随磁盘变大: [{ text: "变长", tone: red }, { text: "变长", tone: red }, { text: "线性增长，但基数极小", tone: amber }]
```

位图法最大的好处是==一张位图就能表示整块磁盘的占用情况，而且通过位运算可以一次检查 64 个块==。Linux 的 Ext 系列用的就是它，而且不只用于数据块，**inode 的分配也用位图管**，因为 inode 也是存在磁盘上的，也得知道哪个 inode 空着。

## 05 · 一个位图块，够管多大

现在算一笔账。假设按最朴素的结构来：

> 一个块的位图 + 跟着它的一串数据块

一个 4KB 的块能表示多少个块？

```
一个块的位数 = 4 × 1024 字节 × 8 位 = 2^15 = 32768 位
每一位管一个块 → 最多管 32768 个块
每个块 4KB → 总共能管 32768 × 4KB = 2^27 字节 = 128 MB
```

**只有 128MB。** 现在随便一个视频文件都比这大。

换成别的块大小也是一样的小，只是数字变一下：

```demo
widget: tuner
title: 一个位图块，最多管多大的空间
actions: false
hint: 拖动滑块换块大小
config:
  param: { label: 块大小, unit: 字节, values: [1024, 2048, 4096, 8192, 16384] }
  outputs:
    - { label: 能表示的块数, unit: 块, values: [8192, 16384, 32768, 65536, 131072], tone: blue }
    - { label: 最大能管的空间, unit: MB, values: [8, 32, 128, 512, 2048], tone: amber }
```

把块调大能缓解，但很快就到顶了。而且块太大会让「读 1 个字节也要捞一大块」的浪费更严重。

==真正的问题不是块多大，而是「用一张位图管整个磁盘」这个前提本身。==

**解决办法：别用一张位图，把文件系统切开。**

## 06 · 块组：把文件系统切成很多小块

既然「一张位图 + 一串块」只能管 128MB，那就 ==让这个结构重复出现 N 次==：

```arch
svg: fs-ext2-blockgroup
caption: 整块盘被切成一个个块组，每个块组内部都有一份自己的位图、自己的 inode 列表和自己的数据块。
```

在 Linux 里，这样一个单元叫一个**块组**。文件系统就是「引导块 + N 个块组」排下去。

块组内部有六样东西，==它们各自解决一个具体问题==：

```spec
title: 一个块组里有什么
subtitle: Ext2 的划分方式
tone: violet
rows:
  - k: 超级块
    v: |
      文件系统的全局信息：inode 总数、块总数、每个块组多少 inode、每个块组多少块……

      **这一份是全局的，不是这个块组自己的。**
  - k: 块组描述符
    v: |
      每个块组的空闲块数、空闲 inode 数。

      它的范围也是**所有块组**，不是只有自己。
  - k: 数据位图
    v: |
      这个块组里哪些数据块空着。

      一个块组有多少块，就需要多少位。这才是 128MB 那个上限的作用点。
  - k: inode 位图
    v: |
      这个块组里哪些 inode 空着。

      inode 也是磁盘上的资源，也需要记账。
  - k: inode 列表
    v: |
      这个块组里所有的 inode，一个一个挨着排。

      inode 是固定大小的，所以「第几个 inode」可以直接算出它的位置。
  - k: 数据块
    v: |
      文件真正的内容（以及目录的内容）。

      占块组里的绝大部分空间。
```

==位图只管得住自己这个块组==，所以上限从「整个磁盘 128MB」变成了「每个块组 128MB」，而块组可以有很多个。磁盘多大都能用同一套结构拼出来。

## 07 · 为什么每个块组里都重复放全局信息

回头看那个看起来很奇怪的设计：超级块和块组描述符是**全局信息**，却要在**每个块组**里都存一份。

```cards
cols: 2
items:
  - title: 理由一：丢了能救回来
    tag: 容错
    tone: red
    body: |
      超级块里有「inode 总数、块总数」这些信息。
      ==它没了，整个文件系统的结构就无从谈起==。
      你不知道该按什么规矩去解析剩下那些字节。

      如果每个块组都有副本，块组 0 的那份坏了，还能拿块组 1 的来恢复。
  - title: 理由二：离数据近一点
    tag: 性能
    tone: green
    body: |
      读一个文件时，需要查它的 inode、查数据块的位置、再读数据。

      如果这些都在同一个块组里，磁头移动距离短；
      如果 inode 全在最前面、数据全在最后面，每次读文件都要横跨整个磁盘。
      ==把管理数据和被管理数据放在一起，减少了寻道和旋转的等待。==
```

### Ext4 后来改了

Ext2 是「每个块组都存一份」。Ext4 觉得太浪费了，改成**稀疏**存放：

> 超级块和块组描述符只写在块组 0、块组 1，以及其他编号可以表示为 **3、5、7 的幂** 的那些块组里。

也就是说块组 2 号往后，只有 3、9、27、81、243、729…… 这些编号的块组带着备份。

```compare
first: 版本
head: [超级块备份放在哪, 代价]
rows:
  - Ext2: ["每个块组都放一份", "占空间多，但几乎没有单点故障"]
  - Ext4: [{ text: "块组 0、1 和 3/5/7 的幂次块组", tone: green }, "省了空间，同时保留了一串间隔越来越远的备份点"]
```

间隔取幂次而不是固定间隔，是为了让备份分布得越来越稀疏。局部损坏（比如一块坏道）不会一次带走所有副本。

---

```quiz
- q: 空闲表法和空闲链表法都不适合大文件系统，根本原因是什么？
  a: |
    它们的管理成本都随「磁盘有多大」线性增长。空闲表要记录每一个空洞，
    空闲链表要给每一个空闲块配一个指针；磁盘越大、碎片越多，这两样就越失控。
    位图法的成本是每块一位，基数小得多，而且一个位图块就能管住三万多个块。
- q: 一个 4KB 的位图块，为什么只能管 128MB？
  a: |
    因为一个块里的位数 = 4096 × 8 = 32768 位，一位管一个块，所以最多管 32768 个块；
    每块 4KB，乘起来就是 128MB。
    解决的办法不是把块调大，而是把这个「位图 + 一串块」的结构重复成很多份，也就是块组。
- q: 每个块组都放一份超级块，为什么说是「浪费但值得」？
  a: |
    超级块是全局信息，每个块组存一份确实是冗余。
    但它买到两件事：一是超级块被写坏时能用别的块组的副本恢复整个文件系统；
    二是把管理数据和被管理数据放在一起，减少了磁头寻道的距离。
    Ext4 后来用稀疏存放把浪费压下去了，但这两个好处都还保留着。
- q: inode 也需要位图管理吗？
  a: |
    需要。inode 也存在磁盘上，也是有限资源。
    一个文件系统能建多少个文件，在格式化的时候就由 inode 总数定死了。
    所以创建文件时要先通过 inode 位图找到一个空位，跟分配数据块是同一个道理。
```

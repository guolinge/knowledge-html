MySQL 为什么用 B+Tree 做索引

从「慢的不是算，是搬」的成本模型出发，把 BST、AVL/红黑树、Hash、B-Tree 逐个淘汰，看 B+Tree 的三处改动怎么被磁盘约束一步步逼出来，最后落到 InnoDB 两棵树的分工。

标签 B+ 树 索引选型 磁盘 IO 回表 InnoDB

线上慢查询排查到最后，常常停在这样一个问题上：一张千万行的 user 表，WHERE email = 'x' 跑了 3 秒，加个索引变成 3ms。同样是查一行，为什么差一千倍？答案不在 SQL 写法，而在索引背后的数据结构。

这篇笔记沿原文的脊柱线走：一场选型淘汰赛。先立靶：胜负手是磁盘访问；再逐个淘汰教科书结构；最后看 B+Tree 怎么被一步一步逼出来。

01一张地图：整场淘汰赛

下面这张图把全文同时摊开：上带是成本模型（靶子），下带是五个候选按淘汰顺序排开。每个候选的 sub 就是它的死因，每条边是「为什么转向下一个」。点图上的框可以从任何你熟悉的结构进去看，底下几条导览按淘汰赛顺序走一遍。

一个读者熟悉的类比：页访问像 HTTP 请求，昂贵往返，能省就省；内存比较像本地函数调用，免费。数据结构选型就是尽量减少「请求数」 —— 和前端合并接口调用是同一个决策原则。

02靶心：慢的不是算，是搬

把 1 秒和 1 毫秒的差距拆开，先看两种路径各付什么账：

账单全表扫描索引定位
怎么找到行所有数据页逐页搬进内存自顶向下只下探 3~4 层
页访问次数~62.5 万次3~4 次
大头花在哪搬页（磁盘，ms 级）下探（页内二分，内存，免费）
总延迟分钟级毫秒级

大多数人的误判是以为慢在「比较了千万次」。比较发生在 CPU 里，是纳秒级；搬页发生在磁盘上，是毫秒级 —— 两者差着五到八个数量级。所以「把 SQL 写得再聪明」救不活慢查询，「加个索引」能救活。

数据涨了十倍百倍呢？这是成本模型最值钱的一个推论：

⚖

索引把查询成本从「跟表大小成正比」变成「跟树高成正比」。 表从 1000 万行涨到 10 亿行，索引查询的成本几乎不涨，全表扫描线性恶化。

顺带把 SSD 时代的口径对齐：

💾

SSD 没有寻道旋转延迟，随机读比 HDD 快两个数量级，「10ms」偏保守。 但 SSD 的随机读依然比内存慢 4~6 个数量级，页访问次数依旧是第一成本项。 成本模型的关键从来不是 10ms 这个数字，是「内存与磁盘之间的数量级鸿沟」这个结构事实。

03淘汰赛上半场：瘦高树家族

BST：每层一次寻道，30 层就是 30 次 IO

BST 的问题出在扇出——每个节点只分出几个孩子。100 万行树高约 20，10 亿行约 30。每下一层 = 一次页访问，20~30 次随机读在 HDD 上就是 200~300ms。树高换算有一条直观的账：

扇出10 亿行的树高点查的页访问
扇出 2~30 层30 次 IO
扇出 100~5 层5 次 IO
扇出 1000~3 层3 次 IO

扇出是树高唯一的旋钮：树高按 log(扇出) 收缩，扇出每大十倍，树高砍掉三分之二。BST 的问题不是「查找算法错」，是每节点两个孩子这个形状天生与磁盘为敌。

还有第二刀。普通 BST 不保证平衡，顺序插入 1,2,3,4,5… 会退化成链表：

插入 1 根
插入 2 只能挂在右边
插入 3 继续右挂
插入 n… 退化成链表 · 查找 O(n)

真实世界的键常常就是按序插入的（自增 id、时间戳），退化不是边角情况，是大概率事件。

AVL / 红黑树：平衡救不了树高，旋转触盘才是死穴

「保证 O(log n) 树高」的直觉到此为止。同一操作在两种介质上结的账完全不同：

一次旋转内存里磁盘上
动作改几个指针变量父块/本块/兄弟块的 读-改-写
IO 次数0 次~3 次
成本纳秒级~30ms

AVL 的平衡约束是精确等式（高度差 ≤ 1），频繁插入下几乎每次都可能触发旋转；红黑树放宽了约束、旋转少了些，但扇出仍是 2，树高一分没治 —— 两条病根只治了半条。

补一个诚实的细节：红黑树在内存场景（std::map、TreeMap）表现很好。它输的不是平衡不好，是平衡的代价模型错了 —— 为内存设计的平衡，拿到磁盘上结算时币种不对。

至此逼出两条硬诉求：高扇出压树高，重平衡别频繁触盘。给节点一个弹性区间（⌈m/2⌉~m 个孩子），多数插入落在区间内就无需重平衡。这两条合起来，就是下一轮的 B-Tree。

04淘汰赛下半场：Hash 与 B-Tree

Hash：等值封神，范围交白卷

Hash 不能一句话打死，要说清哪里行、哪里废：

能力B-Tree 索引Hash 索引
等值 = / <=>支持支持，且很快
范围 < > BETWEEN支持不支持
ORDER BY可加速不能加速
两值间行数估算支持（range optimizer 依赖它）无法估算
联合索引最左前缀支持不支持

等值 O(1) 确实快，所以 MEMORY 引擎才提供 Hash 索引。但哈希把相邻键打散到不同桶里：范围查询只能逐个 key 重算哈希，没有「下一个」的概念。索引一半的价值就在有序，Hash 把有序性彻底破坏了。

🔀

能不能「既要又要」？InnoDB 的自适应哈希索引（AHI）就是这个补丁： 观察到某些等值查询高频命中，就在内存里建哈希捷径，绕开 B+Tree 下探。 但它是内存结构、自动判定、不可手工指定 —— 主结构保序，旁路加速等值，主次不能颠倒。

B-Tree：方向对了，还差临门一脚

B-Tree 一次性接住两条诉求：多叉治树高，弹性区间治触盘。但它的内部节点同样挂着行数据，由此产生两个后果：

同一页 16KBB-Tree 内部节点B+Tree 内部节点
页里放什么[K1][数据1][P1][K2][数据2][P2]…[K1][P1][K2][P2]…[K682][P682]
能放的键数几十个（数据几十到几百字节）几百个（纯键）
扇出掉一个数量级 → 树变高拉满
点查的有效载荷一半是这次查询用不上的行数据几乎全部是搜索路径

后果二在范围查询上。数据散落在内部节点和叶子之间，拿「下一个键」必须做中序遍历：叶子 → 内部 → 叶子 → 内部，来回跳，每次跳跃都是一次随机 IO —— 和 1.1 立靶时最怕的「随机搬页」是同一个病。

🧵

回看这条链：扇出太小 → 高扇出（B-Tree）→ 数据挤在内部节点稀释了扇出 → 把数据下沉。 没有一步是「发明」，每一步都是「还债」—— 还树高债、旋转债、稀释债。 是磁盘约束自己在投票，不是教科书在给结论。

05B+Tree：三处改动，逼出胜势

先看结构本身。下面这张图把一棵 B+Tree 和它的页内布局同时摊开：上半是树（键怎么路由），右侧是两种 16KB 页的内部布局。点框看零件；四条导览分别走「一次点查」「一次范围扫描」「扇出算术」和「键为什么出现两次」。

三处改动逐条对账，每一处都是前文某个死因的直接解药：

改动直接治什么付出什么
内部节点只存键扇出不再被数据稀释 → 3~4 层装下数亿行键在内部冗余出现
数据全部下沉叶子任意 key 深度一致 → 尾延迟稳定点查必须走到叶子
叶子串成链表范围/排序/分页变成顺序滑行链表指针的额外空间

它相对 B-Tree 没有引入任何新机制，只是把「数据该放哪」重新排布了一遍。结构设计的要点常常不在发明，而在摆放。

别只听好话：代价与五结构横评

B+Tree 的赢不是免费，先把它自己的四张账单摆上：

  • 点查也要走到叶子，路径比 B-Tree 命中内部节点略长；但 B+Tree 更矮，实际 IO 未必更多，两股力互相抵消，这里不下绝对结论
  • 叶子链表的指针占额外空间
  • 键在内部节点冗余出现（分隔值在叶子又存一遍）
  • 实现复杂度：分裂、合并、分隔键上提，比 BST 的旋转复杂得多；数据库内核付得起，自研缓存层未必

前三条的共性是「空间换结构」：为读快预支空间。存储敏感的场景（超长行、超宽索引）要重新掂量。B+Tree 的赢建立在读写比远大于一的 OLTP 场景上，不是无条件全胜。

06落地 InnoDB：两棵树的分工

抽象结构讲完，接回现实。核心一句：InnoDB 里没有独立的行存储，数据就是索引。下面这张图把两棵树和两类查询的完整路径摊开：

回表多花的这一次遍历值不值，取决于查询要多少列。落到 SQL 上：

CREATE TABLE user (
  user_id   BIGINT UNSIGNED AUTO_INCREMENT NOT NULL,
  username  VARCHAR(256) NOT NULL,
  email     VARCHAR(256) NOT NULL,
  PRIMARY KEY (user_id)
);

CREATE INDEX email_index ON user(email);

-- 覆盖：email 索引里就有 email，不回表（Extra = Using index）
SELECT email FROM user WHERE email = 'x';
-- 非覆盖：username 不在 email 索引里，必须回表
SELECT username FROM user WHERE email = 'x';

就算什么都不做，每张表也必然长出一棵 B+Tree —— 聚簇索引的选取是一条决策链：

有 PRIMARY KEY？
有全列 NOT NULL 的 UNIQUE？
隐藏聚簇索引 GEN_CLUST_INDEX 6 字节单调递增 row id · 无论哪种，表都是一棵 B+Tree

主键怎么选：自增 vs UUID 撬动的是树的物理形态

主键即聚簇索引的排序键，它决定「新的数据往哪长」：

维度自增整型UUIDv4 随机
插入位置恒在最右叶子遍布全树
页分裂频率低（顺序追加）高（四处开花）
写放大小大
范围局部性时序行物理相邻行分散在非连续叶页

确实需要全局唯一、又不想付随机主键的代价时，折中是有序 UUID（如 UUIDv7，时间戳打头）： 让插入近似顺序，页分裂大幅减少 —— 唯一性和顺序性各拿一头。

07不是银弹：B+Tree 的边界

前面说「写代价可控」，那是相对 AVL 的旋转而言；相对纯顺序追加，页分裂依然是要付的账，随机写下的写放大约 2~3 倍。替代路线是 LSM-Tree：

维度B+TreeLSM-Tree
写路径随机定位页 → 满了分裂顺序追加 memtable/日志 → 后台 compaction
读放大低（3~4 层直达）高（多层归并，合并未完成时更慢）
写放大页分裂 2~3 倍低（顺序追加）
范围查询叶子链表顺序扫弱（跨层归并）
适用负载读多写少 · OLTP写密集 · 日志/时序追加

RocksDB、Cassandra、LevelDB 都是 LSM 阵营。MySQL 为什么不整体换过去？因为 OLTP 的负载画像摆在那：读写比远大于一，范围查询和点查是绝对主流，事务需要就地读最新值 —— 这些全是 B+Tree 的主场。

🧭

B+Tree 是「读多写少 + 强范围查询 + 按块取」这一组约束下被逼出来的最优解，不是唯一解。 选型的终点永远是约束匹配，不是「谁先进」。

想再往深挖的钩子：LSM 的 compaction 策略；InnoDB 给 B+Tree 打的两个补丁（change buffer、自适应哈希索引）；二级索引条件下推（ICP）怎么再省一步回表。

合上页面，试着回答

「慢的不是算，是搬」——千万次比较为什么可以当免费，62.5 万次搬页为什么致命？

比较发生在 CPU 里，纳秒级；搬页发生在磁盘上，毫秒级，两者差 5~8 个数量级。 全表扫描的成本 = 页访问次数 × 10ms ≈ 分钟级；索引把同样的查询变成「下探 3~4 页」。 树每多一层就是多一次页访问，所以树高 = IO 次数，整场淘汰赛的账单都记在这条等式上。

B-Tree 已经多叉 + 自平衡了，差的临门一脚是什么？B+Tree 的三处改动各治什么病？

差在内部节点也存数据：16KB 的一半给了行数据，扇出掉一个数量级；范围查询还要叶子 → 内部 → 叶子来回跳。 三处改动：内部只存键（治扇出稀释）、数据下沉叶子（治深度不齐，尾延迟稳定）、叶子成链（治范围回溯，变成顺序读）。 它没有引入新机制，只是把「数据该放哪」重新排布了一遍。

二级索引的叶子为什么存主键值而不是行指针？什么时候能不回表？

行会随页分裂移动，行指针会失效；主键值永远稳定，这是 B+Tree 结构决定的选择。 查询要的列全部在二级索引里时不用回表 —— 覆盖索引，EXPLAIN 里 Extra = Using index。 主键要短也由此而来：每个二级叶子都冗余一份主键，主键长度是所有二级索引体积的杠杆。

UUIDv4 当主键，伤害发生在哪条路径上？

插入点遍布全树 → 页分裂四处开花 → 写放大、页填充率参差、时序行分散在非连续叶页。 自增主键则恒在最右叶子追加，页只填 15/16，分裂极少。两者伤害的不是「查找逻辑」， 是 B+Tree 的物理生长方式 —— 所以主键选择是给 B+Tree 选「新数据往哪长」。

线上慢查询排查到最后，常常停在这样一个问题上：一张千万行的 user 表，`WHERE email = 'x'` 跑了 3 秒，加个索引变成 3ms。同样是查一行，为什么差一千倍？答案不在 SQL 写法，而在索引背后的数据结构。

这篇笔记沿原文的脊柱线走：**一场选型淘汰赛**。先立靶：胜负手是磁盘访问；再逐个淘汰教科书结构；最后看 B+Tree 怎么被一步一步逼出来。

## 02 · 靶心：慢的不是算，是搬

把 1 秒和 1 毫秒的差距拆开，先看两种路径各付什么账：

```compare
first: 账单
head: [全表扫描, 索引定位]
rows:
  - 怎么找到行: [所有数据页逐页搬进内存, 自顶向下只下探 3~4 层]
  - 页访问次数: [{ text: ~62.5 万次, tone: red }, { text: 3~4 次, tone: green }]
  - 大头花在哪: [搬页（磁盘，ms 级）, 下探（页内二分，内存，免费）]
  - 总延迟: [分钟级, 毫秒级]
```

大多数人的误判是以为慢在「比较了千万次」。比较发生在 CPU 里，是纳秒级；搬页发生在磁盘上，是毫秒级 —— ==两者差着五到八个数量级==。所以「把 SQL 写得再聪明」救不活慢查询，「加个索引」能救活。

数据涨了十倍百倍呢？这是成本模型最值钱的一个推论：

```callout
tone: violet
icon: ⚖
quote: true
text: |
  索引把查询成本从「跟表大小成正比」变成「跟树高成正比」。
  表从 1000 万行涨到 10 亿行，索引查询的成本几乎不涨，全表扫描线性恶化。
```

顺带把 SSD 时代的口径对齐：

```callout
tone: amber
icon: 💾
text: |
  SSD 没有寻道旋转延迟，随机读比 HDD 快两个数量级，「10ms」偏保守。
  但 SSD 的随机读==依然比内存慢 4~6 个数量级==，页访问次数依旧是第一成本项。
  成本模型的关键从来不是 10ms 这个数字，是「内存与磁盘之间的数量级鸿沟」这个结构事实。
```

## 03 · 淘汰赛上半场：瘦高树家族

### BST：每层一次寻道，30 层就是 30 次 IO

BST 的问题出在**扇出**——每个节点只分出几个孩子。100 万行树高约 20，10 亿行约 30。每下一层 = 一次页访问，20~30 次随机读在 HDD 上就是 200~300ms。树高换算有一条直观的账：

```compare
first: 扇出
head: [10 亿行的树高, 点查的页访问]
rows:
  - 扇出 2: [{ text: ~30 层, tone: red }, 30 次 IO]
  - 扇出 100: [~5 层, 5 次 IO]
  - 扇出 1000: [{ text: ~3 层, tone: green }, 3 次 IO]
```

==扇出是树高唯一的旋钮==：树高按 log(扇出) 收缩，扇出每大十倍，树高砍掉三分之二。BST 的问题不是「查找算法错」，是每节点两个孩子这个形状天生与磁盘为敌。

还有第二刀。普通 BST 不保证平衡，顺序插入 1,2,3,4,5… 会退化成链表：

```flow
grid: true
nodes:
  - { id: a, label: "插入 1", sub: "根", row: 0, kind: backend }
  - { id: b, label: "插入 2", sub: "只能挂在右边", row: 1, kind: backend }
  - { id: c, label: "插入 3", sub: "继续右挂", row: 2, kind: backend }
  - { id: d, label: "插入 n…", sub: "退化成链表 · 查找 O(n)", row: 3, kind: external }
edges:
  - { from: a, to: b, label: "右孩子" }
  - { from: b, to: c, label: "右孩子" }
  - { from: c, to: d, label: "右孩子" }
```

真实世界的键常常就是按序插入的（自增 id、时间戳），退化不是边角情况，是大概率事件。

### AVL / 红黑树：平衡救不了树高，旋转触盘才是死穴

「保证 O(log n) 树高」的直觉到此为止。同一操作在两种介质上结的账完全不同：

```compare
first: 一次旋转
head: [内存里, 磁盘上]
rows:
  - 动作: [改几个指针变量, 父块/本块/兄弟块的 读-改-写]
  - IO 次数: [{ text: 0 次, tone: green }, { text: ~3 次, tone: red }]
  - 成本: [纳秒级, ~30ms]
```

AVL 的平衡约束是精确等式（高度差 ≤ 1），频繁插入下几乎每次都可能触发旋转；红黑树放宽了约束、旋转少了些，但扇出仍是 2，树高一分没治 —— ==两条病根只治了半条==。

补一个诚实的细节：红黑树在内存场景（`std::map`、`TreeMap`）表现很好。它输的不是平衡不好，是==平衡的代价模型错了== —— 为内存设计的平衡，拿到磁盘上结算时币种不对。

至此逼出两条硬诉求：**高扇出压树高**，**重平衡别频繁触盘**。给节点一个弹性区间（⌈m/2⌉~m 个孩子），多数插入落在区间内就无需重平衡。这两条合起来，就是下一轮的 B-Tree。

## 04 · 淘汰赛下半场：Hash 与 B-Tree

### Hash：等值封神，范围交白卷

Hash 不能一句话打死，要说清哪里行、哪里废：

```compare
first: 能力
head: [B-Tree 索引, Hash 索引]
rows:
  - 等值 = / <=>: [支持, { text: 支持，且很快, tone: green }]
  - 范围 < > BETWEEN: [支持, { text: 不支持, tone: red }]
  - ORDER BY: [可加速, { text: 不能加速, tone: red }]
  - 两值间行数估算: [支持（range optimizer 依赖它）, { text: 无法估算, tone: red }]
  - 联合索引最左前缀: [支持, { text: 不支持, tone: red }]
```

等值 O(1) 确实快，所以 MEMORY 引擎才提供 Hash 索引。但哈希把相邻键打散到不同桶里：范围查询只能逐个 key 重算哈希，没有「下一个」的概念。==索引一半的价值就在有序==，Hash 把有序性彻底破坏了。

```callout
tone: violet
icon: 🔀
text: |
  能不能「既要又要」？InnoDB 的自适应哈希索引（AHI）就是这个补丁：
  观察到某些等值查询高频命中，就在内存里建哈希捷径，绕开 B+Tree 下探。
  但它是内存结构、自动判定、不可手工指定 —— ==主结构保序，旁路加速等值==，主次不能颠倒。
```

### B-Tree：方向对了，还差临门一脚

B-Tree 一次性接住两条诉求：多叉治树高，弹性区间治触盘。但它的内部节点同样挂着行数据，由此产生两个后果：

```compare
first: 同一页 16KB
head: [B-Tree 内部节点, B+Tree 内部节点]
rows:
  - 页里放什么: ["[K1][数据1][P1][K2][数据2][P2]…", "[K1][P1][K2][P2]…[K682][P682]"]
  - 能放的键数: [{ text: 几十个（数据几十到几百字节）, tone: red }, { text: 几百个（纯键）, tone: green }]
  - 扇出: [掉一个数量级 → 树变高, 拉满]
  - 点查的有效载荷: ["一半是这次查询用不上的行数据", 几乎全部是搜索路径]
```

后果二在范围查询上。数据散落在内部节点和叶子之间，拿「下一个键」必须做中序遍历：叶子 → 内部 → 叶子 → 内部，来回跳，每次跳跃都是一次随机 IO —— 和 1.1 立靶时最怕的「随机搬页」是同一个病。

```callout
tone: violet
icon: 🧵
quote: true
text: |
  回看这条链：扇出太小 → 高扇出（B-Tree）→ 数据挤在内部节点稀释了扇出 → 把数据下沉。
  没有一步是「发明」，每一步都是「还债」—— 还树高债、旋转债、稀释债。
  是磁盘约束自己在投票，不是教科书在给结论。
```

## 05 · B+Tree：三处改动，逼出胜势

先看结构本身。下面这张图把一棵 B+Tree 和它的页内布局同时摊开：上半是树（键怎么路由），右侧是两种 16KB 页的内部布局。点框看零件；四条导览分别走「一次点查」「一次范围扫描」「扇出算术」和「键为什么出现两次」。

```arch
svg: bt-anatomy
caption: ==内部节点是目录，叶子是正文。== 键在内部分隔、在叶子落地 —— 同一条记录在树上出现两次：一次当路标，一次当数据。
parts:
  root:
    label: 根 [12 | 30]
    sub: 只存分隔键
    detail: 内部节点是纯路标：页内二分找到最后一个小于目标键的分隔值，沿它右侧的孩子指针下探。上层访问最频繁，==常驻 buffer pool==，真正落盘的往往只有最后一两层。
  mid1:
    label: 中间 [5 | 8]
    sub: 键是分隔值
    detail: 左子树的所有值都小于它，右子树都大于它。每节点最多 m 个孩子、非根至少 ⌈m/2⌉ 个 —— ==这个弹性区间让绝大多数插入只是塞一个键，不触发任何结构变化==。
  mid2:
    label: 中间 [18 | 24]
    sub: 键冗余出现
    detail: 分裂时中间键上提到父节点，它既留在叶 2 当最大键、又进父节点当分隔值 —— ==同一条键在树上出现两次：一次当路标，一次当数据==。冗余换来的是「每条查询路径等长」。
  mid3:
    label: 中间 [40 | 55]
    sub: 分裂才长高
    detail: 插入溢出 → 节点分裂、中间键上提；==只有根分裂时树才长高==。删除不足则与兄弟合并或借键。写平衡的代价被局部化在分裂/合并这一步。
  leaf1:
    label: 叶子 [5·8 + 整行]
    sub: 键挨着数据
    detail: 叶节点存键、数据（InnoDB 里是整行或主键）和指向下一叶子的指针。16KB 一页能装几百行。
  leaf2:
    label: 叶子 [18·24 + 整行]
    sub: 点查的终点
    detail: 所有数据都下沉到叶子，==每条记录的查找路径深度一致== —— 任意 key 的页访问次数相同，尾延迟稳定。
  leaf3:
    label: 叶子 [40·55 + 整行]
    sub: 范围扫到越界
    detail: 范围查询定位到起点叶子后，顺着 Pnext 水平滑行，扫到越界为止，==全程不回内部节点==。相邻叶页在磁盘上往往也相邻，吃满顺序读和预读红利。
  pageInner:
    label: 内部节点的 16KB
    sub: 全是键和页号
    detail: 按 8B 键 + 8B 指针裸算，16384 ÷ 16 ≈ 1024 项是上限；把页头、页目录这些固定开销算进去，常见估法落在几百到一千（原文取 682 的保守口径）。==精确值不重要，重要的是扇出从个位数跳到百位数==。
  pageLeaf:
    label: 叶子节点的 16KB
    sub: 键挨着数据 + Pnext
    detail: 数据密集但也按页组织 —— 范围扫描按「页」计 IO，不按「行」计：扫一万行只是滑过几十个叶页。
tours:
  - id: point
    label: "一次点查：三次页访问"
    steps:
      - { at: [root], text: "从根开始，页内二分。12 ~ 30 的区间 → 走中间那根指针。==第 1 次页访问==" }
      - { at: [mid2], text: "中间节点还是路标：18 ≤ x ≤ 24 → 下探。==第 2 次页访问==" }
      - { at: [leaf2], text: "叶子落地，整行就在这。==第 3 次页访问== —— 根和上层常驻内存时，落盘的常常只剩这一两次。" }
```

### 别只听好话：代价与五结构横评

B+Tree 的赢不是免费，先把它自己的四张账单摆上：

```checklist
tone: warn
items:
  - 点查也要走到叶子，路径比 B-Tree 命中内部节点略长；但 B+Tree 更矮，实际 IO 未必更多，两股力互相抵消，这里不下绝对结论
  - 叶子链表的指针占额外空间
  - 键在内部节点冗余出现（分隔值在叶子又存一遍）
  - 实现复杂度：分裂、合并、分隔键上提，比 BST 的旋转复杂得多；数据库内核付得起，自研缓存层未必
```

前三条的共性是「空间换结构」：为读快预支空间。存储敏感的场景（超长行、超宽索引）要重新掂量。B+Tree 的赢建立在读写比远大于一的 OLTP 场景上，不是无条件全胜。

```sql
CREATE TABLE user (
  user_id   BIGINT UNSIGNED AUTO_INCREMENT NOT NULL,
  username  VARCHAR(256) NOT NULL,
  email     VARCHAR(256) NOT NULL,

);

CREATE INDEX email_index ON user(email);

-- 非覆盖：username 不在 email 索引里，必须回表
SELECT username FROM user WHERE email = 'x';
```

## 07 · 不是银弹：B+Tree 的边界

前面说「写代价可控」，那是相对 AVL 的旋转而言；相对纯顺序追加，页分裂依然是要付的账，随机写下的写放大约 2~3 倍。替代路线是 LSM-Tree：

```compare
first: 维度
head: [B+Tree, LSM-Tree]
rows:
  - 写路径: [随机定位页 → 满了分裂, 顺序追加 memtable/日志 → 后台 compaction]
  - 读放大: [{ text: 低（3~4 层直达）, tone: green }, { text: 高（多层归并，合并未完成时更慢）, tone: red }]
  - 写放大: [页分裂 2~3 倍, { text: 低（顺序追加）, tone: green }]
  - 范围查询: [叶子链表顺序扫, { text: 弱（跨层归并）, tone: red }]
  - 适用负载: [读多写少 · OLTP, 写密集 · 日志/时序追加]
```

RocksDB、Cassandra、LevelDB 都是 LSM 阵营。MySQL 为什么不整体换过去？因为 OLTP 的负载画像摆在那：读写比远大于一，范围查询和点查是绝对主流，事务需要就地读最新值 —— ==这些全是 B+Tree 的主场==。

```callout
tone: violet
icon: 🧭
quote: true
text: |
  B+Tree 是「读多写少 + 强范围查询 + 按块取」这一组约束下被逼出来的最优解，不是唯一解。
  选型的终点永远是约束匹配，不是「谁先进」。
```

想再往深挖的钩子：LSM 的 compaction 策略；InnoDB 给 B+Tree 打的两个补丁（change buffer、自适应哈希索引）；二级索引条件下推（ICP）怎么再省一步回表。

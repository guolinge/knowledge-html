01它是什么：core 之上加了什么

先看两个包的分工差在哪：

维度corecrowd
认识的输入Rule[] —— 一棵纯数据的表达式树六种业务条件 —— 画像 / 事件 / 关系 / 人群包 / uid / rawSql
认识业务词吗一个都不认识认识，且有 45 行业务枚举
干的活把表达式树编译成 SQL把业务条件翻译成表达式树，再拼成集合运算
依赖谁knexcore + lodash + murmurhash
代码量1347 行 / 13 文件4475 行 / 27 文件
💡

crowd 干的事，用一句话说就是：

把「运营说的那句话」，变成 core 能吃的 Rule[]。

这中间隔着两个世界的距离：业务世界说「最近 7 天加购过」， core 只认「一个列、一个操作符、一个值」。

具体加了哪三件事

翻译

认识业务条件

六种条件各有各的语义，各有各的表。 每种条件自己知道自己该查哪张表、怎么写查询 —— 这部分 core 完全不管。

画像 → 查画像表
事件 → 查事件表 + 按人算次数
人群包 → 查人群包表
组合

做集合运算

架构篇讲的 AND / OR = UNION ALL + GROUP BY + HAVING。 还有第二层 include / exclude 的增删。

AND → HAVING count(uid) = N
OR  → 不加 HAVING
include → UNION ALL
exclude → NOT IN
方言

处理库差异

方言的调用全在这一层。 core 的 buildWhere 是静态方法， 签名里根本没有 dialect。 这是架构的一条裂缝（架构篇第 06 节讲过）。

crowd/src/dialect/
  getEventTable()  ← core 没有这个

04架构：业务条件进来，Rule[] 出去

先更正一个容易搞错的地方

⚠

没有统一的 adapter 层。

业务条件 → Rule[] 的翻译，是每种条件自己做的 —— 六种实现各写各的，没有一个公共的翻译函数。

条件它内部的转换方法代码量
画像adapter()（私有）+ addHackRules()233 行
事件getPropRules / getBaseRules / buildTimeRangRules / createMapPropRule …（十几个）906 行
关系getDetailBaseRule / getPropRules / buildDetailSql / addHackRules …715 行
uid / 人群包 / rawSql没有 —— 太简单，直接用141 / 134 / 107 行
⚠

addHackRules 在 portrait.ts 和 relation.ts 里各有一份，逐字节相同。

这是复制粘贴的重复代码 —— 改一处不会同步另一处。 看到「这里的行为不对」时，记得两份都要改。

翻译长什么样：以画像为例

portrait.ts 里的 adapter() 是递归函数，处理一棵条件树：

adapter(rules) 单个条件或数组
遍历每个 rule
有 'logic'？ 是树
有 'op'？ 是叶子
递归 adapter(items) 保持 logic 不变
有 'dateType'？ 时间条件
直接改名 name → column
展开成 AND 子树 调方言或 utils
throw 条件错误

五个出口各产出什么：

分支产出真实数据
有 logic递归，结构不变{ logic: 'OR', items: [...] } → 递归后塞回去
有 dateType\n且是相对时间戳调方言，展开成 AND 子树{ op: Gte, name: '..._time', value: 30 } → { logic: AND, items: [3 个 Expression] }
有 dateType\n其它时间调 utils，展开成 AND 子树同上，但生成的是通用 Rule
有 rawValue改名 + 透传{ op: Eq, name: 'c', rawValue: 'a+b' } → { column: 'c', op: Eq, rawValue: 'a+b' }
普通条件只改名{ op: IN, name: 'city', value: ['杭州'] } → { column: 'city', op: IN, value: ['杭州'] }
都不是throwportrait adapter: 条件错误: {...}
💡

看第 4 和第 5 行 —— 大部分条件其实只做了一件事：把 name 改成 column。

真正有分量的只有时间条件那一支（展开成一棵子树）。 翻译之所以「轻」，是因为两套词汇用的是同一个树形结构。

05架构：时间条件为什么会「膨胀」

一个输入条件，变成一棵子树。 这是整个翻译里最有内容的一步。

输入 业务条件 1 行 
{ op: 'Gte', name: '..._opened_time',
  dateType: 'Relative', value: 30 }

业务侧说的是一句话：「开户时间在最近 30 天内」。

adapter遇到 dateType 分支
展开 时间表达式 变成两个 
{ op: 'Gte', column: '..._opened_time', value: 开始 }
{ op: 'Lte', column: '..._opened_time', value: 结束 }

因为「最近 30 天」在 SQL 里必须写成「>= 开始 AND <= 结束」。 一个语义，两个条件。

补丁某些操作符还要再加一个
补丁 addHackRules 再加一个条件 
如果是 '<' 或 '<='
  → 再加 { op: 'Gt', column: '...', value: 0 }

代码注释写着原因： > 对于 < 和 <= 的时间范围，需要加上 > 0 的限制条件， > 否则会筛选出值为 0 的数据。 「值为 0」在时间戳语义里代表「从没发生过」， 不加会被当成「很久以前发生过」。

包一层强制 AND
输出 Rule[] 一棵子树 
{ logic: 'AND', items: [ 3 个 Expression ] }

外面强制包一层 logic: 'AND'。 见下一节。

💡

这一支还暴露了架构的一条裂缝。

上面写着「调方言或 utils」—— 因为：

  • 相对时间 + 时间戳格式 → 调方言（两个库的包装不一样）
  • 其它时间 → 调 core 的 utils（getTimeRules，通用逻辑）

同一件事分了两条路，取决于属性格式。 而 getTimeRules 本身被三个文件调用：portrait / event / relation。

06取舍：三个「为什么」

为什么时间条件要强制包一层 AND

// portrait.ts · adapter()
const timeRules = addHackRules(rule.name, rule.op, timeExprs);
// 这里包装一层，因为 timeRules 必须是 And 的关系
// 而 result 这一层的关系可能是 Or
result.push({ logic: Logic.And, items: timeRules });

代码注释直接给了答案。 具体会错在哪：

假设 用户说的是 
「最近 3 天加购过，或者是 VIP」

顶层是 OR，左边是时间条件，右边是画像条件。

不包 展开直接塞进去
不包会怎样 三个条件平铺在 OR 里 
>= 开始   OR   <= 结束   OR   是 VIP

语义完全错了。 任何时间都满足「>= 开始」，所以左边这一支永远为真 —— 等于「所有人都要」。

包一层把三个绑成一个
包一层 三个变成一个整体 
(>= 开始 AND <= 结束)   OR   是 VIP

外层是 AND，把三个条件绑成一个节点， 再参与上层的 OR。语义就对了。

✅

这就是「展开」必须配「包一层」的原因。

展开把一个条件变成三个 —— 但它们在语义上仍然是同一个条件。 如果不包，上层逻辑会把它们当成三个独立的判断。

为什么没有一个统一的 adapter

因为六种条件的翻译逻辑差得太远。

条件翻译的难点
画像时间条件要展开、要补 hack 规则
事件事件名 + 时间范围 + 属性过滤 + 次数阈值，四件事都要处理
关系分 DETAIL / TIMES 两种形态，要判分区
uid / 人群包 / rawSql基本没有难点，直接用

硬抽一个公共层，只会得到一堆「参数不一样、分支不一样」的 if。 所以它选了「各写各的」，代价是 addHackRules 这种重复。

为什么方言调用散在这一层

因为方言是「业务条件遇到的具体问题」，不是「表达式树的通用问题」。

⚠

core 的 buildWhere 是静态方法，签名里没有 dialect —— 它不知道方言存在。

所以所有方言调用都落在 crowd 里，散在 portrait / event / relation 各自的分支里。

这是一条真实的架构裂缝。 好在它有边界： 方言方法都只返回「片段」或「表达式节点」，不生成 SQL（架构篇第 06 节）。

07自测

crowd 包在 core 之上加了哪三件事？

① 认识六种业务条件 —— 每种自己知道该查哪张表； ② 做集合运算 —— AND / OR（UNION ALL + GROUP BY + HAVING）和 include / exclude； ③ 处理库差异 —— 所有方言调用都在这一层，core 的 buildWhere 根本不知道方言存在。

有没有一个统一的 adapter 把业务条件翻译成 Rule[]？

没有。 翻译是每种条件自己做的 —— 六种实现各写各的，没有公共的翻译函数。 画像有私有的 adapter()，事件有十几个 getPropRules / getBaseRules 之类的函数， uid / 人群包 / rawSql 基本没有转换逻辑。 代价是 addHackRules 在 portrait 和 relation 里各有一份，逐字节相同。

「最近 30 天」这一个条件，为什么最后变成了三个条件？

因为它在 SQL 里必须写成 >= 开始 AND <= 结束 —— 一个语义，两个条件。 某些操作符（< / <=）还要再加一个 > 0，否则会把「值为 0」 误当成「很久以前发生过」（0 在时间戳语义里代表「从没发生过」）。

时间条件展开后，为什么要强制在外面包一层 logic: AND？

因为展开出来的三个条件在语义上仍然是同一个条件，但上层逻辑可能是个 OR。 不包的话，「最近 3 天 或 是 VIP」会变成 「>= 开始 或 <= 结束 或 是 VIP」—— 任何时间都满足「>= 开始」，左边这支永远为真，等于所有人都要。

读 crowd 包应该从哪个文件开始？

src/define.ts（43 行）。它是整个业务词汇表 —— 系统认识哪六种条件、有哪几个模块、查哪些表，全在这里。 然后再看 context.ts（入口），最后才进 entrepots/（实现）。

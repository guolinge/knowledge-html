同一个 read()，Go 和 Node 走了两条路

两套运行时都站在同一套系统调用上，分岔在「阻塞归谁承担」：Go 把它记进任务的状态（G 挂起、P 可转交），Node 把它外包给 4 条池线程、主线程只处理回调。栈、GC、抢占、并行度都是这条分岔的下游结果。

先把两个运行时的零件摆在一起

左边是 Go 二进制，右边是 Node 进程。两个框里各有四五个零件，底下都落到同一个操作系统。同一个 read() 在两边会停在不同的零件上 —— 这就是「语言框架的差别」具体指什么。

左边一个任务只花 2 KiB，所以能开几十万个；右边只有一条 JS 线程，所以你的代码一秒都不能卡。这两句话已经把后面所有差别都框住了。

你说对的那半句，和「只是内存和线程」

你画的梯子是对的，而且是对的层次：

你的代码 → 语言/运行时给的抽象 → 系统调用 → 硬件

不管 Go 还是 Node，最后都得用内核给的那一套：创建线程、申请内存、读写文件、收发网络包。这一层两边没有差别，差别在「谁去用、什么时候用、用完怎么收」。

但「差别就是怎么利用内存和利用线程」把结果说成了原因。内存和线程是材料，真正分开两条路的是四个职责的分工：

职责Go runtimeNode（V8 + libuv）
下一条执行什么调度器：G/M/P + 本地队列 + 窃取事件循环：一轮六个阶段，按阶段取回调
阻塞的调用谁去等能 poll 的交给 netpoll（G 挂起）；不能的让 M 陪着，P 转交网络交给 libuv poll；文件/DNS/crypto 交给线程池
内存谁回收runtime 的 GC：并发标记清扫，非分代、非压缩V8 的 GC：分两代，Scavenger 复制 + Mark-Compact
并行度谁决定GOMAXPROCS 个 P，同一刻最多这么多条 M 跑 Go 代码JS 只有一条线程；要更多就自己开 worker_threads

四行里最要命的是第二行。Go 让「等」变成任务的一个状态；Node 让「等」变成池子里一条线程的差事，而你的代码只负责处理回调。

这一条分岔，往下长出了后面所有差别：栈要不要可搬、GC 要不要抢占、代码能不能写出「阻塞」、并发到底是不是并行。

Go 侧：一次 socket 读，线程走人

先看 Go。读一个 socket，数据还没到：

G · 读 socket
M · 内核线程
netpoller
P 的本地队列
1read(fd)：内核返回 EAGAIN
2G 登记到 pollDesc，状态改成 Gwaiting
3同一条线程接着取下一个 G
4数据到了：G 放回 runnext

四步里最关键的是第 2 步：挂起的是 G，不是线程。 G 的栈（2 KiB 起步）还留在原地，寄存器里的现场被存进 g.sched，这条 M 转头就去跑别的 G 了 —— 内核从头到尾不知道发生过什么。

第 4 步之后，G 被某条 M 取到，从 gopark 里返回，接着往下读。它可能换了条线程，但代码里看不出来：conn.Read(buf) 就是一次普通调用。

⚖

这条路只对能 poll 的东西成立：socket、管道。

普通文件在 Linux 上加不进 epoll（epoll_ctl 直接返回 EPERM），Darwin/BSD 的 kqueue 对普通文件也不可靠 —— 所以读磁盘时线程只能陪着进内核。这时候保命的是另一条设计：M 陪内核，P 交出去，别的 G 继续跑。

Node 侧：一次 file 读，池子里的一条线程替你去等

同样一句「读」，Node 的走法完全不同：

JS 主线程
libuv 线程池
磁盘
事件循环队列
1fs.readFile：包成 uv_fs_t 投进池
2池线程真的阻塞在 read 上
3读完，数据在内核缓冲里

第 1 步返回得极快：主线程只是把一个任务投进池子，然后立刻回去跑别的 JS。真正阻塞的是池子里的那条线程，和你写的 JS 没有关系。

所以「Node 是单线程的」这句话只在说一件事：你的 JS 只在一条线程上跑。进程里其实有好几条：

⚠

反过来说，主线程一卡，整个进程就停摆。

本机实测：一段 200 ms 的纯计算循环里，一个 10 ms 的定时器触发 0 次。所以 readFileSync、大 JSON.parse、同步 crypto，在 Node 里不是「慢一点」，是把所有连接一起冻住。

要跑 CPU 密集的活，得自己开 worker_threads —— 它共享内存，但不共享事件循环。

Node 那个循环，一轮到底转几圈

「池子完成之后回调排进队列」，这个队列不是一个，而是按阶段分的几个：

阶段 1 timers 到期的定时器和 interval 回调先跑
setTimeout / setInterval delay 到了才执行 到期
阶段 2 pending callbacks上一轮推迟下来的 I/O 回调
阶段 2 pending callbacks 上一轮没做完的 I/O 回调在这里补跑
被推迟的 I/O 回调 例如某些 TCP 错误 补跑
阶段 3 poll取新 I/O —— 没事干就在这里等
阶段 3 poll 取新的 I/O 事件；没有活的时候，循环就停在这里等
可读 / 可写的 socket libuv poll 返回就绪 主战场
线程池完成的任务 fs / DNS / crypto 的回调 汇入
阶段 4 checksetImmediate 的回调在这一站
阶段 4 check setImmediate 的回调在这里跑
setImmediate 排在 poll 之后、下一轮之前 立即
阶段 5 close callbackssocket.on('close') 这类
阶段 5 close callbacks 句柄关闭时的收尾回调
socket.on('close') 句柄关掉之后触发 收尾
一轮结束 回到 timers每个阶段之间，先清 nextTick，再清 Promise 微任务

每一轮就是这五站，每站有自己的 FIFO 队列，进站之后把这个队列清空（或者达到回调上限）才走下一站。官方文档里还有一站 idle, prepare，只给内部用，写业务遇不到。

两个容易被忽略的位置：

  • poll 会阻塞。 没有定时器、没有 setImmediate 的时候，循环就停在 poll 等 I/O —— 这不是浪费，是省 CPU。
  • 每个阶段之间要清队列。 process.nextTick 排的回调，文档的原话是「在当前调用栈结束后、事件循环继续之前、任何其他排队的任务或阶段之前」执行；await 之后的代码（微任务）也插在这些间隙里。

Node 的「并发」不是同时执行，是排队轮流执行。 一条线程上，回调之间永远不会真的并行 —— 这也解释了为什么一个慢回调会拖住后面所有人。

内存：一个要扫几十万个栈，一个只扫一个堆

两种模型的差别，落到内存上就一句话：要扫的东西不一样多。

维度GoNode（V8）
栈每条任务一块，2 KiB 起；不够就换一块两倍大的，整段搬过去（上限 1 GB）只有一条 JS 栈，大小固定；本机递归 10384 层就 RangeError
堆怎么分一个堆，按 P 切分配区（mcache），常见路径不抢锁分两代：新生代（nursery / intermediate）+ 老生代
回收算法并发标记清扫，非分代、非压缩（源码注释原话）两套：Scavenger 复制新生代；Mark-Compact 收全堆并压缩
停世界要等什么等所有 P 到安全点；有 G 不肯让就用 SIGURG 抢它等主线程到安全点；堆上限本机约 4288 MiB
为什么这么选精度换并发：栈要能扫、能搬，所以必须有精确栈图和抢占分代假设：大多数对象很快死，复制活下来的少数更便宜

第五行是因果，值得单独说：Go 的 GC 是并发的，但它仍然需要短暂停世界，让所有 P 到一个「内存状态一致」的点。而 P 上跑的是几十万个 G —— 如果某个 G 在死循环里不肯到安全点，这次 GC 就卡住了。这就是 Go 必须有异步抢占的原因。

V8 这边没有这个问题：只有一个栈、一条主线程，等它到安全点就行。「要不要抢占」不是风格选择，是「你有多少个栈要停」的直接后果。

「语言框架」这个词，两边指的不是一回事

你说「它们各自实现了自己的一套抽象的系统，简单来说就是一个运行时」—— 这句在 Go 上很贴切，在 Node 上要拆开看。

  • 装进一个进程里的东西 两边的「运行时」都不是一个东西，是一组零件的装配方式
    • Go 的二进制 静态编译，一次装好，版本和语言绑死
      • 编译器产物 机器码，运行时不再改
      • runtime src/runtime 编进每一个二进制，不是外部依赖
        • 调度器 G / M / P 几十万个任务压到十几条线程上
        • netpoller socket 就绪通知
        • GC 并发标记清扫
        • 栈管理 2 KiB 起步，按需搬
      • 标准库 net 包直接用 netpoller，不经过 libc
    • Node 的进程 一个宿主程序，把三样东西装在一起，各自独立升版本
      • V8 13.6.233.17 执行 JS、JIT、管堆和 GC
      • libuv 1.52.1 事件循环、线程池、poll
      • 内建模块 fs / net / crypto / zlib —— 决定哪些活进线程池
      • node 可执行文件 把上面三样接起来，再暴露 process / Buffer 这些全局

差别在升级方式上：换 Go 版本，你换的是编译器和 runtime（调度器、GC 的策略可能一起变）；换 Node 版本，你同时换掉V8 和 libuv，JS 语法、GC 行为、I/O 实现都可能变。所以「Node 24 的 fs 比 Node 18 快」这种事，跟「Go 1.22 的调度器比 1.20 好」不是同一类变化。

最后一行是你原来那句话里缺的那块：Go 和 Node 的差别不是「同一个东西的两种实现」，而是「两套零件清单」。 你在 Go 里能指出 P、g0、本地队列，在 Node 里找不到对应物，只能找到事件循环、线程池、poll。

回到你那句话

原话是：

底层的差别就是怎么利用内存和利用线程，各自实现了自己的一套抽象的系统，最终接口都是操作系统规定的那一套。

前半句要改，后半句完全对。改完是这样：

一句话

两套运行时都站在同一套系统调用上。真正的分岔是「阻塞归谁承担」：Go 把它记进一个任务的状态（G 挂起、P 可转交），Node 把它外包给有限的线程池（主线程只处理回调）。

栈、GC、抢占、并行度，都是这条分岔的下游结果。

如果只能记三句话：

  1. Go 的任务多、线程少，因为「等」不占线程；Node 的线程也少，因为「等」被外包给了 4 条池线程。
  2. Go 的代码允许阻塞（那是任务级事件）；Node 的代码不允许阻塞（那是进程级事故）。
  3. Go 能抢你的代码，Node 不能 —— 因为 Go 有几十万个栈要停，Node 只有一个。

自测

为什么 Node 里一段 200 ms 的纯计算会把所有请求一起拖住，而 Go 里一个死循环只影响它自己？

Node 的 JS 只有一条线程：这段计算占着主线程，事件循环转不动，所有回调都排不上。 Go 里一个 G 占着一条 M 和 P，但 sysmon 会在 10 ms 后抢它，把 P 让给别的 G —— 受影响的是调度延迟，不是整个进程。

"Node 是单线程的" 这句话哪里不准确？

只对 JS 成立。进程里还有 V8 的后台线程、libuv 的事件循环和线程池（默认 4 条）、inspector 等。 本机实测：空转的 Node 进程 7 条线程，8 个并发 fs 读变成 11 条。

同样是读 4 KiB，读 socket 和读普通文件在 Go 里为什么走两条路？

socket 能设成非阻塞并用 epoll/kqueue 等就绪：G 挂起，线程走人。 普通文件在 Linux 上连 epoll 都注册不进去（EPERM），read 只能真的进内核阻塞 —— 这时让 M 陪着，把 P 交给别的 M。

为什么 Go 需要异步抢占，V8 不需要？

Go 的 GC 要停世界、让所有 P 到安全点，而这些 P 上跑着几十万个 G，必须保证每个都能被打断。 V8 只有一个 JS 栈、一条主线程，等它自己到安全点就够了。

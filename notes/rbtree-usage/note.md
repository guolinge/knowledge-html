## 01 · 先把「最好的树」这个想法放下

学完前五篇，很容易产生一个印象：红黑树是「正确」的平衡树，别的是妥协。

实际不是。每种树都在解决一个具体约束，红黑树的强项很窄，但恰好是很多系统最在意的那一条。

```compare
first: 树
head: [它的强项, 它为此放弃的]
rows:
  - "红黑树": ["任何一次插入 / 删除的代价都有硬上界（2 / 3 次旋转）", "树比 AVL 略高（最多 2 倍 log n），查找略慢"]
  - "AVL": ["树最矮，查找最快", "改树时可能连续旋转多处，单次代价没有这么好的上界"]
  - "B+ 树": ["一个节点装几百个键，几层就到底，磁盘上顺序读", "内存里更新代价高、实现重"]
  - "跳表": ["区间遍历天然是链表，实现简单", "内存开销更大，查找常数因子不如树"]
  - "哈希表": ["平均 O(1)，最快", "完全无序 —— 范围查询、排序、找最小都没有"]
```

所以真正该问的问题不是「哪个最快」，而是：==我这个系统的瓶颈是「查找次数」还是「单次改动的确定性」？==

## 02 · 红黑树真正的卖点：单次改动的硬上界

这是前两篇算出来的结论，Linux 内核文档也把它写在了最前面：

```callout
tone: violet
icon: 📌
quote: true
text: |
  红黑树和 AVL 相似，但**插入删除的最坏情况有硬上界**：
  ==插入最多 2 次旋转，删除最多 3 次。==
  查找略慢一点，但仍然是 O(log n)。
```

为什么这一条这么重要？因为「平均快」和「最坏也快」在很多场景里是两件事：

| 场景 | 为什么在意「单次改动的上界」 |
|---|---|
| 内核调度器 | 每次切换任务都要改树，改动期间可能持有锁 —— 改动时长直接影响别的 CPU 等锁多久 |
| 实时系统 | 一个偶发的长操作会让本应准时的任务超时 |
| 高并发数据结构 | 旋转多意味着锁持有久，多核争用变严重 |

AVL 的问题不在于它慢，而在于它的**代价分布更不稳定**：为了把高度差压到 1，一次插入可能需要沿着路径连续旋转多处。红黑树的规矩松一些（黑高相同），所以树高最多是 AVL 的两倍，但改动只影响极少数节点。

```compare
first: 指标
head: [红黑树, AVL]
rows:
  - 树高上界: ["2·log₂(n+1)", "约 1.44·log₂(n+2)"]
  - 查找: ["O(log n)，常数略大", "O(log n)，常数更小（树更矮）"]
  - 插入旋转: [{ text: "最多 2 次", tone: green }, { text: "最坏可达 O(log n) 次", tone: amber }]
  - 删除旋转: [{ text: "最多 3 次", tone: green }, { text: "最坏可达 O(log n) 次", tone: amber }]
  - 每个节点额外存: ["1 个颜色位", "1 个高度 / 平衡因子（通常是 int）"]
```

==红黑树是拿「树高最多两倍」换了「改动次数封顶」。==找到平衡树里最省心的那个点，这就是它在工程里被反复选中的原因。

## 03 · 内核：它出现在几乎所有「按顺序排队」的地方

Linux 内核自己的文档里列了一串用例，都是同一个模式：**一堆东西要按某个值排序，而且随时有人进出**。

```cards
cols: 2
items:
  - title: 进程调度 · CFS / EEVDF
    desc: "每个 CPU 一个 cfs_rq，里面的 tasks_timeline 是一棵按 vruntime（虚拟运行时间）排序的红黑树。挑下一个任务 = 取最左（最小）的那个。"
    tag: kernel/sched/fair.c
    tone: violet
  - title: epoll 的登记表
    desc: "struct eventpoll 里 rbr 是一棵红黑树，按 fd 编号存所有被监控的 epitem。增删监控 = 树操作。"
    tag: fs/eventpoll.c
    tone: blue
  - title: 高精度定时器
    desc: "所有待触发的定时器按到期时间排在红黑树上，每次取最早的那个。"
    tag: hrtimer
    tone: green
  - title: 虚拟内存区域（VMA）
    desc: "一个进程的所有内存映射按起始地址排序，缺页时按地址找它属于哪一段。"
    tag: mm
    tone: amber
  - title: ext3 目录项
    desc: "一个目录里的文件名按哈希排在红黑树上，查名字是树查找。"
    tag: fs/ext3
    tone: muted
  - title: 网络 HTB 调度器
    desc: "分层令牌桶的各个类按速率排在一棵红黑树上。"
    tag: net/sched
    tone: muted
```

这里的共同点是：**这类结构每一毫秒都可能被改动，而且改动发生在持锁的临界区里**。红黑树「改动只碰几个节点」这一条，直接决定了锁要持有多久。

```callout
tone: blue
icon: 🔍
text: |
  **调度器为什么不能直接用一个排好序的数组？**
  因为任务的 vruntime 会不断变化（每跑一次就往后挪），数组里挪一个元素要移动后面所有元素。
  红黑树让「挪位置」变成「删了再插」，代价 O(log n)，而且不会搬动别人。
```

`epoll` 特别值得看一眼，因为它同时用了两种结构，各管一件事：

```compare
first: 结构
head: [在 epoll 里是什么, 为什么是它]
rows:
  - "红黑树（rbr）": ["**登记表**：所有被监控的 fd 都在这", "要按 fd 快速找到、增删 —— 有序 + O(log n) 改"]
  - "链表（rdllist）": ["**就绪表**：此刻有数据的那些 fd", "只做「加进去 / 全取走」，不需要有序，也不需要查找"]
```

这个分工很重要：==红黑树的职责是「记住有谁」，不是「记住谁准备好了」。==「谁准备好了」由内核在事件到来时直接挂到链表上，所以 epoll_wait 的开销和登记了多少 fd 无关 —— 这是 epoll 比 select/poll 快的根本原因，而不是「红黑树比数组快」。

## 04 · 标准库：它成了「有序容器」的默认实现

C++ 和 Java 的标准库里，只要你说「我要一个按键排序的 map」，底层几乎一定是红黑树。

```compare
first: 语言 / 库
head: [具体是哪个容器, 证据]
rows:
  - "C++ (libstdc++)": ["std::map / std::set / std::multimap / std::multiset", "`stl_tree.h` 里 `enum _Rb_tree_color { _S_red = false, _S_black = true }`"]
  - "C++ (libc++)": ["同上", "`__tree` 的注释直接写着 \"is a red-black-tree implementation\""]
  - "Java": ["TreeMap / TreeSet", "JDK 注释：「A Red-Black tree based NavigableMap implementation」，算法改编自 CLRS"]
  - "Java (HashMap)": ["只在 bin 太挤时才用", "见下一节 —— 这是个很好的反例"]
```

为什么标准库选它？因为标准库的接口承诺的是**最坏情况**：`std::map::insert` 的复杂度保证是 O(log n)，而且 C++ 标准对关联容器的迭代器失效规则也依赖「改动只影响局部」。红黑树的硬上界正好能满足这种承诺。

作为对比，AVL 也能满足 O(log n)，但标准库实现要写得更小心（旋转次数不定意味着代码路径更多），而查找那一点优势在大 O 记号里看不出来。

## 05 · 一个漂亮的反例：HashMap 平时根本不用树

如果红黑树这么好，为什么 Java 的 HashMap 主结构是**数组 + 链表**？

因为哈希表在正常情况下根本不需要有序结构 —— 平均 O(1) 比 O(log n) 快得多。红黑树只在一种情况下被请出来：

```journey
- tag: ① 正常情况
  tone: green
  name: 数组 + 链表
  badge: 每个 key 落进一个桶
  fields:
    - { k: 结构, v: "Node[] table，每个桶是一条链表" }
    - { k: 查找, v: "算 hash → 定位桶 → 桶内线性找" }
    - { k: 复杂度, v: "平均 O(1)", tone: ok }
  note: 桶里的元素通常只有 0~2 个（JDK 注释里按泊松分布算了概率：8 个元素的概率约千万分之一）。
- tag: ② 攻击或坏 hash
  tone: red
  name: 一个桶被塞满
  badge: 链表退化
  fields:
    - { k: 结构,  v: "所有 key 都落进同一个桶" }
    - { k: 查找, v: "桶内线性扫描 n 个" }
    - { k: 复杂度, v: "O(n) —— 哈希表退化成链表", note: 恶意构造的 hash 能打垮服务, tone: warn }
  note: 这是真实的安全问题：攻击者构造大量同 hash 的 key，让单个桶变成长链。
- tag: ③ 转成树
  tone: violet
  name: 桶里有 8 个就树化
  badge: TREEIFY_THRESHOLD = 8
  fields:
    - { k: 结构, v: "链表转成 TreeNode（红黑树）", note: 一个 TreeNode 约是普通节点的两倍大 }
    - { k: 查找, v: "桶内变树查找" }
    - { k: 复杂度, v: "O(log n) —— 退化被拦住", tone: ok }
  note: 代价是每个节点更占内存，所以只在桶真的挤了才付这个钱。
- tag: ④ 挤完了
  tone: blue
  name: 降到 6 就转回链表
  badge: UNTREEIFY_THRESHOLD = 6
  fields:
    - { k: 结构, v: "TreeNode 转回 Node" }
    - { k: 为什么不是 8, v: "留一个缓冲带，避免在 7~8 之间来回转", note: 抖动会很浪费 }
  note: 6 和 8 之间留出缓冲带，是典型的「避免抖动」工程手法。
```

这个例子把红黑树的定位说得很清楚：**它不是「更好的链表」，而是「链表退化时的兜底」**。JDK 只在池子真的被塞满时才付「每个节点两倍内存」的钱。

==同一棵树，在 CFS 里是主力结构，在 HashMap 里是安全网。==这就是「工程取舍」的意思 —— 同一个工具在不同约束下的位置完全不同。

## 06 · 那为什么不是跳表？Redis 的答案

Redis 的有序集合（ZSet）也用「有序 + 按分数排」的需求，但它选了跳表（skiplist）而不是红黑树。理由很具体：

```compare
first: 关注点
head: [红黑树, 跳表]
rows:
  - 有序遍历 / 范围查询: ["需要中序后继：树的下一个节点，实现要处理父指针或栈", "底层本来就是有序链表，往后走就是了"]
  - 实现复杂度: ["插入删除要处理多种情形 + 双黑 + 哨兵", "多层链表，插入就是「随机定层数 + 改指针」"]
  - 内存: ["每个节点固定 1 个颜色位 + 3 个指针", "每层一个指针，层数可调（概率参数），可以压得比树更省"]
  - 并发/锁粒度: ["旋转会改动父子关系，并发实现要小心", "改动只碰局部指针，做无锁实现容易得多"]
  - 最坏情况: ["有硬上界 O(log n)", "概率性 O(log n)，理论上会退化（但概率极低）"]
```

Redis 是单线程的，所以「并发」那条用不上；它真正在意的是**范围查询和实现简单** —— `ZRANGE` 就是在链表上走。这是另一个「约束决定选择」的例子。

## 07 · 那为什么不是 B 树？MySQL 的答案

MySQL 的 InnoDB 用 B+ 树，理由完全在磁盘上：

```callout
tone: amber
icon: 💾
text: |
  红黑树的节点是**一个键 + 两个指针**。要找到一条记录，从根走到叶大约 log₂(n) 步 ——
  100 万行是 20 步。每一步都可能是一次随机磁盘读（节点分散在盘上）。
  ==20 次随机 IO，每次 ~10ms，就是 200ms。==

  B+ 树的节点是**一个磁盘页（通常 16KB）+ 几百个键**。同样 100 万行，3 层就到底 ——
  ==3 次随机 IO，往下的顺序读还可能是预读。==
```

这就是「同一个问题，约束不同，答案不同」：

| 约束 | 答案 | 为什么 |
|---|---|---|
| 数据在内存里，每纳秒都在改 | 红黑树 | 单次改动次数封顶，之前讲的那两条 |
| 数据在磁盘上，读一次 10ms | B+ 树 | 把「树高」压到最小，一次 IO 搬回几百个键 |
| 数据在内存里，但要求区间遍历 | 跳表 | 天然是链表 |

==红黑树从来不是「最好的平衡树」，它是「内存里、频繁改动、要求单次代价确定」这个交集的答案。==

## 08 · 一张选型表

最后把上面的东西收成一张表。两个轴就是前面反复出现的两个约束：

```matrix
x: { label: 数据主要放在哪 →, from: 内存, to: 磁盘 }
y: { label: 改动有多频繁 ↑, from: 很少改, to: 频繁改 }
cells:
  - { title: 红黑树, desc: 内存 + 频繁改：每次改动只动几个节点，单次代价封顶。调度器、epoll、定时器都在这格, tone: green }
  - { title: B+ 树 / LSM 树, desc: 磁盘 + 频繁改：一个节点 = 一个磁盘页，树高压到 3 层；代价是每次改动要写页、可能分裂, tone: amber }
  - { title: 红黑树 / 跳表都行, desc: 内存 + 很少改：差距只在常数因子，按团队熟悉度和要不要范围遍历来选, tone: blue }
  - { title: 哈希索引 / 一次性排序的静态数组, desc: 磁盘 + 很少改：建好就不改，顺序读到底，不需要动态平衡, tone: muted }
```

注意左列和右列的区别不是「内存 vs 磁盘」那么简单 —— ==真正被这个轴改变的是「一次比较的代价」==：内存里一次比较约 1 纳秒，所以层数多一点无所谓；磁盘上一次比较可能是一次 10 毫秒的 IO，所以必须用多路节点把层数压到 3 层。

矩阵只是指路牌，不是判据。真要选型还得看三件事：要不要范围 / 顺序查询、内存预算、单次改动要不要有硬上界。具体到本文提到的几个系统，它们各自落在哪一格：

| 系统 | 落在哪格 | 它真正在意的 |
|---|---|---|
| Linux 调度器 / epoll / 定时器 | 内存 + 频繁改 | 改动发生在持锁临界区，时长必须有上界 |
| C++ / Java 的有序容器 | 内存 + 频繁改 | 标准承诺 O(log n)，且改动只影响局部 |
| HashMap 的树化桶 | 内存 + 频繁改 | 只是兜底 —— 平时是链表，桶挤了才转树 |
| Redis ZSet | 内存 + 频繁改 | 但它要的是**范围遍历**，所以选跳表 |
| InnoDB 索引 | 磁盘 + 频繁改 | 一次 IO 要搬回几百个键，所以选 B+ 树 |

==同一格里的红黑树和跳表，是被「要不要范围遍历」这一条分开的。==

```callout
tone: violet
icon: 🧭
quote: true
text: |
  ==选树的时候，先问三个问题：==
  ① 数据在内存还是磁盘？② 要不要范围 / 顺序查询？③ 单次改动的耗时要不要有硬上界？
  三个答案基本就定下来了 —— 红黑树是「内存 + 要范围 + 改动要确定」那个格子里的答案。
```

```quiz
- q: 红黑树比不上 AVL 的地方是什么？为什么工程上仍然常选红黑树？
  a: |
    AVL 的树更矮（约 1.44·log₂n vs 红黑树 2·log₂n），所以查找略快。
    但红黑树的插入最多 2 次旋转、删除最多 3 次 —— 单次改动有硬上界；
    AVL 为了维持严格的高度差，一次改动最坏要连续旋转 O(log n) 次。
    在持锁的临界区里，改动时长确定比平均快更重要。

- q: epoll 里为什么同时用了红黑树和链表？
  a: |
    红黑树是**登记表**（所有被监控的 fd），需要按 fd 快速增删查；
    链表是**就绪表**（此刻有数据的 fd），只做「挂上来 / 全取走」，不需要有序也不需要查找。
    分工清楚之后，epoll_wait 的开销只和「有几个就绪」有关，和登记了多少 fd 无关。

- q: Java 的 HashMap 平时用链表，为什么还要准备红黑树？
  a: |
    因为链表在「大量 key 落进同一个桶」时会退化成 O(n) —— 这既能被意外触发，
    也能被恶意构造的 hash 攻击。所以桶里元素超过 8 个（TREEIFY_THRESHOLD）就转成红黑树，
    降到 6 个再转回链表（留出缓冲带避免抖动）。
    平时不用树是因为 TreeNode 约占普通节点的两倍内存。

- q: Redis 的 ZSet 为什么用跳表而不是红黑树？
  a: |
    主要是范围查询和实现简单：ZSet 最常见的操作是 ZRANGE / ZREVRANGE，
    跳表底层本来就是有序链表，顺着走就行；红黑树要中序后继，实现更绕。
    另外跳表的层数概率可调，内存能压得比树更省；改动只碰局部指针，也更容易写无锁版本。
    代价是最坏情况变成概率性的 —— Redis 接受这个代价。
```

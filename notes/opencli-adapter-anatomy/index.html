opencli 做了什么：一条命令的解剖

从 `opencli udp portrait <关键词>` 出发，把「把网站变成命令」这件事拆开：一条命令经过哪五个角色、adapter 的四块结构、数据从 API 信封到表格的六步变形，以及三个反直觉的地方（请求是 Node 发的、detail 请求白打、trace 抓不到它）。

来源 本机实测（2026-10-12，opencli v1.8.8）：`opencli udp portrait futu_hk_trade_overnight_count`，并用探针包住 globalThis.fetch 记录真实请求序列（limit=1 → 10 个请求；limit=3 → 18 个；单次 305~587ms；业务请求带 26 个 Cookie） · 源码：@jackwener/opencli v1.8.8 dist/src/ 下的 main.js · discovery.js · registry.js · execution.js · output.js · node-network.js · browser/page.js · browser/daemon.js · 私有 adapter 源码：portrait.js 与 utils.js（归档在 crm-dsl-stru 仓库 docs/opencli-udp/） · 飞书《OpenCLI 安装教程（面向 Claude Code 用户）》 https://futu.feishu.cn/docx/QqDUdcYLio4T6Rx22PAcq5GMnku生成 2026-10-12模型 glm-5.3-flash

01opencli 到底做了什么

我们要查「公司现网有哪些用户字段、口径是什么」，答案在 UDP 那个内部网站上（cnudp.futuoa.com）。以前的做法是开浏览器、登录、搜索框里打字、点开详情、把口径 SQL 抄下来。

现在这一趟不用开浏览器：

opencli udp portrait futu_hk_trade_overnight_count

出来的是这个（这里只截前几个字段；终端里直接跑是一张表格，这里是进了管道之后的样子）：

- id: 474
  name: FutuHK累计夜盘交易次数
  enName: futu_hk_trade_overnight_count
  status: 4
  dataType: long
  variableType: range
  defaultValue: '0'
  defaultExplain: 没有夜盘交易过
  relationship: |-
    select nn_uid,count(distinct order_id) as overnight_count
    from futu_hk.hk.ods.trade.t3.main_order.us
    where enable_ba_trade=3 and cum_qty>0 group by nn_uid

opencli 不生产这些数据，它做的是把一个网站变成一个命令。规则写在一个 JS 文件里，那个文件叫 adapter（适配器），portrait.js 就是其中一个。

环节自己开浏览器点opencli 的一条命令
登录人工登录，登录态在浏览器里复用同一个登录态，但不用你操作
找数据搜索框 → 列表 → 点进详情一条命令（内部 1~2 个接口）
拿到什么屏幕上的文字结构化 JSON / YAML / CSV
再加工复制粘贴，或者手写脚本管道接给别的程序；-f csv 直接进表格
谁来维护你每次都要重来一遍规则写在文件里，坏了改那个文件

一次命令里同时在场的有四样东西，后面每一节都会碰到它们：

业务逻辑

adapter（你写的那一个文件）

~/.opencli/clis/udp/portrait.js。一个 cli({...}) 调用，声明四件事： 哪个网站、命令叫什么、要什么参数、函数体怎么取数。

调度

opencli 本体

全局装的 @jackwener/opencli。它负责跑你的 adapter： 找到文件、校验参数、借浏览器、把返回值渲染成表格。

借浏览器

Browser Bridge

一个 daemon（127.0.0.1:19825）+ 一个 Chrome 扩展。 作用是让命令能用上你 Chrome 里已经登录的身份。

数据来源

目标网站

cnudp.futuoa.com。真正有数据的地方。它不关心请求是人发的还是命令发的， 只认请求头里的 Cookie。

一次 --limit 3 的时间线实测 305ms。慢的不是某一次请求，而是次数：4 次业务请求各 26~82ms，12 次读 Cookie 的 RPC 各 6~17ms，剩下的二三十毫秒是进程启动和会话开销。

谁来发现我

第一段 · 声明（第 5~14 行）

一次 cli({...}) 调用：

site: 'udp' + name: 'portrait' → 命令名 opencli udp portrait strategy: Strategy.COOKIE → 需要登录态，所以要有浏览器 browser: true → 这条命令要一个 page 对象 domain: 'cnudp.futuoa.com' → 登录域 navigateBefore: false → 不预先打开网站页面

谁来校验

第二段 · 参数（第 15~19 行）

三个参数，声明成数据而不是写成解析代码：

keyword 必填、位置参数 page 整数、默认 1 limit 整数、默认 10

opencli 按这份声明校验类型、补默认值、生成 --help。 传 --limit 1001：类型校验能过（它确实是整数），进了函数体、走到第 29 行被 adapter 自己的检查拦下，退出码 2。

输出长什么样

第三段 · 返回哪些列（第 20~21 行）

columns 列 12 个字段名，它们决定表格输出的列和顺序。

它只影响显示：函数体返回的对象里字段比这多也不显示， 少一个就显示空。extras 是嵌套对象，表格里直接渲染成字面的 [object Object] —— 这条命令实际上只有 YAML / JSON 好用。

业务逻辑都在这里

第四段 · 函数体（第 22~65 行）

44 行，全是「取数 + 挑字段」。它不解析 HTML、不点按钮、不管输出格式， 因为它拿到的不是网页，而是两个接口的 JSON。

想改它的行为，就是改那个文件：

✏

把一份 adapter 放进 ~/.opencli/clis/<site>/ 就生效（同名覆盖内置的），改完不用编译、不用重启。

04从关键词到一行表格：数据走了六步

这一段是整篇的重点。同一个字段数据在命令里换了六种形态，每一步都丢一点、加一点：

一个关键词的六次变形

??（空值合并）铺满整个 rows.push：接口字段缺了、类型不对，这里都不报错，只是变成 null。数据变少了不会有人告诉你。

05三个反直觉的地方

第一条最反直觉：取数请求不是浏览器发的。

⚠

adapter 里那句 fetch(url, { headers: { Cookie: cookie } }) 执行在 Node 进程里， 不是浏览器。浏览器只借出了 Cookie 串。

证据有两条，都是这一趟实测的：

  • --trace on 抓的 network.jsonl 是 0 字节：追踪只抓浏览器侧的网络，这条请求不经过浏览器
  • 标签页最后停在 about:blank，它压根没被用到

所以排查这条命令时，别去 Chrome 的开发者工具里找那个请求。

第二条：detail 那次请求，这一趟是白打的。

接口返回字段数独有字段
/list 的每一条46 个——
/detail?id=47 个只多一个 auditInfo，而且函数体没用它

portrait.js 对每个 id 都打一次 detail，所以一次命令的请求数不是 2 次，而是 1 + N 次。这件事在 --limit 变大时会被放大：

一次命令要发多少个 HTTP 请求

values 是把实测公式代进去算出来的数字：1 和 3 这两档真跑过（10 个、18 个），其余按同一条公式推算 —— 总数 = 1（探活）+ 3(1+N)（读 Cookie）+ (1+N)（业务）+ 1（关标签页）。公式本身来自代码：readCookie() 每次调用打 3 个域（cnudp / futuoa.com / passport），而 fetchUdpJson() 每次调用都重新读一遍。

第三条：trace 抓不到业务请求，但抓到了别的东西。

🌀

--trace on 的产物在 ~/.opencli/profiles/default/traces/<时间戳>-<随机>/： summary.md 是能读的行动时间线，network.jsonl 是空的（见上一条）， state/ 存着最后页面状态，screenshots/ 存着截图。

这次的时间线只有两行，恰好把命令的骨架说清了：

06:54:38.053Z command start {"args":{"keyword":"…","page":1,"limit":2}}
06:54:38.640Z command end

两行之间 587ms，就是上面那一整趟。

06它会怎么坏

知道每一步谁负责，就能知道坏了该找谁。三种常见失效：

现象真实原因该找谁
AUTH_REQUIRED：提示 session expiredutils.js 自己判出来的：响应跳到了 /login，或者返回的是 HTML 而不是 JSON去 Chrome 里重新登录 futuoa，命令不用改

07自测

opencli 自己会取数据吗？这一趟里真正取数的是谁？

不会。opencli 负责发现 adapter、校验参数、提供浏览器通道、渲染输出； 取数那两行是 adapter 的函数体，用 Node 自己的 fetch 发的，浏览器只借出 Cookie。

为什么一次命令要读 1 + N 次 Cookie？

因为 fetchUdpJson() 每次调用都重新 readCookie()，而它每次打 3 个域的 RPC。 代码里没有缓存。是浪费，还是「每次都拿最新的登录态」，看你怎么判。

--limit 1 和 --limit 200 的请求数差多少？

limit 1 实测 10 个 HTTP 请求；limit 200 按同一条公式是 806 个 （业务请求 1+N，读 Cookie 的 RPC 是它的 3 倍）。 这就是 N+1 请求在小数据上无感、在大数据上致命的原因。

这条命令为什么不需要预先打开网站页面（navigateBefore: false）？

因为它只用到 Cookie，不需要页面里的任何东西。 代价是：哪天接口要求一个只存在于页面里的 CSRF token，这条命令就会失败。

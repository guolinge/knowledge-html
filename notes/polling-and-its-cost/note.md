## 01 · 上一句留下的话

上一篇的结论是：**「等待」不产生任何价值，但一连接一线程的做法让每个「在等」的连接都占着一个线程的名额。**

那第一步就很自然：**别让线程等，让它去问。** `O_NONBLOCK` 干的就是这件事。但它在很多材料里被讲成「性能优化」，这一点会把人带歪。

---

## 02 · 非阻塞改的是「返回的语义」，不是「速度」

先把这点钉死，否则后面全歪。

```compare
first: 设置
head: ["数据没到时 `read` 干了什么", 你的代码要做什么]
rows:
  - 阻塞（默认）: ["把你挂起、交出 CPU，数据到了再唤醒你", "什么都不用做，`read` 返回时数据已经在手里"]
  - 非阻塞（`O_NONBLOCK`）: [{ text: "立刻返回 -1，errno = EAGAIN", tone: red }, "自己决定什么时候再来问，这就是轮询"]
```

!!`EAGAIN` 和 `EWOULDBLOCK` 在 Linux 上是**同一个值**（Darwin/BSD 也一样）。!! 看到哪个都是一个意思：**「这会儿没有，别等了」。**

==注意 `O_NONBLOCK` 一个字都没提「快」。== 它不让 I/O 变快，也不减少任何一次拷贝，只是把「等」换成了一句「还没好」。**它换掉的是行为，不是成本。**

## 03 · 一个线程终于能招呼很多连接了

先回答最直接的疑问：**代码变了吗？** 变了，而且只变了两处。先看前后两段：

以前（上一篇，阻塞 + 一连接一线程）：

```text
listen_fd = socket(...);  bind(...);  listen(listen_fd, 128);

for (;;) {
    conn_fd = accept(listen_fd, ...);          // 没有新连接 → 卡在这
    pthread_create(&t, NULL, handle, conn_fd); // ← 线程在这里创建：每 accept 一次，造一个
}

void handle(int fd) {
    char buf[4096];
    read(fd, buf, sizeof buf);   // 这条连接没数据 → 卡在这，线程睡着
    ...                          // 醒来之前，这个线程什么都干不了
}
```

现在（这一篇，非阻塞 + 一个线程轮询）：

```text
// 全程没有 pthread_create：跑轮询的就是进程自带的那个主线程
listen_fd = socket(...);  bind(...);  listen(listen_fd, 128);
fcntl(listen_fd, F_SETFL, O_NONBLOCK);        // ① 监听 fd 也别挂起我

for (;;) {
    conn_fd = accept(listen_fd, ...);         // 没有新连接 → 立刻回 EAGAIN
    if (conn_fd > 0) {
        fcntl(conn_fd, F_SETFL, O_NONBLOCK);  // ① 新连接也要单独设：Linux 上
        fds[n++] = conn_fd;                   //    它不继承监听 fd 的这个标记
    }
    for (i = 0; i < n; i++) {                 // ② 循环形状变了：遍历名单
        r = read(fds[i], buf, sizeof buf);
        if (r > 0)  handle(fds[i]);           // 谁好了处理谁
        else        /* EAGAIN：还没好，问下一个 */;
    }
}
```

先把 ① 里最容易被一笔带过的那句展开 —— ==「监听 fd 也别挂起我」到底是什么意思==：那行 `fcntl` 改的是 **`accept` 的行为**。

```compare
first: 设置
head: [队列里没有新连接时，accept 干了什么]
rows:
  - 阻塞（默认）: ["==卡住==，线程被挂起，直到有客户端连进来"]
  - 非阻塞（`O_NONBLOCK`）: [{ text: "立刻回 -1，errno = EAGAIN（和 EWOULDBLOCK 同值）", tone: red }, "这不是错误，是「这会儿没有，稍后再试」"]
```

所以监听 fd 不设的话，主线程照样卡在「等新连接」上 —— ==事件循环不能为等一个新连接，把整条线程押上去==。真实的事件循环里，常见写法是==把队列一口气取空==（取到 EAGAIN 为止）再去干别的，因为取一个只要一次系统调用，卡住一次的代价是整条线程：

```text
for (;;) {
    conn_fd = accept(listen_fd, NULL, NULL);
    if (conn_fd < 0) {
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            break;                           // 队列取空了，不是错
        perror("accept");
        break;
    }
    fcntl(conn_fd, F_SETFL, O_NONBLOCK);     // 新 fd 不继承，得单独设
    fds[n++] = conn_fd;
}
```

这三个生产细节：① 设非阻塞更稳妥的写法是先 `F_GETFL` 取出原 flag 再 `| O_NONBLOCK`，别把别的标记冲掉；② Linux 上 accept 回来的新 fd 不继承 —— 用 `accept4(..., SOCK_NONBLOCK)`，或者像上面那样单独再设一次；③ `errno == EINTR`（信号打断了本次调用）不是错误，==重试==就行，别当失败退出。

变的只有两处：

```callout
tone: blue
icon: ✏
text: |
  | | 干的事 |
  |---|---|
  | ① 每个 fd 声明成 `O_NONBLOCK`（连监听 fd 也要，==为什么见上面的展开==） | 把上一节那句「数据没到就立刻返回」真的打开 |
  | ② 循环形状：从「每条连接一个线程，各等各的」变成「一个线程、一份名单、挨个问」 | 「轮询」两个字的本来面目 |

  ==除了这两处，一个字都没换==：`read` 还是那个 `read`，连接 socket 还是那些连接 socket，缓冲区、四元组，一个都没动。
```

还有一处消失了的要看见：**右边那段代码里 `pthread_create` 整个没了。** 左边的线程是 accept 时造的，一条连接造一个；右边跑轮询的线程==不是为哪条连接造的==，就是进程启动时自带的那个主线程 —— 以前它卡在 `accept` 上等新连接，现在它把「问」也干了。==线程数从「跟着连接数涨」变成「跟连接数无关」==，这就是这一节标题那句话的本来面目。

**所以「底层是怎么转换的」这个问法，本身就问错了 —— 底层什么都没转换。** 真正变的，是 `read` 在「数据没到」那一刻走的那条分支：

```arch
      - { at: [tA, tX], text: "变的是人，而且是两边不同时辰出现的：左边的线程 ==accept 时 pthread_create 造==，一条连接一个；右边这个线程 ==进程一起来就在==，500 条连接共用它。" }

```

一句话收束：

> **线程从来不是连接的属性，是「阻塞」把线程钉在了连接上。**

一个被挂起的线程干不了任何别的事，所以「同时被等的连接」有几条，就得有几个线程 —— ==这不是连接的需要，是阻塞的 read 需要一个站着等的人。== 非阻塞把「挂起」换成了一句 EAGAIN：线程从头到尾没离开过 CPU，它当然可以拿着 500 个 fd 挨个问。

## 06 · 病灶不在「谁在遍历」，在「内核不记得」

有人以为 `select` 慢是因为「自己写 for 循环慢」，于是让内核替他遍历。**病没治好，只是换了个地方。**

```compare
first: 三代做法
head: [名单谁遍历, 每次调用要交多少]
rows:
  - 自己写 for 循环: ["你自己，在你自己进程里", "名单不用交，但每问一个就是一次系统调用"]
  - "`select`": ["内核替你遍历", { text: "整份位图，进也拷、出也拷", tone: amber }]
  - "`poll`": ["内核替你遍历", { text: "整个数组，进也拷、出也拷", tone: amber }]
```

`select` 和 `poll` 的差别只在一处：`select` 的 `fd_set` 是**固定大小的位图**，所以被 `FD_SETSIZE` 卡住（Linux/glibc 上默认 **1024**）；`poll` 换成了数组，去掉了这个上限。

**但「每次全拷、全遍历」一点没动。**

!!所以真正的病灶是这一句：**内核不记得你上次关心谁。**!! 每次调用，你都得从头交代一遍，因为上一次的交代它已经忘了。

```callout
tone: violet
icon: 💡
text: |
  换个角度看会更清楚：**`select` / `poll` 的内核实现是无状态的。**

  它像个每次都要重新填表的窗口：你交一份表、它办完、把表还给你，
  下一次来它完全不认识你。所以成本必然和「表有多厚」成正比，
  而不是和「这次办成了几件事」成正比。

  ==要跳出这个结构，就得让内核那头「记着」。==
```

## 08 · 你真正缺的那一块：一个能让线程睡着的位置

讲到这里停下来，把你手里那几段代码摆在一起看 —— 你会发现自己一直缺的不是细节，是一个视角：**线程睡在哪。**

先看你现在这个圈（本篇的轮询）的完整形状：

```text
for (;;) {                     // ← 事件循环：永远转
    accept(listen_fd)          // ① 有新连接吗（EAGAIN 就没有）
    for (i = 0; i < n; i++)
        read(fds[i])           // ② 名单挨个问（EAGAIN 就下一个）
}                              // ← 转回来，立刻再来一圈
```

它有一个致命的性质：==整个圈里没有任何一个能让线程睡着的位置==。每一圈都是实打实的系统调用，一圈转完立刻转下一圈 —— 哪怕一万条连接全都没事。这就是上一节说的忙等。

要让它能睡，圈里必须有一个专门的等待点。下一篇 epoll 装的就是它：

```text
for (;;) {                         // 事件循环：还是永远转
    就绪 = epoll_wait(...);        // ← 唯一的睡处：线程在这睡着
    处理就绪的那几个               // ← 被内核叫醒才会走到这
}
```

圈还是那个圈，但多了一个「睡点」。线程在 `epoll_wait` 上睡着（==真睡，不占 CPU==），内核保证「有事先叫醒」，醒来时手里的就是就绪的那几个 —— ①② 那些问，全都由内核替你做完了。

把三代等待摆在一起，代价的差异一目了然：

```compare
first: 形态
head: [线程睡在哪, 睡/不睡的时候 CPU 在干什么, 代价]
rows:
  - 一连接一线程（阻塞）: ["==每条连接自己的等待队列==：一万个睡处", "真睡，不占 CPU", "一万个线程、一万个执行单位（上一篇的账）"]
  - 本篇：一个线程轮询: ["==没有睡处==：一圈问完立刻问下一圈", "==满负荷空转==", "白问：n-1 次系统调用白花（本篇的账）"]
  - epoll（下一篇）: ["==唯一的一个睡处==：epoll_wait", "真睡，不占 CPU", "一次唤醒，处理就绪的那几个"]
```

==三代的关系不是「谁更快」，是「睡处从一个变成没有、再变成刚好一个」。== 形态一睡得着但睡得太贵；形态二不睡了但开始烧 CPU；形态三把两者同时解决 —— 睡得着，且只睡一处。

再回头看那个 `break`。同一段「取到 EAGAIN 就 break」的取空队列代码，==break 之后去哪，取决于外面套的是哪个圈==：

- 套在本篇的轮询圈里：break 回来的下一站还是 `accept` —— 圈立刻又转起来，==忙等照旧==；
- 套在 epoll 的事件循环里：break 回来的下一站是 `epoll_wait` —— ==线程在那睡着，等内核下一次叫醒==。

所以那段「取到 EAGAIN 就 break」的代码总是和 epoll 一起出现：它不是「不再收连接了」，是「这一轮收完了，回去睡，有事叫我」。也正因为如此，==边缘触发（EPOLLET）下取空不是优化而是必须==：通知只发一次，不取空就没人再叫你（LT/ET 那笔账在[「就绪」那篇](../readiness-and-buffers/)）。

「等待不该占用执行资源」这句话，走到形态三才算兑现：等待还是要发生的 —— ==但线程只睡在一处，而且是内核保证「有事先叫醒」的睡==。这篇的圈缺的就是那个睡点；下一篇把它装上，顺便把「内核怎么知道有事」讲清。

```quiz
    它换掉的是**行为**（等 → 问），不是**成本**。

  a: |

    所以每次调用你都得重交整份名单，成本必然和名单厚度成正比，
    而不是和「这次办成了几件事」成正比。

  a: |
```

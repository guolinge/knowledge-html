关系属性的「不存在」：行级、人群级，以及为什么要拆

一个人多行的关系表里，「最近一天 + 排除获得 A 券的人」有三种写法，只有一种对：小张·小陈败在「行级不等于」，小李败在「人群减法忘了带前置过滤」。07 起用两个可点控件把「一条 SQL 够用 / 硬塞会怎样 / 混写会怎样 / 拆开再交并」四种做法的形状和结果摆在同一批人上；真实 SQL 只留骨架。

01先看数据：一个人可以有多行

关系表的形状是「一个人多行」。拿 UDP 测试用例里那个真实关系做例子（niuniu_user_coupon_receive_last，用户领券记录），只留三列：

列 角色 含义
uid 主体 谁
object_id 主键属性 领的是哪张券 —— 同一张券，一个人只有一行
last_created_at 常规属性 这条记录发生的时间

数据（5 个人，编的，形状和真实用例一致）：

uid object_id last_created_at
小王 A 昨天
小王 B 半年前
小李 A 半年前
小李 C 昨天
小张 A 昨天
小张 B 昨天
小赵 C 三天前
小陈 A 昨天
小陈 C 昨天

一行 = 一次「某个人领某张券」的记录；一个人领了几张券就有几行。 这就是"关系表是一人多行"的样子。

02两个词：主键属性 / 常规属性

主键属性

object_id（券）。它决定「有没有这一行」—— 一个人有多行，每行一个券种。业务上问「他有没有 A 券」问的就是它。

常规属性

last_created_at（时间）。它是「这一行里的一个值」，用来过滤哪些行算数。

两者的关系

「有没有这一行」是人的属性；「这一行的值是多少」是行的属性。否定落在这两者上，结果完全不同。

⚠

这个区分是整篇的地基。

主键属性和常规属性在同一条 WHERE 里长得一样（都是 列 运算符 值）， 但它们的否定语义不一样：主键属性的"没有"是"这个人没有这种记录"（人群级）， 常规属性的"没有"只是"这行不满足"（行级）。

03要表达的条件

产品原话（UDP 代码注释里的例子）：

最近一天（常规属性），排除获得奖品 A（主键属性）的用户

翻成人话：

最近一天有领券记录、并且这一天领的券里没有 A 的人。

按上面那张表，正确答案是：

人 期望 为什么
小王 排除 昨天领的就是 A
小李 保留 昨天领的是 C；A 是半年前领的，不算
小张 排除 昨天领了 A（虽然也领了 B）
小赵 排除 最近一天根本没有领券记录
小陈 排除 昨天领了 A（同时也领了 C）

小李和小张是这道题的两个人肉陷阱。 后面每种错法都会栽在他们其中一个身上。

04三种写法，逐个用户算一遍

下面这个控件把三种写法都算一遍。点上面的按钮切换写法，看每个人命中还是落空；错误的格子会标红。

最近一天 + 排除 A —— 三种写法各留下谁

三种写法的名字和它们的 SQL 形状：

写法它在 SQL 里长什么样它否定的是什么
行级不等于object_id != 'A' 和 最近一天 放在同一个 WHERE 里某一行
行级否定NOT EXISTS (select 1 … where 最近一天 and object_id = 'A')一批行
人群减法uid NOT IN (select uid … where object_id = 'A')一个人

结论（点上面控件可以复现）：

小王 小李 小张 小赵 小陈
行级不等于 排除 ✓ 保留 ✓ 保留 ✗ 排除 ✓ 保留 ✗
行级否定（带前置过滤） 排除 ✓ 保留 ✓ 排除 ✓ 排除 ✓ 排除 ✓
人群减法（不带前置过滤） 排除 ✓ 排除 ✗ 排除 ✓ 排除 ✓ 排除 ✓

只有一个写法全对；两个错法各栽在不同的人身上。

05错法一：把「不等于」写进同一行

object_id != 'A' 配 最近一天，落在同一行上，得到的条件是：

存在一行（last_created_at = 昨天  且  object_id != 'A'）

看小张的两行：

小张：(A, 昨天)   →  object_id != 'A' 不成立
      (B, 昨天)   →  object_id != 'A' 成立，时间也对  →  命中！

他只要领过任意一张不是 A 的券，这个人就被留下。 小陈同理（有 C 那行）。

!= 只能否定「这一行」，否定不了「这个人」。 一个人有 3 行，!= 几乎必然在某一行上成立 —— 行级的不等于，落地成"这个人有没有别的券"，而不是"这个人没有 A 券"。

06错法二：人群减法忘了带「前置过滤」

uid NOT IN (select uid … where object_id = 'A') 是人群级的否定：先算出"有 A 券的人"，再把这些人从结果里减掉。这方向是对的，问题在减法集合是怎么算出来的。

不带前置过滤：有 A 券的人 = {小王, 小李, 小张, 小陈}   ← 全表看，不看时间
              结果里小李被减掉 ✗（他半年前领过 A）

产品要的是"最近一天没有领 A"，所以减法集合里必须带上时间：

带前置过滤：有 A 券的人（限最近一天）= {小王, 小张, 小陈}
            小李保留 ✓

UDP 生成的真实 SQL 就是这个形状（测试用例 c8b，已截断）：

select UID_DECODE(`uid`) as `uid`
from `niuniu_user_coupon_receive_last`
where `object_id` in ('coupon001')
  and (
        `_version` >= 5
    and (`last_created_at` >= UNIX_TIMESTAMP(DS_DATETIME_ADD('day', -3, NOW()))
         and `last_created_at` <= UNIX_TIMESTAMP())
    and `uid` not in (
          select `uid` from `niuniu_user_coupon_receive_last`
          where `object_id` in ('coupon001')
            and (
                  `_version` >= 5
              and (`last_created_at` >= … and `last_created_at` <= …)   -- ← 常规属性又写了一遍
              and (`object_id` in (1, 2))
            )
          group by `uid`
        )
  )
group by `uid`

注意子查询里把常规属性（_version、时间）原样复制了一遍。 这不是啰嗦，这正是"只排除最近一天领过 A 的人"的实现方式 —— 也是后面"拆分"要保护的东西。

07一条 SQL 够用吗？四个状态切着看

判断只有一句话：属性里只有「一类语义」，一条 SQL 就够；混了两类，就必须拆。

⚠

先交代一下「C」是哪来的。 只有「不存在 A」一个主键条件时不需要拆（就是下面第一个状态）。 要看到「必须拆」，条件里得同时出现正向主键条件和「不存在」—— 我拿「存在 C」当这个正向条件。 C 和 A 一样只是 object_id 的一个取值，纯粹为了举例编的；UDP 的测试用例里这个位置用的是「存在 AU」。

下面这个台子把四种做法摆在同一批人上。切着看两件事：编译出来的形状，和5 个人的结果（绿色是命中、红色 ✗ 是错）。

同一批 5 个人，四种做法

每个状态下面都会列出它编译出来的 SQL（表名简化成 coupon_record，昨天 = 最近一天；红边那句就是这个做法错的地方）：

四个状态一句话版：

状态 形状 结果
不拆（只有一个「不存在」） 外层正向 + uid not in (子查询)，子查询里复制一份常规属性 5 个人全对
硬塞进同一行 两个主键条件写在一行的 WHERE 里 小陈被多留
混写：正向行级 + 全表减法 减法集合里漏了常规属性 空集，小李被误杀
拆开再交 / 并 支1 只放行级、支2 带常规属性做减法，各自算 uid 全对

inline 状态里那句「最近一天（复制一份）」是这一节的唯一重点：它不是啰嗦，是把减法限制在「同一批记录」里。

顺带一条：多个「不存在」可以合进同一个子查询（AND 关系）。形状从 object_id 不存在 1 或 2 变成子查询里一句 object_id in (1,2) or object_id in (100) —— 还是一条 SQL，不用拆。

08硬来会怎样：两种错法各自错在哪

把控件切到「硬塞进同一行」和「混写」两个状态，盯住小陈和小李：

做法 谁留下 错在哪
硬塞进同一行：object_id 存在 C + object_id 不存在 A 小李、小陈 一行是 C 就必然「不是 A」，后一条自动成立 —— 「不存在 A」被吞掉
混写：正向行级 + uid not in (全表有 A 的人) 空集 减法集合漏了「最近一天」，小李（半年前领过 A）被误杀
拆开：支1 ∩ 支2 小李 正确
⚠

为什么一条 WHERE 说不清：正向条件要求「同一行满足」，「不存在」要求「这个人不满足」。 写进同一个 WHERE 时，SQL 只会按行级解释 —— 要么把「不存在」吞掉（第一行）， 要么把它当成一个不新的子查询（第二行）。两种解释都不是你要的语义。

拆完以后，UDP 生成的真实 SQL 骨架长这样（c8e，只留结构）：

from (
    select `uid` … where `最近一天` and (存在 C 的行级条件)        -- 支1：行级
  union all
    select `uid` … where `最近一天`
                   and `uid` not in (… `最近一天` and (不存在 A) …)   -- 支2：人群级
) rt1
group by `uid`
having count(`uid`) = 2      -- ← 出现在两支里才留下 = 交集

09拆的规则：一棵树看完

  • 属性里有「不存在」吗？ 没有的话这一页用不上 —— 普通 WHERE 就行
    • 有，而且只有它一个 不拆。一条 SQL：外层正向条件 + uid not in (子查询里复制一份常规属性)
    • 有，并且还有别的属性条件
      • 逻辑是 OR 拆 N+1 支 → union all 去重 = 并集；「不存在」那一支不带常规属性
      • 逻辑是 AND
        • 还有正向的主键条件 拆 2 支 → 支1 = 常规+正向、支2 = 常规+不存在 → union all + having count = 2 = 交集
        • 没有正向主键条件 不拆。多个「不存在」合并进同一个子查询（AND 关系）

对应到协议：关系主键属性上的两个操作符就是 存在（exist，底层 IN）和 不存在（not_exist，人群级减法）。非主键属性不给这两个 —— 它们是"行里的值"，问"有没有这一行"没有意义。

💡

exist 和 in（属于）编译出来是一回事（都是 列 in (...)），区别在适用对象和文案： exist 只给主键属性、说的是"有没有这种记录"；in 给枚举字段、说的是"取值属不属于这个集合"。

10一句话记住

一句话总结

关系属性上的「排除」有三种写法：把 != 写进同一行（否定了一行、否定不了人）、 人群减法忘了带前置过滤（把历史上有过的人一起杀了）、 以及正确的那种 —— 否定作用在「人」身上、并且把常规属性复制进减法集合。 条件里只有一类语义时，一条 SQL 就够；一旦正向主键条件和「不存在」混写、或者逻辑是 OR， 就按语义拆成多支、各自算成 uid 集合，再用交（AND）/ 并（OR）合并。

「最近一天 + 排除 A」里，为什么 object_id != 'A' 不对？

它是行级条件，只能保证"这一行不是 A"。一个人只要有任何一行不是 A （小张有 B 那行、小陈有 C 那行），就会被留下 —— 而产品要的是"这个人最近一天没有 A"。

人群减法里为什么要把常规属性在子查询里再写一遍？

因为要知道"哪些人在最近一天的记录里有 A"。不带时间，减掉的就是"历史上任何时间有过 A 的人"， 小李（半年前领过 A）会被误杀。

AND 拆分用 having count = 2，OR 拆分只 group by uid，差在哪？

union all 之后 having count = 2 表示"两支都命中"= 交集；只 group by uid 是去重 = 并集。

单个「不存在」为什么不需要拆？

只有一个语义方向时，一条 SQL 就能表达：外层写正向条件，uid not in (子查询) 里 把常规属性和被否定的主键条件一起写。拆是为了让"行级"和"人群级"各自独立编译成 uid 集合。

「硬塞进同一行」为什么会把「不存在 A」吃掉？

因为 object_id 一列只有一个取值。同一行同时要求「是 C」和「不是 A」， 只要 C ≠ A 就永远成立 —— 条件不再排除任何人。

01整体长这样

下面是组件的完整状态：客户范围选了「指定团队 · 深圳一组」，包含区里两组条件（组间「或者」），第一组混了特征行、时间行和关系行，第二组有带属性过滤的关系行和一条 UID 行。壳拿到的 metadata 是 pb 读模型，进壳后先 resolveCrowdMetadata() 再往下传。界面上每一个框、每一个下拉，都对应草稿里的一个字段 —— 对照着读，组件和协议就是一回事。

拆分的三条缝

12 个 .vue 不是随便切的，缝开在三个地方：

缝一 · 草稿树的层级

Section = 树第一层、Group = 组、Row = 叶子。界面嵌套和 DraftQuery 嵌套同构，改哪层就渲染哪层。

缝二 · 叶子的类型

portrait / relation / uid 三种叶子各一个行组件。行为差异大的东西不硬塞一个组件用 if 区分。

缝三 · 横切的重复

选名字、切 AND/OR、填值 —— 三件事在多处出现，各抽成一个组件复用（NameSelect / LogicToggle / ValueControl）。

这个页面的每张截图本身就是拆分质量的证据：每个组件都能脱离全家桶，单独喂 props 渲染出来。耦合在壳里的组件做不到这一点。

每个组件与外层的完整接口（谁渲染它、props 怎么进、事件怎么出、内部有哪些状态）在组件内幕。

02壳与范围：InsightCombiner、ScopeBar

壳只做四件事：接 props、把两个候选值加载函数 provide 给深层、渲染 ScopeBar 和唯一的包含区、在身份变化时收窄 scope。业务逻辑一概没有 —— 那些在 ts 层（全景篇 05 节有地图）。

接口 内容
props 进 modelValue（ScopeLeaf）、dataLevel、groups
事件出 update:modelValue（新的 ScopeLeaf）
要点 切换 kind 时保留仍然合法的 groupIds；选项由 allowedScopeKinds(dataLevel) 算出

03名字从哪选：ConditionNameSelect

特征和关系混在同一个级联菜单里，靠 key 前缀（field: / relation:）区分。菜单按 Metadata 的 domains 长出层级，字段和关系挂在各自业务域下面。

停用的字段（status = DISABLED）照样出现在菜单里但不可选 —— 新建条件不给选，回显旧条件时还得让人看懂自己圈过什么。

04区域与组：ConditionSection、ConditionGroup

组里藏着两个界面协议：幽灵行（空组先显示一行「请选择条件」，不在草稿里，选中才落地）和每左一个 UID（addLeaf 拦第二个，按钮同时藏掉）。机制在机制篇 02 节。

RelationRow —— 关系行（最复杂的一个，580 行）

以「把总资产从 100 万改成 200 万」为例。正向是 props 流下去，反向是事件冒上来，五层各干一件小事：

这条链有三个值得记住的形状：

主道是窄的

每一层只有一个业务事件 update:modelValue，参数永远是「这一层视角下的新对象」。行不知道组，组不知道区域，壳不知道宿主要拿草稿干什么。

metadata 是整份下传的

壳先把 pb 读模型 resolve 成内部模型，再整份传给 Section、Group、每一行。深层要的只是几个字段，但一份传到底省掉了逐层挑选和透传 —— 数据只有几十 KB，简单赢了。

侧道只有一条

候选值加载走 provide/inject：壳 provide 三个函数（loadValueSet / searchValues / lookupValues），任何深度的行组件直接 inject，再以函数 prop 递给 ValueControl。值加载是唯一的横切需求，再多一条就值得改成显式 props。

行组件的 convert 事件是行类型切换的出口：PortraitRow 里选到 relation:xxx 发 blankDetail，RelationRow 里选到 field:xxx 发 portraitDraft —— ConditionGroup 接住后原位替换（机制篇 02 节）。

为什么 RelationRow 有 580 行而 UidRow 只有 88 行？拆分时为什么不把 RelationRow 再拆？

RelationRow 的大小来自三块真实差异：两种公式的操作符和值区不同、 客体有三种候选值来源、属性过滤是一组带自己逻辑的子条件。 这三块共享同一个草稿节点（DraftRelation），拆开就得把一个节点的编辑权 分给多个组件，事件和状态同步反而变复杂。 对比之下 UidRow 只是一个文本框加一个解析函数，88 行已经把解析、截断、 同步都写干净了。行数差不是失衡，是叶子本身的复杂度差。

「metadata 整份下传」会不会浪费？为什么不挑好再传？

读模型只有几十 KB 且不可变（revision 哈希锁定），shell resolve 一次、整份下传让 每层组件的 props 契约都一样简单 —— 加一个深层组件不用改中间层的透传。 真要省的是「深层改一份大对象」的心智成本，而这份数据从不被组件修改。 这是典型的「数据小就别为省内存加复杂度」。

怎么证明「拆得干净」？

本篇每张截图都是把对应组件单独挂到空页面、只喂 props（metadata 用 手写 fixture、加载函数用本地假实现）渲染出来的。任何组件如果暗中依赖 全局状态或父组件，这一步就会白屏 —— 而它们都能独立跑起来。

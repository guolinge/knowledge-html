失败之后那一次「重新取值、重新算、再提交」，是你写的 `for` 循环在驱动 —— 不是语法糖，不是 CPU 偷偷补上的，也不是操作系统决定的。

那条指令执行完就退休了，它连你的 `for` 在哪都不知道。下面把这件事拆成能看见的四层：你的代码、标准库、CPU 指令、runtime 与内核。

  读取上面这两张图片，您看清楚我在研究什么问题，大概就是原子操作的问题、CAS 的概念性问题。对，我对里面的东西读得还比较懂，比较顺，但我有一个比较困惑的地方：为什么线程的预期值不是 10 之后，它就失败了，但是呢，它会重新取值？这个“重新读取取值再修改”的动作是谁告诉它的？是程序吗？但我程序里好像也没有写相关的代码。是线程吗？还是操作系统啊？

  #### 答

  用 Go 写很简洁，**不需要引入第三方库**，使用标准库 `sync/atomic` 即可。

  ##### 直接使用 CAS 重试循环

  ```go
  func addOne(value *atomic.Int64) {
  	for {
  		// 读取预期值
  		oldValue := value.Load()

  		// 计算准备写入的新值
  		newValue := oldValue + 1

  		// CAS：当前值仍然等于 oldValue 时，才写入 newValue
  		if value.CompareAndSwap(oldValue, newValue) {
  			return // 修改成功，退出循环
  		}

  		// CAS 失败后，for 循环进入下一轮
  		// 下一轮会重新执行 value.Load()
  	}
  }
  ```

  如果 CAS 失败，执行流程自然来到 `for` 循环末尾，然后开始下一轮，再次执行 `oldValue := value.Load()`。

  所以，**“重新读取”这个动作是 `for` 循环告诉它做的**，不是操作系统自动让它做的。

  ##### 假设两个 goroutine 都读到了 10

  ```text
  value 初始值 = 10

  甲：Load() 得到 10
  乙：Load() 得到 10

  甲：CompareAndSwap(10, 11) → 成功
  当前 value = 11

  乙：CompareAndSwap(10, 11) → 失败
  因为当前 value 是 11，不再是预期的 10

  乙：进入下一轮 for 循环
  乙：Load() 得到 11
  乙：CompareAndSwap(11, 12) → 成功

  最终 value = 12
  ```

  不过，真实运行时不一定刚好产生冲突。也可能甲先完整执行成功，然后乙才读取，此时乙直接读到 `11`，一次 CAS 就能成功。无论有没有冲突，最终结果都是 `12`。

  ##### 如果只是想原子地加一，Go 还能更简单

  实际开发中，如果你只是做 `value = value + 1`，不需要自己写 CAS 循环，可以直接写 `value.Add(1)`。`Add(1)` 已经由 Go 的原子操作机制处理好了，你不需要自己维护 CAS 循环。

  最后再对应到你之前的问题：

  - **CPU**：执行一次 CAS 原子指令；
  - **`CompareAndSwap`**：告诉程序这次成功还是失败；
  - **`for` 循环**：失败后重新读取并重试；
  - **Go 运行时**：负责调度 goroutine；
  - **操作系统**：负责底层线程调度，但不会替你决定 CAS 失败后要不要重试。

  #### 问

  「比较奇怪，为什么上面说除了这个 compare 之外可以用原子操作，但是为什么不用互斥锁mutex?」

  #### 答

  当然可以用 `mutex`。上面的代码不用互斥锁，**只是因为我们正在演示 CAS 和原子操作的工作方式**，不是因为 mutex 不能解决这个问题。

  而且要注意：`CompareAndSwap` 本身就是一种原子操作，`Add(1)` 也是一种原子操作，mutex 则是另一种并发控制方案。

  ##### mutex 是怎样解决问题的

  初始值是 `10`。假设甲先拿到锁：甲 Lock 成功 → 读取 10 → 修改为 11 → Unlock。在甲持有锁的时候，乙执行 `c.mu.Lock()` 会暂时无法进入临界区，必须等甲释放锁。然后乙 Lock 成功 → 读取 11 → 修改为 12 → Unlock。最终结果就是 `12`。

  这里没有“CAS 失败后重新读取”的问题，因为 mutex 保证同一时刻只有一个 goroutine 能执行受保护的代码。

  ##### CAS 和 mutex 的核心区别

  - **CAS**：大家都可以尝试修改，但修改时检查数据有没有被别人动过。如果被动过了，本次修改失败，重新读取并重试。
  - **mutex**：在修改之前先拿锁。拿到锁的人执行，其他人暂时不能进入。

  简单类比：mutex 是厕所只有一把钥匙，拿到钥匙的人才能进去；CAS 是大家都可以提交修改，但提交时发现版本过期，就重新读取再提交。

  ##### 为什么简单计数器经常使用 atomic

  对于单个数字的简单加减，`value.Add(1)` 比 `mu.Lock(); value++; mu.Unlock()` 更简洁，原子加法通常也不需要维护显式的锁结构。不过这不代表 atomic 在任何情况下都一定比 mutex 好，这是一种常见误解。

  **什么时候适合用 atomic**：计数器、状态开关、单个值的替换、简单统计数据。这些操作通常很短，并且只涉及单个值。

  **什么时候应该使用 mutex**：当操作涉及多个步骤、多个变量或者复杂的不变量时，mutex 通常更合适。例如账户转账，需要保证「检查余额 → 扣除余额 → 添加交易记录」属于同一个完整操作。如果只把 `balance` 做成原子变量，并不能自动保证交易记录和余额始终一致。

  ##### CAS 不一定比 mutex 更快

  CAS 经常被称为“无锁操作”，但“无锁”并不表示“没有代价”。如果竞争激烈，很多 goroutine 可能不断发生「读取 → CAS 失败 → 重新读取 → 再次失败」，这会浪费 CPU。

  例如 1 万个 goroutine 都在执行复杂的 CAS 循环，可能出现大量重试。mutex 在竞争严重时可以让等待者暂停，而不是持续抢占和重试，因此有时反而更合适。

  所以不能简单理解为 atomic 一定快、mutex 一定慢，必须结合实际操作和竞争程度判断。

  ##### 三种写法应该怎么选

  - 只是加一：优先考虑原子加法 `value.Add(1)`
  - 为了学习 CAS，或者实现条件更新：使用 CAS 循环
  - 多个变量、多个操作必须保持整体一致：使用 mutex

  CAS 和 mutex 不是谁完全替代谁，而是不同层次的工具。实际项目里，用 mutex 写完全正确，而且很多复杂场景下，**mutex 反而是更清楚、更稳妥的选择**。

## 02 · 那条指令只做一件事：比一下，相等才写

x86 手册里 `CMPXCHG` 的伪代码就这么长，没有循环：

```text
TEMP := 内存里的值
IF 累加器 = TEMP
   THEN ZF := 1;  内存 := 新值      // 相等：写
   ELSE ZF := 0;  累加器 := TEMP    // 不相等：一个字节都不改
FI
```

`ZF` 就是那条指令留下的「相等吗」标志位。Go 把它翻成一个 `bool` 交回给你。两边做法略有差别，但都不是「重试」：

```text
// amd64：一条指令 + 一条取标志位
LOCK CMPXCHGQ  BX, 0(CX)
SETE           AL          ← ZF 直接当返回值

// arm64：一条 CASAL，然后自己比一次
CASAL          x27, x1, [x2]
CMP            x27, x0
CSET           x3, eq      ← 「成没成功」这一步是 CMP + CSET 算出来的
```

arm64 那三行的顺序值得看一眼：`CASAL` 把当时读到的值留在寄存器里，**成功与否是接下来那条 `CMP` 算出来的**。硬件交回的是「值 + 标志位」，不是一句「你成功了」。这一层的全部工作到此结束。

```compare
first: 两条路
head: [相等（提交成功）, 不相等（提交失败）]
rows:
  - 硬件做了什么: [写入新值，置 ZF=1, 不写，置 ZF=0]
  - 内存变成了: ['11', '还是 11（谁也没改）']
  - 函数返回: ['true', 'false']
  - 你的代码下一步: [return，退出循环, 回到开头再读一次]
```

**CAS 保证的是「比较和写之间没有空档」，不是「从你读到你再写之间没有空档」。**

这两个空档要分开看，混在一起就是这道题最容易卡的地方：

| 空档在哪 | 谁造成的 | 谁来兜 |
|---|---|---|
| `Load` 和 `CompareAndSwap` 之间 | 别人改了值，或者你的线程在这中间被换下 CPU | 你的 `for`：拿到 `false` 再读一遍 |
| `CompareAndSwap` 的「比较」和「写」之间 | 不存在 —— 一条指令，中间没有缝 | 不需要兜 |

所以这道题里真正的新信息是：**失败不是「出错了」，失败是一个正常的返回值**。它没有抛异常、没有回滚、没有日志，就是 `false`。正因为失败这么安静，才需要你自己写点什么去处理它。

## 04 · 那为什么 Add 不用写循环

`value.Add(1)` 里没有你要写的循环，因为「读、加、写」被压成了一条指令：

```text
// amd64：一条指令完成读-加-写，不需要「旧值」参与决策
LOCK XADDQ  AX, 0(CX)

// arm64（有 LSE 的新核，即 ARMv8.1 的原子指令扩展）：同样一条
LDADDAL     x0, x2, [x1]
```

`Add` 不需要复查「我算的新值还对不对」，因为新值就是「旧值 + delta」，不管中间被谁改过，加上去都成立。**没有需要复查的东西，就不需要重试。**

但老一点的 ARM 核没有 `LDADDAL`，Go 会把同一个 `Add` 展开成这样：

```text
loop:
  LDAXR   x2, [x1]        ← 独占读
  ADD     x2, x2, x0      ← 加
  STLXR   w27, x2, [x1]   ← 独占写，失败时 w27 ≠ 0
  CBNZ    w27, loop       ← 没落地？整段重来
```

**这里确实有一层你看不见的重试。** 但它重试的是另一件事：

```compare
first: 谁在重试
head: [重试的是什么, 什么时候重试, 要不要你写]
rows:
  - 'CPU 的独占写（LL/SC）': ['「这次读改写有没有被别的核打断」', 独占写没落地, 不用，指令序列自己来]
  - '你的 `for` 循环': ['「我算出来的新值有没有过期」', 'CAS 返回 `false`', '不用写 —— 它就是那个 `for`']
```

两者不能互相替代，因为只有你知道新值怎么算。硬件可以帮你把「11 写进去」做成不可分割的一步，但它不知道该写 11 还是 12 —— 那是你的 `oldValue + 1`。

上面那段 LL/SC 里还有个细节值得看一眼：比较不相等时它 `BNE` 直接跳到返回 `false`，**不会拿旧值硬写**。所以这层重试绝不会把过期的值写进去，它只是让「比较 + 写」这一小段不被打断。

## 05 · 线程和操作系统在这件事里负责什么

现在正面回答「是线程吗？还是操作系统啊？」。四层各自管什么：

| 这一层 | 这一步它在做什么 | 会不会让你重试 | 凭什么 |
|---|---|---|---|
| 你写的代码 | 读一次、算新值、看返回值 | **会 —— 就是它** | 你写的 `for` |
| CPU 的一条指令 | 比一下，相等才写，回一个标志位 | 不会 | 指令退休就结束，它不知道下一次循环在哪 |
| Go runtime | 决定哪个 goroutine 现在跑 | 不会 | CAS 成没成功，它拿不到这个信息 |
| 内核 | 决定哪条线程、在哪个核、跑多久 | 不会 | CAS 全程在用户态，一次系统调用都没有 |

两处容易搞混的地方：

**第一，内核确实能让冲突发生。** 你的 `Load` 和 `CompareAndSwap` 之间，线程完全可能被换下 CPU，让别的 goroutine 跑一段、把值改掉。这是冲突的来源之一。但换回来之后，决定「要不要再来一次」的还是你的 `for` —— 内核只负责让谁在跑，不负责让谁重来。

**第二，无竞争的锁也是纯用户态的。** futex 手册写得很直白：无竞争时锁状态就是一个原子的比较交换指令，`(Such instructions are performed entirely in user mode, and the kernel maintains no information about the lock state.)` 连加锁都不一定进内核，CAS 更不会。

## 06 · 那为什么不用 mutex：因为 mutex 的第一步也是 CAS

这不是修辞。Go 的 `sync.Mutex`，`Lock()` 的第一件事就是一次 CAS：

```go
// src/internal/sync/mutex.go
func (m *Mutex) Lock() {
	// Fast path: grab unlocked mutex.
	if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
		return
	}
	m.lockSlow()   // 没抢到，才走慢路径
}
```

反汇编出来是这样（`mu.Lock(); counter++; mu.Unlock()` 整段的开头）：

```text
CASAL   w27, w2, [x3]              ← 和你的 CompareAndSwap 是同一条指令
CMP     w27, wzr
CSET    x4, eq                     ← 拿到锁了吗
TBNZ    w4, #0, ...                ← 拿到了，直接往下走
BL      internal/sync.(*Mutex).lockSlow
```

所以「用 mutex 就不用 CAS 了」这个说法不成立。**mutex 和你的 `for` 循环，差别只在于「失败之后干什么」**：

```compare
first: 拿到 false 之后
head: [CAS 循环, mutex]
rows:
  - 下一步做什么: [回到开头再抢一次, 先原地自旋几次，还不行就排队睡觉]
  - 谁在等: [没有队列，谁抢到算谁的, runtime 里有一条等待队列]
  - 竞争者多的时候: [所有人一起烧 CPU, 睡着的人不烧 CPU]
  - 公平性: [没有保证，可能有人一直抢不到, 等超过 1ms 进入饥饿模式，直接交接]
```

`lockSlow` 里那几件事值得记住：它先做最多 4 次主动自旋（`active_spin`），还抢不到就调 `runtime_SemacquireMutex` 把这条 goroutine 挂起；在 Linux 上最终落到 `futex`，在 macOS 上是内核条件变量。等超过 1ms（`starvationThresholdNs`），它切成饥饿模式，把锁**直接交接**给队头，不再让新来的人插队。

一句话：**mutex = 一次 CAS + 一套「失败之后排队睡觉、并且尽量保证公平」的策略。**

你在第 03 节里手写的 `for`，是这套策略里最简陋的一档：不排队、不让位、不保证公平，只有「再抢一次」。

## 07 · 实测：抢的人一多，手写 CAS 循环反而最慢

第 06 节那个结论不只写在注释里。同一台机器（Apple M4，Go 1.26.2），每个 goroutine 做 20 万次加一，三种写法各跑 3 遍：

| goroutine 数 | 手写 CAS 循环 | `atomic.Add` | `mutex` | CAS 失败率 |
|---|---|---|---|---|
| 1 | 0.85 – 1.66 ms | 0.37 – 0.57 ms | 0.53 – 1.26 ms | 0% |
| 2 | 7.7 – 12.9 ms | 1.9 – 2.4 ms | 6.2 – 11.5 ms | 20 – 28% |
| 4 | 100 – 125 ms | 9.3 – 10.0 ms | 47 – 49 ms | 68 – 73% |
| 8 | 579 – 740 ms | 30 – 37 ms | 95 – 97 ms | 82 – 84% |

读法：

- **一个人跑**：三种写法差别不大。CAS 循环略慢，因为它多了一次 `Load`，还要多判一次分支。
- **四个人抢**：手写 CAS 循环已经比 mutex 慢一倍，比 `Add` 慢十倍。
- **八个人抢**：CAS 循环 0.58–0.74 秒，mutex 95 毫秒，`Add` 31 毫秒。**手写循环比 mutex 慢 6–7 倍**，失败率 82–84% —— 160 万次成功提交背后是 870 万次尝试，等于每一次加一平均白做 5.4 次 CAS。

原因在失败那一下：每次失败的 CAS 都要把那条缓存行从别人手里抢过来，抢过来才发现值不对；失败的 goroutine 又不退让，立刻回去再抢。抢得越凶，缓存行在两颗核之间来回滚得越快，有用的工作一点没做。

`Add` 为什么不受影响？因为它一条 `LOCK XADD` 就完成，没有「抢过来之后发现过期了」这一步 —— 不存在白做的尝试。

所以「无锁一定比锁快」在竞争激烈时是错的。无锁省掉的是「排队和睡眠」，代价是「白做和重抢」；哪一头更贵，取决于有多少人在抢、每次要干多少活。这里的临界点在本机是 2 到 4 个 goroutine 之间。

## 08 · 怎么选，一句话一档

```compare
first: 你要做的事
head: [用什么, 为什么]
rows:
  - 只是加、减、赋值、读一个数: ['`Add` / `Store` / `Swap`', 一条指令就完成，没有需要复查的东西]
  - '「读到旧值，再决定写什么」（余额够不够扣、状态能不能切）': [CAS 循环, 新值依赖旧值，只有你能算，只能你自己复查]
  - 几个字段必须一起变（余额 + 流水 + 时间戳）: [mutex, 一次 CAS 保护不了第二个字段]
  - 一段业务逻辑要完整走完: [mutex, 锁一段代码，比写一套无锁算法好懂也好查]
  - 不确定，也没测过: [先 mutex, 正确性更容易保证，量出来是热点再换]
```

这五档其实在问同一个问题：**需要复查的范围有多大。**

- 一个数、算得出来 → 让硬件一条指令搞定，不用复查
- 一个数、但新值要算 → 你必须复查，用 CAS 循环
- 不止一个数 → 复查也管不住，改用「一次只让一个人进」

## 09 · 自测

```quiz
- q: CAS 返回 `false` 之后，是谁把执行带回 `for` 的第一行？
  a: |-
      你的 `for` 循环本身。`CompareAndSwap` 只是返回了一个 `false`；CPU 那条指令执行完就结束了，它不知道 `for` 在哪。回到开头重新 `Load`，是 `for` 这个大括号的回边。
- q: 「CAS 是不可分割的」这句话，说的是哪一段时间不可分割？
  a: |-
      只指 `CompareAndSwap` 内部「比较」和「写」之间。从你的 `Load` 到这次提交之间有一大段空档，别人完全可以插进来 —— CAS 的全部作用就是复查这段空档里值有没有被动过。
- q: '为什么 `atomic.Add(1)` 不需要你写重试循环？'
  a: |-
      因为它的新值不依赖「读到的旧值」，加上去永远成立。amd64 上是一条 `LOCK XADDQ`，新 ARM 上是一条 `LDADDAL`；老 ARM 上确实有一层 LL/SC 重试，但那层只管「这次读改写有没有被打断」，不需要你参与。
- q: 既然 mutex 的第一步也是 CAS，mutex 到底替你做了什么？
  a: |-
      替你决定「失败之后怎么办」：先自旋几次，还不行就挂起排队，等超过 1ms 切饥饿模式直接交接。手写的 `for` 只会一件事 —— 立刻再抢一次。
```

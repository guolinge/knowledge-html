单机代码藏着的 7 个假设，分布式里全部失效

一段七行的 while 循环，脚下踩着七个没写出来的假设。逐个拆开它们失效后会发生什么，以及业界各自的标准解法 —— 一致性哈希、幂等与去重、单写者原则、快照加位点、反压、key group。

单机程序脚下踩着七个没写出来的假设。它们不是靠你的代码成立的，是靠 CPU、线程、进程内存和函数调用替你保证的。

一旦拆到多台机器，这七个假设全部失效，必须由系统显式补上。这篇逐个拆开它们，以及业界各自的标准解法。

01一段七行的代码，藏着七个假设

while (true) {
    Order o = read();
    if (o.getAmount() <= 0) continue;
    total += o.getAmount();
    write(total);
}

看起来很朴素。但它默认下面这些事已经成立：

代码里没写、但单机默认成立的假设单机里谁在保证它分布式里会变成什么
只有一个执行者一个线程在跑这段循环数据散在多台机器上，谁算全局值？
内存随手可及都在同一个进程地址空间里跨机器只能走网络 —— 而网络会丢、会重、会乱序
数据按一个顺序处理循环天生就是顺序的多个节点同时改同一个 key，谁覆盖谁？
变量更新不会冲突单线程没有竞态这回事两个进程「读-改-写」交错，丢更新
进程不出故障挂了就整个停，不用想恢复局部故障是常态，必须能精确恢复
上下游速度差自然协调write() 慢，read() 就自动跟着慢中间会无限积压，直到 OOM
机器数量不变没有「扩容」这回事扩了容，历史状态还留在老机器上
🧭

所以分布式带来的问题，不是业务突然变复杂了 —— 而是单机环境里那些被默认保证的条件，到了多机环境必须被明确设计和实现。

下面七个假设逐个拆。每一节都按同样的三步走： 哪个假设失效了 → 会发生什么 → 业界的通用解法是什么。

02假设① 只有一个执行者 —— 数据该分给谁

单机只有一个 total：

订单 → 同一个循环 → 同一个 total

分布式里，同一个变量变成了三份互不知情的副本：

订单流 所有人都在下
机器 A totalA = 100
机器 B totalB = 200
机器 C totalC = 300
全局 total = ?" 没有任何一台机器天然知道

三台机器各算各的，加起来是 600 —— 但没有一台机器知道这个数。所以必须做选择：

策略怎么做代价是什么
全都送到一台机器多台机器把数据都发给同一个汇总节点结果是对的，但没有并行度，汇总节点必然成瓶颈
局部聚合 + 二次汇总每台先算局部值，再合并局部结果需要一个额外的聚合阶段；能用是因为 sum 满足结合律
按 key 分区hash(key) % N，让每个 key 固定由一台机器负责分布式计算的标准答案

但「取模」有个致命伤

下一节就把这个「只影响一小段」拆开讲：环是怎么造的、为什么它就能只动一小段。

03一致性哈希：为什么扩容只搬一小段

上一节最后那张对比图留了个结论：取模 3→5 要搬约 2/3 的 key，一致性哈希只搬一小段。 这一节讲清楚它凭什么。

3.1 取模的病根：它把「节点数」写进了路由公式

owner(key) = hash(key) % N

问题就出在这个 N 上：

hash(key) = 17

17 % 3 = 2   →  C        ← N 从 3 变成 4
17 % 4 = 1   →  B        ← 同一个 key，立刻换了主人

key 的哈希值一个 bit 都没变，变的是除数。 所以 N 一改，几乎每个 key 都得重算、重新搬家。

一句话：N 一旦参与路由计算，N 变 = 路由全变。

3.2 换个做法：把 key 和节点放进同一个空间

一致性哈希不取模。它只做一件事：把「key」和「节点」都哈希成同一个大空间里的坐标。

key  的哈希值  →  0 ~ 2³²-1 里的一个数
节点 的哈希值  →  同一个空间里的一个数

而哈希值到上限后会从头开始，所以这个空间逻辑上是一个环：

0 → 1 → 2 → … → 99
↑                 ↓
└─────────────────┘

注意节点的位置不是人为编号的（不是「A 是 0 号、B 是 1 号」），而是算出来的：

hash("server-A") = 10
hash("server-B") = 40
hash("server-C") = 80

3.3 归属规则：从 key 出发，顺时针找第一个节点

🎯

从 key 在环上的位置出发，沿顺时针走，遇到的第一个节点，就是它的归属节点。

下面这台可以亲手切。先看「一致性哈希 · 3 台」，再切到「4 台」—— 注意 A / B / C 三个点一动没动，只是中间插进来一个 D：

同一个环，两种分配规则 切「分配规则」和「节点数」，看环上哪些 key 换了主人

三个值得盯的地方：

  • 切到「取模 % N」：环被等分成 N 段，边界由 N 直接决定 —— 所以 N 一改，所有边界一起挪位，key 大面积换主。
  • 切到「一致性哈希」：节点是算出来的点，N 从 3 到 4 时 A(10) / B(40) / C(80) 一动不动，只是插进一个 D(65)。
  • 标红的 key：就是这次扩容里换了主人的。取模那一档红一大片，一致性哈希只红一小段。

3.4 加一个节点，到底搬走了哪一段

D 落在 65，按「顺时针第一个」的规则：

扩容前：(40, 80]  →  C          整段都是 C 的

扩容后：(40, 65]  →  D          ← 只有这一小段换了主人
        (65, 80]  →  C          ← 剩下还是 C 的

四段一起看：

(80, 10]  →  A        ✓ 没动
(10, 40]  →  B        ✓ 没动
(65, 80]  →  C        ✓ 没动
(40, 65]  →  C ➜ D    ← 只有这一段

D 只接管「它自己，到它前一个节点之间」的那一段。 远处的 A 不受影响，B 和 C 的大部分也不受影响。

（记号 (40, 80] 读作「大于 40、小于等于 80」。）

3.5 本质差别：N 到底有没有参与路由

维度取模 hash % N一致性哈希
路由公式hash(key) % N —— N 是公式的一部分环上顺时针找第一个节点 —— N 不参与计算
加一个节点时除数变了，几乎所有 key 的余数都跟着变A / B / C 的位置不变，只是环上多了一个点
平均迁移比例约 N/(N+1)：3→4 搬 75%，10→11 搬 90.9%约 1/(N+1)：3→4 搬 25%，100→101 搬 1%
根因节点数出现在计算里，改它 = 改所有结果节点只是环上的坐标，改它 = 只影响相邻一段
🧭

「一致性」不是「结果永远不变」的意思。 它说的是：

节点集合发生小变化时，key 的映射关系也只有小范围跟着变。

换一批节点 → 当然要搬家；但加一台机器 → 平均只搬 1/(N+1)。

3.6 但一台机器只放一个点，会严重不均

环上放几个点全靠哈希运气，运气不好就长这样：

A(5)     负责 (90, 5]    →   15% 的环
B(10)    负责 (5, 10]    →    5% 的环
C(90)    负责 (10, 90]   →   80% 的环     ← 一台扛八成

C 被压死，另两台闲着。怎么解？别让一台物理机在环上只放一个点 —— 这就是虚拟节点。

下一节接着讲：虚拟节点能治哪一类不均，以及哪一类它压根治不了。

04但它不解决热点：四个别混在一起的问题

4.1 一个很自然的疑问

「如果我的 key 哈希之后都集中在 45~65，那顺时针找第一个节点，不就老是落在同一台机器上了吗？」

这个担心是对的 —— 而且它逼出了一个必须讲清的边界：

⚠

一致性哈希不解决「数据分布不均」，它解决的是「节点增减时少搬数据」。

这是两个完全不同的问题，经常被混成一个。

不过在动手之前，先分清到底是哪一种不均 —— 四种情况的解法完全不同：

你观察到的现象真正的原因该用什么
原始 key 看起来很集中（user_10001 到 user_20000）正常，不是问题好的哈希有雪崩效应，输出会散开。先看哈希之后的分布再说
哈希之后仍然集中在 45~65哈希函数质量差，或者取值方式不对换高质量哈希（MurmurHash / xxHash / CityHash），并对完整的 key 做哈希
很多不同的 key 都落在某个局部区间环上点位太少，区间划得太粗虚拟节点
某一个 key 本身就占了很大流量热 key —— 和哈希无关加盐分片 / 专用资源 / 业务分片

4.2 第一种「假集中」：原始值集中 ≠ 哈希值集中

用户 ID 是连续的，看着确实集中：

user_10001 / user_10002 / user_10003 / …

但好的哈希函数有雪崩效应 —— 输入改一点，输出像随机数：

hash("user_10001") = 13
hash("user_10002") = 87
hash("user_10003") = 31
hash("user_10004") = 62

「输入看起来集中」和「哈希值集中」是两件事。 先看哈希后的实际分布，再决定要不要处理。

真正会出问题的是这么用：

int h = userId % 100;    // ✗ 拿原始值取模，等于没哈希

如果 userId 本身有规律（自增、带业务前缀、只取某几位），取模结果就跟着有规律。 正确做法是对整个 key 做一次高质量哈希：

MurmurHash · xxHash · CityHash · SipHash
（SHA-256 也行，但对路由来说太重了）

4.3 第二种：点位不均 → 虚拟节点

一台物理机在环上只放一个点的话，「它负责多大一段」纯看哈希运气：

A(5) → 15%        B(10) → 5%        C(90) → 80%

解法是让一台物理机在环上放很多个点：

物理机 A：  A#0  A#1  A#2  …  A#5      ← 每个都单独哈希
物理机 B：  B#0  B#1  B#2  …  B#5
物理机 C：  C#0  C#1  C#2  …  C#5

环上就不再是「三大块」，而是十几个小块交错：

… A#1 → C#0 → B#2 → A#3 → B#0 → C#1 → A#0 …

这样即使 key 只落在一小段区间里，也会被摊到不同物理机上 —— 因为这一段里穿插了好几个不同机器的虚拟节点。

下面这个可以验证。key 故意挤在 40~65 这一小段：

key 挤在一小段，虚拟节点怎么救 切「每台一个点 / 每台 6 个虚拟节点」看负载条
  • 「每台一个点」那一档：所有 key 顺时针撞到的都是同一个节点，负载条会明显歪掉。
  • 切到虚拟节点：同一批 key 被摊到三台上，负载条接近持平。
📦

虚拟节点还顺手解决了另外三件事：

  • 扩容迁移更均匀 —— 新节点接管的是很多小块，而不是一整大块
  • 节点故障恢复更均匀 —— 一台挂掉，它的许多小块会被多台机器分别接走，不会全压给邻居
  • 异构机器可以按性能加权 —— 高配放 300 个虚拟节点、普通放 100 个，它就自然多扛 3 倍

4.4 第三种：真·热 key —— 这一种虚拟节点也没用

这是最本质、也最常见的一种：

所有流量都属于同一个 key —— 大促时的 iPhone_17，或者统计里的 country = China

不管环上有多少个虚拟节点，同一个 key 的哈希值永远是固定的，它只会落到一个地方。

hash("iPhone_17") = 52     ← 永远落在 52 后面那个节点上

为什么不能简单地「把这个 key 打散到多台机器」？因为大量分布式状态计算要求：

同一个 key 的状态，必须由同一个地方顺序更新

key = iPhone_17，库存 = 100

机器 A：读到 100，写回 99
机器 B：读到 100，写回 99      ← 卖了两件，库存只减了一件

所以默认的分区方式必然让「同一个 key → 同一个分区 → 同一个处理者」。这是为了正确性，不是设计缺陷。

那热 key 怎么办？ 三种思路，适用场景完全不同：

思路怎么做什么场景能用
加盐分片把逻辑 key 拆成 N 个子 key（iPhone_17#0 … iPhone_17#15），撒到多台机器上各算局部值，最后汇总只适用于可合并的统计（sum / count / max / min）
单独分流热点 key 单独路由到专用机器 / 专用分区 / 更大资源池热点数量少，又必须严格顺序（比如库存扣减）
业务分片把「一个总数」拆成多个分片各自维护（总库存 10 万 → 100 个分片各 1000 件）要设计跨分片的超卖、限购、重试、幂等 —— 已经是业务模型问题了
🍰

为什么加盐分片只能用于「可合并的统计」？

iPhone_17#0  →  100 件      ← 局部聚合，可以并行
iPhone_17#1  →  120 件
iPhone_17#2  →   80 件
──────────────────────
汇总         →  300 件      ← sum 可以合并

但「库存扣减」不能这么算：三个分片各扣各的，加起来对不上总量，还会超卖。 可合并的运算可以分片；可变的共享状态不行。

🧭

把这四层分开记：

一致性哈希      →  解决「扩缩容时少迁移」
虚拟节点        →  解决「机器在环上的位置不均」
高质量哈希      →  解决「不同 key 的散列不均」
加盐 / 业务分片  →  解决「单个 key 太热」

它们不是同一件事的四种做法，而是四个不同层次的问题。

搞混的代价很具体：拿「换个更好的哈希函数」去治热 key， 或者拿「多加虚拟节点」去治「只有一个 key 热」—— 都是白费力气。

（回到主线）假设① 到这里讲完了：先分片决定「谁负责哪些 key」，再让分片规则在扩容时少动。 接下来回到七个假设的第二个。

05假设② 内存随手可及 —— 数据必须走网络

单机里这一句，就是一次内存读写：

total += amount;   // total 就在当前进程地址空间里

分布式里，订单在 A，而它需要的状态在 B：

订单在机器 A
user_1 的累计状态在机器 B

A 没法访问 B 的内存，只能发网络消息。而网络比内存多了六种坏脾气：

会延迟

什么时候到不保证。平时 1ms，抖动起来 1s

会丢失

发出去了，不一定会到

会重复

到了，可能到两次 —— 你没发两次，但它真的到了两次

会乱序

先发的可能后到

会断

连接随时可能中断，而且断的时候你不知道对面收到没

无法判断

超时只说明「你等够了」，不说明对面没做

最麻烦的是最后一条

机器 A订单在这里
机器 Buser_1 的 total 在这里
① 发出total += 100
② 但回包丢了执行了，total = 100
③ 不知道超时了：它到底做没做？
④ 重试重试 total += 100
⑤ 重复了total = 200 —— 多算了一次

重试可能重复累加，不重试可能漏算。这个两难没有便宜的解法，只能把语义摊开来选：

投递语义会不会丢会不会重怎么做到
至多一次 At-most-once可能丢不会重发出去就不管了。实现最省事，但会丢数据
至少一次 At-least-once尽量不丢可能重失败就重试。这是绝大多数系统的默认选择
恰好一次 Exactly-once不丢不重不是「一种协议」，而是「事务 + 幂等 + 去重」组合出来的效果，最贵
⚠

「恰好一次」不是买来的，是拼出来的 —— 而且端到端由最弱的一环决定。

投递语义是一个三层栈：

Source 读进来  →  引擎内部处理  →  Sink 写出去

引擎内部可以做到恰好一次，但你 Sink 出去如果是「调一个第三方 HTTP 接口」， 那一环就是至少一次 —— 整条链路的保证，等于最弱那一环。

Kafka 从 0.11 起有幂等生产者（ProducerID + 每个分区的 SequenceNumber 去重）， Flink 有 TwoPhaseCommitSinkFunction —— 但它们都有边界： Kafka 的恰好一次只管 Kafka-to-Kafka，写数据库、调接口、发短信不在保护范围内。

那业界怎么补上「至少一次」的缺口：

  • 幂等写入 —— 让「重复写一次」和「写一次」结果相同，最省心的做法
  • 去重表 / 唯一键 —— 每条消息带唯一 ID，处理前查一下，处理完记一笔
  • 事务 —— 靠外部系统的事务能力，把「写结果」和「记位点」绑成一个原子操作
  • 两阶段提交 —— 一个 checkpoint 对应一个事务：先预提交，checkpoint 成功才正式提交

06假设③ 顺序执行 —— 同一秒改同一个 key

单机这个循环是顺序的，永远不会有两个线程同时执行 total += amount。

分布式里可以：

写者 Auser_1 +100
存储user_1 的 total
写者 Buser_1 +200
①读 total
② 也读读 total
③返回 0
④ 两边都拿到旧值返回 0
⑤写 100
⑥ 覆盖了 A写 200
⑦最终 total = 200，A 的 100 丢了

这叫丢失更新（lost update）。正确结果应该是 300。

一个比「加锁」更深的洞察

第一反应是「加锁」。但先看清 total += amount 其实是三步：读、改、写。

🕳

数据库里有个反直觉的事实：即使你加了行锁，结果仍可能是错的。

-- 这是「相对值」：不管谁先谁后，加起来都对
UPDATE counter SET value = value + 1;

-- 这是「绝对值」：第二个写者拿着过期的读，写回一个错的数
UPDATE counter SET value = 101;

加锁只保证「三步不被打断」，不保证「你写回的数是正确的合约」。 第二个写法即使严格串行执行，也会把前一个的修改抹掉。

这是语义问题，不是锁问题 —— 分布式里也一样：写回绝对值，谁也救不了你。

业界的三种解法

解法怎么保证不冲突什么时候用
悲观锁改之前先锁住（SELECT ... FOR UPDATE），强制串行冲突高、必须严格串行时。代价是等待和死锁风险
乐观锁写的时候校验版本号（WHERE version = 旧值），影响 0 行就是冲突了冲突低、重试便宜时。注意要校验版本号而不是值 —— 否则会踩 ABA
单写者让同一个 key 永远只有一个处理者，从根上消除并发分布式计算的标准答案
🔑

分布式里最优雅的解法不是「锁得更聪明」，而是「让冲突不可能发生」。

hash(userId) % 并行度  →  同一个 user 的所有订单，永远落到同一个处理者

没有并发，就不需要锁 —— 也不需要处理锁带来的一切麻烦（死锁、超时、重试风暴）。

这就是 keyBy、分区、shuffle、路由这一整套机制存在的真正原因： 它们不是为了「分发」而存在，是为了「让同一个 key 只有一个主人」而存在。

07假设④ 变量就在那儿 —— 状态得活过重启

单机里 total 放在 JVM 内存里，天经地义。但分布式里，一个进程随时可能：

宕机 · 被容器平台杀掉 · 因为发版重启 · 机器断电 · OOM · 被调度到别的机器

状态只在内存里的话，机器 A 挂掉 就意味着 A 负责的那些用户状态全部丢失。所以状态必须能被存下来、并且恢复得刚刚好：

① 运行时 算子的状态 只在内存里
user_11000
user_2250

进程一挂，这一整块就没了 —— 而且没有别人知道它原本是多少。

② 拍快照 checkpoint 两个东西一起存
状态快照user_1 = 1000写到可靠存储
输入位点offset = 50000我处理到哪了

这两样必须成对保存。只存状态，你不知道从哪继续； 只存位点，你不知道重新开始时累计值该是多少。

③ 恢复 重启之后 必须对得上
恢复的状态user_1 = 1000
从哪继续offset = 50001正好接上

状态和位点必须来自同一次快照。配错了，要么漏数据、要么重复算。

📌

「存状态」和「存位点」要当成一件事来做。

状态快照：user_1 的 total = 1000
输入位点：Kafka 已处理到 offset = 50000

这两行必须来自同一个时间点。 拿 10:00 的状态配 10:05 的位点，中间那 5 分钟的数据就永远算不进去了。

08假设⑤ 进程不会挂 —— 局部故障是常态

单机只有一个进程，挂了就是「整个程序停了」，好理解也好处理。分布式是另一回事：

100 台机器 · 1000 个容器 · 数万个网络连接

规模一上来，局部故障不是「会不会发生」，而是「哪台机器什么时候坏」。

最难受的是故障发生在中间：

订单算完了  →  状态更新了  →  ✗ 进程在这里挂了  →  结果没写出去
                                    ↑
                              恢复时该怎么办？
恢复策略会怎样
从旧位点重放可能重复写 —— 状态被加了两遍
不重放可能丢结果 —— 这条订单永远没写出去
去问下游收没收到下游可能也答不上来（比如它自己刚重启）

所以容错不是一件事，是一组机制配合：

  • Checkpoint / 快照 —— 定期把状态存到可靠存储
  • Replay —— 出事后从上次的输入位点重放
  • 幂等写入 —— 让「重复写」无害，这是最实在的一道保险
  • 去重 —— 认出「这条我已经处理过了」
  • 事务 / 两阶段提交 —— 让「提交状态」和「写出结果」原子化
  • 故障检测与重启 —— 得先知道谁挂了，才谈得上恢复
⚠

注意这份清单里，只有第 1、2 条是「算」的事，后面全是在「写」上做文章。

这也解释了为什么「恰好一次」这么贵：真正的难点不在状态本身， 而在把状态的变化和对外部世界的写入，绑成一个不会只做一半的动作。

09假设⑥ 快慢自然协调 —— 反压

单机循环里，write() 慢，read() 自然就跟着慢 —— 这是一种天然的节流，你什么都不用做。

分布式里，各步骤在不同进程里，谁也不知道谁的速度：

Source10 万/秒
→
Filter10 万/秒
→
Aggregate10 万/秒
→
Database Sink1 万/秒
反压　Sink 忙 → Aggregate 暂停发送 → Filter 减速 → Source 少拉一点
差 10 倍。第 1 秒积压 9 万条，第 2 秒 18 万条，第 N 秒把内存、磁盘或者消息队列撑爆。
所以必须让下游的「慢」沿数据流的反方向传回去 —— 这个机制叫反压（backpressure）。
🧠

一句话记住反压的本质：

一条流水线的整体速度，最终由最慢的那一环决定。 系统必须让积压可感知、可传回，而不能靠「无限缓存」把问题藏起来。

缓冲只能买时间，不能解决问题 —— 缓存越深，故障时炸得越响。

一个很少被讲、但很要命的细节

早年的 Flink（1.5 之前）反压是靠 TCP 自己的流控做的。它有两个坑：

① 一条 TCP 连接上复用了多个 channel，
   只要其中一个 channel 被堵，整条连接上其它 channel 全被拖住 —— 队头阻塞。

② 更麻烦的是：反压一旦形成，checkpoint 的 barrier 也传不过去了。
   而 barrier 传不过去 → checkpoint 超时 → checkpoint 失败 → 触发更多重试。
   一个性能问题，滚成了一个可靠性问题。

1.5 之后改成了 credit-based 流控：下游主动告诉上游「我还有多少缓冲空间（credit）」，上游有 credit 才发数据。这样每条 channel 独立受限，且 barrier 始终能穿过去。

10假设⑦ 机器数量不变 —— 状态要搬家

最后一个假设最容易被忽略，因为单机时代根本不存在「扩容」这回事。

现在假设按 hash(userId) % 3 分区，每台机器管着一部分用户的状态。你要把并行度从 3 改成 5：

状态不是「请求」，不能只是重新分配就完事

无状态服务扩容很简单：多起两个进程，负载均衡把新请求分过去就行。

并行度 3
A · 分区 0
B · 分区 1
C · 分区 2
并行度 5
A
D
B
E
C
但 user_1 的历史状态还在 A 上。请求重新分配了，状态却没跟过来 —— 新接手的 D 从零开始算，结果直接算错。所以扩容必须做完整套动作：存下状态 → 按新规则拆分 → 把状态搬给新实例 → 从正确的位点恢复。

Flink 是怎么解这一题的

关键在于：不要让「并行度」直接决定「状态的归属」。

hash(userId) % 3   ← 并行度一变，归属全变（取模的问题，第 02 节见过）

                ↓ 换一种做法

先把 key 空间切成固定份数：key group（数量 = maxParallelism）
每个并行实例负责一段连续的 key group
                     ↓
扩缩容时，只是在重新分配这些「固定的块」——
状态搬家的粒度从「一个个 key」变成了「一块块 key group」
📦

key group 的存在，就是为了让「改并行度」不必重算每一个 key 的哈希。

代价是：key group 的数量（最大并行度）在作业第一次提交时就定死了， 之后改不了 —— 因为一旦改，所有历史的 key group 下标就全对不上了。

这是分布式系统里很典型的一种权衡：用一个提前锁死的常量，换运行时的灵活。 类似的设计你在别处也见过 —— 比如 Kafka 的分区数一旦定了就不好改。

11收束：这些复杂性，被「算子」封装了

回头看：这七个问题，没有一个跟你的业务有关。它们全都来自「把单机程序放到多台机器上」这一件事。

通用复杂性

算子替你处理的

你只写业务逻辑：

filter → keyBy → sum → sink

而下面这些全部由引擎接走：

  • 并行化 —— 你说要几个实例，它去起线程
  • 分区路由 —— keyBy 之后，同一个 key 落到同一个实例
  • 状态管理 —— 状态怎么存、存多少、怎么换后端
  • 故障恢复 —— checkpoint + replay，不用你写
  • 反压 —— credit-based 流控，自动的
  • 状态迁移 —— 改并行度时，key group 自动重分配
orders
  .filter(o -> o.getAmount() > 0)
  .keyBy(Order::getUserId)
  .sum("amount")
  .sinkTo(clickHouse);
不该甩锅给引擎

你仍然要负责的

引擎解决的是通用问题。有几件事它替不了你：

  • 幂等边界 —— Sink 写出去那一步的语义，取决于下游系统， 引擎只能帮你到「至少一次 + 事务化写」
  • 消息 ID 生成 —— 去重表要的唯一键，得你的业务提供
  • keyBy 选哪个字段 —— 选错了，热点全压在一个实例上
  • 状态大小 —— 状态会不会无限长？要不要设 TTL？
  • 下游能不能被反复写 —— 你调的那个第三方接口，幂等吗？

这些是「业务语义」问题，引擎看不见，也管不了。

一句话总结

单机依赖的是：唯一状态 + 顺序执行 + 本地内存 + 不走网络 + 少量故障。 分布式面对的是：多份状态 + 并行执行 + 网络通信 + 节点故障 + 动态扩缩容。

所以一句 total += amount; 在分布式里会展开成一串问题： 这个 amount 路由到哪？这个 total 属于谁？会不会并发修改？状态可恢复吗？ 重试会不会重复？下游慢了怎么办？扩容后旧状态怎么搬？

而「算子」就是把这些通用复杂性打包收走的那个抽象。 你表达计算逻辑，引擎负责让它在多机上正确地活下去。

自测

为什么分布式里「加锁」不一定能解决丢失更新？

因为 total += amount 其实是读、改、写三步。 加锁只保证这三步不被打断，但它保证不了「你写回的数是正确的合约」—— 如果写回的是绝对值（SET value = 101）而不是相对值（value = value + 1）， 即使严格串行执行，第二个写者也会拿着过期的读把前一个的修改抹掉。 这是语义问题，不是锁问题。

一致性哈希比 hash(key) % N 好在哪？为什么值钱？

好在扩容时搬的东西少。 hash % N 里节点数一变，几乎所有 key 的归属都重算 —— 3 改 5 时约 2/3 的 key 换主人， N 从 10 变 11 也有约 90%。对「有状态」的系统来说，这意味着大半个状态都要跨网络迁移。 一致性哈希把 key 和节点放在同一个环上，加一个节点只接管一小段， 代价从「几乎全部」降到「约 1/N」。 再加虚拟节点，就顺手解决了负载倾斜。

「恰好一次」是一套协议吗？为什么 Kafka 的 exactly-once 不能保证你写数据库也不重复？

不是一套协议，是事务 + 幂等 + 去重组合出来的效果。 而且投递语义是一个三层栈 —— Source / 引擎 / Sink，端到端由最弱的一环决定。 Kafka 从 0.11 起的幂等生产者（ProducerID + 每个分区的 SequenceNumber） 和事务，只管 Kafka-to-Kafka 这一段。 你 Sink 出去如果写的是数据库或者调第三方接口，那一环仍然是至少一次 —— 要自己去补幂等键、去重表或者事务。

为什么「无限缓冲」不能解决上下游速度不一致？

缓冲只能买时间，不能解决问题。差 10 倍的话，积压是 9 万、18 万、27 万这样线性涨上去的， 内存/磁盘/消息队列迟早撑爆 —— 而且缓存越深，故障时炸得越响、恢复时重放得越久。 正确的做法是让下游的慢沿数据流反向传回去（反压）， 让 Source 主动少拉一点。本质是：流水线的速度由最慢一环决定，系统必须控制积压而不是藏起积压。

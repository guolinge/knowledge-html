select / poll：第一次搬进内核

把「问」从你自己的循环搬进内核：线程终于能睡了，等待不再占执行资源。但名单每次整份重交、内核每轮全扫两遍，返回的还是「标记位」而不是「就绪者本身」。内核是失忆的 —— 这两条没治的病，就是 epoll 的题目。

01轮询篇留下的三条，现在开始还

上一篇结尾列了三条需求：①内核得记住我关心哪些 fd；②内核得只把就绪的还给我；③等待不能再占用执行资源。

select 和 poll 是第一版答案，方向一句话就能说清：把你上一篇亲手写的那个 for 循环，搬进内核。

需求select / poll 给的答案满足了没有
① 内核记住我关心哪些 fd没记住。名单是你每次调用的参数，用完就忘没治
② 只把就绪的还给我返回的是改过标记的整份名单，谁就绪还得你自己查没治
③ 等待不占用执行资源线程真的睡了，睡在每个 fd 的等待队列上治了

治了一条，留着两条。怎么治的、为什么剩下两条治不了，是这一篇的正文。

02两个调用长什么样

先看代码，因为这两个调用的差别小到可以用一句话说完。

// select：名单是位图
fd_set rset;
FD_ZERO(&rset);
FD_SET(listen_fd, &rset);
FD_SET(conn_fd, &rset);

for (;;) {
    fd_set ready = rset;                 // select 会改写位图，每轮从备份复制
    int n = select(maxfd + 1, &ready, NULL, NULL, NULL);
    for (int fd = 0; fd <= maxfd; fd++)
        if (FD_ISSET(fd, &ready))        // 标记位要自己数
            handle(fd);
}

// poll：名单是数组
struct pollfd fds[N];
fds[0] = (struct pollfd){ listen_fd, POLLIN, 0 };
fds[1] = (struct pollfd){ conn_fd,  POLLIN, 0 };
int nfds = 2;

for (;;) {
    int n = poll(fds, nfds, -1);
    for (int i = 0; i < nfds; i++)
        if (fds[i].revents & POLLIN)     // revents 内核填，你挨个看
            handle(fds[i].fd);
}
selectpoll
名单的形状位图，FD_SETSIZE = 1024 格数组，没有 1024 这个上限
返回之后位图被改写，每轮要从备份复制一份每个元素的 revents 被内核填好
上限1024只受内存和进程 fd 数限制

形状的差别就这些。语义两个完全一样：整份名单交进去，改过标记的名单发回来。上面整体图里的每一步，两个调用走的是同一条路。

03一次调用，从头走到尾

开头那张整体图是一条完整的链，导览「一次调用的完整生命周期」会带着代码走一遍。这里只把三件最容易被略过的事说开：

「睡」是怎么实现的。 上一篇的轮询圈永不停也永不睡，因为用户态的代码挂不到任何队列上。进了内核就不一样了：问每个 fd 的时候，内核顺手把一个 pollwake 挂到这个 fd 自己的等待队列上（走的是 poll_wait 这扇门，所有驱动的 poll 方法都会从这扇门交出自己的队列）。全都没好，线程就睡；任何一个 fd 来了数据，中断敲它的队列，挂着的 pollwake 把线程叫醒。上一篇已经见过等待队列了 —— 阻塞 read 把线程挂上去的，就是这同一种东西。

为什么醒了还要再扫一遍。 pollwake 只做一件事：叫醒线程。它不记「是谁敲的我」。所以要找出就绪的那几个，只能把名单从头再问一遍。这就是图上两排「全扫描」的来历：第一遍在睡之前，第二遍在醒之后。

「白问」去哪了。 没消失。以前每次白问是一次系统调用；现在一整轮白问被合并进一次系统调用里，在内核里发生。每轮的成本变成：1 次系统调用 + 一遍 O(名单长度) 的内核扫描（睡一觉就再来一遍）+ 名单进、出各一次整份拷贝。

04治好的那一条：线程终于能睡了

把两个世界放在 CPU 上看：

上一篇 · 用户态轮询这一篇 · select / poll
没事件的时候线程在跑：accept、read、EAGAIN、再问线程在睡，CPU 跑别的进程
一轮的成本n 次 read 系统调用，每次都可能白问1 次系统调用；名单在里头扫一遍（睡了就再加一遍）
等待占用的执行资源一个从头到尾不睡的线程零 —— 睡着的线程不占 CPU

第 ③ 条需求「等待不能再占用执行资源」，到这里是真的成立了。上一篇说「问得太密 CPU 烧满、问得太疏延迟上去」，那个两难也松了：频率这件事交给了内核 —— 有事它敲你，没事它让你睡。

05没治的两条：全扫描没少，名单照样重交

睡是睡了，账还是那笔账。

你关心 2 条连接，名单上有 500 条。每次调用：500 条全拷进内核，内核挨个问（没问到就睡，醒来再问一遍），整份名单改好标记再拷回来，你再把 500 条挨个数一遍找出那 2 个。每一项成本都跟名单长度成正比，跟「这次真有几条就绪」无关。

病根在哪，上一篇 §06 已经点过一次：内核不记得你上次关心谁。select 和 poll 的内核实现是无状态的，像个每次都要重新填表的窗口 —— 你交一份表，它办完把表还给你，下一次来它完全不认识你。整体图上那根虚线就是这件事：每一轮调用都是完整的一生，两轮之间内核干干净净。

💡

把三条需求摆在一起看，epoll 要做的事就剩一件了：

让内核那头「记着」。记名单（你就不用每次重交）， 记就绪（它就不用再把整份名单扫一遍）， 把「问的时候临时挂、返回就拆」的 pollwake， 换成「登记一次、长期有效」的常驻回调。

下一篇的「两张表 + 回调」，就是对着这三句写的。

06同一扇门，不同的挂法

这一篇和下一篇共用一个机关，值得单独钉住：poll_wait 这扇门。内核里所有驱动的 poll 方法都会调它，把自己的等待队列交出来；谁想「等这个 fd」，就从这扇门把东西挂上去。

谁从门里进来挂的是什么待多久敲门之后
select / pollpollwake临时：问的时候挂，返回就拆只叫醒线程，谁就绪靠重扫
epollep_poll_callback常驻：epoll_ctl 挂一次，一直在敲门 + 记账：把 fd 挂进内核的就绪表

select / poll 每次调用重挂一遍、用完全拆，所以内核什么都记不住。epoll 把同一扇门上的挂载变成常驻的，顺手让它多干一件事（记账），「失忆」才被治好。下一篇整体图里「连接 A / B 的等待队列」那两格，挂的就是这个常驻回调。

select 和 poll 的差别是什么？哪些东西没变？

差别只在名单的形状：select 是位图、被 FD_SETSIZE 卡在 1024， poll 是数组、没有这个上限；另外 select 会改写位图（要备份）， poll 是内核往每个元素里填 revents。 没变的：整份名单交进去、改过标记的整份发回来、 内核每轮把名单全扫两遍 —— 语义和成本结构完全一样。

select 睡觉的机制是什么？和上一篇「永不停的圈」差在哪？

问每个 fd 的时候，内核走 poll_wait 这扇门，把 pollwake 挂到那个 fd 自己的等待队列上；全都没好，线程就睡 （TASK_INTERRUPTIBLE）。数据到 → 中断 → 敲 socket 的等待队列 → pollwake 把线程叫醒。上一篇的圈是用户态代码，挂不上任何队列， 只能一直问；进了内核才睡得着。

为什么醒来之后内核还要把名单再扫一遍？

因为 pollwake 只会敲门，不记「是谁敲的我」。唤醒路径上没有任何 「哪个 fd 就绪了」的记录，所以只能从头把名单重问一遍 （第二遍全扫描）找出就绪者。epoll 治的就是这一点： 它的回调敲门时顺手把 fd 挂进就绪表，醒来直接拿。

三条需求，select / poll 治了哪条？没治的病根是什么？

治了第 ③ 条：线程真的睡了，等待不再占用执行资源。 第 ① 条没治（名单每次现场重交），第 ② 条没治（返回标记位， 内核两遍全扫）。病根是内核失忆：无状态的实现， 返回时 poll_freewait 拆掉全部挂载，两轮之间什么都没记住。 要治它就得让内核记着 —— 这是 epoll 的题目。

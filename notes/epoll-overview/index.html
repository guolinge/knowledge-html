一台服务器要同时盯住一万条连接。其中大部分时间里，九千九百条什么也没有发生。

所以真正要设计的不是「怎么读得更快」，是「怎么等得起」。这棵树沿着一条线走：同样是等，Linux 把这件事挂在了哪里，又是谁在数据到达时被叫醒。

这一篇给出全程。后面七篇各放大一层。

01一万条连接，九千九百条在等

先把这个场景说具体。假设一个推送服务：

  • 同时在线 10,000 条 TCP 连接；
  • 每条连接平均几十秒才来一次心跳或消息；
  • 4 核机器，CPU 平时闲得很。

如果每条连接都配一个线程、在线程里阻塞地读，那么 10,000 个线程里，任意时刻只有个位数在真正干活。剩下的都在 read() 里睡着，等一个可能几十秒后才到的包。

这些线程没有烧 CPU。它们的问题在别处：每一条连接都占着一个执行单位，而这个执行单位除了「替这条连接等」之外什么也不做。

四代方案处理的是同一件事，只是把「等」挂到了不同的地方：

方案「等」挂在哪里数据到达时谁被叫醒
阻塞 readsocket 的等待队列上挂一个 task那个 task。它要回到运行队列，等调度器挑中
忙轮询什么都不挂。线程一直跑，反复问「有数据吗」没有人被叫醒。线程自己发现
select / pollN 个 socket 的等待队列上，各挂一个临时条目那个线程。醒来后还要自己找出是哪个 fd
epollsocket 的等待队列上挂一段回调，登记一次就常驻回调先把条目塞进就绪链表，再叫醒睡在 epoll_wait 的线程

看最后一行：被唤醒的对象不再是「一个线程」，而是「一段函数」。它不需要栈，不需要被调度，跑完就结束。这就是 epoll 真正做的事。

04后面七篇各自放大哪一段

概念 · 先看这里

② read 卡住的那一刻

线程从运行队列上被摘下来，挂进 socket 的等待队列。这个队列上挂的条目里有一个函数指针，它决定了后面的一切。

架构

③ 一条连接一个线程

把「8MB 栈 × 一万 = 80GB」这个流传很广的账算清楚，然后看真正贵的那一项：执行单位的数量。

架构

④ 轮询与 select / poll

一个线程开始招呼多条连接。内核替你在 N 个队列上挂条目，代价是名单每次重交、醒来全扫。

架构 · 正身

⑤ epoll 的两个结构

登记表和就绪表。数据到达时，回调把条目塞进就绪表。热路径不查任何树，也不遍历任何名单。

概念

⑥ 就绪是什么意思

可读指的是接收缓冲区里还有数据，不是「刚来了新数据」。LT 和 ET 的差别就在这点残留上。

架构

⑦ O(1) 说的是哪一段

登记、事件到达、收割，三段成本分开算。活跃率一高，epoll 的优势就消失。顺带说清 ONESHOT 和 EXCLUSIVE。

收束

⑧ 治好了什么，没治什么

等待不再需要线程了，但每次 I/O 的系统调用和拷贝还在。io_uring 换的是通信方式。

如果你现在只卡在一个点上，可以直接跳：

你的情况从这里进
知道 read 会阻塞，但不知道线程去哪了② 一篇就够
知道 epoll 有三个调用，但说不清内核里发生了什么② → ⑤。先看清等待队列，再看回调挂上去
用了 ET，线上偶尔有连接再也不响应⑥。多半是有数据没读完，下一次通知可能不会来
面试被问「epoll 为什么快」⑦。答案不在红黑树，在「通知不遍历」

05这篇的结论

💡

四代方案改的都是同一件事：「等」的载体，从线程换成了一段回调。

线程要占栈、要被调度、要等待上下文切换； 回调只需要一个链表节点和一个函数指针。

下一篇从最具体的地方开始：你写的那一行 read()，到底停在了哪里。

阻塞 read、select、epoll 都在等，它们最终都往哪个内核结构上挂东西？

socket 自己的等待队列（struct socket 里的 wq.wait，也就是 sk_wq）。 三者的区别是挂上去的条目不同：阻塞 read 挂一个 task，select/poll 挂临时条目，epoll 挂一段回调。

epoll 让「等」变便宜，具体便宜在哪一步？

便宜在通知到达时不需要唤醒一个线程。回调在数据到达的那个上下文里直接跑完， 只做两件小事：把条目放进就绪链表、叫醒可能在 epoll_wait 里睡着的线程。

为什么说忙轮询没有解决「等」，只是换了个方式付账？

它把「阻塞」换成了「反复问」。线程确实能招呼多条连接了，但没数据时它仍在跑， 每一次问都是一次系统调用。空转和系统调用的开销，就是它付的账。

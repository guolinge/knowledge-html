`````popquote
    #### 答

    你迷糊的核心原因，是把三种不同的「翻译」以及「指令」和「数据」混在一起了：

    1. **编译/汇编**：C 代码、汇编文本 → 机器码
    2. **地址翻译**：虚拟地址 → 物理地址
    3. **指令解码**：机器码 → CPU 内部操作

    它们是完全不同的事情。

    ##### 一、这里说的「指令」到底是什么

    假设源代码是：

    ```c
    int x = 10;

    void f() {
        x = x + 1;
    }
    ```

    它可能被编译成类似的汇编：

    ```asm
    mov eax, DWORD PTR [rip + x]   ; 读取 x
    add eax, 1                     ; 加 1
    mov DWORD PTR [rip + x], eax   ; 写回 x
    ```

    但 CPU 实际取到的不是这些文本，而是类似这样的二进制机器码：

    ```text
    8B 05 FA 2F 00 00
    83 C0 01
    89 05 F1 2F 00 00
    ```

    `mov eax, ...` 只是人类为了方便阅读，对机器码的文字表示。

    所以：

    - 汇编语言是给人看的
    - 机器码字节是 CPU 实际执行的
    - CPU 从内存中取的是机器码，不是 `"mov eax, ..."` 这串文字

    ##### 二、PC/RIP 指向的是什么

    PC/RIP 是一个寄存器，里面保存着：

    > 下一条要执行的机器指令所在的虚拟地址。

    例如：

    ```text
    RIP = 0x400100
    ```

    意思是：

    > 去当前进程的虚拟地址 `0x400100` 取机器码。

    假设那里存放：

    ```text
    8B 05 FA 2F 00 00
    ```

    CPU 取到这些字节，然后解码，才知道它表示：

    ```asm
    mov eax, DWORD PTR [rip + x]
    ```

    因此，RIP 不是指令本身，它只是指令所在位置的地址。

    ##### 三、「拿到指令为什么还需要翻译」

    这里的「翻译」有歧义。

    实际顺序是：

    ```text
    RIP 中有指令的虚拟地址
            ↓
    iTLB 把虚拟地址翻译成物理地址
            ↓
    根据物理地址，从 Cache/RAM 取到机器码
            ↓
    CPU 解码机器码
    ```

    也就是说，**地址翻译发生在真正取到指令之前**。

    ###### iTLB 翻译的不是汇编语言

    iTLB 做的是：

    ```text
    指令虚拟地址 → 指令物理地址
    ```

    例如：

    ```text
    虚拟地址 0x400100
            ↓ iTLB
    物理地址 0x18A32100
    ```

    然后 CPU 才能去 Cache 或 RAM 中找对应的机器码。

    iTLB 不会把：

    ```asm
    mov eax, [x]
    ```

    翻译成机器码，那是汇编器的工作。

    ##### 四、为什么使用虚拟地址

    现代操作系统给每个进程提供独立的虚拟地址空间。

    两个程序都可能认为自己在使用：

    ```text
    0x400100
    ```

    但它们映射到不同的物理内存：

    ```text
    进程 A 的 0x400100 → 物理地址 0x10000100
    进程 B 的 0x400100 → 物理地址 0x28700100
    ```

    所以 RIP 中通常保存的是虚拟地址，需要经过：

    ```text
    虚拟地址 → 页表/TLB → 物理地址
    ```

    CPU 才能访问真实的 Cache 和内存。

    ##### 五、为什么指令地址上没有 x 的值

    因为**指令和变量是两个不同的东西，通常位于不同地址**。

    可以把内存大致想象成：

    ```text
    虚拟地址空间：

    0x400100：mov eax, [rip + x] 的机器码
    0x400106：add eax, 1 的机器码
    0x400109：mov [rip + x], eax 的机器码

    ...

    0x403100：变量 x 的值，例如 10
    ```

    RIP 指向 `0x400100`，那里保存的是「如何操作」的机器指令。

    变量 `x` 位于 `0x403100`，那里保存的才是值 `10`。

    可以类比成：

    - 指令：菜谱，「去冰箱拿鸡蛋」
    - x：冰箱里的鸡蛋
    - 指令地址：菜谱放在哪里
    - x 的地址：鸡蛋放在哪里

    菜谱里会告诉你怎么找到鸡蛋，但菜谱本身通常不包含那颗鸡蛋。

    ##### 六、指令里到底有没有 x 的地址

    有时有，但通常不一定是完整地址，而是某种「地址计算方式」。

    ###### 1. RIP 相对寻址

    例如：

    ```asm
    mov eax, [rip + 0x2FFA]
    ```

    意思是：

    ```text
    x 的虚拟地址 = 下一条指令的 RIP + 0x2FFA
    ```

    指令中保存的是偏移量，而不是 x 的值。

    ###### 2. 栈变量

    例如：

    ```c
    void f() {
        int x = 10;
        x++;
    }
    ```

    可能变成：

    ```asm
    mov eax, [rbp - 4]
    add eax, 1
    mov [rbp - 4], eax
    ```

    这里 x 的地址是：

    ```text
    RBP - 4
    ```

    指令中只有 `-4` 这个偏移量，基础地址在 RBP 寄存器里。

    ###### 3. 堆上的变量

    例如：

    ```c
    int *p = malloc(sizeof(int));
    *p = *p + 1;
    ```

    可能是：

    ```asm
    mov eax, [rdi]
    add eax, 1
    mov [rdi], eax
    ```

    x 的地址已经保存在 `rdi` 这样的寄存器中。

    ###### 4. 立即数

    有些数值可以直接放在指令里：

    ```asm
    mov eax, 10
    add eax, 1
    ```

    这里的 `10` 和 `1` 是立即数，确实编码在指令内部，不需要去内存寻找。

    但普通变量的值可能随时变化，所以一般不能直接永久写在指令里。

    ##### 七、为什么取到指令后还要去找 x

    因为指令只描述「要做什么」，变量保存「要处理的数据」。

    例如 CPU 解码出：

    ```asm
    mov eax, [rip + x]
    ```

    它只知道：

    > 计算 x 的虚拟地址，然后从那里读取 4 个字节放入 EAX。

    接下来 CPU 才会：

    ```text
    1. 地址生成单元计算 x 的虚拟地址
    2. dTLB 将 x 的虚拟地址翻译为物理地址
    3. 查询 L1 D-Cache
    4. 未命中则查询 L2、L3、RAM
    5. 得到 x 的值
    6. 把值放入寄存器
    ```

    注意两种访问是分开的：

    | 访问类型 | 内容 | 使用的 TLB/Cache |
    |---|---|---|
    | 取指令 | 获取机器码 | iTLB、L1 I-Cache |
    | 读取 x | 获取变量值 | dTLB、L1 D-Cache |

    这也是为什么很多 CPU 把一级缓存分成：

    - L1 I-Cache：Instruction Cache，指令缓存
    - L1 D-Cache：Data Cache，数据缓存

    ##### 八、把整个过程重新串起来

    假设 CPU 执行：

    ```asm
    mov eax, [rip + x]
    add eax, 1
    mov [rip + x], eax
    ```

    ###### 第一阶段：取指令

    ```text
    RIP 保存指令虚拟地址
            ↓
    iTLB：指令虚拟地址 → 物理地址
            ↓
    L1 I-Cache 查找机器码
            ↓
    未命中则去 L2/L3/RAM
            ↓
    取回机器码
    ```

    ###### 第二阶段：解码

    CPU 将机器码解码为内部操作，例如：

    ```text
    计算 x 的地址
    读取 x
    加 1
    写回 x
    ```

    现代 CPU 还可能把一条复杂机器指令拆成多个微操作（µops）。

    ###### 第三阶段：读取 x

    ```text
    根据 RIP 和指令中的偏移量计算 x 的虚拟地址
            ↓
    dTLB：x 的虚拟地址 → 物理地址
            ↓
    查询 L1 D-Cache
            ↓
    没有则查询 L2、L3、RAM
            ↓
    得到 x 的值
    ```

    ###### 第四阶段：计算

    ```text
    x 的值进入寄存器
            ↓
    ALU 执行 x + 1
            ↓
    结果进入寄存器
    ```

    ###### 第五阶段：写回 x

    必须有一条 store 操作，例如：

    ```asm
    mov [rip + x], eax
    ```

    结果通常先进入：

    ```text
    Store Buffer → L1 D-Cache
    ```

    采用写回缓存时，对应 Cache Line 会被标记为 dirty，之后可能在缓存行被替换时写回更低层缓存或 RAM。

    ##### 九、你原来的步骤有哪些需要修正

    你的整体理解方向是对的，但有几个重要细节。

    ###### 1. 指令取值也可能发生 Cache Miss

    不只是变量 x 会查 L1/L2/L3/RAM，指令也一样：

    ```text
    L1 I-Cache → L2 → L3 → RAM
    ```

    ###### 2. iTLB 不翻译指令内容

    它只翻译：

    ```text
    指令虚拟地址 → 物理地址
    ```

    ###### 3. dTLB 也不查找 x 的值

    它只翻译：

    ```text
    x 的虚拟地址 → 物理地址
    ```

    真正的值由 Cache/RAM 提供。

    ###### 4. 结果不会自动从寄存器写到 Cache

    必须执行 store 指令，例如：

    ```asm
    mov [x], eax
    ```

    如果编译器认为 x 只需要保存在寄存器中，甚至可能根本不写内存。

    ###### 5. 这些步骤不一定严格串行

    现代 CPU 会：

    - 流水线执行
    - 乱序执行
    - 同时处理多条指令
    - 提前取指
    - 分支预测
    - 推测执行
    - 并行查询 TLB 和 Cache

    你列出的步骤适合作为逻辑模型，但不是精确的时序图。

    ##### 十、编译器可能让整个过程完全不同

    例如：

    ```c
    int f() {
        int x = 10;
        return x + 1;
    }
    ```

    优化后可能直接变成：

    ```asm
    mov eax, 11
    ret
    ```

    此时：

    - 没有从内存读取 x
    - 没有 dTLB 查询
    - 没有 D-Cache 查询
    - 甚至没有真正执行加法

    因为编译器已经知道结果是 11。

    再比如循环变量可能始终保存在寄存器中：

    ```asm
    add eax, 1
    ```

    这也不需要访问内存。

    所以你列出的步骤只适用于：

    > x 确实位于内存中，并且编译后的指令确实需要读取和写回它。

    ##### 十一、你的知识 gap 主要在哪里

    建议重点补齐下面几块。

    ###### 1. 编译过程

    理解：

    ```text

        ↓ 编译器
    汇编代码
        ↓ 汇编器

    关键点：CPU 执行机器码，不执行 C 代码或汇编文本。

    ###### 2. ISA 与机器指令

    需要了解：

    ###### 3. 进程的虚拟地址空间

    理解典型布局：

    ```text
    .text   ：机器指令

    .data   ：已初始化全局变量
    .bss    ：未初始化/零初始化全局变量

    ###### 4. 虚拟内存与 TLB

    ##### 十二、推荐的学习顺序

    不要一开始就把 TLB、Cache、流水线全部揉在一起。按下面顺序会清晰很多：

    1. **变量、指针、内存地址**
    2. **寄存器和基础汇编**

    4. **机器指令的编码与解码**

    > RIP 指向的是「指令在哪里」；指令描述「如何找到并处理 x」；x 的地址指向「数据在哪里」。指令和数据是两个独立的内存对象，访问它们通常需要两次独立的地址翻译和缓存查询。
`````

## 01 · 三件不同的事，都叫「翻译」

| 谁在做 | 输入 | 输出 | 什么时候发生 | 对应你表里的第几步 |
|---|---|---|---|---|
| 编译器 + 汇编器 + 链接器 | C 源码文本 | 汇编文本，然后变成机器码字节 | 编译那一次 | 表里没有这一步 |
| MMU（里面的 iTLB / dTLB） | 一个虚拟地址 | 一个物理地址 | 每一次访问内存，运行时 | 第 2 步、第 5 步 |
| 解码器 | 机器码字节 | CPU 内部的操作（µops） | 每一条指令执行时 | 第 4 步，但它不算「翻译」 |

三种都发生在不同的时间点：编译期一次、每次访问内存一次、每条指令一次。混在一起看，就会出现「已经是汇编了，为什么还要翻译」这种卡住的地方。

==CPU 从来没有见过汇编文本。== 汇编是写给人看的，汇编器把它变成字节；内存里躺着的是字节，`RIP` 指的也是字节数组里的某个位置。

## 02 · 一条 x = x + 1 的两个地址

先看这台机器上真编出来的东西。源码是一行 `x = x + 1`，`x` 是全局变量：

```c
int x = 10;
void f(void) { x = x + 1; }
```

`clang -O0 --target=x86_64-apple-darwin` 编出来，再用 `llvm-objdump` 反汇编，地址和字节是这样：

```text
0000000100000510 <_f>:
100000510: 55                     pushq  %rbp
100000511: 48 89 e5               movq   %rsp, %rbp
100000514: 8b 05 e6 1a 00 00      movl   0x1ae6(%rip), %eax    ## 0x100002000 <_x>
10000051a: 83 c0 01               addl   $0x1, %eax
10000051d: 89 05 dd 1a 00 00      movl   %eax, 0x1add(%rip)    ## 0x100002000 <_x>
100000523: 5d                     popq   %rbp
100000524: c3                     retq
```

符号表里 `_x` 在 `0x100002000`。两个地址对一下：

```text
读取：下一条指令 0x10000051a + 位移 0x1ae6 = 0x100002000  ✓
写回：下一条指令 0x100000523 + 位移 0x1add = 0x100002000  ✓
```

==同一个 x，两条指令里的位移不一样==（`0x1ae6` 和 `0x1add`），因为位移的基准是「各自的下一条指令」。位移不是地址，它只是一段要加到基准上的距离。

```memmap
title: 这两个东西，住在虚拟地址空间的两个不同页里
sub: 本机 clang -O0 编出的 x86_64 二进制（地址取自同一个静态布局）
high: 高地址
low: 低地址
segments:
  - { label: 内核空间, sub: 用户程序碰不到, tone: muted, size: 0.9 }
  - { label: 栈, sub: 局部变量、返回地址，向低地址长, tone: blue, size: 1.8, dir: down, mark: 通道 B 有时用这里 }
  - { label: 映射区 / 堆, sub: mmap、malloc 来的内存, tone: muted, size: 1.2 }
  - { label: 数据段 · x = 10, sub: "4 个字节，在 0x100002000", tone: amber, size: 1.2, addr: "0x100002000", mark: "通道 B 要翻译的就是这一页" }
  - { label: 代码段 · f 的 6 个字节, sub: "movl 0x1ae6(%rip),%eax 就在 0x100000514", tone: green, size: 1.2, addr: "0x100000514", mark: "通道 A 要翻译的就是这一页" }
note: 两者不在同一页。**页号不同 → 页表项不同 → TLB 里是两条不同的条目。**
```

再补一个实测：同一份二进制跑两次，两个地址整体平移了同一个随机量 —— 操作系统把地址空间随机化（ASLR）了：

```text
第一次：&f = 0x100a03510   &x = 0x100a05000
第二次：&f = 0x104903510   &x = 0x104905000
平移量都是 0x3F00000，两者的差始终是 0x1AF0
```

程序拿到的地址每次都不一样，说明它不可能是物理地址 —— 物理内存只有一份，不可能每个进程都从 `0x100a05000` 开始。==`RIP` 和指令里的位移都属于这套「每个进程自己一份」的虚拟地址，所以用之前必须先翻译。==

```arch
  rip:
    badge: 一个寄存器
    rows:
      - { k: 装的什么, v: 一个虚拟地址，不是指令、也不是物理地址 }
      - { k: 指向哪, v: 下一条要执行的指令 }
      - { k: 谁改它, v: 顺序执行时加上这条指令的长度，跳转时直接写新值 }
    note: 本机这条指令长 6 字节，所以下一条是 +6
  itlb:
    badge: 每条指令页一次
    rows:
      - { k: 查什么, v: 虚拟页号 → 物理页框号 }
      - { k: 没命中, v: MMU 去走页表，把结果填回来 }
    note: 页内偏移不参与翻译，原样带过去
  l1i:
    badge: 行 = 128 字节（本机）
    rows:
      - { k: 装什么, v: 机器码的副本 }
      - { k: 这次取回, v: "`8b 05 e6 1a 00 00`" }
      - { k: 谁放进来, v: 上一次没命中时，从 L2 或内存搬上来的整行 }
    note: 取指也会未命中，一样要往 L2、L3、内存问
  dec:
    badge: 每条指令
    rows:
      - { k: 输入, v: 几个字节，不是文本 }
      - { k: 输出, v: "「读 [下一条 RIP + 0x1ae6] 的 4 字节到 EAX」这样的操作" }
      - { k: 关键, v: 到这一步才算出 x 的地址，通道 B 也到这一步才启动 }
  dtlb:
    badge: 另一套表项
    rows:
      - { k: 查什么, v: x 的虚拟页号 → 物理页框号 }
      - { k: 和 iTLB 的关系, v: 两条独立条目，各查各的 }
  l1d:
    badge: 行 = 128 字节（本机）
    rows:
      - { k: 装什么, v: 数据的副本 }
      - { k: 这次取回, v: 4 个字节，值是 10 }
      - { k: 写回, v: store 先进 store buffer，再落进这一行；行标 dirty，等被逐出时才往下写 }
  reg:
    badge: 数据待的地方
    rows:
      - { k: 现在装, v: x = 10 }
      - { k: 算完装, v: 11 }
  alu:
    badge: 只做运算
    rows:
      - { k: 输入, v: 两个值（来自寄存器） }
      - { k: 输出, v: 11 }
    note: 它不访问内存，取数是前面已经做完的事
parts:
  rip:
    label: RIP
    detail: 它只回答「下一条在哪」。指令长什么样、x 在哪，它都不知道。
  itlb:
    label: iTLB
    detail: 指令地址的翻译缓存。条目里除了页框号，还带权限位 —— 取指也会做权限检查。
  l1i:
    label: L1 I-Cache
    detail: 只装指令。和 D-Cache 分开，是为了取指和取数能同时进行、互不阻塞。
  dec:
    label: 解码器
    detail: 把字节拆成操作数和操作。到这一步，指令里那个位移才被加上 RIP，变成 x 的地址。
  dtlb:
    label: dTLB
    detail: 数据地址的翻译缓存。==它只翻译地址，不碰值。==
  l1d:
    label: L1 D-Cache
    detail: 数据的副本。写回策略下，store 只改本地这一行，不立刻写内存。
  reg:
    label: 寄存器
    detail: 值和运算结果真正待的地方。x 有没有被放进寄存器，决定了后面还写不写内存。
  alu:
    label: ALU
    detail: 只做加减位移这类运算。它拿到的都是寄存器里的值。
  l2:
    label: L2
    detail: 指令和数据共用。两条通道的未命中都会到这里问一次。
  l3:
    label: L3
    detail: 再往下一层的大共享缓存，通常跨多个核。
  ram:
    label: RAM
    detail: 页表本身也在这里。取一条新的页表项，就是一次内存访问。
tours:
  - id: fetch
    label: 取一条指令要几步
    steps:
      - { at: [rip], text: "手里只有一个虚拟地址。==这一步什么都没有取到。==" }
      - { at: [itlb], text: "先换成物理页框号。页内偏移不参与翻译，所以页内位置不变。" }
      - { at: [l1i], text: "按物理地址查 L1I，取回 6 个字节。" }
      - { at: [dec], text: "字节拆开，才知道这条指令要干什么 —— 包括它还要读一次内存。" }
  - id: load
    label: 取 x 要几步
    steps:
      - { at: [dec], text: "解码给出 x 的地址：下一条 RIP + 0x1ae6 = 0x…2000。==通道 B 从这里开始。==" }

      - { at: [l1d], text: "查 L1D，取回 4 个字节：10。" }
      - { at: [reg, alu], text: "进寄存器，加 1，结果 11 回寄存器。" }
  - id: miss
    label: 没命中会怎样
    steps:
      - { at: [l1i, l1d], text: "两条通道都可能在自己的 L1 上没命中。指令和数据在这里是平等的。" }
      - { at: [l2], text: "先去 L2 问一次。命中就把整行搬回 L1，顺便放好。" }
      - { at: [l3], text: "L2 也没有，再往下问 L3。" }
      - { at: [ram], text: "只好去内存取。==取回来的仍然是一整行，不是一个变量。==" }
  - id: separate
    label: 为什么要分成两条
    steps:
      - { at: [itlb, dtlb], text: "两个地址落在不同的页里，翻译结果就是两条不同的条目。" }
      - { at: [l1i, l1d], text: "分开的 L1 让取指和取数可以同时进行 —— 合在一起就会互相挤掉对方的行。" }
```

## 05 · 指令里到底有没有 x 的地址

有，但形式不一样：**指令里存的是「怎么算出地址」，不是地址本身，更不是值。**

| 写法 | 机器码里存了什么 | 地址从哪来 | 本机实测 |
|---|---|---|---|
| 全局变量 `x` | 一个 32 位位移（`e6 1a 00 00`） | 下一条指令的 `RIP` + 位移 | `8b 05 e6 1a 00 00` |
| 栈变量 `x` | 一个 8 位位移（`fc`，即 −4） | `RBP` 的值 − 4 | `8b 45 fc` |
| 指针 `*p` | 只有寄存器号 | 寄存器 `rdi` 里的值 | `8b 07`（-O2，p 留在 `rdi`） |
| 立即数 `x + 1` 里的 `1` | 值本身（`01`） | 不需要地址，不用去内存 | `83 c0 01` |

前三种都还要再走一次「翻译 → 查缓存」，第四种不用 —— 因为 `1` 就在指令里。这也解释了为什么==普通变量不能直接写进指令==：它的值会变，而指令一旦编好就固定了。

再回到那个位移。同一个 x，读和写的两条指令里位移不同：

```text
读：0x1ae6  ← 基准是 0x10000051a
写：0x1add  ← 基准是 0x100000523
```

两条指令相差 9 个字节（`addl` 3 字节 + 前面 `movl` 的 6 字节），位移就跟着差了 9。如果位移是 x 的地址，它不该变。

## 07 · 速查与自测

想往前读，前置的几篇在这几处：[《RIP：CPU 怎么记住「下一条」》](../instruction-pointer/)讲 `RIP` 指哪、为什么指令长度不固定；[《进程和线程在两套空间里各有什么》](../two-spaces/)讲一个进程的地址空间长什么样；[《栈帧基址》](../frame-pointer/)和[《函数调用时栈上放了什么》](../stack-call-return/)讲栈上的地址怎么算出来。

```summary
title: 一句话
text: |
  `RIP` 给的是**指令的地址**，指令给的是**怎么算出 x 的地址**，x 的值住在**另一个页**里。
  三样东西、两个页、两次翻译、两个 L1 —— 这就是一条 `x = x + 1` 要看起来像「走了两遍内存」的原因。
```

```quiz
- q: 汇编代码里写着 `mov eax, [x]`，CPU 取到的是这行字吗？
  a: |
    不是。汇编器已经把它变成字节，比如 `8b 05 e6 1a 00 00`。CPU 取到的是这 6 个字节，
    解码之后才知道它是「从 [下一条 RIP + 0x1ae6] 读 4 字节到 EAX」。

    `mov eax, [x]` 是反汇编器把字节翻译回文本给人看的。
- q: 为什么取指令和取数据要各有一个 TLB、各有一个 L1？
  a: |
    因为它们访问的是两个不同页里的两个不同地址。翻译结果按页缓存，两条地址的页号不同，
    就只能各存一份；L1 分开则是为了让取指和取数能同时进行，不互相挤掉对方的行。
- q: 一条 store 执行完，值一定已经在内存里了吗？
  a: |
    不一定。它通常先进 store buffer，再落进 L1D 的那一行，那一行被标成 dirty。
    真正写回 L2、再写回 RAM，要等这一行被逐出。写进缓存和写进内存是两件事。
```

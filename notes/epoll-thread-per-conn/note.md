> 上一篇看到一个事实：线程睡下之后，CPU 是自由的，但那个线程仍然被这条连接占着。
>
> 这篇把这笔账算清楚。先纠正一笔流传很广的错误算式，再看真正贵的那一项。

## 01 · 先算那笔 80GB 的账

反对「一连接一线程」时，最常被引用的一笔账是：

```text
一个线程 8MB 栈 × 10,000 条连接 = 80GB
```

这个数看起来足够吓人，所以很少人去核。它是错的。

8MB 是 `pthread` 默认预留的**虚拟地址空间**，不是已经占用的物理内存。虚拟地址只是页表里的一个范围，页要等你真正写到那里才分配。线程的栈通常只碰到顶部几页。

真实的每线程开销大致是：

```cards
cols: 4
items:
  - title: 内核栈
    tag: 16 KB · x86-64
    desc: 线程进内核态执行时用它。Linux 在 x86-64 上给四页，大小在编译期定死。
    code: |
      THREAD_SIZE = PAGE_SIZE << 2
  - title: task_struct
    tag: 约 10 KB 量级
    desc: 内核里的任务描述，里面有状态、调度信息、指向地址空间和 fd 表的指针。大小随内核配置变。
  - title: 用户栈
    tag: 按需分配
    desc: 默认预留 8MB，实际只占碰到的页。一个普通的处理函数用几十 KB。
  - title: 合计
    tag: 约 40 KB / 线程
    desc: 一万条连接大约几百 MB。不小，但离 80GB 差两个数量级。
```

下面的控件把它算给你看。拖到一万条，内存那一栏是绿色的。

```demo
widget: thread-audit
title: 一连接一线程，亏的到底是什么
hint: 拖连接数，盯住「内存」和「调度器要管的实体」这两行的差别
config:
  conn: { min: 100, max: 50000, step: 100, def: 10000 }
```

!!一万个线程按实算才几百 MB。!! 这个数字不足以解释为什么一连接一线程撑不住 C10K。

顺带一提，真正的内存大头往往也不是线程：每条 TCP 连接的收发缓冲区（可以由内核自动调大）经常比一个线程贵得多。

## 02 · 贵的是「必须存在」这件事

把内存放一边，再看线程在等待时到底提供了什么：

```compare
first: 线程的状态
head: [它做了什么, 它对这条连接的意义]
rows:
  - 停在 read 里:
      - "不在运行队列上，不占 CPU"
      - "它是这条连接的「等待受理人」。没有它，这条连接没人管"
  - 被唤醒:
      - "回到运行队列，等调度器挑中"
      - "它只能处理自己那条连接。醒来之前它不知道别人有没有事"
  - 处理完再读:
      - "又回到 read，继续等这一条"
      - "它这一辈子都被绑在这条连接上"
```

第三条是关键。一个阻塞在 `read(fd_a)` 的线程，**没有办法知道 `fd_b` 有没有数据**。它连看都看不到 `fd_b`，因为它的执行现场停在 `read(fd_a)` 这一行里。

所以「一连接一线程」的成本不是内存，是：

```callout
tone: violet
icon: 💡
quote: true
text: |
  ==每多一条要等的连接，就多一个必须存在的执行单位。==

  而它在 99% 的时间里，存在的目的就是「让这条连接有人等」。
```

这就是 C10K 的真实瓶颈。不是 CPU 跑满了，也不是内存用光了，而是**你不会愿意为一万条空闲连接维持一万个执行单位**：调度器要管一万个实体，每次唤醒要动其中一个，上下文切换的次数随连接数涨。

## 03 · 线程池能救多少

线程池把「创建和销毁」的成本摊掉了，这一点是真的。但它改不了下面这条下限：

假设池子里有 100 个工作线程。每个线程一次只能阻塞在一条连接上。那么池子能同时「照看」的连接上限就是 100 条。第 101 条连接到达时，没有线程可以去等它。

```compare
first: 做法
head: [解决了什么, 没解决什么]
rows:
  - 来一条连接就新建线程:
      - "实现最简单"
      - "创建/销毁开销大；线程数没有上限"
  - 固定大小的线程池:
      - "创建开销摊掉了，线程数可控"
      - "池子大小就是「同时能等多少条连接」的上限"
  - 池子 + 阻塞 read:
      - "适合「任务短、连接少」的服务"
      - "一旦连接数超过池子，新连接只能排队等空闲线程"
```

线程池在这里的角色是「限制并发」，不是「提高并发」。它能防止你把机器打爆，但不会让一个线程同时等两条连接。

要突破这个上限，只有一条路：让线程不要停在任何一条具体的连接上。它应该先问「哪些连接有事」，再挑有事的处理。这就是下一篇的起点。

## 04 · 那怎么办

先记住这一篇的结论，它决定了后面所有方案的形状：

```checklist
items:
  - "线程睡下不占 CPU —— 所以「等」本身不贵"
  - "线程停在 read 里就不能服务别的连接 —— 所以「等」占着一个执行单位"
  - "并发上限 = 你能维持多少个执行单位，而不是 CPU 有多快"
  - "线程池限制并发，但不改变「一个执行单位只能等一条连接」"
```

下一篇看第一个解法：既然「等」占着执行单位，那就别等了，改成不停地问。一个线程从此可以招呼很多条连接，代价是它再也睡不下了。

```quiz
- q: 「一个线程 8MB 栈，一万个线程 80GB」这个算法错在哪？
  a: |
    8MB 是虚拟地址空间预留，不是已分配的物理内存。页按需分配，
    线程实际碰到的用户栈通常只有几十 KB，加上 16KB 内核栈和 task 结构，
    每线程实际开销在几十 KB 量级。
- q: 线程池为什么不能把「一连接一线程」的并发上限提上去？
  a: |
    池子里的线程和普通线程一样，一次只能阻塞在一条连接上。
    池子有 100 个线程，最多就同时照看 100 条连接。
    线程池限制的是并发，不是提高并发。
- q: 一个阻塞在 read(fd_a) 的线程，能知道 fd_b 有数据吗？
  a: |
    不能。它的执行现场停在 read(fd_a) 里，那条调用返回之前，
    它不会去检查任何别的 fd。这正是「一个执行单位只能等一条连接」的含义。
```

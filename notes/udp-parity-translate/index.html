01先把四个词说清楚（都从上面那份记录里认）

就是「一个字段 + 怎么比 + 比什么」

叶子（leaf）

上面 JSON 里那个 {"type":"portrait","condition":{…}} 就是一片叶子。

一个条件里可以有多片叶子，用 {"logic":"AND","conditions":[…]} 这样的树枝串起来。 叶子是「叶子」，因为它下面没有别的东西了 —— 它就是一个具体的判断。

真实的多叶子例子（现网 tag 1235865，两片叶子用 AND 串）：

{"conditions":[
  {"condition":{"items":[{"name":"alex_ftest_character_1778315960","op":"<=","value":99,
                          "dateType":"relative","dateUnit":"day"}]},"type":"portrait"},
  {"condition":{"items":[{"relationName":"alex_ftest_relation_1778490595","op":"NOT IN",
                          "value":["k1"],"formulaType":1}]},"type":"relation"}]}
SQL 里 WHERE 后面的那个判断

谓词（predicate）

「谓词」不是新东西，就是 SQL 里 WHERE 后面一个具体的判断：

WHERE `futu_hk_account_basic_customer_type` = 'Organization'
      └────────────── 这一整段就是一个谓词 ──────────────┘

「把条件编译成谓词」= 把界面上那句「客户类型 = 机构」，落成上面这串列名+比较符+值。

对照之下，现网在别的地方是「编译成一个 uid 集合」—— 不是一段判断，而是一条自己去查人的子查询：

-- 现网对关系条件的写法（一条完整子查询，结果是一批 uid）
select uid from niuniu_user_security_special_watchlist
 where object_id in ('75900664355662') group by uid

这两种写法的区别，就是后面所有「比不了」的根源。

我这一步只比这个

单叶子（single leaf）

一条记录里只有一片叶子，没有 AND / OR 树枝。

为什么只比它：多叶子时现网会用 union all + having count = N 表达 AND / OR， 而我写的是单条 WHERE 里的 (... OR ...) —— 形状不同，逐字比永远不相等。

真实对照（同一份 OR 条件，现网 case 1191481）：

-- 现网：两个叶子 → union all + group by
select uid from (select uid from 关系表A where … group by uid
                 union all
                 select uid from 关系表B where … group by uid) ct1 group by uid

-- 我们：同一条 WHERE 里写 OR
WHERE (uid IN (SELECT …关系表A…) OR uid IN (SELECT …关系表B…))

语义相同、文本不同 —— 这类只能靠跑数比结果（第三篇），不能比文本。

这条记录我们全翻得出来

无跳过叶子

现网的叶子有六类：特征 / 关系 / 实时用户群 / 离线用户群 / 事件 / 原始 SQL。 我只支持前三类（特征、关系、UID），其余会被「跳过」。

「无跳过叶子」= 这条记录里的所有叶子我都翻出来了。 如果有一条被跳过，那条记录的对账就没有意义 —— 因为现网的 SQL 里还带着我没翻的那个条件：

-- 现网 tag 846335 的 SQL：除了特征，还混着一个「离线用户群」条件
select uid from user_portrait where (特征条件)
union all select uid from user_portrait where uid in (
  select uid from crowds where (crowd_id = '29178d-20260630095237-crowd' …))
--                                 └── 这个条件我没翻，比出来的差异全是它造成的 ──┘

03为什么要翻译，而不是直接比两条 SQL

现网记录里已经有它自己的 SQL，我也有自己的输出。最直觉的做法是抓两条直接 diff —— 但那样永远不相等，因为两边把条件变成 SQL 的思路根本不同：

层面现网：条件 → uid 集合我们：条件 → 谓词
一片叶子select uid from 表 where (条件) —— 结果是一批人列 比较符 值 —— 结果是一个判断
AND嵌套 group by uid having count = N直接 AND
ORunion all + having count = N(… OR …)
否定uid not in (select uid …)NOT EXISTS 相关子查询

真实的两条 SQL 摆在一起看（同一条 OR 条件，现网 1191481）：

-- 现网：每个条件是「一批人」，于是 OR 就是两批人并起来
select uid from (
  select uid from niuniu_user_security_special_watchlist where object_id in (…) group by uid
  union all
  select uid from futu_hk_user_security_position        where object_id in (…) group by uid
) ct1 group by uid

-- 我们：每个条件是「一个判断」，于是 OR 就是同一段 WHERE 里的 OR
SELECT u.uid FROM user_portrait u WHERE (
  u.uid IN (SELECT uid FROM 关系表A WHERE object_id IN (…))
  OR u.uid IN (SELECT uid FROM 关系表B WHERE object_id IN (…)))

所以「直接 diff」只有两种结局：全红，或者一条条手工认定「等价」—— 后者等于用眼睛当编译器。

分成两层之后就好办了：

层 比什么 能证明什么 在哪篇
谓词级 单叶子的 WHERE 片段，归一化后逐字比 「字段 + 操作符 + 值」这层编译对不对 第二篇
结果级 两侧 SQL 在同一份数据上跑出来的 uid 集合 OR / 否定 / 计数 这层语义对不对 第三篇

两层都要求先把现网条件翻成我的草稿 —— 因为「我的 SQL」只能从我的草稿编译出来。这就是 ① 存在的理由。

06五个坑（每个都是真实记录）

坑 ① 值也是数组 1074 处 
{"op": "gte", "value": ["1"]}
{"op": "!=", "value": [1]}

现网把比较符的值也落成数组 —— gte 带 ["1"]。而我们的 DSL 是强类型：gte 要标量、in 要数组。

比较符取第一个元素；=/!= 配多值时翻成 in / not_in
坑 ② EXIST 必须带值 2 处 
{"op": "EXIST", "name": "plan_external_id",
 "value": ["1000450", "1000449", "1000451"]}

我按「无值操作符」把 value 丢了，结果我们的 exist 要一个数组（主键属性要命中的值）→ 结构校验直接拒。

只有 eq_default / neq_default 无值；exist / not_exist 要带
坑 ③ 关系叶子用 relationName 228 处 
{"type":"relation","condition":{"relationName":"…","op":"IN"}}

我的「挑条件行」函数只认 name，而关系叶子用的是 relationName → 228 条关系条件全被判成「形状不认识」，关系明细叶子从 686 掉到 914 才补回来。

同时认 name 与 relationName
坑 ④ 老一版前端 1527 处 
{"key":"futu_hk_account_status","val":["1"],"cmp":"=","type":"Portrait"}

不认它就等于把 1527 处语料当不存在 —— 翻译率卡在 42% 上不去。

加 legacy 路径并在报告里单独标方言
坑 ⑤ 英文与中文混排的 operator 收尾 
{"op":"EXISTENCE"}  vs  {"op":"EXIST"}

现网在不同记录里混用 EXIST / EXISTENCE，映射表要两种都认。

映射表里补齐同义词

修完这五个，翻译率 42.4% → 52.5%，buildQuery 通过率 98.9% → 100%。

10自测

「谓词」和「uid 集合」这两种编译方式，差别到底在哪？

谓词是 SQL 里 WHERE 后面的一个判断（列 比较符 值），它本身不产出人； uid 集合是一条完整的子查询（select uid from 表 where …），它产出一批人。 现网走的是后者，我走的是前者 —— 所以 OR 在现网是「两批人并起来」（union all）， 在我这里就是同一段 WHERE 里的 ... OR ...。语义可以相同，文本必然不同。

为什么这一步只比「单叶子 + 画像 + 无跳过叶子」的记录？

① 单叶子：多叶子时现网用 union all + having count = N 表达 AND/OR，我是单条 WHERE，文本没法对应； ② 画像：关系条件现网写成 uid in (select uid from 关系表 …)，我是 NOT EXISTS 子查询，形状不同； ③ 无跳过叶子：如果记录里有我没翻的叶子（tag / crowd / event / rawSql），现网的 SQL 里还带着它， 比出来的差异全是它造成的。三条都满足的谓词，两边应当是同一件事。

本地种子和镜像表，为什么要造两张不同的表？

因为要验的东西不同。本地种子按我们真实的 Catalog 造（18 个特征），用来验我们自己的字段口径； 镜像表按现网语料的词表造（98 个字段、28 张关系表），让语料里的条件能在本地真的跑起来 —— 后者才是验 OR / 否定 / 计数这些语义的前提。两张表名字与列都不同，互不干扰。

镜像层叠起来就是一个 rootfs · 什么才是「叠」

「层叠成 rootfs」不是复制合并，是一条查找规则：从最上层往下问，谁先有算谁的。它顺带解释了目录为什么会合并、改文件为什么贵、删文件为什么不释放空间。

01一句话的答案

镜像层叠起来就是一个 rootfs。

这句话经常被理解成「把几层的文件复制合并成一个新目录」。不是。

准确的版本是：

运行时把几层按顺序挂在一起，然后定了一条查找规则：从最上层往下问，谁先有算谁的。 这条规则跑出来的结果，就是容器进程看到的 /。

所以「叠」是个动作，不是一个结果。它发生在每一次 open 的时候， 而不是在容器启动的时候。

磁盘上

层是真的存在的

每一层是宿主机磁盘上的一个目录

FROM debian:12 是一层，apt install openjdk-17 是另一层， COPY app.jar /app/ 又是一层。

它们是分开存的，谁也不包含谁。

运行时才有

rootfs 不是磁盘上的东西

它是「合并出来的视图」，不是一个实体目录

磁盘上找不到「这个容器的 rootfs」这样一个文件夹。

它是挂载出来的：内核按规则把几层组合着看， 组合出来的样子就叫 rootfs。

所以它是视图，不是副本。

运行时创建

可写层是每个容器独有的

只读层全镜像共享，可写层一人一份

容器一起来，运行时在镜像层上面再盖一层空的。

你写的、改的、删的，全部落在这一层里。

镜像层一个字节都不会变。

02磁盘上真实的样子

看这张图，有几件事是一眼能看出来的：

  • 只读层在磁盘上是一层一层排的，可写层在最上面，起来的时候是空的
  • 一个路径可能只来自某一层（/app/app.jar 只来自层 3）
  • 一个路径可能好几层都有，但只有一个能被看见（/etc/os-release 层 1 和层 2 都有，读到的是层 2 的）
  • 一个目录可能是好几层拼起来的（/etc）

最后两条是这篇文章的重点，下面分开讲。

03「叠」到底怎么叠：一条查找规则

拿 /etc/os-release 举例。容器里读这个路径时，内核不是「打开某个合并后的文件」， 而是从最上层往下问：

第几步问谁它的回答然后
①可写层没有这个路径继续往下问
②层 3 · 应用没有继续
③层 2 · JDK有就是它了，停止查找
④层 1 · 基础系统也有，但没人来问了——

「叠」的全部内容就是这张表。 第一个回答「有」的层赢， 下面的层哪怕也有，也不会被看。

这条规则还解释了另外两件常见的事：

现象用这条规则解释
为什么改配置那么慢第一次改某一层的文件时，要先把它整份复制到可写层（copy-up），见第 05 节
为什么删了文件磁盘没释放删除只是在可写层放了个「此处没有」的标记，下层那份还在，见第 06 节

04三种情况，只有一种是真的「覆盖」

「上层盖住下层」这句话对文件成立，对目录不成立 —— 这是最容易搞错的一条。

情况一：只有一个层有它

最简单。直接露出来，不用做任何事。

情况二：同名文件 → 上层赢，下层被挡住

层 2 里的 /etc/os-release 装 JDK 时被改过
层 1 里的 /etc/os-release debian 自带的那个
容器里 open() 到的 结果是层 2 那一份

注意底下那条虚线。层 1 的那份并没有被删除，也没有被覆盖 —— 它只是被挡住了。 镜像层是只读的，谁也改不了它。

情况三：同名目录 → 两层的内容合并

两层的 /etc 合并成一个 /etc
层 2 的 /etc/ 装 JDK 时加了 java 配置
层 1 的 /etc/ debian 自带的一整套
容器里 ls /etc 两边的文件都在

目录是合并的，不是覆盖的。

如果按「上层赢」理解，ls /etc 就只能看到层 2 的那几个文件， debian 自带的那一整套 passwd、hosts、apt/ 全都不见了 —— 但它们是存在的。

🔑

一条能记住的判据：

撞上的东西是 结果
同名目录 两边的孩子并在一起
同名非目录（文件、符号链接、设备） 上层赢，下层被挡住

内核文档里的原话是非目录（non-directory）：「如果这个名字在任何一层里是 非目录，那么下层的对象就被隐藏」。也就是说 目录 vs 文件 这种撞法， 上层赢 —— 你不会得到一个「又是文件又是目录」的东西。

05改一个文件：copy-up

读写层下面的东西是只读的，那「在容器里改 /etc/os-release」是怎么做到的？

改之前 /etc/os-release 只在层 2
可写层没有这个路径
层 2os-release · 只读
读它的时候直接读层 2 那份，不做任何复制

只有读的话，一直是零成本的

容器里执行 echo 一句话 >> /etc/os-release层 2 改不了
触发 copy-up 先把整份复制到可写层 复制一整份
可写层os-release · 完整副本刚被创建
层 2原封不动
复制多少整个文件，不是只复制要改的那几个字节

一个 2GB 的文件，改一个字节也要先复制 2GB —— 这是真实开销

在副本上改之后的读都走可写层这份
改完之后 磁盘上现在有两份 占了两份空间
可写层改过的版本以后都读它
层 2旧版本 · 还占着空间

层 2 那份永远不会被回收，因为它属于镜像，别的容器可能也在用

所以「容器里改文件」在磁盘上是「多占一份」，不是「改掉了原来那份」。

这也是为什么「别在容器里改大文件」是一条真建议 —— 改一次就多一份。

06删一个文件：whiteout

删除比修改更微妙：文件在只读层里，你删不掉它，但你得让容器看不见它。

删之前 /etc/os-release 能看见
可写层没有这个路径
层 2os-release
open 它成功，读到层 2 那份
容器里执行 rm /etc/os-release层 2 删不掉，只能想别的办法
rm 的那一刻 在可写层做一个「墓碑」 whiteout
可写层出现一个 /etc/os-release它是个特殊标记
它长什么样字符设备，主次设备号都是 0（0/0）老内核里是符号链接；现代内核也可能用零长度文件 + `trusted.overlay.whiteout` 这个 xattr
层 2原封不动，一个字节没动
再 open 这个路径从上往下问一遍
删之后 查不到了 空间没释放
可写层先命中那个墓碑
查到什么「此处没有」—— 停止，不往下找
层 2文件还在，占着原来的空间

这就是「容器里删了大文件，宿主机磁盘没变」的原因

🪦

「墓碑」这个比喻在这里是字面意义上的。

它是一个内核层面的特殊文件，作用是告诉 OverlayFS： 「这个路径在下层有，但在我这里被删了，查到这里就停下，别再往下看了」。

它占的空间极小（一个字符设备节点），但它挡住的可能是下面几个 GB。

同一个机制还有一个变体叫 opaque directory：标记「这个目录整个以我为准， 别往下合并了」。它也是用 xattr 实现的。

07三个容器，一套只读层

可写层是一人一份的，只读层是全镜像共享的。所以在同一台机器上跑三个同一个镜像的容器：

可写层：每个容器各一份
容器 1 Java 进程
容器 2 也是 Java 进程
容器 3 同一个镜像起的
可写层 1 改过的 os-release
可写层 2 还是空的
可写层 3 只改了一个配置文件
镜像层 · 层 1 / 层 2 / 层 3 只读。三份容器共用同一批，磁盘上只有一份

同一台机器上跑 50 个基于同一个镜像的容器，镜像层在磁盘上仍然只有一份。 多出来的开销只是 50 个可写层里各自改过的那点东西。

这也解释了「容器很轻」这句话的准确含义：轻的是运行时开销， 不是镜像本身小 —— 镜像该多大还是多大，只是大家共用一份。

08rootfs 里没有内核

这一点经常被漏掉：rootfs 只包含用户空间的文件。

东西在不在容器的 rootfs 里说明
内核（/boot/vmlinuz、内核模块）不在容器共用宿主机的内核，不自己带一个
/bin /usr /lib 这些命令和库在来自镜像的基础层
你的应用和依赖在来自上面几层
/proc /sys /dev在，但是是运行时挂上去的不是镜像层提供的，是内核暴露出来的视图

所以「容器是一个完整的 Linux 系统」这个说法要打个折： 它是一套完整的用户空间，加一个借来的内核。

📖

顺带一个术语坑：rootfs 这个词有两个意思。

场合 指什么
容器语境（这篇） 容器进程看到的那棵 / 目录树
内核文档 系统启动早期挂的一个 ramfs/tmpfs 实例，是给内核用的临时根

内核文档里甚至明确说「所有 Linux 系统里都有一个 rootfs」—— 那个 rootfs 和你容器里的 rootfs 不是一回事。读到这个词先看上下文。

09四个常被说错的点

  • 「叠起来就是复制合并成一个新目录」—— 不复制。是挂载时的查找规则，每次 open 时现算
  • 「上层盖住下层」—— 只对文件成立；目录是合并
  • 「容器删了文件，磁盘空间就释放了」—— 只是加了个墓碑，下层那份还在
  • 「容器里改文件很方便，反正层是写时复制的」—— 改一个字节要先把整份复制上来，大文件很贵
📏

一条工程上的现实：层数是有上限的。

overlay2 驱动最多支持 128 层 lower。而实际上更早就撞墙 —— 有人实测 docker build 到 122 层左右就报 max depth exceeded， 因为挂载参数的长度受内核页大小限制。

这个数字各来源说法不完全一致（122 / 125 / 128），跟环境有关， 但方向是确定的：层越多越容易出问题。

所以 Dockerfile 里把 RUN 合并成一条，不只是「减少层数好看」—— 它真的在避开一个上限。

「镜像层叠起来就是一个 rootfs」里的「叠」，具体是什么动作？

不是复制合并，是一条查找规则：从最上层往下问，谁先有这个路径就算谁的。 它发生在每次 open 的时候，而不是容器启动的时候。 磁盘上没有任何一个目录叫「这个容器的 rootfs」—— 它是挂载出来的视图。

上层和下层都有 /etc，容器里 ls 会看到什么？

看到两边的并集。目录是合并的，不是覆盖的。 「上层赢」只对非目录（文件、符号链接、设备）成立。 如果按覆盖理解，debian 自带的那些配置文件就全都消失了 —— 但它们在。

容器里 rm 了一个 2GB 的文件，为什么宿主机磁盘没变？

因为文件在只读的镜像层里，删不掉。rm 只是在可写层放了一个墓碑（whiteout， 一个 0/0 的字符设备节点），让查找到这个路径时停下、不再往下看。 镜像层里那份 2GB 还在，而且只要这个镜像还在被使用就不会被回收。

一句话说清 rootfs 和内核的关系。

rootfs 只包含用户空间的文件（命令、库、应用），不含内核。 容器共用宿主机的内核，靠 mount namespace 和 pivot_root 拿到自己的 /。 所以「容器是一个完整的 Linux 系统」应该修正成「一套完整的用户空间 + 一个借来的内核」。

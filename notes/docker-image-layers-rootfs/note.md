## 01 · 一句话的答案

> 镜像层叠起来就是一个 rootfs。

这句话经常被理解成「把几层的文件复制合并成一个新目录」。**不是。**

准确的版本是：

> 运行时把几层按顺序挂在一起，然后==定了一条查找规则：从最上层往下问，谁先有算谁的。==
> 这条规则跑出来的结果，就是容器进程看到的 `/`。

所以「叠」是个**动作**，不是一个**结果**。它发生在每一次 `open` 的时候，
而不是在容器启动的时候。

```cards
cols: 3
items:
  - title: 层是真的存在的
    tag: 磁盘上
    tone: violet
    desc: 每一层是宿主机磁盘上的一个目录
    body: |
      `FROM debian:12` 是一层，`apt install openjdk-17` 是另一层，
      `COPY app.jar /app/` 又是一层。

      它们是**分开存的**，谁也不包含谁。
  - title: rootfs 不是磁盘上的东西
    tag: 运行时才有
    tone: blue
    desc: 它是「合并出来的视图」，不是一个实体目录
    body: |
      磁盘上找不到「这个容器的 rootfs」这样一个文件夹。

      它是**挂载**出来的：内核按规则把几层组合着看，
      组合出来的样子就叫 rootfs。

      ==所以它是视图，不是副本。==
  - title: 可写层是每个容器独有的
    tag: 运行时创建
    tone: green
    desc: 只读层全镜像共享，可写层一人一份
    body: |
      容器一起来，运行时在镜像层**上面**再盖一层空的。

      你写的、改的、删的，全部落在这一层里。

      ==镜像层一个字节都不会变。==
```

## 02 · 磁盘上真实的样子

```arch
svg: docker-layer-view
caption: 左边是宿主机磁盘（层分开存），右边是容器进程看到的 /。中间那三条线，就是这个容器里几个真实路径的来历。
```

看这张图，有几件事是一眼能看出来的：

- **只读层在磁盘上是一层一层排的**，可写层在最上面，起来的时候是空的
- **一个路径可能只来自某一层**（`/app/app.jar` 只来自层 3）
- **一个路径可能好几层都有，但只有一个能被看见**（`/etc/os-release` 层 1 和层 2 都有，读到的是层 2 的）
- **一个目录可能是好几层拼起来的**（`/etc`）

最后两条是这篇文章的重点，下面分开讲。

## 03 · 「叠」到底怎么叠：一条查找规则

拿 `/etc/os-release` 举例。容器里读这个路径时，内核不是「打开某个合并后的文件」，
而是**从最上层往下问**：

```compare
first: 第几步
head: [问谁, 它的回答, 然后]
rows:
  - ①: ["可写层", { text: "没有这个路径", tone: muted }, "继续往下问"]
  - ②: ["层 3 · 应用", { text: "没有", tone: muted }, "继续"]
  - ③: ["层 2 · JDK", { text: "有", tone: green }, { text: "就是它了，停止查找", tone: green }]
  - ④: ["层 1 · 基础系统", { text: "也有，但没人来问了", tone: amber }, "——"]
```

==「叠」的全部内容就是这张表。== 第一个回答「有」的层赢，
下面的层哪怕也有，也不会被看。

这条规则还解释了另外两件常见的事：

```compare
first: 现象
head: [用这条规则解释]
rows:
  - 为什么改配置那么慢: ["第一次改某一层的文件时，要先把它整份复制到可写层（copy-up），见第 05 节"]
  - 为什么删了文件磁盘没释放: ["删除只是在可写层放了个「此处没有」的标记，下层那份还在，见第 06 节"]
```

## 04 · 三种情况，只有一种是真的「覆盖」

「上层盖住下层」这句话对**文件**成立，对**目录不成立** —— 这是最容易搞错的一条。

### 情况一：只有一个层有它

最简单。直接露出来，不用做任何事。

### 情况二：同名**文件** → 上层赢，下层被挡住

```flow
grid: true
nodes:
  - { id: u,  label: "层 2 里的 /etc/os-release", sub: "装 JDK 时被改过", row: 0, tone: green }
  - { id: l,  label: "层 1 里的 /etc/os-release", sub: "debian 自带的那个", row: 0, tone: muted }
  - { id: r,  label: "容器里 open() 到的", sub: "结果是层 2 那一份", row: 1, tone: blue }
edges:
  - { from: u, to: r, label: "上层赢", labelDx: -54 }
  - { from: l, to: r, label: "下层那份还在磁盘上，只是看不见了", dashed: true, labelDx: 40 }
```

注意底下那条虚线。==层 1 的那份并没有被删除，也没有被覆盖 —— 它只是被挡住了。==
镜像层是只读的，谁也改不了它。

### 情况三：同名**目录** → 两层的内容合并

```flow
grid: true
groups:
  - { id: m, label: "两层的 /etc 合并成一个 /etc", tone: green }
nodes:
  - { id: u,  label: "层 2 的 /etc/", sub: "装 JDK 时加了 java 配置", row: 0, tone: green, group: m }
  - { id: l,  label: "层 1 的 /etc/", sub: "debian 自带的一整套", row: 0, tone: muted, group: m }
  - { id: r,  label: "容器里 ls /etc", sub: "两边的文件都在", row: 1, tone: blue, group: m }
edges:
  - { from: u, to: r, label: "并集，不是二选一" }
  - { from: l, to: r }
```

!!目录是**合并**的，不是覆盖的。!!

如果按「上层赢」理解，`ls /etc` 就只能看到层 2 的那几个文件，
debian 自带的那一整套 `passwd`、`hosts`、`apt/` 全都不见了 —— 但它们是存在的。

```callout
tone: violet
icon: 🔑
text: |
  **一条能记住的判据：**

  | 撞上的东西是 | 结果 |
  |---|---|
  | 同名**目录** | ==两边的孩子并在一起== |
  | 同名**非目录**（文件、符号链接、设备） | 上层赢，下层被挡住 |

  内核文档里的原话是非目录（non-directory）：「如果这个名字在任何一层里是
  **非目录**，那么下层的对象就被隐藏」。++也就是说 `目录 vs 文件` 这种撞法，
  上层赢 —— 你不会得到一个「又是文件又是目录」的东西。++
```

## 05 · 改一个文件：copy-up

读写层下面的东西是只读的，那「在容器里改 `/etc/os-release`」是怎么做到的？

```journey
- tag: 改之前
  tone: muted
  name: /etc/os-release
  badge: 只在层 2
  fields:
    - { k: 可写层, v: "没有这个路径" }
    - { k: 层 2, v: "os-release · 只读" }
    - { k: 读它的时候, v: "直接读层 2 那份，不做任何复制" }
  note: 只有读的话，一直是零成本的
  next: "容器里执行 echo 一句话 >> /etc/os-release :: :: 层 2 改不了"

- tag: 触发 copy-up
  tone: amber
  name: 先把整份复制到可写层
  badge: 复制一整份
  fields:
    - { k: 可写层, v: "os-release · 完整副本", note: 刚被创建, tone: warn }
    - { k: 层 2, v: "原封不动" }
    - { k: 复制多少, v: "整个文件，不是只复制要改的那几个字节" }
  noteTone: bad
  note: 一个 2GB 的文件，改一个字节也要先复制 2GB —— 这是真实开销
  next: "在副本上改 :: :: 之后的读都走可写层这份"

- tag: 改完之后
  tone: green
  name: 磁盘上现在有两份
  badge: 占了两份空间
  fields:
    - { k: 可写层, v: "改过的版本", note: 以后都读它, tone: ok }
    - { k: 层 2, v: "旧版本 · 还占着空间" }
  note: 层 2 那份永远不会被回收，因为它属于镜像，别的容器可能也在用
```

==所以「容器里改文件」在磁盘上是「多占一份」，不是「改掉了原来那份」。==

!!这也是为什么「别在容器里改大文件」是一条真建议 —— 改一次就多一份。!!

## 06 · 删一个文件：whiteout

删除比修改更微妙：文件在只读层里，你删不掉它，但你得让容器**看不见**它。

```journey
- tag: 删之前
  tone: muted
  name: /etc/os-release
  badge: 能看见
  fields:
    - { k: 可写层, v: "没有这个路径" }
    - { k: 层 2, v: "os-release" }
    - { k: open 它, v: "成功，读到层 2 那份" }
  next: "容器里执行 rm /etc/os-release :: :: 层 2 删不掉，只能想别的办法"

- tag: rm 的那一刻
  tone: red
  name: 在可写层做一个「墓碑」
  badge: whiteout
  fields:
    - { k: 可写层, v: "出现一个 /etc/os-release", note: 它是个特殊标记, tone: warn }
    - { k: 它长什么样, v: "字符设备，主次设备号都是 0（0/0）", note: "老内核里是符号链接；现代内核也可能用零长度文件 + `trusted.overlay.whiteout` 这个 xattr" }
    - { k: 层 2, v: "原封不动，一个字节没动" }
  next: "再 open 这个路径 :: :: 从上往下问一遍"

- tag: 删之后
  tone: green
  name: 查不到了
  badge: 空间没释放
  fields:
    - { k: 可写层, v: "先命中那个墓碑" }
    - { k: 查到什么, v: "「此处没有」—— 停止，不往下找" }
    - { k: 层 2, v: "文件还在，占着原来的空间" }
  noteTone: bad
  note: 这就是「容器里删了大文件，宿主机磁盘没变」的原因
```

```callout
tone: amber
icon: 🪦
text: |
  **「墓碑」这个比喻在这里是字面意义上的。**

  它是一个**内核层面的特殊文件**，作用是告诉 OverlayFS：
  「这个路径在下层有，但在我这里被删了，查到这里就停下，别再往下看了」。

  它占的空间极小（一个字符设备节点），但==它挡住的可能是下面几个 GB==。

  ++同一个机制还有一个变体叫 **opaque directory**：标记「这个目录整个以我为准，
  别往下合并了」。它也是用 xattr 实现的。++
```

## 07 · 三个容器，一套只读层

可写层是一人一份的，只读层是全镜像共享的。所以在同一台机器上跑三个同一个镜像的容器：

```flow
grid: true
groups:
  - { id: own, label: "可写层：每个容器各一份", tone: green }
nodes:
  - { id: c1, label: 容器 1, sub: "Java 进程", row: 0, tone: green }
  - { id: c2, label: 容器 2, sub: "也是 Java 进程", row: 0, tone: green }
  - { id: c3, label: 容器 3, sub: "同一个镜像起的", row: 0, tone: green }
  - { id: w1, label: "可写层 1", sub: "改过的 os-release", row: 1, tone: green, group: own }
  - { id: w2, label: "可写层 2", sub: "还是空的", row: 1, tone: green, group: own }
  - { id: w3, label: "可写层 3", sub: "只改了一个配置文件", row: 1, tone: green, group: own }
  - { id: img, label: "镜像层 · 层 1 / 层 2 / 层 3", sub: "只读。三份容器共用同一批，磁盘上只有一份", row: 2, tone: violet }
edges:
  - { from: c1, to: w1 }
  - { from: c2, to: w2 }
  - { from: c3, to: w3 }
  - { from: w1, to: img, label: "大家底下都是同一份" }
  - { from: w2, to: img }
  - { from: w3, to: img }
```

==同一台机器上跑 50 个基于同一个镜像的容器，镜像层在磁盘上仍然只有一份。==
多出来的开销只是 50 个可写层里各自改过的那点东西。

这也解释了「容器很轻」这句话的准确含义：轻的是**运行时开销**，
不是镜像本身小 —— 镜像该多大还是多大，只是大家共用一份。

## 08 · rootfs 里没有内核

这一点经常被漏掉：**rootfs 只包含用户空间的文件。**

```compare
first: 东西
head: [在不在容器的 rootfs 里, 说明]
rows:
  - "内核（`/boot/vmlinuz`、内核模块）": [{ text: "不在", tone: red }, "容器**共用**宿主机的内核，不自己带一个"]
  - "`/bin` `/usr` `/lib` 这些命令和库": [{ text: "在", tone: green }, "来自镜像的基础层"]
  - "你的应用和依赖": [{ text: "在", tone: green }, "来自上面几层"]
  - "`/proc` `/sys` `/dev`": [{ text: "在，但是是运行时挂上去的", tone: amber }, "不是镜像层提供的，是内核暴露出来的视图"]
```

所以「容器是一个完整的 Linux 系统」这个说法要打个折：
它是一套完整的**用户空间**，加一个**借来的内核**。

```callout
tone: violet
icon: 📖
text: |
  **顺带一个术语坑：`rootfs` 这个词有两个意思。**

  | 场合 | 指什么 |
  |---|---|
  | 容器语境（这篇） | 容器进程看到的那棵 `/` 目录树 |
  | 内核文档 | 系统启动早期挂的一个 **ramfs/tmpfs 实例**，是给内核用的临时根 |

  内核文档里甚至明确说「所有 Linux 系统里都有一个 rootfs」——
  那个 rootfs 和你容器里的 rootfs 不是一回事。==读到这个词先看上下文。==
```

## 09 · 四个常被说错的点

```checklist
tone: cross
items:
  - 「叠起来就是复制合并成一个新目录」—— 不复制。是挂载时的查找规则，每次 open 时现算
  - 「上层盖住下层」—— 只对文件成立；目录是**合并**
  - 「容器删了文件，磁盘空间就释放了」—— 只是加了个墓碑，下层那份还在
  - 「容器里改文件很方便，反正层是写时复制的」—— 改一个字节要先把整份复制上来，大文件很贵
```

```callout
tone: amber
icon: 📏
text: |
  **一条工程上的现实：层数是有上限的。**

  `overlay2` 驱动最多支持 **128 层** lower。而实际上更早就撞墙 ——
  有人实测 `docker build` 到 **122 层**左右就报 `max depth exceeded`，
  因为挂载参数的长度受**内核页大小**限制。

  这个数字各来源说法不完全一致（122 / 125 / 128），跟环境有关，
  ==但方向是确定的：层越多越容易出问题。==

  所以 Dockerfile 里把 `RUN` 合并成一条，不只是「减少层数好看」——
  它真的在避开一个上限。
```

```quiz
- q: 「镜像层叠起来就是一个 rootfs」里的「叠」，具体是什么动作？
  a: |
    不是复制合并，是一条查找规则：从最上层往下问，谁先有这个路径就算谁的。
    它发生在每次 open 的时候，而不是容器启动的时候。
    磁盘上没有任何一个目录叫「这个容器的 rootfs」—— 它是挂载出来的视图。
- q: 上层和下层都有 /etc，容器里 ls 会看到什么？
  a: |
    看到两边的**并集**。目录是合并的，不是覆盖的。
    「上层赢」只对非目录（文件、符号链接、设备）成立。
    如果按覆盖理解，debian 自带的那些配置文件就全都消失了 —— 但它们在。
- q: 容器里 rm 了一个 2GB 的文件，为什么宿主机磁盘没变？
  a: |
    因为文件在只读的镜像层里，删不掉。rm 只是在可写层放了一个墓碑（whiteout，
    一个 0/0 的字符设备节点），让查找到这个路径时停下、不再往下看。
    镜像层里那份 2GB 还在，而且只要这个镜像还在被使用就不会被回收。
- q: 一句话说清 rootfs 和内核的关系。
  a: |
    rootfs 只包含用户空间的文件（命令、库、应用），不含内核。
    容器共用宿主机的内核，靠 mount namespace 和 pivot_root 拿到自己的 /。
    所以「容器是一个完整的 Linux 系统」应该修正成「一套完整的用户空间 + 一个借来的内核」。
```

## 01 · 什么时候该调度

就绪队列里排着好几个进程，它们都万事俱备，只差一个 CPU。

「下一个让谁上」这件事，由操作系统里的**调度程序**（scheduler）决定。

### 调度发生在这几个当口

进程每换一次状态，都是一次重新决定「谁上」的机会。其中和 CPU 直接相关的是这三条：

```flow
grid: true
groups:
  - { id: sched, label: "每一次状态变化，调度程序都要重新挑一次", tone: violet }
nodes:
  - { id: new,  label: 就绪,  sub: "新进程建好了，插进就绪队列", row: 0, tone: blue, shape: pill, group: sched }
  - { id: run,  label: 运行,  sub: "正在 CPU 上", row: 1, tone: green, shape: pill, group: sched }
  - { id: blk,  label: 阻塞,  sub: "去等 I/O 了，CPU 空出来", row: 2, tone: amber, shape: pill, group: sched }
  - { id: exit, label: 结束,  sub: "跑完了，CPU 得给别人", row: 2, tone: red, shape: pill, group: sched }
edges:
  - { from: new, to: run,  label: "挑一个上" }
  - { from: run, to: blk,  label: "得换人，CPU 不能空着" }
  - { from: run, to: exit, label: "换下一个" }
  - { from: run, to: new,  label: "时间片用完，回到就绪", dashed: true }
```

后两条有个共同点：==CPU 突然空出来了，必须马上补一个上去==，晚一步就白丢一个时间片。
第一条相反，CPU 本来就空着，从容挑一个就行。

```compare
first: 转移
head: [CPU 会空出来吗, 调度程序要做什么]
rows:
  - 就绪 → 运行: [{ text: 不会，本来就空着, tone: green }, "从就绪队列挑一个填进来"]
  - 运行 → 阻塞: [{ text: 会，而且是被迫的, tone: amber }, "马上挑一个接手，晚一步就浪费一个 CPU 时间片"]
  - 运行 → 结束: [{ text: 会, tone: amber }, "同上，从就绪队列里再挑一个"]
```

### 抢占式还是非抢占式

上面三条，都是进程自己先动了（要么刚来，要么走了）。

还有一种情况：进程根本没打算让出 CPU，却被强行叫停。它时间片还没用完，也没有在等任何东西，凭什么把它换下去？

```compare
first: 类型
head: [什么时候换人, 需要什么硬件, 代价]
rows:
  - 非抢占式: ["只在进程自己阻塞或退出时才换", "什么都不用", "一个长作业可以把 CPU 霸占到结束"]
  - { text: 抢占式, tone: blue }: ["时间片一到就换，或来了更高优先级的就换", { text: "时钟中断", tone: amber }, "要频繁保存/恢复现场，切换开销更大"]
```

==抢占式调度的前提是硬件能定时打断 CPU。== 没有时钟中断，操作系统就只能在进程主动让出 CPU 时才有机会插手 —— 那就退化成非抢占式了。

这个「定时打断」是怎么起作用的：

```seq
grid: true
participants:
  - { id: p,  label: 进程 A, sub: 正占着 CPU, tone: green }
  - { id: hw, label: 时钟, sub: 每隔 20ms 响一次, tone: amber }
  - { id: k,  label: 内核, sub: 中断处理 + 调度器, tone: violet }
messages:
  - { from: p,  to: p, label: 一直在跑，没有任何让出的意思, kind: self, note: 1 }
  - { from: hw, to: k, label: 时钟中断, kind: sync, note: 2, gap: 14 }
  - { from: k,  to: k, label: "把 A 的现场保存进 PCB，A 改成就绪", kind: self, note: 3 }
  - { from: k,  to: p, label: 从就绪队列挑下一个上来, kind: reply, note: 4 }
```

==进程自己没动，是硬件替操作系统开了一个口子。== 这个口子每 20ms 出现一次，调度器就在这个口子里做决定。

```callout
tone: violet
icon: ⏱
text: |
  **时间片设多长，是一个两头都不能碰的妥协。**

  | 时间片 | 会发生什么 |
  |---|---|
  | 太短 | 切换次数暴涨。CPU 大量时间花在保存/恢复现场上，不在跑程序 |
  | 太长 | 交互式操作要等很久才轮到一次。极端情况下退化成先来先服务 |

  常见取值在 **20 ms ~ 50 ms** 这个量级。
```

## 02 · 调度原则：五个指标

「调度得好不好」需要能被衡量。衡量它的五个量：

```cards
cols: 2
items:
  - title: CPU 利用率
    desc: CPU 有多少时间真的在干活
    tone: blue
    body: |
      进程去等 I/O 时 CPU 会闲着。这时候赶紧挑一个就绪进程填进来，
      利用率就上去了。

      ==这是调度存在的第一动机。==
  - title: 系统吞吐量
    desc: 单位时间里完成了多少个进程
    tone: violet
    body: |
      一个长作业占着 CPU 不放，完成数就少。

      短作业多跑几个，吞吐量就上去了。这是 SJF 的理论依据。
  - title: 周转时间
    desc: 从进程到达到它结束，一共用了多久
    tone: green
    body: |
      周转时间 = 等待时间 + 运行时间。

      它衡量的是「站在进程视角，我受了多久的罪」。
  - title: 等待时间
    desc: 在就绪队列里干等了多久
    tone: amber
    body: |
      !!等待时间**不包含**阻塞的时间。!!

      进程去等 I/O 是在干活还是干等，不归调度管；
      但「已经就绪了却排不上队」是调度可以直接影响的。
  - title: 响应时间
    desc: 从提交请求到第一次有反应，用了多久
    tone: red
    body: |
      鼠标点了要立刻动，键盘敲了要立刻出字。

      交互式系统里，==响应时间是衡量调度算法好坏的主要标准==。
```

!!!周转时间和响应时间很容易混。!!

- 一个进程总周转 10 秒，但第一秒就拿到了 CPU：周转差、响应好。
- 一个进程总周转 3 秒，但等了 2.9 秒才第一次跑：周转好、响应差。

前者的例子是后台批处理作业，后者的例子是刚启动的终端程序。

### 五个指标会互相打架

```checklist
tone: warn
items:
  - 想让平均周转最低 → 就得让短的先跑，代价是长作业在队尾排队
  - 想让响应最快 → 就得频繁换人，代价是切换开销上去、周转变差
  - 想让谁都不被忘掉 → 就得给等待本身加权（等得越久越优先），代价是每次调度都要多算一遍
  - 想同时做到几样 → 只能分级：给不同作业不同的优先级和时间片，代价是实现和调参都更重
```

==没有哪个算法在所有指标上都赢。== 上面每一条「代价」，落到具体算法上就是它牺牲掉的那部分。

## 03 · 六种算法，同一组作业跑一遍

上面说的都是原则。真正能看出差别的方式，是拿**同一组作业**让六种算法各跑一遍。

```demo
widget: sched-lab
title: 四个作业，六种算法
actions: false
hint: 点算法名切换
config:
  quantum: 2
  mlfq: [1, 2, 4]
  jobs:
    - { id: P1, arrive: 0, burst: 3, priority: 3 }
    - { id: P2, arrive: 2, burst: 6, priority: 1 }
    - { id: P3, arrive: 2, burst: 1, priority: 4 }
    - { id: P4, arrive: 4, burst: 5, priority: 2 }
```

四个作业的情况：

| | P1 | P2 | P3 | P4 |
|---|---|---|---|---|
| 到达时刻 | 0 | 2 | 2 | 4 |
| 需要运行 | 3 | 6 | 1 | 5 |
| 优先级 | 3 | 1（最高） | 4（最低） | 2 |

按一遍下面这几种，看**每个算法的输家和赢家分别是谁**：

```checklist
tone: warn
items:
  - FCFS：P2 排在 P1 后面硬等，最终平均周转 7.25
  - SJF：平均周转压到 5.75，全场最低。但看 P2，它从 2 等到 9
  - HRRN：6.00，界于两者之间。P2 在 P4 之前上了（等得够久，响应比追上来了）
  - RR：周转 8.00，比 FCFS 还差；但平均响应 1.00，所有人很早就摸到过 CPU
  - HPF：10.50，全场最差。P3 明明只要 1 个时间单位，却等到 14 才跑上
  - MLFQ：平均响应 0.25，六个里最好；周转 7.50，排在中间偏后
```

### 逐个算法看

```cards
cols: 1
items:
  - title: 先来先服务（FCFS）
    tag: 非抢占式
    tone: muted
    desc: 谁先进就绪队列谁先跑，跑完或被阻塞才换人
    body: |
      实现最简单，看着也最公平。问题在**长作业挡路**：
      一个需要跑 10 秒的作业排在队首，后面一堆 0.1 秒的作业全都得等它。

      ++适合 CPU 繁忙型作业（每次都要跑很久，排队差别不大）。++
      !!不适合 I/O 繁忙型作业。那些进程频繁进出就绪队列，被长作业堵住的次数最多。!!
  - title: 最短作业优先（SJF）
    tag: 非抢占式
    tone: blue
    desc: 每次挑运行时间最短的那个
    body: |
      理论上能把平均周转时间压到最低：短作业先清掉，等待时间不会累积。

      代价是**长作业可能永远排不上**：只要不断有短作业进来，长作业就一直在队尾。
      这叫饥饿。
  - title: 高响应比优先（HRRN）
    tag: 非抢占式
    tone: amber
    desc: 每次算一遍响应比优先级，挑最高的
    body: |
      ```
      优先权 = (等待时间 + 要求服务时间) / 要求服务时间
             = 等待时间 / 要求服务时间 + 1
      ```

      看这个式子怎么自动平衡：

      - 要求服务时间相同 → **等得越久优先权越高**，长作业不会饿死
      - 等待时间相同 → **要求服务时间越短优先权越高**，短作业被优待

      ==等待本身会拉升优先级，所以长作业等久了总能追上。==
  - title: 时间片轮转（RR）
    tag: 抢占式
    tone: green
    desc: 每人一个固定时间片，跑不完就回队尾
    body: |
      大家一样重要，轮流来。**响应时间通常最好**，谁都不会等太久才第一次被服务。

      但它有两个代价：

      - 切换次数最多，上下文切换的开销明显上去
      - 平均周转时间往往是最差的（每个人都跑了点，但都没跑完）

      ++时间片长度是它唯一的旋钮：太短切换太频繁，太长就退化成 FCFS。++
  - title: 最高优先级优先（HPF）
    tag: 抢占式
    tone: red
    desc: 优先级数字越小越优先，来了更高优先级的立刻换
    body: |
      优先级可以**静态**（建进程时定好，一生不变）或**动态**（运行时间长了降一点，
      等待时间长了升一点）。

      !!最大的问题是低优先级进程可能永远跑不上。!!

      常见的补丁是老化：等得越久，优先级慢慢往上抬。
  - title: 多级反馈队列（MFQ / MLFQ）
    tag: 综合
    tone: violet
    desc: 多条队列，优先级高的时间片短；跑不完就往下降
    body: |
      它是「时间片轮转」和「最高优先级」的组合：

      - 多条队列，优先级从高到低，**优先级越高时间片越短**
      - 新进程进第一级，按先来先服务排队
      - 第一级的时间片里没跑完 → 降级到第二级队尾，以此类推
      - 高优先级队列空了，才轮到低优先级
      - 跑的过程中来了更高优先级的进程 → 立刻让位，自己回原队列队尾

      ++短作业在第一级就做完了，长作业降到后面，等得久但每次能跑更长时间。++
      ==它同时照顾了长短作业，响应时间也不错。代价是实现最复杂。==
```

### 换成银行办业务

把「进程」换成「办业务的客户」，把「CPU」换成「唯一的窗口」，六个算法就变成了银行柜员的一天：

```compare
first: 算法
head: [银行里的做法, 谁最吃亏]
rows:
  - FCFS: ["先来的先办，办完才叫下一个", "前面那位是来办贷款的，一谈几小时"]
  - SJF: ["优先处理几分钟就能搞定的人", "办大业务的客户一直叫不到号"]
  - HRRN: ["等得越久，越优先被叫到", "谁都不会被彻底忘了"]
  - RR: ["每人只办 10 分钟，办不完换下一个", "没人等太久，但大业务被切得七零八落"]
  - HPF: ["普通、VIP、SVIP 分等级，VIP 一来就插队", "普通客户可能一天都排不上"]
  - MLFQ: ["分多个窗口队列，优先级高的队短、时间片也短", "大业务等得久，但轮到自己时能连着办更久"]
```

==多级反馈队列是唯一一个「谁都没被彻底牺牲」的方案。== 这也是它被真实系统普遍采用的原因。

```quiz
- q: 抢占式调度为什么一定要有硬件时钟中断？
  a: |
    因为要「强行」换人。进程自己不想让出 CPU 的时候，操作系统没有别的办法打断它，
    只能靠硬件定时发中断，在中断处理里把当前进程换下来。
    没有时钟中断，调度器只能在进程主动阻塞或退出时才拿到控制权，那就退化成非抢占式了。
- q: 一个进程总周转时间 10 秒，另一个 3 秒。哪个的用户体验更好？
  a: |
    不一定。周转时间说的是「从头到尾用了多久」，响应时间说的是「多久才有第一次反应」。
    10 秒那个如果 0.1 秒就开始出结果了，体验可能比 3 秒那个（干等 2.9 秒才动）好得多。
    交互式系统看响应时间，批处理看周转时间。
- q: SJF 的平均周转时间最低，为什么实际系统不都用它？
  a: |
    因为「这个作业还要跑多久」在真实系统里没法提前知道，只能估。
    而且它会让长作业饥饿：只要一直有短作业进来，长作业永远排在后面。
    另外它优化的是周转，响应时间并不好：一个等了很久的长作业不会因为 SJF 而变快。
```

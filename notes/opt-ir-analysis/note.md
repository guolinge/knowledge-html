第 1 篇留下的问题：每次变换都要先「证明」。那这些证明是从哪来的？

如果一个优化器为每种情况单独判断，规则数量会随程序写法迅速爆炸：`a*2`、`a+a`、`a<<1` 各写一条，`if` 里套 `while` 再套 `if` 又要各写一套。真实的优化器走另一条路：**先搭一层公共设施，把程序变成一种可分析的形状，再让所有优化共用同一批结论。** 这篇讲这层设施的四根柱子。

## 01 · 优化器不是规则大全

先把整体摆出来。编译器中段（middle end）是一条流水线，越往后，拿到的信息越"加工过"：

```lane-stack
- badge: 前端
  title: 源码 → 中间表示
  desc: 词法、语法、语义检查，然后翻译成三地址码
  tone: muted
  nodes:
    - { title: AST, sub: "语法树：结构清楚，但不好直接分析", tag: 树形 }
    - { title: 三地址码, sub: "x = a + b 这种一条一个操作的写法", tag: 线性 }
  next: "一份与源语言无关的表示 :: IR :: 后面所有分析都建立在这上面"

- badge: 中段
  title: 表示层：把代码变成图
  desc: 基本块、CFG、SSA —— 这一层不优化，只改变形状
  tone: blue
  nodes:
    - { title: 基本块 + CFG, sub: "谁能到谁", tag: 控制流 }
    - { title: SSA, sub: "每个变量只有一个定义", tag: 数据流 }
  next: "形状稳定了，才能谈分析 :: :: 同一份 IR，几十个 pass 共享"

- badge: 中段
  title: 分析层：回答特定问题
  desc: 每份分析只回答一个问题，结论被多处复用
  tone: violet
  nodes:
    - { title: 支配树, sub: "谁一定先执行", tag: 结构 }
    - { title: 循环信息, sub: "哪些块构成一个环", tag: 结构 }
    - { title: 活跃变量, sub: "这个值后面还用不用", tag: 数据流 }
    - { title: 别名, sub: "两处访问会不会撞同一块内存", tag: 内存 }
  next: "结论是「可证明的事实」，不是猜测 :: :: 讲清条件才能安全变换"

- badge: 中段
  title: 变换层：改写 IR
  desc: 常量传播、CSE、DCE、LICM、向量化……全部消费上面那批结论
  tone: green
  nodes:
    - { title: 常量传播 / SCCP, sub: "用到支配与可达性", tag: 保守但有依据 }
    - { title: CSE / GVN, sub: "用到 SSA 与值编号", tag: 复用已算过的值 }
    - { title: DCE, sub: "用到活跃变量", tag: 删无用计算 }
    - { title: LICM, sub: "用到循环信息 + 别名", tag: 提到循环外 }
  next: "改写后的 IR 还要再走一轮 :: :: 见第 4 篇的 pass 顺序"

- badge: 后端
  title: 目标代码
  desc: 指令选择、寄存器分配、调度，这一步开始绑定具体机器
  tone: amber
  nodes:
    - { title: 寄存器分配, sub: "用到活跃变量与干涉图", tag: 内存层次 }
```

关键在第三层与第四层的关系：==分析和变换是分开的，一份分析被几十个 pass 消费。== 这就是为什么「优化器很大」不等于「规则很多」：规则多的部分集中在变换层，而变换层的每个 pass 都很薄，因为它们把"证明"这件事外包给了分析层。

## 02 · 先把代码切成基本块，再连成图

分析要能跑，代码得先变成可遍历的形状。第一步是切块：**基本块（basic block）**是一段最长的直线代码，从开头进、从结尾出，中间没有分叉也没有汇合。

切法是找"leader"（块的第一条指令）：

| leader 从哪来 | 为什么 |
|---|---|
| 函数的第一条指令 | 总得有个入口 |
| 任何跳转指令的目标 | 别人会跳到这里，它必须能独立开始 |
| 任何跳转指令的下一条 | 跳走之后，这里是另一条路的起点 |

切完再连边：一个块的结尾能转到另一个块的开头，就有一条边。整张图就是**控制流图（control-flow graph, CFG）**。一个 `while` 循环切出来大概是这样：

```flow
grid: true
nodes:
  - { id: b0, label: B0 · 入口, sub: "i = 0；sum = 0", row: 0, tone: blue, initial: true }
  - { id: b1, label: B1 · 条件, sub: "i < n ?", row: 1, shape: note, tone: violet }
  - { id: b2, label: B2 · 循环体, sub: "sum += a[i]；i++", row: 2, tone: green }
  - { id: b3, label: B3 · 出口, sub: "return sum", row: 2, tone: muted }
edges:
  - { from: b0, to: b1 }
  - { from: b1, to: b2, label: 真, labelDx: -22 }
  - { from: b1, to: b3, label: 假, labelDx: 22 }
  - { from: b2, to: b1, label: 回边, tone: amber, labelDx: -52, labelDy: 22 }
```

这张图上有两样后面反复用到的东西：

- **回边（back edge）**：`B2 → B1`。一条边的头支配它的尾时，这条边就是回边，`B1` 是这个循环的入口（header）。
- **汇合点**：`B3` 有两条入边。凡是"不同的路汇到一起"的地方，都会带来麻烦——第 04 节要在这里放 φ 函数。

CFG 是后面所有结构分析的底座。没有它，"这段代码会不会被执行到""这两条语句哪个先""这个循环的边界在哪"都只能靠读文本猜。

## 03 · 支配关系：谁一定先执行

CFG 上的第一个重要结论是支配（dominance）：

> 如果从入口到节点 n 的**每一条**路径都经过 d，就说 d 支配 n。

这个定义很小，但它把"一定"这个词变成了可计算的。看上面那张图：从 `B0` 到 `B2` 必须经过 `B1`，所以 `B1` 支配 `B2`；`B2` 不支配 `B3`（走假分支可以绕过它）。

支配能推出的东西，几乎每一项都对应一类优化：

```compare
first: 由支配得到的结论
head: [它允许什么, 用在哪]
rows:
  - A 支配 B，A 里算了 `t = x + y`，B 里又要算一次: [可以把 A 的结果直接用到 B，不用重算, 全局公共子表达式消除（CSE/GVN）]
  - 只有当所有路径都经过这里时，某个常量才「一定」是这个值: [可以把这个常量代入后续所有使用点, 稀疏条件常量传播（SCCP）]
  - 循环的 header 支配循环里所有块: [循环里不依赖迭代的值可以提到 header 之前, 循环不变量外提（LICM）]
  - 一个定义支配它所有的使用: [SSA 能成立的前提之一, 构造 SSA]
  - 某条边是回边: [找到了一个自然循环，可以建循环树, 循环优化、展开、向量化]
```

支配关系一般画成**支配树**：每个节点挂在它的直接支配者（immediate dominator, idom）下面。构造算法有接近线性的做法（Lengauer–Tarjan，1979），这也是它能在每个函数上都跑一遍的原因。

!!「支配」说的是控制流上的必然性，不是执行次数。!! 一个块支配另一个块，不代表前者每次都执行，只代表后者执行时，前者一定已经执行过。

## 04 · SSA：给每个定义一个版本

有了支配树，才能做第二步改造：把「变量」拆成「定义」。

普通 IR 里，`x` 在整个函数里是同一个名字，被赋值很多次。想回答「这条指令用的 `x` 是哪个定义写的」，就得做数据流分析。**SSA（static single assignment）** 换了个办法：改名，让每个变量只被赋值一次。

```text
// 原始写法
if (cond) x = 10; else x = 20;
y = x + 1;
```

转换成 SSA 之后，`x` 变成三个名字，汇合处用一个 φ（phi）函数按来路取值：

```flow
grid: true
nodes:
  - { id: entry, label: 入口, sub: "if cond goto B1 else B2", row: 0, tone: blue, initial: true }
  - { id: b1, label: B1, sub: "x1 = 10", row: 1, tone: green }
  - { id: b2, label: B2, sub: "x2 = 20", row: 1, tone: green }
  - { id: b3, label: B3 · 汇合, sub: "x3 = φ(x1, x2)；y1 = x3 + 1", row: 2, tone: violet }
edges:
  - { from: entry, to: b1, label: 真 }
  - { from: entry, to: b2, label: 假 }
  - { from: b1, to: b3 }
  - { from: b2, to: b3 }
```

`φ(x1, x2)` 的意思是：从 B1 过来就取 `x1`，从 B2 过来就取 `x2`。它不执行任何运算，只是一个"在汇合点按前驱选择版本"的记号。

难点不在改名，在于**该在哪些地方放 φ**。放多了是冗余，放少了会算错。Cytron 等人在 1991 年给出的答案很干净：

1. 先算每个节点的**支配边界**（dominance frontier）：那些"被这个节点支配、但它的某个前驱不被支配"的节点集合。
2. 在这个变量所有定义点的支配边界上插入 φ。
3. 迭代到不动点，然后改名：沿着支配树深度优先，遇到 φ 就推入新的版本号。

==SSA 真正省掉的是「反复问」，不是「变量」。== 换成 SSA 之后，「这个值从哪来」是一次查表；常量传播、死代码删除、值编号都变成在图上走一遍的小算法，而不是一遍遍扫全函数。

出 SSA 的时候要还回来：寄存器分配之前，把 φ 拆成边上的拷贝（φ 的两个输入如果落到同一个寄存器，还得处理"丢失的拷贝"问题）。这一步叫 SSA 消除。

## 05 · 别名：两处访问会不会撞同一块内存

控制流解决了"顺序"，剩下的大头是内存。下面四行代码，能不能删掉第一行、能不能把第三行提到循环外，全看一个问题：

```c
*p = 10;
x = *q;       // p 和 q 会不会指向同一处？
*p = 20;
y = *p;       // 这里读到的到底是 10 还是 20？
```

编译器需要的是「被访问的内存集合」，而指针可以让同一块内存在不同时刻有不同的名字。这就是别名分析（alias analysis）要算的东西，它的结论直接决定多少个优化能做：

```compare
first: 分析的精度
head: [它怎么算, 代价与后果]
rows:
  - 完全不分析: [{ text: "任何写入都可能影响任何读取", tone: red }, 几乎不能重排、不能外提]
  - 按类型划分（TBAA，类型别名分析）: [不同类型的指针必不别名, 便宜；但 `int*` 和 `char*` 这类转换会破功]
  - 流不敏感 + 统一（Steensgaard）: [指向关系用并查集合并, 近线性时间；精度低，容易把两个对象合并]
  - 流敏感 + 包含（Andersen 类）: [按程序点精确计算可能指向集合, 立方级复杂度，编译时间换精度]
  - 加上 `restrict` 等人工承诺: [{ text: "由程序员保证一定不别名", tone: green }, 有承诺时最省事，违反承诺就是 UB]
```

这张表说明一个反复出现的模式：**精度和编译时间是一条滑尺，优化器只能选一个位置。** 选得保守，第 1 篇那句「可能别名就当冲突处理」就开始生效，一批优化被挡在门外；选得激进，编译时间和内存都会涨上去，而且一旦分析有 bug 就是错编译。

`restrict`、`__restrict`、`noalias` 这类标注的价值就在这里：它们把「我保证不重叠」这句话写进类型系统，让分析不用猜。

## 06 · 一遍识别，八处复用：循环信息

循环是优化的重点（第 4 篇展开），但识别循环这件事本身只做一次。做完之后，下面这些优化共享同一份结论：

```cards
cols: 2
items:
  - { title: 循环不变量外提（LICM）, desc: "依赖：header 支配全循环 + 体内无人写它的操作数", tag: 消费者 1, tone: green }
  - { title: 归纳变量优化, desc: "依赖：认出 `i` 每次加固定步长，把它的派生量换成加法", tag: 消费者 2, tone: green }
  - { title: 强度削弱, desc: "依赖：循环结构 + 归纳变量，把乘换成累加", tag: 消费者 3, tone: green }
  - { title: 循环展开, desc: "依赖：迭代次数可分析，或者能证明至少执行几次", tag: 消费者 4, tone: blue }
  - { title: 循环交换 / 分块, desc: "依赖：嵌套循环树 + 依赖分析（两次迭代写不写同一块内存）", tag: 消费者 5, tone: blue }
  - { title: 自动向量化, desc: "依赖：迭代间无依赖 + 别名分析证明不重叠", tag: 消费者 6, tone: violet }
  - { title: 循环版本化（versioning）, desc: "依赖：别名不确定时，生成「不重叠快版 / 保守慢版」两个循环", tag: 消费者 7, tone: violet }
  - { title: 软流水 / 调度, desc: "依赖：循环体里各步的依赖距离", tag: 消费者 8, tone: amber }
```

八个消费者，一份循环信息。这就是"统一分析框架"的实际含义：不是少写几行代码，而是**同一批事实被反复使用，不需要每个优化各自重新证明一遍**。

## 07 · 规范化：把一万种写法收成一种

还剩一个规模问题。同一件事，源码里能写出很多种样子：

```c
x = a * 2;
x = a + a;
x = a << 1;
```

如果优化器为每种写法准备一套规则，`a*2 + b*2`、`a+a+b+b`、`(a<<1) + (b<<1)` 又各要一套，规则数量跟着写法组合爆炸。解决办法是**规范化（canonicalization）**：先统一成一种形式，后面的规则只认那一种。

```flow
grid: true
nodes:
  - { id: w1, label: "a * 2", row: 0, tone: muted }
  - { id: w2, label: "a + a", row: 0, tone: muted }
  - { id: w3, label: "a << 1", row: 0, tone: muted }
  - { id: canon, label: 规范形式 · 只留一种, sub: "比如左移 1 位", row: 1, tone: blue, shape: note }
  - { id: rules, label: 后续规则只写一份, sub: "常量折叠、CSE、强度削弱都只匹配这一种", row: 2, tone: green }
edges:
  - { from: w1, to: canon }
  - { from: w2, to: canon }
  - { from: w3, to: canon }
  - { from: canon, to: rules }
```

规范化的对象不只是表达式，还有结构：

| 规范化什么 | 收成什么形状 | 为什么 |
|---|---|---|
| 表达式 | 一种固定的等价写法 | 规则只写一遍；避免 A→B 与 B→A 两条规则互相打架 |
| 控制流 | 每个 `if` 只有一个出口、每个循环有唯一 header | 分析算法不用处理几十种控制流变体 |
| 循环 | 加前导块（preheader），把循环条件挪到 latch | LICM 有地方放代码，展开与向量化只面对一种循环形状 |
| 临界边 | 拆成两条边加一个空块 | φ 的插入点不会落在"一条边同时是两条边"的位置 |
| 数据结构 | 统一成 SSA 形式 | 所有数据流分析共用一套接口 |

!!规范化必须只朝一个方向走。!! 如果同时存在 `a*2 → a<<1` 和 `a<<1 → a*2` 两条规则，pass 会在两者之间来回切换，永远到不了不动点，编译时间就爆了。这也是为什么很多规范化的方向看起来"反直觉"——它选的不是最快的写法，而是**唯一的写法**；到底哪个更快，留给后面的成本模型决定。

## 08 · 速查

```checklist
items:
  - 优化器不是规则大全：规则多的部分在变换层，证明的部分在分析层，两层分开
  - 基本块是最长直线段；CFG 的节点是块、边是可能的转移；回边的头就是循环 header
  - 支配 = 每条路径都经过；支配树让「一定」变成可查的表；Lengauer–Tarjan 接近线性
  - SSA 用改名消灭「当前是哪个 x」；φ 放在支配边界上，出 SSA 时拆成边上的拷贝
  - 别名分析是精度与编译时间的滑尺；`restrict` / 类型信息 / 属性都是给分析送前提
  - 循环识别只做一次，LICM、归纳变量、削弱、展开、交换、向量化共享它
  - 规范化只朝一个方向走，否则来回转换到不了不动点；规范形式不等于最快形式
```

## 09 · 自测

```quiz
- q: 为什么说优化器「不是把所有情况枚举出来」？
  a: |
    因为它把「证明」这一步抽出去做成了公共分析：支配树、SSA、别名、活跃变量、循环信息。
    每个优化都只是「读的分析结论 + 一小段改写逻辑」，所以 pass 本身很薄。

    真正多的是变换的种类，而不是每个变换都要自带一套推理。
- q: 支配关系能用来做什么？举两个具体例子。
  a: |
    支配 = 从入口到该节点的每条路径都经过它。它可以支持：
    ① CSE：A 支配 B，A 里算过的表达式在 B 里可以复用；
    ② SCCP：只有所有路径都经过的地方，某个常量才「一定」成立；
    ③ LICM：循环 header 支配全循环，所以提到 header 之前的计算一定先于使用；
    ④ 构造 SSA 与识别自然循环的前提。
- q: SSA 里的 φ 函数到底在做什么？为什么不能随便放？
  a: |
    φ 在汇合点按「从哪个前驱跳来」选择变量的版本，本身不做运算。
    放少了，汇合点后面的值来源就不唯一；放多了会引入冗余定义，还让后面的分析变慢。

    Cytron 等人的做法是精确地放在「定义的支配边界」上，再迭代到不动点。
- q: 为什么别名分析选「流敏感 + 包含」会让编译变慢？
  a: |
    精度和编译时间是滑尺。流敏感要按程序点分别计算可能指向集合，包含式要解集合约束，
    复杂度可以到立方级。换来的是更少被「可能别名」挡住的重排、外提和向量化。

    所以常见做法是分层：默认用便宜的（类型、流不敏感），只在关键处用贵的，
    或者让程序员用 `restrict` 直接把前提写出来。
- q: 规范化为什么不能两个方向都做？
  a: |
    两条相反的规则会让 pass 在两种写法之间来回切换，永远到不了不动点，编译时间失控。
    规范化选的是「唯一的写法」，不是「最快的写法」；快不快由后面的成本模型判断。
```

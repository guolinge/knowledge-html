你写了两行差不多的代码，编译器删掉了第一行，却不敢动第二行：

```c
x = a + 0;      // 被改成 x = a
x = f() * 0;    // 依然是一次函数调用
```

从算术看，两个式子都在说「值等于零」。差别不在数学，在**删掉之后程序还看不看得出来**：`f()` 可能打印一行字、可能改全局变量、可能根本不返回。这篇讲的就是编译器在这一步上到底在算什么，以及它为什么经常选择「什么也不做」。

## 01 · 两行代码，一个能删一个不能

先把两个例子的结局摆在一起。`+ 0` 是恒等式，`f()` 是不是恒等，取决于 `f` 做了什么：

```c
int f() {
    printf("hello\n");
    return 10;
}

int a = 3;
x = a + 0;    // → x = 3，删掉加法
y = f() * 0;  // → 不能直接写 y = 0，那会少打印一行
```

!!「值等于零」和「行为等于原来」不是一回事。!! 优化改动的是指令，而程序要对得上的东西是**外部能观测到的结果**：打印了什么、写了哪些文件、最终返回什么。前者是算术，后者是契约。

这一节先把契约写清楚，后面所有优化都在这份契约里面活动。

## 02 · 一次优化要过两道闸

编译器内部把这件事拆成两个独立的问题，各有各的名字：

- **合法性（Legality）**：变换之后，程序的可观察行为是否和原来一致？这是个**证明题**，只有「证得出来」和「证不出来」。
- **收益性（Profitability）**：在目标机器上，变换后是不是真的更快/更小？这是个**估算题**，靠成本模型。

两道闸串起来，才是「应用一条优化」：

```flow
grid: true
nodes:
  - { id: cand, label: 候选变换, sub: "模式匹配命中：a + 0、f() * 0", row: 0, tone: blue }
  - { id: legal, label: 合法性, sub: "能不能证明语义不变", row: 1, shape: note, tone: violet }
  - { id: drop1, label: 放弃这次变换, sub: "记一笔 missed optimization", row: 1, tone: muted }
  - { id: profit, label: 收益判断, sub: "按目标机成本模型估算", row: 2, shape: note, tone: amber }
  - { id: drop2, label: 放弃这次变换, sub: "合法但不划算", row: 2, tone: muted }
  - { id: apply, label: 新 IR，交给下一轮, sub: "后面还会被别的 pass 看到", row: 3, tone: green }
edges:
  - { from: cand, to: legal }
  - { from: legal, to: drop1, label: 否 }
  - { from: legal, to: profit, label: 是 }
  - { from: profit, to: drop2, label: 否 }
  - { from: profit, to: apply, label: 是, anim: true }
```

两道闸的顺序不是随便排的。==合法性永远先问，而且它的答案不是「大概没问题」，是「有证明」。== 证不出来就走左边的出口，这一次优化就没了，程序照旧能跑。

这也解释了为什么优化器经常显得笨：它手里没有「我觉得这里应该没事」这个选项。收益算错只是白忙一场，合法性判错就是**编错程序**，而错编译的 bug 极难定位：用户看到的是一段自己没写过的代码在出错。

## 03 · as-if：可观察行为是一张清单

「语义不变」听着抽象，标准给了它一个可操作的边界，也就是常说的 **as-if 规则**。C11 的原话是这样（§5.1.2.3）：

> 实际实现不必求值一个子表达式，只要它能推算出：这个值没有被使用，而且没有产生需要的副作用——包括调用函数、访问 volatile 对象所引起的副作用。

C++ 的说法更直白：**对于相同的输入，程序的可观察行为必须是该输入下可能出现的可观察行为之一。**（[intro.abstract]）

注意这句话里没有「代码形状」「指令条数」「变量还在不在」。这些都不受保护。受保护的是下面这一列：

```compare
first: 程序里的东西
head: [算不算「可观察」, 编译器能不能动]
rows:
  - 中间变量、临时值、寄存器分配: [{ text: 不算, tone: muted }, 随便改，只要用它的地方还算得对]
  - 没有依赖关系的两条语句的先后: [{ text: 不算, tone: muted }, 可以换序，结果一致就行]
  - "`printf` 的次数和顺序": [{ text: 算, tone: green }, 不能少、不能改序]
  - "对 `volatile` 对象的读写": [{ text: 算, tone: green }, 一次都不能多、不能少]
  - 原子操作与同步: [{ text: 算, tone: green }, 改了就是改了内存模型]
  - 程序是否终止、返回什么: [{ text: 部分算, tone: amber }, 见下面这一条]
```

最后一行是个反直觉的地方。C11 §6.8.5 补了一条：如果一个循环的控制表达式不是常量、循环体里不做 I/O、不访问 volatile、不做同步或原子操作，那么**实现可以假设它一定会终止**。换句话说，`while (1) { i++; }` 这种「什么也不干的死循环」不保证被保留下来，编译器有权把它整个删掉。

这条规则对得上现实：GCC 在 `-O2` 就打开了 `-ffinite-loops`，正是这个假设的实现。

!!把「可观察行为」理解成「我看到的东西」会出错。!! 它指的是标准列出的那些东西：I/O、volatile 访问、原子操作、程序终止状态。你调试时看到变量被优化没了、断点跳来跳去，那些都不在清单上。

## 04 · 同一个式子，三种命运

回到 `f() * 0`。它最后会变成什么，取决于编译器手里有多少信息。点下面几个按钮看它一步步走：

```demo
widget: stepper
title: x = f() * 0 走到哪一步就停下了
actions: false
config:
  steps:
    - { label: 看到模式, code: "x = f() * 0;", note: "乘零：值一定是 0。真正的问题变成——f() 这次调用能不能一起删掉。" }
    - { label: 只有声明, code: "int f(void);   // 定义在另一个编译单元\ny = f() * 0;", note: "看不到函数体。它可能写全局变量、可能打印、可能死循环。合法性这一步直接卡住。" }
    - { label: 看到定义, code: "static int f(void) { return 10; }\ny = f() * 0;", note: "体内只读局部量、必然返回。现在可以证明：无副作用、不会有意外分支。" }
    - { label: 加上属性, code: "int f(void) __attribute__((pure));\ny = f() * 0;", note: "跨编译单元时，用属性的方式把「只读、无副作用」这条承诺交给编译器。" }
    - { label: 过收益关, code: "// 少一次 call、少一次乘\ny = 0;", note: "调用与乘法的开销是明确的，成本模型判定划算，才真正落地。" }
    - { label: 证不出来时, code: "y = f() * 0;   // 原样保留", note: "这不是编译器偷懒，是它在没有证明的情况下拒绝下注。" }
```

三行代码，三种命运，可以并排看：

```compare
first: 写法
head: [结果, 为什么]
rows:
  - "`x = a + 0`": [{ text: 改成 `x = a`, tone: green }, 整数加零没有副作用，也不改变后续任何可观察行为]
  - "`x = 42 * 0`": [{ text: 直接折成 `x = 0`, tone: green }, 两边都是编译期常量，折叠连一次运行都不花]
  - "`x = f() * 0`": [{ text: 只有在证明 `f` 无副作用且必返回时才删, tone: amber }, 删掉调用等于删掉它的副作用，这必须证明，不能假设]
  - "`x = *p * 0`（`p` 可能为空）": [{ text: 通常不删, tone: red }, 空指针解引用在 C 里是 UB，但删掉这次读会改变出错时的表现，多数编译器在这里选择保守]
```

最后一行值得单独说：**「删掉一次调用」要同时证明三件事**——它没有副作用、它一定会被执行到（不是死代码）、它一定会返回（不陷入死循环、不触发陷阱）。三件里缺一件，合法的变换就变成错的。

## 05 · 合法性从哪来：每种变换都要一份证据

合法性不是靠直觉，是靠**分析**（analysis）给出的结论。不同的变换要的证据不一样，所以要的分析也不一样：

```compare
first: 想做的变换
head: [必须先证明什么, 靠哪份分析]
rows:
  - 删掉一条赋值: [这个值后面没人用, 活跃变量分析]
  - "把 `a * b` 提到循环外": [每轮算出来都一样，循环里没人改 `a`、`b`, 循环识别 + 别名分析 + 副作用分析]
  - "交换 `*p = 10` 和 `x = *q` 的顺序": ["`p` 和 `q` 不指向同一处", 别名分析]
  - "把 `x + 0` 折成 `x`": [没有隐式转换或异常语义被改变, 类型信息 + 常量传播]
  - 把两次相同表达式合成一次: [两次之间没有东西改过它的操作数, 公共子表达式分析（可用表达式）]
  - 把 `if` 的一个分支删掉: [条件恒真，或那个分支不可达, 常量传播 + 可达性]
```

第三条是这篇里最值得记住的一条：**两行内存访问能不能换顺序，编译器自己看不出来，得先证明两块内存不重叠。** 这就是别名分析（alias analysis）要回答的问题，下一节展开。第 3 篇会把这张表里的分析一个个拆开。

```callout
tone: violet
icon: 🧾
text: |
  **「证不出来」不是失败，是正常输出。**

  优化器的每次判断都会落到三个结果之一：证得出（做）、证得出但不划算（不做）、证不出（不做）。
  第三种情况在编译器内部叫 **missed optimization**，它会被记录、被测试用例覆盖，
  但不会被当成 bug，因为它换来的是「不会编错」。
```

## 06 · 保守近似：三个值，而不是一个猜测

别名分析是最能说明「保守」长什么样的例子。面对

```c
*p = 10;
x = *q;
```

编译器真正需要回答的是：`p` 和 `q` 会不会指向同一块内存。这个问题的答案只有三种：

```compare
first: 分析结论
head: [对这两行的处理, 代价]
rows:
  - 一定别名（must-alias）: [{ text: "必须保持顺序，甚至可以认为 `*q` 就是 10", tone: blue }, 没有代价，只是很少能判出来]
  - 一定不别名（no-alias）: [{ text: "可以换序、可以缓存 `*q` 的值", tone: green }, 这是优化最想要的结果]
  - 可能别名（may-alias）: [{ text: "按「会冲突」处理：不换序、不合并", tone: amber }, 少一次优化，但不会错]
  - 完全无法判定: [{ text: "同「可能别名」", tone: amber }, 同上]
```

关键在于：==「可能别名」这个答案是**故意不精确**的，它把「也许」当成「是」来处理。== 这样做的后果只是少做一次优化；反过来的处理方式——把「也许」当成「不是」——会让编译器在一半的情况下改坏别人的数据。

这也解释了为什么 C 的指针别名问题这么难缠：一次 `char *` 类型的写入、一次函数调用、一个取地址操作，都可能让大片结论退化成「可能别名」。**你写代码时用的类型越模糊，编译器能证明的东西越少。**

## 07 · 两种错误的代价不对称

把两类错误放在一起看，就能理解优化器为什么偏保守：

```compare
first: 犯的错
head: [后果, 谁来发现, 修起来多难]
rows:
  - 该优化没优化（漏）: [{ text: "慢一点", tone: amber }, 性能测试可能发现，也可能永远没人注意, 改一行成本模型或代码写法]
  - 不该优化却优化了（错编译）: [{ text: "程序算错", tone: red }, 通常只有特定输入才触发, 从一条错误的结果反推一条 pass，可能要几天]
```

两类错误的**收益**也不对称：一次漏优化只损失一点点性能，一次错编译可能让整个团队几天找不到原因。所以工程上的选择很清楚：宁可漏，不可错。

!!「我的代码这么写明明是对的，编译器凭什么删」——这句话在讨论的是源码意图，不是标准定义的行为。!! 一旦一段代码落进未定义行为，编译器就有权假设它不会发生，接下来的推导全部建立在那个假设上。

## 08 · 契约的另一面：UB 让编译器变胆大

as-if 保护的是**有定义的行为**。反过来，标准里那些**未定义行为（undefined behavior, UB）** 等于给编译器发了一张通行证：既然你说这种情况不会发生，我就按它不发生来推。

最出名的一次是空指针检查。内核里长期有这种写法：

```c
if (!p) return -EINVAL;
int v = p->field;      // 如果 p 是 NULL，这一行已经是 UB
```

在 `-O2` 下，`-fdelete-null-pointer-checks` 会认为「既然这里解引用了 `p`，那 `p` 一定非空」，于是前面那个 `if` 恒假、整段删掉。2009 年这次发现直接促成了内核在构建时关掉这个优化。

同样的机制还在几个地方：有符号整数溢出是 UB（所以 `x + 1 > x` 不保证为真）、违反严格别名规则是 UB（所以 `int*` 和 `float*` 指向同一块内存的写法会被重排）、把可能为空的指针当有效指针用是 UB。三个开关能把其中一部分还回来：

```compare
first: 开关
head: [换回什么, 代价]
rows:
  - "`-fno-strict-aliasing`": [跨类型的指针别名按「可能别名」处理, 少一批优化]
  - "`-fwrapv`": [有符号溢出按二进制补码回绕, "`x + 1 > x` 重获保证"]
  - "`-fno-delete-null-pointer-checks`": [判空检查按普通代码保留, 一处安全检查不再被删]
  - "`-O0`": [{ text: "上述问题基本消失", tone: red }, 顺带把所有优化一起关掉]
```

++更划算的做法通常是**把契约写清楚**，而不是关开关。++ 该用 `unsigned` 的地方别用 `signed`、该用 `memcpy` 的地方别用指针强转、能用 `__attribute__((pure))` 或 `restrict` 表达的性质就标出来——这些都是把「我知道的事实」交给编译器，让它有东西可以证明。

```callout
tone: amber
icon: ⚠
text: |
  ==优化器不是不信任你，它只是不接受没有依据的信任。==

  你写 `f() * 0` 时心里知道 `f` 无害，但代码里没有一处写着这句话。
  想让它变成 `0`，就要么把定义给它看，要么用属性把承诺写下来。
```

## 09 · 速查

```checklist
items:
  - 先问法律问题，再问收益问题：两次判断分开做，结论才稳定
  - 「语义不变」的口径是可观察行为（I/O、volatile、原子、终止状态），不是代码形状
  - 删一次调用要同时证明：没副作用、会执行到、一定会返回
  - 分析给的是三态结论；「可能别名」按冲突处理，这是设计而不是缺陷
  - 漏优化的代价是速度，错编译的代价是正确性，两者不能放在同一杆秤上
  - 想关掉某个优化之前，先看能不能把契约写清楚（类型、属性、`restrict`）
```

## 10 · 自测

```quiz
- q: 为什么 `x = f() * 0` 不总能改成 `x = 0`？
  a: |
    因为乘零只保证值相等，不保证行为相等。`f()` 可能有副作用（打印、写全局变量），
    也可能不返回。删掉这次调用，程序的可观察行为就变了。

    只有能证明 `f` 无副作用、一定会被执行到、一定会返回时，这次变换才合法。
    证明的来源可以是函数定义、也可以是 `pure` / `const` 这类属性承诺。
- q: as-if 规则保护的「可观察行为」具体指什么？
  a: |
    C11 §5.1.2.3 的口径：I/O、对 volatile 对象的访问、原子与同步操作、
    程序终止状态等。中间变量、寄存器分配、没有依赖的语句顺序都不在里面。

    所以「我调试时变量不见了」不是违规；「printf 少了一次」才是。
- q: 别名分析回答「可能别名」时，编译器为什么按冲突处理？
  a: |
    因为它没有证明「一定不别名」。按冲突处理最多丢一次优化；
    按不冲突处理，一旦真的重叠就是错编译。两类代价不对称，所以选保守的那一边。
- q: 为什么 `-O2` 下有的死循环会消失？
  a: |
    C11 §6.8.5 允许实现假设：控制表达式不是常量、体内不做 I/O、不访问 volatile、
    不做同步或原子操作的循环一定会终止。GCC 的 `-ffinite-loops`（`-O2` 打开）
    就是这条假设的实现，循环如果最终没有可观察结果，就会被删掉。
- q: 有符号溢出为什么会拖累像 `x + 1 > x` 这种判断？
  a: |
    因为有符号溢出在 C 里是 UB，编译器有权假设它不发生，于是 `x + 1` 一定大于 `x`，
    这个比较恒真。要保留回绕语义，用 `-fwrapv`，或者改用无符号类型。
```

一次优化要过两道闸：as-if、合法性，和「证明不了就不做」

x = a + 0 能删，x = f() * 0 未必能删 —— 差别不在算术，在「删掉之后程序还看不看得出来」。这篇把优化拆成两个必须分开问的问题：这次变换是否合法（Legality），以及它是否值得（Profitability）。附 C11 的 as-if 原文与「循环可被假设终止」这一条、别名的三个值、两类错误为什么代价不对称，以及 UB 把证明责任推回给程序员之后，编译器为什么会突然变胆大。

你写了两行差不多的代码，编译器删掉了第一行，却不敢动第二行：

x = a + 0;      // 被改成 x = a
x = f() * 0;    // 依然是一次函数调用

从算术看，两个式子都在说「值等于零」。差别不在数学，在删掉之后程序还看不看得出来：f() 可能打印一行字、可能改全局变量、可能根本不返回。这篇讲的就是编译器在这一步上到底在算什么，以及它为什么经常选择「什么也不做」。

01两行代码，一个能删一个不能

先把两个例子的结局摆在一起。+ 0 是恒等式，f() 是不是恒等，取决于 f 做了什么：

int f() {
    printf("hello\n");
    return 10;
}

int a = 3;
x = a + 0;    // → x = 3，删掉加法
y = f() * 0;  // → 不能直接写 y = 0，那会少打印一行

「值等于零」和「行为等于原来」不是一回事。 优化改动的是指令，而程序要对得上的东西是外部能观测到的结果：打印了什么、写了哪些文件、最终返回什么。前者是算术，后者是契约。

这一节先把契约写清楚，后面所有优化都在这份契约里面活动。

02一次优化要过两道闸

编译器内部把这件事拆成两个独立的问题，各有各的名字：

  • 合法性（Legality）：变换之后，程序的可观察行为是否和原来一致？这是个证明题，只有「证得出来」和「证不出来」。
  • 收益性（Profitability）：在目标机器上，变换后是不是真的更快/更小？这是个估算题，靠成本模型。

两道闸串起来，才是「应用一条优化」：

候选变换 模式匹配命中：a + 0、f() * 0
合法性 能不能证明语义不变
放弃这次变换 记一笔 missed optimization
收益判断 按目标机成本模型估算
放弃这次变换 合法但不划算
新 IR，交给下一轮 后面还会被别的 pass 看到

两道闸的顺序不是随便排的。合法性永远先问，而且它的答案不是「大概没问题」，是「有证明」。 证不出来就走左边的出口，这一次优化就没了，程序照旧能跑。

这也解释了为什么优化器经常显得笨：它手里没有「我觉得这里应该没事」这个选项。收益算错只是白忙一场，合法性判错就是编错程序，而错编译的 bug 极难定位：用户看到的是一段自己没写过的代码在出错。

03as-if：可观察行为是一张清单

「语义不变」听着抽象，标准给了它一个可操作的边界，也就是常说的 as-if 规则。C11 的原话是这样（§5.1.2.3）：

实际实现不必求值一个子表达式，只要它能推算出：这个值没有被使用，而且没有产生需要的副作用——包括调用函数、访问 volatile 对象所引起的副作用。

C++ 的说法更直白：对于相同的输入，程序的可观察行为必须是该输入下可能出现的可观察行为之一。（[intro.abstract]）

注意这句话里没有「代码形状」「指令条数」「变量还在不在」。这些都不受保护。受保护的是下面这一列：

程序里的东西算不算「可观察」编译器能不能动
中间变量、临时值、寄存器分配不算随便改，只要用它的地方还算得对
没有依赖关系的两条语句的先后不算可以换序，结果一致就行
printf 的次数和顺序算不能少、不能改序
对 volatile 对象的读写算一次都不能多、不能少
原子操作与同步算改了就是改了内存模型
程序是否终止、返回什么部分算见下面这一条

最后一行是个反直觉的地方。C11 §6.8.5 补了一条：如果一个循环的控制表达式不是常量、循环体里不做 I/O、不访问 volatile、不做同步或原子操作，那么实现可以假设它一定会终止。换句话说，while (1) { i++; } 这种「什么也不干的死循环」不保证被保留下来，编译器有权把它整个删掉。

这条规则对得上现实：GCC 在 -O2 就打开了 -ffinite-loops，正是这个假设的实现。

把「可观察行为」理解成「我看到的东西」会出错。 它指的是标准列出的那些东西：I/O、volatile 访问、原子操作、程序终止状态。你调试时看到变量被优化没了、断点跳来跳去，那些都不在清单上。

04同一个式子，三种命运

回到 f() * 0。它最后会变成什么，取决于编译器手里有多少信息。点下面几个按钮看它一步步走：

x = f() * 0 走到哪一步就停下了

三行代码，三种命运，可以并排看：

写法结果为什么
x = a + 0改成 x = a整数加零没有副作用，也不改变后续任何可观察行为
x = 42 * 0直接折成 x = 0两边都是编译期常量，折叠连一次运行都不花
x = f() * 0只有在证明 f 无副作用且必返回时才删删掉调用等于删掉它的副作用，这必须证明，不能假设
x = *p * 0（p 可能为空）通常不删空指针解引用在 C 里是 UB，但删掉这次读会改变出错时的表现，多数编译器在这里选择保守

最后一行值得单独说：「删掉一次调用」要同时证明三件事——它没有副作用、它一定会被执行到（不是死代码）、它一定会返回（不陷入死循环、不触发陷阱）。三件里缺一件，合法的变换就变成错的。

05合法性从哪来：每种变换都要一份证据

合法性不是靠直觉，是靠分析（analysis）给出的结论。不同的变换要的证据不一样，所以要的分析也不一样：

想做的变换必须先证明什么靠哪份分析
删掉一条赋值这个值后面没人用活跃变量分析
把 a * b 提到循环外每轮算出来都一样，循环里没人改 a、b循环识别 + 别名分析 + 副作用分析
交换 *p = 10 和 x = *q 的顺序p 和 q 不指向同一处别名分析
把 x + 0 折成 x没有隐式转换或异常语义被改变类型信息 + 常量传播
把两次相同表达式合成一次两次之间没有东西改过它的操作数公共子表达式分析（可用表达式）
把 if 的一个分支删掉条件恒真，或那个分支不可达常量传播 + 可达性

第三条是这篇里最值得记住的一条：两行内存访问能不能换顺序，编译器自己看不出来，得先证明两块内存不重叠。 这就是别名分析（alias analysis）要回答的问题，下一节展开。第 3 篇会把这张表里的分析一个个拆开。

🧾

「证不出来」不是失败，是正常输出。

优化器的每次判断都会落到三个结果之一：证得出（做）、证得出但不划算（不做）、证不出（不做）。 第三种情况在编译器内部叫 missed optimization，它会被记录、被测试用例覆盖， 但不会被当成 bug，因为它换来的是「不会编错」。

06保守近似：三个值，而不是一个猜测

别名分析是最能说明「保守」长什么样的例子。面对

*p = 10;
x = *q;

编译器真正需要回答的是：p 和 q 会不会指向同一块内存。这个问题的答案只有三种：

分析结论对这两行的处理代价
一定别名（must-alias）必须保持顺序，甚至可以认为 *q 就是 10没有代价，只是很少能判出来
一定不别名（no-alias）可以换序、可以缓存 *q 的值这是优化最想要的结果
可能别名（may-alias）按「会冲突」处理：不换序、不合并少一次优化，但不会错
完全无法判定同「可能别名」同上

关键在于：「可能别名」这个答案是故意不精确的，它把「也许」当成「是」来处理。 这样做的后果只是少做一次优化；反过来的处理方式——把「也许」当成「不是」——会让编译器在一半的情况下改坏别人的数据。

这也解释了为什么 C 的指针别名问题这么难缠：一次 char * 类型的写入、一次函数调用、一个取地址操作，都可能让大片结论退化成「可能别名」。你写代码时用的类型越模糊，编译器能证明的东西越少。

07两种错误的代价不对称

把两类错误放在一起看，就能理解优化器为什么偏保守：

犯的错后果谁来发现修起来多难
该优化没优化（漏）慢一点性能测试可能发现，也可能永远没人注意改一行成本模型或代码写法
不该优化却优化了（错编译）程序算错通常只有特定输入才触发从一条错误的结果反推一条 pass，可能要几天

两类错误的收益也不对称：一次漏优化只损失一点点性能，一次错编译可能让整个团队几天找不到原因。所以工程上的选择很清楚：宁可漏，不可错。

「我的代码这么写明明是对的，编译器凭什么删」——这句话在讨论的是源码意图，不是标准定义的行为。 一旦一段代码落进未定义行为，编译器就有权假设它不会发生，接下来的推导全部建立在那个假设上。

08契约的另一面：UB 让编译器变胆大

as-if 保护的是有定义的行为。反过来，标准里那些未定义行为（undefined behavior, UB） 等于给编译器发了一张通行证：既然你说这种情况不会发生，我就按它不发生来推。

最出名的一次是空指针检查。内核里长期有这种写法：

if (!p) return -EINVAL;
int v = p->field;      // 如果 p 是 NULL，这一行已经是 UB

在 -O2 下，-fdelete-null-pointer-checks 会认为「既然这里解引用了 p，那 p 一定非空」，于是前面那个 if 恒假、整段删掉。2009 年这次发现直接促成了内核在构建时关掉这个优化。

同样的机制还在几个地方：有符号整数溢出是 UB（所以 x + 1 > x 不保证为真）、违反严格别名规则是 UB（所以 int* 和 float* 指向同一块内存的写法会被重排）、把可能为空的指针当有效指针用是 UB。三个开关能把其中一部分还回来：

开关换回什么代价
-fno-strict-aliasing跨类型的指针别名按「可能别名」处理少一批优化
-fwrapv有符号溢出按二进制补码回绕x + 1 > x 重获保证
-fno-delete-null-pointer-checks判空检查按普通代码保留一处安全检查不再被删
-O0上述问题基本消失顺带把所有优化一起关掉

更划算的做法通常是把契约写清楚，而不是关开关。 该用 unsigned 的地方别用 signed、该用 memcpy 的地方别用指针强转、能用 __attribute__((pure)) 或 restrict 表达的性质就标出来——这些都是把「我知道的事实」交给编译器，让它有东西可以证明。

⚠

优化器不是不信任你，它只是不接受没有依据的信任。

你写 f() * 0 时心里知道 f 无害，但代码里没有一处写着这句话。 想让它变成 0，就要么把定义给它看，要么用属性把承诺写下来。

09速查

  • 先问法律问题，再问收益问题：两次判断分开做，结论才稳定
  • 「语义不变」的口径是可观察行为（I/O、volatile、原子、终止状态），不是代码形状
  • 删一次调用要同时证明：没副作用、会执行到、一定会返回
  • 分析给的是三态结论；「可能别名」按冲突处理，这是设计而不是缺陷
  • 漏优化的代价是速度，错编译的代价是正确性，两者不能放在同一杆秤上
  • 想关掉某个优化之前，先看能不能把契约写清楚（类型、属性、restrict）

10自测

为什么 x = f() * 0 不总能改成 x = 0？

因为乘零只保证值相等，不保证行为相等。f() 可能有副作用（打印、写全局变量）， 也可能不返回。删掉这次调用，程序的可观察行为就变了。

只有能证明 f 无副作用、一定会被执行到、一定会返回时，这次变换才合法。 证明的来源可以是函数定义、也可以是 pure / const 这类属性承诺。

as-if 规则保护的「可观察行为」具体指什么？

C11 §5.1.2.3 的口径：I/O、对 volatile 对象的访问、原子与同步操作、 程序终止状态等。中间变量、寄存器分配、没有依赖的语句顺序都不在里面。

所以「我调试时变量不见了」不是违规；「printf 少了一次」才是。

别名分析回答「可能别名」时，编译器为什么按冲突处理？

因为它没有证明「一定不别名」。按冲突处理最多丢一次优化； 按不冲突处理，一旦真的重叠就是错编译。两类代价不对称，所以选保守的那一边。

为什么 -O2 下有的死循环会消失？

C11 §6.8.5 允许实现假设：控制表达式不是常量、体内不做 I/O、不访问 volatile、 不做同步或原子操作的循环一定会终止。GCC 的 -ffinite-loops（-O2 打开） 就是这条假设的实现，循环如果最终没有可观察结果，就会被删掉。

有符号溢出为什么会拖累像 x + 1 > x 这种判断？

因为有符号溢出在 C 里是 UB，编译器有权假设它不发生，于是 x + 1 一定大于 x， 这个比较恒真。要保留回绕语义，用 -fwrapv，或者改用无符号类型。

01为什么要多一层

文件系统的种类太多了。磁盘上有 Ext2/3/4、XFS、Btrfs，内存里有 /proc、/sys，网络上有 NFS、SMB。

如果每个程序都要认识这些格式，写一个读文件的代码就得写十份。所以操作系统在中间塞了一层：

应用程序
   ↓  只认这一套接口
虚拟文件系统（VFS）
   ↓  向下适配
Ext4    XFS    NFS    /proc    ...

VFS 定义了一组所有文件系统都要支持的数据结构和标准接口。 程序员只要学会这一套，底下换成什么文件系统都不用改代码。

这一层带来的好处是直接的：open("/mnt/nfs/data.csv") 和 open("/tmp/data.csv") 在写代码的人看来没有任何区别，虽然前者的数据要从网络另一头拿。差异被 VFS 吃掉了。

02一次 write 要穿过几层

从你的代码到磁盘，中间隔着这么几层：

用户空间
用户空间 你的程序 调的是库函数
应用程序 write(fd, buf, n)
库函数 标准库可能先攒一攒 缓冲
陷入内核 syscall从这里开始，CPU 切到内核态
内核
内核空间 系统调用 统一入口
sys_write 检查参数、找到 fd 对应的文件
往下交给 VFS它负责屏蔽差异
内核空间 VFS 这一层是抽象的，不干实事
统一的文件模型 inode / dentry / file 三个结构
挑一个具体文件系统 这个挂载点下面是谁
往下找具体实现规律被抹平了
内核空间 三层缓存 能不能不碰磁盘，全看它们
页缓存 文件内容的副本
dentry 缓存 路径解析的结果
inode 缓存 用过没释放的 inode
缓存里没有这才需要真去读磁盘
内核空间 具体文件系统 到这里才有真正的算法
Ext4 / XFS / Btrfs 本地磁盘
NFS / SMB 网络文件系统
/proc /sys 是内核数据的窗口
要读写块了再往下就是设备了
内核空间 块层与驱动 把文件操作翻译成硬件操作
通用块层 合并请求、排序、调度
设备驱动 对磁盘控制器说话
存储
硬件 存储设备 数据真正落地的地方
本地磁盘 SSD / HDD
网络存储 另一台机器上的盘

每一层都只解决一个问题。 库函数管「少发系统调用」，VFS 管「抹平差异」，缓存管「能不去磁盘就别去」，具体文件系统管「块怎么摆在磁盘上」，块层管「怎么把请求有效率地发给设备」。

三层缓存分别缓存什么

这三层都叫「缓存」，但缓存的东西完全不同，混起来就说不清了：

缓存缓存的是什么命中之后省掉了什么
页缓存文件内容本身（按页/块）不用读磁盘
dentry 缓存路径解析的结果：名字 → inode不用逐层读目录文件
inode 缓存已经读进来的 inode不用再从 inode 区读一次元信息

第 ⑥ 篇讲的「缓冲 I/O」和「直接 I/O」，说的就是在这个图里绕不绕过页缓存这一问题。

03三类文件系统与挂载

按数据存在哪，Linux 的文件系统分三类：

最常见

磁盘文件系统

数据真的存到磁盘上

Ext2 / 3 / 4、XFS、Btrfs、NTFS……

这是「文件系统」这个词最原始的含义：把磁盘上的块组织成文件。

不落盘

内存文件系统

数据在内存里，不在磁盘

/proc、/sys、tmpfs 都是这一类。

读写这类文件，实际上是在读写内核里的数据结构。 比如 /proc/cpuinfo 并不是一个真实存在的文件， 是内核在你读它的时候临时拼出来的。

跨网络

网络文件系统

访问别的机器上的数据

NFS、SMB、CIFS。

在你看来 /mnt/nfs/a.txt 就是一个普通路径， 底下 VFS 会把 read 请求打包成网络请求发出去。

另外，文件系统得挂载到某个目录才能用。

没有挂载时 一块有数据的磁盘 用不了
设备/dev/sdb1内核能看到它
里面Ext4 格式的数据

内核知道有这块盘，但没有路径能通向它

挂载到一个目录让路径能走到它
挂载之后 mount /dev/sdb1 /mnt/data 能用了
挂载点/mnt/data访问入口
效果访问 /mnt/data/x 就是在访问 sdb1

从此这个目录下面的东西，都来自那块盘

Linux 启动时会把根文件系统挂到 /，之后其他文件系统再一层层挂上去。所以整棵目录树可以由好几块不同的物理磁盘拼成。

04文件描述符与打开文件表

打开一个文件时，操作系统要记住「这个进程开着哪些文件、每个读到哪了」。

用起来很简单：

int fd = open("notes.md", O_RDONLY);   // 打开，拿到一个整数
read(fd, buf, 100);                    // 之后只用这个整数，不再用文件名
close(fd);                             // 用完要关，不然会泄漏

那个整数就是文件描述符（file descriptor）。它是一个下标，指向进程自己的一张表。

打开文件表里记着四样东西：

记什么什么意思为什么需要
文件指针这个文件读到第几个字节了同一个文件被两个进程打开时，各自的进度要分开算
打开计数器有几个进程正开着它计数到 0 才能删掉这个表项 —— 不然会把别人正在用的关掉
文件磁盘位置inode 在哪、数据块在哪缓存在内存里，省得每次操作都去磁盘读一遍
访问权限只读 / 读写 / 追加……打开之后要能判断某次 read 或 write 合不合法

文件指针是「每个打开动作一份」，不是「每个文件一份」。 这就是为什么两个进程同时读同一个文件时，各自读到的地方互不影响。

05用户按字节，内核按块

到这里有个绕不开的错位：

用户视角

你看到的

文件是一条连续的字节流

你 read(fd, buf, 1) 读一个字节，就真的拿到一个字节。

文件在程序看来就是一个长长的数组，下标是字节偏移量。

内核视角

磁盘上真实的

一块一块的 4KB 方块，散落在各处

磁盘不认字节，只认块。文件的数据块可能根本不连续， 前后两块可能隔了半个磁盘。

操作系统完全不关心你在内存里把它理解成什么数据结构。

把这两个视角对上的工作，就是文件系统。

用户读 1 个字节 read(fd, buf, 1)
算出这是第几块 字节偏移 ÷ 块大小
把那一块读进来 从磁盘读一整个 4KB
只返回那 1 个字节 剩下的先留在缓存里

写的时候是反过来的：找到那一块、把整块读进来、只改其中你要写的那几个字节、再把整块写回去。

所以文件系统的最小操作单位是块，不是字节。 读 1 个字节和读 4096 个字节，在磁盘层面是完全一样的代价。这也是为什么「小文件随机读」在磁盘上特别慢 —— 每次都要捞一整块回来，而你可能只用了其中几个字节。

有了 VFS，是不是就不需要具体文件系统了？

恰恰相反，VFS 自己不干活。它只是一个统一的接口层和抽象模型， 真正的读写算法还是各文件系统自己实现的（Ext4 怎么找块、NFS 怎么发网络请求都不一样）。 VFS 的价值在于让上层不用关心这些差异。

两个进程同时读同一个文件，一个读到第 100 字节，另一个会受影响吗？

不会。每次 open 都会创建一个独立的「打开文件表项」，各自的读写偏移记在自己的表项里。 两个表项指向同一个 inode（所以看到的是同一份数据），但进度是分开算的。 fork 出来的子进程则不同 —— 它共享父进程的表项，所以父子会共用同一个偏移。

页缓存、dentry 缓存、inode 缓存，这三个是同一回事吗？

不是。页缓存存的是文件内容；dentry 缓存存的是「路径名解析到哪个 inode」这个结果； inode 缓存存的是已经读进内存的 inode（元信息）。 它们分别省掉了「读磁盘」「逐层遍历目录」「读 inode 区」三种不同的开销。

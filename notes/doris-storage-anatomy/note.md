「真正存数据的表对象，有自己的**文件、分区、分桶、副本**」——一句话里四个名词排在一起，看着像四个并列的东西；但它们回答的是四个不同的问题，而且是叠在一起的。这句话出现在上一页的 §06，也出现在每一次建表时对物理表的描述里。

这一页从一张小表开始，一层一层往下搭。表结构和字段名取自你项目里那张快照表（`crm_dc_audience_snapshot`，日分区 + `HASH(uid)` 分桶），但不需要先懂它。

```callout
tone: muted

  **读这篇之前**：知道 SQL 里有表、行、列就行。数据库里其他的都不用。
```

  读完你应该能回答四个问题：

  - 一行数据**被分到哪个抽屉**？（分区）

## 01 · 四层叠起来的样子

先看一张小表长什么样。三天的快照，每天几行：

```text
snapshot_date   snapshot_id   encrypt_uid
2026-10-07      1001          u-1001
2026-10-07      1001          u-1002
2026-10-07      1002          u-1001
2026-10-08      1001          u-1002
2026-10-08      1002          u-1001
2026-10-09      1002          u-1004
```

数据库在磁盘上看不到「表」这个形状，它看到的是文件。表只是把这些行组织起来的一套约定。组织的办法就是往下切两层：

```tree
- label: Table（表）
  sub: crm_dc_audience_snapshot
  note: 一套约定，不是一个文件
  children:
    - label: Partition（分区）
      sub: p20261008
      note: 按 snapshot_date 切，一个分区 = 一天的行
      children:
        - label: Tablet（桶）
          sub: 桶 2
          note: 分区里再按 hash(uid) % N 切；它是复制、调度、并行的最小单位
          children:
            - label: Rowset
              sub: 一次写入产出的一批
              children:
                - label: Segment
                  sub: 列存文件
                  note: 磁盘上真正躺着的字节
                  children:
                    - { label: Column, sub: 每一列单独编码 }
                    - { label: Page, sub: "约 64KB 一页，带 min/max" }
```

这张树里有两个位置值得记住：

- **分区和分桶是两刀**。第一刀按时间（分区），第二刀按人（分桶）。切完之后，最小的一份可独立存放的数据叫 tablet。
- 文件和副本描述的都是 tablet：它落到磁盘上是什么（文件），同一份数据存几遍（副本）。

先切一刀看第一层。

## 02 · 分区：按时间切抽屉

**分区（Partition）** 是把表的行按某个列的值切成互不重叠的几块。最常用的是按日期范围切，官方叫 Range 分区。

```sql
CREATE TABLE crm_dc_audience_snapshot (
  snapshot_date DATE         NOT NULL,
  snapshot_id   BIGINT       NOT NULL,
  encrypt_uid   CHAR(32)     NOT NULL
)
DUPLICATE KEY (snapshot_date, snapshot_id, encrypt_uid)
PARTITION BY RANGE(snapshot_date) ()          -- 按 snapshot_date 切
DISTRIBUTED BY HASH(encrypt_uid) BUCKETS 8    -- 分区里再切 8 个桶
```

上面那份数据会被切成三块：

```text
p20261007 → 2026-10-07 的三行
p20261008 → 2026-10-08 的两行
p20261009 → 2026-10-09 的一行
```

**分区为什么值得切**：查询几乎都带时间。`WHERE snapshot_date = '2026-10-08'` 时，规划器看一眼分区表，把其他两个分区直接丢掉。这叫分区裁剪，`EXPLAIN` 里会写出来：

```text
partitions=1/3          -- 3 个分区里只留 1 个
```

分区还有两个附带好处：删历史数据变成「丢掉一个分区」（一次元数据操作，不用逐行 `DELETE`）；过期数据可以按分区设 TTL。

你项目里那张表用的是动态分区：到点自动建当天的新分区，同时丢掉 14 天前的老分区，不需要人写 DDL。

```callout
tone: amber
icon: ⚠
text: |
  分区键要选**查询真的会拿来过滤的列**。

  拿一个只有 5 个取值的列（比如地区）当分区键，规划器没什么可丢的，
  而每个分区都要付元数据成本：抽屉开了很多，里面都没几页纸。
```

## 03 · 分桶：每个抽屉里再切格子

切完时间，一个分区可能还是很大（一天一千万行）。而且数据要摊到多台机器上才能并行算。所以分区里面再切一刀：按 uid 的哈希值切。

官方给的规则一句话：

```text
bucket = crc32(分桶列) % 桶数
```

上面那张表的 `DISTRIBUTED BY HASH(encrypt_uid) BUCKETS 8`，就是「按 `encrypt_uid` 切 8 个桶」。切出来的每一份，就是一个 tablet。

这里有个容易混的点，值得单独记：

```compare
first: 两刀
head: [怎么切, 切完的效果]
rows:
  - 分区: ["按**时间**切：同一天的行在一起", "同一个人会出现在多个分区里（每天都有一行）"]
  - 分桶: ["按**人**切：`hash(uid)` 相同的行在一起", "同一个 uid 在每个分区里都落到**同一个桶号**"]
```

第二行就是上一页讲 colocate 和本地 join 的物理基础：同一个 uid 的数据，在每一层分区里都在同一个桶里，只要两张表的桶对齐，join 就不用把数据搬来搬去。

分桶也能裁剪。`WHERE encrypt_uid = 'u-1001'` 时，规划器算出这个 uid 落在几号桶，只扫那一个：

```text
partitions=1/3  tablets=1/8      -- 分区和桶都裁掉了
```

```callout
tone: violet
icon: 💡
text: |
  桶数怎么定，官方给的是三条：

  - 取 BE 数量的整数倍，数据分布更均匀
  - 够用就行，尽量少（桶越多，tablet 越多，元数据和扫描任务越多）
  - 单个 tablet 压缩后大约 1GB ~ 20GB；单分区最多 128 个桶

  反例和正例都很好记：按**性别**分桶（只有两个值）会让 8 个桶里两个满、六个空；
  按 **uid** 这种高基数列分桶，才切得开。
```

## 04 · 文件：格子里真正的字节

一个 tablet 里到底是什么文件？官方的磁盘层级是：

```text
Tablet → Rowset → Segment → Column → Page
```

- Rowset：一次写入产出的数据批次。写下一次，多一个 rowset。
- Segment：rowset 里的文件本体。
- Column / Page：segment 内部按列组织，每列的值攒成约 64KB 的一页（page），每页独立编码、独立压缩。

Doris 的表是**列存**：同一列的值在文件里挨着放，而不是同一行的值挨着放。带来的三件事：

```cards
cols: 3
items:
  - title: 只读用到的列
    desc: 查 uid 就不用把年龄、地区那些列读进来
    tone: blue
  - title: 每列用自己的编码
    desc: 数字用 bit-shuffle，低基数字符串用字典，日期用 frame-of-reference
    tone: green
  - title: 每页带 min/max
    desc: 还有可选的 bloom filter；扫描时先看这一页的范围，不命中就整页跳过
    tone: violet
```

```callout
tone: violet
icon: 📦
text: |
  ==「文件」不是「一个 uid 一个文件」。==

  一批行写一次盘，按列打包成一页页。真正决定一次查询读多少的，
  是前面两刀（分区、桶）把数据切在了哪里，以及每一页贴的那个 min/max 标签。
```

## 05 · 副本：同一份 tablet 存几份

**副本（Replica）** 说的是同一份 tablet 数据存在几台机器上。默认是 3 份，放在不同的 BE 上。

写入的流程（官方）：数据先发给这个 tablet 的所有副本 → 每台机器各写自己那份 → 回执 → FE 数一下，**写成功的副本超过一半**就算这次写入成功（3 份里至少 2 份）→ 提交 → 没写成的那些，后台再异步补齐。

所以副本换来的是两件事：一台机器挂了数据不丢，查询还能继续。代价也很直接：磁盘占用乘以副本数，每次写入要等多数派。

自己切一下看：

```demo
widget: storage-anatomy
title: 3 个分区 × 4 个桶，切副本数、挂一台机器
actions: false
config:
  replicas: 3
```

可以试三下：

- 副本数切到 **1**，再点「挂掉 BE-1」：有些 tablet 变成了红色，**读不到**。
- 切回 **3** 再挂 BE-1：每个 tablet 少一份，但还剩两份，查询照常。
- 点任意一个桶：右边会写清它是什么、几份副本、落在哪几台机器上。

你项目 demo 里的表白布的是 `replication_num = 1`（单机跑起来省事），生产环境的表一般是 3。

```callout
tone: red
icon: ⚖
text: |
  ==分区和桶是「切成几份不同的数据」，副本是「同一份数据存几遍」。==

  前者决定数据放在哪里、怎么并行；后者决定坏了怎么办、占多少磁盘。
  两者都会出现在建表语句里，但解决的问题完全不同。
```

## 06 · 叠起来看一次查询

同一个查询，条件不同，读的量差一个数量级。下面用一个 4 个桶的简化模型（真实表是 8 个），切几个 `WHERE` 看：

```demo
widget: prune-lab
title: 3 个分区 × 4 个桶（每桶 250 行），换条件看命中格
actions: false
config:
  q: 2
```

`EXPLAIN` 里那两行就是前面两刀的账：

```text
partitions=1/3      -- 分区裁剪：3 天里只读 1 天
tablets=1/4         -- 分桶裁剪：4 个桶里只扫 1 个
```

一句话算账：

```text
扫的数据量 ≈ 总数据量 × (命中分区 / 总分区) × (命中桶 / 总桶)
副本数不改变这个乘积 —— 它只决定读哪一份、以及坏了还有没有得读
```

还有一个容易忽略的分工：**桶号在每个分区里是同一套**。所以只按 uid 过滤、不带日期时，每个分区都要去同一个桶号找一次（下面那个「只按 uid」就是这种情况）。分区裁剪管不了它，分桶裁剪也跨不过分区。

## 07 · 回到你圈的那句话

```compare
first: 词
head: [它回答什么, 谁决定, 想错了会怎样]
rows:
  - 分区: ["行落在哪个时间抽屉里", "建表时的 `PARTITION BY`，通常按日期", "不按查询会用的列切，白开一堆抽屉"]
  - 分桶: ["抽屉里落到哪个格子（tablet）", "建表时的 `DISTRIBUTED BY HASH(...) BUCKETS N`", "拿低基数列分桶，桶一半空一半挤"]
  - 文件: ["格子里字节怎么摆", "列存格式：Rowset → Segment → Page", "以为一个 uid 一个文件，就读不懂为什么扫描是「按页跳」的"]
  - 副本: ["同一份 tablet 存几遍", "建表时的 `replication_num`，默认 3", "以为副本能提升查询速度，实际上那是在拿磁盘和写延迟换可用性"]
```

再回看你圈的原文：

> 真正存数据的表对象，有自己的文件、分区、分桶、副本

现在可以把这句话展开读：**表在物理上是分区 + 桶切出来的一堆 tablet；每个 tablet 由若干文件组成，并且按副本数存了几份。**

```summary
title: 一句话
text: |
  分区按时间切，分桶按人切，切到最小的一块叫 tablet；
  文件是 tablet 落到磁盘的样子，副本是同一块 tablet 存了几份。
  ==前两个决定「读多少」，后两个决定「坏不坏、占多少」。==
```

```quiz
- q: 分区和分桶都在「切数据」，它们切的方向有什么不同？
  a: |
    分区按列值（通常是日期）切成互不重叠的几块，同一天的行在一起；
    分桶在分区内部按 hash(分桶列) % 桶数 切成 N 份 tablet。
    同一个人会出现在多个分区里，但在每个分区里都落到同一个桶号。
- q: 把「副本数从 1 改成 3」，一次查询扫描的数据量会变成三倍吗？
  a: |
    不会。查询每个 tablet 只读一份副本，扫描量不变。
    变的是磁盘占用（乘三）、写入要等多数派确认，以及一台 BE 挂掉时数据还在不在。
- q: "`EXPLAIN` 里的 `partitions=1/3  tablets=1/8` 分别在说什么？"
  a: |
    分区裁剪：3 个分区里只有 1 个可能包含要查的数据，另外两个不读。
    分桶裁剪：这个分区里 8 个桶只有 1 个可能命中（过滤条件里有分桶键的等值条件）。
```

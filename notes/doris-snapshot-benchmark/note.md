## 01 · 每天 100 份人群快照，存 14 天

运营要做**人群圈选**：提交一个条件（「最近 7 天加购过、AUM 大于 50 万的香港客户」），系统把符合条件的人圈出来。圈出来的这份名单叫**快照**。

快照要每天存、留 14 天，用来做对比（「今天比昨天多了多少人」）和回溯（「上周三圈的是哪些人」）。

数据量是这么长的：

```text
1 个快照  = 100 万人        （就是一堆 user_id）
1 天      = 100 个快照      = 1 亿行
14 天     = 1400 个快照     = 14 亿行
```

设计文档里最初定的是：==每个快照建一张独立的表==。

```text
snapshot_10001    100 万行
snapshot_10002    100 万行
...
snapshot_14000    100 万行        ← 1400 张表
```

这个想法很自然 —— 像文件一样，一个快照一份。删起来一句 `DROP TABLE` 干净利落，一个快照写坏了也不影响别人。

另外两种候选是把它塞进**一张表**，用一列标明「这一行属于哪个快照」，区别只在表模型：

```compare
first: 怎么存
head: [① 共享 Duplicate 表, ② 共享 Unique 表, ③ 一快照一表]
rows:
  - 表数量:
      - { text: "1 张", tone: green }
      - { text: "1 张", tone: green }
      - { text: "1400 张", tone: amber }
  - 怎么区分快照: [靠 `snapshot_id` 这一列, 靠 `snapshot_id` 这一列, 一张表就是快照本身]
  - 同一批人写两次:
      - { text: 叠成两行, tone: red }
      - { text: 只留一行, tone: green }
      - { text: 叠成两行, tone: red }
  - 删掉一天的数据: [一条命令, 一条命令, 要删 100 张表]
```

这张表里埋着三个概念 —— **表模型**、**分区**、**tablet**。==后面每一条结论都从它们长出来。==

在建表之前得先知道这三个是什么。

## 02 · 先把三个概念说清楚

### 表模型：Duplicate 和 Unique

建表时要选一种模型，区别就是**同一行数据写两次会怎样**。

拿一个真实的例子。快照 `10001` 里有两个人，第一次写入：

```text
(10001, 8801)
(10001, 8802)
```

然后**再写一遍同样两行**（模拟「提交成功但客户端没收到结果，于是重试」）：

```text
(10001, 8801)
(10001, 8802)
```

```cards
cols: 2
items:
  - title: Duplicate —— 照单全收
    tag: 追加
    tone: red
    desc: 表里变成 **4 行**，8801 和 8802 各出现两次。
    body: |
      写入路径就是**追加**：不管这条数据以前有没有来过，直接写进去。

      ```text
      (10001, 8801)   ← 第一次
      (10001, 8802)   ← 第一次
      (10001, 8801)   ← 第二次
      (10001, 8802)   ← 第二次
      ```

      好处是快。代价是**重试会叠行**，人数会凭空翻倍。
  - title: Unique —— 按主键去重
    tag: 合并
    tone: green
    desc: 表里还是 **2 行**，第二次写入只是把主键上已有的行覆盖掉。
    body: |
      写入时要**先知道这个主键上已经有什么**，才能决定哪些旧行要让位。

      ```text
      (10001, 8801)
      (10001, 8802)
      ```

      好处是天然幂等。代价写在写入路径上 —— 后面会看到具体多少。
```

### 存储单位：分区、桶、tablet

这三个词是「为什么分表会输」的全部原因。

```cards
cols: 3
items:
  - title: 分区
    tag: PARTITION
    tone: blue
    desc: 按某一列的值，把**一张表横着切几块**。
    body: |
      共享表按 `snapshot_date` 切 —— 一天一块。

      查询里带上 `WHERE snapshot_date = '2026-09-28'` 时，
      Doris 直接跳过其他块，**根本不读**。这叫分区裁剪。
  - title: 分桶
    tag: BUCKET
    tone: violet
    desc: 每个分区内部，再按 `HASH(user_id)` **竖着切 8 份**。
    body: |
      ```sql
      DISTRIBUTED BY HASH(user_id) BUCKETS 8
      ```

      同一份快照的数据被打散到 8 处，写入和查询可以并行。
  - title: tablet
    tag: 存储单元
    tone: amber
    desc: "**分区 × 分桶**，Doris 真正落地存放、复制、做 compaction 的最小单位。"
    body: |
      这是要记住的那个数：

      ```text
      共享表：14 个分区 × 8 个桶  =  112 个 tablet
      分表：  1400 张表 × 8 个桶  =  11200 个 tablet
      ```

      ==共享表的 tablet 数是「天数 × 8」，和快照有几个无关。==
```

## 03 · 第一轮：三种存法同台

第一轮把三个方案摆在同一条跑道上：每快照 10 万行、写 1000 个快照，三种各写完 1 亿行。

| 指标 | 共享 Duplicate | 共享 Unique | 一快照一表 |
| --- | ---: | ---: | ---: |
| 1000 个快照的 INSERT P95 | **48.1 ms** | 183 ms | 51.7 ms |
| 建表 P95 | — | — | 16.8 ms |
| 查询 P50 | 9.8 ms | 11.4 ms | **6.9 ms** |
| Tablet 数 | **8** | 8 | **8000** |
| 峰值 BE CPU | 208% | **411%** | 144% |
| 峰值 FE CPU | 152% | 129% | **232%** |
| 同一批人写两次，表里多少行 | **20 万行** | **10 万行** | 需要先 DROP |

三个读法：

**① Duplicate 和分表的写入都是平的。** 从第 1 个快照到第 1000 个，INSERT 一直在 40–60 ms，没有随快照数抬升。分表的建表时间也停在 7 ms 附近。

**② Unique 是唯一一条会变陡的曲线。** 前 20 次 P50 已经是 78 ms，到 100 个快照升到 103 ms，之后停在 110–120 ms；P95 从 88 ms 涨到 189 ms，单次最大 919 ms。同期它的 BE CPU 到 411% —— 是另外两个方案的两倍。

!!Unique 慢不是因为它做错了什么，是因为它**多做了事**：按主键去重就得先知道主键上已有什么。!!

**③ 分表的 tablet 数，正好是 1000 × 8。**

```text
BE 上报的 tablet 数：8075

8075 − 75（测试开始前就有的基线）= 8000
8000 ÷ 1000 张表            = 8   ← 每张表 8 个桶
```

共享表同期是 **8 个**。两张表之间差了一千倍。

## 04 · 分表输在哪

先把一个反直觉的事实摆上来：

```compare
first: 10M 行、100 张表时的查询
head: [共享表, 一快照一表]
rows:
  - SUM 的 P50: [{ text: "57 ms", tone: amber }, { text: "24 ms", tone: green }]
  - 实际扫了多少字节: ["203 MB", "77 MB"]
  - 为什么: [多扫了 `snapshot_date`、`snapshot_id` 两列, 一张表只有 `user_id` 一列]
```

==分表的读，比共享表快一倍多。==

原因很直白：共享表的每一行都得额外带上「我属于哪一天、哪个快照」，分表不用 —— 表名本身就是答案。

写入也打平：10 万行那一档，两个方案的 INSERT P95 都在 50 ms 附近。

**那分表输在哪？** 输在 tablet 数会跟着快照数一起长。

```text
共享表：加一天         →  +8 个 tablet        （和当天写几个快照无关）
分表：  加一天         →  +800 个 tablet      （每天 100 个快照 × 8 个桶）
```

拖一下看它怎么长的 —— 这是一轮专门建表建到 10000 张的实测：

```demo
widget: tuner
title: 快照表越建越多时，FE 在发生什么
actions: false
hint: 拖动滑块切换表数
config:
  param: { label: 快照表数, unit: 张, values: [100, 500, 1000, 1400, 2500, 5000, 10000] }
  outputs:
    - { label: FE 容器内存, unit: "%", values: [73.0, 77.1, 81.0, 82.1, 79.7, 88.2, 91.1], tone: red }
    - { label: 建表 P95, unit: ms, values: [10.9, 11.0, 10.8, 11.7, 12.5, 12.3, 13.7], tone: blue }
    - { label: SHOW TABLES P95, unit: ms, values: [1.5, 2.3, 2.9, 3.5, 6.7, 14.0, 28.8], tone: amber }
```

从 100 张拖到 10000 张：

- **建表 P95 几乎不动** —— 10.9 ms 到 13.7 ms，只涨了 1.25 倍
- **FE 容器内存从 73% 一路涨到 91.1%**
- **`SHOW TABLES` 涨了 19 倍** —— 1.5 ms 到 28.8 ms

!!先撞到的不是「建表变慢」，是 FE 要记住的东西太多。!!

每多一张表，FE 就要多记住它的库名、表名、列定义、分区、以及每个 tablet 落在哪台 BE 上。这些元数据全都躺在内存里。所以表数一涨，内存就跟着涨，而 `SHOW TABLES` 这种「遍历所有表」的操作第一个变慢。

```callout
tone: amber
icon: ⚖️
text: |
  这里要说句公道话：**这台 FE 在共享表 15 亿行时也是 88% 内存。**

  所以「FE 内存高」不是分表独有的问题 —— 这台机器的 FE 容器只给了 3 GiB，
  本身就偏紧。

  真正的区别是**增长方式**：共享表的内存和快照数无关，分表的是正比关系。
  分表本身不是错的选择，它有一条明确的规模上限，而上限在哪要看你能给 FE 多少内存。
```

分表的取舍，一句话：

> 拿「元数据随快照数线性增长」，换「每次查询少扫两列」。

## 05 · 共享表凭什么不慢

回到最开始那个疑问：

> 14 亿行塞在一张表里，读一个快照难道不用扫全表吗？

不用。因为读取时有两层裁剪，一层砍掉一大块，一层再砍掉一大块。

先看表长什么样 —— 按天分区，主键是三个字段拼起来的：

```sql
CREATE TABLE snapshot_users (
  snapshot_date date   NOT NULL,
  snapshot_id   bigint NOT NULL,
  user_id       bigint NOT NULL
)
DUPLICATE KEY(snapshot_date, snapshot_id, user_id)
PARTITION BY RANGE(snapshot_date)          -- 一天一个分区
DISTRIBUTED BY HASH(user_id) BUCKETS 8
```

主键里 `snapshot_date` 在最前、`snapshot_id` 第二 —— ==这个顺序就是裁剪发生的地方==。点一下看：

```demo
widget: partition-prune
title: 读一个快照，实际要扫多少行
actions: false
hint: 点一个分区，再点它里的一个快照
config:
  days: 14
  snapshotsPerDay: 100
  rowsPerSnapshot: 1000000
```

**第一层：分区裁剪。** 查询里写了 `WHERE snapshot_date = '某一天'`，Doris 看分区定义就知道只需要读那一块，另外 13 个分区**根本不打开**。

```
全表 14 亿行  →  只剩这一天 1 亿行       砍掉 93%
```

**第二层：主键前缀。** `snapshot_id` 是主键的第二个字段 —— 在 Doris 里这叫前缀索引，数据在一个分区内部是按主键顺序排好的。所以定位到某个 `snapshot_id` 时，只需要读那一段连续的区域。

```
这一天 1 亿行  →  只剩这个快照 100 万行    再砍掉 99%
```

实测的 Profile 印证了这条路：

```text
14 天稳态下，读一个快照的 SUM(user_id)：

  ScanRows     1,000,000        ← 不是 14 亿
  P50          11–17 ms
  扫描字节      31 MB

同一张表上查「某个人在不在这个快照里」：
  ScanRows     1                  ← 就查一行
  P50          4–5 ms
```

```callout
tone: green
icon: 🎯
text: |
  ==「一张表装 14 亿行」和「读一次要扫 14 亿行」是两件事。==

  前者是存储布局，后者是查询执行。分区决定读哪一块，主键顺序决定块里读哪一段。
  两张裁剪加起来是 1400 倍。
```

顺带一提，删数据也是这个结构的好处：删除一天 = `DROP PARTITION`，实测 DDL 只要 **3.2 ms**，和表里有多少行无关。

## 06 · 重试：Duplicate 会叠行，怎么办

Duplicate 表有个绕不开的问题 —— 回到 02 节那个例子：**同一批人写两次，表里就有两行**。

这在分布式里不是罕见情况。写入方提交完 SQL、Doris 也已经提交事务，但结果包在网络里丢了。客户端只知道自己超时了，不知道对方做没做。它只能重试。

重试一次，人数就翻倍一次。这不能接受。

Doris 的解法是 **INSERT LABEL**：给这一次业务写入起个名字，服务端记住这个名字做过什么。

```seq
grid: true
participants:
  - { id: w, label: 写入方, sub: Snapshot Worker, kind: backend }
  - { id: f, label: Doris FE, sub: 事务管理, kind: database }
messages:
  - { from: w, to: f, label: "INSERT ... LABEL 'snapshot_10001'", kind: sync, note: ① }
  - { from: f, to: w, label: "提交成功 · 事务 VISIBLE（已生效可读）", kind: reply, note: ② }
  - { from: w, to: w, label: 结果包丢了 · 客户端只看到超时, kind: self, note: ③, tone: red }
  - { from: w, to: f, label: "重试 · 同一个 LABEL", kind: sync, note: ④ }
  - { from: f, to: w, label: "拒绝 · Label [snapshot_10001] has already been used", kind: reply, note: ⑤, tone: red }
```

实测的四种丢包时机，结果全部一致：

| 情形 | 结果 |
| --- | --- |
| 第一次写入成功 | 事务 `VISIBLE`（已生效可读），表里 100 万行 |
| 同一 LABEL 再提交 | 拒绝。表里还是 100 万行 |
| 提交完成、丢弃结果包后重试 | 拒绝。表里仍是 100 万行 |
| 查询刚发出就断开连接 | 服务端仍然提交成功。重试被拒绝，校验通过 |

```callout
tone: red
icon: ⚠
text: |
  ==Label 的窗口不是永久的。==

  这台 FE 的配置是 `label_keep_max_second = 259200`（3 天）、`label_num_threshold = 2000`。

  Label 挡住的是**执行重试**，不是「这个快照永远只能写一次」。窗口过了之后再写一遍，
  Duplicate 表照样会叠行。

  所以如果业务上需要「3 天以后整批重写同一个快照」，要么先删掉那个快照的数据再写，
  要么换 Unique 表 —— 那是它唯一值得付出 4 倍写入成本的时候。
```

## 07 · 结论、边界、上线看什么

三轮跑下来，方案定了：

```spec
title: 快照表
subtitle: 共享 Duplicate + 按天分区 + INSERT LABEL
tone: green
rows:
  - k: 表模型
    v: |
      **一张 Shared Duplicate 表。**
      14 天 × 100 个 × 100 万行写完，INSERT 和 SUM 都没有出现拐点。
  - k: 分区
    v: |
      **每天一个 RANGE(`snapshot_date`) 分区。**
      读一个快照时 ScanRows 是这一个快照，不是 14 亿。删一天是一次 DDL，3.2 ms。
  - k: 主键顺序
    v: |
      **`(snapshot_date, snapshot_id, user_id)`。**
      Profile 实测：100 万行的 SUM 扫 100 万行 / 31 MB。
  - k: 分桶
    v: |
      **`HASH(user_id) BUCKETS 8`。**
      分表对照里 1000 万行的 INSERT P95：1 个桶 2454 ms，8 个桶 610 ms。
  - k: 写入并发
    v: |
      **2。**
      1→2 吞吐 1.57 倍；2→4 只多 15%，P95 从 182 ms 涨到 317 ms；
      并发 8 时这台 3 GiB FE 停在 94% 内存。
  - k: 什么时候改用 Unique
    v: |
      只在**必须原地整批重写、而且不能先删再写**的时候。
      代价是 100 万行时 INSERT P95 从 233 ms 涨到 980 ms（**4.21 倍**），
      而且加并发救不了它 —— 并发 2 / 4 的吞吐是 88.9 / 89.0 个每分钟，几乎不动。
```

### 它没有测什么

一个基准报告的价值，一半在它测出了什么，另一半在它**明确说自己没测什么**。

```checklist
tone: warn
items:
  - 共享表 BUCKETS 1 —— 没有测过，不能从分表的 4 倍差距反推共享表也该避免 1 个桶
  - 分表 × 100 万行 × 超过 100 张表 —— 10000 张那一档用的是 10 万行
  - 1000 万行 × 14 天
  - 带业务宽列的快照 —— 三轮主要只有 user_id，磁盘和扫描量会小一个数量级以上
  - Label 过期之后的重试
  - 多 BE、replication_num > 1 —— 版本数、compaction 队列、FE 内存都要重测
  - 单个快照远大于 1000 万行
```

**尤其是最后一条关于分表的**：报告里写得很清楚 ——「10 万行可以到 10000 张；百万行只证到 100 张」。==不能把 10000 张的结论挪到百万行快照上。==

### 上线时盯什么

这台机器的实测水位。换机器要重新标定。

| 指标 | 这次的正常带 | 需要看 | 这次的停止线 |
| --- | --- | --- | --- |
| FE 容器内存 | 14 天稳态约 88% | 持续高于 90% | 高于 92% 后本轮停止后续阶段 |
| 活跃分区版本数 | 100 万行写完可到 75，60 秒后回到个位数 | 空闲 60 秒后仍高于 80 | 高于 1400 |
| Compaction score | 写入中可到约 100，60 秒后回到 7 左右 | 停止写入 60 秒后仍高于 50 | 连续 10 分钟只升不降 |
| 100 万行 INSERT P95 | 145–233 ms | 同一并发下持续高于约 400 ms | 高于上一档 3 倍 |
| 错误码 -235 / -238 | 0 | 出现就查版本数 | 连续出现 |

tone: red
icon: ⚠
text: |
  ==绝对毫秒数不能外推。==

  这台是 Apple M4 单机、1 FE + 1 BE、`replication_num = 1`。

```summary

  快照之间靠 `snapshot_id` 分开、按天分区删除、写入方用 LABEL 保证同一次提交不会成功两次 ——

```

```quiz
- q: 「一张表装 14 亿行」为什么读一个快照只要扫 100 万行？
  a: |
    两层裁剪叠在一起：

    ① **分区裁剪** —— 表按 `snapshot_date` 分区，查询带上这个条件时，
       另外 13 天的分区根本不打开。14 亿 → 1 亿。
    ② **主键前缀** —— 主键顺序是 `(snapshot_date, snapshot_id, user_id)`，
       `snapshot_id` 在第二位。数据在分区内按主键顺序排好，
       定位到某个 `snapshot_id` 只读那一段连续区域。1 亿 → 100 万。

    实测 Profile：ScanRows = 1,000,000 / 31 MB。

- q: 分表的查询比共享表更快，那它到底输在哪？
  a: |
    输在 **tablet 数会随快照数线性增长**，而共享表不会。

    ```text
    共享表：14 个分区 × 8 个桶 = 112 个 tablet   （和快照个数无关）
    分表：  1400 张表 × 8 个桶 = 11200 个 tablet （每加一个快照就 +8）
    ```

    实测：1000 张表时 BE 上报 8075 个 tablet（基线 75 + 1000×8），共享表同期是 8 个。
    建到 10000 张时，FE 容器内存到 91.1%，而建表 P95 只从 10.9 ms 涨到 13.7 ms ——
    **先撑不住的是 FE 要记住的元数据，不是建表速度。**

    所以分表不是错的选择，它是在用「元数据线性增长」换「每次查询少扫两列」。

- q: 已经用了 INSERT LABEL，为什么还需要关心 Unique？
  a: |
    因为 Label 的窗口不是永久的。这台 FE 是 3 天 / 2000 个 label，
    它保证的是**执行重试**不会成功两次，不是「这个快照永远只能写一次」。

    窗口过期后再写一遍，Duplicate 表照样叠行。所以如果业务上存在
    「3 天以后整批重写同一个快照」的需求，要么先删掉那个快照的数据再写，
    要么换 Unique —— 那是唯一值得付出 4.21 倍写入成本的时候。

- q: 为什么报告反复强调「绝对毫秒不能外推」？
  a: |
    因为这是一台单机：Apple M4、1 FE + 1 BE、`replication_num = 1`。
    生产是多 BE 集群，版本数、compaction 队列、FE 内存的表现都会不一样。

    能带走的不是「233 ms」这个数，而是**倍数关系**（Unique 慢 4 倍）
    和**「先撞到什么上限」**（分表先撞 FE 内存，共享表 tablet 数不涨）。

把「等」换成「问」：轮询与 select / poll

忙轮询让一个线程招呼多条连接，代价是空转；select/poll 让线程能睡，代价是名单每次重交、醒来全扫一遍。两代方案换的是同一个东西：等待挂在哪里。

上一篇的结论是：一个执行单位只能等一条连接，因为它的执行现场停在那一行 read() 里。

那就换个做法：不停了。线程挨个问过去，谁有数据就处理谁。这一篇从最朴素的忙轮询开始，走到 select / poll，看它们各自治好了什么，又欠下什么。

01忙轮询：一个线程，一堆 fd

把 fd 设成非阻塞，read() 就不会再停了。没数据时它立刻返回 -1，errno 是 EAGAIN：

for (;;) {
    for (int i = 0; i < n; i++) {
        ssize_t r = read(fds[i], buf, sizeof buf);   /* 全部 O_NONBLOCK */
        if (r > 0) {
            handle(fds[i], buf, r);
        } else if (r == -1 && errno == EAGAIN) {
            continue;                                 /* 这条没有，问下一条 */
        }
    }
}

一个线程从此可以招呼任意多条连接。它不会停在任何一条上，因为它根本没有「等」这个动作。

代价立刻就出现了：没有数据的时候，这个循环照转。

CPU

空转

一万条连接全空闲，这个循环仍然跑满一个核。它在反复确认「还是没数据」。

系统调用

白问

每一次 read 都要进一次内核。如果 99% 的连接此刻没数据，那 99% 的调用都是白跑。

死结

延迟与开销二选一

想延迟低就得多问，多问就多烧 CPU；想省 CPU 就少问，延迟就上去。

拖一下这个控件，看白问率怎么随连接数变化：

一个线程挨个问过去 拖大连接数，看「白问率」和「每次要交多少份名单」怎么一起变差

忙轮询的问题不在于它慢，而在于它的开销和「有多少连接」成正比，跟「有多少活」无关。

02把「问」搬进内核

如果可以一次把一万个 fd 交给内核，让它替你检查，线程就能在没事的时候睡下 —— 那就两全了。select 和 poll 做的就是这件事：

接口怎么交名单有什么限制
select三个 fd_set 位图：读、写、异常fd 号必须小于 FD_SETSIZE（通常是 1024），超出的位图放不下
poll一个 pollfd 数组，每项带 fd 和关心的事件没有 1024 这个上限；nfds 受 RLIMIT_NOFILE 约束

只要交一次名单，内核检查完，没事就让线程睡，有事就叫醒它。听起来像是「内核替你轮询」。实际实现完全不是这样。

内核做的是「替你挂监听器」

一次 poll() 在内核里大致是这个过程：

第一步 挂 对名单里的每个 fd 各挂一个临时条目
对每个 fd 调一次它自己的 poll 方法 socket 的 poll 会走到 poll_wait() N 次
把当前线程的条目挂进那个 fd 的等待队列 每个 fd 一份，挂在 fd 自己的队列上 N 份
全部挂完，再看有没有现成的
第二步 查 已经就绪的直接返回
有人就绪，这次调用立刻返回 不需要睡，也不用等
一个都没有，才准备睡 睡之前会再查一遍，防止挂完到睡下有数据到达
都没事 睡
第三步 睡 线程挂起，等待队列上的条目待命
状态置 TASK_INTERRUPTIBLE，让出 CPU 和阻塞 read 的睡法一样
任一 fd 有数据，它的队列唤醒你的条目 内核只知道「这个队列有人等」
被叫醒 但你不知道是谁
第四步 醒 重新扫一遍，找是谁
对名单里每个 fd 再调一次 poll 方法 看谁的就绪位被置上了
返回就绪个数，拆掉所有临时条目 下一次调用，从头再挂一遍
名单和条目都拆了 下次重来

关键在第 ③ 步和第 ④ 步：

  • 内核能让你睡，是因为它在你的线程和 N 个 fd 的等待队列之间，各挂了一个临时条目。这跟阻塞 read 挂的是同一种东西，只是这次挂了很多份，而且不属于某一个 fd。
  • 唤醒只说明「你挂的某一份被触发了」。它没有把「是哪个 fd、来了多少数据」送到你手上。所以醒来必须自己重扫名单。
  • 这 N 份条目在 poll() 返回前会被全部摘掉。下一次调用，得从头再挂一遍。
⚠

「select / poll 在内核里轮询」是个很常见的误解。

内核里没有一张常驻名单，也没有一个循环在替你看守。它只是在你调用的这段时间里， 临时把监听器挂到各个 fd 的等待队列上，等你醒来就全部拆掉。

03三个固定成本

理解实现之后，代价就很好数了：

成本发生在哪怎么随连接数变
名单拷贝每次调用，从用户空间把名单拷进内核select 拷三张位图；poll 拷 N 个 pollfd。都是 O(N)
全量扫描挂的时候扫一遍；醒来找是谁，再扫一遍O(N)，跟这一轮有几个 fd 真就绪无关
就绪信息只返回个数，以及每个 fd 的 revents 位要自己遍历找出哪几个；select 还会改写你的 fd_set，下次要重填

举一个具体的例子。一万条连接，这一轮只有 10 条有数据：

select / poll epoll
每次调用拷进内核的名单 10,000 项 0 项（登记早就在内核里）
内核检查的 fd 数 10,000 0（没人遍历名单）
返回给用户就绪项 10 个，但要自己扫出来 10 个，直接是一个数组
调用结束后要拆掉的东西 10,000 个临时条目 0

中间两行是分水岭。select / poll 的开销跟着「你关心多少条」走，epoll 的开销跟着「这一轮有多少条真有事」走。

04它还欠着一件事

把上面三笔成本归到一起，会发现它们都指向同一个缺失：

💡

内核没有「记住」谁在关心什么，也没有「记住」谁已经就绪。

名单是每次调用临时交的，监听器是临时挂的，就绪信息是醒来现扫的。

要治这个，需要两样东西：

  1. 一张常驻的登记表：登记一次，一直有效，不用每次重交；
  2. 一张常驻的就绪表：数据到达时，由 fd 那边主动把「我好了」写进去，醒来直接取。

这两张表就是 epoll。下一篇看它们长什么样，以及那个「主动写进去」的动作是谁做的。

忙轮询用非阻塞 read，为什么 CPU 还是会跑满？

因为它在没数据时也一直循环，反复进内核确认「还是没数据」。 开销跟连接数成正比，跟真正有数据的连接数无关。

select / poll 让线程能睡，靠的是什么？

调用的过程中，内核对名单里的每个 fd 各挂一个临时等待条目， 线程再睡下。任一 fd 有事件就唤醒线程。睡的能力来自这些临时条目，不是来自内核里的轮询。

为什么 select / poll 醒来后还要把名单扫一遍？

唤醒只告诉线程「你挂的某个条目被触发了」，没有说明是哪个 fd、发生了什么。 内核此时也不知道，因为它没有常驻的就绪信息。

有一句话经常在讲对象存储时被顺带扔出来，然后就被跳过去了：

> 目录树的元数据必须有一致性保证。一个目录下有上亿个文件时，`ls` 要遍历该目录的元数据索引，而这个索引通常收敛在少数元数据节点上；`rename` 要求原子，跨目录 rename 要加锁，跨机房时这些语义的一致性成本呈指数级增长。

它读起来像结论，其实是**一整套机制**被压成了三行。这一页把它拆成四步，每步都给具体的数和图。

## 01 · 先把两样东西分开：数据，和名字

最容易被这句话绕晕的地方是：它说的**不是**「存不下」。

想象一个仓库。一边是货架上的货，另一边是门口那本登记簿：**哪个编号的货叫什么名字、多大、放在哪个货架、谁能取**。

```compare

rows:
  - 数据: [
      "照片、视频、日志文件里**真正的字节**",
      { text: "能。切开、分散到更多机器上，多复制几份也不怕 —— 因为每一份都一样", tone: green }
    ]
  - 名字与归属: [
      "「`/photos/cat.jpg` 这个文件在不在、多大、权限是什么、属于哪个目录」",

    ]
```

判据只有一句：

```callout
tone: violet

  ==数据可以复制，名字不能复制。==

  复制数据只是多占一份空间。复制名字会出现**两份真相**：
  同一个路径，A 机器说「在」，B 机器说「不在」——

  那 `/photos/cat.jpg` 到底是谁？客户端该信谁？
```

## 02 · 目录其实就是一张表

这是整件事的钥匙。在 Unix 里，**目录不是一个抽象概念，它本身就是一个文件**，内容是这张表：

三者分开之后，所有操作都能一句话说清：

```cards
cols: 2
items:
  - title: "`ls /logs`"
    tone: blue
    desc: 把那张「名字 → inode 号」的表读一遍
    body: |
      拿到的是名字和编号。**这一遍只读目录自己这一个文件。**

      `ls` 不用去碰任何一个 log 文件的字节。
  - title: "`ls -l /logs`"
    tone: amber
    desc: 读完表，再逐个去查 inode
    body: |
      「多大、谁能读、什么时候改的」都在 inode 里，不在目录表里。

      所以 `ls -l` 是 **1 次读目录表 + N 次查 inode**（N = 目录里有多少个文件）。
      ==这一条是后面所有成本的根源。==
  - title: "往 /logs 里建一个文件"
    tone: violet
    desc: 加一行，但不止改一处
    body: |
      要一起生效的至少有三处：目录表加一行、目录自身的大小和修改时间变了、
      新文件的 inode 链接数 +1。

      **这三处必须同时生效**，否则别人会看到一个「目录里列着它、但它自己不存在」的状态。
  - title: "`unlink`（删一个文件）"
    tone: muted
    desc: 从表里删一行
    body: |
      表里删一行 + inode 链接数 −1；链接数归零时才真正释放数据块。

      「删了名字但数据还在」和「删了数据但名字还在」都是不能被别人看到的中间态。
```

```callout
tone: violet
icon: 📒
text: |
  ==把「目录」想成一本账，而不是一个文件夹图标。==

  账本有一个性质：**它只能有一个「当前状态」**。
  两个人同时在同一页上写，就得有人先来后到 —— 这就是后面所有麻烦的种子。
```

## 03 · 一亿个文件放在一个目录里

先算一下这张表有多大。每条目录项大致是「固定头 + 名字」：固定头约 8 字节（inode 号、长度、类型），整条按 4 字节对齐。

```text
名字 12 个字符  →  8 + 12 = 20  →  按 4 字节对齐 = 20 字节
算上块尾空隙，按 32 字节一条估算（留余量）

   1 亿条  ×  32 B  ≈  3.2 GB
```

==一个目录，本身就是一个 3.2 GB 的文件。==

于是 `ls /logs` 要干的事就具体了：

```callout

  但拆完之后：`ls` 要问完所有分片再合并，一次改名的两端可能落在不同分片，
```

```text
✓  /logs/2026/10/10/ab/access-00001.log ← 三层，每个目录几百到几千个
```

```callout
  代价是你要事先想好按什么维度切（时间、租户、hash 前缀），
  而且按别的维度查就得自己拼路径 —— 目录树的「随便怎么查都行」这件事，
  本来就是靠一份全局索引换来的。
```

这就是原话里「`ls` 要遍历该目录的元数据索引，而这个索引通常收敛在少数元数据节点上」的完整意思。

## 04 · `rename` 为什么要原子

`rename` 在字面意思是「改个名字」，但一次跨目录的 `rename` 要改的是**两个目录的两张表**：

```text
rename("/a/x.txt", "/b/y.txt")

/a 的表：删掉一行   x.txt
/b 的表：加上（或覆盖）一行   y.txt
```

问题出在「另一个客户端正在看」的时候：

```raw
<div class="fmc-eye">
  <div class="fmc-eye-col">
    <div class="fmc-eye-head">客户端 A<span>正在搬文件</span></div>
    <ol class="fmc-steps">
      <li>删掉 /a/x.txt 这一行</li>
      <li class="fmc-gap">…还没加 /b/y.txt 那一行…</li>
      <li>往 /b 的表里加一行</li>
    </ol>
  </div>
  <div class="fmc-eye-col">
    <div class="fmc-eye-head">客户端 B<span>正在读 /a/x.txt</span></div>
    <ul class="fmc-seen">
      <li><b>第 1 步前</b>：读到了，内容完整 ✓</li>
      <li class="fmc-bad"><b>第 1~2 步之间</b>：文件不见了 ✗</li>
      <li><b>第 3 步后</b>：文件在 /b 那里</li>
    </ul>
  </div>
</div>
```

POSIX 要求的正是：**外面的人要么看到旧名字，要么看到新名字，不能看到「两边都没有」**。如果目标已经存在、要被覆盖，也不能出现「半覆盖」。

所以实现上只有一条路：**把两张表先锁住，改完再一起放开。**

```flow
grid: true
nodes:
  - { id: l1, label: "① 锁住 /a", sub: "别人此刻改不了 /a", row: 0, kind: security }
  - { id: l2, label: "② 锁住 /b", sub: "两把锁的顺序必须固定，否则两个 rename 会互相等成死锁", row: 1, kind: security }
  - { id: m, label: ③ 一次改两处, sub: "删源表一行 + 加目标表一行，在持锁期间完成", row: 2, kind: backend, tone: violet }
  - { id: u, label: "④ 释放两把锁", sub: "从这一刻起，外面看到的就是新位置", row: 3, kind: backend, tone: green }
edges:
  - { from: l1, to: l2, label: 有序加锁 }
  - { from: l2, to: m }
  - { from: m, to: u }
```

换几种实现看看差别在哪：

==「原子」这个词的全部含义就是：这个持锁区间不能被外面看见。== 它不便宜 —— 一次 `rename` = 两次表修改 + 一次加锁 / 解锁。

## 05 · 把目录拆开之后，慢的地方换了位置

既然一张表太大，那就把这张大表按 `hash(完整路径)` 拆到 4 台元数据节点上：每条「名字 → inode」落在哪台，是算出来的。看起来很自然。

```cards
cols: 2
items:
  - title: 拆完确实得到了什么
    tone: green
    desc: 容量和并发都上去了
    body: |
      - 每个节点只装 1/4 的条目，单节点不再 3 GB
      - 四个节点可以并行响应不同的请求
      - 加机器 = 迁移一部分分片
  - title: 但每条语义都要重新回答一遍
    tone: red
    desc: 这些问题的答案都不能靠「一台机器说了算」
    body: |
      - `ls`：要**同时问 4 个分片**，拿到 4 份部分结果再合并、去重、排序
      - 新建文件：得先算出「这个名字属于哪个分片」，再路由过去
      - **两个客户端同时建同名文件**：同名一定落在同一个分片，由它串行化谁成功 —— 这是拆完之后剩下的简单情况
      - 改名的两端落在不同分片：一次操作变成**分布式事务**
      - 分片迁移时：正在进行的查询不能看到「一半有、一半没有」
```

## 06 · 跨机房：把「指数级增长」翻成人话

先把那句「指数级增长」修一下：它不是数学意义上的指数，而是**每多跨一层边界，往返次数就乘一层**。

先看一次「加锁 → 改两处 → 提交」要几个来回：

```text
① 申请锁 /a          →  1 个往返
② 申请锁 /b          →  1 个往返
③ 提交、确认写入      →  1 个往返
                        ─────────
                        3 个往返
```

光在光纤里大约每毫秒走 200 公里，所以**距离直接换算成时间**：

```compare
first: 两端的位置
head: [一个往返（RTT）大约, 这次 rename 要多久]
rows:
  - 同一台机器（锁在内存里）: [{ text: "≈ 0.01 ms", tone: green }, "≈ 0.03 ms"]
  - 同机房不同机器: [{ text: "≈ 0.2 ms", tone: green }, "≈ 0.6 ms"]
  - 同城两个机房: [{ text: "≈ 2 ms", tone: amber }, "≈ 6 ms"]
  - 跨洲（上海 ↔ 美西）: [{ text: "≈ 130 ms（海底光缆不走直线，光速下限约 100 ms）", tone: red }, "≈ 390 ms"]
```

```demo
widget: rtt-lab
title: 距离一拉开，这个目录一秒能做几次改名
actions: false
config:
  place: rack
  rounds: 3
```

数字有点刺眼的地方在这里：**锁要一直握到最后一个往返结束 —— 别人排的队，就是这段时间。**

```text
跨洲一次 rename 要 390 ms，而且这期间两把锁都拿在手里

  这个目录每秒最多完成： 1000 ms ÷ 390 ms ≈ 2.6 次
  同机房同样两把锁：     1000 ms ÷ 0.6 ms ≈ 1660 次

  差了 650 倍 —— 而这个差距不是硬盘慢了，是光跑得就那么快。
```

再叠一层：真正复杂的操作不止跨两个目录，还要跨**分片、副本、地域**。每多一层协调，就多一组往返和一次「谁先谁后」的约定。这就是「非线性急剧上升」的来源 —— 它不是一条曲线，是**每一层都在乘一遍**。

```callout
tone: red
icon: 🌐
text: |
  跨机房还带来一个躲不开的选择题。

  网络一旦分区（两边联系不上），你只有两种选择：

  - **拒绝操作** —— 保证「所有人看到的一样」，代价是服务在分区期间不可用
  - **两边都继续写** —— 保证可用，代价是出现了**两份真相**，事后要合并

  POSIX 的语义（原子 rename、文件锁、目录一致性）==只能选第一种==。
```

## 07 · 天花板的形状：四件事只能同时要三件

把前面几节收成一件事：文件存储要做到无限规模，有四件事互相顶着。

```cards
cols: 2
items:
  - title: ① 单目录无限大 + 无限并发
    tone: blue
    desc: 一个目录装几十亿个文件，读写都不慢
  - title: ② 完整 POSIX
    tone: violet
    desc: 原子 rename、文件锁、目录项强一致、权限立刻生效
  - title: ③ 跨节点 / 跨地域强一致
    tone: amber
    desc: 不管相隔多远，所有人看到的状态必须一样
  - title: ④ 低延迟 + 高可用 + 低成本
    tone: green
    desc: 快、不断、便宜 —— 用户对任何存储的默认期待
```

现实里只能放弃其中一个。常见的选择长这样：

```compare
first: 优先保什么
head: [放弃什么, 谁在这么做]
rows:
  - 极致 POSIX 兼容: [
      "元数据强协调，跨地域延迟和扩展性受限",
      "单机房 NFS、企业级 NAS"
    ]
  - 海量文件 + 高并发: [
      "单目录的语义被弱化（禁止超大目录、限制 rename、限制锁）",
      "HDFS、大规模分布式文件系统"
    ]
  - 多地域低延迟: [
      "异步复制、最终一致，放弃部分操作的原子可见性",
      "跨地域的对象存储、CDN 源站"
    ]
  - 超大规模 + 超低成本: [
      { text: "整个目录模型和 POSIX 都不要了", tone: red },
      "对象存储（S3 / OSS / COS）"
    ]
```

```summary
title: 一句话
text: |
  文件的内容可以靠加机器近似线性扩容；
  但一旦要求「全局目录树 + 强一致元数据 + 跨目录原子操作」，
  系统就必须**一直**有人在回答「这个名字是谁的、现在在哪、别人看到的是不是一样」。

  ==那个「一直有人在回答」的成本，才是天花板。==
```

## 08 · 对象存储绕过了哪一条

回到这张表，对象存储的选择是最后一行的**全部四条都放弃**：

```compare
first: 它放弃的
head: [于是得到了什么]
rows:
  - 没有目录: ["只有 key 字符串，`photos/2024/a.jpg` 里的 `/` 是个普通字符；快就是真的快，不需要维护索引"]
  - 没有原子 rename: ["改名 = copy 到新 key + delete 旧 key，允许中间态 —— 因为对象本身不可变，不存在「改坏一半」"]
  - 没有文件锁: ["对象只能整块替换（PUT 覆盖整个对象），最后写入者赢，不存在「两个人同时改一个字节」"]
  - list 不用维护目录: ["前缀列举 = 按 key 字典序走一个扁平索引；没有「每个目录一份、改动必须原子生效」的结构要维护"]
```

```callout
tone: green
icon: 🪣
text: |
  结果是：真正需要「必须有一个人说了算」的东西，只剩下一件 —— **key 该落到哪个分片**。

  而这件事用哈希就能算：==谁算都是同一个答案，不需要问任何人。==

  这就是「扁平 key 空间可以无限打散」的全部含义，也是对象存储里那句
  「目录是查询期演出来的幻觉」的**代价的另一面**：
  你想拿到那棵树，就得有人一直维护它。
```

```quiz
- q: "为什么说「数据能靠加机器扩，元数据不能」？"
  a: |
    数据（真正的字节）可以在很多机器上各存一份，每一份都一样，复制不产生矛盾。
    名字和归属（谁叫什么、在哪个目录、权限是什么）只能有一个答案：
    同一个路径在两台机器上有不同说法，客户端就不知道该信谁。
    加机器只增加「存的地方」，不会让「谁是权威」这件事变简单。
- q: 一个目录里有 1 亿个文件，`ls -l` 为什么比 `ls` 慢一个数量级？
  a: |
    目录本身是一个文件，内容是一张「名字 → inode 号」的表。`ls` 只读这张表。
    `ls -l` 还要为每个文件去查它的 inode（大小、权限、时间），
    于是从「读一遍表」变成「读一遍表 + 1 亿次逐个查询」。
    这一亿次查询就是压向元数据节点的请求。
- q: "`rename` 为什么要加锁？不加锁会怎样？"
  a: |
    跨目录 rename 要改两张表（源目录删一行、目标目录加一行）。
    如果中间被别的客户端看见，就会有一段「两边都没有」的窗口 ——
    观察者会觉得文件凭空消失了。
    POSIX 要求外部只能看到「操作前」或「操作后」，所以必须把两张表在同一个持锁区间里改完。
- q: "为什么把目录拆成很多分片，`rename` 还是快不起来？"
  a: |
    因为分片解决的是「表太大」，不能解决「同名只能有一个」。
    只要还承诺强一致的目录语义，就一定有个地方要串行仲裁（跨分片时是分布式事务/两阶段提交）。
    拆开之后 `ls` 还要扇出到多个分片再合并、慢的那片决定整体时延。
    协调点只是从一张表换成了一套规则。
- q: "「跨机房后一致性成本指数级增长」—— 用一句人话说是什么？"
  a: |
    一次操作要几个网络来回，来回的时间由距离决定（光速下限）。
    锁要一直握到来回结束，所以距离越远，同一个目录每秒能完成的改名次数越少 ——
    同机房约 1600 次/秒，跨洲不到 3 次/秒。
    再叠上分层（目录、分片、副本、地域），每一层都要一轮协调，成本是一层乘一层上来的。
```

## 01 · 一个被跳过去的问题

前面每一段都在用「**就绪**」这个词：就绪表、就绪事件、这个 fd 就绪了。

那它到底在说什么？换个问法：

> **epoll 告诉你「这个 fd 可读」的时候，数据已经在你手里了吗？**

没有。==而「就绪」这个词的全部含义，就藏在「没有」这两个字里。==

---

## 02 · 数据是内核先收下来的

网卡收到包，不会直接塞进你的 `read` 返回值里。中间隔着一段**内核的缓冲区**。

```flow
grid: true
nodes:
  - { id: nic, label: "网卡收到包", sub: "中断把包交给内核协议栈", row: 0, tone: blue }
  - { id: stack, label: "协议栈处理", sub: "拆包、校验、按连接找到对应的 socket", row: 1, tone: violet }
  - { id: q, label: "socket 的接收队列", sub: "==数据停在这里，这是内核的内存==", row: 2, tone: amber }
  - { id: you, label: "你的 read 把它拷过来", sub: "这时数据才归你", row: 3, tone: green }
edges:
  - { from: nic, to: stack, label: "" }
  - { from: stack, to: q, label: "放进去" }
  - { from: q, to: you, label: "你来取" }
```

所以有两件完全不同的事：

| | 什么时候发生 | 谁在管 |
|---|---|---|
| **数据到了** | 包到达的那一刻 | 内核（你完全不知道） |
| **数据归你** | 你调 `read` 的那一刻 | 你 |

==epoll 夹在中间。它只负责通知第一件事，不负责第二件。==

---

## 03 · 「就绪」说的是状态，不是数据

把它翻译成一句人话：

> **就绪 = 现在去读，不会让你等。**

它承诺的是**「读这个动作立刻能有结果」**，不是「数据已经给了你」。这个区别看着小，但 `epoll` 最有名的两个触发模式争的就是它。

## 04 · LT 和 ET 争的是一件事

```demo
  total: 128
  chunk: 64
```

**建议按这个顺序点**（切模式后会自动重置日志）：

```cards
cols: 1
items:
  - title: "LT 下：点「网卡来数据了」→「epoll_wait()」→「read 一次」→ 再点「epoll_wait()」"
    tone: blue
    body: |
      ==第二次 `epoll_wait` 还是会返回这个 fd==，因为缓冲区里还剩一半，
      内核在把 fd 从就绪表摘下来之后，一看还有数据，又把它挂了回去。
      所以 LT 下**你一次只读一点也没关系**，剩下的下次再说。
  - title: "ET 下：同样四步"
    tone: red
    body: |
      ==第二次 `epoll_wait` 返回 0==，而缓冲区里明明白白还剩 64 字节。
      看那条红色的日志和底下那行警告：**你的线程在 epoll_wait 上睡得很安稳，那份数据没人管。**
      这就是 ET 下最经典的 bug，而且它不会报错，只会「卡住」。
  - title: "怎么避免：ET 必须读到 EAGAIN"
    tone: green
    body: |
      ET 只在「从空变成非空」那一刻通知一次。既然不会有第二次通知，
      你就得**一次把它读干净**，循环 `read` 直到返回 `EAGAIN`。
      点「read 到空」再点 `epoll_wait`，两种模式的表现就一样了。
```

## 05 · 所以 ET 必须配非阻塞

这里有个连环：

```flow
grid: true
groups:
  - { id: chain, label: "ET 的三步连环，缺一环就出事", tone: red }
nodes:
  - { id: a, label: "ET 不重复通知", sub: "只在状态变化那一刻叫你一次", row: 0, tone: amber, group: chain }
  - { id: b, label: "所以你得读到 EAGAIN", sub: "一直读，读到「这会儿真没有了」为止", row: 1, tone: amber, group: chain }
  - { id: c, label: "那次 read 必须能立刻返回", sub: "==如果 fd 是阻塞的，它就会卡在那次 read 上==", row: 2, tone: red, group: chain }
  - { id: d, label: "于是永远回不到 epoll_wait", sub: "整个事件循环停了，一个连接把所有人拖死", row: 3, tone: red, group: chain }
edges:
  - { from: a, to: b, label: "" }
  - { from: b, to: c, label: "" }
  - { from: c, to: d, label: "" }
```

!!这就是「ET 必须配 `O_NONBLOCK`」的完整理由。!! 它不是一条编码规约，是这条链上推出来的必然结果。

```callout
tone: amber
icon: ⚖
text: |
  **反过来不成立**：LT 下非阻塞不是严格必需的。

  因为 LT 每次都会告诉你「还有数据」，你一次读一点、读不完就下次再说，
  不会出现「必须读到 EAGAIN」这个要求。所以 LT + 阻塞 fd 也能跑 ——
  前提是所有 I/O 都听 `epoll_wait` 的指示，别自己乱读。

  ==很多文章把「必须非阻塞」说成对 LT/ET 都成立，那是记错了。==
```

## 06 · 内核里其实就是「摘下来之后要不要放回去」

LT 和 ET 这两个名字（水平 / 边缘）听着很玄，但内核实现里只有一句判断。

`epoll_wait` 返回事件的时候，做的是这么几件事：

```flow
grid: true
nodes:
  - { id: pop, label: "① 把 fd 从就绪表摘下来", sub: "这时候它已经不在表里了", row: 0, tone: blue }
  - { id: copy, label: "② 把事件拷到用户态", sub: "这一步 LT 和 ET 一模一样", row: 1, tone: blue }
  - { id: chk, label: "③ 看一眼模式，再看一眼缓冲区", sub: "==全部差别就在这一步==", row: 2, tone: violet }
  - { id: lt, label: "LT：还有数据？挂回去", sub: "所以下次还会通知你", row: 3, tone: green }
  - { id: et, label: "ET：不挂", sub: "除非有新事件来把回调再触发一次", row: 3, tone: red }
edges:
  - { from: pop, to: copy, label: "" }
  - { from: copy, to: chk, label: "" }
  - { from: chk, to: lt, label: "水平触发" }
  - { from: chk, to: et, label: "边缘触发" }
```

!!所以：**「水平/边缘」这两个名字描述的是「什么时候触发」，但实现上真正发生的事是「摘下来之后要不要放回去」。**!!

记住后半句，这两个模式就再也不需要背了，你能自己推出来：

- 放回去 → 只要还有数据就一直叫你 → **水平触发**
- 不放 → 只有状态变化时才叫你 → **边缘触发**

## 07 · 一个反例，把「就绪」说透

`epoll_ctl` 想登记一个**普通文件**，会直接失败，返回 `EPERM`。

为什么？==因为普通文件**永远都是"就绪"的**。==

```compare
first: fd 类型
head: [它会不会「等」, epoll 拿它怎么办]
rows:
  - socket / 管道: ["会。数据什么时候来不由你定", "这正是 epoll 存在的意义：==替你等==、等到了叫你"]
  - 普通文件: [{ text: "不会。磁盘上的数据就在那，随时可读", tone: red }, "「就绪」这个概念对它没有意义，所以内核直接拒绝"]
```

所以 epoll 的能力边界，反过来正好定义了「就绪」：

> **就绪 = 这个操作有可能要等，而现在不用等了。**

普通文件永远不会等，所以它从不「就绪」，也就不需要谁去通知你。这也是为什么 epoll 解决不了磁盘 I/O：**它管的是「等」，不是「慢」。**

---

## 08 · 于是它仍然是同步 I/O

回到开头那个问题：数据在你手里吗？**没有。**

epoll 只做到「告诉你现在读不会卡」，==而**把数据从内核缓冲区拷到你自己的内存**这件事，还是你的线程亲自做的==。第二步的等待（拷贝那一段）一点没省掉。

这就是 `fs-io-models` 里那句话的机制版本：

> 同步 / 异步的分界线，是**「拷贝那一段要不要你等」**。epoll 属于前者。

想要连拷贝都不等，得换一个模型，那是这个系列最后一篇的事。

---

```quiz
- q: epoll 说「这个 fd 可读」的时候，数据在哪里？
  a: |
    在**内核的接收缓冲区**里（socket 的接收队列），还没到你的手上。
    「就绪」说的是状态，不是数据，它承诺的是「现在去读不会让你等」，
    而不是「数据已经给你了」。数据归你，是在你调 read 那一刻才发生的。
- q: LT 和 ET 的差别，用一句实现层面的话怎么说？
  a: |
    epoll_wait 返回事件时，会把 fd 从就绪表里**摘下来**，把事件拷到用户态，
    然后看一眼模式：
    LT 如果发现缓冲区还有数据，就**把它挂回就绪表**，下次还会通知你；
    ET 不挂，除非有新事件把回调再触发一次。
    所以「水平/边缘」这两个名字描述的是触发时机，
    真正的机制是「摘下来之后要不要放回去」。
- q: ET 为什么必须配非阻塞 fd？
  a: |
    因为 ET 不会重复通知，所以你必须一次读到 EAGAIN；
    而读到 EAGAIN 意味着最后一次 read 会走「没有数据」这条路径 ——
    如果 fd 是阻塞的，那次 read 会**卡住**，线程永远回不到 epoll_wait，
    整个事件循环就被一个连接拖死了。
    反过来 LT 下非阻塞不是严格必需的，因为它每次都还会再通知你。
- q: 为什么 epoll 不能用来监视普通文件？
  a: |
    因为普通文件永远都是「就绪」的，它不会等，数据就在那随时可读。
    epoll_ctl 登记普通文件会直接返回 EPERM。
    这反过来正好定义了「就绪」：这个操作有可能要等，而现在不用等了。
    普通文件从不「就绪」，也就不需要谁去通知你。
- q: 既然有 epoll，为什么说它仍然是同步 I/O？
  a: |
    因为 epoll 只负责通知「现在读不会卡」，
    把数据从内核缓冲区拷到你自己的内存，还是你的线程亲自做的。
    拷贝那一段的等待一点没省掉。同步/异步的分界线就是
    「拷贝那一段要不要你等」——epoll 属于要等的那一边。
```

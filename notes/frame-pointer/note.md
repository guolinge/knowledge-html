## 01 · 三个东西先分开：栈帧、栈顶、帧基址

上一篇讲完了一次调用在栈上占的那一段，那一段叫**栈帧**（stack frame）。这里只讲其中一根指针：**帧基址**（frame base），也叫**帧指针**（frame pointer）。x86 上它是 `RBP`，AArch64 上它是 `x29`。

一句话定义：==帧基址是这一帧里一个**不动的地址**，局部变量、返回地址、上一帧都按它加偏移去找==。因为它不动，函数体里 `RSP` 怎么变都不影响这些查找。

先把三个容易混的东西并排放好：

```compare
first: 看什么
head: [栈帧 stack frame, 栈顶 RSP / SP, 帧基址 RBP / x29]
rows:
  - 是什么: [一次调用占的那整段内存, 现在用到哪一格, 这一帧的固定原点]
  - 会不会动: [调用时整段出现，返回时整段消失, 函数体里一直在动, 序言之后基本不动]
  - 谁在管: [编译器排的布局, "`push` / `pop` / `sub` / `call`", "序言里的一条 `mov`"]
  - 拿它算什么: [装返回地址、旧帧、局部变量, 下一次压栈往哪写, 局部变量和旧帧的固定偏移]
```

后两个的差别，在真机上停一下就看得见。x86-64 的 `calc` 停在 `callq _add` 之前（lldb 实测）：

| 东西 | 值 | 和 RBP 的关系 |
|---|---|---|
| `RBP` | `0x30413cfa0` | 原点 |
| `RSP` | `0x30413cf90` | `RBP - 0x10`（`sub rsp,0x10` 腾出来的） |
| `&x`（参数） | `0x30413cf9c` | `RBP - 4` |
| `&s`（局部变量） | `0x30413cf98` | `RBP - 8` |
| `[RBP]` 那一格 | `0x30413cfc0` | main 的帧底（旧 RBP） |
| `[RBP+8]` 那一格 | `0x1000003a9` | main 里 `callq _calc` 的下一条 |

`RSP` 比 `RBP` 低 16 字节，局部变量全落在 `RBP` 下面，而返回地址和旧帧底在它上面。==`RBP` 不是这一帧的边界，它是一个原点==：往下是自己的东西，往上是调用者的东西。

```memmap
  - { label: 旧的 RBP, sub: "0x30413cfc0 —— push rbp 压的", tone: violet, size: 1.2, mark: "RBP+0 · RBP 指这" }
  - { label: 局部变量 int x、int s, sub: "0x30413cf9c 和 0x30413cf98", tone: amber, size: 1.4, mark: "RBP-4 / RBP-8" }
  - { label: 腾出来没用上的 8 字节, sub: "sub rsp, 0x10 给了 16 字节，两个 int 只用掉 8", tone: muted, size: 0.9, mark: "RBP-8 以下" }
  - { label: 当前栈顶, sub: "0x30413cf90 —— 下一次压栈写这里", tone: green, size: 0.9, mark: "RBP-0x10 = RSP" }

```

刻度不是随便定的，来源得分开说：

| 偏移 | 里面是什么 | 谁定的 |
|---|---|---|
| `RBP+16` 起 | 第 7 个及以后的整数参数（`+16`、`+24`、`+32` …） | **ABI 定的**。前 6 个走寄存器（`rdi` `rsi` `rdx` `rcx` `r8` `r9`），多出来的按顺序摆在返回地址之上 |
| `RBP+8` | 返回地址 | **ABI 定的**。`call` 压的，所以它永远紧贴 `RBP+8` |
| `RBP+0` | 上一帧的 `RBP` | **序言定的**。`push rbp` 压的，`mov rbp,rsp` 让 `RBP` 正好落回来 |
| `RBP-4`、`RBP-8` … | 局部变量、保存的寄存器、临时数据 | **编译器自己排的**，不同函数、不同优化级别都不一样 |

前两行可以验：写一个 8 参数函数，第 7、8 个参数就出现在 `16(%rbp)` 和 `24(%rbp)`（本机 `clang -O0` 反汇编）：

```text
_many:
0x100000340  pushq  %rbp
0x100000341  movq   %rsp, %rbp            ; RBP 钉好
0x100000344  movl   0x18(%rbp), %eax      ; 第 8 个参数 h
0x100000347  movl   0x10(%rbp), %eax      ; 第 7 个参数 g
0x10000034a  movl   %edi, -0x4(%rbp)      ; a —— 前 6 个从寄存器抄下来
0x10000034d  movl   %esi, -0x8(%rbp)      ; b
…
```

## 03 · 序言：三条指令把原点钉下来

`RBP` 落地只需要三条指令（x86-64，本机 `clang -O0`）：

```text
0x100000360  pushq  %rbp        ; 把调用者的帧底压栈：RSP -= 8，[RSP] = 旧 RBP
0x100000361  movq   %rsp, %rbp  ; RBP = RSP —— 正好指到刚写的那一格
0x100000364  subq   $0x10, %rsp ; 往下腾局部变量区；RBP 不动
```

关键在第三步之后：==`RBP` 指的那一格装的是「旧 RBP」，不是返回地址==。返回地址在它上面一格，因为 `call` 比 `push rbp` 先发生。

AArch64 上做同一件事，只是把「旧帧指针 + 返回地址」合成一次存储：

```text
_calc:
0x100000348  sub  sp, sp, #0x20          ; 腾 32 字节
0x10000034c  stp  x29, x30, [sp, #0x10]  ; [sp+0x10]=旧 fp，[sp+0x18]=返回地址
0x100000350  add  x29, sp, #0x10         ; x29 = sp+0x10，正好指向那两格的第一格
…
```

所以两个架构的帧头布局是一样的：`[FP]` 是上一帧的帧指针，`[FP+8]` 是返回地址。这也是为什么调试器可以只认这一个规律，就跨架构回溯。

### 别看见 push rbp 就说「用了帧指针」

`rbp` 和 `x29` 都是**被调用者负责保存**的寄存器（callee-saved）。函数要借用它们，就得先存起来；存了不等于拿它当帧指针用。判别看后半句：

| 架构 | 只保存了寄存器 | 真的当帧指针用 |
|---|---|---|
| x86-64 | `pushq %rbp` | `pushq %rbp` **加** `movq %rsp, %rbp` |
| AArch64 | `stp x29, x30, [sp, #16]` | 再加一条 `add x29, sp, #16` |

本机实测的反例：AArch64 加 `-fomit-frame-pointer` 编译后，`stp x29, x30` 仍然在（`x29` 必须保存），但 `add x29, sp, #16` 没了 —— 那才是帧指针。

## 04 · 尾声：把原点还回去，一整轮就闭合了

```text
0x100000380  addq  $0x10, %rsp   ; 撤掉局部变量区
0x100000384  popq  %rbp          ; 还原调用者的帧底
0x100000385  retq                ; 弹出返回地址，跳回去
```

如果序言用的是 `push rbp; mov rbp,rsp; sub rsp,N`，尾声可以缩成两条：

```text
leave   ; = mov rsp, rbp  然后  pop rbp
ret
```

`mov rsp, rbp` 一句话就把 `RSP` 拉回帧底，中间那些局部变量**不用清理**：内存里的旧值还在，但已经没人认领了，下一次压栈会盖掉它。==「释放」在这里只改一个指针，不动内存。==

序言和尾声分开看还是两段。把一整轮连起来走一遍，才看得清两个指针是怎么互相「铺路」的：右边两条通道各放一个标记，`SP` 是 `RSP`，`BP` 是 `RBP`，它们只在两步里站到同一行。


看的时候盯三处：

- **第 3 步**：`RBP ← RSP`。这一刻两个标记落在同一行，之后 `RSP` 怎么走，`RBP` 都不再跟。
- **第 8 步**：`RSP` 加回 `0x10`，正好落回 `RBP` 那一行 —— 尾声靠的是「编译器记得 `sub` 了多少」，不是靠 `RBP`。
- **第 9 步**：`RBP ← [RSP]`，把序言存进去的 main 帧底取回来。如果编译器用 `leave`，第 8、9 步就是一条指令。

## 05 · 顺着 RBP 链往上走，就是调用栈

每一帧的第一格都存着上一帧的 `RBP`，于是这些格子串成一条链。回溯只需要重复两步：

1. 读 `[FP]` → 上一帧的帧指针
2. 读 `[FP+8]` → 这一帧的返回地址，也就是「谁调了我」

本机实测（AArch64，停在 `calc` 里），顺着链走三跳：

```text
calc 的 fp = 0x16fdfef40
  [0x16fdfef40] = 0x16fdfef60   ← main 的 fp
  [0x16fdfef48] = 0x100000394   ← 返回地址：main 里 bl _calc 的下一条

main 的 fp = 0x16fdfef60
  [0x16fdfef60] = 0x16fdff5c0   ← dyld 的 start 的 fp
  [0x16fdfef68] = 0x18e5e04e4   ← 返回地址：dyld 里调 main 之后

dyld 的 fp = 0x16fdff5c0
  [0x16fdff5c0] = 0              ← 链到头
```

最后那个 `0` 是**约定的链尾**（AAPCS64 明写：上一帧地址为 0 表示链结束；x86-64 的 ABI 同样要求最外层把帧指针置 0）。lldb 的 `bt` 打出来的就是同一条链：

```text
(lldb) bt
* frame #0: 0x0000000100000358 demo-arm64`calc(x=10) at demo.c:4:17
  frame #1: 0x0000000100000394 demo-arm64`main at demo.c:9:13
  frame #2: 0x000000018e5e04e4 dyld`start + 6992
```

这条链就是「崩溃时看到的调用栈」和「性能剖析里的火焰图」的数据来源。代价是每个函数都多占一格存旧帧指针，再花两条指令维护它 —— 这正好引出下一节：什么时候值得。

## 06 · 什么时候真的需要它

教材里的说法通常是「`RSP` 会因为压栈出栈不断变化，所以按 `RSP` 算偏移不可靠」。这句话对了一半，真机上的情况更细。

`call` 返回之后 `RSP` 会复原，编译器在每一刻都清楚「`RSP` 离帧底多远」，所以它完全可以用 `RSP` 偏移。本机实测的几组编译组合：

| 平台 / 选项 | 有没有帧指针 | 局部变量怎么寻址 |
|---|---|---|
| Darwin x86-64 `-O0` | 有（`push rbp` + `mov rbp,rsp`） | `-4(%rbp)`、`-8(%rbp)` |
| Darwin x86-64 `-O2` | 有（Apple 工具链默认保留） | `-16(%rbp)`、`-20(%rbp)` |
| Darwin x86-64 `-O2 -fomit-frame-pointer` | 无 | `(%rsp)`、`12(%rsp)` |
| Linux x86-64 `-O2` | 无（默认就省） | `(%rsp)`、`12(%rsp)` |
| Darwin arm64 `-O2` | 有（`add x29, sp, #32`） | **仍然是** `[sp, #12]`、`[sp, #8]` |

最后一行最值得看：帧指针明明维护好了，编译器还是拿 `SP` 去寻址局部变量 —— 因为这一帧大小是编译期固定的，用 `SP` 算更省事。==帧指针在不在，和用不用它寻址，是两件事。==

真正把它逼回来的，是**运行时才知道帧有多大的情况**。加一个变长数组再看：

```c
int vla(int n) {
    int a[n];
    for (int i = 0; i < n; i++) a[i] = i;
    g();
    return a[n - 1];
}
```

即使显式加了 `-fomit-frame-pointer`，本机 `clang -O2 -arch arm64` 编出来的 `_vla` 里还是有这一行：

```text
_vla:
    stp  x20, x19, [sp, #-32]!
    stp  x29, x30, [sp, #16]
    add  x29, sp, #16          ; ← 帧指针被逼回来了
    sub  sp, sp, #16
    …
    stur x8, [x29, #-24]       ; 栈保护用的 canary，也只能按 x29 定位
```

帧的大小随 `n` 变，`RSP` 在函数体里被动态改过，编译器没法再用一个固定偏移找局部变量 —— 只能先钉一个不会动的原点。

```compare
first: 对比项
head: [有帧指针, 省略帧指针（FPO）]
rows:
  - 局部变量寻址: [用固定偏移找局部变量，读汇编好跟, 全按 `RSP` 偏移，靠编译器记账]
  - 变长数组 / `alloca`: [直接支持, 要么被强制打开，要么另找寄存器存帧底]
  - 回溯调用栈: ["读 `[FP]` 链，一步一帧", "解析 `.eh_frame` / DWARF 表（编译器留下的「每一刻帧多大」的元数据），慢一些"]
  - 占用寄存器: [少一个通用寄存器, 多一个可用寄存器]
  - 典型默认: ["Darwin 默认保留；Linux x86-64 默认省略", "`-O1` 以上常见"]
```

所以「需要帧指针」有三种不同的理由，别混着说：

- **编译器需要**：变长栈分配、`alloca`、某些需要精确定位的调试/插桩特性。
- **工具需要**：崩溃栈、性能剖析、调试器 —— 有它就省掉解析 unwind 表。
- **人需要**：读汇编时有个不动的锚点，心理负担小很多。

## 07 · 速查：容易记反的六件事

```checklist
tone: cross
items:
  - "`RBP` 指向返回地址。—— 返回地址在 `RBP+8`；`RBP` 指的那格是旧的帧指针。"
  - "`RBP` 是这一帧的最低地址。—— 那是 `RSP`；`RBP` 在帧里偏上的位置。"
  - "局部变量固定在 `RBP-4`、`RBP-8`。—— 偏移是编译器排的，存个 callee-saved 寄存器就会挪。"
  - "看见 `push rbp` 就说明用了帧指针。—— 还要看有没有 `mov rbp, rsp`；`x29` 同理，看 `add x29, sp, #N`。"
  - "没有 `RBP` 就没有栈帧。—— 帧还在，只是没有固定原点，寻址全靠 `RSP` 加编译期记账。"
  - "顺着 `[RBP]` 能一直走到程序入口。—— 链尾是 0，到 0 就停。"
```

```summary
title: 一句话
text: |
  `RBP` 是这一帧的**原点**：`+8` 是返回地址、`+0` 是上一帧、负偏移是自己的局部变量。
  它不动，所以局部变量和回溯都有一个稳定参照；`RSP` 会动，管的是「下一次往哪写」。
```

```quiz
- q: "`RBP` 指向的那一格里，装的是什么？"
  a: |
    调用者的帧指针（旧 `RBP`）。它由序言的 `push rbp` 压进去，`mov rbp,rsp` 让 `RBP` 正好落在这一格。
    返回地址在它上面一格（`RBP+8`），是更早的 `call` 压的。

  a: |

  a: |
    因为这一帧的大小在编译期就固定了，`RSP` 到帧底的距离每一刻都已知，用 `SP` 寻址同样稳，还省一条指令。
    只有在栈大小运行期才确定（变长数组、`alloca`）时，编译器才必须依赖帧指针。
```

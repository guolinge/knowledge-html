01一个真实的场景

先忘掉代码。

运营要发一张优惠券，只发给「最近 7 天加购过、并且是 VIP」的用户。

这句话要落地，系统必须回答一个问题：这批人是谁？

数据长这样：

用户 1001  最近 7 天加购过 3 次，VIP 等级 3   →  要发
用户 1002  最近 7 天没加购，VIP 等级 5        →  不发（没加购）
用户 1003  最近 7 天加购过 1 次，不是 VIP      →  不发（不是 VIP）
用户 1004  最近 7 天加购过 8 次，VIP 等级 4   →  要发

要找出这批人，得去数据库里查。这件事就叫「圈人」。

🎯

圈人 = 按一组条件，从数据里筛出符合条件的用户 ID 列表。

数据散在两个地方

「最近 7 天加购过」和「是 VIP」看着像一句话，其实查的是两张完全不同的表：

「加购过」  →  事件表：行为流水，用户做过什么
「是 VIP」  →  画像表：静态属性，用户现在是什么样

要回答「最近 7 天加购过并且是 VIP」，就得把两张表的结果接起来：

事件表 → 查出「最近 7 天加购过的人」→ 一批 uid
画像表 → 查出「VIP 等级 ≥ 3 的人」 → 一批 uid
两批 uid 取交集                                → 最终答案

那为什么不直接让运营写 SQL

人不对

运营不会写 SQL

业务侧是产品和运营，不是工程师。让他们写 join 和 group by 不现实

明天还要跑

口径要能复用

同一批人明天还要圈一次。不能每次重写一段 SQL，而且两次口径可能不一致

安全

要防注入

条件里的值是外部传进来的。直接拼字符串会被 ' OR '1'='1 改写条件

兼容

要跑在两个库上

同一句话，Doris 和 ByteHouse 的函数名、表结构都不一样

💡

所以需要一层中间物：用业务语言描述「要什么人」，由它生成 SQL。

「条件」就是这层描述的基本单位。

02原料：圈人用的四种东西

上面那句话里出现了「加购」和「VIP」。它们是两类不同的原料，但系统里一共有 4 种。

每个都配真实数据 —— 看不懂定义就看数据。

uid —— 用户的唯一标识

一串代表「一个人」的编号。系统里到处用它把数据串起来。

1001

有个细节：uid 在库里是加密存储的。所以写 SQL 时会出现两个函数：

UID_ENCODE(1001)    -- 查询时：把明文 uid 加密，拿去跟库里的值比对
UID_DECODE(`uid`)   -- 取出时：把加密的 uid 解密，给业务用

画像 —— 用户的「静态属性」

描述用户现在是什么样。一行 = 一个人。

uid   | city | vip_level | 开户时间
------|------|-----------|------------
1001  | 杭州 | 3         | 2020-01-01
1002  | 深圳 | 5         | 2021-06-15
⚠

关键特征：会被覆盖，只存当前值。

用户今天改成 VIP 4，昨天是 VIP 3 这件事就没了 —— 所以画像回答不了「他以前是不是 VIP」。

事件 —— 用户的「行为流水」

描述用户做过什么。一行 = 一个人 + 一个时刻 + 一个动作。

uid   | event_type | event_time   | 商品
------|------------|--------------|------
1001  | 加购       | 10:03:12     | A001
1001  | 加购       | 15:20:41     | B007
1001  | 下单       | 15:31:08     | B007
1004  | 加购       | 09:12:33     | A001
✅

关键特征：只追加，不覆盖。

因为是流水账，所以能回答「最近 7 天加购了几次」—— 画像表永远回答不了这种问题。

人群包 —— 预先算好的一批人

运营今天圈了一批人，明天还想用同一批。于是把结果存下来，给个编号。

crowd_id | crowd_version | uid
---------|---------------|------
C_888    | v3            | 1001
C_888    | v3            | 1002
C_888    | v3            | 1004

crowd_version 是版本号 —— 同一批人重新算一遍结果可能变，所以要用版本区分「当时那批人」。

四种原料对比

原料回答什么问题一行代表什么会变吗
uid这是谁一个人不变
画像他现在是什么样一个人的所有属性会被覆盖
事件他做过什么、几次一个人某一刻的一个动作只追加
人群包预先算好的一批人是谁人群包 + 版本 + 一个人只追加
💡

「只追加」和「会被覆盖」这一条差别，比看起来重要得多。

它决定了你能问什么问题：

  • 想「几次」「最近 N 天」→ 只能问事件
  • 想「现在是多少」→ 问画像

后面写条件的时候，选错原料是最常见的错误来源。

03表达：条件与条件树

一个条件由什么构成

把「最近 7 天加购过」和「是 VIP」拆开看，它们是同一种结构：

拆开看「最近 7 天加购过」「是 VIP」
判断对象事件「加购」画像属性 vip_level
判断方式次数 > 0>=
判断值—3
额外限定最近 7 天—

共同点：都是「对某个东西做一个判断」。

为什么必须是树

因为业务说的是：

「最近 7 天加购过，并且是 VIP」           → 并且（叶子, 叶子）
「最近 7 天加购过，或者是 VIP」           → 或者（叶子, 叶子）
「（加购过 或 下单过）并且是 VIP」         → 并且（或者（叶子,叶子）, 叶子）
⚠

最后那个例子说明为什么必须是树，不能是一个平铺的列表。

「或者」可以出现在「并且」里面。平铺列表表达不了这种嵌套。

AND 顶层
OR 子树枝
是 VIP 叶子
加购过 叶子
下单过 叶子

树只有两种节点：

逻辑

树枝

用 logic + items 把条件串起来。业务说的「并且」「或者」就是它

{ logic: 'AND', items: [ ... ] }
一个判断

叶子

最小的条件单元。对某个东西做一次判断

{ op: 'IN', name: 'city', value: ['杭州'] }
💡

所有复杂度都来自「树枝可以套树枝」，没有别的。

六种叶子

上面例子里出现了「事件」和「画像」。系统一共支持 6 种叶子，这是这个库的词汇表：

静态

画像

用户的静态属性。最常用

行为

事件

做过什么事、几次。功能最多、最复杂的一个

复用

人群包

预先算好的一批人。可复用

最简单

uid

直接给一批用户 ID，不查表。常用于「这批人再加上…」

按对象

关系

用户和某个对象的关系。比如「领过这张券的人」

兜底

rawSql

直接塞一段 SQL。逃生口，前五种表达不了时用

为什么正好是六种？ 因为「判断对象」的来源只有这六类：

  • 判断对象的来源 六种叶子，各查各的表
    • 画像 一个人现在是什么样
    • 事件 一个人做过什么
    • 人群包 预先算好的一批人
    • uid 直接给的 ID，不查表
    • 关系 一个人和某个对象的关系
    • rawSql 兜底：直接给 SQL

04两套词汇

这是读后面几篇最容易懵的地方。

同一棵条件树，业务侧和底层用两套词汇描述。

同一个条件业务条件（业务侧写的）Rule[]（底层认的）
属性叫什么namecolumn
例子{ op: 'IN', name: 'city', value: ['杭州'] }{ op: 'IN', column: 'city', value: ['杭州'] }
时间条件用 dateType 描述，如「最近 3 天」展开成多个条件
逻辑组合logic + itemslogic + items（一样）
💡

看出来了吗？两套写法长得几乎一样，主要差别是属性名（name → column）。

这不是巧合：它们用的是同一个树形结构，只是词汇表不同。 所以翻译起来很轻 —— 大部分节点直接透传，只有业务独有的词汇需要改写。

为什么要有两套

因为两边的关注点不同：

关心「要什么人」

业务条件

用业务词汇。时间写「最近 3 天」、属性写业务名。人能读懂、能复用、能存进配置

{ op: 'Gte', name: '开户时间',
  dateType: 'Relative', value: 3 }
关心「怎么写 SQL」

Rule[]

用 SQL 词汇。属性是列名、时间已经展开成具体比较。纯数据，没有任何业务概念

[ { logic: 'AND', items: [
    { op: 'Gte', column: '..._time', value: 开始 },
    { op: 'Lte', column: '..._time', value: 结束 }
]} ]
✅

这样分层换来的是：底层完全不需要知道「什么是相对时间」。

它只认「一个列、一个操作符、一个值」。 所以换一种业务场景时，底层一行都不用改。

中间的三样东西

两套词汇之间有三个词要认：

翻译器

adapter

把业务条件翻译成 Rule[] 的那个环节。它知道业务，底层不知道

输入: { op: 'Gte', name: '开户时间',
        dateType: 'Relative', value: 3 }
输出: 一棵 AND 子树（两个比较）
六种

entrepot

「条件入口」。六种叶子各有一个实现，每种知道自己该去哪张表、怎么写查询

画像   → 查画像表
事件   → 查事件表
人群包 → 查人群包表
uid    → 不查表
关系   → 查业务明细表
rawSql → 透传
库差异

方言

同一个语义在不同数据库怎么写。因为要同时跑在两个库上

取 map 里的一个 key：
  ByteHouse → mapElement(`name`, 'a')
  Doris     → ELEMENT_AT(`name`, 'a')

还有两个词

两个数据库

ByteHouse / Doris

这套代码要同时在两个数据库上跑。同名函数写法不同，这就是「方言」存在的原因

业务说法

圈人 / 用户域

「圈人」是业务说法，「用户域」是数据侧的说法。指的是同一件事

⚠

有个词容易混：crowd 有两个意思。

  • 一个意思是包名，指整个用户域业务包
  • 一个意思是一种条件类型，指上面那个「人群包」

看到它先看上下文：说包的时候是前者，说条件类型的时候是后者。

05一句话串起来

到这里，所有词都能串成一条线了：

业务侧 一句话需求 
「最近 7 天加购过，并且是 VIP」

运营用业务语言描述要什么人。

写成人能读懂、能存进配置
业务侧 条件树 业务词汇 
AND
├── 事件：加购，最近 7 天，≥ 1 次
└── 画像：vip_level ≥ 3

叶子是六种条件之一，树枝是 AND / OR。 用业务词汇：属性叫 name，时间写「最近 7 天」。

adapter 翻译业务词汇 → SQL 词汇
底层 Rule[] SQL 词汇 
AND
├── 子查询：事件表 group by uid having count ≥ 1
└── 画像表 where vip_level >= 3

时间已经展开成具体的比较了。 这里没有任何业务概念，只有列名、操作符、值。

底层 编译遇到库差异就调方言
数据库 一段 SQL 文本 
select `uid` from `画像表` as `t1`
left join ( ... ) as `t2` on `t1`.`uid` = `t2`.`$user_id`
where ...

数据库只认文本，不认对象、不认函数。 翻译到这里就结束了。

⚠

上面那段 SQL 里藏了一个坑：t1.uid = t2.$user_id。

画像表的用户列叫 uid，事件表的叫 $user_id —— 同一个东西，两个名字。 所以事件条件必须多做一次 join 把两边接起来。

这不是设计失误，是两个系统各自的历史遗留。现在只要记住： 看到 $user_id 就知道那是事件表的用户列。

所以这个库到底在做什么：

⚙

输入一棵条件树（业务语言），输出一段 SQL（数据库语言）。

06自测

「最近 7 天加购过」和「是 VIP」这两件事，为什么要分开处理？

因为它们的数据在两张不同的表里，而且性质不同： 「加购过」在事件表（行为流水，只追加，能回答「几次」）； 「是 VIP」在画像表（静态属性，会被覆盖，只存当前值）。 要回答「并且」，就得把两张表的结果接起来（取交集）。

为什么条件必须是「树」，不能是一个平铺的列表？

因为「或者」可以出现在「并且」里面。 「（加购过 或 下单过）并且是 VIP」这种语义，平铺列表表达不了。 树只有两种节点：logic + items（树枝）和叶子，树枝可以套树枝。

「画像」和「事件」最关键的区别是什么？这个区别决定了什么？

画像会被覆盖，事件只追加。 这决定了你能问什么问题：想「几次」「最近 N 天」只能问事件； 想「现在是多少」问画像。选错原料是最常见的错误来源。

为什么要有「业务条件」和「Rule[]」两套词汇？

因为两边关注点不同。业务条件关心「要什么人」，用业务词汇（时间写「最近 3 天」）， 人能读懂、能复用；Rule[] 关心「怎么写 SQL」，只有列名和操作符，没有业务概念。 这样分层换来的是：底层完全不需要知道「什么是相对时间」， 换业务场景时底层一行都不用改。

六种条件叶子为什么正好是六种？

因为「判断对象」的来源只有六类：一个人的属性（画像）、行为（事件）、 预先算好的一批人（人群包）、直接给的 ID（uid）、 和某个对象的关系（关系），以及兜底（rawSql）。 每种都知道自己该去哪张表。

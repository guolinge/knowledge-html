01一行代码要跑起来，中间隔了什么

先看一个具体的东西。你在终端敲下：

$ python train.py --epochs 30

回车之后，它开始吃 1.2 GB 内存、打开 3 个数据文件、占满一个 CPU 核。这时候你在另一个窗口敲 ps，会看到它：

  PID TTY      TIME CMD
 8412 pts/3  00:12:37 python

这一行就是一个进程：一个正在运行的程序。

程序本身只是个文件，躺在硬盘上，不占 CPU、不占内存、也不会自己变。只有当操作系统把它装载进内存、CPU 开始执行里面的指令，它才成为一个进程。

python 可执行文件 硬盘上的一份文件，4.2 MB
运行它 装载进内存，CPU 开始执行指令
进程 8412 吃 1.2 GB · 开着 3 个文件
进程 8413 同一份代码，另一份数据
进程 9021 只是在看 --help

同一个文件可以同时跑出好几个进程，而文件本身一动不动。 用做饭打个比方：菜谱是程序，食材是数据，照着菜谱做菜这件事才是进程。同一份菜谱，三个人同时各做一份。

CPU 为什么不能干等

假设有一段代码要「从硬盘读一个 500 MB 的文件」。硬盘读完要几百毫秒，而 CPU 执行一条指令是纳秒级，这两件事差了八个数量级。CPU 要是在这几百毫秒里干等着，那它 99.99% 的时间都在发呆。

所以操作系统不让它等：

进程 A要读那 500 MB
CPU只有一个
硬盘慢六个数量级
进程 B就绪队列里的另一个
1read(fd, buf, 500MB)
2把请求交给硬盘
3不等了，转去跑 B
4数据好了：发一个中断
5A 被唤醒，接着上次往下跑

第 4 步那条中断，是整个机制的关键。 没有它，CPU 就只能隔一会儿去问一次硬盘「好了没」，也就是轮询。

做法CPU 在等硬盘时干什么代价
轮询反复去读设备的状态寄存器，问「好了没」CPU 被白白烧掉，但它实现简单
中断驱动把请求交出去，转头去干别的多了一套中断机制和对应的硬件支持

烧水的类比很贴切：你不会站在水壶前面盯着它烧开，而是先去干别的，听到「嘀」的一声再回来倒水。那声「嘀」就是中断。

从轮询换成中断，花了十几年

1950s 中期

中断机制出现

UNIVAC 1103 / 1103A 和 NBS 的 DYSEAC 都被算作早期实现，「谁是第一台」至今有争议

1958

IBM 709 用上 DMA

数据在设备和内存之间直接搬，CPU 连「搬」这个动作都不参与了

1964

CDC 6600 对 I/O 仍然用轮询

当时最快的机器之一，却没走这条路

最后一行的意思很明确：中断不是一夜之间取代轮询的，两套办法长期并存。 所以「CPU 什么时候开始事件驱动」这个问题，本来就没有一个确切的日期。

并发的错觉

单核 CPU 在某一瞬间只能执行一个进程。但在 1 秒钟里它可能切换几十次，每个进程跑几十到几百毫秒。

于是在人眼看来，音乐在放、浏览器在渲染、下载在下，好像是同时在跑。

这叫并发：宏观上同时，微观上轮流。

真并行是另一回事，它需要多个 CPU 核：

单核 并发 同一瞬间只有一个人真的在跑
0 → 20ms 进程 A 占着 CPU A
20 → 40ms 换成进程 B B
40 → 60ms 又换回 A A
再加一个核这才叫并行
双核 并行 同一瞬间两个都在跑
核 1 A 从头跑到尾，没被换下去 一直跑
核 2 B 也从头跑到尾 一直跑

看两排的区别：并发那排的格子是串成一串的，同一列只有一个格子； 并行那排的格子是并排的。

02进程的七种状态

进程不是从头跑到尾的。它更像「运行 → 暂停 → 运行」这样断断续续地往前走：跑一会儿被换下去，等某个条件满足了再被换上来。

它停下来的原因只有两类，这决定了它停在哪个状态。

先看内存里的五个状态

内存里的五个基本状态
创建 刚分配 PCB
就绪 就差 CPU
运行 正占着 CPU
结束 资源被回收
阻塞 等 I/O 返回

三条基本状态的区别，只有一句话：

状态占着 CPU 吗能跑吗什么时候进这个状态
运行占着正在跑被调度器选中之后
就绪没占着能跑，在排队创建完成、时间片用完、或等的事件来了
阻塞没占着跑不了自己开口要一个还没来的事件，比如读盘

就绪和阻塞都「没在跑」，区别在于给不给它 CPU。

给就绪的进程一个 CPU，它立刻能跑。给阻塞的进程一个 CPU 也没用，它在等的那件事还没发生。

阻塞是进程自己要求的（发起 I/O、申请锁），所以也只能由别人叫醒它。一个阻塞中的进程没法叫醒自己。

再加两个：创建和结束

  • 创建：PCB 申请好了、资源分好了，但还没进就绪队列。这个状态极短。
  • 结束：进程跑完了或者出错了，等操作系统回收资源。也极短。

再加两个：挂起

到这里是五个状态。但还有一个现实问题：

如果一个进程被阻塞了，它占的物理内存还留着吗？

物理内存就那么点，让一堆啥也干不了的进程占着，是纯浪费。虚拟内存管理会把阻塞进程的物理内存换出到硬盘，等要跑了再换回来。

于是多出一个独立的维度：进程在不在物理内存里。把「在不在内存」和「就绪 / 阻塞」交叉一下，三个状态就变成了四个：

上排：在物理内存里　　下排：已被换出到硬盘
就绪 在内存，就差 CPU
阻塞 在内存，在等事件
就绪挂起 在硬盘，进内存就能跑
阻塞挂起 在硬盘，也还在等

「挂起」说的就是下面那一排：进程不占物理内存。它和「就绪还是阻塞」是两件互不相干的事，所以能交叉出四个格子。

「阻塞挂起」是两件事叠在一起，不是第三种等待。

进程可以既阻塞又挂起：它在等一个事件（阻塞），同时它不占物理内存（挂起）。这两个条件互相独立，上面那四个框就是全部组合。

触发挂起的原因不止内存不够：

系统决定

内存不够，被换出去

最常见的一种。阻塞的进程先让位

进程自选

自己 sleep 一会儿

设个定时器，到点了唤醒自己。原理就是「阻塞 + 定时中断」

用户操作

用户手动挂起

Linux 里 Ctrl+Z 把一个前台进程挂到后台，它就不占 CPU 了

外部干预

调试器 / 作业控制

进程被停下来，等人下一条指令

所有迁移收在一张表里

从到触发条件谁决定的
无 → 创建一个新进程被建立操作系统
创建就绪PCB 初始化完成，可以进队了操作系统
就绪运行被调度器选中，拿到 CPU调度器
运行就绪时间片用完，被换下来调度器
运行阻塞请求 I/O、申请锁，要等进程自己
运行结束跑完或出错进程自己 / 操作系统
阻塞就绪等待的事件发生了别的进程 / 中断
就绪就绪挂起物理内存不够，被换出操作系统
阻塞阻塞挂起物理内存不够，被换出操作系统
就绪挂起就绪被换回内存操作系统
阻塞挂起阻塞被换回内存，但事件还没来操作系统
阻塞挂起就绪挂起在外存上等到了那个事件别的进程 / 中断

最后一行容易看漏：在外存上等的事件也会到。这时候进程已经准备好跑了，但还是不在内存里，所以进的是「就绪挂起」。

从阻塞出来，只能先到就绪，不可能直接跳到运行。 谁来跑，由调度器说了算。

03操作系统靠什么记住一个进程

进程在运行过程中要停下来、换下去、过一会儿再换回来。换回来的时候它得接着上次继续跑，所以操作系统得把它的一切都记下来。

记在一张表里，这张表叫进程控制块（Process Control Block，PCB）。

PCB 是进程存在的唯一凭证：有进程就一定有 PCB，进程没了 PCB 也跟着没。你 ps 看到的每一行，背后都对应着一个活着的 PCB。

PCB 里记了什么

分四类：

PCB进程的档案袋
我是谁

进程标识符（pid）：每个进程一个，唯一。 你在 ps 里看到的 8412 就是它。

用户标识符（uid）：这个进程归谁。权限检查靠它。

我现在怎么样

当前状态：就绪 / 运行 / 阻塞 …… 决定它在哪个队列里排队。

优先级：抢 CPU 时谁先上。

我占用了什么

内存地址空间的信息（代码段、数据段、堆、栈各在哪、多大）。 打开的文件列表、正在用的 I/O 设备。

我跑到哪了

CPU 里各个寄存器的值。

这一项是关键：进程被换下去的时候，CPU 里那一堆寄存器的值会存进 PCB； 下次换回来再从 PCB 恢复进寄存器。没有这一项，进程就没法「接着上次」继续跑。

队列：把 PCB 串起来

一个进程的 PCB 单独放着没意义，操作系统真正要回答的是「下一个该跑谁」。

所以 PCB 按状态串成队列：

  • PCB 的三种去处 操作系统按状态把 PCB 串成不同的队列
    • 就绪队列 所有就绪的串成一条链表，调度器从头取一个
      • PCB(A) → PCB(C) → PCB(D) 都就绪，在排队等 CPU
    • 阻塞队列 · 等磁盘 每个事件各有一条，不是一条大队列
      • PCB(B) 在等一次 read 返回
    • 阻塞队列 · 等锁 事件不同，叫醒的时机就不同
      • PCB(E) 在等一把互斥锁
    • 运行队列 单核 CPU 上只可能有一个在跑，它退化成「一个指针」
      • pointer → PCB(F) 正在 CPU 上的那一个

为什么要用链表，而不是数组？因为进程会频繁地被创建、终止、阻塞、唤醒，PCB 要不停地在队列之间搬家。链表的插入删除是 O(1)，不用搬数据。

另一种组织方式是索引：状态相同的 PCB 放进一张索引表，表项指向 PCB。查起来快，但插入删除时要维护表。实际系统多用链表。

04进程的四件事：创建、终止、阻塞、唤醒

这四件事合起来叫「进程控制」，都是操作系统在管。

操作 01

创建

分 pid → 分资源 → 初始化 PCB → 插进就绪队列

操作 02

终止

停下来 → 子进程一起处理 → 资源还回去 → 删 PCB

操作 03

阻塞

跑不下去了，保护现场，把自己挂到等待队列上

操作 04

唤醒

等的事到了，把 PCB 从等待队列挪回就绪队列

后两个总是成对出现，而且执行它们的往往不是同一个进程：

进程 A要读盘的那个
内核调度器 + 中断处理
进程 B就绪队列里的另一个
1read(fd, buf, 500MB)
2保护现场，A 转阻塞，PCB 挂进磁盘等待队列
3调度器选中 B，B 开始跑
4磁盘中断到了：把 A 的 PCB 挪回就绪队列
5A 被唤醒，但还得排队等调度

图的读法：第 2 步是 A 自己把自己挂上去，第 4 步是中断处理把 A 摘下来。 A 从头到尾都动不了，只能等。 唤醒不等于立刻运行，它只是重新有了排队的资格。

创建进程

四步：

① 分配一个唯一的 pid，申请一个空白的 PCB
② 给进程分配资源（内存、文件等）。资源不够就先等着
③ 初始化 PCB 里的各项
④ 如果调度队列装得下，把 PCB 插进就绪队列，等被调度

PCB 是有限的。申请不到 PCB，创建就直接失败，不是「排队等一个 PCB」。

🌱

父进程创建子进程之后，代码是怎么执行的？

以 Linux 的 fork() 为例。父进程调用它之后，父子两个进程都从 fork() 的下一行继续往下执行， 代码是同一份，只是靠返回值区分身份：

pid_t pid = fork();

if (pid == 0) {
    // 子进程走这里。fork 在子进程里返回 0
    do_child_work();
} else if (pid > 0) {
    // 父进程走这里。fork 在父进程里返回子进程的 pid
    wait_for_child(pid);
}
// 两个进程都会走到这里
pid = fork() 父进程执行到这一行
父进程 pid > 0：拿到子进程的号
子进程 pid == 0：刚复制出来的那一份
都从 fork 的下一行继续跑 代码是同一份，靠返回值分岔
共享同一批物理页 写时复制：谁要写哪一页，才复制哪一页

子进程可以 exec() 换成另一个程序，那就彻底变成别的进程了。父进程如果先退出，Linux 会把它的子进程交给 1 号进程（systemd）接管，而不是让它们变成孤儿。

终止进程

三种终止方式：正常结束、异常结束、被外界 kill 掉。

① 找到要终止的进程的 PCB
② 如果它正在运行，立刻停掉，把 CPU 让出去
③ 如果它有子进程，把这些子进程也处理掉
④ 把它占的资源全部还给父进程或操作系统
⑤ 从它所在的队列里摘掉 PCB

阻塞进程

① 找到自己的 PCB
② 保护现场（寄存器等存进 PCB），状态改成阻塞，停止运行
③ 把 PCB 插进对应事件的阻塞队列

唤醒进程

阻塞和唤醒是成对出现的：有进程调了阻塞语句，就一定有一个唤醒语句等着它。

① 在那个事件的阻塞队列里找到目标 PCB
② 把它从阻塞队列里摘出来，状态改成就绪
③ 插进就绪队列，重新排队等调度

唤醒不是「让它立刻跑」。它只是从「跑不了」变成「能跑了，去排队」。

05上下文切换：切走的到底是哪两样东西

进程之间共享 CPU。什么时候让谁上，由操作系统决定。

「把一个进程换下去、把另一个换上来」这件事，叫进程的上下文切换。

先看 CPU 上下文

CPU 执行指令时，靠两样东西知道自己在干什么：

是什么 类比
CPU 寄存器 CPU 内部容量极小、速度极快的一块存储 口袋：随手就能拿到
程序计数器（PC） 存着正在执行的指令位置、或下一条指令的位置 你夹在书里的书签

桌面上的东西放口袋，比从书包里掏快得多。寄存器相对内存就是这样：寄存器纳秒级，内存几十纳秒，硬盘毫秒级。

这两样合起来叫 CPU 上下文：CPU 运行任何任务前都要依赖的环境。

于是 CPU 上下文切换就是这么一趟往返：

旧任务 寄存器里是它的状态
① 存起来 寄存器的值 + PC 的值
② 装回去 把新任务的上下文填进寄存器和 PC
新任务 ③ 跳到 PC 指的位置开始跑

进程上下文比 CPU 上下文多什么

「任务」有三种：进程、线程、中断。所以 CPU 上下文切换也分三类。

进程这块要复杂一些，因为进程是由内核管理和调度的，切换只能发生在内核态。

它要多搬两样东西：

用户空间 也要存 用户态资源
虚拟内存页表、地址空间映射
栈用户栈的指针和内容，函数调用链在上面
全局变量数据段里的那些

这些是进程私有的，换了进程就不一样了

进入内核切换动作全部发生在内核态
内核空间 也要存 内核管理
内核栈系统调用执行到哪了
寄存器含 PC、栈指针

存完之后，这些信息都落在 进程自己的 PCB 里

所以完整的定义是：

进程上下文切换 = 换掉用户空间的资源（虚拟内存、栈、全局变量）+ 换掉内核空间的资源（内核栈、寄存器）。

换下去时存进 PCB，换上来时从 PCB 恢复。整个过程对进程自己是透明的，它只觉得自己被暂停过一下。

💰

这次切换是有成本的，而且成本不小。

切换本身要执行内核代码、要读写内存、还会把 CPU 的缓存和 TLB 弄脏。 这段时间 CPU 没在跑你的程序，也没在跑别人的程序，纯在搬东西。

所以调度策略有一个隐含目标：让每次切换尽量值回票价。 时间片太短 → 切换太频繁 → 全在搬东西； 时间片太长 → 交互式操作卡顿。这就是下一节要权衡的事。

什么时候会触发切换

最常见

时间片用完

运行 → 就绪。调度器从就绪队列挑下一个

系统压力

资源不够被挂起

比如内存不足，等资源满足了才能继续

进程自选

自己 sleep

进程主动挂起自己，让出 CPU 去睡一会儿

抢占

来了更高优先级的进程

当前进程被挂起，让高优先级的先跑

被动

硬件中断

CPU 上的进程被中断挂起，转而执行内核里的中断服务程序

前三种是进程自己在某个时刻「跑不下去了」，后两种是外界插进来的。

就绪和阻塞都「没在跑」，为什么它们是两个状态？

因为能不能跑不一样。就绪=万事俱备只差 CPU，给它 CPU 立刻能跑； 阻塞=还在等一个事件，给它 CPU 也没用。这个区别决定了它排在哪个队列里。

「阻塞挂起」是阻塞之外的第三种等待吗？

不是，是两个独立条件的叠加：既在等一个事件（阻塞），又不占物理内存（挂起）。 等的事件到了，它变「就绪挂起」：能跑了，但还得先换回内存。

进程上下文切换，为什么要连虚拟内存和栈一起换，光存寄存器不够吗？

寄存器只记录「执行到哪了」。进程还拥有一整套私有的地址空间和用户栈， 换了进程之后，同样的虚拟地址指向的是完全不同的物理内存。 不换页表，新进程读到的就是别人的内存。

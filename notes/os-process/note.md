## 01 · 一行代码要跑起来，中间隔了什么

先看一个具体的东西。你在终端敲下：

```
$ python train.py --epochs 30
```

回车之后，它开始吃 1.2 GB 内存、打开 3 个数据文件、占满一个 CPU 核。这时候你在另一个窗口敲 `ps`，会看到它：

```
  PID TTY      TIME CMD
 8412 pts/3  00:12:37 python
```

这一行就是一个**进程**：一个正在运行的程序。

程序本身只是个文件。它躺在硬盘上，不占 CPU、不占内存、也不会自己变。只有当操作系统把它装载进内存、CPU 开始执行里面的指令，它才成为一个进程。

| | 程序 | 进程 |
|---|---|---|
| 存在形态 | 硬盘上的可执行文件 | 内存里正在跑的一份执行 |
| 有几份 | 一份文件 | 同一个程序可以同时跑出好几个进程 |
| 会自己变吗 | 不会 | 每时每刻都在变：跑到哪了、占了多少内存、打开了哪些文件 |

用做饭打个比方：菜谱是程序，食材是数据，照着菜谱把菜做出来这件事，才是进程。同一份菜谱，三个人可以同时各做一份、互不干扰，那是三个进程。

### CPU 为什么不能干等

假设有一段代码要「从硬盘读一个 500 MB 的文件」。硬盘读完要几百毫秒，而 CPU 执行一条指令是纳秒级，这两件事差了**八个数量级**。

CPU 在这几百毫秒里干等着，那它 99.99% 的时间都在发呆。

所以操作系统不让它等：进程 A 发出读盘请求后，CPU 立刻转去执行进程 B；硬盘把数据准备好了，发一个**中断**告诉 CPU，CPU 再回到 A 继续往下跑。

烧水的类比很贴切。你不会站在水壶前面盯着它烧开，而是先去干别的，听到「嘀」的一声再回来倒水。那声「嘀」就是中断。

````callout
tone: violet
icon: 📜
text: |
  **「别等，让事件来敲门」不是一开始就有的。**

  早期机器用**轮询**：CPU 反复去读设备的状态寄存器，问「好了没」。浪费 CPU，但实现简单。

  转向中断驱动是 1950 年代中后期到 1960 年代慢慢完成的，**没有一个确切的日期**：

  | 时间 | 发生了什么 |
  |---|---|
  | 1950s 中期 | 中断机制出现。UNIVAC 1103 / 1103A 和 NBS 的 DYSEAC 都被算作早期实现，==「谁是第一台」至今有争议== |
  | 1958 | IBM 709 用上 DMA：数据在设备和内存之间直接搬，CPU 连「搬」这个动作都不参与了 |
  | 1964 | CDC 6600，当时最快的机器之一，对 I/O **仍然用轮询** |

  最后一行才是重点：中断不是一夜之间取代轮询的，两套办法长期并存。
````

### 并发的错觉

单核 CPU 在某一瞬间只能执行一个进程。但在 1 秒钟里它可能切换几十次，每个进程跑几十到几百毫秒。

于是在人眼看来，音乐在放、浏览器在渲染、下载在下，好像是同时在跑。

==这叫并发：宏观上同时，微观上轮流。==

真并行是另一回事，它需要多个 CPU 核：

```lane-stack

  nodes:

    - { title: "20 → 40ms", sub: "换成进程 B", tag: B }
    - { title: "40 → 60ms", sub: "又换回 A", tag: A }
  next: "再加一个核 :: :: 这才叫并行"
- badge: 双核
  title: 并行

    - { title: "核 1", sub: "A 从头跑到尾，没被换下去", tag: 一直跑 }

```

## 02 · 进程的七种状态

进程不是从头跑到尾的。它更像「运行 → 暂停 → 运行」这样断断续续地往前走：跑一会儿被换下去，等某个条件满足了再被换上来。

它停下来的原因只有两类，这决定了它停在哪个状态。

### 先看内存里的五个状态

```flow

  - { id: exit,  label: 结束, sub: "资源被回收",  row: 0, tone: red,   shape: pill, group: five }
  - { id: block, label: 阻塞, sub: "等 I/O 返回", row: 1, tone: amber, shape: pill, group: five }

  - { from: block, to: ready, label: "事件到了" }
```

三条基本状态的区别，只有一句话：

```compare

head: [占着 CPU 吗, 能跑吗, 什么时候进这个状态]
rows:
  - 运行: [{ text: 占着, tone: green }, "正在跑", "被调度器选中之后"]
  - 就绪: ["没占着", "能跑，在排队", "创建完成、时间片用完、或等的事件来了"]
  - 阻塞: ["没占着", { text: "跑不了", tone: amber }, "自己开口要一个还没来的事件，比如读盘"]
```

==就绪和阻塞都「没在跑」，区别在于给不给它 CPU。==

给就绪的进程一个 CPU，它立刻能跑。给阻塞的进程一个 CPU 也没用，它在等的那件事还没发生。

!!阻塞是进程**自己**要求的（发起 I/O、申请锁），所以也只能**由别人**叫醒它。一个阻塞中的进程没法叫醒自己。!!

### 再加两个：创建和结束

- 创建：PCB 申请好了、资源分好了，但还没进就绪队列。这个状态极短。
- 结束：进程跑完了或者出错了，等操作系统回收资源。也极短。

### 再加两个：挂起

到这里是五个状态。但还有一个现实问题：

> 如果一个进程被阻塞了，它占的物理内存还留着吗？

物理内存就那么点，让一堆啥也干不了的进程占着，是纯浪费。虚拟内存管理会把阻塞进程的物理内存换出到硬盘，等要跑了再换回来。

于是多出一个独立的维度：**进程在不在物理内存里**。把「在不在内存」和「就绪 / 阻塞」交叉一下，就从三个状态变出五个：

|  | 在内存里 | 被换到硬盘上 |
|---|---|---|
| 就绪 | 就绪 | 就绪挂起 |
| 阻塞 | 阻塞 | 阻塞挂起 |

==「挂起」说的就是右边这一列：进程不占物理内存。== 它和「就绪还是阻塞」是两件互不相干的事。

进程可以既阻塞又挂起：它在等一个事件（阻塞），同时它不占物理内存（挂起）。这两个条件互相独立，前面那张表的四个格子就是全部组合。

## 03 · 操作系统靠什么记住一个进程

进程在运行过程中要停下来、换下去、过一会儿再换回来。换回来的时候它得接着上次继续跑，所以操作系统得把它的一切都记下来。

记在一张表里，这张表叫**进程控制块**（Process Control Block，PCB）。

**PCB 是进程存在的唯一凭证**：有进程就一定有 PCB，进程没了 PCB 也跟着没。你 `ps` 看到的每一行，背后都对应着一个活着的 PCB。

### PCB 里记了什么

分四类：

```spec
title: PCB
subtitle: 进程的档案袋
tone: violet
rows:
  - k: 我是谁
    v: |
      **进程标识符**（pid）：每个进程一个，唯一。
      你在 `ps` 里看到的 `8412` 就是它。

      **用户标识符**（uid）：这个进程归谁。权限检查靠它。
  - k: 我现在怎么样
    v: |
      **当前状态**：就绪 / 运行 / 阻塞 …… 决定它在哪个队列里排队。

      **优先级**：抢 CPU 时谁先上。
  - k: 我占用了什么
    v: |
      内存地址空间的信息（代码段、数据段、堆、栈各在哪、多大）。
      打开的文件列表、正在用的 I/O 设备。
  - k: 我跑到哪了
    v: |
      **CPU 里各个寄存器的值**。

      这一项是关键：进程被换下去的时候，CPU 里那一堆寄存器的值会存进 PCB；
      下次换回来再从 PCB 恢复进寄存器。==没有这一项，进程就没法「接着上次」继续跑。==
```

### 队列：把 PCB 串起来

一个进程的 PCB 单独放着没意义，操作系统真正要回答的是「下一个该跑谁」。

所以 PCB 按状态串成队列：

```tree
- label: PCB 的三种去处
  note: 操作系统按状态把 PCB 串成不同的队列
  children:
    - label: 就绪队列
      note: 所有就绪的串成一条链表，调度器从头取一个
      children:
        - { label: "PCB(A) → PCB(C) → PCB(D)", note: 都就绪，在排队等 CPU }
    - label: 阻塞队列 · 等磁盘
      note: 每个事件各有一条，不是一条大队列
      children:
        - { label: "PCB(B)", note: "在等一次 read 返回" }
    - label: 阻塞队列 · 等锁
      note: 事件不同，叫醒的时机就不同
      children:
        - { label: "PCB(E)", note: 在等一把互斥锁 }
    - label: 运行队列
      note: 单核 CPU 上只可能有一个在跑，它退化成「一个指针」
      children:
        - { label: "pointer → PCB(F)", note: 正在 CPU 上的那一个 }
```

队列本身是**链表**：

- 就绪队列：所有就绪的 PCB 串在一起，调度器从头取一个。
- 阻塞队列：不是一条，而是每个事件一条。等磁盘的有等磁盘的队列，等锁的有等锁的队列。事件类型不同，叫醒的时机就不同。
- 运行队列：单核 CPU 上只可能有一个正在跑的进程，所以它退化成「一个指针」。

为什么用链表而不是数组？因为进程会频繁地被创建、终止、阻塞、唤醒，PCB 要不停地在队列之间搬家。链表的插入删除是 O(1)，不用搬数据。

另一种组织方式是索引：状态相同的 PCB 放进一张索引表，表项指向 PCB。查起来快，但插入删除时要维护表。实际系统多用链表。

## 04 · 进程的四件事：创建、终止、阻塞、唤醒

这四件事合起来叫「进程控制」，都是操作系统在管。

```cards

items:
  - { title: 创建, desc: "分 pid → 分资源 → 初始化 PCB → 插进就绪队列", tag: 操作 01, tone: blue }
  - { title: 终止, desc: "停下来 → 子进程一起处理 → 资源还回去 → 删 PCB", tag: 操作 02, tone: red }
  - { title: 阻塞, desc: "跑不下去了，保护现场，把自己挂到等待队列上", tag: 操作 03, tone: amber }
  - { title: 唤醒, desc: "等的事到了，把 PCB 从等待队列挪回就绪队列", tag: 操作 04, tone: green }
```

后两个总是成对出现，而且==执行它们的往往不是同一个进程==：

A 从头到尾都动不了，只能等。
==唤醒不等于立刻运行，它只是重新有了排队的资格。==

### 创建进程

四步：

```
① 分配一个唯一的 pid，申请一个空白的 PCB
② 给进程分配资源（内存、文件等）。资源不够就先等着
③ 初始化 PCB 里的各项
④ 如果调度队列装得下，把 PCB 插进就绪队列，等被调度
```

!!PCB 是有限的。申请不到 PCB，创建就直接失败，不是「排队等一个 PCB」。!!

````callout
tone: violet
icon: 🌱
text: |
  **父进程创建子进程之后，代码是怎么执行的？**

  以 Linux 的 `fork()` 为例。父进程调用它之后，==父子两个进程都从 `fork()` 的下一行继续往下执行==，
  代码是同一份，只是靠返回值区分身份：

  ```c
  pid_t pid = fork();

  if (pid == 0) {
      // 子进程走这里。fork 在子进程里返回 0
      do_child_work();
  } else if (pid > 0) {
      // 父进程走这里。fork 在父进程里返回子进程的 pid
      wait_for_child(pid);
  }
  // 两个进程都会走到这里
  ```

  内存不是真的复制一份。Linux 用**写时复制**（copy-on-write）：
  父子暂时指向同一批物理页，谁要写哪一页，才把那一页复制出来。

  子进程可以 `exec()` 换成另一个程序，那就彻底变成别的进程了。

  父进程如果先退出，Linux 会把它的子进程交给 **1 号进程**（`systemd`）接管，
  而不是让它们变成孤儿。
````

### 终止进程

三种终止方式：正常结束、异常结束、被外界 `kill` 掉。

```
① 找到要终止的进程的 PCB
② 如果它正在运行，立刻停掉，把 CPU 让出去
③ 如果它有子进程，把这些子进程也处理掉
④ 把它占的资源全部还给父进程或操作系统
⑤ 从它所在的队列里摘掉 PCB
```

### 阻塞进程

```
① 找到自己的 PCB
② 保护现场（寄存器等存进 PCB），状态改成阻塞，停止运行
③ 把 PCB 插进对应事件的阻塞队列
```

### 唤醒进程

阻塞和唤醒是成对出现的：有进程调了阻塞语句，就一定有一个唤醒语句等着它。

```
① 在那个事件的阻塞队列里找到目标 PCB
② 把它从阻塞队列里摘出来，状态改成就绪
③ 插进就绪队列，重新排队等调度
```

!!唤醒不是「让它立刻跑」。它只是从「跑不了」变成「能跑了，去排队」。!!

## 05 · 上下文切换：切走的到底是哪两样东西

进程之间共享 CPU。什么时候让谁上，由操作系统决定。

「把一个进程换下去、把另一个换上来」这件事，叫**进程的上下文切换**。

### 先看 CPU 上下文

CPU 执行指令时，靠两样东西知道自己在干什么：

| | 是什么 | 类比 |
|---|---|---|
| **CPU 寄存器** | CPU 内部容量极小、速度极快的一块存储 | 口袋：随手就能拿到 |
| **程序计数器**（PC） | 存着正在执行的指令位置、或下一条指令的位置 | 你夹在书里的书签 |

桌面上的东西放口袋，比从书包里掏快得多。寄存器相对内存就是这样：寄存器纳秒级，内存几十纳秒，硬盘毫秒级。

这两样合起来叫 **CPU 上下文**：CPU 运行任何任务前都要依赖的环境。

于是 **CPU 上下文切换**就是三步：

```
① 把上一个任务的 CPU 上下文（寄存器的值、PC 的值）存到某处
② 把新任务的上下文加载进这些寄存器和 PC
③ 跳到 PC 指向的新位置，开始跑新任务
```

### 进程上下文比 CPU 上下文多什么

「任务」有三种：进程、线程、中断。所以 CPU 上下文切换也分三类。

进程这块要复杂一些，因为进程是由内核管理和调度的，==切换只能发生在内核态==。

它要多搬两样东西：

```journey
- tag: 用户空间
  tone: blue
  name: 也要存
  badge: 用户态资源
  fields:
    - { k: 虚拟内存, v: "页表、地址空间映射" }
    - { k: 栈, v: "用户栈的指针和内容，函数调用链在上面" }
    - { k: 全局变量, v: "数据段里的那些" }
  note: 这些是进程私有的，换了进程就不一样了
  next: "进入内核 :: :: 切换动作全部发生在内核态"

- tag: 内核空间
  tone: violet
  name: 也要存
  badge: 内核管理
  fields:
    - { k: 内核栈, v: "系统调用执行到哪了" }
    - { k: 寄存器, v: "含 PC、栈指针" }
  note: 存完之后，这些信息都落在 ==进程自己的 PCB== 里
```

所以完整的定义是：

> **进程上下文切换 = 换掉用户空间的资源（虚拟内存、栈、全局变量）+ 换掉内核空间的资源（内核栈、寄存器）。**

换下去时存进 PCB，换上来时从 PCB 恢复。整个过程对进程自己是透明的，它只觉得自己被暂停过一下。

```callout
tone: amber
icon: 💰
text: |
  **这次切换是有成本的，而且成本不小。**

  切换本身要执行内核代码、要读写内存、还会把 CPU 的缓存和 TLB 弄脏。
  这段时间 CPU 没在跑你的程序，也没在跑别人的程序，纯在搬东西。

  所以调度策略有一个隐含目标：==让每次切换尽量值回票价==。
  时间片太短 → 切换太频繁 → 全在搬东西；
  时间片太长 → 交互式操作卡顿。这就是下一节要权衡的事。
```

### 什么时候会触发切换

```cards
cols: 2
items:

  - { title: 硬件中断, desc: "CPU 上的进程被中断挂起，转而执行内核里的中断服务程序", tag: 被动, tone: muted }
```

前三种是进程自己在某个时刻「跑不下去了」，后两种是外界插进来的。

```quiz
- q: 就绪和阻塞都「没在跑」，为什么它们是两个状态？
  a: |
    因为能不能跑不一样。就绪=万事俱备只差 CPU，给它 CPU 立刻能跑；
    阻塞=还在等一个事件，给它 CPU 也没用。这个区别决定了它排在哪个队列里。
- q: 「阻塞挂起」是阻塞之外的第三种等待吗？
  a: |
    不是，是两个独立条件的叠加：既在等一个事件（阻塞），又不占物理内存（挂起）。
    等的事件到了，它变「就绪挂起」：能跑了，但还得先换回内存。
- q: 进程上下文切换，为什么要连虚拟内存和栈一起换，光存寄存器不够吗？
  a: |
    寄存器只记录「执行到哪了」。进程还拥有一整套私有的地址空间和用户栈，
    换了进程之后，同样的虚拟地址指向的是完全不同的物理内存。
    不换页表，新进程读到的就是别人的内存。
```

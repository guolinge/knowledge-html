后面三篇讲的都是「编译器能证明什么」。但有一类信息，编译器无论如何都证明不了，因为答案根本不在代码里，它取决于这次运行喂了什么数据。

```c
if (type == TYPE_A) { ... }     // 99% 的请求走这里
else if (type == TYPE_B) { ... } // 剩下 1%
```

静态看，两个分支一样重。真实运行时，一个占 99%，一个占 1%。这一篇讲两件事：怎么把这类信息交给优化器（PGO 和 JIT），以及怎么确认优化真的有效、真的没把程序改坏。

## 01 · 静态看不到的三件事

编译器手里只有代码和类型声明。有三类信息它拿不到，而这三类恰好最值钱：

```compare
first: 拿不到的信息
head: [为什么拿不到, 拿到之后能量什么]
rows:
  - 分支与路径的概率: [取决于输入分布，代码里没写, 基本块布局、热冷分离、内联倾向、寄存器分配]
  - 变量的真实类型: [静态类型是声明，运行时可能是子类、可能是 union 的另一支, 去虚化、类型特化、直接内联目标]
  - 间接调用的目标: [函数指针、虚函数、闭包，目标在运行时才确定, 把间接调用变成直接调用，进而内联]
  - 值的范围与对齐: [输入约束没有写在类型里, 去掉边界检查、选择更窄的指令、判断能否向量化]
```

注意最后一行：这四类信息都有一个共同点：**它们不是语义事实，是运行分布的统计**。`type == TYPE_A` 占 99% 这件事明天可能变成 50%，编译器如果把它当成永远成立，就是在赌。所以后面两节讲的两条路线，差别正在于「敢赌到什么程度」。

## 02 · PGO：先跑一遍，再编译一遍

**PGO（profile-guided optimization，基于剖析的优化）** 的做法朴素得有点意外：把程序编译两遍。第一遍插桩，跑真实负载，把计数器落盘；第二遍读这些数据，重新编译。

```lane-stack
- badge: 第一遍
  title: 插桩编译
  desc: 每个基本块、每条边、每个调用点塞一个计数器
  tone: blue
  nodes:
    - { title: gcc -fprofile-generate, sub: "或者 clang -fprofile-instr-generate", tag: 比平时慢 }
    - { title: 产物带 .gcda / .profraw, sub: "运行结束后写出计数", tag: 可合并 }
  next: "拿到「这次跑了什么」 :: :: 还没开始优化"

- badge: 运行
  title: 跑真实负载
  desc: 用生产环境的输入跑一遍代表性场景
  tone: amber
  nodes:
    - { title: 输入要有代表性, sub: "测试用例覆盖不到的路径，profile 里是 0", tag: 关键前提 }
    - { title: 多份 profile 可以合并, sub: "把几次运行的计数加在一起", tag: 摊平偏差 }
  next: "合并成一份 profile :: :: 覆盖率决定这次优化的上限"

- badge: 第二遍
  title: 带 profile 重编
  desc: 分支概率、调用次数、间接目标全都知道了
  tone: green
  nodes:
    - { title: 热路径排在一起, sub: "基本块布局按实际走向重排", tag: 指令缓存 }
    - { title: 热函数更愿意内联, sub: "成本模型拿到真实调用次数", tag: 代码体积花在刀刃上 }
    - { title: 冷代码分到独立段, sub: "-freorder-blocks-and-partition", tag: 减少热区污染 }
```

得到的还是同一个源程序，只是这份二进制贴着真实负载。代价是构建流程多了两步。

PGO 的价值来自一个简单事实：==优化的收益取决于「哪些代码真的在跑」，而这只能测出来。== 一份 profile 让成本模型从「猜」变成「按实测分配预算」。

但它的前提也很硬：**负载要有代表性**。用一份只覆盖登录流程的 profile 去优化整个服务，结果是登录路径被优化到极致，支付路径被当成冷代码扔到远处，那反而更慢。这就是为什么工程上强调「用生产流量的采样，而不是用单元测试跑出来的 profile」。

采样式 PGO（sample-based，例如 AutoFDO）绕开了插桩：直接用 `perf` 采样生产进程，把采样地址映射回代码位置当权重。精度低一些，但不需要专门的插桩构建，也不需要在生产环境跑一个慢几倍的二进制。

## 03 · JIT：先跑起来，再优化

JIT（just-in-time）把「测量」挪进了运行时。它不需要你先跑一遍负载，因为程序本身就在跑：

```seq
participants:
  - { id: i, label: 解释器, tone: blue }
  - { id: fb, label: 类型反馈, tone: violet }
  - { id: jit, label: 优化编译器, tone: amber }
  - { id: hot, label: 优化后的代码, tone: green }
messages:
  - { from: i, to: fb, label: 记录这次的参数类型, kind: sync, note: 1 }
  - { from: fb, to: jit, label: 这个函数够热了, kind: sync, note: 2 }
  - { from: jit, to: hot, label: 编译：假设参数都是 number, kind: sync, note: 3 }
  - { from: hot, to: i, label: "遇到 string，去优化", kind: reply, note: 4 }
  - { from: i, to: jit, label: 用「可能是任意类型」再编译, kind: sync, note: 5 }
  - { from: jit, to: hot, label: 换上新版本, kind: reply, note: 6 }
```

三代浏览器引擎都走这条路，只是层数不同：先解释执行（V8 的 Ignition），热起来换一个更快的编译器（Sparkplug / Maglev），再热就上最激进的优化编译器（TurboFan）。每一层都比上一层更依赖假设，也都更需要一条退路。

JIT 相比静态编译多出来的两件事，恰好是静态编译做不到的：

| JIT 能做 | 为什么静态编译做不到 |
|---|---|
| 按实际类型特化 | 同一个函数在程序里被不同类型调用，静态只能生成通用版本；JIT 可以生成「number 专用版」 |
| 按实际分支概率重排 | 需要真实运行数据，而静态编译时程序还没跑 |
| 换掉已加载的函数 | 代码在内存里，可以重新编译、原地替换 |
| 假设失效时退回 | 需要运行时状态，解释器一直在旁边待命 |

## 04 · 去优化：激进的假设必须能安全撤回

第 3 步那句「假设参数都是 number」是整个流程的收益来源，也是风险来源。收益在于：知道是 number 就不用装箱、不用查类型、不用走通用路径。风险在于：这个假设**可能不成立**，而且不成立的时候程序不能崩，得继续算对。

所以 JIT 必须保留两样东西：

- **类型反馈（type feedback）**：这个函数过去被哪些类型调用过。够纯才敢特化。
- **去优化（deoptimization）的能力**：在进入优化代码的每个「假设点」埋一个守卫（guard）；守卫失败就抛出一个信号，运行时把当前状态**重建**成解释器能理解的样子（局部变量、操作数栈、程序计数器），然后从那条字节码继续执行。

!!去优化不是出错兜底，是设计里的一等公民。!! 没有它，JIT 就不敢做任何激进假设；有了它，JIT 才敢「先按最常见的类型编译，错了再退」。

这也解释了为什么 JIT 的性能曲线常常是锯齿状的：一段代码被优化、遇到新类型退回、重新优化成更通用的版本、再遇到新类型……**优化器在运行时不停地做「猜—验证—修正」**，和人在做性能优化时的动作是一样的。

```callout
tone: violet
icon: 🔁
text: |
  ==去优化把「正确性」和「激进程度」解耦了。==

  静态编译器两个都要，所以只能在保守的那条线上选一个点。
  JIT 把「激进」放在快路径、「保守」放在慢路径，于是两边都拿到了：
  常见情况按最理想的假设跑，罕见情况退回解释器，结果仍然正确。
```

## 05 · 闭环：让「变快了」变成可复现的结论

PGO 和 JIT 是编译器自己的闭环。你自己做优化时，闭环长这样：每一步的产出都是下一步的输入。

```lane-stack
- badge: 第 1 步
  title: 建立基线
  desc: 先有一个能重复的数字
  tone: muted
  nodes:
    - { title: 固定输入与机器状态, sub: "同一份数据、同一台机器、关掉别的负载", tag: 可复现 }
    - { title: 多轮取中位数, sub: "跑 5 次看离散度，不看单次最好成绩", tag: 排除抖动 }
  next: "拿到「现在多快」 :: :: 没有基线，后面所有结论都不成立"

- badge: 第 2 步
  title: 找热点
  desc: 用 profiler，不用直觉
  tone: blue
  nodes:
    - { title: 火焰图看占比, sub: "最宽的那块才是热点", tag: 采样 }
    - { title: 计数器看为什么, sub: "IPC、cache miss、分支失败", tag: 归因 }
  next: "落到具体函数与行 :: :: 注意：热点常常不是你写的代码（如 memcpy）"

- badge: 第 3 步
  title: 提一个可证伪的假设
  desc: 「为什么慢」要说成一句话
  tone: violet
  nodes:
    - { title: 好假设, sub: "列遍历导致每条缓存行只用 1/16", tag: 可验证 }
    - { title: 坏假设, sub: "这里应该能优化一下", tag: 无法验证 }
  next: "知道这次要改什么、预期变多少 :: :: 预期变不动的，就是假设错了"

- badge: 第 4 步
  title: 一次只改一件事
  desc: 否则测出来的数字无法归因
  tone: amber
  nodes:
    - { title: 保留 diff 与原因, sub: "为什么这么改，预期多少", tag: 便于回滚 }
    - { title: 顺手改的三处要拆开, sub: "一次一个变量", tag: 归因 }
  next: "得到一份可以单独回滚的改动 :: :: 接下来先问对不对，再问快不快"

- badge: 第 5 步
  title: 先验正确性
  desc: 优化改坏程序时，测试往往是唯一发现它的地方
  tone: red
  nodes:
    - { title: 单元 + 回归, sub: "覆盖边界值、空输入、并发", tag: 必过 }
    - { title: 差分对比, sub: "新旧两版对同一输入比结果", tag: 最灵敏 }
  next: "确认结果不变 :: :: 这一步不过，后面测什么都白搭"

- badge: 第 6 步
  title: 再验性能 + 回归
  desc: 端到端，不是那个局部指标
  tone: green
  nodes:
    - { title: 同一套基准重跑, sub: "看的是整体耗时，不是某条指令", tag: 阿姆达尔 }
    - { title: 其它场景有没有变慢, sub: "优化常常是此消彼长", tag: 防回退 }
```

走完第 6 步之后有三种结局：保留、回滚，或者回到第 1 步再来一轮，直到收益不再显著。

这套流程里最容易被跳过的是第 5 步。优化改坏程序的典型症状不是崩溃，而是**某些输入下结果不一样**——它在测试里可能刚好没被覆盖到。

## 06 · 测试体系：优化器最危险的错误是悄悄的

编译器项目的测试比普通项目重得多，因为「编出来的程序算错」这种 bug，只能靠对比来发现：

```cards
cols: 2
items:
  - title: 单元测试
    desc: 每条 pass 有自己的输入输出用例
    tag: 定位最快
    body: |
      一个 pass 一段 IR，断言输出长什么样。好处是失败时范围极小，
      坏处是只覆盖「想得到的情况」。
  - title: 回归测试
    desc: 每个修过的 bug 都要留下一个用例
    tag: 防复发
    body: |
      优化 bug 的复现条件常常很怪（某个常量、某条边的顺序）。
      不留下用例，下次重构就会原样再犯一次。
  - title: 差分测试
    desc: 同一份程序，两个编译器（或两个 -O 级别）结果必须一致
    tag: 抓错编译
    body: |
      Csmith 就是用随机生成合法 C 程序的办法做这件事：
      把 `-O0` 和 `-O3` 的输出对比，不一致就是其中一个错了。
      论文里报出 325 个以上 GCC / LLVM 的 bug，绝大多数是错编译。
  - title: 随机程序测试
    desc: 让生成器去覆盖人想不到的组合
    tag: 覆盖组合爆炸
    body: |
      前提是生成器保证程序合法（无 UB），否则差异无法归因：
      程序本身有未定义行为时，两边结果不同是允许的。
  - title: 性能基准
    desc: 既防变慢，也防「优化了但没收益」的 pass 常驻
    tag: 端到端
    body: |
      基准要能重复、能归因。单点抖动大时看中位数和分布，
      而不是挑一次最好成绩写进报告。
  - title: 编译时间 / 代码体积基准
    desc: 优化是有预算的
    tag: 容易被忽略
    body: |
      多一轮 pass 换来 1% 运行时间、编译时间涨 20%，多数项目不会接受。
      体积同理：内联和展开都会让二进制变大。
  - title: 形式化验证
    desc: 把「语义保持」写成机器检查的证明
    tag: 最彻底
    body: |
      CompCert 走的就是这条路：编译器的正确性有证明，不是靠测试抽样。
      代价是要限制编译器能做什么，所以它不做最激进的优化。
```

## 07 · 谁该做什么：把分工定清楚

前六节讲的是编译器怎么优化。回到你自己的代码，分工其实很清楚：

```compare
first: 谁
head: [负责什么, 不适合做什么]
rows:
  - 你: [选择算法与数据结构、定义清楚约束（类型、`restrict`、`noexcept`）、保持结构可维护、标明哪些是热路径, 手工模仿编译器的内联与寄存器分配]
  - 编译器: [内联、寄存器分配、指令选择、删冗余、按目标机做局部优化, 替你换算法、替你判断业务语义]
  - 运行信息: [提供真实分支概率、类型分布、调用热度, 替你想清楚「该不该慢」这件事]
```

有一类改动要特别警惕：**为了让编译器生成更好的代码，把源码写得更难懂**。比如手动展开循环、手动把函数拆成三段、手动把判断挪到循环外。这些做法在 1990 年代是必要的，现在多数已经被编译器接管，而它们留下的成本——可读性、可维护性、改需求时的阻力——是确定的。

++只有在测量证明必要的时候，才把源码改成机器喜欢的样子。++ 那时候它就不叫「优化风格」，叫「有依据的妥协」，应该在注释里写清原因和数字。

## 08 · 工具与理解：判断不能被外包

现代工具能做的事很多：profiler 告诉你时间在哪，编译器告诉你为什么没向量化（`-fopt-info-vec`、`-Rpass=loop-vectorize`），AI 能帮你写基准、读汇编、提候选。但下面这些判断仍然要自己做：

- 这次跑出来的热点，是不是**生产环境的**热点（负载代表性）。
- 这个优化有没有改变可观察行为（第 1 篇那张清单）。
- 基准测的是不是你真正关心的东西（端到端还是局部）。
- 这份 profile 是不是已经过时（业务变了，分布就变了）。
- 这段代码的「慢」是不是本来就应该接受（比如一次必须的加密）。

==工具能缩短「找到候选」的时间，缩短不了「判断该不该做」的时间。== 后者需要知道这个系统在业务上承诺了什么。

## 09 · 速查

```checklist
items:
  - 静态编译拿不到分支概率、真实类型、间接调用目标；这三样恰好最值钱
  - PGO = 插桩跑一遍 + 带 profile 重编；成败取决于负载是否有代表性
  - 采样式 PGO 用 perf 采样代替插桩，精度低但不用改构建
  - JIT 的分层：解释 → 基线 → 优化，越往后越依赖假设
  - 去优化是设计的一部分：守卫失败时重建解释器状态，继续算对
  - 自己的闭环：基线 → 热点 → 可证伪的假设 → 单变量改动 → 正确性 → 性能回归
  - 优化器 bug 靠差分测试抓（Csmith 那一类方法）；自己改代码靠回归与差分对比抓
  - 性能是多目标：运行时间、编译时间、代码体积都要看
```

## 10 · 自测

```quiz
- q: 为什么静态编译器需要 PGO 才能把热路径排在一起？
  a: |
    因为「哪条路径热」取决于输入分布，代码里没有这个信息。
    基本块布局、内联倾向、寄存器分配都要按热度分配预算，没有 profile 只能靠静态启发式猜。

    PGO 用一次真实运行把这些数字填上；前提是那次运行要有代表性。
- q: PGO 的 profile 没有代表性会怎样？
  a: |
    覆盖率低的路径会被当成冷代码：排到远处、不内联、不做优化。
    如果生产流量恰好主要走这些路径，程序会比不做 PGO 更慢。

    所以工程上用生产流量的采样，而不是用单元测试跑出来的 profile。
- q: JIT 为什么必须支持去优化？没有它会怎样？
  a: |
    因为 JIT 的收益来自激进假设（比如「参数都是 number」）。假设可能失效，
    而程序不能因此算错。去优化在守卫失败时重建解释器状态，从对应字节码继续执行。

    没有它，JIT 就不敢特化，也就失去了相对静态编译的优势。
- q: 优化改坏了程序，为什么单元测试可能发现不了？
  a: |
    错编译的症状往往不是崩溃，而是某些特定输入下结果不同。
    单元测试覆盖的是想得到的情况，组合爆炸的地方容易漏。

    更灵敏的做法是差分：同一输入，新旧两版（或 -O0 与 -O3）对比结果。
    Csmith 就是用随机生成合法程序 + 差分对比，找出了几百个编译器 bug。
- q: 什么时候值得把源码改成「机器喜欢的样子」？
  a: |
    只有测量证明必要时。现代编译器已经接管了内联、展开、寄存器分配这类工作，
    手工模仿换来的是确定的维护成本，和不确定的收益。

    真要做，就要留下依据：改了什么、预期多少、实测多少、为什么其它写法不行。
```

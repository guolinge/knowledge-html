01同样是「等」，内核给不给句柄

G 已经挂回了 M，那 G 阻塞了怎么办？

答案是分流。而分流的原因只有一条：「等待」能不能被内核以外的机制接管，取决于内核给不给句柄。

等的是什么内核给不给句柄于是怎么处理
网络 fd给。epoll / kqueue / IOCP 能统一监视注册一个事件，数据到了内核来喊你 → 交给 netpoller
文件 I/O不给。read 就是要在内核里睡到磁盘把数据搬上来只能真的阻塞一条 M → 走 hand-off
CGO / 部分同步系统调用同理，没有 poll 接口同上

这就是「网络 I/O 与阻塞系统调用为什么走两条路」的全部理由。 runtime 必须准备两条路，因为有一类等待它接管不了。

02泳道一：网络 I/O，等待被 netpoller 吸收

G 挂在 netpoller 上，M 全程没睡
G 调 conn.Read 数据还没到
gopark fd 注册进 epoll，G 状态改成 Waiting
M 立刻取下一个 G 从 LRQ 拿一个继续跑
goready fd 就绪，G 被放回 LRQ

gopark 和 goready 这两个名字值得记住：所谓「阻塞」在 Go 里就是一次状态改写加一次入队，没有任何内核参与。 这正是第 ① 篇那趟「进出内核的旅程」被绕开的全部秘密。

谁在驱动 netpoller？两条路：空闲的 M 取不到 G 时会顺带 poll 一次；后台的 sysmon 也会周期性检查。就绪的 G 被批量放回 LRQ，等下一次被选中。

G1要读网络
runtimenetpoller 在这
M那条真线程
1conn.Read → 数据没到
2fd 注册进 epoll；G1 状态改为 Waiting
3M 转头去跑 LRQ 里的 G3
4epoll 通知 fd 就绪 → goready，G1 回 LRQ
5下次被选中时，它像什么都没发生过

03泳道二：真阻塞，换一条 M 顶上

hand-off：M 与 P 解绑，P 交给别人
G 要读文件 没有 poll 接口可用
先解绑 P 交出「运行 Go 代码的许可」
M1 陪 G 沉进内核 它这下是真的睡了
P 交给 M2 继续消费 LRQ，服务没停
read 返回 G 重新入队，M1 变成备用线程
⚠

hand-off 是兜底，不是免费。

每个真阻塞的调用都要一条 M 沉底陪着。一百个 G 同时做文件 I/O， runtime 就要维持一百条 M —— M 膨胀，内核调度压力回升，第 ① 篇的线程成本原样回来。

这也是为什么重文件 I/O 场景里，goroutine 的优势会打折： netpoller 才是优势的主引擎，hand-off 只是止损。

顺带解释一个常见疑问：为什么 M2 是「新建或唤醒」，而不是等 M1 回来复用？ 因为阻塞的 M1 何时醒来无人知晓，runtime 不会把赌注压在它身上 —— 先补一个可用的，等 M1 回来再收编。

04旧 M:N 为什么没有这条路

机制缺口

缺一半：没有 netpoller

没人把网络等待统一收进用户态调度器

旧式线程库只能包裹既有的系统调用接口， 它无法要求内核把等待语义交出来。

于是网络等待只能和文件等待一样，一条 M 配一个 —— 或者干脆连坐。

契约缺口

缺另一半：语言级封装

没有语言级 I/O 封装来保证「每次阻塞前都先解绑」

就算有 netpoller，也得保证每一次可能阻塞的调用都走正确的路径。 这件事只能由语言和标准库一起保证。

Go 能做成，是因为 runtime 与标准库是一起设计的 —— netpoller 是 runtime 的一部分，net 包天生知道该怎么配合它。

05内核看到的，和 runtime 看到的

视角看到的画面结论
OS 看到的M 一直在跑，从未进入等待态「这个进程是 CPU 密集的」
runtime 看到的G 在等：等网络、等 channel、等定时器「绝大多数 G 只是暂时睡着」

从 OS 的视角看，那条线程从未进入等待态。 Go 在操作系统层面，把 I/O 密集型活折叠成了 CPU 密集型活。

这就是「看起来会阻塞、实际不阻塞」的完整含义 —— 阻塞的语义被 netpoller 与 hand-off 消化在用户态，内核看到的只是一台一直在干活的机器。

🔄

一个正在发生的变化。

io_uring 让普通文件也能提交异步读、由内核完成队列回调，正在改变文件 I/O 的处境。

但截至 Go 1.27，标准库的文件 I/O 仍走阻塞系统调用加 hand-off， io_uring 的集成仍在演进。读这类文档时要分清版本。

为什么网络 I/O 和文件 I/O 在 Go 里走两条完全不同的路？

因为「等待」能不能被内核以外的机制接管，取决于内核给不给句柄。 网络 fd 可以被 epoll/kqueue/IOCP 统一监视，所以能交给 netpoller； 文件 read 在经典模型里没有 poll 接口，就是要在内核里睡到磁盘把数据搬上来， 只能走 hand-off，让一条 M 陪着沉下去。

hand-off 的代价是什么，什么时候会显出来？

每个真阻塞的调用都要一条 M 陪着。一百个 G 同时做文件 I/O， runtime 就要维持一百条 M，内核调度压力回升，线程成本原样回来。 所以在重文件 I/O 或 CGO 场景里，goroutine 的优势会明显打折 —— netpoller 才是优势主引擎，hand-off 只是止损。

为什么说「从 OS 视角，那条线程从未进入等待态」？

因为网络等待被 netpoller 消化了：G 被挂起，M 转头去跑别的 G，内核看不到 M 睡过。 文件 I/O 确实会让一条 M 睡下去，但那条 M 已经把 P 交了出去， 剩下的 P 继续在跑 Go 代码。所以内核看到的是一台一直在干活的机器， 而 runtime 看到的是「绝大多数 G 只是暂时睡着」。

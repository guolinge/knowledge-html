02三条真问题

问题 ① 一个条件节点里的多个叶子，我只取了第一个 129 条 
"condition": { "items": [ {"name":"A","op":">"}, {"name":"B","op":">"} ] }
→ 我只翻出了 A

现网的条件节点 condition.items 是一个叶子列表（按 condition.logic 组合）。我的翻译器早期版本把它当单叶处理，只取第一个 —— 于是我们的条件树少了一个叶子，UDP 的 SQL 里却有两个，结果集自然对不上。

改成摊平 items 里的所有叶子：多个时包成一个 group；另外按行自身形状分派（relationName 走关系、否则走画像）
问题 ② array 字段用错了函数 17 条报错 
Can not find the compatibility function signature:
array_contains(VARCHAR(1024), VARCHAR(1))

我们按 Doris 的真 ARRAY 列写 array_contains，而现网这类列是逗号分隔字符串。这不是环境问题，是编译器的一条真实差异被数据顶出来了（上一篇结尾就发现了，这一篇定案）。

数语料确认该用哪个函数 → 改用 find_in_set
问题 ③ TIMES + 属性过滤，我把语义读反了 45 条 
我以为是「每一行都满足属性」
实际是「没有行，或存在一行满足属性」

这是本轮最有价值的一条：它不是"写错代码"，是我从源码里读出来的结论本身就错了，而且我还把它当成"已对齐"写进了文档。是结果级对拍用三个数字把它钉死的。

见 04 节：两个交互控件把这三层拆开看，再改编译器

03array 的定案：回去数语料

解决方式不是拍脑袋，是回去数 6500 条语料里两种函数各出现在什么语境：

函数出现条数长什么样
find_in_set30 条and (((find_in_set('11', attr_array)) or (find_in_set('32', attr_array)))) —— 关系属性，逗号串
array_contains26 条ARRAY_CONTAINS(CAST(IFNULL(ELEMENT_AT(properties, 'option_ids'), '[]') AS ARRAY<VARCHAR>), '1') —— 事件属性，JSON 数组

结论很干净：圈选路径（画像 / 关系属性）的数组列是逗号串，array_contains 属于事件 JSON 数组那条链路。于是编译器改掉：

-- 改前（错）：array_contains(`u`.`tags`, 'CN')
-- 改后（对齐现网）：(find_in_set('CN', `u`.`tags`))
-- 多值语义：has = 任一项命中（OR）；not_has = 每一项都不包含（AND）

这一改，17 条执行报错直接清零。

04主角：一条被数据抓住的语义误读

4.1 那句话长什么样

现网对「关系 + 计数 + 属性过滤」编译成这样（两次"不在"套在一起）：

uid 不在 ( 从关系表里查： uid 不在 ( 从关系表里查： 满足属性 ) )

我当时把它读成了「每一行都得满足属性」。 理由听起来很顺：两层否定叠起来，不就是"不存在不满足的行"吗？

不是。下面两个控件把这三层拆开看 —— 先别看结论，自己点一遍。

三层拆开看：哪一层筛的是"人"，哪一层筛的是"行" 点上面的按钮，一层一层看

4.2 三种读法，差在哪

同一个数据集，把三种可能的语义摆在一起（这就是我当时脑子里的三种候选）：

「计数 ≥ N 且属性 ≥ 10」的三种读法 三种读法各切一次，看"小美"和"小明"的结果怎么变
🎯

现网是 B。 一句话记住它：

先按"总行数"筛一遍人数，再要求"至少有一行合格" —— 不是"每一行都合格"。

而且"计数"数的是总行数，不是"合格的行数" —— 这两件事加起来，就是它的完整口径。

4.3 为什么"两层层套"看起来像 A、其实是 B

关键在第 ② 层判断的对象：

层 SQL 在做什么 判断的是
① 从关系表里查「满足属性」的行 行 → 得到"至少一行合格"的人
② 从关系表里查「主人的 uid 不在①的名单里」的行 人（这行的主人有没有合格过）→ 得到"有记录、但一次都没合格过"的人
③ 从全体人里去掉② 人 → 剩下"从没记录的人" + "至少合格过一次的人"

第 ② 层只会收一次都没合格过的人。一个人哪怕有 10 行不合格，只要有一行合格，他就不会进第 ② 层，也就不会被第 ③ 层踢掉。

否定的是"合格的行" → 问的是"有没有合格的"； 想表达"每一行都合格"，得拿"不合格的行"去做否定 —— 那是另一个写法（我们原来那句 不存在(有不合格的行)）。

一个字的差别，值 117 个人。

4.4 实测把它钉死

在本地种子库上，三种语义各跑一遍（case 937061）：

语义 人数
总行数 > 0 4021
B：存在一行满足（现网语义，= UDP 记录 SQL 的结果） 0 ✓
A：每一行都满足（我原来的实现） 117 ✗

UDP 的记录 SQL 返回 0，和我实现的 117 对不上 —— 数字不会骗人。这比"再读一遍源码"有用得多。

4.5 改了什么

-- 改前（A：要求每一行都满足）
AND NOT EXISTS (SELECT 1 FROM 关系表 r WHERE r.uid = u.uid AND NOT (props))

-- 改后（B：没有行，或存在一行满足）
AND (NOT EXISTS (SELECT 1 FROM 关系表 r WHERE r.uid = u.uid)
     OR EXISTS   (SELECT 1 FROM 关系表 r WHERE r.uid = u.uid AND (props)))

同时把文档里那条写错的结论改正，并把三个实测数字留在原地 —— 免得以后又有人（包括我）把它读回去。

05重跑：85.3% → 98.8%

第 ④ 步第二轮

  • 一致率 85.3% → 98.8%（1209 → 1400 / 1417）
  • 执行报错 17 → 0
  • 剩下的 17 条：全部是同一类结构差异，见下

剩下的 17 条长这样（case 1094803）：

SQL（节选） 人数
我们 … OR u.uid IN (231368439, 231436539, …) 384
现网 … union all select uid from (SELECT 231368439 AS uid UNION ALL SELECT 231436539 AS uid UNION ALL …) uidt 403

现网是用字面量凭空构造 uid（表里没有的 uid 也会出现），我们是 uid IN (…) 过滤主表（表里没有就不出现）。只影响"不在表里的 uid"，属于已登记的结构差异，不是编译器 bug。

📌

这也解释了这类 case 为什么在本地种子上不可能对上：本地表只有 1 万个 uid， 现网那句话里点名的人大多不在里面。这类差异只能定性、不能定量。

06你问过的几个问题

你的问题回答的要点在哪
「客体是什么？计数能不能选客体？」客体 = 关系表里「跟谁发生关系」的那一列（股票代码 / 天数 / 渠道），也就是「一对多」里的那个「多」。计数选客体 = 只数某个对象的记录 —— 现网不支持，我们已按它的现状去掉（更早一轮的事）系列第 ③ 篇 + docs/udp-sql-diff.md §8.5
「8.4 能说人话吗？发生了什么」就是我们按「每一行都满足」实现，而现网是「至少一行满足」；我读源码读错了，是数据把它抓出来的本篇 04 节
「这里我开始不理解了（两层层套）」第 ② 层筛的是「人」不是「行」：只看这个人「有没有合格过」，不看「某一行为什么不合格」本篇 4.3 + 第一个控件
「为什么需要我拍板？」因为有些取舍不是对错问题，而是「跟现网对齐，还是保留自己的能力」。有证据的直接改（如数组函数），要产品定的才请拍板系列第 ④ 篇 06 节

08这次验证了什么、没验证什么

    09自测

    翻译器"一个条件节点里的多个叶子只取第一个"这个 bug，为什么在结果级对拍里一下就能看见？

    因为结果级比的是人的集合。少一个叶子 = 条件变宽 = 圈出来的人变多， 人数立刻和现网不一样；而文本级对拍如果只挑了"第一个叶子"去比， 两边可能都对得上 —— 少的那部分根本不在比较范围里。

    「计数 ≥ 3 且属性 ≥ 10」里，现网对属性的要求是下列哪一个？ ① 每一行都满足属性 ② 至少有一行满足属性 ③ 满足属性的行数 ≥ 3

    ②。「计数」数的是总行数（不是合格行数），属性能是个"存在性"要求，两者取交集。 实测：本地种子上 ② = 0 人，与现网记录 SQL 一致；① 会得到 117 人。

    为什么第 ② 层（中间的"不在"）只会收"一次都没合格过"的人？

    因为它的判断条件是"这行的主人 uid 在不在第 ① 层名单里" —— 判断对象是人，不是这一行。 主人合格过一次，他的每一行都不满足这个条件，于是这个人根本不会进第 ② 层。 想把"有某些行不合格"表达出来，得换成对"不合格的行"做否定。

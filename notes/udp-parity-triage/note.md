## 03 · array 的定案：回去数语料

解决方式不是拍脑袋，是回去数 6500 条语料里两种函数各出现在什么语境：

```compare
first: 函数
head: [出现条数, 长什么样]
rows:
  - "`find_in_set`": ["30 条", "`and (((find_in_set('11', attr_array)) or (find_in_set('32', attr_array))))` —— **关系属性**，逗号串"]
  - "`array_contains`": ["26 条", "`ARRAY_CONTAINS(CAST(IFNULL(ELEMENT_AT(properties, 'option_ids'), '[]') AS ARRAY<VARCHAR>), '1')` —— **事件属性**，JSON 数组"]
```

结论很干净：**圈选路径（画像 / 关系属性）的数组列是逗号串**，`array_contains` 属于事件 JSON 数组那条链路。于是编译器改掉：

```sql
-- 改前（错）：array_contains(`u`.`tags`, 'CN')
-- 改后（对齐现网）：(find_in_set('CN', `u`.`tags`))
-- 多值语义：has = 任一项命中（OR）；not_has = 每一项都不包含（AND）
```

这一改，**17 条执行报错直接清零**。

## 04 · 主角：一条被数据抓住的语义误读

### 4.1 那句话长什么样

现网对「关系 + 计数 + 属性过滤」编译成这样（两次"不在"套在一起）：

```sql

```

**我当时把它读成了「每一行都得满足属性」。** 理由听起来很顺：两层否定叠起来，不就是"不存在不满足的行"吗？

不是。下面两个控件把这三层拆开看 —— 先别看结论，**自己点一遍**。


### 4.3 为什么"两层层套"看起来像 A、其实是 B

关键在第 ② 层判断的对象：

| 层 | SQL 在做什么 | 判断的是 |
| --- | --- | --- |
| ① | 从关系表里查「满足属性」的行 | **行** → 得到"至少一行合格"的人 |
| ② | 从关系表里查「主人的 uid 不在①的名单里」的行 | **人**（这行的主人有没有合格过）→ 得到"有记录、但一次都没合格过"的人 |
| ③ | 从全体人里去掉② | **人** → 剩下"从没记录的人" + "至少合格过一次的人" |

第 ② 层只会收**一次都没合格过**的人。一个人哪怕有 10 行不合格，**只要有一行合格，他就不会进第 ② 层**，也就不会被第 ③ 层踢掉。

> 否定的是"**合格的**行" → 问的是"**有没有**合格的"；
> 想表达"**每一行都**合格"，得拿"**不合格的**行"去做否定 —— 那是另一个写法（我们原来那句 `不存在(有不合格的行)`）。

一个字的差别，值 **117 个人**。

### 4.4 实测把它钉死

在本地种子库上，三种语义各跑一遍（case `937061`）：

| 语义 | 人数 |
| --- | --- |
| 总行数 > 0 | 4021 |
| **B：存在一行满足**（现网语义，= UDP 记录 SQL 的结果） | **0** ✓ |
| A：每一行都满足（我原来的实现） | 117 ✗ |

UDP 的记录 SQL 返回 **0**，和我实现的 117 对不上 —— 数字不会骗人。这比"再读一遍源码"有用得多。

### 4.5 改了什么

```sql
-- 改前（A：要求每一行都满足）
AND NOT EXISTS (SELECT 1 FROM 关系表 r WHERE r.uid = u.uid AND NOT (props))

-- 改后（B：没有行，或存在一行满足）
AND (NOT EXISTS (SELECT 1 FROM 关系表 r WHERE r.uid = u.uid)
     OR EXISTS   (SELECT 1 FROM 关系表 r WHERE r.uid = u.uid AND (props)))
```

同时把**文档里那条写错的结论**改正，并把三个实测数字留在原地 —— 免得以后又有人（包括我）把它读回去。

剩下的 17 条长这样（case `1094803`）：

| | SQL（节选） | 人数 |
| --- | --- | --- |
| 我们 | `… OR u.uid IN (231368439, 231436539, …)` | 384 |
| 现网 | `… union all select uid from (SELECT 231368439 AS uid UNION ALL SELECT 231436539 AS uid UNION ALL …) uidt` | 403 |

现网是**用字面量凭空构造 uid**（表里没有的 uid 也会出现），我们是 `uid IN (…)` 过滤主表（表里没有就不出现）。只影响"不在表里的 uid"，属于**已登记的结构差异**，不是编译器 bug。

## 09 · 自测

```quiz
- q: 翻译器"一个条件节点里的多个叶子只取第一个"这个 bug，为什么在结果级对拍里一下就能看见？
  a: |
    因为结果级比的是**人的集合**。少一个叶子 = 条件变宽 = 圈出来的人变多，
    人数立刻和现网不一样；而文本级对拍如果只挑了"第一个叶子"去比，
    两边可能都对得上 —— **少的那部分根本不在比较范围里**。
- q: 「计数 ≥ 3 且属性 ≥ 10」里，现网对属性的要求是下列哪一个？
    ① 每一行都满足属性 ② 至少有一行满足属性 ③ 满足属性的行数 ≥ 3
  a: |
    ②。「计数」数的是**总行数**（不是合格行数），属性能是个"存在性"要求，两者取交集。
    实测：本地种子上 ② = 0 人，与现网记录 SQL 一致；① 会得到 117 人。
- q: 为什么第 ② 层（中间的"不在"）只会收"一次都没合格过"的人？
  a: |
    因为它的判断条件是"这行的主人 uid 在不在第 ① 层名单里" —— 判断对象是**人**，不是这一行。
    主人合格过一次，他的**每一行**都不满足这个条件，于是这个人根本不会进第 ② 层。
    想把"有某些行不合格"表达出来，得换成对"不合格的行"做否定。
```

圈选组件包的全景：22 个文件 2795 行；读模型（pb → resolve）、草稿 vs DSL、Metadata 五件套、包的地图与依赖面。协议在 @insight/dsl，编译器在 @insight/sql-builder。

运营在圈选页点了几下：客户范围 = 本人，加一条「总资产 ≥ 100 万」，再粘贴一批 UID。这些下拉框、条件组、AND/OR 开关，全都不是洞察子应用自己写的，它们来自一个独立的 Vue 组件包 @insight/combination。

这个包 22 个文件、2795 行。它的活可以一句话说完：把 Metadata 渲染成圈选界面，把人的操作变成一份叫 DraftQuery 的草稿。草稿协议本身住在 @insight/dsl，它只是消费方；草稿怎么变成 SQL，它也不管。

这篇回答三个问题：

  • 它在整条链路的哪个位置，边界在哪？
  • 「受控组件」「草稿」「DSL」「Metadata」这几个词各自指什么？
  • 包里的 22 个文件怎么分工，协议为什么搬去了 @insight/dsl？

每个控件怎么决策、候选值怎么加载、草稿怎么被检查，在机制篇。

01它在哪条链路上

一次圈选预览要穿过四层。组件包住在第二层，上面吃 Metadata，下面把草稿交给宿主。

LAYER 01 元数据层 字段、关系、操作符的定义与物理映射，只有 Data Admin 能写
Data Admin（MySQL） crm_dc_portrait / crm_dc_relation / ... 写
CrowdMetadata GET /api/audience/metadata 的 pb 投影 读
ResolvedCrowdMetadata 壳里 resolve 出来的内部模型 解析
宿主拉一次 Metadata 传给壳；壳先 resolve 再喂给子树组件自己不发请求
LAYER 02 组件层 —— 这个包在这里 把 Metadata 渲染成界面，把操作变成草稿
InsightCombiner 壳：props 进、草稿事件出 12 个 .vue
DraftQuery 允许半填的编辑中间态（协议在 dsl） 9 个 .ts
宿主在提交前调 buildQuery组件只抛变更，不提交
LAYER 03 提交与校验 草稿收窄成 DSL，服务端再查一遍
buildQuery(draft) 结构完整性检查，实现也在 dsl @insight/dsl
服务端校验+编译 validateStructure + Semantics → compile @insight/sql-builder
SQL 交给 DAL组件对这一层不可见
LAYER 04 执行层 活查预览、异步快照
countSql / listSql / uidsSql 同一段 WHERE，四种外层 compile 产物
DAL → Doris 预览同步，快照异步 执行

技术方案给这个包画了很清楚的边界：不绑定具体 HTTP 接口，不生成 SQL，也不连接数据库。三件事都推给了别人：

  • 发请求 —— 候选值的加载函数由宿主注入（loadValueSet / searchValues 两个 props）
  • 生成 SQL —— 那是 @insight/dsl 的事，组件只产出 DSL 的输入（草稿）
  • 连数据库 —— 它连 Catalog 都不拿，物理表名列名对组件不可见

02受控组件：草稿的真相在宿主手里

modelValue 的类型是 DraftQuery。宿主用 v-model 持有它，组件在任何操作之后生成一份新的草稿对象抛出来，自己不保存、也不修改传入的东西。

@insight/combination
宿主持有草稿 const query = ref(createEmptyQuery())
props.modelValue DraftQuery
渲染界面 10 个子组件按 Metadata 渲染
用户操作 选字段 / 切操作符 / 填值 / 加组
生成新草稿 { ...旧草稿, 改动的那一片 }
emit(update:modelValue) 组件到此为止
宿主赋回 v-model 回到 props，循环闭合

组件包内部那五步（虚线）是纯计算：旧草稿 + 用户操作 = 新草稿。最后一格的赋值是宿主的事，赋回之后 props 变了，从渲染那格重新走一遍，循环闭合。为什么这么设计？因为草稿的真相只在宿主手里，组件无权改它；宿主也就有机会在接收前做处理，比如异步收窄 scope（机制篇 06 节）。

demo 宿主（apps/client/src/App.vue）的接法：

<InsightCombiner
  v-model="query"
  :metadata="metadata"
  :load-value-set="loadValueSet"
  :search-values="loadSearch"
  :data-level="dataLevel"
  :groups="visibleGroups"
>
  <template #scope-prefix>…模拟身份切换…</template>
</InsightCombiner>

组件对外的全部接口就这些：

prop 类型 干什么
modelValue DraftQuery 圈选草稿，v-model 绑定
metadata CrowdMetadata Data Admin 的 pb 读模型；壳内部 resolveCrowdMetadata() 转成 ResolvedCrowdMetadata 再喂子树
dataLevel 'self' | 'team' | 'all' 当前登录人的数据级别
groups {id,name}[] 可见团队，team 范围的选项
scopeReady boolean（默认 true） 身份加载完了吗，没好不收窄
loadValueSet (setKey) => Promise<ValueItem[]> 宿主封装的值集合加载
searchValues (resolverKey, keyword) => Promise<ValueItem[]> 宿主封装的动态候选搜索
lookupValues (resolverKey, values) => Promise<ValueItem[]> 按 value 反查 label，回显已保存取值
事件 update:modelValue 唯一的业务事件，参数是新草稿
插槽 scope-prefix 范围选择器上方的一块地（demo 放了身份模拟器）

03草稿与 DSL：两个长得像的类型

草稿和 DSL 的结构几乎一样，差别只有一条：草稿允许半填，DSL 必须完整。刚新增一条条件、只选了字段还没选操作符、区间只填了一端，都是合法草稿，但不许提交。

  • DraftQuery 组件对外协议 version: 1, scope, include, exclude
    • scope 客户范围叶子：self / team(groupIds) / all
    • include DraftTree | null 界面只渲染这一块
      • group logic: 'AND' | 'OR' 条件组，children 混放三种叶子
        • DraftPortrait field + op + value?
        • DraftRelation relation + formula(detail|times) + objects? + props?
        • UidLeaf op: in|not_in + uids[]
    • exclude DraftTree | null 结构支持，本期界面没有编辑入口

同样的条件在两个状态下的样子：

草稿 · 编辑中 DraftQuery.include 
{
  "type": "portrait",
  "field": "aum_hkd",
  "op": "gte"
  // value 还没填 —— 合法
}

组件的日常状态。buildQuery 会在这一步抛 INCOMPLETE_LEAF。

用户填入 1000000
DSL · 可提交 InsightQuery.include 
{
  "type": "portrait",
  "field": "aum_hkd",
  "op": "gte",
  "value": 1000000
}

buildQuery 的产物。服务端在这个基础上做语义校验和编译。

内容 草稿 DraftQuery DSL InsightQuery
字段、关系、操作符 可以是 ''、未选 必填，且 op 合法
值 缺失、半填都行 按 op 给标量 / 数组 / 区间
关系 objects 可以不填 detail 必须非空；times 可省
关系 props 属性条件可以半填 写出时必须 logic + 完整 items
谁产生 组件，随时 调用方调 buildQuery(draft)

两个类型的关系是刻意的，测试文件里有一行类型断言：

type _legalQueryIsDraft = Expect<InsightQuery extends DraftQuery ? true : false>;

合法的 DSL 一定能当草稿用。所以「打开一张历史 DSL 回显」不需要转换，直接塞回组件就行；反方向才需要 buildQuery 收窄。

10-12 的重构把这两个类型和 buildQuery 一起搬进了 @insight/dsl：组合包的 draft.ts 现在只有 3 行，纯粹再导出 —— 组件和 BFF 共用同一份协议，错误码自然也还是同一套。

04Metadata：组件吃进去什么

metadata prop 是 Data Admin 的 pb 读模型 CrowdMetadata（由服务端从 crm_dc_* 那批表投影出来，那条线在配置层那篇）：camelCase、I18n 是 zhCn/zhHk/en、status 是数字、类型信息嵌在 fieldType 里。壳拿到它就调 resolveCrowdMetadata() 转成内部模型 ResolvedCrowdMetadata，子组件只消费解析后的模型。两种形状都没有表名和列名，只有业务语义：

字符串

revision

这份投影的内容哈希（字符串），任一条状态或文案变化都会变

树

domains

业务域树，字段的分组菜单按它长

字典

operators

扁平操作符列表：key、多语言名、排序，相对时间带 template

主体

features

画像特征。每条带自己的 valueSource

主体

relations

关系。客体在关系上，属性挂在 properties 里；isPrimaryKey: 1 的属性会被自动带上（见组件内幕）

每条 feature / 关系属性身上都背着同一组形状四元组。组件里所有的「该显示什么」，追到底都是这四个字段决定的：

variableType

enum（枚举）或 range（非枚举）。决定操作符家族

dataType

long / double / string / boolean。决定值长什么样

contentType

0 普通、1 日期、2 时间、3 金额、7 城市……决定相对时间操作符和控件形态

enumType

none / custom / value_set / dynamic。决定候选值从哪来

候选值来源单独说。同一个「值输入框」，四种字段的加载方式完全不同：

valueSource候选值在哪什么时候到手
NONE没有候选值不加载，控件形态由 controlFor 决定
CUSTOM就带在 Metadata 里（items 数组）组件拿到就可用，零请求
VALUE_SET共享值集合，字段上只有 setKey下拉打开时调宿主注入的 loadValueSet，宿主侧缓存
DYNAMIC字段上只有 resolverKey（如 stock_search）输入关键词后调 searchValues；已保存取值调 lookupValues 反查 label

CUSTOM 和 VALUE_SET 的条目都带 status，停用的候选值照样返回：新建条件只用 ENABLED，回显旧条件时按 value 找回 label。DYNAMIC 没有停用态，已选值不在搜索结果里时靠注入的 lookupValues 补 label，补不到才显示原值。

非 Vue 的部分

packages/combination/src 的 TypeScript 层9 个文件 · 按行数排
query.ts (85)

草稿工厂和纯函数。建空查询/空组/各类叶子、加组加叶、clampScope 收窄、parseUids 粘贴解析。全部是无副作用的纯函数，好测。

values.ts (69)

候选值组合式函数。CUSTOM 直取、VALUE_SET 加载（带过期票据防竞态）、DYNAMIC 的 search / resolve 两个函数缓存。

messages.ts (155)

三语言文案。zh-CN / zh-HK / en，同一份 key。界面上的字只有两个来源：这份文件和 Metadata 里的多语言名。

index.ts (51)

导出面。默认导出组件 + 草稿工厂；协议那半边（buildQuery、OP_LABELS、resolveCrowdMetadata、类型）全部从 @insight/dsl 再导出 —— 宿主只 import 一次。

label.ts (28)

useLabel()。取多语言名的回退链：当前语言 → zh-CN → zh-HK → en；t() 支持带参数（相对时间模板用）。

relationDraft.ts (17)

新建关系行的草稿工厂。选中关系时按 isPrimaryKey === 1 的属性自动补上属性过滤（跳过 uid / object_id 这类主体列）。

conditionKey.ts (13)

下拉的 key 前缀。field:xxx / relation:xxx。特征和关系混在同一个级联菜单里，选完靠前缀分回去。

context.ts (7)

三个注入 key。loadValueSet / searchValues / lookupValues 的 Symbol，provide 在壳里，行组件和值控件在任意深度 inject。

draft.ts (3)

一行注释 + 一整组再导出。草稿协议与 buildQuery 的实现住在 @insight/dsl，组件和 BFF 共用同一份。

它借了 @insight/dsl 的什么

依赖方向还是一条直线，但 10-12 之后变了性质：apps/client → @insight/combination → @insight/dsl，而 @insight/dsl 现在是协议全家（类型、草稿、操作符、形状判定），编译器新拆去了兄弟包 @insight/sql-builder。组合包对 dsl 的 31 处 import 全部走包根，不再有子路径：

借的东西在哪用在哪
协议类型@insight/dsl 包根CrowdMetadata / ResolvedCrowdMetadata / DraftQuery 全家 / ValueSource / OperatorMeta
草稿与校验同上buildQuery、portraitDraft / blankDetail 等构造函数 —— 组件不再自己维护一份
操作符表同上OP_LABELS / opLabel / RELATION_DETAIL_OPS / RELATION_TIMES_OPS / UID_OPS（OPERATOR_DISPLAY 是 dsl 里的唯一来源）
形状判定同上applicableOps / controlFor / isTemporalContent —— 控件决策引擎，机制篇 03 节的主角
读模型解析同上resolveCrowdMetadata()：pb 形状 → 组件内部模型
时区换算同上clock：日期控件显示的字符串 ↔ Unix 秒
错误类型同上CompileError —— 结构校验的错误码，和编译器共用

UI 依赖是 element-plus（全套控件）和 vue-i18n（文案）。除此之外没有别的运行时依赖。

06继续往下

  • 组件图鉴：12 个组件的真实渲染截图、每个的对外接口、拆分依据与五层数据流。
  • 组件内幕：components/ 里每个组件的父子联系、内部状态与数据流，全部对到当前代码。
  • 机制篇：受控数据流的实现、一行怎么长出来（幽灵行与 convert）、控件决策引擎、候选值三条管道、buildQuery 检查清单、scope 收窄，每节配可操作的交互。
  • 配置层那篇：Metadata 从 MySQL 到读模型投影的那条线，含停用字段的回显规则。
  • @insight/dsl 那篇：草稿协议和 DSL 之后怎么被校验、编译成 SQL（注意那篇写的是拆分前的代码）。
组件里用户填到一半的条件（还没选操作符）存在哪？存在组件里吗？

不在。组件是受控的：草稿的真相在宿主手里（v-model 绑的 ref）。 组件每次操作都生成一份新草稿对象抛给宿主，自己只留展开状态这类临时 UI 状态。 组件销毁重建，草稿也不丢 —— 因为它从来没在组件里住过。

草稿和 DSL 为什么分成两个类型，而不是一个？

编辑是允许中间态的：只选字段不填值、区间只填一端，都必须能在界面上活着。 提交是另一回事：DSL 必须完整才能被编译。buildQuery(draft) 是两个状态之间唯一的关口， 它抛的错误码（INCOMPLETE_LEAF 等）和 SQL Builder 共用一套。

组件需要知道字段对应数据库里哪张表哪一列吗？

完全不需要。两份读模型投影里都没有表名列名，Catalog（物理映射）只发给 Node BFF 侧的编译器。组件连 Catalog 都拿不到，这是「DSL 与物理模型解耦」在组件侧的体现： 新增一个字段只改元数据，组件和 SQL Builder 都不用发版。

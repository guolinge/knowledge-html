从字节看懂 HTTP/1.1 与 HTTP/2：报文、分块和帧

从十六进制和 TCP 字节流入手，逐步看懂 HTTP/1.1 的头部、消息体和 chunked，以及 HTTP/2 的帧头、流和多路复用；结合可互动的真实字节样例。

标签 网络协议 HTTP HTTP/1.1 HTTP/2 TCP HPACK

在浏览器里访问一个地址，客户端和服务器要交换 HTTP 请求与响应。底下的 TCP 负责传送字节，但它不会替 HTTP 标出“这一条请求到哪里结束”。

这篇用同一组可核对的字节，回答四个问题：字节和字符有什么关系？HTTP/1.1 怎么确定头部与消息体？chunked 在哪一层工作？HTTP/2 的帧又怎样分开、归属到不同请求？

先认识三个东西：字节是这里最小的计数单位，一个字节有 8 位；报文是一次 HTTP 请求或响应；帧是 HTTP/2 组织数据的单位，一条请求或响应可以由多个帧组成。

01字节、十六进制和字符

先看 GET 的三个字节。下面三行只是同一份数据的不同展示方式：

二进制写法     01000111   01000101   01010100
十六进制写法      47         45         54
按 ASCII 显示      G          E          T

例如，一个字节的值 0x47，按 ASCII 解释是 G。47 是十六进制写法，不代表传输了字符 4 和 7；那两个字符分别是字节 0x34 和 0x37。

ASCII 还约定了控制字符。回车是 0x0d，换行是 0x0a，两个连起来常写成 \r\n。\r\n 是方便阅读的记号，实际是两个字节，不是反斜杠和字母组成的四个字节。

0d 0a\r\n回车加换行，不能直接显示成图形

十六进制转储左边的数字是什么？

下面是一次请求的开头。中间每两个十六进制数字代表一个字节；右边是按 ASCII 显示的样子。

0000  47 45 54 20 2f 68 65 6c 6c 6f 20 48 54 54 50 2f  |GET /hello HTTP/|
0010  31 2e 31 0d 0a 48 6f 73 74 3a 20 31 32 37 2e 30  |1.1..Host: 127.0|

0000、0010 是工具加的偏移量：本行第一个字节从整份数据的哪里开始。偏移从 0 数起，用十六进制表示；0x10 等于十进制 16，所以第二行从第 16 个字节开始。偏移量本身没有在请求里传输。

右侧的 . 有时是不可打印字节的占位符，有时是真正的句点 0x2e，要结合中间一列看。本页的互动字节带用 · 标示不可打印字节，真实句点仍显示为 .。

📌

这份请求的字母和标点可以按 ASCII 阅读，行尾还有不可打印的回车、换行。文本也不只限于 ASCII；例如中文通常会用 UTF-8 等编码。HTTP 消息体还可能是一张图片或其他任意字节。

02TCP 交付字节，不交付 HTTP 消息

TCP 在连接的每个方向上提供有序字节流。假设发送方一次写入以下内容：

GET /hello HTTP/1.1\r\n

接收方完全可能分三次读到：

第 1 次读取    GET /he
第 2 次读取    llo HTTP/1.
第 3 次读取    1\r\n

这是一个示意，三段拼起来还是发送方写出的字节。实际每次读到多少取决于缓冲区、数据到达时机等；一次读取也可能包含多次写入的数据。

TCP 负责传输

在连接正常时按顺序交付字节，并处理传输中的丢失和重传。连接也可能失败，应用需要处理提前结束或错误。

HTTP 负责解释

HTTP 接收字节、保存解析进度，并按协议判断头部、消息体或帧的边界。不能把一次 read 当成一条完整报文。

发送方调用 write 的次数、TCP 分段、接收方调用 read 的次数，以及 HTTP 的消息或帧边界，是不同层面的事情。HTTP/1.1 和 HTTP/2 都要面对这个字节流。

03HTTP/1.1：空行之后，还要判断消息体

一条 HTTP/1.1 请求报文通常由起始行、头部字段、空行和可选的消息体组成。下面的 \r\n 用来标出真实的行尾；额外的排版换行、箭头和中文注释都不是传输的内容。

GET /hello HTTP/1.1\r\n              ← 起始行
Host: 127.0.0.1:18080\r\n             ← 头部字段
User-Agent: curl/8.7.1\r\n            ← 头部字段
Accept: text/html\r\n                 ← 头部字段
\r\n                                  ← 空行：头部结束

起始行里的 GET 是方法，/hello 是请求目标，HTTP/1.1 是版本。ASCII 告诉我们字节对应什么字符；HTTP 的语法告诉我们这些字符各代表什么。

空行结束的是头部，不一定是整条报文

最后一个字段行的结尾是 \r\n；紧跟着的空行又是一个 \r\n。所以常在字节里看到 0d 0a 0d 0a。如果消息有 body，body 从这之后开始，但不能只靠空行知道它有多长。

Content-Length 里的数按十进制理解，单位是字节，不是字符。例如 hello 是 5 个 ASCII 字节；你好 用 UTF-8 编码是 6 个字节。

04chunked：HTTP 自己给每块写长度

当发送方开始发送时还不知道消息体总长度，可以使用 HTTP/1.1 的 Transfer-Encoding: chunked。它把内容编码成若干块，每块先写长度，再写数据；最后用长度为 0 的块收尾。

假设应用要发送 Hello world。下面是编码后的消息体；\r\n 仍代表两个真实字节，排版换行不另计：

5\r\n
Hello\r\n
6\r\n
 world\r\n
0\r\n
\r\n
第 1 块 5 → Hello 长度是 5，接收方读取后面的 5 个字节
大小行 5\r\n 长度 5
数据 Hello 5 字节
块后行尾 \r\n 2 字节
继续读下一块接收方已经知道第一块结束在哪里
第 2 块 6 → 空格 + world 前面的空格也是内容，所以一共 6 个字节
大小行 6\r\n 长度 6
数据 ␠world 6 字节
块后行尾 \r\n 2 字节
没有更多数据仍要读取结束块和尾部结束
结束 0 → 不再有数据块 本例没有尾部字段，0 行后面的空行标记编码结束
结束块 0\r\n 长度 0
尾部结束 \r\n 空行

把大小行、行尾和结束标记去掉，应用拿到的是 Hello world，共 11 字节。本机的完整 HTTP/1.1 响应是 99 字节，其中下面展示的分块编码部分占 26 字节。

一步一步读取两个 chunk 先按接收方的步骤走，再切到“应用拿到的内容”

块长度写成十六进制字符：例如 A 表示十进制 10，字符 A 自己的字节值是 0x41。解析器读完长度行后，按长度读取数据；即使数据内部包含 \r\n，也不会误当成块结束。

💡

chunked 是 HTTP/1.1 对消息体的编码方式，不是 TCP 的发送开关。一个 chunk 可以被分多次 TCP 读取，一个读取也可能包含多个 chunk。已知总长度时，Content-Length 也可以用于边生成边发送。

05找边界的工作与出错的风险

扫描头部，不等于扫描整份消息体

HTTP/1.1 的头部没有固定的总长度；接收方要找到每行结尾和结束头部的空行。头部越长，要检查的头部字节通常越多。

但头部解析完之后，如果规则给出 Content-Length: 8，接收方就按数量读取 8 个字节；如果是 chunked，就逐块读长度行，再按该块长度读取。不需要在整段 body 里搜索 \r\n\r\n 来找结束位置。 接收和消费数据本身仍然要花时间，也不能跳到 TCP 中尚未到达的字节。

body 里有空行，会不会误判？

下面的 body 是 ab\r\n\r\ncd。其中 \r\n\r\n 确实出现在内容里，但它总共仍是 8 个字节：

Content-Length: 8\r\n
\r\n
ab\r\n\r\ncd

body 的 8 个字节：61 62 0d 0a 0d 0a 63 64

正确的解析器已经在第一个空行后进入了“读取 body”的阶段；按长度读满 8 个字节即可。body 中的换行是数据，不会被当成第二个头部结束符。

如果长度给错了呢？

假设发送方本来想把 hello 作为第一条请求的 body，后面紧接着下一条请求 GET /next…。保持字节不变，只改变假设声明的长度，看接收方会把哪里当成下一条的开头：

同一串字节，长度错一位会怎样？ 分别点长度 4、5、6；每个读法再点“下一步”

在客户端、前端代理和后端服务器之间，如果不同设备对同一段请求使用了不同的边界，后端可能把前端当作 body 的一部分字节解释成另一条请求。这类请求走私的关键是解析结果不一致；不是 body 里出现 \r\n\r\n 就会发生。

⚠

发送方不得在同一条 HTTP/1.1 报文中同时发送 Transfer-Encoding 和 Content-Length。对收到这两个字段的普通请求，Transfer-Encoding 优先；服务器可以拒绝，或仅按它处理，但响应后必须关闭连接。选择转发的中间设备还须先移除收到的 Content-Length。完整条件见 RFC 9112 §6.1 和 §6.3。

06HTTP/2：每帧开头固定 9 个字节

HTTP/2 不再用 HTTP/1.1 的 chunked 格式组织消息体。它把通信数据组织成帧：每帧先有固定 9 字节的帧头，后面跟长度可变的载荷。

HTTP/2 仍然可以有 Content-Length 头字段，但它和帧头里的 Length 不是同一个东西：后者只说明当前帧的载荷有多长。

假设流 1 已由之前的 HEADERS 帧建立，下面是一个 DATA 帧。它的载荷是 hello；此例没有填充字节。竖线仅用于分组，不是实际传输的字节。

00 00 05 | 00 | 01 | 00 00 00 01 | 68 65 6c 6c 6f
  长度     类型  标志      流编号           载荷
   5      DATA  结束       1              hello
14 字节的 HTTP/2 DATA 帧 逐步读取帧头，再看后面的载荷

判断这一帧到哪结束，只需知道帧头位置和载荷长度：00 00 05 是整数 5，接收方在 9 字节帧头后再消费 5 字节。它不需要在载荷中搜索结束符，但仍需接收字节、校验帧，并按帧类型处理内容。

这个长度不一定等于整条 HTTP 消息体长度，也不总是应用正文长度：例如 DATA 帧可以带填充；HEADERS 或 SETTINGS 帧的载荷装的是其他信息。

每帧都要额外带 9 字节帧头；帧头里的整数和标志也不能像普通文本一样直接阅读，排查时通常需要协议解码工具。分帧带来的组织能力并不保证每次请求都比 HTTP/1.1 快。

Length 是 24 位，能表示的最大载荷长度是 2²⁴ − 1 = 16,777,215 字节。实际每帧能发多少由接收方的 SETTINGS_MAX_FRAME_SIZE 限定，初始为 16,384 字节，可设置得更大；部分帧类型还有自己的大小限制。一个较大的消息体可以分成多个 DATA 帧。

07流编号让不同请求的帧可以交错

**流（stream）**是 HTTP/2 一条连接中的逻辑通道。一次请求及其响应通常使用同一流编号：客户端和服务器各自按这个编号发送帧。流不是另一条 TCP 连接。

接收方按帧头里的流编号归属数据；帧仍通过同一个方向的字节流依次到达。

这里依靠的是分帧、流编号和流状态等规则一起工作，不只是“知道长度就能交错”。例如，一组尚未结束的 HEADERS / CONTINUATION 字段块必须连续发送，不能在中间插入其他流的帧。

HTTP/2 可以减少 HTTP/1.1 在同一连接上等待前一个响应的限制，但它仍运行在 TCP 之上：如果 TCP 某段字节丢失，后面的字节可能都得等待重传，这会影响同一连接上的多个流。实际快慢还取决于网络、实现和服务器行为。

110 字节：前言、两个控制帧、一个请求头帧 按顺序点“下一步”；第二种读法对应 HEADERS 的内容

HPACK 是 HTTP/2 的头字段压缩格式。它既能引用预定义的静态表，也能在条件允许时使用动态表和 Huffman 编码；动态表会受大小限制并可能淘汰条目，通信双方需要维持各自方向上的编码／解码状态。37 字节的字段块经解码后得到：

:method:    GET
:scheme:    http
:authority: 127.0.0.1:18081
:path:      /hello
user-agent: curl/8.7.1
accept:     */*

帧边界与头字段压缩是两件事：帧头告诉解析器载荷在哪里，HPACK 才告诉它这些字节表示哪些字段。一个字段块也可能跨 HEADERS 和 CONTINUATION 帧，不能只靠“跳过载荷”来完成 HTTP 的全部处理。

本例使用明文的本地 HTTP/2。通常访问 HTTPS 时，HTTP/2 帧会经过 TLS 加密后再交给 TCP；直接查看网络上的 TCP 字节，通常先看到的是 TLS 记录和密文，需要解密才能看到帧。

HTTP/3 的 QUIC 流在传输层分别交付：丢失某条流的数据时，不必像 TCP 的单条字节流那样等待缺失位置之后的所有流。若一个丢失的 QUIC 包包含多个流的数据，这些流都可能受影响；共享拥塞控制、流量控制或 QPACK 状态也可能带来等待。因此它不是“任何情况下都没有阻塞”。

回到最初的问题

TCP 传的是字节；ASCII 是解释部分字节的一种方式。HTTP/1.1 先按行读头部，再用长度、分块等规则确定消息体；HTTP/2 用固定帧头中的长度确定帧边界，再用流编号组织帧。

头部结束、一个帧结束、整条消息结束，是不同的问题。

自测

一条 HTTP/1.1 请求没有 Content-Length，也没有 Transfer-Encoding。空行后还要等 body 吗？

不需要。按 HTTP/1.1 的请求定界规则，这种请求的消息体长度为 0。普通响应在没有其他长度规则时，则可能以连接关闭确定结束。

chunked 是 TCP 的分包开关吗？

不是。它是 HTTP/1.1 对消息体的编码：每块写十六进制长度和数据，最后用 0 长度块与尾部结束。TCP 的发送、分段和读取边界不等于 chunk 边界。

Content-Length 为 8，body 是 ab\r\n\r\ncd，内容里的空行会结束消息吗？

不会。解析器已经进入读取 body 的阶段，并按长度消费 8 个字节；其中的 \r\n\r\n 是内容。

HTTP/2 帧头里 Length 是 5，是不是整个响应只剩 5 字节？

不是。它只表示当前帧的载荷是 5 字节，不含 9 字节帧头；一条响应可以有多个帧。发送方向是否结束还要看 END_STREAM 等流状态。

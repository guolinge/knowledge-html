拆进程还是开线程：别背口诀

「CPU 密集用进程、I/O 密集用线程」把一个多维权衡压成了一维，而且压缩的那个维度排在第五问。走一遍真实的检查顺序，再看三个生产架构怎么分层。

标签 操作系统 选型 多进程 多线程 GIL 并发

01口诀错在哪

你一定听过这句话：

「CPU 密集用进程，I/O 密集用线程。」

它没错，但没用到点上 —— 它把一个多维的权衡压成了一维。

📏

问题是：阻塞特征（CPU 密集 / I/O 密集）只是众多维度里的一个， 而且它自己还依赖运行时。

在你走到「它是 CPU 密集还是 I/O 密集」这一问之前， 至少还有四问挡在前面：要不要隔离？要不要共享内存？共享多少？ 固定开销扛不扛得住？

口诀只配做最后一步的注脚，不能当第一步。

02走一遍真实的检查顺序

选型决策树 点选项往下走 —— 注意阻塞特征排在第几问

走完之后回头看一眼路径条：「CPU 密集还是 I/O 密集」出现在第五问， 前面四问都是结构约束。

七个维度可以分成两层：

层次维度它约束什么
结构约束故障隔离与安全边界跑不可信代码必须进程化 —— 硬需求，没有替代方案
结构约束共享数据的规模与通信频率共享多且频繁 → 线程；高频小消息 → IPC 序列化成本会吃掉一切
结构约束单任务内存与固定开销每线程 8 MiB 虚拟栈 vs 每进程一套页表与资源结构
环境约束运行时限制语言运行时决定「线程」是否等于「并行」
环境约束调度规模64 位 Linux 单进程实测约 32K 线程；超过这个量级答案不再是「更多线程」
环境约束可观测性进程边界清晰（perf / ps / 崩溃栈分层）；线程级观测要另找工具
环境约束部署模型独立发布、独立限流、独立重启、灰度 —— 这已经不是性能问题，是交付问题

03为什么结论不能跨运行时搬运

这是口诀最坑人的地方 —— 同一个问题，换个语言答案就变了。

运行时线程能真并行吗于是 CPU 密集该用什么
Python不能 —— GIL 让同一时刻只有一个线程执行字节码进程（绕开 GIL）
C++ / Rust / Java / Go能线程（更轻）
Node.js主线程单条事件循环worker_threads（每个 worker 有独立 V8 isolate）或子进程

Python 生态的共识本身没错：多线程适合 I/O 密集（等待时让出 CPU 隐藏延迟）， 多进程适合 CPU 密集（绕过 GIL 获得真并行）。

🐍

但把 GIL 的结论搬到别处就是错误泛化。

「Python 的 CPU 密集要用进程」这个结论， 根因是 GIL，不是「CPU 密集」这个属性本身。

把它搬到 C、Java 或 Node worker 上，前提就已经不成立了。++

所以问「线程还是进程」之前，先问一句： 在这个运行时里，「线程」到底等不等于「并行」？

04I/O 密集 ≠ 必须多线程

这条可能是最反直觉的：高连接数场景的正确答案，通常不是「更多线程」。

十万连接 → 十万线程？（不是）
十万连接的真实解法
十万个线程 每个都在等 fd 就绪
事件循环 · epoll / kqueue 一个线程管住十万个 fd 的等待
调度器名单上十万个实体 其中绝大多数什么也没干
核数级别的小线程池 只接手会真正阻塞的活：磁盘、同步库

线程池的规模是「核数级别」，不是「连接数级别」。

🔢

顺便修正一个时间观：线程数上限的「民间传说」大多来自 21 世纪初。

现代多核大内存机器上，单进程跑一万线程在生产环境是可以做到的。 真正的约束是栈大小：Linux 默认每线程 8 MiB 虚拟内存， 一万线程约 80 GiB 虚拟地址 —— 但常驻只有实际用到的那些（约 80 MiB 量级）。

这个 8 MiB 是虚拟地址空间预留，页是按需分配的 —— 「一万线程 × 8MB = 80GB 内存」是个流传很广的误算。

调小栈（pthread_attr_setstacksize / ulimit -s）是常规手段， 小栈还能让失控递归更快失败。再往上就混入协程式异步。

05生产架构不是二选一，是分层组合

真实系统几乎从不「只多进程」或「只多线程」，而是在两层之间分层。

案例一 · 浏览器

  • function sub() { [native code] }

进程层负责「谁跟谁一起死」，线程层负责「谁跟谁一起跑」—— 两层各管一件事。 一个 tab 崩了只带走它自己那个渲染进程；而渲染进程内部，几十个线程照样并行干活。

Chromium 官方讲得很直白：每个标签页一个独立进程，单个窗口的 bug 或失控脚本 不连累浏览器整体。

代价是每窗口一份固定内存。 Google 的赌注是总体膨胀反而更少 —— 内存紧张时，操作系统可以把不活跃的窗口整个换出（swap）。 线程模型做不到这么粗粒度的调度。

案例二 · Web 服务

master
worker 内部
master 进程 bind 监听 · 拉起崩掉的 worker · 平滑重启
事件循环 accept 新连接 —— 多核靠 worker 的数量
线程池 磁盘、同步库这类真会阻塞的活
只读共享的进程内缓存 共享状态靠线程，省掉序列化

三层各答一题，这个分工值得单独记：

层它解决什么为什么不能换
多个 worker 进程多核一个 worker 只有一个事件循环，单进程用不满多核
事件循环并发连接数事件循环里不能有阻塞调用，否则整个 worker 卡住
线程池阻塞任务磁盘 I/O 与同步库的活必须有人接手
进程内只读缓存共享状态进程间共享缓存要么复制要么上 IPC，不值当

案例三 · 批处理计算

每个任务一个隔离进程（防止一次编译 / 转码把服务搞挂）， 进程内用线程并行处理多个目标，并共享只读的依赖缓存。

场景隔离层（进程）并发层（线程 / 异步）取舍理由
浏览器每个站点 / 标签页一个进程渲染 / 合成 / IO 线程崩溃与资源滥用隔离优先
Web 服务每 worker 一个进程事件循环 + 线程池多核 + 隔离 + 高连接数
批处理计算每任务一个进程线程共享只读缓存不可信输入隔离 + 内存省

06一句话收束

🎯

三样东西是叠加关系，不是三选一。

它决定 谁跟谁……
进程 谁跟谁一起死
线程 谁跟谁一起跑
异步 谁等的时候别人在干嘛

所以正确的问题不是「用进程还是用线程」，而是 「这几层分别由谁负责」—— 上面三个案例都是三层各有各的答案。

组合的分层原则可以背下来： 外层按故障域切进程，内层按并发度上线程，最里层按等待量用异步。

「CPU 密集用进程、I/O 密集用线程」这句话，最大的问题是什么？

它把一个多维权衡压成了一维，而且压缩的那个维度（阻塞特征）排在检查顺序的第五问。 在它之前还有四问：要不要独立故障域？要不要直接共享内存？共享多少？ 固定开销（每线程 8MB 虚拟栈 vs 每进程一套页表）扛不扛得住？ 这些都是结构约束，比阻塞特征更靠前。 而且阻塞特征这个维度自己还依赖运行时 —— 同一个问题换个语言答案就变了。

为什么「Python CPU 密集要用进程」这个结论不能搬给 C++ 或 Java？

因为它的根因是 GIL，不是「CPU 密集」这个属性本身。 Python 的线程因为 GIL 拿不到真并行，所以要靠进程绕过去。 C++、Java、Go 的线程就是真并行，同样的任务用线程更轻。 Node 又是另一种情况：主线程是单条事件循环，计算要用 worker_threads。 所以问选型之前先问一句：在这个运行时里，「线程」到底等不等于「并行」？

十万个连接，为什么不该开十万个线程？

线程池的规模应该是「核数级别」，不是「连接数级别」。 十万个线程意味着调度器名单上有十万个实体，其中绝大多数什么也没干 —— 真正的成本不是内存（8MB 是虚拟预留，页按需分配），而是调度与内核资源。 正确解法是事件循环（epoll/kqueue）管住等待，再加一个核数级别的小线程池 接手会真正阻塞的活（磁盘、同步库）。

「一万个线程 × 8MB 栈 = 80GB 内存」，这句话错在哪？

8MB 是虚拟地址空间预留，不是物理内存占用。页是按需分配的。 一万个线程确实会占用约 80GB 虚拟地址空间，但常驻内存只有实际用到的那些 （约 80MB 量级）。这也是现代机器上单进程跑一万线程在生产可行、 而不是民间传说里那样不可能的原因。 真正的约束是栈大小，可以用 pthread_attr_setstacksize 或 ulimit -s 调整 —— 小栈还有个好处：失控递归会更快失败。

为什么浏览器要给每个标签页一个独立进程，而不是一个线程？

因为故障域。线程共享地址空间，一个渲染器的 bug 或失控脚本能拖垮整个浏览器； 独立进程的非法访问会被页表拦下，崩溃只影响那一个标签页。 代价是每个窗口一份固定内存开销，但 Chromium 的赌注是总体膨胀反而更少： 内存紧张时操作系统可以把不活跃的窗口整个换出（swap）， 这种粗粒度的调度是线程模型做不到的。

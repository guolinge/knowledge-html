## 01 · 口诀错在哪

你一定听过这句话：

> 「CPU 密集用进程，I/O 密集用线程。」

它**没错，但没用到点上** —— 它把一个多维的权衡压成了一维。

```callout
tone: red
icon: 📏
text: |
  **问题是：阻塞特征（CPU 密集 / I/O 密集）只是众多维度里的一个，
  而且它自己还依赖运行时。**

  在你走到「它是 CPU 密集还是 I/O 密集」这一问之前，
  至少还有四问挡在前面：**要不要隔离？要不要共享内存？共享多少？
  固定开销扛不扛得住？**

  ==口诀只配做最后一步的注脚，不能当第一步。==
```

## 03 · 为什么结论不能跨运行时搬运

这是口诀最坑人的地方 —— ==同一个问题，换个语言答案就变了。==

```compare
first: 运行时
head: [线程能真并行吗, 于是 CPU 密集该用什么]
rows:
  - Python: [{ text: "不能 —— GIL 让同一时刻只有一个线程执行字节码", tone: red }, "进程（绕开 GIL）"]
  - "C++ / Rust / Java / Go": [{ text: "能", tone: green }, "线程（更轻）"]
  - Node.js: [{ text: "主线程单条事件循环", tone: red }, "`worker_threads`（每个 worker 有独立 V8 isolate）或子进程"]
```

Python 生态的共识本身没错：多线程适合 I/O 密集（等待时让出 CPU 隐藏延迟），
多进程适合 CPU 密集（绕过 GIL 获得真并行）。

```callout
tone: amber
icon: 🐍
text: |
  **但把 GIL 的结论搬到别处就是错误泛化。**

  「Python 的 CPU 密集要用进程」这个结论，
  根因是 GIL，不是「CPU 密集」这个属性本身。

  ++把它搬到 C++、Java 或 Node worker 上，前提就已经不成立了。++

  所以问「线程还是进程」之前，先问一句：
  ==**在这个运行时里，「线程」到底等不等于「并行」？**==
```

## 04 · I/O 密集 ≠ 必须多线程

这条可能是最反直觉的：**高连接数场景的正确答案，通常不是「更多线程」。**

```flow
grid: true
groups:
  - { id: bad, label: "十万连接 → 十万线程？（不是）", tone: red }
  - { id: good, label: "十万连接的真实解法", tone: green }
nodes:
  - { id: b1, label: "十万个线程", sub: "每个都在等 fd 就绪", row: 0, tone: red, group: bad }
  - { id: b2, label: "调度器名单上十万个实体", sub: "其中绝大多数什么也没干", row: 1, tone: red, group: bad }
  - { id: g1, label: "事件循环 · epoll / kqueue", sub: "一个线程管住十万个 fd 的等待", row: 0, tone: green, group: good }
  - { id: g2, label: "核数级别的小线程池", sub: "只接手会真正阻塞的活：磁盘、同步库", row: 1, tone: green, group: good }
edges:
  - { from: b1, to: b2, label: "代价落在这" }
  - { from: g1, to: g2, label: "分工" }
```

==线程池的规模是「核数级别」，不是「连接数级别」。==

```callout
tone: violet
icon: 🔢
text: |
  **顺便修正一个时间观：线程数上限的「民间传说」大多来自 21 世纪初。**

  现代多核大内存机器上，**单进程跑一万线程在生产环境是可以做到的**。
  真正的约束是栈大小：Linux 默认每线程 8 MiB **虚拟**内存，
  一万线程约 80 GiB 虚拟地址 —— 但常驻只有实际用到的那些（约 80 MiB 量级）。

  这个 8 MiB 是**虚拟地址空间预留**，页是按需分配的 ——
  ==「一万线程 × 8MB = 80GB 内存」是个流传很广的误算。==

  ++调小栈（`pthread_attr_setstacksize` / `ulimit -s`）是常规手段，
  小栈还能让失控递归更快失败。再往上就混入协程式异步。++
```

## 05 · 生产架构不是二选一，是分层组合

真实系统几乎从不「只多进程」或「只多线程」，而是**在两层之间分层**。

## 案例一 · 浏览器

```tree
- 浏览器
  - 主进程 · UI / 网络
  - 渲染进程 · tab 1
    - 渲染主线程
    - 合成器线程
    - IO 线程 + worker
  - 渲染进程 · tab 2
    - （同样有自己的一整套线程）
```

==进程层负责「谁跟谁一起死」，线程层负责「谁跟谁一起跑」—— 两层各管一件事。==
一个 tab 崩了只带走它自己那个渲染进程；而渲染进程内部，几十个线程照样并行干活。

Chromium 官方讲得很直白：每个标签页一个独立进程，单个窗口的 bug 或失控脚本
不连累浏览器整体。

> **代价是每窗口一份固定内存。** Google 的赌注是总体膨胀反而更少 ——
> 内存紧张时，操作系统可以把不活跃的窗口**整个换出**（swap）。
> ==线程模型做不到这么粗粒度的调度。==

## 案例二 · Web 服务

```compare
  - 线程池: ["**阻塞任务**", "磁盘 I/O 与同步库的活必须有人接手"]

```

## 案例三 · 批处理计算

每个任务一个隔离进程（防止一次编译 / 转码把服务搞挂），
进程内用线程并行处理多个目标，并共享**只读**的依赖缓存。

```compare

  - Web 服务: ["每 worker 一个进程", "事件循环 + 线程池", "多核 + 隔离 + 高连接数"]
  - 批处理计算: ["每任务一个进程", "线程共享只读缓存", "不可信输入隔离 + 内存省"]
```

## 06 · 一句话收束

```callout
tone: green
icon: 🎯
text: |
  **三样东西是叠加关系，不是三选一。**

  | 它决定 | 谁跟谁…… |
  |---|---|
  | ==进程== | 谁跟谁一起**死** |
  | ==线程== | 谁跟谁一起**跑** |
  | ==异步== | 谁**等**的时候别人在干嘛 |

  ++所以正确的问题不是「用进程还是用线程」，而是
  「这几层分别由谁负责」—— 上面三个案例都是三层各有各的答案。++

  **组合的分层原则可以背下来：**
  外层按**故障域**切进程，内层按**并发度**上线程，最里层按**等待量**用异步。
```

```quiz
- q: 「CPU 密集用进程、I/O 密集用线程」这句话，最大的问题是什么？
  a: |
    它把一个多维权衡压成了一维，而且压缩的那个维度（阻塞特征）排在检查顺序的第五问。
    在它之前还有四问：要不要独立故障域？要不要直接共享内存？共享多少？
    固定开销（每线程 8MB 虚拟栈 vs 每进程一套页表）扛不扛得住？
    这些都是结构约束，比阻塞特征更靠前。
    而且阻塞特征这个维度自己还依赖运行时 —— 同一个问题换个语言答案就变了。
- q: 为什么「Python CPU 密集要用进程」这个结论不能搬给 C++ 或 Java？
  a: |
    因为它的根因是 GIL，不是「CPU 密集」这个属性本身。
    Python 的线程因为 GIL 拿不到真并行，所以要靠进程绕过去。
    C++、Java、Go 的线程就是真并行，同样的任务用线程更轻。
    Node 又是另一种情况：主线程是单条事件循环，计算要用 worker_threads。
    所以问选型之前先问一句：在这个运行时里，「线程」到底等不等于「并行」？
- q: 十万个连接，为什么不该开十万个线程？
  a: |
    线程池的规模应该是「核数级别」，不是「连接数级别」。
    十万个线程意味着调度器名单上有十万个实体，其中绝大多数什么也没干 ——
    真正的成本不是内存（8MB 是虚拟预留，页按需分配），而是调度与内核资源。
    正确解法是事件循环（epoll/kqueue）管住等待，再加一个核数级别的小线程池
    接手会真正阻塞的活（磁盘、同步库）。
- q: 「一万个线程 × 8MB 栈 = 80GB 内存」，这句话错在哪？
  a: |
    8MB 是**虚拟地址空间预留**，不是物理内存占用。页是按需分配的。
    一万个线程确实会占用约 80GB 虚拟地址空间，但常驻内存只有实际用到的那些
    （约 80MB 量级）。这也是现代机器上单进程跑一万线程在生产可行、
    而不是民间传说里那样不可能的原因。
    真正的约束是栈大小，可以用 pthread_attr_setstacksize 或 ulimit -s 调整 ——
    小栈还有个好处：失控递归会更快失败。
- q: 为什么浏览器要给每个标签页一个独立进程，而不是一个线程？
  a: |
    因为故障域。线程共享地址空间，一个渲染器的 bug 或失控脚本能拖垮整个浏览器；
    独立进程的非法访问会被页表拦下，崩溃只影响那一个标签页。
    代价是每个窗口一份固定内存开销，但 Chromium 的赌注是总体膨胀反而更少：
    内存紧张时操作系统可以把不活跃的窗口整个换出（swap），
    这种粗粒度的调度是线程模型做不到的。
```

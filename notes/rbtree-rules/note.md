## 01 · 五条性质，先照字面看一遍

红黑树是一棵二叉搜索树，每个节点多带一个颜色位（红 / 黑）。它要求下面五条同时成立：

```cards
cols: 2
items:
  - { title: "① 每个节点是红的或黑的", desc: "一个比特，用来记录结构", tone: muted }
  - { title: "② 根是黑的", desc: "约定，去掉它只是让边界情况多一条", tone: muted }
  - { title: "③ 每个叶子（空位 NIL）是黑的", desc: "空位也参与记账 —— 数黑高时用得上", tone: muted }
  - { title: "④ 红节点的两个孩子都是黑的", desc: "换句话说：不允许出现连着两个红", tone: amber }
  - { title: "⑤ 从一个节点出发，到它下面所有空位的路径上黑节点数相同", desc: "这个数目叫黑高（black height）", tone: violet }
```

一眼看过去，前三条像在补约定，④⑤ 才是真规矩。拿一棵具体的树来对照：

```demo
widget: rbtree-lab
actions: false
title: 一棵红黑树：7 个键
config:
  mode: show
  show234: false
  tree: "50B(30R(20B,40B),70B(60R,80R))"
  note: "根 50 是黑的（②）。红节点 30、60、80 的孩子都是黑的（④）。"
```

逐条核对：

| 性质 | 在这棵树上的核对 |
|---|---|
| ② 根是黑的 | 50 是黑的 |
| ④ 红节点的孩子都黑 | 30 的孩子是 20 和 40（都黑）；60 和 80 是叶子，孩子都是空位（黑） |
| ③ 空位是黑的 | 每根「没有孩子」的位置都算一个黑节点 |
| ⑤ 黑高相同 | 50 → 30 → 20 → 空位：50、20、空位 = 3 个黑；50 → 30 → 40 → 空位：也是 3 个 |

到这里它还是一堆规定。真正让这五条讲得通的，是下一节。

## 02 · 关键的一步：红边 = 「我和父节点住在同一个节点里」

给每个节点加一条读法：

> 如果一个节点是**红的**，它就并进父节点，和父节点算作同一个 2-3-4 节点。

按这条读法，上面那棵树立刻变了模样：

```demo
widget: rbtree-lab
actions: false
title: 同一棵树：睁眼看是红黑树，收起来看是 2-3-4 树
config:
  mode: show
  show234: true
  tree: "50B(30R(20B,40B),70B(60R,80R))"
```

虚线框就是 2-3-4 节点。这棵 7 个键的树只有三个节点：

- 根那个框里有 3 个键（30、50、70）→ 4-节点；
- 左边一个框有 2 个键（20、40）→ 3-节点；
- 右边一个框也有 2 个键（60、80）→ 3-节点。

==红黑树和 2-3-4 树是同一件事的两种写法。==红黑树的每个节点多一个颜色位，2-3-4 树的每个节点多几个键位 —— 记录的东西是同一个。

而「几-节点」和「几个红孩子」的关系是固定的：

```compare
first: 2-3-4 节点
head: [二叉写法长什么样, 红孩子个数]
rows:
  - 2-节点（1 个键）: ["一个黑节点，孩子都是黑的或空位", 0]
  - 3-节点（2 个键）: ["一个黑 + 一个红孩子（左或右）", 1]
  - 4-节点（3 个键）: ["一个黑 + 两个红孩子（一左一右）", 2]
```

一个黑节点最多带 2 个红孩子 → 一个 2-3-4 节点最多 3 个键。这就是性质 ④ 的全部内容。

## 03 · 五条性质逐条翻译

把这五条翻成 2-3-4 树的语言，它们就不再像随手定的：

```compare
first: 红黑树的规定
head: [翻译成 2-3-4 的语言, 它到底在保证什么]
rows:
  - "① 每个节点有颜色": ["红边表示「和父节点同属一个节点」", "二叉树上多一个比特，用来记多键节点的边界在哪"]
  - "② 根是黑的": ["根所在的节点没有父节点可以合并进去", "最顶层那个 2-3-4 节点必须自成一体"]
  - "③ 空位是黑的": ["每个空位记一个黑", "黑高能把空位也算进来，于是「路径长度」可以按黑节点数比较"]
  - "④ 红节点的孩子都黑": ["一个节点里最多 3 个键", "红边不能首尾相连 —— 3 个键正好需要 2 条红边，再多就说明这个「节点」装了 4 个键"]
  - "⑤ 所有路径黑高相同": ["所有叶子在同一层", "2-3-4 树天生平衡的那条性质，一字不差地搬了过来"]
```

两条最要紧的是 ④ 和 ⑤：

- ④ 是「一个节点最多 3 个键」的二叉写法。3 个键都挤在一起时，二叉形状里必然是「黑、红、红」连成一条链 —— 所以规则被写成了「红节点的孩子必须是黑的」。
- ⑤ 是「所有叶子同深」的二叉写法。==这条才是平衡的来源。==它没有说「左右子树高度差不超过 1」，而是说「每条路上的黑节点数一样多」—— 前者是结果，后者才是好维持的规矩。

## 04 · 黑高到底怎么数

这是最容易含糊的一步，所以单独讲。黑高（black height）记作 bh(x)：**从 x 出发（不含 x 本身），到它下面任何一个空位，路上经过的黑节点数。**

这几个字都重要：

- **不含 x 本身** —— 所以黑高是「往下还有几个黑」；
- **任何一个空位** —— 性质 ⑤ 说的是「所有路径都相同」，所以随便挑一条都行；
- **空位也算一个黑** —— 性质 ③。

拿刚才那棵树，从根 50 数一遍：

```demo
widget: rbtree-lab
actions: false
title: 数从 50 往左走的那条：黑节点标了 +1
config:
  mode: walk
  bh: true
  show234: false
  tree: "50B(30R(20B,40B),70B(60R,80R))"
  path: [50, 30, 20]
```

路径 50 → 30 → 20 → 空位，黑节点是 50 和 20（30 是红的，不算），再加上末尾的空位 —— 一共 3 个。所以 bh(50) = 3。换一条路 50 → 70 → 60 → 空位：50、70、空位，也是 3。

!!最容易数错的两个地方：把起点自己算进去、忘了末尾的空位。!!两种数法都会让「所有路径相同」这个结论失效，但性质本身没变。

## 05 · 高度上界：h ≤ 2·log₂(n+1)

把五条用起来，能直接算出树有多高。用**边的条数**记高度 h。

**第一步：h ≤ 2·(根的黑高)。** 从根到最深的空位，这条路上有 h 条边、h+1 个节点（含空位）。由 ④，红节点不能相邻，所以路上最多一半是红的 —— 黑节点至少占一半，也就是根的黑高至少是 h/2。

**第二步：根的黑高 ≤ log₂(n+1)。** 先证一条：对任意节点 x，以它为首的子树里，内部节点至少有 2^bh(x) − 1 个。归纳一步就看得出来：x 的每个孩子，黑高要么是 bh(x)（孩子是红的）要么是 bh(x)−1（孩子是黑的），按归纳假设两边各自至少有 2^(bh(x)−1) − 1 个内部节点，加上 x 自己就是 2^bh(x) − 1 个。把 x 换成根，内部节点数就是 n：

```
以 x 为根的子树里，内部节点数 ≥ 2^bh(x) − 1
把 x 换成根：n ≥ 2^bh − 1  →  bh ≤ log₂(n+1)
```

两步合起来：**h ≤ 2·log₂(n+1)**，层数最多比它多 1。

这个「2 倍」有来头：红黑树是 2-3-4 树的二叉写法，一个装 3 个键的 2-3-4 节点，在二叉树上要摊成两层（黑 + 红），所以红黑树的高度最多是同一棵 2-3-4 树的两倍。拖动下面这个滑杆看几种规模：

```demo
widget: tuner
title: 三种树的层数上限
actions: false
config:
  param: { label: 键的个数 n, unit: 个, values: [1000, 10000, 100000, 1000000, 10000000] }
  outputs:
    - { label: 红黑树：最坏层数（2·log₂(n+1)）, unit: 层, values: [20, 27, 34, 40, 47], tone: violet }
    - { label: 2-3-4 树 / 形状完美的 BST, unit: 层, values: [10, 14, 17, 20, 24], tone: blue }
    - { label: 普通 BST（按顺序插入时）, unit: 层, values: [1000, 10000, 100000, 1000000, 10000000], tone: red }
```

100 万个键：红黑树最坏 40 层，2-3-4 树只要 20 层。而按顺序插入的普通 BST 是 100 万层，没有上界。

上界不等于实际高度。同一个实现跑顺序插入 1…10⁶，实测 **37 层、黑高 19** —— 比上界还低。

## 06 · 旋转在做什么

五条性质是「什么样才算合法」，接下来两篇讲「怎么把它改成合法」。改的时候只有一个几何动作：**旋转**。

旋转就是换父子关系。看一次左旋：

```demo
widget: rbtree-lab
actions: false
title: 一次左旋：键的集合没变，谁当黑节点变了
config:
  mode: show
  show234: true
  trees:
    - { cap: 旋转前：3-节点，黑节点是 20, tree: "20B(10R,)" }
    - { cap: 以 20 为轴左旋：10 顶上来当黑节点 —— 还是那一个 3-节点, tree: "10B(,20R)" }
```

两件事同时成立：

- **键的中序没变**。旋转不会把树变回无序 —— 10 还是在 20 左边。所以任何时刻，旋转都不破坏搜索树的查找能力。
- **2-3-4 树的形状没变**。上面两棵二叉树的框里都是 {10, 20}，都是同一个 3-节点。变的只是「这两个键里让谁当那个黑节点」。

那么修复的时候为什么还要变色？因为 3 个键的节点有额外要求：**3 个键里，中间的键必须是黑的**。所以把键摆成合法形状时，旋转必须和变色绑在一起 —— 转到合适的位置之后，把中间那个键染黑。

插入修复的三种情形，本质就在做这件事：情形 1 处理「4 个键挤在一个节点里」，情形 2 和 3 处理「3 个键怎么摆成中间为黑的形状」。

```demo

  mode: quiz
  show234: false
  tree: "50B(30R(20B,40B),70B(60R,80R))"
```

四个问题都答完再看结论。全对说明这五条性质你已经能自己用了 —— 那就可以进插入和删除了。

```callout
tone: green
icon: ✅
text: |
  **判断一棵二叉树是不是红黑树，只需要三条检查：**
  ① 根是不是黑的；② 有没有哪个红节点的孩子也是红的；③ 从根到每个空位的黑节点数是不是都一样。
  前两条扫一遍就完了，第三条要真的数 —— ==忘了末尾那个空位是最常见的错。==
```

```quiz
- q: 「不允许连着两个红」这条规定，翻译成 2-3-4 树是在保证什么？
  a: |
    一个 2-3-4 节点最多装 3 个键。在二叉写法里，3 个键必然是一个黑节点带两个红孩子 ——
    红边不会首尾相连。如果出现连着两个红，就说明这个「节点」里挤了 4 个键，超出了 4-节点的容量。
    所以这条规定 = 「一个节点最多 3 个键」。

- q: 为什么「所有路径黑高相同」而不是直接规定「左右子树高度差不超过 1」？
  a: |
    高度差不超过 1 是结果，不是好维持的规矩：插入一个键会改动一整条路径上的高度，
    要维持高度差就得回头检查很多节点。
    黑高相同是一条局部的、只看颜色的规矩 —— 插入和删除后只需要在改动点附近做有限次调整，
    而且它推出来的正是「所有叶子同深」这个 2-3-4 树的性质。

- q: 数一棵树的黑高，容易数错的哪两处？
  a: |
    ① 把起点自己算进去（黑高不含起点本身）；
    ② 忘了末尾的空位（性质 ③ 规定空位记一个黑）。
    两种错都会让「所有路径相同」看起来不成立。

- q: 一次旋转把 20B(10R) 变成 10B(,20R)，2-3-4 树里的什么变了、什么没变？
  a: |
    没变的是键的集合和树的中序：两个键还是 {10, 20}，还是同一个 3-节点。
    变的是「谁当这个节点的黑节点」—— 从 20 换成了 10。
    这也是修复里旋转必须配合变色的原因：3 个键的节点要求中间的键当黑节点，
    转到位置之后得把颜色也摆对。
```

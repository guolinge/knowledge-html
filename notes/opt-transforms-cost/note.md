前两篇讲完了「能不能做」：先证明合法，再看值不值。这一篇展开那个「值不值」。同一条变换，在不同机器、不同代码形状下，收益能差出一个数量级，而决定权在一份**成本模型**手里。它也是优化器最像工程而不是像数学的地方：没有定理可证，只有估算和回退。

## 01 · 强度削弱：一条经典规则，和它今天的处境

**强度削弱（strength reduction）** 指的是用便宜的操作替代昂贵的操作。最经典的一例是把循环里的乘法换成累加：

```c
for (int i = 0; i < n; i++) {
    x = i * 4;      // 每轮一次乘法
    a[i] = x;
}
```

改成

```c
x = 0;
for (int i = 0; i < n; i++) {
    a[i] = x;       // 每轮一次加法
    x = x + 4;
}
```

这条规则 1977 年由 Cocke 和 Kennedy 写成算法时，乘法的代价确实是加法的好几倍：它要靠多次移位和相加，或者走一条慢得多的乘法器。改写成累加，等于把每轮的一次"贵操作"换成"便宜操作"。

但今天的机器不是这样了。x86-64 上 `i * 4` 常常被编译成一条 `LEA` 指令：`base + index*4` 这种地址计算是它的本职工作，延迟 1 个周期，和加法一样。也就是说，==这条规则换来的可能只是"指令数不变、延迟不变"，收益接近零==。

那它还有用吗？有，但用处变了：

```journey
- tag: ① 原始写法
  tone: muted
  name: for 循环
  code: |
    for (int i = 0; i < n; i++) {
      a[i] = i * 4;
    }
  note: 每轮一次乘法。`i` 是归纳变量：它每轮固定加 1。
  next: "认出归纳变量 :: :: 这是强度削弱的前提"

- tag: ② 强度削弱后
  tone: blue
  name: 累加形式
  code: |
    x = 0;
    for (int i = 0; i < n; i++) {
      a[i] = x;
      x = x + 4;
    }
  note: 乘法没了，多了一个变量 `x`，多一条加法。
  noteTone: ok
  next: "看目标机值不值 :: :: 交给成本模型"

- tag: ③ 今天的判断
  tone: amber
  name: 由成本模型决定
  badge: 收益可能为零
  badgeTone: red
  fields:
    - { k: 指令数, v: "1 → 1", note: LEA 一条就够, tone: warn }
    - { k: 延迟, v: "1 → 1 周期" }
    - { k: 寄存器压力, v: "多一个活着的变量", note: 有时反而更差, tone: warn }
  note: 真正的收益出现在「步长是运行时才知道的值」或「能顺带暴露向量化」的时候。
```

这段演变的结论，比这条规则本身重要：**经典优化规则提供的是候选变换，是否采用由面向目标机器的成本模型决定。** 规则是 1977 年总结的，机器是每年在变的，两者不能混为一谈。

## 02 · 循环：五件套各自解决什么

循环之所以是重点，因为程序的时间大多花在少数几个循环里。围绕它形成的优化各有各的前提和风险：

```cards
cols: 2
items:
  - title: 循环不变量外提（LICM）
    desc: 循环里算出来每轮都一样的值，提到循环外只算一次
    tag: 前提：header 支配全循环 + 体内没人写它的操作数
    body: |
      要过两道门：**合法性**要求这个值在循环里不被改写（别名分析说了算），
      **收益**要求循环至少跑几次——只跑一次时，外提反而多付一次开销。
  - title: 循环展开（unrolling）
    desc: 把循环体复制几份，减少判断与跳转次数，顺便暴露并行
    tag: 前提：迭代次数可分析
    body: |
      展开后一次迭代干 `k` 倍的活，判断次数变成 1/k。代价是代码体积变大，
      指令缓存可能装不下。==展开得太多会把向量化要的形状毁掉。==
  - title: 循环交换（interchange）
    desc: 交换嵌套循环的内外层，让内存访问顺着行方向走
    tag: 前提：依赖分析证明交换不改变结果
    body: |
      对行优先存储的矩阵，`for i for j a[i][j]` 是一条缓存行用满；
      换成 `for j for i a[i][j]` 就变成每一步跳一整行。交换回去就恢复了。
  - title: 循环分块（blocking / tiling）
    desc: 把大矩阵切成能装进缓存的小块，块内一次用完
    tag: 前提：块内数据量 ≤ 缓存
    body: |
      交换只能改顺序，改不了"整个矩阵装不进缓存"这个事实。分块是把它切小：
      每一块在缓存里做完，再换下一块。
  - title: 向量化（vectorization）
    desc: 一次处理 4 / 8 / 16 个元素，用 SIMD 指令
    tag: 前提：迭代间无依赖 + 别名证明
    body: |
      依赖分析证明第 i 次和第 i+1 次不互相干扰，别名分析证明数组不重叠，
      成本模型再判断"打包拆包的开销是不是白花"。
```

## 03 · 交换和分块：让一次取回的数据被用满

这两种优化讲的其实是同一件事的两个层面。假设矩阵按行存储，一行 1000 个 `int`，一条缓存行装 16 个。按行遍历时，取回一条缓存行，接下来 15 次访问都命中它，缓存利用率 100%。按列遍历时，每次访问都跳到下一行，也就是下一条缓存行：

```compare
first: 遍历方式
head: [每条缓存行被用几次, 结果]
rows:
  - 行优先，按行遍历: [{ text: "16 次", tone: green }, 一次未命中换来 16 次命中]
  - 行优先，按列遍历（1000×1000）: [{ text: "1 次", tone: red }, 每一步都跨到下一行；一列要碰 1000 条缓存行、约 64 KB，超过 L1，回来时已经失效]
  - 分块之后按块遍历: [{ text: "接近 16 次", tone: green }, 块内的行在缓存里待到用完为止]
```

**循环交换**解决的是"顺序不对"：把内外层换一下，访问就回到行方向。**循环分块**解决的是"整块装不下"：即使顺序对了，如果数据总量远超缓存，下一次回来时还是要重新读。分块把它切成小方块，一块在缓存里做完再换下一块。

块的大小是算出来的，不是拍的。三个 `n×n` 矩阵各取一个 `B×B` 块，同时活着的元素是 `3 × B²`，每个 8 字节（double），要装进缓存：

```text
3 × B² × 8 ≤ 缓存容量  →  B ≈ sqrt(缓存容量 / 24)
```

L1 只有几十 KB 时，这个式子给出个位数的 `B`；用 L2 的容量能得到十几到几十。取多大最终还是要靠实测——缓存是组相联的，块大小刚好和组数共振时会互相踢出，这就是 Lam 等人在 1991 年专门分析过的"自冲突"。

## 04 · 内联：收益和代价都要算

函数内联是最能说明"成本模型"的优化，因为它的收益和代价都很具体：

```compare
first: 维度
head: [具体是什么]
rows:
  - 收益 · 去掉调用开销: [参数传递、栈帧建立、返回跳转都不用了]
  - 收益 · 暴露新机会: [实参是常量时可以常量传播；调用者上下文可以做死代码删除；跨函数优化有了视野]
  - 代价 · 代码体积: [每个调用点复制一份函数体，指令缓存压力上升]
  - 代价 · 寄存器压力: [内联后活着的变量变多，可能从寄存器溢出到栈上]
  - 代价 · 编译时间: [函数体进入更多上下文，后面的 pass 要处理更多代码]
```

所以内联的判断长这样：**这个调用点值不值得**，而不是**这个函数值不值得**。同一个函数，热路径上调用一次值得内联，冷路径上调用二十次可能不值得；实参是常量时更值得，参数多到要压栈时更不值得；递归函数几乎不内联，除非能证明深度有限。

编译器为此准备了一堆旋钮：函数多大以内无条件内联、超过多少只看调用次数、整体代码增长的上限是多少。这些阈值不是真理，是工程折中：调大一点性能可能涨，代码体积和编译时间也一起涨。

```callout
tone: amber
icon: ⚖
text: |
  ==内联不是「越多越好」，是「在预算内挑最值的那几个」。==

  代码体积和编译时间都是有限资源。把整个程序内联成一个大函数，
  通常换来的是指令缓存颠簸和更慢的编译，而不是更快的程序。
```

## 05 · pass 顺序：机会是被前一个 pass 造出来的

看一段很小的代码：

```c
int add1(int x) { return x + 1; }
int y = add1(2);
```

先内联，再常量折叠，三步就能化成常量：

```journey
- tag: ① 原始
  tone: muted
  name: IR
  code: |
    int add1(int x) { return x + 1; }
    int y = add1(2);
  note: 一个函数调用，实参是常量。
  next: "先内联 :: :: 顺序反过来，后面两步都看不到"

- tag: ② 内联之后
  tone: blue
  name: IR
  code: |
    int y = (2) + 1;
  note: 调用没了，加法两侧都成了常量。
  next: "再折叠 :: :: 两边的值都不依赖运行时"

- tag: ③ 常量折叠
  tone: violet
  name: IR
  code: |
    int y = 3;
  note: 加法没了。
  next: "清理 :: :: 没有调用者的函数留着也是负担"

- tag: ④ 死代码删除
  tone: green
  name: IR
  code: |
    // add1 没有调用者了，整个函数删掉
  note: 又腾出一次新的内联机会，如果它的调用者也被删了。
```

把顺序换一下，结果完全不同：

```compare
first: 顺序
head: [每一步看到什么, 最终结果]
rows:
  - 内联 → 常量折叠 → 死代码删除: [内联造出 `2 + 1`；折叠把它变成常量；删除清掉空函数, [{ text: "y = 3，函数也没了", tone: green }]]
  - 常量折叠 → 死代码删除 → 内联: [{ text: "折叠看不到函数体里的 `x + 1`，删除也删不掉调用", tone: amber }, [{ text: "停在 y = add1(2)", tone: red }]]
  - 先展开循环再向量化: [展开后循环体变大，依赖关系却没变, 常常更难向量化]
  - 先向量化再展开: [{ text: "向量化已经把 4 个元素打包了，再展开是复制向量体", tone: blue }, 通常更合适]
```

这就是著名的 **phase ordering problem（阶段顺序问题）**：一个 pass 的输出是下一个 pass 的输入，前一个 pass 既能创造机会，也能破坏机会。理论上穷举顺序不现实，实际的做法是：

1. 定一个经验顺序，把"造机会"的 pass 放前面（内联、常量传播、规范化），"清理"的放后面（DCE、CFG 化简）。
2. 包在一个循环里，跑到不动点为止。
3. 用编译时间预算把这层循环卡住——真实项目里往往就是"再跑一轮 pass 流水线，直到没有变化或者超时"。

!!不动点这个说法很漂亮，落地时是个预算问题。!! 每一轮都要重新算分析、重新跑 pass，编译时间随轮数线性涨。所以实践里常见的是"跑两轮然后停"，而不是数学意义上的收敛。

## 06 · 成本模型为什么难

成本模型要回答的是"在目标机器上，这段代码会多快"。它能看到的是静态信息：

```compare
first: 成本模型看到的
head: [真实机器上还受什么影响]
rows:
  - 指令条数与指令类型: [乱序执行能把无关指令重叠掉，实际瓶颈可能是一条依赖链]
  - 静态估的缓存代价: [缓存是否命中取决于数据大小、访问顺序、同核上另一条线程在干什么]
  - 分支的静态概率: [真实分支行为由输入决定，预测器还会自己学习]
  - 函数体大小: [指令缓存、uop 缓存、对齐、解码宽度都会改变结果]
  - 目标 CPU 的定值参数: [同一份二进制在不同微架构上表现不同，一次编译要照顾一族机器]
```

于是成本模型天生只能近似。它的价值不在于"算得准"，而在于**方向对**：让热路径上的优化更容易通过、冷路径上的优化更容易被拒绝。算错一次的后果是"白忙一场"，而不是"编错程序"——这也是它为什么敢用估算。

也正因为它是估算，很多优化问题不是"能不能做"，而是几个连续量的取舍：做多大、做几次、在哪个位置做、对哪些函数做、速度和体积怎么换。

## 07 · 速查

```checklist
items:
  - 经典规则给候选，成本模型给结论；同一条规则在不同机器上收益可以差一个数量级
  - 强度削弱在今天可能零收益（LEA 一条就够），它的价值转移到了「步长运行时才知道」和「帮忙向量化」
  - 循环五件套各有前提：LICM 要别名、交换要依赖、分块要容量、向量化要无依赖且不重叠
  - 分块尺寸是算出来的：`3 × B² × 8 ≤ 缓存`；但组相联带来的自冲突只能靠实测
  - 内联的判断单位是「这个调用点」，不是「这个函数」
  - pass 顺序决定机会：内联造常量、常量造死代码、删代码又造内联机会
  - 不动点在工程上是「跑两轮然后停」，编译时间预算才是真正的边界
```

## 08 · 自测

```quiz
- q: "`i * 4` 改成 `x += 4` 在今天的 x86-64 上为什么可能一点也没变快？"
  a: |
    因为 `i * 4` 常常被编译成一条 LEA：`base + index*4` 是地址计算的常见形式，
    延迟 1 个周期，和加法相同。指令数没减少，延迟也没减少。

    这条规则真正有价值的场景是：步长只有运行时才知道（必须真乘）、
    或者削弱之后能暴露向量化。是否采用由目标相关的成本模型决定。
- q: 循环交换和循环分块分别在解决什么问题？
  a: |
    交换解决「顺序不对」：行优先存储的矩阵被按列遍历，每一步都跳一整行，
    交换内外层就回到行方向。

    分块解决「装不下」：即使顺序对了，数据总量远超缓存时下一次回来还得重读。
    分块把它切成能装进缓存的小块，块内一次用完。块大小由缓存容量算出，但要实测确认。
- q: 为什么内联的判断单位是「调用点」而不是「函数」？
  a: |
    收益和代价都发生在调用点上：热路径上的一次调用，内联收益大、体积代价摊得薄；
    冷路径上二十次调用，体积代价乘二十、收益几乎为零。

    所以判断要带上上下文：调用次数、实参是否是常量、函数体大小、是否递归、
    以及当前函数的整体增长预算。
- q: 同一个内联和折叠，换个顺序结果就变了，这说明什么？
  a: |
    说明 pass 之间有依赖：内联创造 `2 + 1` 这个机会，折叠才看得到它。
    这就是阶段顺序问题——前一个 pass 既能创造机会也能破坏机会。

    实践上的做法是定一个经验顺序，包进循环跑到不动点，再用编译时间预算卡住。
- q: 成本模型算错了会怎样？为什么优化器敢用它？
  a: |
    算错的后果只是「这次变换白做」，不是编错程序——合法性由另一道闸保证。
    所以它可以只求方向对：热路径更容易通过，冷路径更容易被拒绝。
```

01需求：为什么需要「条件」这个抽象

先看一个真实场景。

运营要发一张优惠券，只发给「最近 7 天加购过、并且是 VIP」的用户。

要落地，得回答「这批人是谁」。而这些数据散在两个地方：

「加购过」  →  在事件表（行为流水）
「是 VIP」  →  在画像表（静态属性）

最直接的做法：让运营写 SQL。

SELECT uid FROM event_v2      WHERE event_type = '加购' AND event_time > ...
INTERSECT
SELECT uid FROM user_portrait WHERE vip_level >= 3

这条路走不通，有四个原因：

运营不会写 SQL

业务侧的人是产品和运营，不是工程师

口径要复用

同一批人明天还要圈一次，不能每次重写

要防注入

条件里的值是外部传进来的，直接拼字符串会被注入

要跑在两个库上

同一句话，Doris 和 ByteHouse 的 SQL 写法不一样

🎯

所以需要一层中间物：用业务语言描述「要什么人」，由它生成 SQL。 「条件」就是这层描述的基本单位。

02一个条件由什么构成

把「最近 7 天加购过」和「是 VIP」拆开看，它们其实是同一种结构：

拆开看「最近 7 天加购过」「是 VIP」
判断对象事件「加购」画像属性 vip_level
判断方式次数 > 0>=
判断值—3
额外限定最近 7 天—

共同点：都是「对某个东西做一个判断」。

一个判断

叶子条件

最小单位。对某个东西做一次判断

{ op: 'IN', name: 'city', value: ['杭州'] }
组合

树枝条件

用 AND / OR 把条件串起来。业务说的「并且」「或者」就是它

{ logic: 'AND', items: [ ... ] }

为什么条件要能嵌套

因为业务说的是：

「最近 7 天加购过，并且是 VIP」          → AND(叶子, 叶子)
「最近 7 天加购过，或者是 VIP」          → OR(叶子, 叶子)
「（加购过 或 下单过）并且是 VIP」        → AND(OR(叶子,叶子), 叶子)

最后一个例子说明为什么必须是树，不能是列表 —— 「或者」可以出现在「并且」里面。

AND 顶层
OR 子树枝
是 VIP 叶子
加购过 叶子
下单过 叶子

03六种条件入口（entrepot）

为什么是六种？ 因为「判断对象」的来源只有六类。

静态属性

portrait

用户的属性。查 user_portrait 表，一行 = 一个人

{ op: 'IN', name: 'city', value: ['杭州'] }
→ WHERE city IN ('杭州')
行为

event

用户做过什么、几次。查 event_v2，要 join 回画像表

{ eventName: '加购', timeRange: '最近3天',
  formula: { op: 'Gt', value: 3 } }
→ 子查询 group by $user_id having count > 3
预先算好

crowd

已经圈好存下来的一批人。查 crowds 表

{ op: 'IN', items: [
    { crowdId: 'C_888', crowdVersion: 'v3' }
]}
直接给

uid

直接给一批用户 ID，不查表。最简单的一种

{ op: 'IN', value: ['111','222'],
  hasEncoded: false }
和对象的关系

relation

用户和某个对象的关系。查业务明细表

{ formulaType: 'DETAIL', op: 'IN',
  relationName: 'niuniu_user_coupon_receive_last',
  value: ['coupon001'] }
兜底

rawSql

直接塞一段 SQL。前五种表达不了时用

'select uid from some_table where ...'
⚠

为什么叫「入口」（entrepot）？

因为它是一个条件进入 SQL 世界的入口 —— 每种条件都知道自己该去哪张表、该怎么写 WHERE。

「条件」是业务视角的说法，「入口」是实现视角的说法。同一件事。

一个容易忽略的差异：五种能嵌套，一种不能

类型能不能嵌套成树为什么
portrait / event / relation能它们的判断对象本身可以再组合，比如「城市是杭州 或 深圳」
crowd / rawSql能同样支持 AND / OR 组合多个
uid不能它就是一个 ID 列表，没有可组合的语义

04表达式模型：四种形态

为什么不能直接用 SQL 字符串

因为一条 SQL 里，「数据」和「代码」是两种东西：

SELECT uid FROM user_portrait WHERE city = '杭州'
       ↑                        ↑   ↑      ↑
     标识符                   标识符 数据  数据
  • 标识符（表名、列名）→ 要包反引号：`city`
  • 数据（值）→ 要参数绑定，不能直接拼进去（否则被注入）

但如果写成 JSONExtract(properties, 'a') —— 这段是代码，不能包反引号。

⚠

把「数据」当成「代码」处理，或者反过来，就是注入漏洞。

四种形态 = 两个维度的组合

形态列名怎么处理值怎么处理
NormalExpression包反引号 formatField参数绑定 encodeValue
RawValueExpression包反引号原样（已经是 SQL）
RawColumnExpression原样（是表达式）参数绑定
RawExpression整段透传 `whereRaw`—
最常用

NormalExpression

列名和值都是普通数据。99% 的条件都是这一种

{ op: 'IN', column: 'city', value: ['杭州'] }
→ WHERE `city` IN (?)     bindings: ['杭州']
值是 SQL

RawValueExpression

列名是普通的，但值本身是一段 SQL（比如子查询）

{ op: 'Gt', column: 'cnt', rawValue: '(select avg(x) from t)' }
→ WHERE `cnt` > (select avg(x) from t)
列名是 SQL

RawColumnExpression

值普通，但列名是一段表达式（比如 JSON 取值）

{ op: 'Eq', rawColumn: "JSONExtract(props, 'a')", value: 1 }
→ WHERE JSONExtract(props, 'a') = ?
整段透传

RawExpression

整条 where 都是 SQL。方言方法返回的就是它

{ raw: "CASE WHEN `x` REGEXP ? THEN 1 ELSE 0 END = 1",
  value: '^abc' }
💡

看出来了吗？四种形态是「列名要不要处理」×「值要不要处理」的 2×2 组合， 再加一个「整段都别处理」的兜底。

为什么要分这么细：因为「哪些部分是用户数据、哪些部分是 SQL 代码」必须精确区分。 这个区分做错了，就是注入漏洞。

判别靠「哪个字段存在」

export const isCondition      = (rule) => 'logic' in rule;
export const isRawValueExpr   = (rule) => 'rawValue' in rule;
export const isRawColumnExpr  = (rule) => 'rawColumn' in rule;
export const isRawExpr        = (rule) => 'raw' in rule;
⚠

这是鸭子类型。 好处是不用建 class、JSON 直接可用、跨进程传输天然友好。

代价是拼错字段名不会报错 —— 会掉进「都不是」那个分支抛异常。

05组织：条件怎么组合成树

一棵条件树，从业务侧看是这样：

AND
├── 事件：加购，最近 7 天，至少 1 次
└── OR
    ├── 画像：vip_level >= 3
    └── 画像：channel = 'APP'

换成 JSON：

{ logic: 'AND', items: [
    { eventName: '加购', timeRange: '最近7天', ... },
    { logic: 'OR', items: [
        { op: 'Gte', name: 'vip_level', value: 3 },
        { op: 'Eq',  name: 'channel',   value: 'APP' }
    ]}
]}
💡

树只有两种节点：logic + items（树枝）和叶子。 所有复杂度都来自「树枝可以套树枝」，没有别的。

06组织：两套词汇，两次翻译

这是全篇最容易懵的地方：同一棵树，业务侧和 core 用两套词汇描述。

同一个条件业务条件（crowd 的输入）Rule[]（core 的输入）
属性名namecolumn
例子{ op: 'IN', name: 'city', value: ['杭州'] }{ op: 'IN', column: 'city', value: ['杭州'] }
时间条件用 dateType 描述，如「最近 3 天」展开成多个条件（见第 07 节）
逻辑组合logic + itemslogic + items（一样）
业务条件 运营/产品能懂的语言
Rule[] core 能懂的语言
SQL 字符串 数据库能懂的语言
✅

两次翻译，各管一件事：

  • adapter（在 crowd 包里）：业务词汇 → 数据词汇
  • knex（在 core 底层）：数据词汇 → SQL 字符串

core 永远不知道「什么是相对时间」「什么是画像属性」。

07架构：以画像为例，看条件怎么翻译

⚠

先更正一个容易搞错的地方：没有统一的 adapter。

翻译是每种条件自己做的 —— 六种实现各写各的，没有一个公共的翻译函数。

这一节讲的 adapter() 是 portrait.ts 的私有方法，只是因为它写得最清楚， 拿它当例子。事件和关系各有自己的一堆函数（getPropRules / getBaseRules / buildTimeRangRules …），uid / 人群包 / rawSql 则基本没有转换逻辑。

展开讲在 ⑧ crowd 篇。

它是个递归函数

adapter(rules) 单个条件或数组
遍历每个 rule
有 'logic'？ 是树
有 'op'？ 是叶子
递归 adapter(items) 保持 logic 不变
有 'dateType'？ 时间条件
直接改名 name → column
展开成 AND 子树 调方言或 utils
throw 条件错误

五个出口各产出什么

分支产出真实数据
有 logic递归，结构不变{ logic: 'OR', items: [...] } → { logic: 'OR', items: [递归结果] }
有 dateType\n且是相对时间戳调方言，展开成 AND 子树{ op: Gte, name: '..._time', value: 3 } → { logic: AND, items: [3 个 Expression] }
有 dateType\n其它时间调 utils，展开成 AND 子树同上，但生成的是通用 Rule
有 rawValue改名 + 透传{ op: Eq, name: 'c', rawValue: 'a+b' } → { column: 'c', op: Eq, rawValue: 'a+b' }
普通条件只改名{ op: IN, name: 'city', value: ['杭州'] } → { column: 'city', op: IN, value: ['杭州'] }
都不是throw条件错误: {...}

重点：时间条件为什么会「膨胀」

一个输入条件，变成一棵子树。

输入 业务条件 1 行 
{ op: 'Gte', name: '..._opened_time',
  dateType: 'Relative', value: 30 }

业务侧说的是一句话：「开户时间在最近 30 天内」。

adapter遇到 dateType 分支
展开 时间表达式 变成两个 
{ op: 'Gte', column: '..._opened_time', value: 开始 }
{ op: 'Lte', column: '..._opened_time', value: 结束 }

因为「最近 30 天」在 SQL 里必须写成「>= 开始 AND <= 结束」。 一个语义，两个条件。

补丁某些操作符还要再加一个
补丁 addHackRules 再加一个条件 
如果是 '<' 或 '<='
  → 再加 { op: 'Gt', column: '...', value: 0 }

代码注释写着原因： > 对于 < 和 <= 的时间范围，需要加上 > 0 的限制条件， > 否则会筛选出值为 0 的数据。 「值为 0」在时间戳语义里代表「从没发生过」，不加会被当成「很久以前发生过」。

包一层强制 AND
输出 Rule[] 一棵子树 
{ logic: 'AND', items: [ 3 个 Expression ] }

外面强制包一层 logic: 'AND'。 代码注释解释了原因： > 这里包装一层，因为 timeRules 必须是 And 的关系， > 而 result 这一层的关系可能是 Or 不包的话，「最近 3 天 或 是 VIP」会被解析成 「>= 开始 或 <= 结束 或 是 VIP」—— 语义就错了。

08架构：entrepot 六种实现怎么组织

每种条件是一个类

  • Entrepot 六个类，共同的形状 每种条件一个类，都实现 list / count
    • Portrait portrait.ts · 233 行 查 user_portrait
    • Event event.ts · 906 行 最复杂：事件名 + 时间 + 属性 + 次数
    • Relation relation.ts · 715 行 和对象的关系
    • Crowd crowd.ts · 134 行 查 crowds
    • Uid uid.ts · 141 行 不查表
    • RawSql rawSql.ts · 107 行 透传
💡

每个类只有两个公开方法：list() 和 count()。

  • list(condition, decode) → 一段能查出 uid 列表的 SQL
  • count(condition) → 一段能数出人数的 SQL

接口小得可怜，但这就是全部。

工厂负责分发

EntrepotStruct { type, condition, options }
switch (condition.type) 工厂里的分发
Portrait
Event
其余四种
throw 未知类型
SQL 字符串
⚠

未知类型直接 throw，不静默返回空。

这个选择很重要：静默失败会让 bug 跑到生产才被发现 —— 生成的 SQL 少了一个条件，圈出来的人就多了一批。

09架构：方言怎么隔离库差异

为什么需要方言

同一句业务话，两个数据库的 SQL 完全不一样：

要做的事ByteHouse 写法Doris 写法
map 取 keymapElement(\name`, 'a')`ELEMENT_AT(\name`, 'a')`
判空isNull(\x`)`\x` IS NULL`
转整数toInt64(\x`)`CAST(\x` AS SIGNED)`
JSON 数组包含hasAny(assumeNotNull(JSONExtract(...)), ...)JSON_CONTAINS(CAST(... AS JSON), ...)
相对时间戳要 UNIX_TIMESTAMP(...) * 1000 包装不要包装（event_time 是 DATETIME）

castToInt / castToFloat / castBoolToInt

⚠

方言方法没有一个是直接产出 SQL 的。

它们返回两种东西：SQL 片段字符串（被拼进 Expression.raw）， 或者完整的 Expression / Rule（直接进表达式树）。

真正把表达式树变成 SQL 的是 knex，不是方言。

什么时候调方言

只有属性类型特殊时才调 —— 普通条件（=、>、IN）根本不碰方言。

一个具体的例子：时间戳为什么必须走方言

库实现方式生成的 SQL 形态
ByteHouse薄壳 —— 直接转发给 utils.getTimestampRules()..._time >= UNIX_TIMESTAMP( DS_DATETIME_ADD('day', -3, NOW()) ) * 1000
Doris自己实现 —— 因为 Doris 的 event_time 是 DATETIME..._time >= DS_DATETIME_ADD('day', -3, FROM_UNIXTIME(UNIX_TIMESTAMP(), '%Y-%m-%d 00:00:00') )
⚠

差别在于要不要 UNIX_TIMESTAMP(...) * 1000 那层包装。

ByteHouse 的 event_time 是毫秒时间戳（数字），要把日期转成毫秒再比。 Doris 的 event_time 是 DATETIME（日期类型），直接比就行。

所以「时间戳必须走方言」不是风格差异，是列的数据类型不同。

10自测

为什么条件必须是「树」，不能是一个平铺的列表？

因为「或者」可以出现在「并且」里面。 「（加购过 或 下单过）并且是 VIP」这种语义，平铺列表表达不了。 树只有两种节点：logic + items（树枝）和叶子，树枝可以套树枝。

六种条件入口为什么是六种？

因为「判断对象」的来源只有六类：用户的属性（portrait）、 行为（event）、预先算好的人群（crowd）、直接给的 ID（uid）、 和对象的关系（relation），以及兜底（rawSql）。 每种都知道自己该去哪张表。

Expression 为什么要有四种形态？

因为一条 SQL 里「数据」和「代码」是两种东西，处理方式不同： 标识符要包反引号，数据要走参数绑定，但表达式不能包反引号。 四种形态是「列名要不要处理」×「值要不要处理」的 2×2 组合， 再加一个「整段都别处理」的兜底。混了就是注入漏洞。

「最近 3 天」这一个条件，为什么最后变成了一棵子树？

因为「最近 3 天」在 SQL 里必须写成 >= 开始 AND <= 结束 —— 一个语义、两个条件。 某些操作符还要再加一个 > 0（否则会把「值为 0」误当成「很久以前发生过」）。 最后外面强制包一层 logic: 'AND'，否则和同一层的 OR 混在一起语义就错了。

方言方法是直接生成 SQL 的吗？

不是。 它们返回 SQL 片段字符串（被拼进 Expression.raw）， 或者完整的 Expression / Rule（直接进表达式树）。 真正把表达式树变成 SQL 的是 knex，不是方言。

相对时间戳为什么必须走方言，而不能用通用实现？

因为两个库的 event_time 列数据类型不同： ByteHouse 是毫秒时间戳（数字），要 UNIX_TIMESTAMP(...) * 1000 包装； Doris 是 DATETIME，直接比就行。不是风格差异，是数据类型差异。

工厂遇到未知的 condition.type 会怎样？

直接 throw，不静默返回空。 静默失败会让 bug 跑到生产才被发现 —— 生成的 SQL 少了一个条件， 圈出来的人就多了一批。

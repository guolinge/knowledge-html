# 方案：sql_builder_v2 的嵌套产物树

> 状态：**已完成**（2026-09-26）· 12 篇全部产出
> 源码：`sources/gitlab/sql_builder_v2 @ 2c500b2`
> 机器可读的树在 [`sql-builder-v2.yaml`](sql-builder-v2.yaml)

---

## 一、目标

不是「三篇笔记」，而是**一棵嵌套的、互相链接的产物树**：

- **六层**（业务背景 → 概念 → 组织 → 架构 → 设计取舍 → 代码细节）对整个项目走一遍
- **每一层的模块**，只要大到需要单独理解，就**自己再走一遍六层**
- 产物不是一篇 HTML，是**一组**，节点之间有 `needs`（前置依赖）关系
- 读者沿树走，每篇开头都写清楚「读这篇之前需要知道什么」

```callout
tone: red
icon: ⚠
text: |
  **现状的问题不是「内容不够」，是「按生成时间切，不按理解路径切」。**

  三篇（架构 / 文件地图 / 核心抽象）里，**概念讲了 3 遍、组织讲了 3 遍、架构讲了 2 遍**，
  而「代码细节」这一层几乎空白。读者每看完一篇就发现缺一块，于是回头补。
```

## 五、机制

### 1. 计划文件 `plans/<topic>.yaml`

树的**唯一真相源**。驱动首页渲染，也让人能审阅。

```yaml
topic: sql-builder-v2
title: 理解 sql_builder_v2
source: sources/gitlab/sql_builder_v2 @ 2c500b2

nodes:
  - id: concepts
    title: 概念：这个库在解决什么问题
    layer: 概念                 # 概念 / 组织 / 架构 / 模块
    needs: []                   # 前置节点的 id
    artifact: sql-builder-v2-concepts   # 对应的笔记 slug
    status: planned             # planned / drafted / done
    children: []
```

### 2. `meta.json` 增加一个字段

```json
{
  "tree": { "topic": "sql-builder-v2", "id": "core-rule" }
}
```

`layer` / `needs` / `title` 都从 plan 文件取 —— **不在两处维护**。

### 3. 页面上渲染「前置」区块

每篇正文之前自动插入（来自 plan 的 `needs`，标题也从 plan 取）：

```
读这篇之前，你需要先知道：
  ← core 篇：packages/core 由什么组成、怎么工作
```

### 4. 首页改成**树视图**

```
▾ 理解 sql_builder_v2                       12 / 12 篇
    ├─ ① 概念篇          ✅
    ├─ ② 组织篇          ✅
    ├─ ③ 架构篇          ✅
    ├─ ④ core 篇         ⬜ 待产出
    │   ├─ ⑤ Rule[] 篇   ⬜ 待产出
    │   ├─ ⑥ 方言篇      ⬜ 待产出
    │   └─ ⑦ 时间表达式篇 ⬜ 待产出
    └─ ⑧ crowd 篇        ⬜ 待产出
        ├─ ⑨ entrepot 篇 ⬜ 待产出
        └─ ⑩ combi 篇    ⬜ 待产出
```

**读者一眼知道：我在哪、下一步看什么、哪些还没写。**

没挂到树上的笔记（Flink、JOIN 等）显示在「未归类」区，不影响。

## 八、树是边写边长的

```callout
tone: red
icon: ⚠
quote: true
text: |
  ==**第一次读代码，只看得见「结构」，看不见「哪个分支信息量大」。**==

  信息量是在**写的时候**才暴露的。一开始定了 10 篇，
  写到第 6 篇时发现两处「塞不下」—— 树长到了 12 篇。
```

| 长出来的节点 | 什么时候发现的 | 为什么够格 |
|---|---|---|
| **⑧ 数组条件的两种路径** | 写 ⑥ 方言篇时 | 它不是「方言层的一个方法」，是一条独立的架构裂缝：跨 core+crowd、3 个 DB 分支、两套机制并存、带 MySql 时代的历史痕迹 |
| **⑫ 条件树重写** | 回头审时 | **架构篇的主干图漏了一整个步骤** —— `initMajorListSqlGen` 的第一行就是 `treeSimplifier()`，然后才翻译。所以它是主干的一部分，会被别的节点引用 |

**判断标准**（不是「它挺大」，而是）：

> **它能被别的节点 `needs` 吗？**
> 能 → 独立成篇；不能且只有父节点用它 → 就是父节点的一节。

**还处理了一个循环依赖**：架构篇要提优化器，优化器住在 crowd 里，而 crowd `needs` 架构篇 —— 会成环。
解法是**架构篇只「提一句 + 链接」，不加 `needs`**（和它对待 ⑤ Rule[] 篇一样）。

### 反过来：该并的要并

`code-map` 里有一节「推荐的看代码顺序」（6 步阅读指南），收尾检查时发现新树没覆盖它。
但按判据它**不能被别人 `needs`**（它是起点指南，不是谁的前置）——
所以**并入组织篇**，而不是开新篇。
